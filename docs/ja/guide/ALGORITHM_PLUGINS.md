# アルゴリズムプラグイン

> **単一バージョンと共有ランタイムの構成**：現在のバインドモディファイアは、規範となる facade `version = 1` を使います（`rig.scaffold` は `v1` と `v2` を残します）。`:algorithms:binding` は `pluginPackages` タスクで、単一の共有 `shared/runtime.jar`（入り口は `ExpressionWorker`）と、各型の軽い `<slug>/plugin.json` マニフェストを出力します。型とマニフェストの数は、`algorithms/binding/build.gradle.kts` の宣言と、生成された `index.txt` を基準にします。ホストは、コマンドとファイル要約で常駐ワーカープロセスをプールし、入力とコンテキストのリソースハッシュをキャッシュします。外部プラグインは、任意の言語で `protocol: 1` のワーカープロセスプロトコルを実装し続けられます。

プリセットの各モディファイアは、アルゴリズムインターフェースを通して評価します。組み込みアルゴリズムはアプリのプロセス内で実行します。外部アルゴリズムは常駐ワーカープロセスで、Python、Kotlin、Rust、C、C++、C# を使えます。インストールパッケージは複数のアルゴリズムを含められます。

組み込みアルゴリズムは、型とアルゴリズム改訂番号ごとにプラグインカタログへ入り、各項目は独立して起動と停止ができます。スイング、シミュレーション、物理、モーション、表情スイッチ、眉と目の透かし髪、肌のクリップ、バインド構造は、独立した Kotlin 実装の入り口を持ちます。新しいインスタンスは `builtin.*` のパッケージ身元、完全なバージョン、内容要約を記録します。すでに独立してパッケージしたアルゴリズムは完全なパッケージを覆い、残りの入り口はバイトコード要約を使います。要約が一致しないときは利用不可と表示し、自動では置き換えません。履歴プロジェクトの中で、プラグイン参照のない組み込みインスタンスは、元のアルゴリズム改訂のまま読み、開くときに履歴を書き換えません。`id=builtin,digest=builtin` は、旧インターフェースの全体の起動と停止のための互換入り口にすぎません。

外部パッケージは `dependencies` で、`plugin_list` が返す組み込みパッケージの ID とバージョンを参照できます。インストール時に同じ内容要約を固定し、組み込み項目が停止している、または対応するバージョンがないときは、依存パッケージも利用できません。`builtin` の全体身元は残します。`builtin.*` のインストールパッケージは、パッケージ ID とアルゴリズム改訂に一致する安定した型の別名を宣言し、履歴の組み込みアルゴリズムを回復できるようにする必要があります。起動と停止の状態は環境設定に保存し、評価はメモリスナップショットから読み、項目ごとにシステム環境設定へはアクセスしません。

アプリには、独立して実行できるモディファイアパッケージが同梱されます。完全な型の範囲は、ビルドが生成した組み込みパッケージのインデックスを基準にします。履歴インスタンスは、固定した改訂のまま再生し続けます。一部の推奨プリセットは今も v1 を使い、ホストが生成したテンプレートから結果を取り出します。比較的新しいバージョンの一部も、ホストが生成した前置の動き、または局所的な前後投影を受け取ります。独立して実行できるパッケージと、モデル全体のテンプレート呼び出しがないことは、それだけでは、元のソース入力の境界の移行が完了した証明にはなりません。

Gradle の `processResources` は、`bundledAlgorithm` のリソース宣言から組み込みパッケージのインデックスを生成します。組み込みパッケージを追加するときは、ビルドでそのタスクとリソースディレクトリを宣言し、アプリは生成したインデックスからパッケージマニフェストを読みます。既存パッケージのマニフェストとペイロードは、今までどおり元のバイトで要約を計算します。

眉をフィットすると他のメッシュの座標枠が変わる両目の素材では、現代のプリセットを新規作成するとき、頭、目、眉のために互換バージョンを一緒に選びます。フィットした眉、眉の形、眉とまぶたの連動、まばたきに眉を伴うもの、跳ね返りは、共有枠組みでまとめて評価します。笑い目、見開き、視線、感情、ハイライト、余震、虹彩の押しつぶしにも対応するバージョンがあります。まぶたのフェードアウトは v3 を引き継ぎます。保存済みのインスタンスは、プロジェクト内で固定したアルゴリズム改訂とパッケージ要約で再生します。

このうち物理グループの実装は `:algorithms:physics` へ移っています。`PendulumAlgorithm` は共通の評価インターフェースを直接実装し、設定の解析、物理グループの変換、出力の衝突検査は、すべてそのモジュールで完了します。アルゴリズムが使うのは `algorithm-api` だけで、アプリの登録入り口は呼び出しを委譲するだけです。通常の物理の書き出しと他のジェネレーターは、同じ変換実装を再利用します。別に `algorithm-worker` がワーカープロセスの入り口を提供し、`./gradlew :algorithms:physics:pluginPackage` が `algorithms/physics/build/plugin` に独立したインストールディレクトリ（`plugin.json` と、依存を運ぶ `algorithm.jar`）を生成し、`plugin_install` へ渡せます。パッケージ ID は `builtin.70687973696373.v1`、入り口はその名前空間の `/pendulum`、`aliases: ["physics"]` はプロジェクト内の型、アルゴリズム改訂、出力 ID を残します。

アプリは、物理グループ、モーション、スイング、ベイクしたシミュレーション、表情スイッチ、眉と目の透かし髪、肌のクリップ、バインド構造の完全なインストールパッケージを持ち、残します。新しいインスタンスはパッケージ全体の内容要約を固定します。現在のパッケージと完全に一致するときはプロセス内で実行します。旧パッケージの参照は、対応する内容がインストールされているときだけワーカープロセスで実行し、現在の実装へは戻りません。旧バージョンのインストールパッケージはアンインストールと再インストールができます。現在のアプリ同梱バージョンは、起動と停止だけができます。移行より前に、入り口のバイトコード要約だけを記録した開発期の参照は書き換えられず、新しいパッケージで置き換えることもできません。元の内容が見つからないときは、今までどおり利用不可を報告します。

モーションの実装は `:algorithms:motion` へ移っています。パッケージ ID は `builtin.6d6f74696f6e.v1`、入り口は `/clip`、安定した別名は `motion` です。`MotionData` は元の形式のデータモデル、JSON の読み書き、カーブ変換を提供し、アプリのエディタと独立したワーカープロセスがこの実装を共有します。モジュールは再生セッション、UI、Umamo に依存しません。ビルドコマンドは `./gradlew :algorithms:motion:pluginPackage`、出力ディレクトリは `algorithms/motion/build/plugin` です。

スイングの実装は `:algorithms:swing` にあります。パッケージ ID は `builtin.7377696e67.v1`、入り口は `/sway`、安定した別名は `swing` です。メッシュの包み、キーフォームの評価、スイングの物理グループは、すべてアルゴリズムモジュールで完了し、プロジェクトや履歴のインターフェースは呼びません。このモジュールは GPL の Umamo エンジンと、`:umamo-ir-bridge` の汎用 IR 変換橋を使い、GPL アルゴリズムに属するため、MIT の API／形式モジュールとしては配布できません。Cubism の専有 SDK は含みません。ビルドコマンドは `./gradlew :algorithms:swing:pluginPackage` です。

ベイクしたシミュレーションの評価は `:algorithms:simulation` にあります。パッケージ ID は `builtin.73696d756c6174696f6e.v1`、入り口は `/baked`、安定した別名は `simulation` です。入力には元のベイク結果と、捕捉した自動ウェイトが含まれます。プラグインはベイクと上流入力が一致するかを検査し、そのあとウェイト、モードのキーフォーム、物理グループを書き戻します。既存の作者ウェイトが優先し、欠けた、または期限切れのベイクから欠けた結果を生成することは許されません。数値のベイクは今までどおり元の手順で実行し、この移行はソルバを変えません。このモジュールも GPL エンジンに依存します。ビルドコマンドは `./gradlew :algorithms:simulation:pluginPackage` です。

アルゴリズムマニフェストは `derivedOutputs` を宣言でき、もとからの決定的なオブジェクト名を残すために使います。各規則は `kind`、`localName`、`prefix`、`suffixes`（既定 `[""]`）、`numbered`（既定 `false`）を含みます。ホストが受け付けるのは `prefix + instance.outputId(localName) + suffix` だけです。`numbered` をオンにすると、さらに `_2` から `_10000` までの規範的な十進接尾辞を許します。規則はオブジェクトの種類をまたげず、宣言した書き込み範囲を超えられず、任意の正規表現は受け付けません。スイングは `Warp_Swing_` と `PhysicsSwing_` の規則を使い、元のプロジェクトのオブジェクト ID を保ちます。

フィットした顔 v2、フィットした目 v3、フィットした口 v2 は、追加パネルでバージョンを選んで使えます。フィットした顔 v2 は、共有する中立スキャフォールド v2 の完全な対象集合を要求します。フィットした目 v3 とフィットした口 v2 は、それぞれ移行できる目のスキャフォールドと、中立の口のスキャフォールドを要求します。フィットした目 v4 は、共有スキャフォールド v2 の完全な対象集合と、フィットした顔 v1 の組み合わせにも対応します。その中に旧版の体があるときは v1 を使う必要があります。v4 は目が必要とする頭の座標枠を調整し、作者のジオメトリまたは参照を残せないときは評価を拒否します。ソース素材からプリセット付きのプロジェクトを新規作成するとき、完全な共有スキャフォールド v2 を使い、プラグインが使えるなら、旧版の体 v2 を採用します。バージョンを指定して旧版の体 v2 を手動で選ぶこともできます。それはソースの測定から体の動きと頭の俯仰を計算し、ソースデータを持つスキャフォールドを要求します。共有スキャフォールドは完全な対象集合を使う必要があります。口の縁取り v2 は、同じ静的スキャフォールド上の旧版の口 v2 を必要とし、その前に他の活動中のバインドがあってはなりません。虹彩の押しつぶし v2 もバージョンを選んで使え、フィットした目と、ソース測定と一致する虹彩トポロジを必要とします。虹彩の押しつぶし v3 はフィットした頭の回転に対応し、目の余震 v3 を含む独立したまぶたの列のあとに続けることもできます。v4 は、ハイライト v3 が頭の回転のキャリアへ書いた変形を残すことにも対応します。虹彩トポロジをすでに変更しているときは v1 を使ってください。プロジェクトは安定した型と、選んだインストールパッケージを保存し、後続のモディファイアは元の型で前置項目を探せます。

旧版の目 v2 は明示的に選べ、v2 のソーススキャフォールドの完全な対象集合を要求します。旧版スタイルのプリセットは、編集しておらず、既定の調整で、通常の頭の回転を使うソース素材では v2 を選びます。フィットした頭の回転、またはすでに変更した目のトポロジのときは v1 を選んでください。

フィットした眉 v2 は、追加パネルでバージョンを選んで使えます。共有 v2 スキャフォールドを要求し、検証済みの体、頭の回転、目の前置バージョンに対応します。推奨プリセットはフィットした眉 v1 を使います。

フィットした眉 v3 は、同じ共有スキャフォールド上のフィットした顔 v3 のあとで選べます。フィットした目 v2 と v5 を組み合わせた完全な推奨モデルと対照済みで、そのうち v2 の組み合わせは、インストール後のフィットした眉の JVM 評価も検証しています。フィットした口の互換経路は、今もフィットした眉のテンプレートを要求することがあります。

旧版の眉 v2 は明示的に選べ、ソースデータを持つ共有スキャフォールドと、互換の通常の頭の回転またはフィットした頭の回転に対応します。眉の親分岐を付け替えたとき、またはフィットしたキーフォームがメッシュの予算を超えるときは v1 を使います。

旧版の顔 v2 も明示的に選べます。ソースの測定から頭の回転を計算し、ソースデータを持つ共有スキャフォールド v2 と完全な対象集合を要求し、同じスキャフォールドを使う旧版の体 v1 または v2 の前置に対応します。新しいソースプロジェクトが旧版プリセットを選ぶとき、ソースデータと対象の要求を満たし、同梱パッケージが使えるなら v2 を使います。組み込みプリセットへ切り替えると、同じ規則で新しいスタックを作ります。保存済みのインスタンスは、固定したバージョンで再生します。

被写界深度の頭の回転 v2 は、追加パネルでバージョンを選んで使えます。ソースデータを持つ共有スキャフォールド v2 と、旧版の顔 v1 または v2 が必要で、体 v1 または v2 は任意です。フィットした顔と被写界深度の頭の回転は重ねられません。現在の v2 は殻の向きを覆います。

フィットした顔 v3 は、旧版の体 v1 または v2 のあとで、バージョンを選んで使えます。体の俯仰の調整を引き継ぎ、唯一の前置の体のバインドと、フィットした顔が同じ完全な共有 v2 スキャフォールドを使うことを要求します。現代のプリセットは今もフィットした顔 v1 を使い、既存のフィットした目の経路はフィットした顔のテンプレートを構築し続けます。

フィットした目 v5 は、完全な共有 v2 スキャフォールド、旧版の体 v1 または v2、フィットした顔 v1 または v3 を必要とします。追加の計画は、補う必要がある前置バインドを列挙します。現代のプリセットは今もフィットした目 v2 を使い、一部の任意のまぶたアルゴリズムもこのバージョンに依存します。

目の見開き v2 はバージョンを選んで使えます。ソースの目の測定と、フィットした目のバインドから、目を開くキーフォームと透明度を広げます。ハイライト、まばたきに眉を伴うもの、またはまぶたの結合がすでに前にあるときは、v1 を使い続けてください。

目の見開き v3 は、フィットした頭の回転のあとで、まぶたの変形を再計算することもできます。閉眼線が必要とする頭の回転デフォーマを含みます。既存のデフォーマを外す、他のメッシュと共有するデフォーマを再計算する、またはソース測定が現在のバインドを再現できないときは、今も v1 を選べます。

眉の形 v2 はバージョンを選んで使え、共有スキャフォールド v2 と互換のフィットした眉を必要とします。v3 はフィットした眉 v3、フィットした目 v5 に対応し、虹彩の押しつぶし v3 のあとに続けられます。先に眉の形を追加し、そのあと他の眉の動きを追加してください。眉の高さのキーフォーム、トポロジ、または親の枠を変更しているときは v1 を使い続けられます。

眉の弾み v2 は、跳ね返りのブレンドシェイプと物理を追加します。共有スキャフォールド v2、フィットした眉 v1 または v2 を必要とし、フィットした目と組むときはフィットした目 v2 を必要とします。眉のジオメトリやキーフォームを編集したとき、または前にまぶたや眉の連動がすでにあるときは v1 を使ってください。

眉の弾み v3 は、互換のまばたきに眉を伴うものと、眉とまぶたの連動のあとで、バージョンを選んで使えます。前置の眉の枠とデフォーマを残し、跳ね返りの形状と物理を追加します。v4 はフィットした眉 v3、フィットした目 v5、まばたきに眉を伴うもの v3、眉とまぶたの連動 v4 に対応します。ソースの枠を変更した、または前置デフォーマを再現できないときは v1 を使ってください。

まばたきに眉を伴うもの v2 は、眉の動きをまばたき、見開き、笑い目と連動させ、共有スキャフォールド v2 と、元の高さおよび角度のキーフォームを保つ互換のフィットした眉を必要とします。v3 はフィットした眉 v3、フィットした目 v5、推奨順で前に並ぶ独立したまぶたアルゴリズムに対応します。眉のトポロジ、またはこれらのキーフォームを編集したときは v1 を使ってください。

眉とまぶたの連動 v2 から v4 は、バージョンを選んで使えます。v2 と v3 は共有スキャフォールド v2、フィットした目 v2、互換のフィットした眉を必要とします。v3 はフィットした頭の回転と前置の視線連動に対応し、既存のデフォーマ ID を残します。v4 はさらにフィットした目 v5、フィットした眉 v3 に対応し、TML プリセットで前置の視線 v3 と目の感情の組み合わせ順を検証済みです。目のトポロジまたは親の枠を変更した、前に頬とまぶたの連動または重複する眉とまぶたの連動がある、独立した深度の向きを使うときは v1 を使ってください。

笑い目 v2 は共有スキャフォールド v2 とフィットした目 v2 を必要とします。元のまぶたに笑い目のキーフォームを追加します。まぶたのジオメトリを編集した、または前にまぶたや眉の連動がすでにあるときは v1 を使ってください。

笑い目 v3 はフィットした目 v5 にも対応し、フィットした頭の回転のあとでまぶたの変形を再計算し、そのあと見開き v3 を続けられます。既存のデフォーマを外す、他のメッシュと共有するデフォーマを再計算する、またはソース測定が現在のバインドを再現できないときは、今も v1 を選べます。

目の余震 v2 は、まぶたの跳ね返りと対応する物理グループを追加し、共有スキャフォールド v2 と互換のフィットした目を必要とします。v3 はフィットした目 v5、前置の視線 v3、目の感情に対応し、再構築できるまぶたのキャリア ID を残します。前に眉とまぶた、または口と頬の連動がある、またはまぶたのソース枠やキーフォームを編集したときは v1 を使ってください。

視線がまぶたを連れる v2 は、ソースのまぶたから共有と単眼の視線連動を生成し、共有スキャフォールド v2 と互換のフィットした目を必要とします。v3 はフィットした頭の回転のあとのフィットした目 v5 に対応し、笑い目と見開き v3 のあとに続けられ、ソース測定から再構築できる頭の回転キャリアを残します。ソースのまぶたジオメトリを編集した、または前に余震、眉とまぶた、口と頬の連動があるときは v1 を使ってください。

目の感情 v2 は、フィットした怒り、哀しみ、細目の変形を追加し、共有スキャフォールド v2 と互換のフィットした目を必要とします。v3 はフィットした目 v5 と視線 v3 のあとに続けられ、再構築できるキャリア ID を残します。まぶたのジオメトリを編集した、前置の眉とまぶたまたは口と頬の連動がある、キャリアを外す、または共有キャリアを変更する必要があるときは v1 を使ってください。

陰鬱の表情 v3 は、共有 v2 スキャフォールドの上で、顔と鼻のためにそのデフォーマを再構築できます。色の軸を追加する前に、元の肌メッシュと前置バインドを照合します。v3 は明示的な選択が必要です。ソース座標枠を編集した、陰鬱の表情がすでにある、他のパーツがキーフォームの予算を超えるときは v1 を使います。

陰鬱の表情 v4（`expression.gloom@4`）は、明示的に選ぶ必要があるソース入力の候補で、プリセットの既定は変えません。範囲は、同じ側の単眼、眉、まつ毛がそろった口全体の開口素材に限り、独立した閉口図や層に分けた唇の図は含みません。肌は未編集で未分割のプリセットソースメッシュである必要があります。必須の前置は、共有スキャフォールド v2、body/legacy v2、フィットした顔 v3、フィットした目 v5、フィットした眉 v4、フィットした口 v3、縁取り v7、母音 v6、キャプチャ v5、顎 v7、口の弾性 v8、頬の赤み v1 で、同じソース連鎖に属します。頬の赤みを暗に上げることはありません。

アダプタは、元の測定、トポロジ、UV、ソース座標枠、マテリアルのメタデータ、正確な前置の身元だけを捕捉します。独立したワーカープロセスが、顔、鼻、耳、細部の動きと感情チャンネルを再構築し、まず実際のメッシュとキャリアと前状態を照合し、そのあと本物の通常軸を証人として、範囲を限った変更を提出します。入力には、ホストが生成した前後投影、肌のキーフォーム、テンプレート、生成コールバックは含みません。目のモジュールが所有するハイライトの透明度は変わりません。

対象を絞ったテストは、左右と口腔の細部の 6 組み合わせ、実際の色の変化、インストールしたワーカープロセス、キャッシュを切った接頭の再生を覆います。回復した縁取りラスターは、実際の縁取り提供者の出力身元だけを根拠に、ソース測定から除外します。元の作者の層は残り、未知の派生素材は拒否します。検証済みの接頭を適用したあと、ソース捕捉の値とリソースはバイト単位で一致します。

任意の前置が受け付けるのは、明示的に列挙したバージョンと依存関係だけで、詳細は移行台帳を参照してください。前置の首、腕、衣装のモジュールは、今も候補の範囲外です。必須の前置が欠けている、または互換でないときは、捕捉前に一時停止します。非対応の素材、変更した肌／枠／チャンネル、身元が一致しない提供者、変更待ちのキャリアの外来の子孫は拒否されます。既存の既定、履歴の実装、パッケージロックは変わりません。この狭い範囲の候補は、プリセット連鎖全体が移行済みであることを表しません。

裾 v2 はバージョンを選んで使え、胴の分岐の下にぶら下がる上衣と下衣に当てはまります。共有ソース座標枠を使い、互換プリセットでは元の裾のメッシュ、物理、シミュレーションのバインドを残します。

腕のスイング v2 はバージョンを選んで使え、共有スキャフォールド v2 の元の吊り腕の枠と、同じスキャフォールド上の体と顔のバインドを必要とします。v3 は前置のフィットバインドに従って吊り腕の枠を再計算し、対になる手袋の親枠が変わったときにスイングのキーフォームを移します。腕を付け替えた、中立の格子点を編集した、既存の作者キーフォームを移す必要があるときは v1 を使ってください。

リボンとペンダント v2 はバージョンを選んで使え、同じソース座標枠を共有する対象に当てはまります。元の吊り点に従ってスイングと物理を生成し、互換プリセットのシミュレーションベイクを残します。ソース座標枠をまたぐときは v1 を使います。

獣耳、尻尾、翼 v2 はバージョンを選んで使え、同じソース座標枠を共有する対象に当てはまります。アクセサリはそれぞれのソースの吊り点に沿ってスイングし、獣耳はまばたきの揺れを残し、スケルトンを有効にしたときは尻尾と翼をスケルトンが担います。

## インストールとアンインストール

バインド構造は、アルゴリズム改訂 1／2 の独立パッケージを提供します。`./gradlew :algorithms:binding:pluginScaffold1 :algorithms:binding:pluginScaffold2` を実行し、出力は `algorithms/binding/build/plugin-scaffold-1` と `plugin-scaffold-2` です。パッケージ ID は `builtin.7269672e73636166666f6c64.v1`／`.v2`、入り口はパッケージ名前空間の `/structure`、安定した別名は `rig.scaffold` です。2 つの改訂は、それぞれ履歴の対象ごとの階層と、共有階層の意味を固定します。

陰鬱の表情 v5（`expression.gloom@5`）は、口の弾性 v10 と頬の赤み v5 のあとの明示的な組み合わせの候補で、他の必須バージョンとソース素材の制限は v4 と同じです。変更していない `skinReplayV1` を再利用して、実際の頬の赤みの前状態と陰鬱の後状態を再構築し、実際の前置の頬の赤みの強さを読み、目が所有するハイライトの透明度を残し、頬の赤み v5 と同じ完全なパッケージ、能力、ソース接頭の検証を実行します。独立したパッケージのタスクは `:algorithms:binding:pluginGloomV5` です。合同リンク 15 件の対象を絞ったテストはすべて通過し、スキップはありません。実際の既定および混合段階の等価、左右と 3 種の口腔の組み合わせ、独立した強さの調整、実際の密な頬の赤みのキャリア配分、インストールした JVM の出力、実際の接頭の適用、キャッシュを切った再生、アーカイブを開き直すこと、ソース入力／提供者の保護を覆います。照合した 444 個の履歴パッケージファイルは変わりません。直列のルートプロジェクト全量回帰は合計 1298 件で、1133 件が通過、165 件が条件付きスキップ、失敗またはエラーはゼロです。既存インスタンスはバージョンとパッケージロックを残し、既定のバージョン選択と旧プロジェクトの変換はこの連鎖を上げず、その場でのバージョンアップ画面も追加していません。

素材が欠けている検証は、次の実際のソースサンプルと、その初期化で得た前置連鎖に限ります。

- 表情の細部レイヤーが欠けている：左右とも受け付ける。
- 目のハイライトだけが欠けている：左側は受け付ける。右側は実際に旧い口と頬の連動 v1 を選び、口の弾性 v10 に拒否される。
- まぶたの線とまぶたの影の細部が欠けている：左右とも受け付ける。
- 目のハイライト、まぶたの線、まぶたの影の細部が同時に欠けている：左右とも受け付ける。
- 表情の細部、目のハイライト、まぶたの線／影、鼻が同時にない最小サンプル：左右とも実際に旧い口と頬の連動 v1 を選び、口の弾性 v10 に拒否される。

これらは実際のソース頭部枠の適合境界であり、これをもって実際の口と頬の連動の提供者を上げることはできず、任意の欠けたレイヤーの素材が対応されることにもなりません。下顔のジオメトリが凍結した顎 v7 の配分予算を超えるときは、今も弾性 v10 の前に拒否します。密な頬の赤みの結果は、私的な下顔キャリアの動的接続を証明しません。

現在の `scaffold/5` 契約は、対象の身元、ソースレイヤー、中立座標の測定、未バインドのメッシュトポロジ、アトラス UV を捕捉します。プラグインはこれに従ってパーツツリー、デフォーマ、メッシュの取り付け、既定キーフォームを計算します。`scaffold/1` から `scaffold/4` の履歴パッケージは、元の入力を読み続け、当時必要だったテンプレートリソースを含みます。

環境設定の「アルゴリズムプラグイン」を開き、ZIP を選ぶか、ローカルディレクトリ、HTTPS／SSH／git:// の Git アドレスを入力します。Git アドレスにはブランチ、タグ、完全なコミット番号を付けられます。インストーラは実際のコミットを記録します。リポジトリのルートは、ビルド済みのプラグインパッケージである必要があり、サブモジュールは取得せず、インストールスクリプトは実行せず、ユーザーのマシンでソースをコンパイルしません。

パッケージは、現在のプラットフォームのプログラムと、必要な実行環境を運ぶ必要があります。Kotlin の JAR はアプリの JVM を使います。Python と .NET のプラグインは、ユーザーが別に開発環境を入れていると仮定できません。プラグインはローカルコードを実行し、プロセスの隔離は安全なサンドボックスではありません。

インストーラはプロトコル、プラットフォーム、設定 schema、ファイル一覧、SHA-256 を検証してから、原子的に公開します。同じ内容を繰り返しインストールしても複製は生まれません。サードパーティパッケージの同じバージョンは、異なる内容で上書きできません。組み込みパッケージの更新は、同じバージョンの異なる digest の共存を許します。アーカイブは元の内容を残し、新しいインスタンスは既定で現在の同梱パッケージだけを選び、履歴インスタンスは今までどおり完全な参照で解決します。更新は旧パッケージを自動では削除しません。

現在の同梱パッケージと正確に一致するインスタンスは、プロセス内で実行し続けます。インストール済みの履歴の完全パッケージは、その元のペイロードで実行します。互換読み取りが受け付けるのは既知の旧ホスト指紋だけで、`builtin.*` の ID だけを根拠に未知の digest を現在の実装へ置き換えません。より早い動的バイトコードの指紋がアーカイブされておらず識別できないときは、パッケージ不足を明確に報告します。プロジェクトを開いても、この種の参照は書き換えません。

アンインストールは、プロジェクト内のインスタンス、パラメータ、上書きを残します。欠けている、または停止したプラグインは「プラグインがありません」と表示します。欠けたアルゴリズムの実際の出力が未知であるため、その接尾は保守的に一時停止します。影響を受けたプロジェクトは書き出せず、同じパッケージを再インストールしたあと再評価すると回復します。組み込みパッケージは停止と回復ができ、アプリ同梱のファイルは削除できません。プラグイン状態の変化は、開いているプロジェクトをバックグラウンドで更新し、履歴ノードは追加しません。

環境設定はインストールディレクトリと有効状態を記録し、既定のディレクトリはユーザーディレクトリの `.psd2live/plugins` です。プロジェクト、履歴、書き出したプリセット JSON はパッケージ参照だけを保存し、実行可能コードは埋め込みません。

## MCP

GUI と MCP は同じ管理サービスを使います。`plugin_list` は、パッケージの身元、有効状態、アルゴリズム一覧、設定 schema、既定値、依存、対象の型、読み書きの範囲を返します。同梱パッケージは、自身のマニフェストの依存、衝突、読み書きの宣言を使います。組み込みアルゴリズムの設定 schema は、ホストの検証契約に由来します。`problems` は読み込めないパッケージを列挙します。

```json
{"source":"D:/plugins/example-python.zip"}
```

以上が `plugin_install` の業務要求です。`plugin_inspect` は同じ入力を受け付け、検査するだけでインストールしません。Git の要求には `ref` を追加できます。

`plugin_enable`、`plugin_disable`、`plugin_uninstall` は、`plugin_list` が返す `id` と `digest` を使います。組み込み項目も、一覧が返す独立した身元を使います。旧い 2 つの値がどちらも `builtin` である呼び出しは、全体の起動と停止にだけ互換で、アンインストールには使いません。一覧以外はすべてバックグラウンドタスクを返し、`job_wait`／`job_get` で終態を照会します。開いているプロジェクトは不要です。

外部モディファイアの追加と編集は、今までどおり `modifier_plan`、`modifier_add`、`modifier_update` などの既存操作を使います。設定はプラグインが提供する schema で検証します。計画の結果はパッケージ参照を固定し、確定のあいだにプラグインが変わると旧い候補を拒否します。すべての公開操作は、厳密な結果 schema を宣言します。

## プラグインを書く

JVM 契約は、独立した `:algorithm-api` モジュールに分かれ、アプリとプラグインが同じ宣言を共有します。依存するのは中立の `:format-model` と JSON シリアライズライブラリだけで、アプリ、Umamo、Compose、プロジェクト、履歴には依存しません。`./gradlew :algorithm-api:build` は、バージョン `1.7.0` の API JAR とソース JAR を生成します。

`ModifierAlgorithmPlugin.evaluate(input, instance, checkpoint)` は、上流の `RigIR`、不変の `RigModifierInstance`、キャンセル検査関数を受け取り、候補の `RigIR` を返します。実装は入力配列をその場で変更できません。長いループは `checkpoint` を呼ぶ必要があり、例外はそのままホストへ返します。オブジェクトの身元は `instance.outputId(localName)` を使い、既存の別名と互換です。ホストは今までどおり、出力の検証、依存、上書き、CAS、履歴の確定を担います。API は同時に、対象参照、固定したパッケージ参照、マニフェスト、バージョン範囲、依存の宣言を公開します。元の JSON フィールド、シリアライズ型の名前、オブジェクト ID のエンコードは変わりません。

API JAR 自体は、インストールできるアルゴリズムパッケージではありません。独立してコンパイルできる契約は、組み込み実装がアプリから出たことではありません。組み込みパッケージの読み込みと履歴実装の保持は、今までどおり上の移行状態に従って扱います。外部の 6 言語のワーカープロセスは、以下のバージョン付きプロトコルを使い続けます。

### JVM モデル結果の適合

`algorithm-worker` は、`ModifierAlgorithmPlugin` を常駐 JVM プロセスに入れられます。入り口は `AlgorithmWorker.run(mapOf((type to version) to implementation))` を呼び、アプリ、エディタ、プロジェクトに依存する必要はありません。標準出力はプロトコル応答にだけ使います。要求の `invocation` は完全なインスタンス情報（永続化した出力別名を含む）を提供し、もとからの `instance`、`config`、`targets` フィールドは他の言語と互換のままです。

ホストが `capabilities` で `rig_objects` を宣言したあと、ワーカープロセスは `commands` の代わりに `objects` を返せます。両者は同時に現れられません。`objects` は `changed`、`removed`、`mesh_order`、`deformer_order` をちょうど含まなければなりません。要求の入力を基線とし、変わった `frame`、`mesh:<id>`、`deformer:<id>` のリソース参照と、削除されたキーだけを列挙します。リソースは `RigIrObjects` のバイナリ形式を使い、参照は `sha256` と `bytes` を含みます。単一リソースの上限は 64 MiB、合計の上限は 512 MiB です。ホストは要約、大きさ、オブジェクト型、ID を検証し、パスをリソース参照としては受け付けません。

ホストはオブジェクトの差分を完全な上流入力へマージするため、読み書きの宣言で切り落とした無関係な内容は失われません。そのあと構造、数値、宣言した書き込み型、出力 ID を検査し、候補、上書き、トランザクションの手順へ入ります。プロセス内とワーカープロセスは同じアルゴリズム実装を呼びます。ホストは、物理の設定コマンドを通してそのアルゴリズムを再実行しません。バイナリ結果の適合は、他の言語がすでに持つコマンド出力プロトコルを変えません。

6 言語のソースとパッケージツールは [examples/plugins](../../../examples/plugins/README.md) を参照してください。パッケージルートの `plugin.json` が宣言するもの：

- `protocol: 1` または `protocol: 2`、パッケージの `id`、`version`、`name`。
- `commands`：`windows-x86_64` などのプラットフォーム識別子をキーとする引数配列。JVM パッケージは `jvm: ["$JAVA", "-jar", "worker.jar"]` を使います。シェルは通しません。
- `files`：各有効ペイロードの相対パスと SHA-256。範囲外のパス、シンボリックリンク、列挙していないファイルは禁止します。
- `algorithms`：アルゴリズム型は `包ID/` で始まらなければなりません。アルゴリズムのバージョン、名前、対象、依存、相互排他、読み書きの範囲、組み合わせ可能な書き込み型、`configSchema`、`defaults` を宣言します。
- 任意の `parameters` は、共有する標準パラメータの `id/name/min/max/default` を宣言します。定義は上流の同名パラメータと互換である必要があります。他の新しいオブジェクトは、インスタンスが属する ID を使います。

`protocol` はワーカープロセスの通信プロトコルのバージョンです。`plugin.json` のルートの `version` はインストールパッケージの依存を解決するために使い、アルゴリズム一覧の整数 `version` は型とともに実行可能な入り口を識別します。たとえば `mouth.outline@4` は縁取りアルゴリズムの第 4 版です。プロジェクトは、アルゴリズムの入り口と、インストールパッケージのバージョン、内容要約、依存ロックを同時に固定します。パッケージを上げたあと、既存インスタンスは保存時に固定した入り口を使い続けます。

`protocol: 1` は、要求と応答がそれぞれ 1 行の UTF-8 JSON を占めます。バイナリリソースは `PSD2LIVE_PLUGIN_RESOURCES` ディレクトリ下の SHA-256 ファイル参照です（`{"sha256": "...", "bytes": N}`）。`protocol: 2`（ネイティブバイナリと多言語の高性能プラグイン向け。Rust/C++/Zig/Go/Python など）は、一時ファイルがなく、SHA-256 のディスク I/O がゼロの、バイナリフレームの標準入出力を使います。`[u32le headerLen][UTF-8 JSON header][u32le blobCount]([u32le keyLen][UTF-8 key][u32le dataLen][bytes])*`。バイナリ参照はインラインキー `{"inline": "<key>", "bytes": N}` に変わり、ホストはプロセス起動時に環境変数 `PSD2LIVE_PLUGIN_PROTOCOL=2` でワーカープロセスへ知らせます。どちらのプロトコルでも、標準出力はプロトコル転送にだけ使い、ログは標準エラーへ書きます。要求は `protocol/id/method/type/version/instance/config/targets` を含みます。応答は `protocol/id` をエコーし、`commands`、`objects`、`changes`、または `error` を返します。同じワーカープロセスは要求を直列に処理し、障害またはタイムアウトのあとプロセスを再構築します。実行中の要求をキャンセルするとプロセスを終了し、その部分的な結果は確定しません。キューに入った要求は独立してキャンセルでき、実行中の他の要求は中断しません。応答を待っているあいだもキャンセルを検査します。

モデル入力は、宣言した読み書きコンポーネントで切り詰めます。未知の範囲または `*` は、保守的に完全な入力を使います。`changed` と `removed` はオブジェクトインデックスを同期し、`reset` は新しいセッションを表します。`frame`、`mesh:<id>`、`deformer:<id>` の値はリソース要約で、リソースディレクトリは要求と `PSD2LIVE_PLUGIN_RESOURCES` が提供します。リソースは `RigIrObjects` のバージョン付きの正確なバイナリ形式を使います。`mesh_order` と `deformer_order` は順序を残します。

後続の要求は、変わっていないメッシュとデフォーマのバイナリリソースを再利用します。新しいオブジェクトは先にエンコードし、そのあと内容ハッシュで送るかどうかを判断します。

可搬ビュー `meshes` は、対象メッシュの ID、透明度、位置／UV バッファの参照を提供します。`parameters` は、読み取りを宣言済みのパラメータを提供します。浮動小数バッファの形式はリトルエンディアンの `f32le` で、ファイル名は SHA-256 と等しくなります。戻りコマンドの浮動小数配列も、この参照で表せます。ホストは要約と有限な数値を検証したあと展開します。

戻りコマンドが対応するもの：

- `mesh_opacity`：対象メッシュの `id` と、範囲 0〜1 の `value`。
- `physics`、`motion`：`config` は対応する組み込みモディファイアの設定形式を使い、出力 ID はホストが管理します。
- 編集プリミティブ：`structure`、`set`、`parameter_keys`、`delete`、`canvas_geometry`、`canvas_topology`、`canvas_create_warp`、`canvas_create_rotation`、`canvas_create_glue`、`canvas_glue_edit`、`path_put`、`path_delete`。作者の編集記録の形式を引き継ぎます。これらは隔離した候補の中でだけ実行し、履歴へ直接は書きません。

新しいオブジェクト ID は `modifier:<实例ID>:<局部名称的UTF-8十六进制>` です。ホストは実際の書き込み範囲、共有パラメータ、依存、上書き、衝突を検証します。プラグインはドキュメント、履歴、GUI を直接操作してはなりません。

## 性能の境界

アルゴリズムの生成、worker の通信、同期ベイクの計時は、捕捉したリビジョンからオフスクリーン GPU の読み戻しまで、およびモデルを有効化した捕捉からウィンドウ GPU の完了までとは別の指標です。後の 2 つの開発ツール、モード、除外範囲は[開発ツール](DEVELOPMENT.md#開発ツール)を参照してください。それらを足して、完全な編集遅延とすることはできません。

組み込みアルゴリズムは直接呼び出し、プロセスをまたぐシリアライズのコストは担いません。外部プラグインはプロセスを再利用し、内容アドレスでバッファを転送し、入力を増分で同期します。作者の基礎入力、バインドの中間テンプレート、依存を宣言できるアルゴリズム結果は、それぞれキャッシュします。フォルダの調整はアルゴリズム評価を起こしません。

この回の受け入れが検査するのは、独立したアルゴリズム生成、出力の等価、履歴の再生です。性能の最適化は移行の完了後に行います。診断ツールは、初回と繰り返しの生成時間を記録し続け、同期ベイクの時間を別に列挙します。

一部の組み込みバインドは、今も生成テンプレートから結果を取り出します。隣り合う組み込みアルゴリズムの宣言した読み書き範囲が重ならず、依存が満たされているとき、ホストは変更を並列に計算できます。ホストはスタック順に、実際の読み取りと書き込みの前置条件を再確認してから結果をマージします。他のアルゴリズムは順に評価し続けます。初回と繰り返しの生成は、それぞれ計時します。

## バージョンと依存関係

3 つのバージョン階層は独立しています。`protocol` は通信プロトコルのバージョンです。パッケージの `version` は `主.次.修订` のバージョンです。アルゴリズムの `version` は、永続化済みの整数改訂番号です。アルゴリズムの整数番号は互換を残し、実行言語を替えても番号を振り直しません。パッケージバージョンは `1.2.3-rc.1+build.7` に対応します。ビルド印は前後の比較に参加せず、完全なパッケージ内容は今までどおり要約で区別します。初期のパッケージの整数バージョンは `N.0.0` として比較します。新しいパッケージは完全なバージョン番号を使ってください。

パッケージの `dependencies` はコードの前置条件を宣言し、`conflicts` は同時に有効にできないパッケージバージョンを宣言します。これらはアルゴリズムの `requires` とは異なります。後者は、スタックに同じ対象のアルゴリズム結果がすでにあることを要求し、別のパッケージをインストールまたは起動しません。

```json
{
  "dependencies": [
    {"id": "geometry-core", "version": {"minimum": "1.2.0", "maximum": "2.0.0"}}
  ],
  "conflicts": [
    {"id": "other-cloth", "version": {"exact": "1.0.0"}}
  ]
}
```

- `minimum` は境界を含み、`maximum` は境界を含みません。`exact` は範囲と組み合わせられません。`version` を省略すると任意のバージョンです。プレリリースバージョンは数字／テキストの区間で並べ、プレリリースを暗に除外することはありません。
- インストール時は、範囲を満たす最も高い有効バージョンを選び、完全な推移的依存を固定します。前置の不足、循環、衝突はインストール／有効化を拒否し、依存を自動ではダウンロードせず、他のプラグインも閉じません。
- 衝突検査は双方向で、一方が宣言すれば有効になります。異なるバージョンは共存できますが、明示的な衝突は有効化を止めます。
- ホストはインストールの依存ロックを保存します。プロジェクトのプラグイン参照は `dependencyDigests`（`包ID@版本` → 内容要約）を保存します。あとから更新バージョンをインストールしても、旧インスタンスの依存は置き換わりません。
- 前置項目を無効／アンインストールするとワーカープロセスが止まり、下流は残って利用不可になります。元の内容を回復すると再び利用できます。同じパッケージを再インストールしても解決先の依存が異なるときは、旧プロジェクトの参照は利用不可のままで、黙って上げることはできません。
- `plugin_list` と `plugin_inspect` は `available/issues/dependencies/conflicts/resolved_dependencies` を返します。`enabled` はユーザーのスイッチを表すだけで、`available` の代わりにはなりません。環境設定パネルは、利用できない具体的な理由も同時に表示します。

依存関係は、プラグインをまたぐ関数呼び出しではありません。アルゴリズムの協調は、上流のモデル内容とアルゴリズムの `requires` で完了します。要求の中の `dependencies` は、固定したパッケージの身元を提供し、プロジェクトオブジェクトや他のワーカープロセスのハンドルは公開しません。

## 下層の能力とモジュールの境界

`:algorithms:binding`、`:algorithms:swing`、`:algorithms:simulation` は、GPL モジュール `:umamo-ir-bridge` の `io.github.psd2live.bridge.PuppetIr` を共有し、`:targets:cubism` を通して汎用の変換能力を得ることはありません。橋が依存するのは `:umamo` と `:format-model` だけです。対象のダウングレード、コンパイル、書き出しは、今までどおり書き出し先に属します。MIT の `:algorithm-api`、`:format-model`、`:format-compile` は、この GPL 実装に依存しません。

| 層 | 責任 |
| --- | --- |
| `ModifierAlgorithmPlugin.kt` | シリアライズできるパッケージ、アルゴリズム、対象、パラメータ、バージョン関係の契約 |
| `ModifierPluginDependencies.kt` | バージョン比較、範囲の一致、依存グラフ、衝突の診断 |
| `ModifierPluginStore.kt` | 検証、原子的なインストール、依存ロック、停止、アンインストール |
| `ModifierPluginWorkers.kt` | 常駐プロセス、キャンセル／タイムアウト、増分入力、バイナリリソース |
| `ModifierPluginOutput.kt` | 候補モデルで下層コマンドを実行し、実際の書き込み範囲を検証する |
| `RigModifierEvaluator.kt` | スタックの意味、共有パラメータ、上書き、寄与、書き込みの衝突、結果キャッシュ |
| アプリケーション層 | GUI／MCP の操作、バックグラウンドタスク、CAS、履歴の確定 |

要求の中の `capabilities` は、ホストが対応するコマンドを列挙します。下層の操作には次が含まれます。

| 目的 | コマンド | 主な書き込み範囲 |
| --- | --- | --- |
| パラメータの作成、範囲、フォルダ、関係、オブジェクトの親子 | `structure` | `parameter/hierarchy/relations/mesh/deformer/part`。実際の変化に従って宣言する |
| キーフォームのジオメトリとチャンネル、コピーと削除 | `set/copy/delete/parameter_keys` | `mesh/deformer/parameter/glue` |
| メッシュのジオメトリ、トポロジ、デフォーマの作成 | `canvas_geometry/canvas_topology/canvas_create_warp/canvas_create_rotation/warp` | `mesh/deformer/hierarchy/authoring` |
| Glue とパス | `canvas_create_glue/canvas_glue_edit/path_put/path_delete` | `glue/authoring` |
| 頂点ウェイトグループ | `vertex_group_put/vertex_group_delete` | `authoring` |
| 物理グループとモーション | `physics/motion` | `physics/motion` |
| 対象メッシュの透明度 | `mesh_opacity` | `mesh` |

`reads/writes` は `textures/canvas/advanced/hit_areas/rest_pose` にも対応し、`*` はモデル全体を表します。能力を宣言したことは、これらのデータを変更する専用コマンドがあることではありません。たとえば現在、外部プラグインがテクスチャリソースを直接作るコマンドは提供していません。細分フィールドを宣言していない入力は保守的なキャッシュを使い、その独立性は推論しません。

ウェイトコマンドの例（配列の長さはメッシュの頂点数と等しくなければならない。`bytes/count/format/sha256` 付きのバッファ参照も使える）：

```json
{"op":"vertex_group_put","target":"mesh:cloth","name":"Cloth weights","kind":"pin","weights":[0,0.5,1]}
```

キーフォームの例：

```json
{"op":"set","target":"mesh:cloth","key":{"ParamAngleX":30},"channels":{"opacity":0.8}}
```

パラメータの作成は、`structure.edits` の中の `action=create,kind=parameter,id,name,min,max,default,parent_id` を使います。共有パラメータは、アルゴリズムの `parameters` で互換の定義をあらかじめ宣言する必要があります。共有しない新しいオブジェクトは、インスタンスが属する決定的な ID を使います。コマンドの詳細フィールドは、対応する作者の編集プリミティブを引き継ぎ、ホストが同じ検証を実行します。モデル編集の不変条件を迂回することは許されません。

すべてのコマンドは、まず隔離した候補の中で順に実行します。出力を検証したあとで評価結果を返します。付随データ（ウェイト、パスなどの作者の内容）、テクスチャ、キャンバス、レンダリング階層も、実際の書き込み検査と衝突報告に参加します。パッケージが `mesh` だけを宣言して、コマンドで作者のウェイトを変更することはできません。プロセスの隔離は安全なサンドボックスを提供せず、プラグインは今までどおりユーザーがインストールしたローカルの実行可能コードです。


### オーサード入力のコンテキスト

API 1.2.0 は、任意の `ContextualModifierAlgorithmPlugin` を追加し、独立した `ModifierAlgorithmContext` を受け取ります。`values` は構造化したオーサード入力を保存し、`resources` は論理名で不変のバイナリデータを保存します。ユーザー設定には書かず、プロジェクト、履歴、ローカルパスは公開しません。元のプラグインインターフェースは互換のままです。

ホストは `author_context_v1` 能力を宣言します。要求の任意の `context` は、`version: 1`、メタデータのリソース参照 `values`、論理名からリソース参照への写像 `resources` を含みます。参照は SHA-256 と長さで検証します。メタデータの上限は 1 MiB、単一リソースの上限は 64 MiB、最大 10000 項目、合計 512 MiB です。同じ内容のペイロードはディスクへ 1 回だけ落ちます。非対応のバージョンと壊れたリソースは評価を拒否します。省略時のコンテキストは空です。

ホストは、定義した `authorContext` で入力を捕捉します。接頭キャッシュとコンポーネント依存キャッシュは、どちらもコンテキストの内容を比較し、リソースが変わると再評価します。このインターフェースと転送能力は実装済みです。残りのバインドルゴリズムのレイヤーの意味と、元画像の適合は移行中で、まだすべてがこの入り口で実行されるわけではありません。

表情スイッチの適用計算は、`:algorithms:binding` の `ExpressionAlgorithm` へ移り、`ContextualModifierAlgorithmPlugin` を実装します。スイッチの透明度カーブを直接構築し、作者のチャンネル残差をマージし、連鎖物理の表情入力を補います。アプリ、履歴、プロジェクトのサービスは呼びません。コンテキスト `schema: "expression/1"` の `layers` はパラメータ名と任意のスイッチ番号を保存し、`meshes` はメッシュからレイヤーへの写像を保存し、`opacity` はソースの透明度を保存し、`chain_owners` は前置連鎖のモディファイア身元を保存します。バイナリリソース `parameters` は `RigIrBinary` で、解決済みのパラメータ定義だけを含む空のモデルをエンコードします。`./gradlew :algorithms:binding:pluginPackage` は `algorithms/binding/build/plugin` を生成し、パッケージ ID は `builtin.65787072657373696f6e2e746f67676c6573.v1`、入り口は `/toggles`、別名 `expression.toggles` を残します。現在のパッケージはプロセス内で実行し、履歴パッケージはワーカープロセスを通して同じコンテキストを受け取ります。ホストは、既知の組み込み別名とアルゴリズム改訂にだけオーサード入力のアダプタをバインドし、前置依存、相互排他、組み合わせ可能な書き込み宣言を照合します。動的な共有パラメータは、ホストが捕捉したオーサード入力から承認し、新しいパラメータは承認した定義と完全に同じである必要があります。ワーカープロセスが許可リストを自分で広げることはできません。別名と規範の入り口は同じ適合を使います。標準パラメータ名が衝突するときのパラメータ解決は、互換の生成経路を残します。

`MoodChannels` は、バインドモジュールの独立した色計算の核として、完全な生成と局所テンプレートが共有します。頬の赤み／影を既存のバインドへ追加するとき、通常の経路は変換前のソースジオメトリを再利用し、パラメータと色／透明度のチャンネルだけを更新し、そのあと元の Cubism 構造変換を実行します。すでに折りたたんだキーフォームの結果は再利用せず、色の軸が増えたために向きのデフォーマを落とすことを避けます。標準パラメータの名前が衝突するとき、再利用できる前置入力がないときは、完全な生成経路を残します。段階キャッシュを切っても完全な生成を通り、等価の検証に使います。頬の赤み v2 と陰鬱の表情 v2／v3 はパッケージ済みで、局所的な色の変更を直接生成します。陰鬱の表情 v3 は、互換の顔と鼻のデフォーマも再構築できます。

`BlendShapeLowering` は、独立した Cubism のブレンドシェイプからキーフォーム／担うデフォーマへの変換を提供し、GPL のバインドモジュールにあります。呼び出し側は名前の方針とキャンセル検査関数を渡し、アプリのローカライズ、プロジェクト、履歴のサービスには依存しません。アプリの適合は元の名前と決定的なオブジェクト ID を残します。新しい色の軸はキーフォームの予算を変えることがあるため、局所的な色の計算は、今も変換前の入力からこの手順を実行し直す必要があります。この下層能力は、残りのバインドモディファイアが独立した入り口への移行を完了したことと同じではありません。

`MoodBinding` は、変換前のバインドモデル、捕捉済みのパラメータ定義／順序、メッシュごとの色のウェイトを受け取り、色のパラメータ、パラメータツリー、生成チャンネル、Cubism 変換を完成させ、同時に変換前の入力と最終モデルを返します。評価を繰り返すと、所属する色のトラックを置き換え、パラメータは累積しません。宣言していないメッシュは元の内容を残します。このインターフェースはプロジェクトオブジェクトや編集プレビューを受け取らず、作者の上書きは今までどおりホストがマージします。互換経路は、このインターフェースを通して、モデルをダウングレードする前に色を計算します。

`BindingComparison` は、候補の生存期間の中で、オブジェクトの身元に従ってメッシュ／デフォーマの規範表現をキャッシュします。局所マスクの変化を判断するときは、対象メッシュと指定した祖先だけを比較し、モデル全体は変換しません。ジオメトリ配列の内容、チャンネルのキーフォーム、ブレンドシェイプ、他のメッシュ属性は、今も比較に参加します。キャッシュは可変の入力をまたいで再利用できません。

`SeeThroughBinding` は、捕捉済みの覆いの候補、設定、命名関数、ID 割り当て関数を受け取り、眉と目の複製、前髪の逆マスク、描画順、透明度の継承を独立して計算します。プレビューの更新が受け取るのは前後のモデルと、複製／窓の写像だけで、プロジェクトや画面の状態は読みません。アプリケーション層の `SeeThroughLayers` は、ソース画像のピクセル覆いの識別と、設定／ローカライズの適合を残します。型と呼び出しインターフェースは互換のままです。2 種類のモディファイアは、どちらも `SeeThroughAlgorithm` のコンテキスト入り口で評価します。`schema: "see-through/1"` は、覆いの候補 `candidates`、目／眉の種別 `eyes`、前置の透かし髪インスタンス `earlier_owners`、描画間隔 `draw_order_step`、逆マスクの能力 `inverted_masks`、単一の `{meshName}` を含むローカライズ名のテンプレート `name_pattern` を含みます。ピクセル覆いの候補は、ホストが捕捉したソース画像に従って計算し、共有します。プラグインは現在のモデル順で候補と前髪をフィルタし、生成順を残します。設定 `values.opacity` は、もとからの 0〜100 の範囲を保ちます。`pluginEyeSeeThrough`／`pluginBrowSeeThrough` の Gradle タスクは `algorithms/binding/build/plugin-eye`／`plugin-brow` を生成し、それぞれ `eye.see-through`／`brow.see-through` の別名を残し、入り口の接尾辞は `/visibility` です。パッケージはインストール、回復でき、常駐ワーカープロセスが実行します。現在の組み込みバージョンはプロセス内で直接呼びます。

`ModelIdRemap` は、GPL バインドモジュールが公開するモデル参照の書き換えツールです。キーフォームの軸、ブレンドシェイプの制限、親／パーツ、マスク、Glue、パラメータツリーとリンク、パス、頂点グループ、描画ツリーを覆います。呼び出し側が提供した写像だけを適用し、新しい身元を割り当てたり、ホストの衝突検査を迂回したりはしません。ホストは今までどおり、インスタンスが派生する ID と書き込み権限を担います。写像と無関係なモデルの区画とメッシュは元の参照を残し、読み取り専用の入力キャッシュを壊さないようにします。アプリケーション層の `RigIdRemap` は互換の別名です。

バインドモジュールは `GeometryResidual`、`MeshBlendResidual`、`WarpBlendResidual` を提供し、それぞれキーフォームのジオメトリ、メッシュのブレンドシェイプ、デフォーマのブレンドシェイプを、作者の座標系で三者マージします。`BindingVertices` は、捕捉済みの頂点インデックス／重心の対応に従って x/y の値を渡します。入力は読み取り専用のモデルと頂点の対応で、ループはキャンセル検査を受け付け、出力はジオメトリメッシュ／チャンネルまたはブレンドシェイプです。ソースプロジェクト、履歴、画面は読まず、結果も確定しません。インスタンスの上書きの帰属、衝突の判定、原子的な確定は、今までどおりホストが担います。アプリ内の旧い名前は互換の別名として残します。

`BindingFrames` は `carriedToParent`、`pointsInParent`、`reparent` を提供し、静的メッシュ、キーフォーム、ブレンドシェイプを対象の親空間へ変換し、共有する祖先より下の作者分岐だけを反転することにも対応します。通常の編集のバインドし直しと、モディファイアのマージは、この実装を共有します。中立ポーズを戻せないとき、または親の循環が現れたときは結果を拒否します。独立したインターフェースはキャンセル検査を受け付け、モディファイアの経路はホストの検査関数を渡します。モデルの身元は変更せず、プロジェクト状態も公開しません。

`BindingMerge.apply` は、独立したバインド結果のマージ入り口です。入力は現在の読み取り専用モデル、インスタンス、候補が限定する `BindingMerge.Source` で、出力は新しいモデルです。`Source` は前後の生成投影、固定 ID の写像、静的座標の投影、パラメータ互換の決定、頂点の対応を提供し、リアルタイムのプロジェクト／UI を読んだり、編集を確定したりしてはなりません。主手順はモジュール内で、担うデフォーマの追加と削除、パラメータツリー／リンク、キーフォーム、ブレンドシェイプ、マスクのマージを完成させます。`BindingAxes` は軸のマージと、有限なキーフォーム座標の列挙を統一します。このインターフェースはプロセス内の計算契約であり、完成した外部プラグインの転送プロトコルではありません。現在の製品適合は、今も生成テンプレートとメッシュの対応を提供し、物理の結果、口の初期ポーズ、トランザクションはホストが補います。残りのアルゴリズムは、今もテンプレート生成をそれぞれの計算へ置き換え、リソース化した入力へ接続する必要があります。

`SkinClipAlgorithm` は、IR の上で直接、肌の重ねに顔のマスクを追加し、メッシュを変換したり完全なバインドを生成したりはしません。`schema: "skin-clip/1"` は、順序のある顔オブジェクトと境界 `faces`、ソース画像の切り抜きがない候補の重ねの境界 `overlays`、前置の同類インスタンスがすでに担当する対象 `already_active` を捕捉します。インスタンスの対象が実際の範囲を決めます。アルゴリズムは元の 85% 被覆判定を引き継ぎ、同じマスクがすでにあるものは残し、衝突する作者のマスク／反転状態を拒否し、他のフィールドとオブジェクトは変わりません。ソース画像の切り抜き、すでに有効なインスタンス、対象の複製の写像は、ホストが捕捉します。`./gradlew :algorithms:binding:pluginSkinClip` は `algorithms/binding/build/plugin-skin` を生成し、`face.skin-clip` の別名を残し、入り口の接尾辞は `/clip` です。この入り口のパラメータ宣言と評価は、もうバインドテンプレートを呼びません。後続の他のアルゴリズムは、今も自身の入力のために切り抜き付きのテンプレートを生成することがあります。

下流のバインド要求が、肌の切り抜きで終わるソーステンプレートであるとき、前のテンプレートを再利用して同じ切り抜きプラグインを呼び、オブジェクトの身元とマスク状態だけを渡し、ジオメトリは再構築しません。切り抜きの差分は、同時に遅延して、ダウングレード変換前の入力へ合流します。他のマスクとチャンネルは元のままです。適用済みの接頭は、捕捉したソースの切り抜きデータを使い、取り除いた活動インスタンスはもう照会しません。段階キャッシュを切ると、完全な生成を等価検証の経路として残します。これは他のバインドモジュールのテンプレート構築をなくしたことにはなりません。

口の縁取りのソース素材の捕捉は、ソース分析、作者の分割／削除状態、縁取りの色／幅、メッシュ設定、言語でキャッシュします。動きのレシピ、バインドの強さ、調整値は、その素材キーに参加しません。バインドテンプレートは唇の線のラスターと付加アトラスを再利用し、後続の各モジュールが輪郭を取り出し、同じ画像をエンコードし直すことを避けます。段階キャッシュを切ったときは再計算します。このキャッシュは互換経路に奉仕します。独立してパッケージした口の縁取り v2 は、互換の静的な旧版の口に対して、縁取りを直接生成できます。

組み込みの履歴パッケージの捕捉入力契約は、実際の使用に従って検査します。依存、相互排他、または組み合わせ可能な書き込み宣言がホストの適合と一致しないときは、その正確なパッケージのパラメータ照会、入力捕捉、評価だけを拒否し、パッケージ ID／バージョンを報告します。このパッケージをインストールしただけでは、他のプロジェクトがアルゴリズムカタログを構築することを止めません。互換でないパッケージは、現在の組み込みアルゴリズムへ戻りません。

`MouthContour`、`MouthColumn`、`MouthStrokeMesh` は、縁取りの独立したジオメトリ核を提供します。x/y の頂点配列と三角形インデックスで境界を取り出し、等弧長で上下の唇をサンプリングし、交差する端点のパスと、角丸／端のキャップ付きの固定トポロジの帯状メッシュを構築します。呼び出し側は捕捉したジオメトリを提供し、製品の `MeshData`、プロジェクト、UI は渡しません。製品は薄い適合と型の別名を残します。ソース画像の意味、ピクセルのラスタライズ、アトラス、インスタンス出力のマージは、今も縁取りプラグインの入り口へ移行し続ける必要があります。これらのジオメトリ API 自体は結果を公開せず、プロジェクトオブジェクトの ID も割り当てません。

`MouthOutlineRaster` は、捕捉した唇の線の列、色、幅、座標変換関数を、RGBA、キャンバス位置、不透明ピクセル数へ直接変換します。`perimeterColor` は元の RGBA の外境界から縁取り色を選び、内部の細部や透明ピクセルの RGB は読みません。ラスタライズは元の AWT の三角形塗りと継ぎ目の線描きを引き継ぎ、キャンセル検査を受け付け、描画リソースの解放を保証します。製品が担うのはソースレイヤーの分類と出力レイヤーの包装だけです。この核は、今も独立してインストールできる完全な縁取りモディファイアではありません。

プラグインカタログのスナップショットとパッケージ依存の解決は、管理の改訂に従って再利用し、正確なパッケージ参照の解決結果を最大 256 個キャッシュします（欠けている参照を含む）。インストール、アンインストール、組み込みまたはユーザーパッケージの起動と停止のあと、次の照会はスナップショットを再構築して解決します。固定済みの依存内容は自動では上がりません。このキャッシュはファイル検証の結果をキャッシュせず、インストールと実行前の完全性検査の代わりにはなりません。段階の統計は、依存解決の回数とキャッシュヒット数を提供します。

プログラムは、同梱マニフェストから完全な組み込みプラグインカタログを読みます。プロジェクトの評価、または開いたプロジェクトの履歴があるバージョンを参照する、インストールした外部パッケージがある前置依存を固定する、またはワーカープロセスを起動する必要があるときだけ、プログラムは対応する実行可能ファイルをアーカイブします。アーカイブは、アプリを上げたあとこれらの正確なバージョンを回復するために使います。カタログを閲覧するだけではアーカイブへ書きません。プロジェクトの評価はアーカイブと並列にでき、候補はアーカイブの検証が終わってから返します。

インストール、カタログの回復、ワーカープロセス起動前のプラグインペイロードの SHA-256 検証は、64 KiB のストリームバッファを使います。ディレクトリを回復するときは、最大 4 つのインストールパッケージを同時に検証し、検証はすべてのバイトを読み、大きさの制限を残し、各ブロックのあいだでキャンセルを検査します。`plugin payload verification` は各検証の合計時間を記録し、`plugin load: installed catalog` と `plugin load: retain bundled packages` は、それぞれカタログ回復とアーカイブの実際の時間を記録します。

共有デフォーマ段階のキャッシュキーは、実際に読んだ強さ／調整、基礎アルゴリズムの選択、頭の向き、視線連動、腕のスイング、衣類／パーツの連鎖、髪の設定だけを残します。局所的な目の変形や、縁取りの色／幅などのメッシュ入力は、共有デフォーマ一式を無効にしません。ソースジオメトリ、アンカー、親の枠、ボーン、言語は、今も対応するキャッシュキーに参加します。これはバインドテンプレートの重複計算を減らし、これらのテンプレートがすべて独立したプラグイン評価へ置き換わったことにはなりません。

明確な体のレイヤー（上／下衣、手足、脚、首の装飾、首）のメッシュ段階は、目、眉、口の局所モジュールをもう入力にしません。胸の動き、首の追従、頭の深度の向き、基礎の選択、もとからのピクセル／メッシュ／親の枠の条件は残します。衣類の連鎖などが親を変えるときは、今もメッシュキーで無効になります。他のレイヤーは保守的な入力範囲を保ちます。

`BrowFit`／`BrowRig`／`BrowOptions` は、独立したバインドモジュールにあります。フィットの入り口は RGBA、サイズ、キャンバス位置、左右、頭の水平、座標写像を受け取り、眉の座標系と 17 点の中心線を出力します。動きの入り口は、眉の高さ／角度のキーフォーム、眉の形、まばたき／微笑の連動、跳ね返りのブレンドシェイプを生成し、キャンセル検査を受け付けます。共有の `Bounds`／`Side` もバインドモジュールにあり、製品の旧い名前は Kotlin の型別名として残り、レイヤーの適合は入力の捕捉だけを担います。アルゴリズムの式は変わりません。これはまだ眉の各モディファイアの完全なインストール可能入り口ではなく、インスタンスのマージとコンテキスト転送は今も接続する必要があります。

`HeadTurn`／`HeadShell`、`BustRig`、`ThinPlateSpline`、`BiharmonicField` は、独立した頭の深度の向き、胸の動き、点集合のフィット、平滑な変位場を提供します。インターフェースが受け取るのは数値、点集合／固定ノード、共有ジオメトリ型だけです。メッシュの動きは元のキーフォームとブレンドシェイプの定義を残し、反復求解と点ごとの出力はキャンセルに対応します。`ThinPlateSpline.solve` は、元のピボット消去付き実装を公開し、他のバインド核が再利用します。入力行列はその場では書き換えません。製品の元の型名は別名のままです。レイヤーの識別、インスタンスの組み合わせ、インストール可能な入り口は、後続の適合が完成させます。

`ThinPlateSpline.solveColumns` は、同じ正方行列の複数の右辺列を受け取り、ピボット消去は 1 回だけ実行します。薄板スプラインの X／Y フィットは、この入り口を共有します。各列は元の求解の演算順と特異なピボットの処理を保ち、行列と右辺の入力はどちらも書き換えず、キャンセル検査は消去の各ラウンドを覆います。

表情スイッチの捕捉アダプタは、すべての表情パラメータが左右の目の開閉または口の開閉であるとき、フィット後の標準範囲を直接照会し、パラメータ照会のために完全なメッシュとアトラスを生成しません。他の標準名は今も互換経路を通ります。生成後の Cubism ダウングレードがパラメータ型を変えることがあるためです。カスタム名は独立した表情カタログを使い続けます。これはホストの入力捕捉の最適化であり、他のバインドモディファイアの完全なテンプレート生成は、まだなくなっていません。

眉の元ピクセルのフィットは、共有段階キャッシュで再利用します。キーはソースレイヤー、アイラインの方向、顔の中心、座標空間を含み、眉の形、まばたき、跳ね返り、ハンドルの修正は含みません。修正は元のフィットのあとで適用し、動きの出力は各インスタンスのオプションを読み続けます。ソースレイヤーまたは測定座標を替えると、元のフィットは無効になります。

バインドテンプレートの切り詰めは、エンジンの `withParametersDeleted` でパラメータを一括削除し、渡した順で元のチャンネルの折りたたみ、静的値の昇格、ブレンドシェイプの除去の意味を残し、最後にレンダリングツリーを 1 回だけ派生します。一括入り口はパラメータ間のキャンセル検査に対応します。返すのはモデル候補だけで、プロジェクトや履歴は公開しません。

独立したバインドモジュールの `BindingProjection.retain` は、モデル、残すパラメータ集合、任意のソース画像ポーズの既定値を受け取り、残りのパラメータを外し、補間後の静的なメッシュ／デフォーマのジオメトリを残します。ホストはソース画像の既定値で、口の素材が開いた口のポーズにあることを宣言し、プラグイン核は製品のパラメータカタログに依存しません。残したパラメータは、この上書きの影響を受けません。入力はその場では変更せず、オブジェクトと軸の処理のあいだのキャンセル検査に対応します。テンプレートの切り詰めと静的投影は、どちらもこの入り口を使います。ソース画像の識別と完全なバインドテンプレートの生成は今もホストにあり、すべてのモディファイアのインストール可能入り口への移行は完了していません。

`ScaffoldBinding.apply` は、バインド構造の階層クローン、安定 ID、共有オブジェクトの衝突検査、親の枠の移行、組織ツリーのメンバー移動を担い、エンジンの編集プリミティブを直接使い、製品の JSON 編集ディスパッチャはもう呼びません。`CapturedSource` は、対象インデックスに従った静的テンプレートと通常の素材メッシュを受け取ります。ジオメトリ、UV、トポロジがどれも変わっていない元の素材だけに直接取り付けを使い、残りのメッシュは既定ポーズの逆座標変換で位置を残します。バージョン 1 の対象ごとの階層、バージョン 2 の共有階層、固定後の別名は互換のままです。この核はホストと、インストール可能なワーカープロセスが使っています。構造テンプレートのソース画像計算は、今もホストの捕捉アダプタが提供します。

目の動きの核 `EyeRig`、素材の観察データ `EyeFit`／`EyeArtwork`、内部の目の帯、まぶた、目を開くカーブのモデルは、独立したバインドモジュールに入ります。`rig/eye-opening.bin` はモジュールとともに配布します。ホストはレイヤーの識別とモディファイアの組み合わせを担い続け、今回の切り出しは目のモディファイアが完全に独立したことではありません。

### 構造化した変更のインターフェース（JVM API 1.3）

`ChangingModifierAlgorithmPlugin.changes` は `ModifierModelChanges` を返します。安定した ID を持つパラメータ、パーツ、デフォーマ、メッシュ、物理グループ、モーションは、`ModifierObjectChanges` で追加、更新、削除、再利用を明確にします。更新と削除は予期する旧オブジェクトを伴い、オブジェクトの身元は書き換えられません。他の単一値または順序のある関係は `ModifierFieldChange` を使い、「変更しない」と「null へ変える」を明確に区別します。関わらないフィールドとバッファは参照を残します。

ホストは適用前に `changeWrites` で実際の書き込み部分を検証し、そのあとオブジェクトの前置状態を検証します。繰り返し操作、既存 ID の追加、旧値の不一致は拒否します。適用が生むのは隔離した候補だけで、プロジェクトは確定しません。`contributions()` が現在報告するのはオブジェクト集合の操作で、単一値フィールドの完全なユーザー寄与は含みません。正式な寄与、参照検査、上書き、トランザクションは、今までどおり既存のホスト手順を通ります。物理グループのアルゴリズムは、この入り口を使っています。

外部ワーカープロセスは `model_changes_v1` 能力を交渉したあと、`changes` を直接返し、完全な出力を具現化してエンコードしません。その能力を宣言していないホストは、今までどおり元の `objects` 応答を得ます。`commands`、`objects`、`changes` は、ちょうど 1 種類だけが現れる必要があり、外層のプロトコルは今も 1 です。

`changes` は `schema`、`before`、`after`、`objects`、`fields` を厳密に含みます。`schema` は `model_changes_v1` です。`before`／`after` は SHA-256 とバイト数付きのバイナリリソース参照で、既存の RigIR バイナリバージョン 6 を使い、関わるオブジェクトとフィールドだけを置き、変わっていないメッシュは含みません。`objects` のキーは `parameters`、`parts`、`deformers`、`meshes`、`physicsGroups`、`clips` で、各値は `[新增数, 更新数, 删除数, 复用数]` の順に並びます。前置ペイロードの順は削除、再利用、更新の旧オブジェクトです。結果ペイロードの順は追加、更新の新しいオブジェクトです。オブジェクト操作の総数の上限は 10000、各ペイロードの上限は 64 MiB です。

`fields` は、置き換える単一値または関係フィールドを列挙します（`ModifierModelChanges` のフィールド名と一致）。列挙したフィールドは前後のペイロードから値を取り、明示的に null へ置き換えることを許します。JVM のエンコードとデコードの補助ライブラリは `AlgorithmChanges` です。ホストはバージョン、キー集合、個数、リソースの完全性、書き込み範囲、旧オブジェクトの前置条件を検証し、そのあと既存の完全な参照と出力の合法性検査を実行します。インストールパッケージのマニフェストの書き込み名は、`textures`、`glue` などの既存のカタログ語彙を引き継ぎます。

現在の物理パッケージは、プロセスをまたぐインストール、連続した評価、開き直し、アンインストール、再インストールの等価を実測済みです。他の言語は今も既存のコマンドプロトコルを使えます。6 言語が新しい変更ペイロードを 1 つずつ実装し受け入れを終えることは、まだ完了していません。ホストは完全な寄与比較を実行し続けます。読み取り専用の入力ビュー、ワーカープロセスの読み取り追跡、生成画像は、後述の対応する節を参照してください。

### ソース素材の捕捉（JVM API 1.4）

`ModifierSourceInputs` は `source_layers/1` で、生成前のソース素材を表し、生成テンプレートやホストのコールバックは含みません。`ModifierSourceLayer` は、安定したソース ID、意味上の tag／side／role、ソースキャンバスの左上、幅と高さ、観察境界、重心、不透明ピクセル数、RGBA のリソース名を保存します。`targets` は安定したモデル対象 ID をソース ID へ写します。画像は左上から始まり、行ごと、パディングなしの非プリマルチプライド RGBA8 です。素材のソース座標はピクセルで Y は下であり、観察境界と重心もその空間を使います。

`to_model` は、ソースキャンバスからモデルキャンバスへのシリアライズできるアフィン行列 `xx, xy, tx, yx, yy, ty` で、鏡映に対応し、特異行列は拒否します。親デフォーマ空間の変換ではありません。`raster(layer)` はキャッシュした読み取り専用ビューを提供し、`alpha(x,y)` は範囲外でゼロを返し、`rgba()` は独立した複製を返します。リソースには内容要約があり、既存の `author_context_v1` 転送を再利用できます。構築時に、重複するソース ID、対象参照、有限な座標、サイズ、RGBA の長さを検査します。各画像の上限は 64 MiB で、コンテキストの総量制限に従います。

`context()`／`from()` がこのスナップショットをエンコードおよびデコードします。ホストの `RigSourceCapture` は、すでにある素材と分類結果だけを捕捉します。目の輪郭フィットは、独立したバインドモジュールでこの契約を直接読むようになっています。ホストの適合は元の座標変換の呼び出しを残し、独立した消費者は `to_model` を使え、製品型は不要です。ここで置き換えるのは入力の境界とフィット実装の位置だけで、動きの設計は変えず、目のモディファイアのジオメトリ生成、組み合わせ、パッケージが完了したことにもなりません。

現在このスナップショットはラスターの観察入力であり、独立したマスクリソース、親空間のジオメトリビュー、上流能力のスナップショット、読み取り集合の追跡は含みません。これらは今も枠組みの後続作業に属します。ソースマスクの処理は、呼び出し前の素材がもとから持つ意味を保ち、このインターフェースが素材の連鎖全体を独立して表せると言いません。

### 読み取りオブジェクトによる評価（JVM API 1.5）

`ReadingModifierAlgorithmPlugin` の入り口は `ModifierEvaluationInput` を受け取り、`RigIR` 全体を直接は得られません。`parameter(id)`、`mesh(id)`、`deformer(id)`、`part(id)`、`physics(id)`、`motion(id)` は読んだオブジェクトを記録します。オブジェクトが見つからなくても観察を 1 回記録し、その後そのオブジェクトが現れるとキャッシュが無効になります。集合または他の全体フィールドを読むときは、そのフィールドの完全な値と順序を記録します。`context` は現在、完全なコンテキストで追跡します。

`parentsOfMesh(id)` は、直接の親から外へ向かうデフォーマの連鎖を返し、それぞれが宣言したローカル座標を残します。対象とすべての祖先を読み、循環、欠けた親、重複する身元を拒否します。ここでは異なる空間の点を自動では混ぜず、実際の座標の運搬は今もバインドモジュールの座標アルゴリズムを使います。

`reads()` は、その回の呼び出しの独立した読み取りスナップショットを与えます。ホストは新しい入り口について、インスタンス設定、プラグイン実装の身元、オーサードコンテキスト、読み取り集合、構造化した変更をキャッシュします。上流を変更したあと、読んだ値が今も一致し、出力の書き込み前置条件が今も満たされるときだけ再利用します。前置条件が変わったときは再計算します。再利用も、書き込み範囲の検査、上書き、寄与の衝突、トランザクションの手順を通ります。失敗またはキャンセルした候補は、成功したスナップショットを置き換えません。物理プラグインは現在、実際に参照するパラメータと物理設定だけを読み、すべてのジオメトリは読みません。

固定していないプラグインの実行失敗は、インスタンスごとに隔離します。失敗したインスタンスはジオメトリ、物理、オブジェクトの帰属を公開せず、その依存項目は一時停止し、独立したインスタンスは評価を続けます。初期化、編集、シミュレーションのベイクは同じ原則を使います。有効なドキュメントコマンドは、失敗状態を持つモディファイアスタックを確定でき、エラーはモディファイアパネルに表示し、設定を直すか再び有効にすると再試行できます。一括コマンドは今も完全な履歴ノードを 1 つだけ確定します。無効な要求、キャンセル、状態の衝突、固定済みの内容を守れない変更は、今も確定全体を拒否します。

プロセス内キャッシュは、インスタンス、アルゴリズム実装、捕捉したコンテキスト、実際に読んだ値を照合します。プロセスをまたぐ読み取り集合と再利用の条件は、後述の対応する節を参照してください。

### 明示的な上流能力（JVM API 1.6）

アルゴリズムマニフェストの `provides` は、提供する能力の別名を宣言します。`requires` はアルゴリズム型または能力の別名を参照でき、循環検査は両方を覆います。パッケージの意味バージョン依存は、今もマニフェストの `dependencies`／`conflicts` が扱い、インスタンスの実行前置関係と混同しません。

`ModifierAlgorithmContext.upstream` は、ホストが解決した前置能力を保存します。各 `ModifierUpstreamCapability` は、要求した能力名、実際のアルゴリズム型とアルゴリズムバージョン、前置インスタンス ID、対象参照、固定した設定、出力別名、分かっているときの完全なパッケージ参照（バージョン、内容要約、依存内容のロック）を含みます。ホストが選ぶのは、消費者の対象と明示的な provider の選択を満たす、先行／すでに固定した提供者だけです。旧い記録にパッケージ参照がないときは null のままにし、現在インストールされているバージョンを推測しません。接頭を適用するとこれらの身元情報を残し、固定した内容は下流の依存を満たし続けます。

`ModifierEvaluationInput.upstream`／`providers(capability)` は、これらの入力を読み取り集合とキャッシュ無効の判断に入れます。通常のソース素材 `values` の schema は変わらず、上流スナップショットは別に渡します。外部アルゴリズムは、マニフェストで `contextVersion: 2` を宣言して初めて上流入力を受け取り、旧いマニフェストの既定は 1 です。コンテキストに上流データがないときは v1 をエンコードし続け、上流データがあるときは v2 をエンコードし、元の `version`、`values`、`resources` の外に `upstream` のリソース参照を追加します。メタデータの上限は 1 MiB です。v2 の受信側も v1 を読み、旧パッケージに v2 を強制送信することはありません。

GUI/MCP が共有するプラグイン説明は、`context_version` と `provides` を追加し、結果 schema もこの 2 つのフィールドを同期して宣言します。検証済みなのは、能力の別名の解決、上流設定の変化によるキャッシュ無効、接頭の適用が能力を保つこと、パッケージ身元の保存と回復、v1/v2 コンテキストのエンコードとデコードです。外部の読み取り集合の返信と親空間の座標サービスは後述を参照してください。新しいアルゴリズムの完全な移行は、今も完了していません。

### 親空間の座標サービス

GPL バインドモジュールの `BindingCoordinates.forMesh(input, meshId, pose)` は、`ModifierEvaluationInput` から対象メッシュ、完全な祖先連鎖、祖先が実際に参照するパラメータを捕捉し、他のメッシュや無関係なデフォーマは変換しません。`pose` は明示的なパラメータ値で、与えていない値はパラメータの既定値を使います。現在の再生フレームは読みません。親の循環、欠けた親／パラメータ、無効な座標は失敗します。

`toCanvas`／`fromCanvas` のキャンバス座標はピクセルで Y は下です。サービス内部がランタイムのワールド座標の Y 反転を処理し、プラグインがもう一度自分で反転することはできません。逆変換は既存のランタイムソルバを使い、局所の種を渡せます。結果は対象点の 0.05 ピクセル以内へ再投影する必要があり、そうでなければ拒否します。点の配列は有限な XY の対である必要があり、入力は変更せず、変換の境界はキャンセルを検査します。

`BindingCoordinates.reparent` は `BindingFrames.carriedToParent` を再利用し、構造化したメッシュ変更を返します。既定位置、キーフォーム、ブレンドシェイプを運び、もとからの非ジオメトリ属性を残します。階層やプロジェクトの編集を自動では確定せず、依存の検証の代わりにもなりません。入れ子の非線形メッシュ／回転座標、Y 方向、実際の読み取り範囲、付け替えたあとの既定ポーズ／キーフォーム位置の検査は通過しています。このサービスは共有枠組みの能力であり、残りのいずれかのモディファイアの完全な移行としては数えません。

### 外部読み取りの追跡と再利用

ホストが `input_reads_v1` を宣言したあと、`ReadingModifierAlgorithmPlugin` を実装する JVM ワーカープロセスは、`changes` とともに `reads` を返せます。各項目は `{section, id?}` です。ID を省略するとフィールド全体を読んだことを表し、ID があると指定したオブジェクトを読んだことを表し、存在しないオブジェクトの観察も含みます。読み取り集合の上限は 10000 で、重複／無効な照会は拒否されます。API の `meshIds` はメッシュのメンバーと順序だけを観察し、そのジオメトリと表示チャンネルは読みません。プロセスをまたぐときは `input_mesh_ids_v1` 能力で交渉します。この能力に対応しないホストは変更結果を受け取り続けますが、この読み取りキーを含むキャッシュ観察は受け取りません。旧いホストは追加フィールドを受け取らず、旧いプラグインは今も `objects` またはコマンドを返せます。

ホストは、実際に送った入力の投影とコンテキストで観察値を再構築し、プラグインが提供する旧値は受け付けません。成功した結果は、パッケージのワーカープロセスとインスタンスごとに保存し、最大 128 項目です。アルゴリズムの記述、完全なインスタンス設定、コンテキスト、読んだ値が一致したあと、構造化した変更を現在の完全なモデルへ適用しようとします。書き込みの前置条件を満たさないときは再評価します。再利用も、出力の身元、参照、範囲、モデルの合法性の検査を実行します。飛ばすのは入力のバイナリシリアライズとワーカープロセス呼び出しだけです。

キャッシュは、まだ送っていない入力の改訂を進めません。次の実際の要求は、今までどおり前回送った状態に対して増分を生成します。ワーカープロセスが終了、停止、アンインストールしたとき、キャッシュで可用性検査を迂回することはできません。例外とキャンセルはそのワーカープロセスを捨てます。`plugin worker evaluations` と `plugin read cache hits` の計数は、専用の受け入れに使います。

実際の物理プラグインパッケージで検証済みです。入力を繰り返し、読んでいないパラメータを増やしてもワーカープロセスの評価回数は増えず、読んだパラメータを変更すると再評価し、最終モデルは一致します。開き直し、アンインストール、再インストールの手順は有効なままです。この結果は完全な生成の性能目標を達成した証明ではなく、他の 5 言語が新しい読み取りプロトコルへ接続済みであることにもなりません。

### 生成画像のホスト境界

API の `ModifierRasterOutput` は、生成した画像、メッシュ、編集可能なパスを記述します。`owner` は捕捉した元のメッシュと前置状態、`mesh` は追加したメッシュ、`layer` はソース画像のメタデータ、`pixels` は不変の RGBA8 内容リソース、`paths` は追加したメッシュだけを参照できます。キャンバス位置はソース画像のメタデータが記録し、ジオメトリは親のローカル座標を保ちます。既定の UV は素材のローカルピクセルで、ホストがアトラスを割り当てたあとでアトラス UV へ変換します。`PAGE` は、すでにアトラスへバインドした旧い出力との互換にだけ使い、素材ピクセルをそのモードと誤って印付けてはなりません。

ホストはまずバッチ全体を検査します。元のメッシュが変わっていないこと、出力の身元が衝突しないこと、画像のサイズとバイト数が一致すること、ジオメトリとパスの参照が有効なことです。各リソースは 64 MiB 以下、バッチ全体は 256 MiB 以下です。そのあと隔離した候補に専用のアトラスページ、ソース画像、tile の記録を追加し、新しいメッシュを元のメッシュの前に置き、パスと編集可能な原図も一緒に加えます。旧いページはレイアウトし直しません。失敗またはキャンセルは候補を公開せず、今までどおり外層の CAS と履歴トランザクションが確定します。

既存の口の縁取りリソースの付加は、この境界を使っており、元のピクセルとアトラスの振る舞いを残します。API 1.9 の `ModifierModelChanges.rasters` は、リソース出力と通常のオブジェクト変更を同じ候補に入れます。先に通常の変更を適用し、次にリソース出力の `owner` がその中間候補と一致することを照合し、最後にホストのリソース割り当て器を呼びます。そのため、同じ回で元のメッシュを変更するなら、`owner` は宣言した更新後のメッシュを使うべきです。ホストの割り当て器がないときに `apply` を直接呼ぶと、明確に失敗します。JVM ホストは `applyWithResources` を使います。リソースの書き込みは、保守的に `mesh`、`part`、`hierarchy`、`textures`、`authoring` の範囲を要求します。

ホストが `model_changes_v2` を交渉したあと、リソースを含む変更は、元の疎な変更の封筒に `rasters` 配列を追加します。リソースがないときは v1 を送り続けます。各項目は `model`、`pixels`、`uv_space` を厳密に含みます。前の 2 つは `{sha256, bytes}` のバイナリリソース参照で、後者は `RASTER_PIXELS`、または互換用の `PAGE` です。モデルペイロードは RigIR のバイナリ形式を使い、順に並べた owner／新しい mesh と、`authoring.sources` の中で唯一の `raster` 出所のレイヤーメタデータ、`authoring.paths` だけを含みます。他のモデルフィールドは空の既定値である必要があります。ピクセルは独立した RGBA8 リソースです。単一リソースの上限は 64 MiB、モデルとピクセルを合わせたバッチ転送の上限は 256 MiB、最大 10000 項目です。ハッシュの誤り、余分なフィールド、誤ったペイロード、交渉していない送信は、すべて失敗します。

JVM ワーカープロセスはこの結果を自動でエンコードします。他の言語は同じプロトコルを実装できますが、6 言語の画像結果の受け入れはまだ完了していません。読み取りキャッシュは、アトラスを割り当てていない変更を残し、ヒットのたびに現在のホスト候補と捕捉したアトラス設定が、リソースの検証と割り当てを実行します。フィットした口の縁取りの独立した JVM パッケージは、この契約を使っています。


### フィットした口のソース入力（移行中）

GPL アルゴリズムライブラリは `MouthSourceContext(fit, options, lineWidth)` を提供します。`encode()` は転送できる `ModifierAlgorithmContext` を返し、`decode(context).rig()` は製品モジュールを読み込まずに `MouthRig` を構築します。3 層のモデルデータはアルゴリズムパッケージとともに運び、製品が担うのはソース素材の分類と輪郭のサンプリングだけです。これはアルゴリズムの入力インターフェースであり、`mouth/fitted` のインストール入り口とホストの配線が完了したことにはなりません。

制御オブジェクトは `schema: "mouth_source/1"` と `measurement: <SHA-256>` を厳密に含みます。リソース表はこの要約をキーにします。リソースはビッグエンディアンの Float32 で、順は口の原点／座標軸／幅、上下の輪郭、任意の層に分けた枠、すべての口のオプション、任意の線幅です。輪郭はそれぞれ 49 個のスカラーです。層に分けた枠は、4 組の 65 個の二次元輪郭点、開口の列とその上下の境界、任意の局所パーツ境界、歯の測定を保存します。可変の列数は有界の Int32 を使い、任意の値とスイッチは 1 バイトの 0／1 を使います。オプションは、7 点の閉口カーブと、キャプチャ、母音、顎、奥行き、弾性、舌などのスイッチと数値を残します。

このペイロードが含むのはソース測定と設定だけで、評価済みのポーズや完全なバインドテンプレートは運びません。デコードは、未知の schema、欠けている／要約が一致しないリソース、有限でない数値、不正な長さ、末尾の余分なバイトを拒否します。座標は今もソースフィットのキャンバス空間と局所枠を使い、転送は浮動小数値を正規化も再サンプリングもしません。


候補プロトコル `mouth-fitted/1` は、scaffold がすでに捕捉した `source_meshes` リソースを参照でき、対象メッシュからソースメッシュへの写像を明示的に指定します。アルゴリズムが元の座標を使うのは、親、三角形インデックス、正規化した各中立座標の浮動小数のビット値がすべて一致するときだけです。作者が頂点を動かした、トポロジを変えた、付け替えたあとは、現在のジオメトリから再計算し、旧いリソースを当てはめることはできません。UV だけが変わっても、元の位置は無効になりません。アルゴリズムは型付きの変更を出力し、同じ回の評価のダウングレード前の候補をホストへ提供して、後続のバインドの組み合わせに使えます。ホストは今までどおり、作者の残差のマージとトランザクションの確定を担います。
