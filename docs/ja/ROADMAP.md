## 帰属と優先度

このページは今後の方向だけを記録し、日程は約束しません。コードに入口があること、完全な作業の流れが使えること、効果が受け入れを通ることは、別々に判断します。評価は [STATUS.md](STATUS.md) にだけ記録し、完了した項目はこのページから外します。[更新履歴](CHANGELOG.md) を参照してください。

今回の履歴パッケージの保持、分割参照、コールドとホットの結果、パーツ設定と折りたたみ、キャッシュの所有権、GPL 変換ブリッジ、コントローラーの試験導入は統合済みです。受け入れは [STATUS](STATUS.md#2026-11-14-アーキテクチャ最適化の受け入れ) を参照してください。このあとキャッシュ契約と、最初の正しいフレームの計測境界に沿って進めます。テクスチャの一括置き換えの中で、アトラスページ待ちを優先して分解し、完全な履歴を残したまま閉じる、開き直すコストを細かく分けます。既存のパッケージ依存の例外は項目ごとになくし、新しいキャッシュの試験導入は、完全な意味の差分と効果の計測を続けます。全量回帰の 1 分という目標も、引き続き照合が必要です。

**現在の製品の進め方：ユーザー定義プラグインの閉ループの使いやすさと実機受け入れ → 内蔵の「スタイル」（フィッティング）効果の最適化 → 自動シャドウなどの新しい効果。** ユーザーが Agent を通じて能力拡張を作る第 1 期の閉ループ（独立した足場、契約の発見、宣言的パラメータ、初回の追加、再起動なしで取り消しできるパッケージ交換、ワーカープロセスの世代隔離、保存して開き直す）は、コード実装と単体／エンドツーエンドのテストまで終わっています。使いやすさは、実際の Agent タスクとウィンドウの目視受け入れとともに閉じます。マシンをまたぐパッケージ共有は後で届けます（既存のプリコンパイル済みパッケージのインストール規則は残します）。全体の UX 再構成は別に評価します。内蔵効果は、開いてすぐ使えることと、プラグインを書く見本の両方に役立ちます。素材をまたいだ安定性を先に上げ、そのあと種類を広げます。

【次】**ユーザー定義プラグインの閉ループの実機受け入れと、マシンをまたぐ共有**：デスクトップウィンドウと実際の Agent ホストで、「内蔵リストにない新しい挙動」の人手による実測と使いやすさの仕上げを行い（[STATUS](STATUS.md) に記録）、マシンをまたぐパッケージ共有の能力を補います。

新しい能力は、Cubism との関係によって 3 段階に入れます。

| 帰属 | 意味 |
| --- | --- |
| p2lrt | Cubism はまったく対応せず、ベイクもできない。p2l ランタイム、ウェブ、Godot、ラスター書き出しでのみ有効 |
| 互換 | Cubism は対応しないが、キーフォーム、パラメータ、振り子、テクスチャへベイクできる。キーの間は近似になることがある |
| p2ledior | Cubism が完全に対応し損失がないか、編集過程にだけ影響するツール |

優先度は各項目の先頭に付けます。

- 【次】現在の段階で優先して実装する。同時には 5 件程度を超えない。
- 【その後】現在の段階のあと、または他の項目に依存する。
- 【将来】難度はあるが、将来実現したい。
- 【継続】機能の進行とともに少しずつ整え、単一の完了点がない項目。
- 【未定】やるかどうかがまだ決まっていない。

文末に「当面の予定なし」があります。各項目のあとの括弧は、帰属と作業の性質です。**深化**（既存のシステムに能力を足す）、**最適化**（同じアルゴリズムまたはプリセットの効果と性能）、**新規**（新しいシステム）、**再構成**（既存のシステムの構造を変える）。

## 段階

現在は、上のユーザープラグイン拡張の閉ループを先に完成させます。既存のパーツプラグインスタックを再利用し、汎用の変形モディファイアをすべて完成させることを前提にはしません。下の表は、エディター能力の依存グループを残したものであり、現在の製品優先度と競う日程ではありません。汎用モディファイアに依存する新しい効果は、必要な能力に合わせて進め、古いデフォーマの上に先に実装してから移すことは避けます。

| 段階 | 内容 |
| --- | --- |
| 独立した能力 | モディファイアと無関係な編集、アニメーション、書き出し機能。実際の需要に合わせて手配する |
| 段階の目標 | [モディファイアスタックの再構成](#モディファイアスタックの再構成)：着手前に、設計と段階計画を先に書く |
| 依存する能力 | モディファイアに依存する機能。ライティングとシャドウ、内部造形の三次元投影プリセット、髪のボリュームシェル、デフォーマ類、2D ジオメトリノードなど |

## モディファイアスタックの再構成

- [ ] 【次】**汎用の変形モディファイア**（互換 · 再構成）：既存のプリセット／パーツプラグインスタックの上で、Warp、Rotation などを、非破壊のモディファイア（Lattice、Bend、Twist、Wave など）としてさらに表現し、キーフォームへベイクする。ワークスペースのランタイム権威とパーツプラグインは既存の基盤である。汎用の変形層は、まだ段階設計が必要で、少なくとも次に答える。
  - モディファイアがドキュメント層とジェネレーター依存グラフのどこにあり、`RigEditOverlay` の再生順、生成結果の上書きとどう関係するか。
  - 既存の Warp / Rotation / 変形パス / ボーンスキニング / 内部造形を、どうモディファイアとして表現し、古いプロジェクトをどう互換再生するか。
  - Cubism への書き出しダウングレードのベイク精度と損失レポート。p2lrt はモディファイアをそのまま残すか。
  - 段階：最初の一群でどのモディファイアを作り、それらに依存するどの機能をどの期で解錠するか。
  - 自動生成されたパーツもモディファイアスタックに接続し、「適用」して普通のレイヤーにできる。たとえば上下のリップの縁取りは、適用後に口の形の設定との連動が切れ、直接描ける（[#54](https://github.com/tsunehimatoi/psd2live/issues/54)。現在、リップラインへ描くと案内が出るだけ）。
- [ ] 【その後】**2D ジオメトリノード**（p2ledior / 互換 · 再構成、難度あり）：ジェネレーターの再構成。ノードグラフでパーツを手続き生成する。静的な生成は損失がなく、手続きアニメーションはベイクが必要。モディファイアスタックの直後に続く。
- [ ] 【将来】**デフォーマ類**（互換 · 再構成）：配列 / インスタンス化、毛羽、ストロークからのパーツ生成、変身。モディファイアスタックと同じ、一度のデフォーマ再構成に属する。
- [ ] 【継続】リグ生成の内部段階を、独立したグラフノードに分ける。ブレンドシェイプの書き戻しによる、シミュレーションキーフォームの上書き。
- [ ] 【継続】プリセット実装の登録、選択、拡張の仕組み。部位、基礎アルゴリズム、モジュール、レシピのレジストリ。パラメータ量でモジュールを切り替えるプリセットと予算。パーツ役割の推定と修正はすでにできている（[リグプリセットのアーキテクチャ](spec/RIG_PRESETS.md)）。物理演算、スイング、シミュレーション、モーションのレシピライブラリは、まだモジュールとして登録されていない。ブレンドシェイプの出力とダウングレーダー、モジュールのバージョンと「生成結果を更新」の接続は、これからである。
- [x] **自動生成が手作業の仕上げ水準に達する**（互換 · 深化）：目（まぶたのフィッティング、笑い目、見開き、感情、まぶた付きの視線、余韻、ハイライト、虹彩の扁平）、眉（眉のフィッティング、眉の形、眉と目の連動、まばたきに追従）、口（段階的な開口、口の形の中間キー、閉口時の線の切り替え、母音、顔トラッキングの口、顎、頬が下まぶたを押す、口内の奥行き、戻り）、立体的な振り向きと顔の重なりのクリッピング、髪束のチェーン、スカートの裾 / サテンリボン / ペンダントのチェーンと胸の揺れ、頬紅と陰鬱、より豊かな標準表情、自然なまばたきと視線の移動、モジュールリグ向けに調整した VTube Studio の対応、キャンバス上の特徴点の修正は実装済み。4 つの素材のレビューを通過し、新旧のレシピが併存する（[リグプリセットのアーキテクチャ](spec/RIG_PRESETS.md)）。
- [ ] 【その後】自動生成の残り。眉のばねと感情の扇状の派生量。口の歯列の分割、舌出し、口内の明暗。首と体で首かしげを分担し、首の影を頭に掛けて首へクリッピングする。振り向きのとき前後の髪の描画順を切り替え、まばたきに前髪の揺れを付け、髪質のノブを振り子パラメータへ入れる。腕の受動的な揺れチェーン、硬い飾りを布へ固定、自動 Glue、獣耳 / 尻尾 / 翼の条件モジュール。スイッチの編成（積のゲート、場面転換、インパルス）と漫符、着替え。発話カーブ、駆動のレイヤー分け、VBridger の母音対応。キャンバス上で駆動メッシュのオフセットをドラッグする、フローティングのマクロノブ。ユーザーが基礎キーフォームを編集したあと、絶対形式のブレンドシェイプの基準を取り直す。

## ライティングとシャドウ

モディファイアに依存する後続の能力であり、必要なモディファイア能力がそろってから単独で進める。製品の優先度は、ユーザー拡張の閉ループ、関連する使いやすさ、内蔵スタイルの最適化のあとである。最初の範囲は、「既存のシャドウレイヤーが角度に追従して動く」か「前髪の投影が顔に落ちる」のどちらか 1 つを受け入れにする。静的な主光源だけを行い、絵師が描いたシャドウレイヤーを優先する。動的な光はランタイムにだけ残す。ボリュームの代理は、振り向き角度を広げることを目標にしない。大きな角度は、多視点の素材でしか賄えない。

- [ ] 【その後】**絵師のシャドウ / ハイライトレイヤーが角度に追従して動く**（互換 · 新規）：クリッピング + 乗算 / スクリーンのレイヤーを認識するか、SHADOW / HIGHLIGHT / RIM タグを追加し、角度に追従して動き、フェードインとフェードアウトする。輪郭内の明暗の伸縮は、内部造形を再利用できる。
- [ ] 【その後】**静的な主光源**（互換 · 新規）：明暗の境界線、前髪の投影、天使の輪のハイライト、遠い側を暗くする、レイヤー間の接触シャドウ。シャドウレイヤーのキーフォームと、デフォーマの色のキーフォームへベイクする。
- [ ] 【その後】**ランタイムの動的な光**（p2lrt · 新規）：法線マップによるピクセル単位のライティング。Cubism へ書き出すときは静的な光へ下げ、損失レポートへ書く。
- [ ] 【その後】**髪のボリュームシェル**（互換 · 新規、難度あり）：下を向く、上を向くときに、前髪が額から離れる、または額に沿う。角度軸へベイクする。
- [ ] 【将来】**逆ライティングのベイク**（互換 · 新規）：絵師がすでに描いた明暗から法線を逆算し、静的な主光源に使う。

## 既定リグの品質

- [ ] 【その後】**内部造形に基づく三次元投影プリセット**（互換 · 深化）：眼球の球体（虹彩とハイライトが球面に沿って滑り、縁に近づくと圧縮される）、胴のねじれ（体の X のとき、衣紋と模様が変わらない外輪郭の中で横へ動く）、表面空間のテクスチャ（模様がレイヤーの平行移動に付くのではなく、曲面に沿って動く）。Cubism の「3D 回転表現」とまとめて考える。内部造形をモディファイアへ移してから行う。
- [ ] 【未定】**剛体の保持**（p2ledior · 最適化）：既定リグが、ボタンや眼鏡などに回転デフォーマを自動挿入する。モディファイアに依存するかは、計画段階で確認する。
- [ ] 【将来】**変形を感知するテクスチャ密度**（p2ledior · 最適化）：既定のテクスチャアトラス割り当てで、拡大される領域の解像度を自動で上げる。
- [ ] 【将来】**欠けている領域の案内図**（p2ledior · 新規）：各角度で露出する、まだ描かれていない領域を算出し、補描または余白を残すよう案内する。
- [ ] 【将来】**多視点の振り向き**（互換 · 新規）：正面、3/4、側面の複数セットの美術が、変形とクロスフェードに対応する。
- [ ] 【継続】顔の輪郭 / シャドウ、体の局所的な動き、衣装の物理演算、獣耳と尻尾などの専用プリセットを改善する。
- [ ] 【継続】シミュレーションの品質と性能。ベイク時間の短縮（後ろ髪は約 6–8 秒）、細い髪束のモードごとのフィッティング、面積で質量を割り当てたあとの振り向きの粗さ、新しいマテリアルモデルでのモデルプリセットの再計測、ドラッグ時に書き出しの振幅が小さいこと。

## 編集ツール

各モードと PS / SAI、Cubism の項目ごとの対照は、差の表を参照する。描画、メッシュ、[変形](spec/DEFORMER_AND_PARAMETER_SPEC.md#ツールの対照と差分)。

- [ ] 【継続】**描画ツールの残りの差**（p2ledior · 深化）：絵師が必要とする優先度で、筆圧（ペンタブレットのネイティブ入力への接続が必要）、ビューの回転 / 反転、にじみと水彩の混色、選択範囲の変形と液化、合成画面からのスポイト、ブラシプリセットと流量。

## 性能とプロジェクト

- [ ] 【継続】編集確定の増分再構築。描画、画像の置き換え後の再生成チェックは、外形が変わらない編集に対して先にダーティチェックを行い、`BoundBaseKey` の入力集合を再利用し、G′ を完全に生成してから捨てない。生成チェックが合成したアトラスページは、プレビューの PNG 区間再利用を汚さない。各コマンドオブジェクトは、ランタイム級のパイプラインキャッシュ（メッシュ、`RigStageCache`、生成ジオメトリ）を共有し、最初の確定のコールドスタートを避ける。

## モディファイアのアルゴリズムプラグインと性能

実行順、フレームワークの敷居、項目ごとの台帳は、モディファイアプラグイン移行の実行規範を参照する。先にフレームワークを検証し、そのあと項目ごとに並行して移行する。カーネルの切り出しは、完全な移行には数えない。

- 【次】内蔵項目は、項目ごとの管理、入口の要約、外部パッケージの依存ロックをすでに備えている。独立して公開できる内蔵パッケージへの切り出しを続け、履歴のバイナリは残す。現在の入口はいまもアプリとともにコンパイルされ、リグの計算は共有の生成サービスに依存しているため、独立した公開への移行完了とは見なさない。（互換、再構成）
- 【次】内蔵のリグを、テンプレート一式の抽出から、所属する結果の直接計算へ変える。生成効果と出力 ID は残す。既定プリセット、単項目の追加、プリセットの切り替えは独立プラグインを通り、ホストの古いテンプレート生成経路を片付ける。履歴のあるプロジェクトは、ロックしたバージョンで再生し、生成とベイクは現在の効果を保つ。性能の最適化は、再構成を届けたあとに手配する。（互換）
- 【その後】宣言された読み書き依存に沿って並行計算し、連続する入力をまとめ、期限切れの候補を取り消す。完全な境界で計時したあと、ローカルのホットスポットを移行するかを決める。（互換、最適化）
- 【次】HTTPS／SSH の資格情報の環境、言語をまたぐ複雑なジオメトリ、画面操作の受け入れを補う。手元の Git 配布とワーカープロセスの障害は、対象を絞った受け入れを通過し、今回の全量回帰も通過した。6 言語の基礎的なインストールと評価の通過は、完全なプラグイン生態系または性能目標が受け入れ済みであることを意味しない。（互換、深化）
