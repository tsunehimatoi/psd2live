# Rig プリセットのアーキテクチャ：部位、基礎アルゴリズムとモジュール

[ドキュメント目次](../README.md) · モジュールとアルゴリズムのカタログ：顔 · [デフォーマとパラメータ](DEFORMER_AND_PARAMETER_SPEC.md) · [ドキュメント層](DOCUMENT_LAYER.md)

本ページでは、自動生成を、選べて、無効にできて、調整できる部分として、どのように編成するかを説明します。

- 各部位には、互いに排他な**基礎アルゴリズム**が 1 種類または数種類あり、そのうえに重ねられる**モジュール**がいくつか加わります。
- プロジェクトの**レシピ**には、各部位がどの基礎アルゴリズムを使うか、どのモジュールを無効にしたか、どの数値を変えたかを記録します。

各アルゴリズムとモジュールの設計（何を読むか、何を出力するか、キーフォームをどう計算するか、見栄えの基準）は、4 つのカタログにあります。本ページが定めるのは、それらの登録、選択、保存、再生、公開のしかただけです。

## 目標

自動生成されるモデルは、既定の状態で、手作業で細かく調整したモデルが視覚表現において持つ長所を備えます。

- 目、眉、口には、開閉だけではなく、完全な表情の空間があります。
- まばたきや発話には、周囲の連動と余韻が伴います。
- 振り向きには奥行きがあります。
- 髪と衣装には、重さと位相のずれがあります。

これらの能力は、1 つずつモジュールにします。

- **既定ですべて有効**：新規プロジェクトでは、適用できるモジュールをすべて既定で有効にします。
- **必要に応じて無効化**：ユーザーはパラメータ量に応じて任意の 1 つを無効にでき、プリセットまたはパラメータ予算で、一度にまとめて無効にすることもできます。
- **少数のノブ**：各モジュールが公開するのは、意味のあるノブを少数だけです。各ノブは、内部で一群の下位の数値を駆動します。今後は、キャンバス上で特徴点とハンドルをドラッグして調整できるようにします。

モジュールができたかどうかは、効果だけを見て判断します。

1. レビューツール（`RigReviewTool`）で、ポーズ板とモーション区間を出します。
2. その部位の「見栄えのよい姿」と「よくある不具合」を、1 条ずつ対照して確認します。
3. 数値の検査は、手がかりにするだけです。

## 用語

| 用語 | 意味 | コード |
| --- | --- | --- |
| 部位（area） | 1 枚のカードが扱う範囲。頭と顔、目、眉、口と下半顔、髪、体、衣装と装身、表情、モーション。1 枚のカードが左右両側を扱います | `RigArea` |
| 基礎アルゴリズム（base） | 部位の中で互いに排他なやり方。たとえば、まぶたの閉じを元のアルゴリズムにするか、テンプレートのフィットにするかです。ID は `部位/名称` で、バージョン番号と調整できる数値を持ちます | `RigBase` |
| モジュール（module） | 部位の中で重ねられる 1 つの能力。たとえば笑い目、まぶた付きの視線、まばたきの余韻で、それぞれスイッチがあります。ID は `部位.名称` です | `RigModule` |
| ノブ（knob） | 基礎アルゴリズムまたはモジュールの、調整できる数値 1 つ。単位、範囲、既定値、高度として折りたたむかどうかです | `RecipeKnob` |
| レシピ（recipe） | プロジェクトが各部位に選んだ基礎アルゴリズム、無効にしたモジュール、変更した数値。設定の `rig` に保存します | `RigRecipe` |
| パーツ役割（part role） | レイヤーがその部位の中で何であるか。ハイライト、瞳、下まつ毛、二重の線、影、頬紅、横髪、アホ毛、ポニーテール、三つ編み、獣耳、サテンリボン、ペンダント、硬い飾り、袖、スカート | `PartRole` |
| モデルプリセット | 開始ページのクイック構成（最小 / 既定 / 完全）と、モデルプリセットパネルの各グループ | `StartQuickPreset` |
| Rig 数値 | 元のアルゴリズムが、パラメータを満値にしたときの振幅。各部位の元の基礎アルゴリズムのパラメータです。パネルでは、各部位カードの「数値」に置きます | `RigTuning` |

## レジストリ

`core/recipe/RigModules.kt` が、唯一のレジストリです。部位は、パネルがカードを表示する順に登録します。

**基礎アルゴリズム**

- 各部位の最初の基礎アルゴリズムは `部位/legacy`、つまりレジストリを導入する前の生成方式です。
- より新しい基礎アルゴリズムはそのあとに登録し、最後のものが新規プロジェクトの既定です。

**モジュール**

各モジュールは、次を宣言します。

| フィールド | 意味 |
| --- | --- |
| `tier` | 重要度。`CORE`（部位が完成して見えるために必要）、`MAJOR`（明らかな視覚的な品質）、`MINOR`（仕上げ）。プリセットと予算は、これで絞ります |
| `requires` | 依存するモジュール。依存先を無効にすると、それに依存するモジュールも一緒に無効になります |
| `applies` | 素材が、処理するパーツを備えているか（部位、左右、パーツ役割で判断します）。当てはまらないモジュールは表示せず、コストにも数えず、生成もしません |
| `parameters` | その素材に対して追加するパラメータ |
| `estimate` | 無効なときのコスト見積もり |
| `physicsGroups` | 生成する物理グループ |
| `setting` | 設定の中にある、従来から対応するスイッチ（下記） |

**ID とバージョン**

- ID は、プロジェクトに保存され得るようになったら、改名しません。
- アルゴリズムが既存プロジェクトの生成結果を変えるときは、バージョン番号を上げます。レシピには、設定値を記録したときのバージョンを残します。

**旧スイッチを引き継ぐモジュール**

レジストリより前からあったいくつかのスイッチも、モジュールとして登録します。

| モジュール | 対応する設定 |
| --- | --- |
| `eye.see-through` | `seeThroughEyes` |
| `eye.jelly` | `physicsEyeJelly` |
| `brow.see-through` | `seeThroughBrows` |
| `mouth.outline` | `mouthOutlineEnabled` |

- これらのスイッチは元の設定そのもので、古いプロジェクトでも同じように有効です。
- ノブはありません。

## コスト

コストの 4 項目は、次のとおりです。

- 追加パラメータ（ID を 1 つずつ列挙します）。
- 追加キーフォーム。そのモジュールのパラメータをキーに持つメッシュの上で、増えるマスの数です。
- ブレンドシェイプの形の数。
- 物理グループの数。

コストの出所は、次のとおりです。

- モジュールが有効なときは、生成済みの Rig から実測します（`ModuleCost.measure`）。
- モジュールが無効なときは、モジュール自身の見積もりを使い、パネルは “≈” と標します。

## レシピ：選択、保存、アップグレード

**新旧のプロジェクト**

- 新しいプロジェクトの設定には `rig` キーを書き、内容が空オブジェクトのときは、すべて既定です。各部位は既定の基礎アルゴリズムを使い、適用できるモジュールはすべて有効です。
- レシピを導入する前に保存したプロジェクトは、設定に `rig` キーがなく、旧レシピ（`RigRecipe.Legacy`）として読みます。
  - 各部位は `legacy` 基礎アルゴリズムを使います。
  - 旧スイッチを引き継ぐモジュール以外は、どのモジュールも有効にしません。

  そのため、古いプロジェクトはこれまでどおり生成され、設定テキストと改訂の身元も変わりません。
- アップグレードでは `rig: {}` を書きます。取り消しできます。
- 旧レシピへ戻すときは `rig: null` を書き、設定からもこのキーがなくなります。

**変更（設定パッチ `changes.rig`）**

パネルと MCP は、同じ経路を通ります。

| 内容 | 書き方 |
| --- | --- |
| 部位の基礎アルゴリズム | `bases: {部位: {base, values}}`。`null` にすると既定へ戻ります |
| モジュール | `modules: {模块: {on, values}}`。`null` にすると「有効、数値は既定」へ戻ります |

- 同じ基礎アルゴリズムまたはモジュールを保つとき、数値は既存のものとマージします。
- 旧スイッチを引き継ぐモジュールでは、`on` を対応する設定へ書き、`values` は付けられません。
- 次は、すべて拒否します。
  - 未知の部位、基礎アルゴリズム、モジュール、数値。
  - 範囲を超える値。
  - `bases`、`modules` 以外のキー。

**保存形式**

- 既定と異なる項目だけを書きます。モジュールは `on: false` と、変更した数値だけを記録します。
- 読み込み時、認識できない部位、基礎アルゴリズム、モジュール、数値は読み飛ばすので、より新しいバージョンで保存したプロジェクトも開けます。数値は範囲内へクランプします。

## 再構築と再生

レシピは生成設定であり、次のしかたで再構築に参加します。

- 段階キャッシュが読める設定へ入ります（`RigBuilder.stageConfig`）。
- `RigGenerationChange` は、これを生成規則の変化として数えます。レシピを変更すると新しい基礎 G′ が生成され、旧基礎 G およびオーサード M と 3 者でマージし、ログの末尾に `rig_checkpoint` を書きます。ユーザーが旧基礎の上で行った編集は、マージ規則に従って残します。
- モジュールが追加したパラメータは、そのモジュールが生成するときだけモデルへ入ります。モジュールを無効にしたあと、参照されなくなったパラメータは、マージに伴って取り除きます。

そのため、モジュールのオンオフもノブの調整も、取り消しできる履歴の 1 回の確定であり、保存して開き直したあとも、同じように再構築されます。

「パラメータを変えると再計算し、ユーザーの微調整は残す」モジュールは、ログのあとのジェネレーターとして実装し、`DocumentGenerators` に、それが所有するキーフォームを登録するべきです（[ドキュメント層](DOCUMENT_LAYER.md) を参照）。

## パーツ役割

パーツ役割は、意味タグを細分化します。

- たとえば、同じ虹彩のレイヤーでも、ハイライト、瞳、虹彩本体は、それぞれ動きます。
- 同じまつ毛のレイヤーでも、下まつ毛、二重の線、まぶたの影は、目を閉じるときの挙動がそれぞれ異なります。

**タグ語として**

- 各役割は、1 つのタグ語です。`highlight`、`pupil`、`lower`、`lid`、`shadow`、`blush`、`side`、`ahoge`、`ponytail`、`braid`、`animal`、`ribbon`、`pendant`、`rigid`、`sleeve`、`skirt`、`upperlip`、`lowerlip`、`upperline`、`lowerline`。
- 役割語は、部位と左右の語とともに、レイヤーのタグへ書きます（`LayerTags`）。
- 各役割が細分化できる部位は決まっており、当てはまらない部位に置いても働きません。

**自動判断**（`PartRoles`）は、次の順で行います。

1. レイヤー名と、所属フォルダにある、中国語、日本語、英語、韓国語のキーワード。
2. 同じ部位の各レイヤーの中での位置と、ブレンド方式。たとえば、次のとおりです。
   - 虹彩の中にある、より小さいスクリーンのレイヤー、または明るいレイヤーはハイライトで、より小さい暗いレイヤーは瞳です。
   - 目の中心線より下のまつ毛レイヤーは下まつ毛で、上まつ毛の上にある細い線は二重の線です。
   - 乗算の顔、髪、衣装のレイヤーは影です。
   - 顔の横から、顔の中部より下まで垂れる前髪は横髪です。
   - 一枚もの（左右に分けない）の下衣で、裾が腰より狭くなく、裾の中央が途切れていないもの（ズボンは両脚のあいだで途切れます）は、スカートです。

**ユーザーによる修正**

- ユーザーがタグに書いた役割を優先します。
- 推定した役割をタグから 1 つ取り除くと、`PartRole.PLAIN`（役割なし）として記録し、解析は推定し直しません。
- MCP の `layer_classify` は、`part` フィールドで設定します。役割語、`none`、または `auto` です。
- 役割は、レイヤー分類の上書きの中にあります。役割を持たない上書きは、以前のテキストとまったく同じです。

**誰が役割を読むか**

- 役割を読むのはモジュールだけで、旧レシピは読みません。そのため、役割は古いプロジェクトの生成結果を変えません。

## パネルと MCP

**パネル**

モデルプリセットパネルの「部位とモジュール」グループは、次のとおりです。

- 上部には、次があります。
  - プリセット（完全 / 標準 / 簡略 / カスタム）。
  - パラメータ予算。「重要度が低いものから高いものへ、パラメータが多いものから少ないものへ」モジュールを無効にし、追加パラメータが予算を超えないようにします。
  - リセットボタン。
- その下は、各部位のカードです。カードのヘッダーには、有効なモジュール数と追加パラメータ数を表示し、展開すると次のとおりです。
  - 基礎アルゴリズムが複数あるときは、基礎アルゴリズムのドロップダウンと、そのノブを表示します。
  - 各モジュールは 1 行です。スイッチとコストを示し、有効にするとノブを表示します。
  - 現在の素材に適用できるモジュールだけを表示します。
  - 最後は、その部位の「数値」の折りたたみです。その部位の Rig 数値です（`RigTuning`。頭と顔には頭部の転向と鼻・耳が含まれ、体には体の回転、上下、前後の傾き、大きさの変化、体の Z と呼吸、立体とパースが含まれます）。よく使うものは小グループに分けて並べ、残りは「高度」へ折りたたみ、これらの数値だけをリセットするボタンを付けます。
- 現在のレシピで、実際に効いている Rig 数値だけを表示します。あるモジュールまたは基礎アルゴリズムが生成時に自分で描く部分については、対応する旧数値を表示しません（`RigTuning.replacedBy`、`RigModules.tuningInEffect`）。`face.depth-turn` を生成するとき、顔、顔パーツ、前後の髪が AngleX / AngleY 上に持つ九宮格の振り向き数値は表示しません（スタイル化した振り向きがそれらを置き換え、元のデフォーマは振り向きのキー上で静止したままです）。フィットした目は、元の閉じ目の数値（まばたきの奥行き、目角、まつ毛の押しつぶし）を置き換え、フィットした眉は眉の上がりを置き換え、フィットした口は元の口形の数値を置き換え、髪のチェーンは前後の髪それぞれの全体スイングとカールを置き換えます。古いプロジェクト（レシピをアップグレードしていないもの）と、これらのモジュールを無効にしたときは、これらの数値がこれまでどおり表示され、作用します。プロジェクトファイルと MCP は、引き続きすべてのフィールドを受け付けます。
- 古いプロジェクトでは、グループの上部に、アップグレードできる案内を出します。自動ではアップグレードしません。

**MCP**

- `module_catalog`（読み取り専用）は、すべての部位、基礎アルゴリズム、モジュール、ノブを列挙します。プロジェクトを開いているときは、さらに次を返します。
  - 新レシピかどうか、各部位の現在の基礎アルゴリズム。
  - 各モジュールが適用できるか、有効か、およびコスト。
- `settings_update` は、`changes.rig` を通してレシピを変更します。
- `workspace_inspect scope=settings` は保存形式を返すので、そのまま書き戻せます。

## 特徴点フィッティング（`core/fit`）

顔パーツの新しい基礎アルゴリズムは、決め打ちの式には頼らず、原画の特徴点を読み取り、標準テンプレートをそこへフィットします。

| コンポーネント | 働き |
| --- | --- |
| `EyeFitting` | まず両目の白目の中心を結ぶ線から、頭部の水平方向を求めます（目が 1 つだけのときは、Rig の水平を取ります）。目の座標系はそれに合わせて傾き、首をかしげたキャラクターや体を横に向けたキャラクターは、自分の顔に沿って開閉します。この方向に沿って、白目の不透明ピクセルの両端が目頭と目尻です。さらに両目角のあいだを、順に「顔の下向き」に沿って読み、上下のまぶたの縁を取り出します（各 17 サンプル。作画では通常、白目をまつ毛の下へ完全に押し込みます）。閉じ目の線からはその中心線を、虹彩からは外枠を読みます。座標は目頭を原点とし、単位は、両目角を頭部の水平方向に測った距離です。目尻は、目頭より高くても低くてもかまいません。幅、開閉比、上下のまぶたの縁の順序、目角の傾きを検査し、不合格の目は元のアルゴリズムへ戻して、理由を示します |
| `EyelidModel` | 疑似 3D のまぶたです。まぶたは、目角を結ぶ線を軸に回転する平面で、眼球との交線がまぶたの縁になります。そのため、まぶたが下がるあいだ、まぶたの縁は常に眼球を覆う弧であり、目角の線を越えたときだけ直線になり、そのあと閉じ目として下へ曲がる弧になります |
| `ThinPlateSpline` | 薄板スプラインです。テンプレートの特徴点を、検出した特徴点へ正確に合わせ、同じ写像をテンプレートの各ポーズに使います |
| `BiharmonicField` | 規則格子上の重調和変位場です。拘束のある箇所（まぶたの縁、唇の縁）にだけ変位を与え、それ以外は最も滑らかな解を取り、外周はゼロです。まぶたの皮膚や影などが、まぶたの縁に合わせて複数行で滑らかに動くために使います |
| `EyeRig` / `EyeBand` | `eye/fitted` は原画から、主筆の帯身、独立した束、側縁、上下のパーツ、接合区を観察します。帯身は連続曲線と横断面から閉じた形を生成し、線幅を保ちます。通常の閉じと、笑いの閉じは、別々に生成します。認識済みの尖った束は、局所的にすぼめて帯身の反対側までまたがることができ、根の区域は滑らかに遷移します。側縁は、帯身の近くへすぼめます。追加の目の形は、同じ目の座標の中で変位を生成し、全体の振り向きは、既存の親が担ったままです。中立の原画キーは、厳密に変わりません。信頼できる筆致の観察がないときは、元のまぶたのパスを残します。白目のクリッピングと筆致のジオメトリは、別々に生成します。両目が 1 つのレイヤーに合わさっているときは、ソースの位置に従い、左右の開閉を独立してリグします |

0）。それでもクリッピング元になります。レイヤー分けした口の各レイヤーは、原画に沿って描いたメッシュを残し、縁取りの口の列分割メッシュには置き換えないので、開口のメッシュは原画を完全に覆います。口の上のハイライトと影は、中心がどこに落ちるかに従い、上唇か下唇に追従するか、口腔の奥としてほとんど動かず、口腔にクリッピングされます。歯、舌、口腔の奥をクリッピングするのは口腔だけです。レイヤー分けした口は、縁取り帯を生成しません | `EyeModules` | 目のモジュールのメッシュとチャンネルです。開閉の軸（`eye.wide` は 2 まで延びます）と笑い目の軸（`eye.smile`）が、まぶたのキーフォーム格子を作ります。まぶた付きの視線、感情の目の形と細目、まばたきの余韻は、重ねるブレンドシェイプで、開閉の程度で重みを制限し、閉じ目では働きません。笑い目では、原画の閉じ目の線が、上へアーチする弧になります。虹彩は閉じると下へ押しつぶされ、見開くと少し縮みます。ハイライトは振り向きと逆の方向へずれます。まぶたの線とハイライトは、開閉に先立ってフェードアウトします。ブレンドシェイプの各形は、メッシュ自身の描画順と不透明度を記録し、重ねるのは変位だけです |

**振り向きのときの目、眉、横顔の連動**では、上下のまぶたの縁の四分点と、目頭・目尻で、目の開口を測ります。フィットは各ポーズの顔の横の輪郭を読み、変形後のまぶたの縁の高さから正味の距離を求めます。横振りに空間の制約があるとき、遠い目は目頭をアンカーにして横方向の開口を縮め、元のフィットのまぶたの縁の高さを保ち、虹彩は開口の幅に連動します。余白がまだ足りないときは、目全体を内側へ動かします。眉は同じ側の目の横方向の修正に追従し、眉の中心線と上まぶたの縁の対応するサンプルで、縦方向の間隔を制約します。横の耳と顔の皮膚が重なる区域から接点を読めるときは、耳の根が顔の皮膚の動きに従い、耳輪へ向かって独立した変位へ徐々に戻ります。遠い耳は、横振りが深くなるほど、接点の重みを弱めます。対応するランドマークがない部位は、元のスタイル変形を引き継ぎます。

**額の上部の輪郭**は、既定の振り向きスタイルで、原画の額の頂、目のライン、額の横断面にフィットします。前髪が原画で連続して覆い、顔の縁を越える余白が小さいとき、横振りは、転向する側の額の上部の縁をすぼめます。斜めの見下げは、俯仰に応じてこのすぼめを弱め、スタイルの中にある斜めの輪郭の変化は残します。補償は、額の縁から中心線、額の頂、目のラインへ連続して減衰し、前髪は自分のデフォーマを使い続けます。

**既定スタイルでの口と鼻の振り向き**は、両口角、上下の唇の中点、目のラインでの顔幅、両目の間隔、独立した鼻の鼻先と上縁、および顔の輪郭上の顎を読みます。左右へ振り向くとき、顎は顔の輪郭とともに動き、目のラインでの顔幅と両目の間隔が、それぞれ鼻先の先行と、口と鼻の間隔を決め、顔の横の余白が、鼻先と口角の動ける範囲を制限します。見上げと見下げは、それぞれ縦方向の変位を計算し、見下げでは、鼻から上唇まで、および下唇から顎までの余白で、変形後の開口を制約します。目のラインまで実線で描かれた鼻筋は、上縁で顔の面へ戻り、短い鼻の線とハイライトは、鼻先とともに全体が移動します。顔の皮膚に描かれた鼻は、顔の皮膚の動きに従います。

口が共有する曲げデフォーマは、口幅が顔幅に占める割合と、原画の開口の縦横比に従い、横振りのときの幅、高さ、上下の唇の中点をフィットします。開閉と口形は、その子メッシュの上で、独立して評価します。斜めのキーフォームは、スタイルの交差項を残します。独立した鼻のレイヤー、または信頼できるランドマークがないときは、使える口と顔の輪郭のフィットを使います。

拡張した見開きの区間（`Eye Open > 1`）は、`EyeOpeningModel` が単独で表します。上まぶたと下まぶたは、それぞれ横と縦の 2 本の 4 次チェビシェフ変位曲線を持ち、バイナリは `rig/eye-opening.bin` にあり、Clenshaw の漸化式で評価します。変位は `wideLift × (open − 1)` でスケールするので、原画の値 1 は厳密に変わりません。横は元の目幅を単位とし、縦は元の開口の高さを単位とします。曲線の定数項が持ち上げ全体を受け持ち、残りの項が両端の差と局所の弧を調整するので、中央だけをアーチ状に高くすることはありません。上下のまぶたは目角で 2 次元の変位を共有し、白目とまつ毛は同じ開口を共有します。複合した目の線は、上下のまぶたのあいだの位置に応じて変位を連続的に割り当て、外へ伸びる尾は原画のオフセットを残し、上まつ毛は同じ列の厚さを保ちます。下まぶたに近い筆致は、元の下まぶたの上で最も近い縁の点に追従し、急な目角の下にある厚い尾を、縦の列でせん断して裏返すことを避けます。二重の線と影の重調和場は、横と縦の拘束を同時に受けます。既定の上方向の持ち上げは元の開口の 10% で、0 まで調整できます。既定は穏やかな見開きを目標とし、明示的に保存した振幅はその値を保ちます。元の閉じの区間は独立して残り、見開くとき虹彩は原画の寸法と位置を保ち、縮瞳は独立した感情の制御が行います。

開閉に関係する不透明度のトラックは、実際のパラメータの全範囲を覆い、見開きの端点も含みます。閉じ目の線は 1 より大きいあいだ隠れ続け、まつ毛、二重の線、ハイライトは、それぞれの開き目のときの見え方を保ち、トラックを外れたあと静的な不透明度へ戻ることはありません。

`FitDetectionTool` は、検出結果と各開度のまぶたの縁を原図の上に重ね描きし、フィットの確認に使います。フィットした目のまつ毛、白目、閉じ目の線のメッシュはおよそ 4 倍細かく、弧に曲げてもポリゴンの折れ角は出ません。

眉のモジュール（いずれも `brow/fitted` の上に作ります）は、次のとおりです。

| モジュール | 重要度 | 追加パラメータ | 働き | ノブ |
| --- | --- | --- | --- | --- |
| `brow.shape` | 中核 | `ParamBrowLAngle` / `R`（−1 内端を下げる … +1 上げる）、`ParamBrowLX` / `R`、`ParamBrowLForm` / `R`（−1 平ら … +1 アーチ） | 眉の角度、左右の移動、眉の形 | 振幅 |
| `brow.lid-coupling` | 重要 | — | 上まぶたと眉は、同じ一枚の皮膚のように動きます。眉を下げるか寄せると、上まぶたが下へ押されて平たくなり（見開くような視線）、上げると上まぶたが上がります。感情は瞳へも扇状に広がり、眉を上げるとき（驚き）は虹彩が少し縮み、眉を下げると少し広がります。フィットした目が必要です | 振幅 |
| `brow.blink` | 重要 | — | 目を閉じると眉がわずかに沈み（内端の方が多く）、`eye.wide` で見開くと上がり、笑い目で閉じると戻って上がります | 沈み |
| `brow.spring` | 仕上げ | `ParamBrowLSpring` / `R`（物理出力） | 眉が止まるとき、わずかに行き過ぎてから戻ります。振り子は眉の高さと角度を入力とします（物理グループ `PhysicsBrowLSpring` / `R`） | — |

## 実装の取り決め

- `legacy` 基礎アルゴリズムのコード経路は、変えません。
  - 新しい基礎アルゴリズムとモジュールは、分岐点で `config.recipe.base(部位)` と `RigModules.builds(模块, config, 素材)` により、実装を選びます。
  - 実装は純粋なジオメトリ入力だけに依存し、画面の状態は読みません。
- 1 つのモジュールが、あるパラメータのキー位置を変えるとき、そのパラメータを共有するすべてのメッシュは、同じキーの組を使わなければなりません。たとえば白目は虹彩のマスクなので、まつ毛と同じキーでなければなりません。
- 二次的な変化は、主キーフォームの上にブレンドシェイプを重ねることを優先し、キーフォームの数が次元の積で増えることを避けます。ブレンドシェイプに対応しない書き出し先は、ダウングレーダーがベイクするか捨て、損失レポートへ書きます。
- 生成結果に含めるのは、Cubism が表現できるブレンドシェイプだけです（`CubismBlendShapes`。基礎 Rig を組み立てたあとに実行します）。Cubism がブレンドシェイプを重ねるのは、「ブレンドシェイプ」型のパラメータだけで、この種のパラメータはキーフォームの軸になれません。通常のパラメータに掛かったブレンドシェイプは moc3 / cmo3 へ書けず、Cubism のランタイムは描画を誤ります。そのため、次のようにします。
  - ブレンドシェイプだけが使い、既定値が 0 で、各形の静止キーが 0 にあるパラメータ（母音、顔トラッキング、眉の形、髪と布のチェーンの節、腕のスイング、胸部など）は、ブレンドシェイプのパラメータに変えます。
  - いずれかのキーフォーム軸でもあるパラメータ（振り向きの角度、目と口の開閉、視線、眉の高さと角度、口形）の上にある形状は、キーフォームに変えます。メッシュ自身のキーフォーム格子（ジオメトリと各チャンネルの軸の和集合。つまり moc3 における、そのメッシュのキーフォーム数）が 256 個を超えず、頂点の値が 12 万を超えないときは、これらのパラメータのキーに沿ってメッシュへ折り込み、結果は厳密です（形状の重みは、キーのあいだでも、点のあいだの制限でも線形であり、すべてのキーで値を取るメッシュは、完全に再現されます）。超えるときは、メッシュ自身の Warp へ渡します（`<网格 ID>_Turn` が振り向きを置き、`<网格 ID>_Shape<n>` が残りの連動を置き、それぞれキーフォームは 64 個を超えません）。メッシュと元の親のあいだに挿入し、8×8 の格子点を、形状がメッシュ頂点に対して自身の各キーフォームで生む変位へ、最小二乗でフィットします。Live2D の手作業モデルが、振り向きをパーツの Warp に置くやり方と同じです。親が曲がっているとき、Warp は格子点でしか近似できず、誤差はキャンバスの 1 ピクセル程度です。
  - 形状が変える不透明度と色は、メッシュのチャンネルへ折り込みます。生成する形状は、描画順を変えません（各形の描画順は、メッシュの最終的な静止値を取ります）。
- 生成するオブジェクトとパラメータの ID は、決定的です。
  - モジュールが追加するパラメータは、Cubism の標準名を優先し、顔トラッキングの拡張には、よく使われるコミュニティの名前を使います。
  - 新しいオブジェクトの ID は、モジュールと対象から派生し、乱数は使いません。

## モジュールの拡張

1. カタログに設計を書きます。
   - 適用条件、出力、段階的なアルゴリズム、ノブ。
   - 見栄えのよい姿と、よくある不具合。
   - 失敗したときに、何へ戻るか。
2. `RigModules` に登録します。所属する部位、重要度、依存、適用条件、パラメータ、コストの見積もり、ノブです。
3. 生成の分岐点に実装します。`legacy` の経路は変えません。
4. 4 言語の名称と説明を補います（`settings.rig.module.*`、`settings.rig.knob.*`）。
5. 検証します。
   - `RigReviewTool` でポーズ板とモーション区間を出し、見栄えの基準と対照して確認します。
   - `ExportGoldenTool` で、旧レシピのプロジェクトがバイト単位で変わらないことを確認します。
   - 回帰テストを追加します（`RigRecipeTest`、`RigModulesScenario`）。

## 3 層の口形とトラッキング書き出し

口全体の素材が縁取りを生成するとき、閉じ口の線は口形設定の連続曲線を使い、開口の輪郭の中点は、閉じ口の線としては残しません。独立してレイヤー分けしたリップラインは、原画の構造を残します。原画と目標の輪郭でサンプリング密度が異なるとき、サンプリングの残差は閉じとともに回収され、上下の唇縁と、唇をまたぐ縁取りの重なり区間が、閉じ口で同じ 1 本の線へすぼまることを保証し、急な口角に短い尾を残しません。原画の開き口のポーズは、元の輪郭を残します。

生成する縁取りが適用されるのは、唇の原画がない口腔のレイヤーだけです。すでに上または下のリップライン、唇の皮膚、または閉じた口のすき間があり、重なった完全な口形の差分があるときは、縁取りを追加しません。口内のクリッピングレイヤー、唇のハイライト、影も、縁取りのソースにはしません。ネイティブの生成とアルゴリズムプラグインは、同じ候補レイヤーの判定を使います。

縁取りの中心線と、原画のリップラインは、別々にバインドします。中心線は目標の唇縁に沿って動き、そのあと目標のパスから、線幅を保つ断面を生成します。厳密な閉じ口では、生成した縁取りと原画の線の口の両方が、各表情の基礎開度の残差を消します。原画のリップラインは、それぞれの唇縁のステーションに沿って、素材の厚さと口角の筆致を残し、口角は、ソースの開きの弧を追加の厚さとしては残しません。口内の境界と唇縁は、一致した対応関係を使い、唇の皮膚は覆う面積を残します。唇を押す、歯を出す、下顎などの付加的な動きは、共通の口形の目標の上に重ね続け、筆の太さを口腔の開度として残すことはできません。

フィットした口は、正規化した輪郭、変形の部分空間、ユーザーパラメータの 3 層で評価します。原画の開き口の中立ポーズは元の位置を保ち、閉じ口では上下の唇縁が接します。セル画のリップラインは、局所の接線と法線で太さを保ち、厚塗りの唇の皮膚の外縁は、主となる顔と口の周りの変形を共有します。上の歯と下の歯は、それぞれ上顎と下顎に追従し、口をゆがめるときは歯列全体が傾き、押される側ですぼみます。片側の口角、および片側の膨らませと引き結びは、独立したパラメータで重ねます。

レイヤー分けした口の歯と舌は、口腔のマスクでクリッピングし、開口に合わせてフェードインしません。不透明度がゼロの口腔レイヤーも、マスクになれます。舌出しは、決定的な ID の伴走メッシュ `<舌网格 ID>_Out` を生成します。静止時は透明で、口腔のクリッピングを受けず、下唇の上かつ上唇の下にあります。母音の口形は単独で駆動でき、開口パラメータが大きくなると減衰し、音声と顔トラッキングを重ねたときに、口が二重に開くことを避けます。

`eye.gaze-lid` は `ParamEyeBallLX/LY/RX/RY` を追加します。共有の視線パラメータは、残します。独立した視線は、対応する虹彩とまぶたに同時に作用し、2 次元パラメータのミラー、およびプロジェクトの再構築と両立します。

VTube Studio の書き出しは、次の選択を提供します。各出力パラメータは 1 回だけマップします。存在しないモデルパラメータには、マッピングを生成しません。

| 設定 | 選べる値と挙動 |
| --- | --- |
| `vts_mouth` | `standard` は顔トラッキングです。`voice` は音声の母音です（母音パラメータがないときは、音量で開口を駆動します）。`voice_hybrid` は音声と顔トラッキングの混合です。`vbridger` は、プラグインの JawOpen、MouthPucker、MouthFunnel、MouthShrug、MouthPressLipOpen の入力を追加します |
| `vts_gaze` | `independent` は左右が独立です。古いモデルは共有の視線へ戻します。`shared` は右目の視線を共用します。`mouse` はマウス位置です |
| `vts_brows` | `independent` は左右の眉の高さです。`shared` は Brows を共用します |
| `vts_position` | 既定はオフです。既存の `ParamFacePositionX/Y/Z` をマップします |
| `vts_angry` | 既定はオフです。実験的な FaceAngry 入力を、既存の目の感情パラメータへマップします |

公式の、頭部、視線、口、マウス、音声の 33 項目の入力を覆います。互いに排他な入力は、モードに従って選びます。カスタムモデルは `Param<输入名>` で、対応する公式入力へ接続できます（たとえば `ParamVoiceSilence`）。書き出し側は、そのために空のパラメータを作りません。VBridger モードでは、ユーザーがプラグインを実行し、対応する入力を用意する必要があります。

入力名は [VTS 公式パラメータ表](https://github.com/DenchiSoft/VTubeStudio/wiki/VTS-Model-Settings#supported-input-parameters-face-tracking-etc) に、プラグインのパラメータは [VBridger 公式ドキュメント](https://github.com/PiPuProductions/VBridger-Documentation/wiki) に基づきます。

現在の視覚上の制限として、厚塗りの唇の皮膚は、口のゆがみを最大にして開口と重ねたとき、口の周りの皮膚の点ごとの変位の混合によって、局所のメッシュが裏返ることがあります。この組み合わせは、まだ視覚の受け入れを通過しておらず、共有する皮膚の場をさらに修正する必要があります。

### 目の構造の訂正

`module_catalog.eye_structure` は、各目について、原画のパス、コンポーネント ID、ソースの要約、上下の帰属、ジオメトリの種別、接合区、分岐パスを返します。観察のソースは元の生成ピクセルで、元のレイヤー、UV、描画順、明示的なマスクを残します。数字の接尾辞は、差し替え画像を表しません。

`settings.rig.eyeParts[layerId][componentId]` は、`side`、`region`、`primitive`、`contacts`、`path` を上書きでき、同時に、一致する `sourceStamp` を持たなければなりません。パスと接合の座標は、その目の局所座標を使います。内角が原点、目幅が単位、第 2 軸は顔の下方向です。ソースと一致しない上書きも保存しますが、変わったあとの原画には適用しません。ソースが戻ると、再び有効になります。コンポーネント、レイヤー、または `eyeParts` 全体の null パッチはリセットに使い、連続する設定ジェスチャは、リセットの前後関係を保ちます。新しい設定ノードは schema 5 を使います。構造の訂正がない古いプロジェクトは、元のノードバージョンのままです。
