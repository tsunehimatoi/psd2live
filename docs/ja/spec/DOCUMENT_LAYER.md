# ドキュメント層：ジェネレーター、上書き、キャッシュ

形式の設計は、プロジェクトを「意図 + ユーザー上書き」と定義します。ジェネレーターはパラメータだけを保存し、生成結果は純関数で算出し、ユーザーが生成結果の上で行った変更は安定 ID で記録し、ジェネレーターを再実行するときは三者マージを行います。第 1 段階では、スイングジェネレーターを見本として仕組みを検証しました。本ページは、残りのジェネレーターへの展開、計測に従って生成キャッシュへ接続すること、およびプロジェクト形式 v2 の実装状態を記録します。

## 実装済み

| 部分 | 位置 | 内容 |
| --- | --- | --- |
| 内容ハッシュ | `format-compile` `document/ContentHash` | 各部分の規範テキストの SHA-256。長さで区切り、IR の値は直接ハッシュできます |
| 依存グラフ | `document/GeneratorGraph` | ジェネレーターは、読み取る安定 ID と所有する安定 ID を宣言します。トポロジカルソート、環の禁止、1 つのオブジェクトに所有者は 1 つだけです。変化のあと、再計算が必要な下流のジェネレーターを出します |
| 生成キャッシュ | `document/GenerationCache` | 入力の内容ハッシュで生成結果をキャッシュします（LRU）。ミスしたときはロックの外で計算し、遅いジェネレーターがほかのキーをブロックしません |
| 三者マージ | `document/ThreeWayMerge` | キーごとにマージします。ユーザーが変えていないものはジェネレーターに従い、ジェネレーターが変えていないものはユーザーの値を残し、両方が変えていて異なるときはユーザーの値を残して衝突を報告します |
| ドキュメントのジェネレーターグラフ | ルートプロジェクトの `core/DocumentGenerators` | プロジェクトのジェネレーターを依存グラフのノードとして登録します。再生はグラフの順にスイングとシミュレーションを実行します。上書きは、グラフからキーフォームの所有者を探します |
| 生成結果の上書き | `core/GeneratedOverrides` | スイングの Warp キーフォームと、ベイクしたシミュレーションメッシュのキーフォームの上のキャンバス編集を `generated_override` として記録し、すべてのジェネレーターのあと、制御点または頂点の三者マージで再生します |
| スケルトンとモーションのキャッシュ | `core/SkeletonRig.generate`、`core/MotionPresets.tracks` | スケルトンのベイクと生成モーションを、入力の内容ハッシュで `GenerationCache` に接続します |
| 再生チェックポイント | `core/legacy/ReplayCheckpoints` | チェックポイントを持たないログだけに使います。基礎 Rig のインスタンスとログ接頭辞の内容で、再生の途中モデルをキャッシュします。追加は新しいエントリだけを再生し、取り消しは既存のチェックポイントに当たります |
| ジェネレーターの再利用 | `core/DocumentGenerators`（`GeneratorReuse`） | スイングとシミュレーションは、オブジェクト単位の読み取りを宣言します。読み取りが変わらないときは、前回の出力をパッチとして適用し、生成し直しません |
| 分割の実体化 | `core/ArtPrimitiveJournal`、`core/RigRegenerationCheckpoint`（`split`）、`application/WorkspaceArtPrimitives` | 分割は 1 回の再生成です。パーツが元のレイヤーに代わって生成に参加し、ユーザーが元のレイヤーへ行った変更は三者マージでパーツへ運ばれ、`art_primitive` 記録のあとにチェックポイントを書きます。[分割の実体化](#分割の実体化アートプリミティブ記録-art_primitive) を参照 |
| オーサード Rig とチェックポイント | `core/RigEditOverlay`（`replayAuthored`/`finish`）、`core/RigCheckpoint`、`core/RigRegeneration`、`project/MaterializedRigStore` | 再生はオーサード段階と仕上げ段階に分かれます。オーサード Rig は改訂ごとに保存し、構築へ直接使います。生成結果がログの下で変化するときは三者マージしてチェックポイントを書きます。[チェックポイント](#チェックポイント) とチェックポイント Rig を参照 |
| プロジェクト形式 v2 | `project/ProjectFormatV2` | 各改訂を、内容アドレスで、schema バージョン付きのドキュメントノードに分けます。v1 は開いたあと、次の保存で移行します。[プロジェクト形式](PROJECT_FORMAT.md) を参照 |

`format-compile` の 4 つの枠組み部分は MIT で、どの GPL モジュールにも依存しません。

## プリセット設定の下書き

プリセットのコントロールは設定パッチだけを投影し、現在プレビューしている `RigEditOverlay` やメッシュのベースラインを、設定編集の確定としては提出しません。`WorkspaceSettingsIntent.patchSettings` は、即時表示のための連動規則を出します。`WorkspaceGenerationCommands.prepareSettingsDraft` は、キャプチャ済みの確定ドキュメントへ同じ意図を適用し、オーサードのポーズを解放し、再構築して生成結果をマージします。プレビューと確定は同じ純粋な候補を使い、プレビューが作るチェックポイントは一時モデルの中にだけあります。

スライダー、数値入力、色のポップアップは、編集セッションで操作を区切ります。`WorkspaceSettingsDraft` は、連続する数値のサンプルを最終パッチへまとめ、同時に、ポーズを解放するスイッチの切り替え順を残します。セッションが終わると、`WorkspaceDraftQueue` とランタイムの CAS を経て、履歴ノードを 1 つ公開します。変化がなければ追加しません。シミュレーションと物理の編集は、引き続き各自のアプリケーション層コマンドを使います。保存は、先にコントロールのセッションを終え、下書きの確定を待ちます。古い編集記録と履歴スナップショットは、元のままです。

## ジェネレーターの依存グラフ

`DocumentGenerators.graph` は、プロジェクトごとに次のノードを作ります（オブジェクト ID では、`document:<部分>` がドキュメント状態、`rig:<阶段>` が Rig 全体の段階、`parameter:<ID>` が生成されたパラメータ、`keyform:<warp|mesh>:<目标>@<参数>` が、ジェネレーターがそのパラメータに沿って対象へ追加するキーフォームです）。

| ノード | 読み取り | 所有 |
| --- | --- | --- |
| `rig.footprints`（メッシュの輪郭） | ソース画像、設定、レイヤーごとのメッシュ設定 | `rig:footprints` |
| `rig.scaffold`（アンカー、顔、枠組み、デフォーマ） | `rig:footprints`、レイヤー分類、設定、スケルトン定義 | `rig:scaffold` |
| `mesh:<图层>`（レイヤーごとのメッシュとキーフォーム。レイヤー一覧を渡さないときは `rig.meshes` にまとめます） | `rig:scaffold`、そのレイヤーのピクセル、分類、メッシュ設定 | `rig:mesh:<图层>` |
| `rig`（組み立てとテクスチャアトラスのバインド） | 各レイヤーのメッシュ、`rig:scaffold`、ソース画像、設定、レイヤー分類 | `rig:base` |
| `skeleton`（スケルトンのベイク） | `rig:base`、スケルトン定義 | `rig:skeleton` |
| `journal`（編集の再生） | `rig:skeleton`、編集ログ | `rig:authored` |
| `skeleton.skin`（ログが配置したメッシュのボーンスキン。ログが、ボーンにバインドしたメッシュを自分のデフォーマの下へ掛けたときだけ存在します） | `rig:authored`、スケルトン定義 | これらのメッシュが、その四肢のボーン、上にある体の半区間、スケルトンポーズのパラメータの上に持つキーフォーム |
| `swing:<ID>`（ベイクしていない各スイング） | `rig:authored`、そのスイングの設定 | そのパラメータと、そのパラメータが各対象 Warp の上に持つキーフォーム |
| `simulation:<ID>`（ベイク済みで有効な各シミュレーション） | `rig:authored`、そのシミュレーションの設定とベイク | そのモードパラメータと、モードパラメータがベイクメッシュの上に持つキーフォーム |
| `overrides`（上書きのマージ） | 生成されたすべてのキーフォーム、上書き、ジェネレーターの集合 | `rig:final` |
| `seeThrough`（前髪越しの複製） | `rig:final`、設定 | `rig:seeThrough` |
| `physics`（物理グループ） | `rig:final`、`rig:seeThrough`、生成されたパラメータ、物理とスケルトンの設定 | `physics` |
| `motions`（生成モーション） | `rig:final`、`rig:seeThrough`、`physics`、モーション設定、スケルトン定義 | `motions` |

- 再生（`RigEditOverlay.applyTo`）は、グラフのトポロジ順で、ログよりあとのノードを実行します。先に `skeleton.skin`、次にスイングとシミュレーションで、これまでの「先にスイングをすべて、次にシミュレーションをすべて」という順序と同じです。同順位は宣言順で解きます。
- 前髪越しの複製（`SeeThroughLayers`。[デフォーマとパラメータの参考](DEFORMER_AND_PARAMETER_SPEC.md#自動変形) を参照）では、`rig` ノードが候補だけを記録します（前髪に覆われた眉と、各目のレイヤー、およびその前髪）。`seeThrough` ノードは、上書きのマージ、レイヤーの表示と非表示、描画順の上書きのあと（`AuthoredRig.finished` の末尾、`withSeeThrough`）に、設定に従って原本から複製を作り、目のために前髪へ窓を開けます（前髪の逆クリッピング。`BuiltRig.seeThroughWindows`）。マスク、描画順、不透明度は、その時点の原本と前髪から得ます。窓開けが変えた前髪のマスクは完成した Rig の中にだけあり、オーサードとログの中の前髪はそれらを持ちません。インスペクターは `authoredMasksOf` を通して、ドキュメント自身のマスクを表示し、編集します。旧版のソフト削除が、窓を開けた目のレイヤーをすべて削除するときは、窓を回収します（`withSeeThroughWindowsPruned`）。複製はオーサード Rig の中にはなく、`keyform:` オブジェクトを何も所有しません。参照フィールド（分割の参照フィールドと `id`、`masked_by` など）でそれを名指しするドキュメント操作は、すべて（`WorkspaceDocumentEdits` の分配箇所とログの記録箇所で）`WorkspaceGeneratedCopyEdit`（`generated_copy`）により拒否します。3 つの設定は再生だけを引き起こし、生成設定には数えません。複製には自分のレイヤー項目がなく、レイヤーとしてメッシュを扱う箇所は `BuiltRig.layerOf` で原本のレイヤーを取ります（旧版のソフト削除は、原本とともに複製を削除し、アトラスの圧縮と再バインドも行います）。生成の移行を Rig データとして読む構築は、複製を作りません（`SeeThroughLayers.withoutCopies`）。未確定のプレビュー（キャンバスの各ツールが `CanvasEditor.preview` へ代入するもの、インスペクターのリアルタイムフィールド、Warp の制御場）は、一律に `SeeThroughLayers.refresh` を経て、プレビュー中の原本と前髪に合わせ、引き継いだ複製を作り直します。マスク、順序、外観は確定時と同じです。再構築全体のプレビュー（スイング、内部造形の試し再生）では、複製がすでに新しいインスタンスなので、同じモデルをそのまま返し、参照でプレビューを識別する箇所には影響しません。
- ドキュメントが 2 つのジェネレーターに同じパラメータを宣言させると、先に宣言した方が所有権を残し、後の宣言は捨てます。再構築は続けられ、衝突はジェネレーター自身が報告します。
- `DocumentGenerators.stale(before, after)` は、1 回のドキュメント変化のあと再実行が必要なジェネレーターを出します。変化した部分を読んだジェネレーターと、その下流すべてです。変更または削除されたジェネレーターが以前所有していたオブジェクトも、変化とみなします。たとえば 1 つのスイングを調整すると、そのスイング、上書きのマージ、物理、モーションだけを再実行し、Rig の生成、スケルトン、ほかのシミュレーションは再実行しません。
- Rig の生成は、段階ごとにノードへ登録します（下記の [Rig の生成段階](#rig-の生成段階) を参照）。`graph(overlay, layers)` にレイヤー一覧を渡すと、レイヤーごとに `mesh:<图层>` ノードが 1 つになり、あるレイヤーのピクセルが変化すると、そのレイヤーのメッシュ、組み立て、およびその下流だけが失効します。

## 増分再生

`RigEditOverlay.applyTo` は、順に、オーサード（チェックポイントがあるときは最後のチェックポイントから始め、そのあとのエントリだけを再生します。[チェックポイント](#チェックポイント) を参照。チェックポイントがないときは、旧形式の静的編集、つまりパラメータの削除と作成、静的 Warp、構造、キーフォームの set/copy/delete と、`authoringJournal` の全エントリを実行します）、スイングとシミュレーション、上書きのマージ、遅延したパネル編集を実行します。生成されたドキュメントは、最初の編集のあとチェックポイントを持ち、そのあとは最大で `CHECKPOINT_INTERVAL` 件を再生します。下に述べる再生チェックポイントが扱うのは、チェックポイントを持たないログだけです（より古いバージョンが書き、まだ編集していない改訂）。スイングとシミュレーションは、`GeneratorReuse` が読み取り集合に従って再利用します。

**再生チェックポイント**（`core.legacy.ReplayCheckpoints`。チェックポイントを持たないログだけに使います）

- チェックポイントは、「旧形式の静的編集 + 先頭 `i` 件のログ」のあとのモデルです。探す条件は、基礎モデルが同じインスタンスであること、旧形式の部分が等しいこと（スイングとシミュレーションのパラメータ集合を含みます。これが、どの構造編集を遅延するかを決め、インターフェースの言語も含みます）、先頭 `i` 件のそれぞれが、チェックポイントが再生したエントリと同じであること（先に参照を比べ、異なれば内容を比べます）です。
- 失効は接頭辞の内容だけを見て、添字は見ません。より早いエントリを書き換えるコマンド（ドラッグのマージ、生成結果の上書きのキャプチャ、メッシュの正規化）は、そのエントリ以降のチェックポイントを自然に不一致にし、最も新しい有効なチェックポイントから再生します。
- 各チェーンは、添字 0、16 件ごと、および最後の 3 件の状態を残し、いずれもソフト参照です（メモリが逼迫すると解放します）。チェーンは最大 4 本残します（最近の使用を優先します）。分岐するときは旧チェーンを残し、やり直しや元への切り替えに使います。
- 1 件追加するときは、その 1 件だけを再生します。1 つ前の状態への取り消しは直接当たり、再生しません。完全な再構築（開き直し、タイル寸法を変えるペイントと画像の差し替え）は、新しい基礎 Rig のインスタンスを生み、最初から再生します。どのタイルの寸法と位置も変えないペイントや画像の差し替えは、同じ基礎 Rig のインスタンスを引き継ぎます（下記の「テクスチャアトラスとペイント」を参照）。チェックポイントは通常どおり当たります。
- スケルトンは基礎 Rig の中でベイクし（ログより前）、ログのあとにあるのはキャンバススキンの書き戻しだけです。スケルトンの編集は基礎 Rig の内容を変えるので、それまでのチェックポイントはすべて成立しなくなり、最初から再生します。「影響を受けた最初のエントリより前から続ける」は、スケルトンには適用しません。内容で基礎 Rig を照合しません。2 倍の tml（4096²）では、基礎 Rig 全体の IR 内容ハッシュがおよそ 160 ms なのに対し、26 件のログの完全な再生はおよそ 6 ms です。内容が同じ再構築は、段階キャッシュが同じインスタンスを返すので（「Rig の生成段階」を参照）、インスタンスの一致で足りています。
- `PuppetModel` とそのオブジェクトは、不変の値として共有します。`-Dpsd2live.replayCheckpoints=false` は、チェックポイントとジェネレーターの再利用を同時に閉じます。コード上では 2 つのスイッチです（`ReplayCheckpoints.enabled`、`GeneratorReuse.enabled`）。それぞれ閉じられます。

**ジェネレーターの再利用**

- スイングの読み取りは、各対象 Warp とそのすべての祖先（計測がある親の空間）、パラメータ一覧とパラメータツリー、ワールド原点（自動支点）です。書き込みは、自分のパラメータ、パラメータツリー、対象 Warp です。
- ベイク済みシミュレーションの読み取りは、対象メッシュとベイクメッシュ（ジオメトリ、ブレンドシェイプ、チャンネル）、パラメータ一覧とパラメータツリー、ランタイムの対象（ブレンドシェイプを使うかどうか）です。書き込みは、自分のパラメータ、パラメータツリー、これらのメッシュです。
- ジェネレーターの実行後、その出力をパッチとして記録します。新しいパラメータ一覧とパラメータツリーに、置き換えたオブジェクトを足します。記録の前に検証します。変えたのは読み取り集合の中のオブジェクトだけで、残りのフィールドの参照は変わらないこと。そうでなければキャッシュしません。
- 設定が同じで、読み取り集合が項目ごとに同じとき（先に参照を比べ、異なれば内容を比べます）、パッチを現在の入力へ直接適用し、読み取り集合の外のオブジェクトは現在の値を保ちます。参照の比較には、ほとんどコストがありません。内容ハッシュで読み取り集合を比べると、かえってジェネレーター自身より高くなります（下の表を参照）。
- 内容の比較が漏らすことはあっても（配列フィールドは参照で比較します）、誤って一致と判定することはありません。見逃しは、生成し直すだけです。
- `DocumentGenerators.stale` は、引き続きドキュメント単位の再実行範囲を出します。再生のときは、より細かいオブジェクト単位の読み取り比較を正とします。たとえば、関係のないメッシュを編集するときはスイングもシミュレーションも再利用し、スイング対象の Warp またはその祖先を編集するときは、そのスイングだけを再実行します。

**効果**（`CommitPerfTool.baseline`。同一マシンでの前後比較。「閉じる」はチェックポイントとジェネレーター再利用を閉じること、「追加」は最後の 1 件を除いたログを先に再生し、そのあと完全なログを再生すること）は、次のとおりです。

| 場面 | これまでの再生 | 閉じる | 1 件追加 | 同じドキュメントを繰り返し再生 |
| --- | ---: | ---: | ---: | ---: |
| 場面 a（スケルトン + スイング 2 つ + ベイク済みシミュレーション） | およそ 3.7 ms | およそ 4.3 ms | およそ 1.0 ms | およそ 0.6 ms |
| ログ 64 件 | およそ 16 ms | およそ 20 ms | およそ 0.7 ms | およそ 0.1 ms |
| ログ 214 件 | およそ 43 ms | およそ 45 ms | およそ 0.4 ms | およそ 0.1 ms |

ジオメトリ編集を 200 件追加したあと、1 回の確定はおよそ 98 ms からおよそ 46 ms へ下がり、確定の中の再構築はおよそ 79 ms からおよそ 23 ms へ下がりました。残る主なものは moc3 のパッキングとジオメトリの安全検査で、ログの長さとともに増えることはありません。

## チェックポイント

ログを再生する前提は、エントリを書いたときに向き合っていた生成結果が変わらないことです。生成の入力を変える編集（髪のシミュレーションのスイッチ、スケルトン、生成設定と分類、分割など）で基礎 Rig が変わったあと、古いエントリは新しい結果の上では再生せず、マージしたあとデータとして保存します。

- **トリガー**（`WorkspacePreviewBuilder.build`、`RigRegenerationCheckpoint.checkpointed`）。新しいドキュメントが現在のドキュメントを継続し（`RigEditOverlay.continues`。ログが現在のログで始まること。共通の先頭にチェックポイントがないときは、旧形式の静的フィールドも同じでなければならず、チェックポイントがあるときは、それらを読みません）、追加の経路を通れないときです。新しいドキュメントの基礎 Rig を生成し、古いエントリが見ていた部分を取り（`BuiltRig.resolvedPuppet(records)`。境界より前の v2 分割記録のパーツは所定の位置にあり、それよりあとの記録の乗客は残します）、現在の基礎 Rig の `resolvedPuppet()` と中立 IR で比較します。異なるときは、現在の基礎を G、新しい基礎を G′、現在のオーサード Rig を M としてマージし（`RigRegeneration.merge`。G と M は先に新しいテクスチャアトラスへ再バインドします）、現在のログの末尾、今回の編集の新しいエントリより前に `rig_checkpoint` を挿入します。同じときは、通常どおり再生します。
- **親の上書きと描画順の上書き**。どちらも基礎生成の入力です。生成されたモデルの上でこれらを変えても、同様に再生成としてマージし、チェックポイントを書きます（チェックポイントだけを通して構築するときは基礎 Rig を生成しないので、マージしなければこれらは見えません）。
- **生成設定と分類**（`RigGenerationChange.changed` が変化と認めるもの。顔の特徴、口形、メッシュのみ、頭と体の強度、`rigTuning`、レイヤー分類）。生成されたモデルは、編集の準備の時点でマージし、チェックポイントを書きます（`WorkspacePreviewBuilder.normalizeMeshEdits`）。G′ は現在のソース画像から生成し（保存済みのメッシュ入力はそのまま使い、`generationSource` が凍結したあと加わったレイヤーもその中にあります）、`rig_generation_transition`、`rig_generation_frames`、および移行に伴って作るメッシュ記録は、もはや書きません。マージは現在のログ末尾のオーサード Rig から始まるので、同じ 1 回の編集が追加できるエントリは、その後ろだけです。より早いエントリを同時に書き換える編集は拒否します（「分けて確定」）。古いエントリを、新しい生成結果の上へ静かに再生し直すことはありません。CMO3 をインポートしたモデルには、マージできる生成結果がないので、引き続き移行記録を書きます（[旧版の再生](#旧版の再生) を参照）。
- **分割**（`RigRegenerationCheckpoint.split`）。[分割の実体化](#分割の実体化アートプリミティブ記録-art_primitive) を参照。チェックポイントは分割記録のあとに書き、記録そのものは再生しません。
- **記録**（`RigCheckpoint`）。オーサード Rig の索引（オブジェクトは `RigObjects` にあり、ドキュメントとともに永続化します）、それが基づく生成スナップショット、マージの問題です。モデルプリセットが髪のシミュレーションを有効にするときは、プリセットの内部でも同様にマージしてチェックポイントを書き、マージ後の Rig でウェイトを計算します。
- **直接編集**。生成されたモデルの上で、ログを継続してエントリを追加する編集は、ログにチェックポイントがないとき、または最後のチェックポイントのあとにすでに `RigEditOverlay.CHECKPOINT_INTERVAL`（32）件があるとき、先に元のログの末尾、新しいエントリより前へ、現在のオーサード Rig のチェックポイントを書きます（`RigEditOverlay.checkpointsBeforeEntries`、`WorkspacePreviewBuilder`）。生成スナップショットは、前のチェックポイントが保存したものを引き継ぎ、ないときは現在の基礎 Rig を取ります。そのため、最初の編集のあと、どの構築も最大で 32 件に今回の編集のエントリを足した分しか再生しません。追加するエントリは現在のオーサード Rig に作用し、より早いエントリを書き換える編集（ドラッグのマージ、取り消し、やり直し）は、チェックポイントからそのあとのエントリを再生するか、保存済みの改訂を取ります（`PSD2LivePipeline.updateRigEdits`、`RigPreviewModel.authoredWithoutBase`）。どちらも基礎 Rig は生成しません。tml のサンプルでは、最初の編集がおよそ 0.2 秒、そのあとのチェックポイント化がおよそ 50 ms、コールド構築がおよそ 0.2 秒です。CMO3 をインポートしたモデルも、この 2 種類のチェックポイントを書きます（生成スナップショットは持たず、バインドキーは `cmo3-import` です）。インポートのベースラインの上で、チェックポイントから再生します。
- **再生**。`replayAuthored` は最後のチェックポイントから始め、その Rig を `reboundTo` で基礎 Rig のテクスチャアトラスへバインドし、そのあとのエントリを 1 件ずつ再生します（再生チェックポイントは通しません。再生チェックポイント `core.legacy.ReplayCheckpoints` は、チェックポイントを持たないログだけに使います）。`authoredRig` のメッシュ対応は、チェックポイントの頭部から取ります。そのあとに `art_primitive` 記録がないときは、構築はチェックポイントから直接行います（`RigEditOverlay.authoredFromCheckpoint`、`materializedPreview(rebind = true)`）。基礎 Rig は生成しません。
- **生成ベースライン**。`rig_generation_baseline` が凍結した生成設定と分類が基礎生成を制約するのは、そのあとにチェックポイントがないときだけです（`RigGenerationBaseline.restore`）。それよりあとのエントリは、すべてチェックポイントから再生を始め、基礎生成はドキュメントの現在の設定で行います。
- **確定**。ランタイムは、再構築が挿入したチェックポイントを、確定するドキュメントへ取り込みます（`WorkspaceRuntime.adopted`）。バッチのメンバーは、1 つ前の候補から構築し（`rebuildFrom`）、マージの M は 1 つ前の候補のオーサードです。
- **仕上げ段階**は、引き続きログ全体を走査します。生成結果の上書きと、遅延したパネル編集は、チェックポイントの影響を受けません。
- **報告**。最後のチェックポイントの問題は、`RegenerationQuality` を経て `workspace_inspect` の `quality.regeneration` へ入ります。確定の前に `workspace_preview_regeneration` で試行実行できます。確定と同じように候補を準備して再構築し、書き込む予定のチェックポイント（`regeneration` はマージの問題を持ち、`materialized` は新しいエントリより前のオーサードです）と、増減するオブジェクトを報告し、何も公開しません（`WorkspaceDocumentCommands.previewRegeneration`）。
- **シミュレーションのベイク**は、オーサード Rig が仕上げ段階を経た結果を読みます（`SimAuthoring.AuthoredRigs`、`RigPreviewModel.authoredPuppet`）。基礎 Rig は生成しません。
- 生成されたモデルでスケルトンを有効にしたあとは、ログの中で頂点グループを再サンプリングしません（マージがそれらを移行します）。CMO3 をインポートしたモデルには、マージできる生成結果がないので、従来の方式のまま処理します。

## 生成結果の上書き

- キーフォームの所有者はグラフが決めます。編集したキーの中であるパラメータが既定値を離れ、グラフの中に `keyform:<类型>:<目标>@<该参数>` を所有するジェネレーターがあるとき、そのマスは生成されたマスです。
- **スイング**は、そのパラメータ軸が対象 Warp の上に追加するキーフォームを所有します。上書きは、ジェネレーター、対象 `warp:<ID>`、完全なキー、そのとき生成された格子（`base`）、ユーザーの格子（`points`）を記録し、制御点ごとにマージします。
- **ベイクしたシミュレーション**は、モードパラメータがベイクメッシュの上に持つキーフォームを所有します（キーフォーム軸として書き戻すシミュレーションです。ブレンドシェイプとして書き戻すときは、メッシュの格子の中にその軸がなく、編集は上書きとして認識しません）。上書きは、対象 `mesh:<ID>`、そのとき生成された頂点オフセット（`base`）、ユーザーが編集したあとのオフセット（`points`。現在のモデルへそのキャンバス編集を適用して得ます）を記録し、頂点ごとにマージします。ベイクし直したあと、またはゲインを変えたあと、ユーザーが動かしていない頂点は新しいベイクに従い、ユーザーが動かしてベイクが変えていない頂点は残り、両方が変えた頂点はユーザーの値を残して衝突を報告します。
- **チャンネル**。ジェネレーターが自分の軸へ打った、透明度、描画順、乗算色、スクリーン色のキーフォームも、同様にそれの所有です。あるチャンネルのトラックがログよりあとではじめてジェネレーターの軸を持ち（オーサード Rig の同じトラックにはその軸がなく）、編集したキーの中でそのパラメータが既定値を離れるとき、そのマスは生成されたものです。キーフォームの `set` がそれを書くとき、そのようなチャンネルごとに、`channel`（`opacity` / `draw_order` / `multiply_color` / `screen_color`）付きの上書きを 1 件書きます。`base` はそのとき生成された値、`points` はユーザーの値です（スカラーは数 1 つ、色は成分 3 つ）。再生するときは成分ごとに三者マージし、衝突と孤立は通常どおり報告します（`GeneratedOverrideIssue.channel`。品質レポートの `evidence.channel`）。同じ 1 件の `set` の中で、ジェネレーターが打っていないチャンネルと、ログ自身がその軸の上に作ったトラックは、通常のログ編集のままです。生成されたチャンネルのマスへコピーする、またはそこからコピーする、ジェネレーターがチャンネルの上に持つキーを削除する、これらも記録の時点で拒否します。オーサード Rig を持たない呼び出し側（`ownedWrites` が `authored` を渡さないとき）は、チャンネルの上書きを認識せず、挙動はこれまでと同じです。現在、ログよりあとにチャンネルを打つジェネレーターはありません。この経路は、静的な主光源や透過表示など、色または透明度のキーフォームを書くジェネレーターのために用意しています。
- これまで、これらのキーフォームの上のキャンバス編集は通常の `canvas_geometry` として書き、再生のときパラメータがまだ存在せず、再構築全体が失敗して、編集を確定できませんでした。今は、確定のときに上書きへ書き換えます。
- ジェネレーターが削除された、ベイクした（スイング）、ベイクを取り消した（シミュレーション）、または軸を変えたあと、キーが生成されたマスに対応しなくなると、上書きは効かず、孤立として報告します。その下の静止形へ落ちることはありません。メッシュを生成し直して頂点数が変わったときも、同様に孤立として報告します。
- 生成パラメータの既定値での編集は、引き続き通常の編集で、変えるのは静止形状です。古いプロジェクトの中のコマンドは変わりません。上書きを書くのは、新しい確定だけです。
- Bezier の編集とキーフォームの `set`（MCP の `rig_deform` を含む）が生成されたマスへ書くときも、同様に上書きへ書き換えます。子の位置を残す編集、生成されたマスへコピーする、またはそこからコピーする、ジェネレーターの軸の上でキーを増減する、これらは上書きとして表せないので、記録の時点で拒否します（`GeneratedOverrides.ownedWrites`）。
- ほかのオブジェクトで生成パラメータを使うとき（キーを打つ、チャンネルのキーフォーム、改名、範囲の変更）、先にログの中で、ジェネレーターの現在の定義に従ってそのパラメータを作ります（`GeneratedParameterAdoption`）。そのあとパラメータはドキュメントに属し、ジェネレーターはそれを引き継ぎます。チェックポイント Rig を参照してください。
- 上書きは基礎 Rig の生成に影響しません。生成ジオメトリのキャッシュのキーは上書きコマンドを無視するので、上書きの増減で基礎 Rig が生成し直されることはありません。
- **問題の報告**。再生のたびに、記録どおりに効かなかった上書きを、構造化された記録として残します（`GeneratedOverrideIssue`。種別は `conflict` / `orphaned`、ジェネレーター ID、対象、完全なキー、衝突した点の数または孤立した上書きの点の数、形状の総点数。孤立のときは理由 `missing_keyform` / `shape_mismatch` / `superseded` を付けます）。`BuiltRig.overrideIssues` へ、ログの順に格納し、マージの意味は変えません。分割に置き換えられたメッシュの上の上書きの理由は `superseded` です。
- `core/quality/GeneratedOverrideQuality` は、これらの記録を観察レポートへ変換します（バージョン 4、領域 `overrides`、検査は 3 つ。`generated_overrides`。`superseded_entries` は、バージョン 2 の分割より前に、それが置き換えたメッシュが失敗したことだけを理由に、空操作として再生したエントリで、レベルは info。`see_through` は、設定が要求するのに作れなかった前髪越しの複製で、`SEE_THROUGH_DROPPED`、レベルは info）。衝突は `GENERATED_OVERRIDE_CONFLICT`、孤立は `GENERATED_OVERRIDE_ORPHANED` です。レベルは規則の列挙だけが決め（いずれも warning。`can_proceed` は常に true）、テキストからは推定しません。問題がないときは、レポートは完全で findings は空です。MCP の `workspace_inspect`（scope は `project`。プロジェクトを読み込み済みのとき）は `quality.overrides` を返します。厳密な構造は `WorkspaceQualitySchemas` を参照してください。
- インスペクターのツールバーは、問題があるとき件数のバッジを表示し、選択中のオブジェクトの問題をインスペクターの上部に列挙します。バッジをクリックすると、すべての問題の一覧へ切り替わります。文言は、種別と理由コードでローカライズします（中国語、英語、日本語）。

スケルトンのベイクの補正キーフォームは、上書きへ変えていません（`skeleton.skin` が、ログの配置したメッシュの上に書くキーフォームは除きます。[ログが配置したメッシュ](#ログが配置したメッシュ) を参照）。スケルトンは編集ログより前に実行し、ログの中のキャンバス編集はもともとスケルトンのあとに再生し、メッシュの再構築とともに新しいトポロジへ移行します。上書きへ変えると、かえってメッシュを分け直したあとに孤立します。物理グループと生成モーションは、既存の全体上書きを引き継ぎます（同じ ID のユーザーの物理グループが生成グループを置き換え、`builtin` のモーションクリップが生成モーションを置き換えます）。

## 計測と生成キャッシュ

`GeneratorCostTool`（`PSD2LIVE_TOOLS=1`）は、tml の上で各ジェネレーターと、その入力の内容ハッシュの所要時間を測り、`build/tools/generator-cost/report.txt` へ出力します。

| 項目 | 生成 | 入力ハッシュ | 結論 |
| --- | --- | --- | --- |
| スケルトンのベイク（自動スケルトン） | およそ 4.7 秒 | およそ 5 ms（基礎 Rig の IR + スケルトン定義） | キャッシュへ接続し、ヒット後の Rig 生成はおよそ 20 ms |
| 生成モーション（すべてのプリセット。スケルトンのプリセットを含む） | およそ 16 ms | 1 ms 未満 | キャッシュへ接続し、ヒット後はおよそ 1 ms。Rig IR のコンパイルはおよそ 16 ms からおよそ 2 ms へ下がります |
| スイング（2 つ） | 2.8 ms | 8.4 ms | 内容ハッシュのキャッシュはしません。オブジェクト単位の読み取り集合で参照を比べたあと、出力パッチを再利用します（[増分再生](#増分再生) を参照） |
| ベイクしたシミュレーションの書き戻し | およそ 0.8 ms | およそ 8.6 ms（ベイク JSON） | 同上 |
| 物理グループの目録 | およそ 0.1 ms | およそ 0.1 ms | キャッシュしません |
| シミュレーションのベイクそのもの | およそ 13 秒 | — | 明示的な操作です。結果はすでにドキュメントに保存してあり、再計算しません |

- スケルトンのキャッシュキーに含めるのは、ベイクが実際に読む内容だけです。ボーンにバインドしたメッシュ（完全。UV は未バインドのレイヤーオフセット）。ボーンを掛ける、曲げる Warp と、メッシュのバインドに使うデフォーマ（体、呼吸、傾き、脚の Warp、頭部の回転、ボーン自身の ID、バインドしたメッシュの親）と、そのすべての祖先。パラメータ、パーツ、Glue、パラメータツリー。残りのデフォーマと Drawable は、ID、種類、順序、親だけを取ります。さらにスケルトン定義、体の枠、バインドしたメッシュの中の手作業トポロジ、立ちポーズ、インターフェースの言語を含みます（生成したデフォーマとパラメータの名称はローカライズ済みです）。テクスチャアトラス、ソースファイル、変形パスは、読むことも書くこともせず、キーに入りません。ヒットしても基礎 Rig が異なるときは、読んでいないデフォーマと Drawable（ベイク時の掛け替え後の親に従います）、テクスチャアトラス、ソースファイル、パスを新しい基礎 Rig から取り、描画順を導き直します。ベイクがほかの方法で、読んでいないオブジェクトを変えていたときは、その結果がヒットするのは、IR 全体が同じ基礎 Rig に対してだけです。キャッシュは最近の 4 件を残します。取り消し、履歴の切り替え、書き出しの前後で同じ Rig を繰り返し生成すること、およびボーンがメッシュをバインドしていないときのトポロジ編集やメッシュ設定（体の枠を変えないとき）は、ヒットします。スケルトン付きの完全なプレビュー再構築は、およそ 5.4 秒からおよそ 0.5 秒へ下がります。
- 内容ハッシュを安定させるため、Rig 生成の目と唇の変形パスは、メッシュ ID とパスの役割から派生する決定的な ID に変えました。これまで、生成のたびにランダムな UUID でした。
- リクエストが ID を与えない新しいオブジェクト（キャンバスと MCP が作る Warp、Rotation デフォーマ、Glue、変形パス、分割の断片、前後分割のレイヤーとメッシュ、インポートと追加のレイヤー）は、`StableIds` がリクエストの内容（`state`、`request_id` などの送信情報を除きます）から ID を派生します。同じドキュメントの上の同じリクエストは、再試行、試行実行、確定で同じ ID を得て、すでに使われているときは順に `_2`、`_3` を足します。バッチの中で参照する必要があるオブジェクトは、引き続きリクエストの中で ID を与えるべきです。ログとドキュメントにすでにある ID は、そのまま残します。セッション、タスク、履歴ノード、パラメータのスナップショット、素材ワークフローの記録など、Rig またはドキュメントのオブジェクトに属さない ID は、この制約を受けません。
- 生成モーションのキャッシュキーには、プリセット名、スケルトン定義、調整値、除外するパラメータが含まれます。
- 基礎 Rig そのものは、引き続き既存の `GeneratedGeometryCache`（生成入力を保存したプロジェクト）と、高速な再生経路が扱います。前者は最近の 4 件を残し（強い参照は最新の 1 件だけで、残りはソフト参照で、メモリが逼迫すると解放します）、取り消しと履歴の切り替えで最近の入力へ戻るときに再利用します。
- `canvas_geometry` のログエントリは、バージョン 2 から、実行位置のジオメトリに対する疎な量子化増分を保存します（`v`、`n`、`q`、任意の頂点インデックス `i`、整数増分 `d`）。生産側は引き続き絶対の点を提出し、`RigAuthoringJournal.compile` が符号化し、プレビューと確定が適用するのは、どちらも復号したあとのコマンドです。バージョン 1 の絶対の点は、通常どおり再生します。
- エディタのプレビューの moc3 パッケージは、読み戻して検証しません（`validateBundle`）。ユーザーへ書く書き出しは、引き続き検証します。テスト JVM（アサーション有効）または `psd2live.validatePreviewBundles=true` のときは、プレビューも同様に検証します。
- moc3 パッケージの中の physics3 と motion3 の生成と正規化（指数を展開する正規表現の置換）は、これまでおよそ 18–21 ms で、パッケージ全体の半分近くを占めていました。`Moc3Target` は、入力（物理グループ、モーション、パラメータの集合、ファイル名の接頭辞）に従って、最近の 4 件のテキストをキャッシュし、ジオメトリ編集はこれらの入力を変えません。Rig IR のコンパイルのモーション一覧も、入力に従って最近の 4 件をキャッシュします。これまで、コンパイルのたびに各プリセットがスケルトン定義を直列化して生成モーションのキャッシュを調べていました（およそ 2.5 ms。IR のコンパイルは 2.9 から 0.3 ms）。`POS_VALUES` は先に全長を計算してから一塊で書き、書き出し側は大きさがちょうど合うとき、バッファをそのまま渡してコピーしません（tml のスケルトン Rig の moc3 はおよそ 7 MB。書き出しは 13.7 から 6.8 ms）。パッケージ全体はおよそ 48 ms からおよそ 20 ms へ下がり、書き出しはバイト単位で変わりません（`ExportGoldenTool`）。Drawable ごとの IR キャッシュは作っていません。`PuppetIr.toIr` は配列を包むだけで、およそ 0.2 ms です。
- ジオメトリの安全検査は、オブジェクトを比較するとき、各メッシュとデフォーマのジオメトリをリストへ箱詰めしません。同じインスタンスは直接同じとみなし、それ以外は配列をビットごとに比較します。座標ごとのサンプリングは、各対象の参照面積と有効性の検査を再利用し、メッシュのサンプリングは選択用の正規化領域を飛ばし、ベースラインと候補の点が同じときは状態を再利用します。完全なレポートは、これまでとバイト単位で一致します（`SafetyGoldenTool` が無作為の編集 24 組を照合します）。通常のメッシュ編集はおよそ 15–30 ms から 2 ms 以内へ下がります。ボーンをバインドし、合成領域が 16384 個の座標までサンプリングされるメッシュは、引き続きおよそ 1 秒必要です（これまでおよそ 2–3 秒）。確定は、追加されたログコマンドに従って比較範囲を狭めます。規則は [MCP_AUTHORING.md](../agent/MCP_AUTHORING.md#ジオメトリ検査と試行実行) を参照してください。
- Rig の生成はテクスチャアトラスの配置を読みません。`RigBuilder` は先に未バインドの Rig を生成し（`BuiltRig.unbound`）、メッシュのテクスチャ座標は、頂点がレイヤー矩形の左上に対して持つキャンバス単位のオフセットです。テクスチャアトラスには、配置を持たないタイルだけがあり、ページはありません。そのあと `UvBinding` が、現在の配置に従ってページ UV へ換算し、ページとタイルへ書きます。同じレイヤー群で配置だけを変えると、未バインドの Rig とその内容ハッシュは変わらず、変わるのはバインド結果だけです。0..1 のレイヤー単位ではなくオフセットを使うのは、バインドが従来のページ UV をビットごとに再現するためです（書き出しはバイト単位で変わりません）。スケルトンは未バインドの Rig の上でベイクします（`BAKE_VERSION` の skeleton-3 以降）。関節の細分化が追加する頂点はレイヤーオフセットで補間し、そのあとほかの頂点とともに `UvBinding` がページ UV へ換算するので、ベイクはテクスチャアトラスを読みません。タイルの移動、拡大縮小、並べ替えは、いずれもスケルトンのキャッシュにヒットします（tml に自動スケルトンがあるとき、タイルを固定して密度を変え、予算を変える 1 回の確定はおよそ 4.5–10.8 秒からおよそ 30–140 ms へ下がり、さらに 1 レイヤーをソフト削除するときはおよそ 90–150 ms です。`TexturePerfTool`）。これまでページ UV の上で補間していたときと比べ、異なるのは追加頂点の UV の末位の丸めだけです。キャンバス、オフセット、ラスタ、ページ UV のあいだの換算は、一律に `LayerTexture` が提供します（ペイントの再マップ、生成 Rig の現在のテクスチャへの並べ替え、メッシュ移行のログ、CMO3 のインポートが共用します）。
- テクスチャアトラスとペイント（`AtlasLayout`）。自動レイアウトは規範的な矩形の配置です（`RectPack`、MaxRects。各タイルの四周に `padding` を残し、面積、長辺、高さの 3 つの順序で、それぞれ「最短辺の残り」と「最も低い底辺」の 2 つの採点を使い、ページ数が最も少なく、最終ページの使用高さが最も小さいものを取ります）。決めるのはドキュメントだけです。新規作成、開き直し、取り消し、ペイントの確定、書き出しは、同じレイアウトを得ます。求解の結果は、タイル寸法、ロック、固定、予算でキャッシュし（最近の 8 個）、テクスチャ寸法を変えない確定は求解し直しません。増分なのはページであってレイアウトではありません。各ページは、「ページ寸法 + 各タイルの矩形とピクセル要約」というレシピで合成してキャッシュします（ソフト参照。最近の 8 ページ）。レシピが変わっていないページは、前のモデルの同じ `AtlasPage` インスタンスをそのまま使います。変化したページは合成し直し、それが置き換えるページと異なる行を記録します。「変わっていないタイルは固定し、変化したタイルは別に空きを探す」という履歴に依存するレイアウトは採用していません。寸法が変わらないときは両者は同じです（タイルは元の位置へ描き直します）。寸法が変わるときは、どのレイアウトでもそのタイルの UV が変わり、ネイティブプレビューはメモリからモデルを再構築しなければならず、規範的な再配置が余分に行うのは、ページの合成 1 回と、またがる行の帯の符号化だけです（およそ 20 ms）。その代わり、レイアウトは編集履歴と無関係になります。
- ページ PNG の遅延符号化。`AtlasPage.png` は、書き出しが書く ImageIO の規範符号化で、書き出し、または IR のコンパイルが読むときだけ生成します。エディタの実行パッケージは `previewPng` を使い、16 行を 1 つの帯とし、Sub フィルタ、それぞれ独立した deflate（level 1。full flush で終えます）で符号化し、帯ごとに IDAT チャンクを 1 つ持ち、Adler-32 は各帯をまとめて求めます。復号したピクセルは、規範符号化と完全に同じです。派生ページは、汚れた行がある帯だけを符号化し直し、残りの帯は置き換えられるページから取ります。ページ全体をゼロから符号化するときは、帯を並列に処理します。変わっていないページのバイト配列は同じインスタンスのままなので、プレビューパッケージの指紋はハッシュし直さず、`CubismPreviewReload` は変化したページだけをアップロードします。
- ペイントの候補は、2 回目のパッキングをしません。メッシュを残すペイント（および画像の差し替え）は、`WorkspaceRasterEdits` の中でピクセルだけを切り取り（`RasterPaintCommit.paintedSource`）、生成入力を凍結します。Rig、テクスチャアトラス、実行パッケージは、すべてそのあとの 1 回の再構築から来ます。メッシュの再構築が必要なペイントは、引き続き `RasterPaintCommit.prepare` を呼んで移行記録を得ますが、プレビューの実行パッケージはコンパイルしません。再構築のとき、`WorkspacePreviewBuilder` は現在のモデルのテクスチャアトラスを `buildPreview` へ渡し、そのページと帯だけを借りるので、結果はゼロから構築したものと完全に同じです。
- 並べ替えたあとの基礎 Rig は、「生成ジオメトリのキャッシュエントリ + レイアウト + テクスチャレイヤーのメタデータ（ピクセルは含みません）+ 新しいメッシュ ID」で、最近の 4 個をキャッシュします。タイルの寸法と位置が変わらないペイントは、同じ基礎 Rig のインスタンスを得るので、再生チェックポイントは引き続きヒットします。レイヤーの不透明度の統計（`LayerClassifier`）はラスタ配列の身元でキャッシュし、合成プレビュー画像（`PreviewRenderer.composite`）は各レイヤーのラスタの身元と位置で最近の 3 個をキャッシュし、再構築はペイントされたレイヤーだけを走査し直します。

## Rig の生成段階

`RigBuilder.build` は、宣言した入力を持つ段階に分かれます。各段階の出力は、`RigStageCache`（パイプラインごとに 1 つ。`PreviewMeshCache` に掛かります）が、「その段階が読む内容だけ」を含むキーでキャッシュします。キーは、既存の安い要約と設定の部分集合を取ります。ラスタは、配列の身元で記憶した SHA-256（`RasterDigest`）です。レイヤーのメタデータ（ID、名称、グループ、順序、境界、意味、足跡の境界と重心、不透明ピクセル数）と、`stageConfig` です。これが残すのは、メッシュ、口、強度と調整、生成モード、ランタイムの対象だけです。スケルトン、ログ、レイヤーごとの表、表示と非表示、描画順、テクスチャ、物理、モーション、書き出しの設定は、いずれもキーに入りません。スケルトンを読む段階は、読んだ部分を自分でキーに入れます。

| 段階 | キー（読む内容） | 容量 |
| --- | --- | ---: |
| 足跡 `footprint` | ラスタの寸法と要約、整数位置、アルファのしきい値、そのレイヤーのメッシュ設定、メッシュの尺度 | 512 |
| 枠組み（毎回計算。およそ 1 ms） | 足跡付きの解析。アンカー、顔の Rig、頭、顔、髪の枠、立ちポーズと体の枠 | — |
| デフォーマ `deformers` | 立ちポーズの内容キー、各枠、顔の Rig のすべての数値、アンカー、左右があるレイヤー（メタデータ + Rig 空間の境界）、上衣の境界、設定。スケルトンはスイッチと、使える最初の上半身ボーンの両端だけを取ります（`torsoFrame`） | 8 |
| 顔の前傾 `lean` | デフォーマ一覧のインスタンス | 8 |
| メッシュ `mesh:<图层>` | レイヤーのメタデータとピクセル要約、Rig 空間の境界と重心、親とその枠、頭部空間。目のレイヤーは顔の Rig を取り、対応する白目の境界、メッシュの尺度、そのレイヤーのメッシュ上書き、設定 | 1024 |
| チャンネル `channels` | 種別、パラメータ、開閉のキー、意味、歯のフェードアウト | 256 |
| 唇 `lips` | 所属する Drawable、メッシュ段階の出力インスタンス、親の枠、唇レイヤーのメタデータ、ピクセル、パックするかどうか、描画順、表示と非表示、設定 | 64 |
| バインドとスケルトン `bound` | 組み立てたモデル（構造が等しく、メッシュはインスタンスで比較）、髪のシミュレーションのスイッチ、テクスチャアトラスの配置とページ寸法、各レイヤーのバインドメタデータ、スケルトン定義と入力、残りの結果フィールド、スケルトンキャッシュを空にした回数 | 4 |

- 組み立て（マスク、パーツ、パラメータ）は毎回やり直します。およそ 1 ms です。すべての段階がヒットするとき、`bound` は前回と同じ `BuiltRig` インスタンスを直接返します。`generatedBase` の並べ替えキャッシュは、ジオメトリのキャッシュエントリではなく、ジオメトリ Rig のインスタンスをキーにするので、どの段階も読まない内容だけを変えたとき（たとえばログエントリを追加して生成ジオメトリのキャッシュが不一致になるとき）も、基礎 Rig は同じインスタンスのままで、再生チェックポイントは引き続きヒットします。
- `bound` にヒットするとき、そのスケルトンのベイクを最近の使用として印します（`SkeletonRig.touch`）。プロジェクトを保存するとき、頭部キャッシュ（`ProjectHeadCache`）が取るのは、引き続き現在のベイクです。`SkeletonRig.clearCache` が増やすカウントはキーに入るので、空にしたあとはベイクし直します。`bound` は引き続きテクスチャアトラスの配置をキーにしますが、その中のスケルトンのベイクは配置を読みません。テクスチャアトラスが変化すると `bound` は不一致になり、スケルトンのキャッシュはヒットして、バインドだけをやり直します。
- メッシュ設定が変わると、そのレイヤーの足跡がアンカーと枠組みを動かすことがあり、親の枠が変わったメッシュはそれに伴って再構築します（tml で下衣のメッシュを変えると、およそ 5 個のメッシュを再構築します）。顔の各レイヤーのメッシュは、元のインスタンスを保ちます。
- `PreviewMeshCache` のラスタ要約は、配列で記憶する `RasterDigest` に変えました。これまで、呼び出すたびに各レイヤーをハッシュし直していました。
- `-Dpsd2live.rigStages=false`（`RigStageCache.enabled = false`）は、段階キャッシュと要約の記憶を閉じ、比較に使います。

**正しさ**。`ExportGoldenTool` は、変更前（bcf919f2）とバイト単位で一致します。

**スケルトンの確定**。スケルトンの編集（ボーンの作成、バインド、関節の移動、ボーンの削除）は `bound` を不一致にし、スケルトンをベイクし直します。ベイクは `SkeletonRig` の中でさらに 2 段のキャッシュに分かれ、触れていない四肢は再計算しません。

- 単一メッシュのスキン（`skinDrawable`。ベイクの主な所要時間）は、読む内容のすべてでキャッシュします。そのメッシュとそのデフォーマ鎖（四肢の木の各ボーン、親、ホスト、およびすべての祖先）の損失のない IR、IR に現れるパラメータとその木の各ボーンパラメータの範囲と既定値、静止時のキャンバス頂点、木の中の各ボーンとその親ボーン、プリセットポーズ、帰属するボーン、木の中のブレンドシェイプのボーン、サンプリング、手描きのウェイト、ホストです。値はソフト参照で、最大 128 項です。`SkeletonRig.clearCache` は一緒に空にします。
- 関節の細分化（`SkeletonMeshRefine`）は、メッシュ配列、静止時のキャンバス頂点、関節帯、段数でキャッシュします。
- ベイク全体のキャッシュキーは、同じ基礎 Rig のインスタンスと同じ入力に対して、1 回だけ計算します。
- 触れたメッシュ自身のスキンでは、各サンプル（ある組のボーンパラメータ値の下での `computeDeltas`。各ボーンの変換、関節テンプレート、ARAP、表面の平滑）は、そのパラメータ値だけに依存します。そのため、フィット、キーフォームのマス、ポーズのブレンドシェイプに必要なサンプルは、まとめて共通のスレッドプールで並列に解き、元の順序で読み戻します。結果はスレッド数に依存せず、逐次の求解とビットごとに同じです（`SkeletonRig.parallelSamples` は、テストが閉じるためだけにあります）。フィット（`fittedSides`）は各ボーンの両側を同期して進め、各ラウンドは元の順序で各区間を検査し、先に取るのは少数の後続区間だけで、余分に計算するのは失敗した区間よりあとのサンプルだけです。ARAP の大域方程式（自由頂点のラプラシアン行列に、そのポーズの誘導の罰則項を足したもの）は、1 回の求解のすべての局所と大域の反復、および 2 つの座標軸の上で変わらないので、求解のたびに包絡コレスキー分解を 1 回行うように変えました（逆 Cuthill-McKee の並べ替えと包絡は、メッシュごとに 1 回だけ計算します）。大域ステップのたびに行うのは三角の後退代入 2 回で、ステップごとに最大 200 回反復する共役勾配を置き換えます。共役勾配の結果との差は、4096² のキャンバスで 0.0005 px を超えません（`SkeletonBakeDiffTool`。すべてのキーフォームとブレンドシェイプのキー。レンダリングはピクセルごとに同じです）。`BAKE_VERSION` は skeleton-4、スキンのキャッシュバージョンは skin-2 で、古いバージョンが書いた頭部キャッシュはヒットしません。フィットの許容差は、引き続きキャンバス 1 ピクセルです。サンプル数はキャンバスが大きくなると増えますが、現在の所要時間では、既存プロジェクトのキーフォーム数をこのために変える必要はありません。
- デフォーマの段階がキーに入れるのは、スイッチと上半身のボーンだけです（上の表を参照）。ほかのボーン、バインド、ポーズ、ウェイトの変更は、デフォーマのインスタンスを保ちます。

残りは主に、正規化の構築と確定の構築の中の解析と、ランタイムパッケージです。`SkeletonCommitTool.equivalence` は、ボーンの作成、バインド、移動、ジオメトリ編集、取り消し、やり直し、分岐の切り替え、ボーンの削除のあと、ランタイムモデルと、すべてのキャッシュを空にし、段階キャッシュとチェックポイントを閉じたコールド再構築（再生後の Rig、基礎 Rig の IR ハッシュ、ランタイムファイル）を段階的に比較し、すべて一致します。`SkeletonIncrementalBakeTest` は、キャッシュのヒット範囲がコールドベイクと一致することを覆い、並列と逐次でサンプルを解いたベイクがビットごとに同じであることを比較します。`SkeletonArapTest` は、分解による求解と共役勾配による求解を比較します。

**効果**（`CommitPerfTool.rigStages`、`PSD2LIVE_TOOLS=1`。同一マシンの同じ 1 回の実行で、先に閉じてから段階キャッシュを開きます。`WorkspaceGenerationCommands` を経た確定の実時間の中央値）は、次のとおりです。

## レイヤーごとの寸法

レイヤーのキャンバス上の位置と、ピクセル数は互いに独立です（`core/LayerSpace.kt`）。

- キャンバス矩形は、浮動小数のキャンバス単位です。つまりソースレイヤーの `rect` で、既定は整数の境界です。レイヤーがキャンバスのどこにあるかを決め、ペイントや画像の差し替えなどのピクセル操作は、これを変えません。
- ラスタは、レイヤーの実際のソースピクセル W×H で、任意の解像度にできます。
- ネイティブ密度は、ラスタピクセル / キャンバス単位で、2 軸は異なってもかまいません。ラスタが整数境界をちょうど覆い（1 ピクセルが 1 キャンバス単位）、分数の矩形を持たないレイヤーは、これまでと完全に同じです。

ジオメトリ（`core/CanvasDensity.kt`）は、次のとおりです。

- 解析、分類、アンカー、輪郭、メッシュ生成、唇、連結成分の分割は、いずれもキャンバス単位でラスタを読みます。密度が 1 でない、または矩形が分数のレイヤーは、解析のときキャンバス解像度のビュー `CanvasDensityLayer` へ置き換えます。同じレイヤーで、ラスタを面積平均（拡大するときはバイリニア）で整数境界へ、1 ピクセル 1 キャンバス単位へ再サンプリングし、矩形の外は透明です。そのため `meshTrace = CANVAS` の下では、32 単位の矩形の上の 1024² のラスタと 32² のラスタは、同じメッシュを生成します。完全に透明なプレースホルダのラスタは、ビューを取り替えません。`meshTrace = TEXTURE`（新規プロジェクトの既定）のときは、メッシュの輪郭だけがテクスチャそのものを読みます（元の密度で整数境界へ敷き、最大アルファで、メッシュ単位の 4 倍より細かくならない作業解像度まで縮めます）。頂点の間隔とオフセットは、引き続きキャンバス単位です。メッシュトポロジを参照してください。分類、アンカーなど、残りの解析は引き続きキャンバスビューを読みます。
- ジェネレーターのテクスチャ座標は、引き続き整数境界の左上に対するキャンバス単位のオフセットです。`UvBinding` / `LayerTexture` は、テクスチャレイヤー（`textureLayer`。ビューの背後にある元のラスタ）の空間で、オフセットを元のラスタへ、さらにタイルへ換算します。`raster = (offset − (rect − bounds)) × 密度` です。矩形が整数のとき減算項は 0 で、結果はこれまでとビットごとに同じです。
- プレビューの合成（`PreviewRenderer.drawLayer`）、素材ワークフロー、観察のレンダリングは、ラスタをキャンバス矩形へ伸ばして描きます。

テクスチャアトラス（`AtlasLayout`）は、次のとおりです。

- 各タイルのテクスチャピクセルは、ラスタピクセル × `textureUpscale` × 密度倍率（`textureOverrides.density`。既定 1、つまりラスタの元の解像度）× fit です。`textureUpscale` は、引き続き要約でキャッシュするソース画像の前処理で、効果はこれまでと同じです。
- ページ寸法は予算の `pageSize` を取り、これまでと同じように、最大レイヤーのキャンバス解像度の寸法を収められるまで大きくします（次の 2 の冪。最大 16384）。密度がもたらすはみ出しは、fit が処理します。
- fit ≤ 1 は、ロックしていないすべてのレイヤーが共有する 1 つの係数です。先に fit 1 で配置し、`maxPages` ページを超えなければ 1 を使います。超えるときは、1/4096 の整数ステップの上で二分探索し、収まる最大のステップを取ります。結果を決めるのはドキュメントだけで、同じ入力は同じレイアウトを得ます。ロックしたレイヤー（`lock`）は fit 1 を保ちます。固定したレイヤー（`pin`）は、指定したページ位置へ先に置き、矩形の配置はそれらを避けます。
- ロックまたは固定したレイヤーが、それだけで予算を超えるときは、静かに縮小しません。ロックと固定を外したあと一緒に fit を求め、`PackedAtlas.notices` の中で説明します（プログラムのログへ書くだけです）。1/4096 でも収まらないときは、fit 1 のままページ数を超えて、説明します。fit < 1 のときも、同様に説明を出します。説明は書き出しの警告へ入ります。
- タイル寸法がラスタと等しくないときは、`RasterResample`（`format-compile`。決定的。アルファを事前乗算）で再サンプリングします。ページのレシピは「タイル矩形 + ピクセル要約」をキーにするので、影響を受けません。配置の `scaleX/scaleY` は、タイルピクセル / ラスタピクセルです。
- 既定値（すべてのラスタが境界と等しく、既定の密度、既存の設定、fit 1）の下では、レイアウト、UV、ページ、書き出しは、これまでとバイト単位で同じです（`ExportGoldenTool`）。
- 保存した配置（`atlasArrangement` 設定。`project/AtlasArrangement.kt`）があるとき、`AtlasLayout` は自動レイアウトを求めず、`AtlasArrange.keep` が保存した位置と fit で配置します。予算のページ内にあり、ページからはみ出さず、すでに置いたタイルと衝突しないタイルは、元の位置を残します。それ以外（新しいレイヤー、大きくなって隣と重なる、またはページからはみ出すタイル）は、ページの 4×4 ピクセルのセル格子の、最初の空き位置へ入れます。説明を出すのは、元の保存位置が失効したタイルだけで、新しいレイヤー（分割に置き換えられ、まだ圧縮で消えていない元レイヤーを含む）は、静かに入れます。矩形タイル同士は `padding` の間隔で判断し、メッシュの覆う区域が関わるときはセルで判断し、`ceil(2×padding/4)` セルだけ広げます。保存した覆う区域は、構築のたびにタイルの現在のラスタで補正します（`AtlasArrange.covering`）。セル格子がラスタ寸法と合わないとき（ペイントまたは画像の差し替えが切り取りを変えたとき）は無効にし、タイル全体の矩形として扱います。ラスタの中でアルファが 8 以上のピクセルが覆う区域の外に落ちるとき（ペイントがメッシュを超えたとき）は、それらのセルを補うので、隣のタイルがそれと衝突するときは空きへ押し出され、互いに重なることはありません。空きへ移したタイルも、同様に覆う区域で探し、自分のセルだけを書きます。凍結した規範レイアウトから得た配置は、バイト単位で同じページを再構築します。
- 一度きりの配置（`atlas_pack`、`AtlasLayout.arrange`）では、メッシュの覆う区域を、現在のモデルの最終メッシュのテクスチャ座標から取り、ラスタの中でメッシュの外にあるピクセルのセルを補います（`WorkspaceAtlasFootprints`。セルはラスタ 4 ピクセル、各辺は最大 192 セル。三角形とセルが交わるには 0.01 ピクセル深く入る必要があり、レイアウトが変わったあとの末位の丸めが結果を変えることを避けます）。面積、高さ、長辺の 3 つの順序で、セル格子の上を上から下、左から右へ最初に適合する位置へ置き、ページ数が最も少なく、最終ページの使用行が最も少ないものを取ります。矩形は互いに入れ子になれます。予算のページ数に収まらないときは、fit を先に 64/4096 ステップで二分し、そのあと 8/4096 まで細かくします。矩形だけで配置するとき（`shape=rect`）は、自動レイアウトの結果を直接凍結します。ページを合成するとき、覆う区域を持つタイルは自分のセルだけを書きます（`TileKey.mask` がレシピに入ります）。次元を上げたテクスチャも、隣の外へ縁を広げません。そのあとのメッシュ編集が、配置したときの覆う区域を超えると、テクスチャアトラスが読む `notices` が、配置し直すよう知らせます。自動配置（`auto=true`）は、保存した配置を削除します。閉じるとき、またはタイルを動かすときは、現在のレイアウトを保存します。保存した配置の下では、位置を保てるタイルがないもの（新しいレイヤー、分割パーツ、隣が大きくなって押し出されたタイル）は、再構築のたびに最初の空き位置へ入れ直します。そのため、タイルを動かすときと、密度またはロックを変えるときは、先に現在のモデルのすべてのタイル位置を配置へ書き戻します（`WorkspaceTextureEdits.settled`）。これらのタイルはそのあと元の位置を保ち、動かしたあと、または縮小したあとに空いた位置へは入りません。同時に、覆う区域を持たないタイルには、そのメッシュの覆う区域を補います（`meshed`、`WorkspaceAtlasFootprints`）。そのあとタイルは、メッシュが実際に使うセルだけで重なりを判断し、テクスチャアトラスビューでドラッグするときの判断（`WorkspaceTextureView.meshFootprint`）と完全に一致するので、ビューが許す位置が、そのまま着地する位置です。タイルは中心を軸に回転できます（`ArrangedTile.rotation`、`AtlasPlacement.rotation`）。ページの合成は回転を逆にサンプリングし（`AtlasLayout.writeTurned`。メッシュのセルだけを書きます）、覆う区域は回転後のセルで交差を求め（`AtlasArrange.shape` の `rotation`）、メッシュの UV は `LayerTexture.tilePlacement` で Umamo の回転配置へ換算し、書き出しも同様に回転を持ち出します。テクスチャアトラスビューの移動、拡大縮小、回転は編集セッションです（`TextureWorkspaceState.session`）。変えるのはビューの表示だけです。適用するときは、密度と位置を 1 つの `layer_set_pixel_density` / `atlas_set_tile` のバッチとして確定し、再構築は 1 回、履歴ノードは 1 つです。この 2 種類の編集（単項目またはバッチ。GUI または MCP）は、公開の前に `WorkspaceTextureEdits.requireKept` が候補モデルを比較します。それまで位置を保っていたタイルのいずれかが、新しいレイアウトで配置位置から押し出されると、`WorkspaceTileCollision`（`tile_collides`）を投げ、その回は全体を確定しません。バッチが検査するのは最終レイアウトだけで、しかもバッチが再配置、予算の変更、ピクセルの置換、キャンバス矩形の移動を含まないときだけ検査します。対での判断（`AtlasArrange.meet`）は、先に間隔だけ外へ広げた回転の外接枠を比較し、交わるときだけメッシュのセルを比較するので、密な矩形配置へ覆う区域を補ったあと、セルの切り上げで誤って交差と判定することを避けます。
- メッシュの身元。生成入力を変える編集（レイヤーの増減、分類または生成設定の変更）は、正規化のとき、先に現在の各メッシュの ID を `splitDrawableIds` へ書きます（`WorkspacePreviewBuilder.pinnedIdentities`）。ジェネレーターはこれに従って命名します。そうしないと、分類と同類の通し番号から派生する ID が改名または番号の振り直しをし、再生成のマージが、ユーザーの古いメッシュを退役オブジェクトとして新しいメッシュの横に残します。
- レイヤーの削除（`layer_delete`、`WorkspaceLayerEdits`）は、本当の削除です。レイヤーはソース画像と生成入力から離れ、そのメッシュはログ記録 `layer_delete`（`LayerDeletionJournal`）でオーサード Rig から離れ、構築はその記録の前にチェックポイントを書き、それより前の作成記録は再生しません。取り消しは、履歴の切り替えです。次の遅延フィルタは、古いバージョンがソフト削除したレイヤー（`deletedLayerIds`。読み取り専用。`layer_restore` で戻せます）と、唇の帯などの派生行にだけ使います。
- ソフト削除したレイヤー（旧式の分割が残した元レイヤーを含む）は、遅延フィルタのモードでは、引き続き完全な生成と再生に参加し、完全なテクスチャアトラスがそのタイルをパックします。フィルタしたあとのモデルは、残したレイヤーだけでパックし直します（`RigLayerDeletion.compact`）。残ったメッシュは `RigGenerationSource.repack` で新しいテクスチャアトラスへ移り、キャンバス単位で換算し、同じテクセルをサンプリングします。そのためプレビュー、テクスチャワークスペース、CLI と GUI の書き出しは、いずれも削除済みレイヤーのピクセルを含みません。基礎 Rig がバインドした完全なテクスチャアトラスは `RigPreviewModel.generationAtlas` に記録し、高速な再生（`updateRigEdits`）はフィルタのあと、同様にバインドし直します。CMO3 のインポートは、元のレイアウトを残します。残ったメッシュがどのテクスチャアトラスでもタイルを見つけられないときは、完全なテクスチャアトラスへ戻します。レイヤーを戻すと、完全なテクスチャアトラスを再び得ます。分割に置き換えられた元レイヤー（`ArtPrimitiveJournal.visibleAnalysis` が除くもの）も同様です。生成のときは引き続きパックし、プレビューと書き出しは、再生のあと可視レイヤーで圧縮します。生成ジオメトリのテクスチャアトラス（`generationSource` のジオメトリ Rig）は、テクスチャの上書きと保存した配置を読まないので、テクスチャの確定はジオメトリのキャッシュを失効させません。

書き出しは、次のとおりです。

- moc3 が読むのはページとページ UV だけで、追加の処理は要りません。
- cmo3（`Cmo3LayerArt`、`targets/cubism`）。Cubism Editor のレイヤーは 1 ピクセルが 1 キャンバス単位で、エディタはレイヤーからテクスチャアトラスを再構築します。既定の `canvas` では、密度が 1 でないレイヤーを、キャンバス矩形の寸法（ダウンサンプリング）でレイヤー画像へ書き、保存するテクスチャアトラスのページは高解像度を残すので、タイルのパック倍率はそれに合わせて大きくなります。いずれかのタイルのテクスチャアトラス密度（テクスチャピクセル / キャンバス単位）が 1 より大きいだけで、書き出しは `TEXTURE_SIZE` / `APPROXIMATED` の損失項目を出します（「Cubism Editor rebuilds the atlas from canvas-resolution layers」）。従来の `textureUpscale` を持つプロジェクトにも、同様に適用します。内部設定 `layer_art=native` は、元の解像度でレイヤーを書き、モデル画像の変換でキャンバスへ拡大縮小します。エディタでの実測はまだで、既定はオフです。

画像の差し替え（`core/LayerImageReplace.kt`）は、次のとおりです。

- `LayerImageReplace.replace(document, layerId, raster, fit)` は候補ドキュメントを返します。キャンバス矩形と整数境界は変わらず、ラスタだけを置き換えます（`STRETCH` は直接伸ばし、`CONTAIN` は比率を保って中央に置き、透明を補います）。最初の差し替えのとき、それまでのソース画像を生成入力として凍結します（メッシュを残すペイントと同じです）。メッシュ、キーフォーム、バインドは変わらず、再構築のあと異なるのは、バインドした UV とページだけです。呼び出し側は、通常どおり再構築して確定します。

インポート（`core/LayerImport.kt`、素材ワークフロー、CMO3 のインポート）は、次のとおりです。

- 画像ファイルのインポート（`layer_import_images`）は、透明な縁を切り取ったあと、元のラスタを残します。キャンバスを超えるときは、キャンバス矩形だけをキャンバス内へ等比で縮小し、ラスタは変えないので、密度は 1 より大きくなります。収まる画像は、引き続き 1 ピクセル 1 キャンバス単位の整数境界で、これまでと同じです。
- インポートした画像は、1 回の確定で、オーサード Rig の中に自分のメッシュを持ちます（`canvas_mesh_create`）。生成入力は凍結せず、プレースホルダも書きません。ジェネレーターは、作成記録が所有するレイヤーを透明なプレースホルダとみなし（`RigGenerationSource.createdCoverage`）、それにテクスチャのタイルを打つだけです。
- レイヤー全体の変換（`layer_transform`、`application/WorkspaceLayerTransform`）。レイヤーのフレーム（整数境界と浮動小数の矩形）は変わらず、ピクセル、テクスチャのタイル、テクスチャ座標は、いずれもフレームに錨を下ろします。変換 `LayerTransform`（2×3 のアフィン）はレイヤーに記録し、レイヤーの各メッシュは、静止ポーズで物体モードの `canvas_geometry` を 1 件書きます。ジェネレーターが読むのはフレームだけで、変換は読まないので、移動は作者の編集であり、再生成ではありません。ペイントのセッションはフレームの中で行い、キャンバスは完全な変換で表示します（セッションのラスタは、レイヤーとともに回転する四辺形として描き、筆と形状は逆変換でフレームへ落ち、ブラシの大きさは変換の面積比で換算します）。物体モードのドラッグが、あるレイヤーのすべてのメッシュを覆うとき、キャンバスはその操作で確定します（`AffineFit` が、ドラッグの前後の点をフィットし、純移動、軸方向の拡大縮小、一般のアフィンの順に、最初に 0.01 キャンバス単位以内で合うものを取ります。回転していないドラッグが、浮動小数の雑音で回転として記録されることはありません。変換を合成するときは、100 万分の 1 の桁の残差を捨て、`isAxisAligned` は 1e-5 の相対回転角を許します）。`layer_set_canvas_rect` は、現在の表示矩形から出発する 1 回の変換です。レイヤー変換だけが異なるソース画像は、生成とテクスチャアトラスにとっては同じ 1 つです（`PSD2LivePipeline.sameArt`）。そのため移動は高速経路を通り、モデルは新しいソース画像を使います。作成記録が所有するレイヤーの増減だけ、またはレイヤーの移動だけの確定は、再生成の比較を飛ばします（`WorkspacePreviewBuilder.onlyUsersLayersChanged`）。開発ツール `LayerFlowPerfTool` は、インポート、移動、親の変更、再構築、削除の確定所要時間を測ります。
- 素材レイヤー（`layer_add_from_asset` / `layer_set_placement`）は、素材のピクセルをラスタとし、配置したキャンバス矩形をレイヤー矩形とします。`WorkspaceCanvasPlacement.canvasUnitsPerPixelX/Y` が実際の比です。平行移動、拡大縮小、明示的なミラーの位置合わせは補間しません（ミラーは行と列を反転するだけです）。回転を伴う位置合わせだけが、素材自身の密度で、外接枠へラスタ化します。
- CMO3 のインポートは、各タイルのモデル画像の変換（`_materialLocalToCanvasTransform`。umamo の `Cmo3AtlasIngest.canvasTransformByTile`）とパック倍率から、ページのテクセル / キャンバス単位を求めます。1 より大きいときは、レイヤーを同じ整数境界の上でその密度のラスタとして再構築します（たとえば高密度のレイヤーがテクスチャアトラスのページにだけ保存されている書き方と、レイヤーそのものをモデル画像でキャンバスへ拡大縮小する書き方の両方です）。そうでなければ、これまでとバイト単位で同じです。umamo のソースレイヤー一覧は、引き続きファイルが記録する、レイヤー画像の上の矩形のままで、キャンバスへは換算しません。
- 寸法の制限（`LayerSizeBudget`）。ラスタとキャンバス解像度のビュー（外接枠）は、それぞれ 16MP を超えず、ネイティブ密度は各軸 256 ピクセル / キャンバス単位を超えず、矩形は各軸少なくとも 0.5 単位です。超えるときは明確に拒否し、CMO3 のインポートが超えるときは、全体の密度を下げます。

ペイント（`core/PaintSpace.kt`）は、次のとおりです。

- ペイントは、レイヤー自身のラスタ格子の上で行います（`PaintSpace`）。下書き画像のピクセルが、レイヤーのラスタピクセルそのもので、同じ密度でキャンバスの縁まで伸び、16MP を超えるときは、レイヤーの周りの余白を比率で縮めます。ジェスチャ、半径、線幅、色の採取は、いずれもキャンバス単位で、アフィン写像で下書きのピクセルへ落ちます。2 軸の密度が異なるとき、ブラシの半径は幾何平均を取ります。密度が 1 で矩形が整数のレイヤー（および完全に透明なレイヤー）の下書きは、キャンバスそのもので、これまでとビットごとに同じです。
- 確定は、不透明ピクセルへ切り取ったラスタと、そのキャンバス矩形を持ちます（`WorkspacePaintRaster.rect`）。キャンバス解像度へは縮めません。矩形はレイヤーの元の矩形から測ります。動いていない辺は元の座標を残し、拡張も切り取りも密度を保ち、整数境界は外接枠を取り、矩形と整数境界が同じときは保存しません。確定のときは、レイヤーの元の区域と、筆が書いた区域だけを読み、キャンバス全体はコピーしません。完全に消したレイヤーはこれまでと同じで、キャンバス原点の 1×1 の透明ピクセルになります。
- 前後分割の前レイヤーは、ラスタ寸法を保ちます。ピクセル中心で確定ピクセルから採取し、格子が揃うときはビットごとにコピーします。メッシュを残すペイント、メッシュを再構築するペイント、CMO3 をインポートしたペイントは、いずれも `LayerSpace` でタイルをアドレスします（`RasterPaintCommit` のスライスの再マップ、`Cmo3ModelImport` のペイントのテクスチャ座標）。連結成分の分割は、ソースレイヤー自身のラスタの中でパーツを切り取り、パーツは元の密度を保ちます。

テクスチャのコマンド（`application/WorkspaceTextureEdits`、`WorkspaceTextureOperations`）。テクスチャワークスペース（テクスチャアトラスのページと密度のヒートマップ、レイヤーごとの寸法パネル、編集キャンバスの元ピクセルのプレビュー。[操作早見表](../guide/USER_GUIDE.md#テクスチャワークスペースの要点) を参照）は `WorkspaceTexturePort` を経て確定し、MCP の `layer_set_canvas_rect`、`layer_replace_image`、`layer_set_pixel_density`、`atlas_set_tile`、`atlas_set_budget`、`atlas_pack` と、同じ純粋な候補を共用します。いずれもバックグラウンドのタスクと、原子的なバッチのメンバーです。問い合わせは `layer_get_texture`、`atlas_get`、`atlas_check_placement`、`atlas_render_page` です（[MCP インターフェース](../agent/MCP_AUTHORING.md#テクスチャとテクスチャアトラス) を参照）。分数の矩形を umamo のソースレイヤー一覧（整数）へ書くときは、整数境界を取ります。一覧からテクスチャを解釈するメッシュの移行（`LayerTexture.of`）は、分数の矩形に対しては近似です（整数の矩形は厳密です。タイルの幅と高さがラスタ寸法、一覧がキャンバス寸法で、比が密度そのものです）。生成入力の縁の補完（`RigGenerationSource.padded`。メッシュを残すもの、新しいメッシュ、`art_primitive` のパーツのテクスチャの覆い）は、高密度のレイヤーに対して元の密度で透明を補い、ダウンサンプリングしません。`art_primitive`、`canvas_mesh_create` / `canvas_mesh_rebuild` の `canvas_uvs` はキャンバス単位で、`LayerTexture.of` を経て高解像度のタイルへ写像します。

## 性能ベースライン

`CommitPerfTool.baseline`（`PSD2LIVE_TOOLS=1`）は、tml の上に、自動スケルトン、スイング 2 つ（前髪、頭飾り）、ベイク済みの後ろ髪シミュレーション 1 つを持つプロジェクトを組み、段階ごとに確定経路を測り、`build/tools/commit-perf/baseline.json` と `baseline.md` へ出力します。数字は、Windows の開発機 1 台での 1 回の実行から取ったもので、同一マシンの前後比較にだけ使います。マシン、JIT のウォームアップ、同時負荷が異なれば、絶対値は 2 倍以上異なり得て、段階のあいだの比率の方が信頼できます。段階の値は、ウォームな呼び出しを複数回した平均です。確定の値は、アプリケーション層のコマンド境界を経た実時間です（確定のたびに履歴ストレージへ書く時間を含みます）。ネイティブの Cubism プレビューの再読み込みには、ネイティブランタイムと GL コンテキストが必要なので測っていません。測ったのは、再読み込みの前にランタイムファイルを書くこと（「書き出し」）だけです。

- 再生、改訂番号のハッシュ、ストレージの書き込みは、いずれもログの長さに対して線形に増えます（これがベースラインです。再生チェックポイントのあと、追加した確定の再生はログの長さと無関係です。[増分再生](#増分再生) を参照）。作業ストレージは、改訂ごとに完全なスナップショットを 1 つ書きます。200 件のとき、確定のたびにおよそ 7 MB 増え、場面の列全体のあとストレージはおよそ 1.2 GB です。
- スケルトンのキャッシュキーを狭めたあと、無関係なトポロジ編集のあとの完全な再構築では、スケルトンがヒットします（再ベイクは 0 回）。`canvas_geometry` を量子化増分で保存するように変えたあと、上の表でメッシュ全体を平行移動するエントリはおよそ 17 KB からおよそ 12 KB へ下がり（ログ 200 件は文字数 3.6 M から 2.5 M、再生はおよそ 82 から 66 ms）、一部の頂点だけを動かすブラシ編集は、動かした頂点数に応じて小さくなります。

- ペイントと画像の差し替えは、テクスチャアトラスのパッキングと PNG の符号化が支配し、しかも候補の準備と再構築がそれぞれ 1 回ずつ行います（これがベースラインです）。
- ペイントをレイヤーのラスタ空間で確定するように変えたあと（上記「レイヤーごとの寸法」のペイントを参照）、候補はキャンバス全体をコピーしません。ツールは、ペイントのセッションと同じキャプチャのしかた（レイヤーの元の区域と筆の区域）を使うように変え、同じマシンで、小さいレイヤーのペイント確定の中央値はおよそ 0.25 秒からおよそ 0.17 秒へ下がり、そのうち候補の準備はおよそ 56 ms からおよそ 1.5 ms へ下がり、残りは確定の中の再構築です。
- テクスチャアトラスを規範レイアウト + ページのレシピキャッシュ + 帯のプレビュー PNG に変え、ペイントの候補がパックしなくなったあと（上記「テクスチャアトラスとペイント」を参照）、同じマシンで同時負荷の下での前後比較です（2 回の実行の絶対値は、いずれも上の表の空きマシンの数字より高いです）。小さいレイヤーのペイント確定の中央値はおよそ 2.5 秒からおよそ 0.35 秒へ下がり（安定後はおよそ 0.3 秒）、そのうち候補の準備はおよそ 1.5 秒からおよそ 0.17 秒、確定の中の再構築はおよそ 1.2 秒からおよそ 0.2 秒です。同じ形状の画像差し替えはおよそ 2.1 秒からおよそ 0.3 秒です。ミラーして画像を差し替え、メッシュを再構築するのはおよそ 3.1 秒からおよそ 0.45–0.8 秒です。スケルトン付きの完全な再構築（スケルトンはヒット）はおよそ 1.0–1.6 秒からおよそ 0.25–0.4 秒です。ページ全体のプレビュー帯の符号化はおよそ 20 ms です（規範 PNG はおよそ 0.5 秒で、書き出しのときだけ生成します）。解析を 2 回合わせるとおよそ 0.2 秒からおよそ 0.03–0.06 秒です。書き出しファイルは変更前とバイト単位で同じです（`ExportGoldenTool`）。プレビューパッケージは、テクスチャページの PNG 符号化以外は変わりません。

**プロジェクトを開く**。スケルトンのベイクキャッシュはプロセスの中にだけあるので、コールドスタートのあと、スケルトン付きのプロジェクトを初めて開くときは、引き続きおよそ 5–7 秒ベイクします。保存するとき、頭部のベイクをアーカイブの任意の頭部キャッシュ `cache/head/` へ書きます（形式は [プロジェクト形式](PROJECT_FORMAT.md#ヘッドキャッシュ) を参照）。開くときは、revision、プログラムのバージョン、ジェネレーター定数、言語を照合したあと、`SkeletonRig` のキャッシュへ種をまきます。再構築は引き続き完全な経路を通り、ヒットするかどうかはスケルトンキャッシュ自身の内容キーが決め、結果はコールド再構築とビットごとに同じです。保存するベイクが残すのは、読み取り集合の中のメッシュとデフォーマだけで、読み取り集合の外のオブジェクトは ID と順序だけを残し、ヒットするときは新しい基礎 Rig から取ります。`OpenPerfTool.profile` は、上記の場面（スケルトン + スイング 2 つ + ベイク済みシミュレーション）で 3 種類のアーカイブを保存します。アプリの現在の書き方（各改訂のオーサード Rig と頭部キャッシュ。開くときは生成も再生もしません。チェックポイント Rig を参照）、頭部キャッシュだけ（生成と再生。スケルトンのベイクを種まき）、両方なし（生成、再生、スケルトンのベイク）です。開く前に毎回、オーサード Rig のストレージ（`MaterializedRigStore.clear()`）とスケルトンキャッシュ（`SkeletonRig.clearCache()`）を空にし、それぞれ 3 回開き、3 者が同じモデルを構築したことを照合します。下の表は、オーサード Rig を導入する前に、あとの 2 種類のアーカイブを測ったものです（それぞれ 3 回開き、スケルトンキャッシュは空です）。

| アーカイブ | 展開と種まき | 頭部の再構築 | 合計（つまり最初の表示） | スケルトンのベイク |
| --- | ---: | ---: | ---: | ---: |
| 両方なし（5.5 MB） | およそ 0.35–0.4 秒 | およそ 4.7–5.4 秒 | およそ 5.5 秒 | 毎回 1 |
| 頭部キャッシュだけ（10.9 MB。ベイクのエントリ 6.9 MB。圧縮後 5.4 MB） | およそ 0.37–0.47 秒 | およそ 0.18–0.25 秒 | およそ 0.7 秒 | 0 |

保存はおよそ 0.5 秒増えます（ベイクの直列化と圧縮）。開いたあとの最初の表示は、完全な再構築の結果そのもので、実行パッケージを別にキャッシュしてはいません。キャッシュがあるとき再構築はおよそ 0.2 秒しか残らないので、古い実行パッケージを先に表示してから置き換える利益は限られます。

## 分割の実体化：アートプリミティブ記録 `art_primitive`

これまでの分割（`canvas_source_partition`、`canvas_depth_split`）は、元のレイヤーをソース画像に残してソフト削除し、再生するときは先に元のメッシュをビットごとに生成し直し（ジオメトリの指紋と親を照合）、記録の位置でそのバインドをパーツへコピーしていました。これには 3 つの問題があります。生成規則が 1 つ変わると、古い記録は再生できません。テクスチャアトラスは引き続き元のレイヤーをパックし、CMO3 の書き出しがそのピクセルを連れます。「すべて戻す」が、元のレイヤーを連れ戻します。今の分割は、元のレイヤーをパーツとして**実体化**します。パーツが唯一の描画オブジェクトで、元のレイヤーは存在せず、分割の前へ取り消すことだけができます。

**分割は再生成です**（`WorkspaceArtPrimitives.materialize`、`RigRegenerationCheckpoint.split`）。分割はソース画像を変えます（元のレイヤーをパーツが置き換えます）。[チェックポイント](#チェックポイント) の方式でマージします。G は現在の生成結果、G′ はパーツが元のレイヤーに代わったあとの生成結果です。G と現在のオーサード M の中の元メッシュは、どちらも分割自身（`SplitParts`。連結成分と多角形は `SourcePartitionJournal.splitParts`、前後分割は `DepthSplit.splitParts`）が、同じパーツへ切ります。それぞれ自分のその元メッシュの静止位置、キーフォーム、チャンネル、ブレンドシェイプ、パス、頂点グループ、Glue を取り、同じ一組の頂点の出所を経るので、ユーザーが動かしていないパーツと、生成したパーツはビットごとに同じです。ユーザーが元メッシュへ行った変更はパーツの上の変更になり、三者マージ（`RigRegeneration.merge`）がそれらを G′ のパーツへ運びます（親が変わるときは親の空間で換算し、スケルトンが関節の行を挿入するときはキャンバスのテクスチャ座標で移行します）。分割が自分で新しく作る Glue（多角形の切断点の追従、前後分割の方向 Glue）は M の側にだけあり、ユーザーに属します。分割は `art_primitive` 記録を書き、その直後に `rig_checkpoint` を書きます（マージ結果と G′ のスナップショット）。記録そのものは、決して再生しません。そのあとの構築は、このチェックポイントから始まり、基礎 Rig は要りません。

- 元のメッシュをジェネレーターが生成しているとき、記録はバージョン 2 の**宣言**です。各パーツの静止キャンバスメッシュ（G の中の元メッシュから切り出したパーツを、生成デフォーマが既定ポーズの下でキャンバスへ換算したもの）、レイヤー、分類、`fixed_topology`（パーツがユーザーの Glue、頂点グループ、またはパスを持つとき真）を持ち、`authored` は空オブジェクト、`glues` は空です。基礎生成はこれに従ってパーツを生成します（[バージョン 2 の記録](#バージョン-2-の記録) を参照）。そのあとの顔の設定、立ちポーズ、スケルトン、分類の変化は、次のマージで同様にパーツへ届きます。
- 元のメッシュが生成されたものではないとき（ログが作ったメッシュ。たとえば生成入力を凍結したあとにインポートした画像）、記録はバージョン 1 で、パーツはすべてのデータを持ち、そのレイヤーは基礎生成へ入らず、パーツはマージの中でユーザーのオブジェクトです。
- バージョン 1 への後退、2 パスのキャプチャ、ガードはありません。マージは失敗せず、移行がきれいでない箇所は、マージの問題として報告します。元メッシュのトポロジを手で変えてあるとき、G の側からは同じパーツを切り出せないので、パーツはユーザーのトポロジとして残します（マージの中で、ユーザーがトポロジを変えたときの規則と同じです。チェックポイント Rig の再生成マージを参照）。

**記録**（ログエントリ。バージョン 1。今は、生成されていない元メッシュのためだけに書き、より古いバージョンの分割はすべてこれを書きました。バージョン 2 は [下記](#バージョン-2-の記録) を参照）は、次のとおりです。

| フィールド | 内容 |
| --- | --- |
| `op`、`v`、`origin` | `art_primitive`、`1`、`split`（多角形または連結成分）、または `depth`（前後分割） |
| `texture_source_id` | パーツのテクスチャがあるソース（生成モデルでは `art-0`） |
| `supersedes`、`supersedes_layers` | この位置で削除するメッシュ ID と、そのソースレイヤー ID |
| `replace` | 置き換えられるメッシュからパーツのメッシュへ。パーツツリーの中の位置に使います。`masks` を与えないときは、ほかのメッシュのマスクにも使います |
| `masks` | 任意です。置き換えられるメッシュがマスクであるとき、どのパーツがそれを担うかです（前後分割は後ろのレイヤーだけを使います） |
| `primitives` | パーツごとに 1 項。`id`、`layer_id`、`source_id`、`source_bounds`（テクスチャが覆わなければならないキャンバス矩形）、`neutral_bounds`、名称、親、パーツ、ブレンドモード、静的なマテリアルと表示、マスク、`user_data`。親空間の頂点 `positions`、`triangles`、キャンバス単位のテクスチャ座標 `canvas_uvs`。使うパラメータ定義、ジオメトリのキーフォーム `geometry`、チャンネルのキーフォーム `channels`、ブレンドシェイプ `blends`（制限曲線を含む）、パス `paths`、頂点グループ `vertex_groups` |
| `glues` | `replaced` は、モデルの順序で、置き換えられるメッシュに接する各 Glue に対応する置換 Glue です。`appended` は、最後に追加する Glue です（連結成分の分割の切断点の追従、前後分割の方向 Glue） |
| `depth` | 前後分割だけのとき。`back`、`front` のレイヤー ID と `glue_id`。`DepthSplit.isFrontLayer` は、これによって前レイヤーのペイントがトポロジを残すようにします |

**再生**（`ArtPrimitiveReplay.replay`。旧版の再生。記録のあとにチェックポイントがない古いログの中でだけ行います。[旧版の再生](#旧版の再生) を参照）。欠けているパラメータは記録に従って作ります。`supersedes` の中のメッシュを削除し、パーツを元メッシュの一覧とパーツツリーの位置へ置きます（元メッシュがすでにないときは、記録したパーツ、またはルートへ加えます）。ほかのメッシュのマスクは `masks` / `replace` に従って書き換えます。置き換えられたメッシュに接する Glue は、順に `replaced` の中の対応する項へ取り替えます（数が現在と合わないときは、接する Glue をすべて削除したあと、順に置換項を追加します）。そのあと `appended` を追加します。置き換えられたメッシュのパスと頂点グループは削除し、パーツのパスと頂点グループは記録に従って書きます。再生は、置き換えられたメッシュのジオメトリを読まず、その指紋も照合しません。テクスチャ座標はキャンバス単位で保存し、再生するときは現在のテクスチャアトラスで換算します。

**分割のときにキャプチャした状態**。`RigEditOverlay.authored` は、旧形式の編集とログ全体のあと、スイングとシミュレーションの書き戻しより前のモデルを出します。パーツはそのモデルから取るので、スイングとシミュレーションが生成した軸は、記録へ書きません。連結成分と多角形のパーツの頂点、キーフォーム、ブレンドシェイプ、パス、頂点グループ、Glue は、元の分割アルゴリズムで移行します。シミュレーションの対象、ベイクのオフセット、Glue の役割はパーツへ移り（前後分割は後ろのレイヤーへ移ります）、そのあとはシミュレーションが通常どおり書き戻します。

**生成入力**。分割は生成入力を凍結し（`generationSource`）、元のレイヤーはそこだけに残ります。生成のときは、次のとおりです。

- 置き換えられた生成レイヤーは、引き続き基礎 Rig の生成に参加し、その置換レイヤーが現在のソース画像の中で占める位置に並びます（置換レイヤーのうち最も高い `order` を取ります）。そのため、ほかのレイヤーの描画順、デフォーマの枠組み、ID は分割の前と一致し、記録より前のログは通常どおり再生します。
- パーツがあるレイヤーは記録が所有し、基礎生成へは入りません。それらの現在のピクセルは、`source_bounds` へ透明を補って覆ったあとパックします。
- 置き換えられたレイヤーは、テクスチャアトラスの中で 1×1 の透明なプレースホルダだけを占め、記録より前のログエントリがアドレスできるようにします。記録を再生したあと、`BuiltRig.withRigEdits` が、Rig のテクスチャアトラスのタイルとアートの一覧からそれを削除するので、プレビューの解析もそれを列挙せず、書き出す CMO3 にはそのレイヤーがありません。
- 口をレイヤー分けしたとき、その生成した唇は残します。レイヤー分けしたのが唇そのものなら、その唇は置き換えられます。

**パーツのあとの編集**。パーツは通常のソースレイヤーで、ペイントでき、削除と復元ができ、再び分割できます（分割されたパーツも、同様に置き換えられます）。パーツのメッシュ設定を変えるときは、`MaterializedMeshRebuild` が `canvas_mesh_rebuild` を追加し、キーフォームとバインドを移行します。パーツは、生成規則に従って自動では生成し直しません。

**スケルトンのスキン**（バージョン 1 のパーツ。旧版の再生）。スケルトンはログより前に基礎 Rig をベイクしますが、パーツは記録を再生してはじめて現れるので、基礎 Rig だけを見ると、ボーンにバインドしたパーツは存在しません（左右を一緒に描いたあと分割した脚や靴は、そのためスキンされず、脚のボーンにはキーフォームのないパラメータだけが残ります）。そのためスケルトンの段階（`RigBuilder`）は、先に記録から、ボーンにバインドしたパーツを復号し（`ArtPrimitiveReplay.skinnable`。キャンバス単位のテクスチャ座標。タイルとマスクは持ちません）、基礎 Rig と一緒にベイクし、スキンしたあとのパーツと、ベイクがそれらに足した Glue を基礎 Rig から取り出し、`BuiltRig.primitiveSkins` へ格納します。基礎 Rig が含むのは、引き続き置き換えられた元メッシュだけで、記録より前のログは通常どおり再生します。記録を再生するときは、自分で復号する代わりにスキン結果を使います（親はボーンのデフォーマです。テクスチャ座標は現在のテクスチャアトラスで換算し、マスクは記録から取ります）。両端がすでに所定の位置にある Glue は、そのあと加わります。次のパーツは、引き続き記録が自分で復号します。親、またはキーフォームのパラメータを、より早いログエントリが作らなければならないもの、パスまたは頂点グループを持つもの（ベイクは、それらを追加した頂点へ移行しません）。記録の親を基礎生成がもはや作らないときは、復号は [親が生成されなくなる](#親が生成されなくなる) に従って掛け替えます。再生チェックポイントは、`primitiveSkins` のインスタンスをキーの一部とします。`RigEditOverlay.applyTo` / `authored` と、シミュレーションのベイクは、いずれもそれを渡す必要があります（`authored(BuiltRig)`）。

**所有関係**。パーツは編集ログのノードに属します（`journal` が所有する `rig:authored`）。ジェネレーターの依存グラフには、単独では列挙しません。スイングとシミュレーションは、通常どおりそれらを読みます。置き換えられたメッシュの上にあった `generated_override` は、対象を失ったあと、孤立として報告します。

**置き換えられた ID の参照**。ドキュメント操作の中の参照フィールド（`layer_id`、`target`、`source_id`、`middle_ids`、`meshes` など）が、置き換えられたレイヤーまたはメッシュを指すときは、エラーを返し、それを置き換えた現在の ID を列挙します（複数回の分割をまたいで、段階的に展開します）。`source_get_components` も同様です。`layer_restore` は、元のレイヤーを連れ戻すことができません（それは `deletedLayerIds` の中にありません）。

**互換**。古い `canvas_source_partition`、`canvas_depth_split` は、元の規則で再生し、最初の編集のときにチェックポイント化します（[旧版の再生](#旧版の再生) を参照）。`LegacySplitReplayTest` は、古いバージョンが保存したプロジェクトで、各履歴ノードを再生したあとの IR ハッシュが、古いバージョンと一致することを照合します。古いプロジェクトの中でソフト削除した元レイヤーは、引き続き戻せます。古いプロジェクトの上の新しい分割は、実体化の規則で行います。CMO3 をインポートしたモデルの分割は、引き続き旧規則を使います（元レイヤーのソフト削除）。

### 親が生成されなくなる

ログが、ある記録より前に作ったデフォーマは、その記録へ再生するとき、再び存在します。そのため、記録の親が再生位置で欠けているときは、基礎生成がもはやそれを作らない場合だけです。分割のあと生成設定を変えたときです（スケルトンを有効にすると、腕が垂れる Warp `DeformArmHang_L/R` を生成せず、ボーンが腕を引き継ぎます）。このとき記録は次の規則で再生し、保存してある記録は書き換えません。規則は `VanishedParent` と、各記録の再生実装が行い、結果は決定的です。

- **バージョン 1 のパーツ**（`ArtPrimitiveReplay.rehome`。旧版の再生）。パーツは、それが置き換えるメッシュ（`replace` の中のキー）が現在いる親へ掛け替えます。そのメッシュ自身がより早い記録のパーツで、スケルトンのベイクが復号するとき基礎 Rig の中にまだそれがないとき（`skinnable` の `earlier`）、その記録に沿って、それが置き換えるメッシュを前へ探し続けます。位置は、「記録の頂点からキャンバスのテクスチャ座標へ」の最小二乗アフィンフィット（規則的な静止メッシュ、または剛体の枠組みの下では厳密です）で、既定ポーズのキャンバス位置へ戻し、新しい親の空間へ逆写像します。キーフォームとブレンドシェイプの変位は、フィットした線形部分でキャンバス変位へ換算したあと、同様に入れます。置き換えられたメッシュが見つからないときは、これまでどおり `Art primitive parent is missing` と報告します。
- **`canvas_mesh_rebuild`**（`RasterMeshJournal.replay`）。メッシュはすでに別の親の空間にあり、ジオメトリの指紋はもう照合できないので、頂点数だけを照合するように変えます（`glue_map` の長さ）。記録の `points` と `previous_parent_points` は、同じアフィンフィットで、メッシュの現在の親の空間へ移します。
- **構造編集の `bind`（メッシュ）と `move`（デフォーマ）**（`RigStructureEdits.replay`）。対象の親が欠けているとき、その項は効かず、オブジェクトは元の場所に残ります。新しく確定する編集は `RigStructureEdits.apply` を通り、親が欠けていれば、引き続きエラーになります。
- **`canvas_mesh_create`** には、辿れる、置き換えられたメッシュがないので、親が欠けているときは、これまでどおりエラーになります。

ボーンにバインドしていても、ログがボーン以外のデフォーマの下へ掛けたメッシュは、ベイクの中では掛け替えず、ログのあとにスキンします。[ログが配置したメッシュ](#ログが配置したメッシュ) を参照してください。

### ログが配置したメッシュ

スケルトンのベイクは、ログより前に、ボーンへバインドしたメッシュをボーンの Rotation デフォーマの下へ掛け替え、位置とキーフォームをどちらもボーン空間へ移します。ログがそのあとこのメッシュを自分で配置するとき、つまり構造編集の `bind` でボーンではないデフォーマへ掛ける、または `warp` 記録がそれを新しい Warp で包むとき、これらの記録はメッシュの局所座標を残します（`space=local`、`fit_local`）。ボーン空間にあるメッシュの上では、正しく再生できません。この種のメッシュは、`SkeletonCanvasSkin.placedByRecords` が、スケルトン定義と編集から決めます（先に旧版の `structureEdits` / `warpEdits`、次にログを順に読みます。メッシュの最後の `bind` がボーンのデフォーマへ向かうときは、数えません）。次の規則で扱います。ログにチェックポイントがあるとき、スキンの段階には別に、チェックポイントのオーサード Rig の中で、その四肢のどのボーンにも動かされないバインド済みメッシュを含めます（`SkeletonCanvasSkin.placed` / `unskinned`。チェックポイントのあと `bind` でボーンのデフォーマへ掛けたものは除きます）。記録が置いたものでも、再生成のマージが置いたものでも、古いバージョンが置いたものでも同じです。ベイクが決めるのは記録だけです。チェックポイント Rig の、構造の引き継ぎとマージの忠実さを参照してください。

- **ベイク**（`SkeletonRig.apply` の `canvasSkinned`）。四肢のほかのメッシュと同じように関節を細分化し、同じ四肢のパーツと溶接し（`GlueSkel__` の Glue）、ブレンドシェイプの計画に数えます。ただし掛け替えず、スキンのキーフォームも書かず、生成した親の下に残します。本来掛けるべきボーンは、掛け替えたとしても、通常どおりデフォーマを残します（メッシュがないからといって、刈り込んだり折りたたんだりしません）。キャンバスの上ではボーン鎖全体とともに動くので、計画は鎖の上のすべてのボーンパラメータを互いに結合しているとみなし、ブレンドシェイプにはしません。残りのメッシュの経路は変わりません。ログが配置したメッシュを持たないプロジェクトでは、ベイクと書き出しはバイト単位で変わりません（`ExportGoldenTool`）。
- **スキン**（生成ノード `skeleton.skin`。ログのあと、スイングとシミュレーションより前）。ボーンの作用はキャンバス空間で定義します。あるポーズの下で、各頂点は自分のウェイト（`SkeletonWeights` / `SkeletonManualWeights`）に従い、ボーンのキャンバス変換（`SkeletonPoseSolver.frames`。デフォーマを持つボーンはデフォーマを読み、それ以外は親ボーンに従って回転します）に動かされ、さらにベイクと同じように、関節テンプレート、ARAP、表面の平滑で補正します（`SkeletonRig.corrected`）。得たキャンバス位置は、メッシュの最終的な親の鎖が同じポーズの下で持つ逆写像で、親の局所空間へ入れ、静止時との差を、メッシュがボーンパラメータの上に持つキーフォームとして書きます。ブレンドシェイプ類のパラメータ（計画が独立と認めたボーン、スケルトンのポーズ）は、ブレンドシェイプとして書きます。軸は、そのメッシュを動かす四肢のボーン、その上にある体の半区間、スケルトンポーズのパラメータで、ベイクと同じ許容差で、最も少ないキーを取ります。メッシュは掛け替えず、ログの配置はそのまま残ります。その上にユーザーの Warp が何層あっても同じです。
- **既存のキーフォーム**。スキンのキーフォームは、メッシュがもともと持つキーフォームと足します（パラメータを共有するときは、両方のキーをマージします）。これらのマスへのキャンバス編集は、`GeneratedOverrides.capture` が `skeleton.skin` の `generated_override` として書き、再生するときは三者マージします。ログがすでにメッシュへ与えている、同じパラメータのブレンドシェイプは、ユーザーのデータとみなし、変えません。
- **Glue**。もう 1 つのスキンメッシュと対になる頂点は、各キーで同じキャンバス目標を取ります。もう一端をベイクのスキンが担うとき（ボーンの下に掛かっているとき）は、Rig が評価した位置を取ります。両端をこの段階がスキンするときは、Glue の両側のウェイトで会合点を取り、両者が共有パラメータの上で同じキーを使うようにします。これらの頂点は ARAP の中で固定点になり、メッシュは継ぎ目へ滑らかに遷移します。
- **トポロジ**。関節の細分化はログより前に起き、そのあとの頂点ごとの記録は、細分化したあとのメッシュを対象にします。ログの中でそのメッシュを対象とする頂点ごとの記録（`canvas_geometry`、`vertex_group_put`、メッシュの `generated_override`）の頂点数が、細分化する前の頂点数と等しいとき（そのメッシュを細分化しないバージョンで書いたとき）、そのメッシュは細分化しません（`SkeletonCanvasSkin.lockedTopology`。手作業トポロジと同じです）。これらの記録が食い違うことを避けるためです。関節のボーンにバインドされたほかのメッシュも、この種の記録がすべて細分化前の頂点数で書いてあるとき（スケルトンより前に書いた頂点グループなど）は、同様に細分化しません。細分化後の頂点数で書いた記録があるときは、通常どおり細分化します。
- **コストとキャッシュ**。四肢の根のボーンと、その上の体の半区間は、四肢全体を剛体として動かすだけなので、求解するときは先にそれらを含めず、そのあと変換を適用します。必要な求解数は、四肢の内部の関節のキーだけに依存します。出力は `GeneratorReuse` が、読む内容に従って再利用します。スケルトンのキャッシュキーは、この種のメッシュがあるとき、その集合を含みます。

### バージョン 2 の記録

バージョン 1 は、元のレイヤーを分割した時点のオーサード全体を、パーツへスナップショットします。基礎生成が見るのは、引き続き元のレイヤー（乗客）だけで、パーツは見えず、ジェネレーターがメッシュへ書いたキーフォーム（目の開閉、スケルトンのスキンなど）も記録の中で凍結するので、そのあとの顔の設定、立ちポーズ、スケルトンの変化はパーツへ届きません。バージョン 2 は、パーツを基礎生成へ参加させます。生成された元メッシュの分割は、すべてバージョン 2 を書き、スイッチはありません。今のバージョン 2 の記録は宣言だけです（`authored` は空で、ユーザーのデータはそのあとのチェックポイントの中にあります。[分割は再生成](#分割の実体化アートプリミティブ記録-art_primitive) を参照）。より古いバージョンが書いたバージョン 2 の記録は、`authored` の中に作者のデータを持ちます。以下の残差、2 パスのキャプチャ、乗客の許容、再生が述べるのはそれらで、[旧版の再生](#旧版の再生) の中でだけ使います。

**解決済みのレイヤー集合**（`core/PrimitiveResolution`）。生成レイヤーから、v2 の記録が置き換えたレイヤーを除き、v2 のパーツのレイヤーを足します。アンカー、顔の Rig、頭部空間、枠組み、立ちポーズと脚、体の枠組み、デフォーマ（対の Warp、腕が垂れる Warp を含む）、白目、マスクの出所になるメッシュ、唇の顔の Rig、スケルトンのバインドは、この集合だけを読みます。プレビューの解析も、これと一致します。パーツのピクセルは、現在のピクセルを `source_bounds` へ透明で補ったもので、メッシュは引き続き記録の値を取ります。分類は `layerOverrides` を取り（分割のときに継承します）、ないときは記録の `classification` を取ります。分割のベースライン（`splitBaselineLayerIds`）を持つコンテキストも、同様にパーツを数え、置き換えられたレイヤーを除きます。デフォーマを残す構築（`buildPreservingDeformers`。ペイントの確定が使います）も同じです。

**乗客**。置き換えられたレイヤーは、引き続き元の位置で生成します（タグの計数が決める ID と、既定の描画順は変わりません）。使うのは自分の凍結したピクセルと、レイヤーごとのキーフォームだけで、上記の集約段階は読みますが、そこへは返しません。ボーンにはバインドしません。それが存在するのは、記録より前のログエントリがアドレスするためだけで、記録を再生するときに削除します。

**仮置き**。パーツは基礎 Rig の中で、記録した静止キャンバスメッシュとして生成します（メッシュ化し直さず、テクスチャ座標はキャンバス単位です）。生成したキーフォーム、チャンネル、マスク、パーツツリーの位置、スケルトンのスキンを得ます。UV をバインドしたあと、全体を `BuiltRig.primitiveSkins` へ移します（溶接の Glue、生成したパス、パーツを指す生成マスク、パーツのスロット、所有関係、遅延した親、中立の境界とともに）。基礎 Rig の中でパーツを指す参照は、その乗客へ書き換えるので、記録より前に見えるのは「分割前」の Rig です。`BuiltRig.resolvedPuppet()` は乗客を除いてパーツを入れるので、生成の移行（`RigGenerationMigration.generatedRig`）の previous と desired はこれで比較し、顔の設定や分類などの変化も、同様にパーツへ届きます。

**記録のフィールド**（`v: 2`。残りの最上位フィールドはバージョン 1 と同じです）。各パーツは `id`、`layer_id`、`source_id`、`source_bounds`、`neutral_bounds`、`name`、`classification`、`mesh{canvas_positions, triangles, canvas_uvs}` を持ちます（静止キャンバスメッシュ。パーツが引き続き原本の生成した親の下にあるときは、基礎 Rig の生成デフォーマで換算し、ログが親の鎖へ行った編集は、再生するときに 1 回だけ作用します。ログが親を変えたときは、オーサードの親を経ます）。`parent` と `part` が空なのは、生成結果を取るという意味で、ログの編集が元のレイヤーを変えたときだけ書きます。マテリアルのフィールドは、生成した値と異なるときだけ書きます。`masks` が空なのは、生成したマスクを取るという意味です。`parameters` が含むのはユーザーの軸だけです。`geometry_residual`、`channels_residual`。`blends`、`paths`、`vertex_groups` が含むのはユーザーのデータだけです（スケルトンポーズのブレンドシェイプと、生成したパスは含みません）。`fixed_topology`（パーツが頂点ごとのユーザーデータを持つとき真。スケルトンは関節の行を挿入できません）。`frozen_axes`。`glues` が含むのはユーザーの Glue だけです（`GlueSkel__` の溶接は含みません）。

**残差**。キャプチャするとき、A は元のレイヤーのオーサード、G は基礎生成の出力（スケルトンを含む）で、残差 A − G を、分割の頂点の出所を経てパーツの頂点へ移します。キーの中に、既定値にないジェネレーターの軸があるマスは、記録の直後の `generated_override` として書きます（`base` は候補の基礎パーツのマス、`points` は `base` に残差を足したもの、`generator` はその軸を所有するノードです）。残りは `geometry_residual` / `channels_residual` へ書きます。再生するとき、パーツのメッシュは、仮置きした生成メッシュ ⊕ 残差で、上書きは通常どおり、すべてのジェネレーターのあと三者マージします。基礎がキーフォームを生成しないパーツ（ゼロメッシュ。唇の帯のスライス、遅延した親のパーツ）には、足し戻せる生成の動きがないので、残差はオーサードのすべてのキーフォームを取ります（A − 0）。同じ記録の口のパーツは、口のパーツをすべてマージした開口で口形を生成し、それぞれの境界では生成しません。そうしないと、半分の口がそれぞれ口全体として開き、切口で裂けます。

**再生**。乗客を削除し、仮置きしたパーツを置きます（キャンバスのテクスチャ座標は現在のテクスチャアトラスで換算し、遅延した親はその親の空間へ移します）。生成したマスクとパーツのスロットを戻し、両端があるときは溶接を加え、生成したパスを書き、そのあと残差と作者の層を足します。仮置きのトポロジが記録と異なるとき（スケルトンが関節の行を足した、そのあとのメッシュ再構築）、頂点ごとのデータは、キャンバスのテクスチャ座標で新しいメッシュへ移行します。

**2 パスのキャプチャとガード**（より古いバージョン）。分割は先に基礎フィールドを書き、候補の基礎がパーツを生成してから、それと対照して残差と上書きを書きます。候補の基礎が、既存のログが参照するオブジェクトをすべて引き続き生成し、ログ全体がその上で再生できるときだけバージョン 2 を書き、そうでなければバージョン 1 へ戻り、`v2_fallback {reason, detail}` を付けます。今の分割はマージで置き換えるので、後退はありません。古い記録の上の `v2_fallback` は、履歴として残すだけです。

**乗客の許容**。記録より前のエントリが、参照するメッシュがすべて、そのあとの v2 記録の乗客であることだけを理由に失敗するときは、空操作として再生し、説明を 1 件残します（`SupersededEntryNote`。ログの番号、`op`、対象、理由）。ほかの失敗は、通常どおりエラーになります。説明は再生チェックポイントとともに保存し、チェックポイントから続けるときも完全で、`BuiltRig.supersededEntryNotes` を経て `workspace_inspect` の `quality.overrides` へ入ります（`SUPERSEDED_ENTRY_SKIPPED`。info。止めません）。

**再分割**。パーツは再び分割でき、通常のレイヤーを分割するときと同じです。G と M の中のパーツを、それぞれ切ってからマージします。より古いバージョン 1 の記録が v2 のパーツを置き換えるとき、そのパーツは透明なプレースホルダと固定メッシュとして、解決済みの集合の中に残り、基礎の枠組みは変わりません。

**パーツのあとの編集**。ペイントはピクセルだけを取り替え、パーツのメッシュは記録の値を保ちます。`rebuild_mesh` のペイント、またはレイヤーごとのメッシュ設定の変更は、記録のあとに `canvas_mesh_rebuild` を追加し、キーフォームとバインドを移行します。

**所有関係とキャッシュ**。`DocumentGenerators` のドキュメント入力 `document:primitives`（v2 記録の固定入力）を、足跡、枠組み、メッシュ、スケルトンが読みます。パーツの `keyform:mesh:<部件>@<参数>` は、仮置きの所有関係に従い、`mesh:<图层>` / `rig.meshes`（特徴の軸）または `skeleton`（ボーンの軸）に属します。`GeneratedOverrides.capture` は、これによって、そのあとのこれらのマスへの編集を上書きとして書きます。段階キャッシュとバインドキャッシュのキーは、v2 記録の固定入力の要約を含みます。

**互換**。より古いバージョンが書いたバージョン 1 と、作者のデータを持つバージョン 2 の記録は、そのあとにチェックポイントがないとき、通常どおり再生します（スケルトンのスキンと、自分での復号を含みます）。読むときは書き換えず、最初の編集のときにチェックポイント化します（[旧版の再生](#旧版の再生) を参照）。v2 記録を持たないドキュメントは、元のコード経路を通ります（`ExportGoldenTool` はバイト単位で一致します）。v1 と v2 の記録は混在でき、v2 の記録が v1 のパーツを置き換えるときは、それを削除します。宣言的な記録を再生するとき（たとえばチェックポイントのない構築の中）は、生成したパーツとして置きます。古いバージョンの明示的なアップグレードコマンド（`source_upgrade_split_records`）は、削除済みです。

**既知の制限**は、次のとおりです。

- 分割した口の、生成した唇は、引き続き置き換えられた口（乗客の凍結したピクセル）から取り、パーツの現在のピクセルの合成からは取りません。分割した時点では両者は一致します。そのあとパーツの上でペイントしても、唇のテクスチャは追従しません（通常の口の唇のテクスチャも、メッシュ入力から取るので、メッシュを再構築する前は追従しません）。パーツのメッシュを再構築しても、唇は生成し直しません。
- `frozen_axes`。書き込み側は常に空を書くので、現在は現れません。基礎生成が空でない値を読んだとき、生成メッシュの軸の中に凍結された軸があれば、そのパーツの生成メッシュ全体をゼロにし、作者のデータだけを残します。旧版の再生が空でない値に出会うと、直接エラーになります（未対応です）。
- パーツのメッシュを再構築したあと、その生成したマスを対象とする `generated_override` は移行せず、形状が合わないときは孤立として報告します。
- 口形の輪郭を開いているとき、口のパーツの固定メッシュは原本の輪郭メッシュで、足跡は原本のラスタメッシュと少し異なります。口の枠が決める、生成した唇の静止位置は、およそ 0.4 px 違います。パーツ自身の開口の形状には、輪郭の寄与が含まれません（およそ 0.13 px）。
- v2 のパーツは枠組みの生成に参加します。固定メッシュのキャンバス位置は、親を往復するときに浮動小数の丸めがあり、分割していないメッシュの局所座標と、枠組みの制御点は、数 ulp 異なり得ます（ワールド座標では 1e-4 px 未満）。バージョン 1 はビットごとに変わりません。
- 元メッシュのトポロジを手で変えてあるとき、パーツはユーザーのトポロジのままユーザーのオブジェクトとして残り、ジェネレーターがそのあと変えても、これらのパーツのジオメトリへは届きません。

**テスト**。`PrimitiveResolutionTest`（手書きの v2 記録の基礎生成）、`ArtPrimitiveRecordV2Test`（旧版記録の符号化、残差、再生、乗客の許容、チェックポイントから続けたときの説明。エンコーダはテストの中の `LegacyArtPrimitiveV2`）、`SplitPartsCheckpointTest`（分割のチェックポイント、対の Warp、スケルトンのスキン）です。tml の上での分割の効果は、`ArtPrimitiveV2VisualTool` で目視します（分割していないものと分割したものの、各ポーズでの差。これまでのバージョン 2 の記録と同じです）。

## 旧版の再生

より古いバージョンは、いくつかの編集を、基礎 Rig の上で再生する記録として書いていました。分割の `art_primitive`（バージョン 1、および作者のデータを持つバージョン 2）、生成の移行（`rig_generation_transition`、`rig_generation_frames`、`rig_generation_scaffold`、`rig_mesh_activation`）、古い `canvas_source_partition` / `canvas_depth_split`、およびログより前の旧形式の静的フィールドです。生成されたモデルは、これらを書かなくなりました。CMO3 をインポートしたモデルには、マージできる生成結果がないので、引き続き移行記録と古い分割を書きます。ただし、それらを書いた確定は、直後にインポートしたモデルのチェックポイントをそのあとに書きます（`WorkspacePreviewBuilder.importedRecordsCheckpointed`）。記録が再生されるのは、この 1 回の構築の中だけで、そのあとの構築、開くこと、取り消しは、いずれもチェックポイントから始まります。そのため `core.legacy` が動くのは 2 か所だけです。まだチェックポイントを書いたことのない古いログを、初めて編集する前と、インポートしたモデルがこの種の記録を書く、その 1 回の確定です。

- **チェックポイント化は 1 回だけ**。ログが、最後のチェックポイントのあとに、引き続きこの種の記録を持つとき（チェックポイントがないときは、旧形式の静的フィールドも含みます。`RigEditOverlay.replaysLegacy`）、それを継続する最初の編集は、先に元のログの末尾、新しいエントリより前へ、現在のオーサード Rig のチェックポイントを書きます（`WorkspacePreviewBuilder`）。生成スナップショットが手元にあれば、一緒に保存します。これらの記録は、これで最後に 1 回再生し、そのあとの構築はすべてチェックポイントから始まります。開くこと、履歴の切り替え、保存は、ログを書き換えません。古い改訂は、引き続き記録に従って構築します。
- **コード**。この経路と、インポートしたモデルの上でだけ使う部分は、`core.legacy` にあります。`ArtPrimitiveReplay`（バージョン 1 と、作者のデータを持つバージョン 2 の記録の再生、スケルトンのベイク前にバージョン 1 のパーツを復号すること、再生成のマージのときにバージョン 1 のパーツを入れること）、`StubTolerance` と `SupersededEntryNote`（乗客の許容）、`VanishedParent`、および生成の移行の書き込みと再生（`RigGenerationMigration`、`RigGenerationJournal`、`RigGenerationFrames`、`RigGenerationScaffold`、`RigMeshActivation`、`RigGenerationResidual`、`RigGenerationTextures`）です。`ArtPrimitiveJournal` は、記録の形式とドキュメントの問い合わせを残します（置き換えの関係、所有するレイヤー、テクスチャの覆い）。編集が生成結果を変えるかどうかを判断する `RigGenerationChange` は、マージ経路のトリガー条件で、`core` にあります。マージ（`RigRegenerationCheckpoint`）は、引き続き `core.legacy` から古い移行記録を読み、デフォーマに付けた名前とバージョン 1 のパーツを取るので、古いログの G と G′ は同じ方式で配置します。これらは互換のための読み取りで、新しい機能とともに広げません（`LegacyReplayBoundaryTest` が、それを参照できるファイルを固定します）。
- **固定**。`LegacySplitReplayTest` は、古いバージョンが保存したプロジェクトで、各履歴ノードを記録に従って構築した IR ハッシュを照合します。

## 今後

- 分類の変更に残る所要時間は、解析にあります。生成されたモデルはマージへ変えたので、生成の移行は通らなくなり、残るのは、CMO3 をインポートしたモデルの移行と、分割のベースラインが、新しいラスタに対して `CharacterAnalyzer.analyze` を繰り返し実行することです（レイヤーごとの分類は 1 回およそ 0.5 秒）。レイヤーのメタデータとラスタの要約で、分類結果をキャッシュできます。
- ブレンドシェイプとして書き戻すシミュレーションのキーフォームの上書き。上書きの報告を、統一した品質検査の枠組みへ入れたあと、その規則のレジストリと柵を使うように変えます。
- チャンネルの上書きの既知の制限（現在、ログよりあとにチャンネルを打つジェネレーターはなく、この経路は発火しません。最初のそのようなジェネレーターを加える前に処理します）は、次のとおりです。
  - キーフォームの `set` が、生成したチャンネルのトラックの静止マスへ書くとき（キーの中でジェネレーターのパラメータが既定値にあるとき）、`journalOnly` がジェネレーターの既定値の軸を剥がすのはジオメトリ編集だけで、チャンネル編集のキーは引き続きその軸を持つので、ログを再生するとき、ユーザー自身のトラックの上にその軸を作ってしまいます。
  - チャンネルの上書きを加えるより前のバージョンは、各上書きを頂点または制御点の座標として読み、数値の個数が偶数であることを要求します。スカラー（1 個）と色（3 個）の上書きは、どちらも「Invalid override form」と報告し、チャンネルの上書きを含むプロジェクトは、古いバージョンでは再生に失敗します。
- プロジェクトを開くとき、チェックポイント化した結果を直接読むこと。オーサード Rig の保存と読み取り、チェックポイント、再生成のマージ、試行実行は、いずれも実装済みです（チェックポイント Rig の実装の進捗）。CMO3 をインポートしたモデルは、インポートのベースラインの上でチェックポイントから再生し、オーサード Rig だけでは構築しません。

## 内部造形ジェネレーター

任意の `interiorEffect:<id>` ノードは、作者のログのあと、生成結果の上書きの前に実行します。`NativeInteriorEffect` は、`rigEdits.interiorEffects` に、レシピ、コンパクトなネイティブの blend フィールド、物理グループを保存します。既存の入力パラメータは読み取り専用で、生成するパラメータと対象の Mesh の軸には、所有者が 1 つだけです。レシピの変更、追加と削除、スイッチは、いずれも失効の伝播に参加します。メッシュ、素材、またはバインドが一致しないときは、レシピを残し、期限の切れた頂点は飛ばします。ネイティブの UI と MCP は `interior_put` を共用し、一時的な試しの動きはドキュメントへ入りません。停止した効果と、失効した効果の、使っていない固有パラメータは、書き出しの複製の中だけで片付けます。未公開の密な実験は、互換を残しません。削除は `interior_delete` を通して、同じ再生の連鎖へ入ります。内部造形を参照してください。
