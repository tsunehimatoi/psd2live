# プロジェクト形式 v2

[ドキュメント目次](../README.md)

`.psd2live` は暗号化していない ZIP です。JSON は UTF-8、ラスターリソースは PNG です。保存後のプロジェクトには、編集を続けるために必要なソース素材と履歴が含まれ、元の PSD のパスには依存しません。書き出しレポート `.psd2live.json` は、この形式ではありません。

ZIP エントリの圧縮方式：PNG（`assets/`、`images/`、観察図）と CMO3 のソースファイルは、それ自体がすでに圧縮されているため、`STORED`（非圧縮）で書きます。1 MiB 以上の、その他の JSON でないファイル（ソース PSD など）は、まず標本を取り、最速レベルで標本を圧縮した結果が元の大きさの半分未満のときだけ DEFLATE（最速レベル）にし、そうでなければ `STORED` です。JSON などの残りのエントリは、通常どおり DEFLATE します。`manifest.json` は最後のエントリです。エントリは名前で並べ、更新時刻は一律に 1980-01-01、名前は UTF-8 です。エントリ数、オフセット、または長さが古典的な ZIP の範囲を超えるときは、ZIP64 レコードを書きます。小さいエントリは複数スレッドで先に読み取って圧縮し、そのあと順に書きます。読み戻しの照合と、開くときの展開も、エントリごとに並列です。読み取りは、どの圧縮方式とどのエントリ順でも受け付けます。以前のバージョンはすべてのエントリを DEFLATE し、マニフェストを他のエントリのあいだに置いていましたが、そのようなアーカイブも通常どおり開きます。圧縮方式とエントリ順は形式の身元には属さず、マニフェストのハッシュは展開後のバイトを対象にします。

## 保存状態とプロジェクトの置き換え

タイトルバーの `*` と、保存 / 破棄の確認は、プロジェクトの内容に基づきます。アーカイブがついでに画面状態を記録するかどうかとは分かれます。

| 変化 | 保存が必要か |
| --- | --- |
| ソース画像、モデル編集、生成 / 書き出しの設定、出力ディレクトリ、履歴の切り替え | はい |
| パラメータのポーズとロック、スナップショット、履歴の注釈、タイムライン補助（パラメータのブックマークと、各モーションのマスク、凍結トラック、マーカー）、キャンバスのレイヤー / デフォーマの可視性、素材とタスクの記録 | はい |
| ワークスペースの作成、削除、改名、並べ替え。キャンバスの作成または閉じる | はい |
| 選択とホバー、検索、カメラ、ワークスペース / キャンバスのフォーカス、編集 / プレビューモード、レイアウト、パネルの展開と表示オプション | いいえ。手動保存のときは、回復できる画面状態を今までどおり記録する |
| 再生、トラッキングのスイッチ、リアルタイムプレビューのフレーム、観察ログ | いいえ |

保存は完全なバージョンを 1 つ捕捉します。ディスクへ書いているあいだに現れた新しい内容の変更は、未保存の状態を残し、画面操作は保存の完了に影響しません。未確定のフィールドをディスク上の値へ戻しても、1 回の変更マークだけでは `*` は残りません。確定済みの履歴は、今までどおり保存が必要です。

GUI の破棄して開くは、それまで実行中の編集とフィールドの確定が終わるのを待ってから、置き換えの境界を捕捉します。破棄を選ぶと、それまでの未保存の内容を置き換えてよいことになります。読み込み中の新しい内容の編集、または別のプロジェクト置き換えは、この回のオープンを失敗させます。読み込み中の画面操作は、置き換えを止めません。キャンセルまたは読み込み失敗は、元のプロジェクトと回復記録を残します。きれいなプロジェクトへの置き換えに成功したあと、古い回復の書き込みより後に、破棄した回復マークを片付けます。

## アーカイブのレイアウト（v2）

保存は v2 を書きます。各履歴リビジョンは、内容アドレスのドキュメントノードに分かれ、変わっていない部分はリビジョン間で共有します。ノードはそれぞれ schema バージョンを持ちます。

| パス | 内容 |
| --- | --- |
| `manifest.json` | 形式名、バージョン `2`、プロジェクト UUID、ペイロードの SHA-256 一覧 |
| `source/original.psd` または `source/original.cmo3` | 元のインポートソースファイル。画像から作ったプロジェクトは PSD のソースファイルを生成する |
| `history/HEAD.json` | 現在のノードとノードの順序 |
| `history/nodes/` | 不変の親連鎖ノードとメタデータ（v1 と同じ） |
| `history/revisions/<key>.json` | 各リビジョンのインデックス：`{schema, nodes:{类型:哈希}, overrides?, clips?, payloads?}` |
| `document/nodes/<类型>/<sha256>.json` | ドキュメントノード `{schema, kind, value}`。型は `source`（ソースレイヤーとグループ）、`generation-source` / `mesh-source`（旧版が書いた `placement-source` は読み取り時に無視）、`layers`（可視性、ソフト削除、分類、親、メッシュとテクスチャの上書き）、`settings`、`rig`（パラメータ、スケルトン、スイング、シミュレーション、物理、クリック領域などの Rig 定義）、`journal`（作者の編集ログ。上書きは含まない）、`layout`（ユーザータグ、素材の関連、生成状態）、`materials`（素材ライブラリ。フォルダと項目。ピクセルは `assets/` のラスターを参照し、SVG の原文は埋め込む。PSD / CMO3 から読んだフォルダは `origin` のファイル名を持ち、その項目の `placementCanvas` は既定の配置があるキャンバスサイズ）、`document`（残りのフィールド）。`layout` と `materials` は、ドキュメントが Layout 状態を持つときだけ書き、それらを知らない旧バージョンは開くことを拒否する |
| `document/nodes/payload/<sha256>.json` | 大きなログ項目の内容アドレスのペイロードノード。schema 2 のリビジョンが `payloads` に列挙する |
| `document/overrides/<sha256>.json` | 生成結果の上書き `generated_override`。編集ログ内の位置とともに |
| `document/clips/<sha256>.json` | モーションクリップ（`motions`。各クリップの `events` を含む）、生成モーションの設定（`motionPresets`）、表情（`expressions`）、ポーズ（`pose`）。後の 2 つは、プロジェクトが表情を編集したか、ポーズグループを設定したときだけ書く |
| `document/bakes/<sha256>.bin` | シミュレーションのベイク結果（パックした JSON。後述の「ベイクファイル」を参照）。schema 4 のリビジョンが `bakes` に列挙する |
| `assets/` | 重複を除いた RGBA ラスター。PNG で保存する |
| `auxiliary/assets/` | 一時保管の素材メタデータ |
| `auxiliary/views/`、`auxiliary/view-images/` | 観察図の空間写像。より早く保存したプロジェクトには各レンダリング画像も付くが、現在の保存ではもう書かない |
| `auxiliary/workflow/` | 素材の参照パッケージ、登録 / 配置などの補助記録 |
| `auxiliary/tasks.json` | Agent のタスクとイベントの記録 |
| `workspace.json` | レイアウト、カメラ、選択、パラメータプレビュー、履歴の注釈、タイムライン補助（`timelineAids`）、ログなどの永続 UI 状態 |
| `images/<hash>.png` | ログの画像 |
| `rig/objects/` | Rig オブジェクト。チェックポイントの記録が参照するオブジェクト（チェックポイントのあるリビジョンでは必須）、および各リビジョンのオーサード Rig のオブジェクト |
| `rig/revisions/` | 任意。各リビジョンのオーサード Rig のインデックス（後述の「オーサード Rig」を参照） |
| `cache/head/` | 任意。ヘッドリビジョンの再構築に使う、削除できるキャッシュ（後述の「ヘッドキャッシュ」を参照） |
| `thumbnail.png` | 任意。スタートページ用のプレビュー画像。保存時のモデルの静止ポーズ。長辺は 256 px 以下。開くときは読まず、保存のたびに書き直す |

ドキュメントノード、上書き、クリップファイルのファイル名は、そのバイトの SHA-256 で、開くときに 1 つずつ照合します。分割は損失がありません。開くときはインデックスに従って各リビジョンの完全なドキュメントを組み立て直し、revision ID、ノード ID、分岐は変わりません。完全な Rig モデルは保存しません。リビジョンにオーサード Rig があるときは、開くときにそれから直接構築し、なければソース画像、設定、編集から再構築します。補助ディレクトリは、関係する機能を使うかどうかに応じて現れます。`cache/` には削除できる再構築キャッシュだけを置き、どの身元にも参加しません。

### チェックポイント

ログ項目 `rig_checkpoint`（`{op, v:1, authored:{header, frame, deformers, meshes}, issues}`）は、オーサード Rig をデータとして、ログ内のその位置に保存します。`authored` は後述のオーサード Rig のインデックス（ヘッドとオブジェクトのハッシュ）で、`issues` は、それを書いた再生成のマージがきれいに移行できなかった内容です（`{kind, target, detail}`。固定した Rig を参照）。再生は最後のチェックポイントから始まります。そのオーサード Rig（テクスチャアトラスが変わったときは、キャンバスのテクスチャ座標でバインドし直す）に、その後の項目を足します。それより前の項目は履歴として残すだけで、もう再生しません。編集が基礎生成の結果を変えたとき、生成したモデルを初めて編集したとき、最後のチェックポイントのあと 32 件に達したときに、プログラムがチェックポイントを書きます（[ドキュメント層](DOCUMENT_LAYER.md#チェックポイント)を参照）。ユーザーはそれを直接編集しません。後の 2 つは、編集前のオーサード Rig を保存し、生成スナップショット `generated` は前のチェックポイントのものを引き継ぎます。そのため、このバージョンで編集した生成プロジェクトは、すべてリビジョン 3 です。

チェックポイントのオブジェクトはドキュメントに属します。作業ディレクトリは、それらを参照するスナップショットを書く前に、オブジェクトを `<project>/rig-objects/` へ書き、保存時に `rig/objects/` へアーカイブします。

### オーサード Rig

`rig/revisions/` は、各リビジョンのオーサード Rig を保存します。基礎生成（スケルトンのベイクを含む）に、旧形式の静的編集とログ全体を足したあと、スイング、シミュレーションの書き戻し、上書きのマージより前の Rig です（設計は固定した Rig を参照）。

| パス | 内容 |
| --- | --- |
| `rig/objects/<sha256>.bin` | Rig オブジェクト 1 つ（`RigIrObjects`）。枠組み（デフォーマとメッシュ以外のすべての内容）、単一のデフォーマ、または単一のメッシュ。バイトの SHA-256 で名付け、リビジョンとチェックポイントのあいだで共有する |
| `rig/revisions/<revision>.json` | `{header, frame, deformers:[...], meshes:[...]}`。ヘッドと、Rig の順に列挙したオブジェクトのハッシュ |

- オブジェクトは中立 IR のバイナリ形式でエンコードします（`RigIrBinary`。浮動小数は元のビットのまま保存）。魔数、エンコードバージョン、オブジェクト型を自ら持ちます。読み取りは `RigIrObjects.MIN_VERSION` 以降の各バージョンを受け付け、IR に追加したフィールドは、それを加えたバージョン以降でだけ読みます。エンコードバージョン 5 以降、浮動小数配列はバイト平面で書きます（すべての値の最初のバイト、次に 2 番目……）。数値は変わらず、DEFLATE の圧縮率は明らかに上がります。バージョン 6 は IR のクリック領域を加えます（旧バージョンのオブジェクトは通常どおり読む。その後に保存して新しく書いたオブジェクトはすべてバージョン 6 のエンコードで、内容が変わっていないオブジェクトも新しいハッシュを得る。そのためアップグレード後、最初にチェックポイントを書くときアーカイブは一度に大きくなり、その後は通常どおり共有する）。既存オブジェクトは、そのハッシュでチェックポイントから参照され、元のエンコードを保ちます。
- ヘッド `{format:"psd2live-authored-rig", version:1, build, binding_key, pages, layers, bounds, face, warnings, skipped, visibility}`：メッシュからテクスチャページ、ソースレイヤー、中立境界への写像、顔の中心、半径、初期の傾き、生成の警告、再生で飛ばした項目、レイヤーの表示と非表示を適用する必要があるメッシュ、テクスチャアトラスのバインドキー。浮動小数は元のビットを整数として書きます。
- ファイル名の中のリビジョンキーは、ドキュメントのリビジョン ID（`WorkspaceRevisions.of`）です。つまり構築がそれを探すキーです。
- バインドキーは、基礎 Rig を生成したときのテクスチャアトラスの配置、ページサイズ、テクスチャレイヤー矩形の要約です。開くときは、現在のプログラムがそのリビジョンのテクスチャアトラスをパックします。キーが同じときは、保存したテクスチャ座標を直接使い、異なるとき（このプログラムのパック結果が異なるとき）は、キャンバスのテクスチャ座標に従って新しいタイルへ移します。項目を読めないとき、または検証に失敗したときは、通常どおり構築します。
- 保存は、現在のプロセスが各リビジョンについて構築したオーサード Rig と、アーカイブを開いたときに読んだ項目を書きます。ただし対象はヘッド、各分岐の末端、ログにチェックポイントがないリビジョンに限ります。残りのリビジョンは最後のチェックポイントから構築し、基礎 Rig を生成する必要がないため、それぞれを 1 部ずつ保存しません（変更したメッシュは、それぞれアーカイブ内の別のオブジェクトになる）。ないリビジョンは書きません。`-Dpsd2live.materializedRigs=false` は読み書きを切ります。
- リビジョンインデックスは、リビジョン ID にもドキュメントノードにも入りません。それがないリビジョンも通常どおり構築します。ログにチェックポイントがあるときはチェックポイントから構築し、なければ生成して再生します。CMO3 をインポートしたモデルは、オーサード Rig を書きません。

### ヘッドキャッシュ

保存時に `cache/head/` を書けます。ヘッドリビジョンの再構築のうち、高価で、安全に再利用できる中間結果を保存し、開くときに再計算を飛ばせるようにします。これは権威あるデータではありません。開くときは、今までどおりソース画像、設定、編集ログから完全に再構築し、キャッシュはジェネレーターのメモリキャッシュへ先に入れるだけです。使うかどうかはそのキャッシュ自身の内容キーが決め、キャッシュ付きとキャッシュなしの再構築はビット単位で同じモデルになります。

| パス | 内容 |
| --- | --- |
| `cache/head/manifest.json` | `{format:"psd2live-head-cache", version:1, build, generator, revision, language, entries:[{kind, file, sha256, bytes}]}` |
| `cache/head/skeleton-bake.bin` | ヘッドのスケルトンベイク。JSON ヘッダ（ベイクバージョン、キャッシュキー、スケルトン定義、読み取り集合、読んでいないオブジェクトの親の付け替え記録、任意の完全ハッシュ）+ 出力モデルのバイナリ IR（`RigIrBinary`。浮動小数は元のビットのまま保存。テクスチャアトラス、ソース画像の一覧、変形パスは含まず、ヒットしたときは新しい基礎 Rig から取る） |

- キー：ヘッドの revision ID、プログラムのバージョン（`Compiler.version`）、ジェネレーター定数 `ProjectHeadCache.GENERATOR`（生成の論理が変わり、項目自身のキーがそれに気づかないときに増やす）、画面の言語。どれか 1 つでも異なれば、全体を無視します。項目内のスケルトンキャッシュキー（`SkeletonRig.BAKE_VERSION`、ベイクが読んだすべての内容、言語を含む）が、ヒットするかどうかをさらに決めます。
- キャッシュするのはスケルトンベイクだけです（コールドスタートは約 5〜7 秒、ヒットは約 1〜7 ms）。1 つの項目が 64 MB を超えるときは書きません。保存時は、プロセス内で最近使った、スケルトン定義がヘッドと同じベイクを取ります。なければキャッシュは書きません。`-Dpsd2live.headCache=false` は書き出しと読み取りを切ります。
- 開くとき、マニフェストの形式、キー、項目のチェックサムが合わない、項目がない、途中で切れている、デコードできない、のいずれでもログに記録して捨てるだけで、開くことの失敗にはしません。読み取ったあと、展開ディレクトリの `cache/` を削除します。
- キャッシュは `history/` と `document/` の外にあり、revision ID、ドキュメントノード、履歴には入りません。そのディレクトリがないアーカイブも通常どおり開きます。アーカイブのマニフェストは、これらのファイルを通常どおり列挙して検証します。以前の v2 プログラムは、それを残りのエントリと一緒に展開したあと読まないため、キャッシュ付きのアーカイブも開けます。それらが再び保存するときは、そのディレクトリを残しません。

### ノード schema

ノードとリビジョンインデックスの schema は、新しいフィールドを使うときだけ上げます。残りのノードは今までどおり schema 1 を書き、内容はバイト単位で変わらないため、古いプロジェクトを保存したあとのノードハッシュとリビジョンインデックスは、これまでと同じです。

| schema | 適用 | 新しいフィールド |
| --- | --- | --- |
| ノード 1 | 次のフィールドを含まないノード | — |
| ノード 2 | `source` および 3 種の付加ソース画像ノードに、`rect` を持つレイヤーがある。`layers` が `textureOverrides` を含む。`settings` が `atlas` または `atlasArrangement` を含む | 後述のテクスチャフィールドを参照 |
| ノード 3 | `source` または付加ソース画像ノードに、`transform` を持つレイヤーがある | レイヤー全体の変換 `[a, b, c, d, e, f]`（`x' = a·x + c·y + e`、`y' = b·x + d·y + f`。キャンバス単位、y は下）。レイヤーのフレーム（整数境界と `rect`）に作用する。テクスチャ座標はフレームに錨を下ろし、生成はフレームを読むだけ。単位変換は書かない |
| ノード 4 | `layout` / `materials` ノードが、Layout ノード導入後に追加したフィールドを含む | 参照図、参照レイヤーとピン、描画、素材のキャンバスと参照マーク |
| ノード 5 | `clips` ノードが `expressions`、`pose` を含むか、`events` を持つモーションクリップがある | 表情 `{id, name, fade_in, fade_out, entries:[{parameter, blend, value}]}`（`blend` は `ADD` / `MULTIPLY` / `OVERWRITE`）。ポーズ `{fade_in, groups:[[{part, links?}]]}`。イベント `[{time, value}]` |
| ノード 5 | `rig` ノードが `hitAreas` を含む | クリック領域 `{id, name, meshes}`。判定順。[書き出し先](EXPORT_TARGETS.md#クリック領域)を参照 |
| ノード 6 | `rig` ノードが `modifierStack` を含む | 明示的で順序のあるモディファイアインスタンス、アルゴリズムのバージョン、固定対象、設定、休眠中の上書き、引退したインスタンス ID、適用済みの能力。省略時のフィールドは旧プリセットの手順を表し、空のスタックは付加プリセットがないことを表す |
| ノード 6 | `clips` ノードに `file` を持つモーションがある | 適用済みモーションが残す安定したファイル名。通常のクリップの改名では変わらない |
| ノード 7 | `clips` ノードに `captured_ranges` を持つモーションがある | 固定したカーブに対応するパラメータ範囲 `{min, max, repeat}`。再構築のときに元の制御点を変えないため |
| リビジョン 1 | ログがペイロードノードを参照しない | — |
| リビジョン 2 | ログがペイロードノードを参照し、インデックスが `payloads` を列挙する | `{"$payload": "<sha256>"}` のログ項目 |
| リビジョン 3 | ログがチェックポイント記録 `rig_checkpoint` を含む | インデックスの `rig` が、記録が参照する Rig オブジェクトを列挙し、アーカイブが `rig/objects/` にそれらを保存する。`payloads` も同時に列挙できる |
| リビジョン 4 | ベイク結果を持つシミュレーションがある | `rig` ノードの各ベイクを `{"$bake": "<sha256>"}` と書き、インデックスの `bakes` がそれらを列挙し、内容は `document/bakes/` にある。`payloads` と `rig` も同時に列挙できる |

schema 1 だけを読むプログラムは、schema 2 のノードまたはリビジョンに出会うと開くことを拒否し、新しいフィールドを捨てません。現在のプログラムは、ノード schema 1〜4（`settings` ノードは 1〜5、`rig` ノードは 1〜6、`clips` ノードは 1〜7）、リビジョン schema 1〜4 を読み、より高い schema は今までどおり拒否します。schema 5 を知らないプログラムは、表情、ポーズ、またはモーションイベントを持つ `clips` ノードに出会うと、それらを捨てるのではなく開くことを拒否します。リビジョン schema 4 の `rig` ノードは、インデックスが列挙したベイクだけを参照でき、開くときはハッシュで各ベイクファイルを照合します。以前のプログラムはリビジョン schema 4 に出会うと開くことを拒否するため、ベイク付きのプロジェクトを保存したあとは、それらではもう開けません。リビジョン schema 3 のインデックスは `rig` を列挙しなければならず、開くときは `rig/objects/` にそれらのオブジェクトがあることを 1 つずつ照合し、1 つでも欠けていれば開くことを拒否します。schema 3 に対応しないプログラムは、この種のリビジョンからモデルを構築できないため、開くことを拒否します。リビジョン schema 2 はペイロードを少なくとも 1 つ列挙しなければならず、ログは自分が列挙したペイロードだけを参照できます。保存時、schema 2 のノードをすでに含むリビジョンは、512 文字以上の作者ログ項目をペイロードノードとして外へ出します（ログノード内の参照は 80 文字未満）。各ペイロードは 1 回だけ書き、リビジョンインデックスは schema 2 です。schema 1 だけを読むプログラムは、もともとこの種のリビジョンを開けません。新しいフィールドを含まないドキュメントは、今までどおりすべて schema 1 を書き、ノードとインデックスはバイト単位で変わりません。こうして、長い履歴の各リビジョンが完全なログを 1 部ずつ保存することはなくなり、アーカイブの体積と保存時間は、リビジョン数の二乗では増えなくなります。

### ベイクファイル

シミュレーションのベイク（`rigEdits.simulations[*].bake`）は頂点オフセットの配列が主で、しばしば 1 つのリビジョンドキュメントの大部分を占め、しかも多くのリビジョン間で変わりません。それは `rig` ノードには置きません。異なるベイクごとに、バイトの SHA-256 でパックした JSON ファイルとして保存し、リビジョン間で共有します。ボーンなど他の Rig 定義を変えても、ベイクはコピーされません。

パックした JSON（`PackedJson`）は、JSON 値を損失なく保存します。要素が少なくとも 8 個で、各数のテキストがちょうどその float32 値の規範テキスト（プログラムが float を書くときの書き方）である配列を、JSON テキストの中で `{"$f32": 序号}` に置き換え、数値は元のビットでテキストのあとに書きます。残りの数値は元のテキストを残し、デコードすると要素ごとに同じ JSON になります。レイアウト：魔数 `P2LJ`、バージョン 1、フラグ（1 はテキスト中に参照がないこと。元の値自体が `{"$f32": …}` オブジェクトを含むときに使う）、テキスト長と UTF-8 テキスト、配列の個数、そのあと各配列の長さと、その float をバイト平面で並べたもの（すべての float の最初のバイト、次に 2 番目……。DEFLATE 圧縮のため）。整数はビッグエンディアンです。

### テクスチャフィールド

4 つのフィールドはすべて任意で、省略は旧い意味そのものであり、旧ドキュメントの revision には参加しません。生成とアトラスのパックがそれらを読みます（規則は[ドキュメント層](DOCUMENT_LAYER.md#レイヤーごとの寸法)を参照）。

- ソースレイヤー `rect: [left, top, width, height]`：浮動小数のキャンバス矩形（キャンバス単位）。つまりレイヤーのキャンバス上の位置で、ピクセル操作はそれを変えません。省略時、または整数境界と等しいときは書きません。整数の `left/top/width/height` は今までどおり外接枠で、矩形はその中になければなりません。レイヤーのラスター（`raster` の幅と高さ）は任意の解像度でよく、矩形とは無関係です。ラスターピクセル / 矩形サイズが、そのレイヤーのネイティブ密度で、2 軸は異なってもかまいません。
- ドキュメント `textureOverrides: {图层 ID: {density?, lock?, pin?: {page, x, y}}}`：レイヤーごとのテクスチャ密度の倍率（省略時は 1。つまりラスターの元の解像度）、ロック（アトラスが縮小を必要とするとき密度を保つ）、固定したアトラス位置（ページ、左上のページピクセル）。すべて既定値の項目は書きません。`layers` ノードにあります。
- 設定 `atlas: {pageSize, maxPages, padding}`：アトラスの予算。省略時の予算は、旧い `atlasSize` / `texturePadding` に既定ページ数 8 を足したものです。欠けている子フィールドも、同様にこの 2 つへ戻ります。
- 設定 `atlasArrangement: {fitStep, tiles: {图层 ID: {page, x, y, rotation?, footprint?: {cell, columns, rows, bits}}}}`：保存したアトラスのレイアウト。`x`、`y` は、タイルの回転前の矩形の左上です。`rotation`（度。省略時 0）はタイル中心のまわりの回転で、向きは Umamo の配置と同じです（y が下のときは時計回り）。省略時は再構築のたびに自動配置します（旧い意味）。存在するときは各タイルがその位置を保ち、ロックしていないすべてのタイルが `fitStep / 4096` の共通 fit を使います。`footprint` は、メッシュがレイヤーラスター上で覆うセルです（各セルは `cell` ラスターピクセル。`bits` は行ごとに並べたビットマップで、Base64 エンコードの `BitSet`）。footprint 付きのタイルは、これらのセルだけを書きます。新しくインポートしたプロジェクトは、最初のレイアウトを保存します。

## v1 の互換と移行

v1 のアーカイブは、今までどおり開けます。v1 は各リビジョンを完全なスナップショットとして保存します。

| パス | 内容 |
| --- | --- |
| `workspace/<projectId>/HEAD.json`、`history/nodes/` | 現在のノード、ノードの順序、ノードのメタデータ |
| `workspace/<projectId>/history/snapshots/` | 各リビジョンの完全なドキュメント。ソースレイヤー、設定、構造、編集の上書き |
| `workspace/<projectId>/blobs/` | 重複を除いた RGBA ラスター（PNG） |
| `workspace/<projectId>/assets/`、`views/`、`view-images/`、`workflow/`、`tasks.json` | 補助データ |

残りのエントリ（`manifest.json`、`source/`、`workspace.json`、`images/`）は v2 と同じです。v1 を開くときは、これらのスナップショットを直接読み込み、メモリ上のドキュメントは v2 と一致します。次の保存が v2 を書き、対象ファイルを置き換える前に、元の v1 ファイルを同じディレクトリの `<名称>.v1.psd2live` として別に保存します（同名のバックアップがすでにあるときは上書きしない）。移行が変えるのは保存レイアウトだけで、すべてのリビジョン、分岐、注釈、素材、観察図、タスク記録はそのまま残ります。作業ディレクトリの内部は、今までどおりスナップショットのレイアウトを使います。開くときはアーカイブをスナップショットへ展開し、保存はスナップショットを通さず、メモリ上の履歴をエンコードして v2 ノードへ分割し、一時ディレクトリへ直接書きます。

作業ディレクトリのスナップショットが v1 と異なる点は、共有する内容だけです。新しく書いたスナップショットは、空でない `rigEdits.authoringJournal` を `{count, chunks:[键...]}` と書き、項目を内容でブロックに分けて `history/journal/<键>.json` に保存します（ブロックは、要約が選んだ項目のあとで終わり、平均約 4 件、16 件または約 64K 文字を超えない。キーはブロック内の各項目の SHA-256 の SHA-256）。64K 文字以上の `rigEdits.importedCmo3` は `{payload: sha256}` と書き、内容は `history/payloads/<sha256>.txt` にあります。シミュレーションのベイクは `{"$bake": sha256}` と書き、内容は `history/bakes/<sha256>.bin` です（アーカイブと同じパック JSON。同じベイクは各リビジョン間で 1 回だけ読み、同じオブジェクトへデコードする）。項目を追加するときは末尾のブロックだけが増え、それより前に閉じたブロックはリビジョン間で共有します。読み取り時はキーで照合したあと元のスナップショットへ戻し、キーの順序は変わりません。v2 にパックする前も同様に先へ戻すため、アーカイブノードは影響を受けません。スナップショットはコンパクト JSON に変わりました。ブロック分割に対応しない旧プログラムは、オブジェクト形式を読むとエラーになり、ログを捨てることはありません。v2 の展開も、この共有形式でスナップショットを書きます。読み取り時は同じ項目を各リビジョン間で 1 回だけ解析し、同じオブジェクトを共有します（共有ブロックに限りません。ログの末尾ブロックはログの終わりで切れ、隣り合うリビジョンの末尾項目は内容による重複排除でまとまる）。旧版が書いた完全なスナップショットは通常どおり読み、2 種類のスナップショットは混在できます。

内部ファイル名には論理 ID のハッシュを使え、表示名から推論することはできません。PNG は透明ピクセルの下の RGB を残します。異なるリビジョンはラスターリソースを共有します。

## 保存と復元

PSD / CMO3 をインポートするときは、まず元のバイトを作業ディレクトリの `sources/<sha256>.<格式>` へコピーし、その複製から解析します。外部パスは出所の説明にだけ使い、元のファイルの移動、削除、書き換えは保存に影響しません。`workspace.json` の `originalSource: {format, sha256}` がこの出所を記述し、保存は複製の要約を再確認し、アーカイブを開くときは照合して出所を引き継ぎます。記述子のない旧プロジェクトも開けます。画像から作った、または元の出所がないプロジェクトは、ルートの履歴ソース画像から PSD を生成し、CMO3 をインポートしたモデルは、ドキュメント内の元のペイロードを残し続けます。

自動回復は、作業ディレクトリの `recovery.json` を使います（schema `version: 1`。アーカイブ v2 は変えない）。読み込みの身元、Runtime state、履歴の HEAD、永続する補助データ、ワークスペースの presentation、タスク記録を含みます。先に履歴と参照リソースを書き、次にチェックポイントを原子的に更新し、最後にセッションの回復ポインタを更新します。ポーズ、スナップショット、注釈、可視性、またはワークスペースの内容が独立して変わったときも回復の書き込みを起こし、リアルタイムフレームと純粋な表示の変化は起こしません。回復はチェックポイントの HEAD をチェックアウトし、これらの内容を戻して、未保存のままにします。古い作業ディレクトリにチェックポイントがないときは、履歴の互換で回復します。タスク記録は、実行を自動では再開しません。

バックグラウンドの書き込みは、目的地ごとに、実際にディスクへ落ちたバージョンを確認します。待ち状態の完全なスナップショットはまとめられ、より早い証跡は、それを上書きした完全なバージョンが確認します。失敗は対応する目的地に残り、同じ目的地の成功した再試行だけが消します。保存は、プロジェクトに関係する重要な証跡を待ち、無関係な観察リソースの書き込みが回復の失敗を隠すことはありません。通常の保存 / 破棄による終了は、キューを空にしたあと、一致する回復ポインタを削除し、所有する展開ディレクトリを解放します。異常終了は回復リソースを残します。空にする処理がタイムアウトしたときは登録を残し、次回の起動では、生きているプロセスも回復の参照もない、登録済みの一時ディレクトリだけを回収します。

ボーンデータは設定の `rigEdits.skeleton` にあり、現在のボーン下位構造のバージョンは 9 です（プロジェクト形式のバージョンは変えません）。ボーンは明示的な `connected`（省略時は旧い座標推定と互換）、複製の `parameterOverride`、`mirror` の対、`ik` の求解設定を保存します。スケルトンは `symmetryAxisX`、名前付きの `savedPoses`、ボーン ID をキーとする `ikTargets`、アートプリミティブ ID をキーとする `manualWeights` を保存します。手作業のウェイトは、静止キャンバスの `positions`、`triangles`、頂点ごとのボーン ID → ウェイトの `weights` を含み、暗号化された頂点を三角形補間で読めるようにします。旧プロジェクトは、省略時に空の手作業ウェイト、固定対象なし、既定の IK 設定として読み、編集は続けられます。

保存は不変の状態を捕捉し、同じディレクトリの一時ファイルへ順に書き、マニフェストを検証してから、対象を原子的に置き換えます。原子的な置き換えに対応しないときは失敗を報告し、旧プロジェクトを残します。捕捉後に起きた新しい編集は、今までどおり未保存の内容に属します。

保存は、すでにある内容を繰り返しエンコードしません。作業ディレクトリにすでにあるラスター PNG は、ハードリンク（非対応のときは更新時刻を残したコピー）で一時ディレクトリへ入れ、ピクセルからエンコードし直しません。リビジョンの分割結果も 1 回だけ計算します。作業ディレクトリの `archive/` ミラーは、保存済みまたは開いた各リビジョンの v2 インデックス（`archive/revisions/<快照键>.json`：`{version, index, rasters}`）と、それが参照するドキュメントノード（`archive/document/`）を保存します。保存時はこれらのファイルを直接リンクし、新しいリビジョンだけをエンコード、分割、ハッシュ計算するため、再び保存する時間は履歴の長さではなく変更量に従います。v2 アーカイブを開くとき、現在の規則で分割したリビジョン（インラインのベイクがない。schema 2 のノードを含むときは長いログ項目がすでに外へ出ている）は、そのノードとともにミラーへ直接移し、開いたあとの最初の保存も新しいリビジョンだけを処理します。残りのリビジョンは保存時に分割し直します。ミラーの記録バージョンが異なる、またはファイルが欠けているときは、通常どおり分割します。アーカイブを書くときは、`document/` の各エントリの SHA-256 がファイル名と一致することを照合し、ミラーファイルの破損は保存を失敗させ、誤ったアーカイブは書きません。アーカイブを書くときは各ファイルを 1 回だけ読み、SHA-256 と CRC-32 は書き込み時に計算し、それに基づいてマニフェストを生成します。`STORED` エントリの要約は、エントリ名、長さ、更新時刻でプロセス内にキャッシュし（プロジェクトを開いて展開するときも記録する）、変わっていないラスターを再び保存するときはコピーするだけで再計算しません。一時ファイルを書き終えて `fsync` したあと、ストリームで読み戻して照合します。エントリ集合は、書いたエントリにマニフェストを足したものちょうどであり、各エントリの長さと CRC は書き込み時と一致し、マニフェストのバイトは同じです。アーカイブをディスクへ展開してハッシュを再計算することは、もうしません。キャッシュの失効が誤ったアーカイブを書くことはありません。`STORED` エントリは書き込み時に CRC と長さで実際のバイトを検査し、読み戻しでもう一度照合し、どれか合わなければ保存は失敗して元のファイルを残します。開くときの完全な SHA-256 検証は変わりません。

開くときは、ヘッドリビジョンだけを読んでデコードします。残りのリビジョンは、初めて使うとき（履歴の切り替え、観察、保存がそれらの内容を必要とするとき）に読みます。同じ作業ディレクトリが読むリビジョンは、ログ項目、ベイク、ラスターを共有します。v2 アーカイブを開くとき、現在の規則で分割したリビジョンは作業スナップショットを書かず、初めて使うときにミラー内のノードから直接組み立てます（各ノード、項目、Rig オブジェクトの参照は、展開時にすでに 1 つずつ照合済み）。保存は、読んでいないリビジョンをデコードしません。そのチェックポイントの Rig オブジェクトはミラーのインデックスが列挙し、オーサード Rig はノードのリビジョン ID で探します。履歴の中の異なるラスターは 1 回だけデコードし、1 つのリビジョンのラスターは複数スレッドで並列にデコードします（スレッド数はコア数とヒープメモリに制限される）。作業ディレクトリ自身が書いた 8 ビット RGBA/RGB、非インターレースの PNG は RGBA バイトへ直接デコードし、他の PNG は ImageIO で読みます。結果はいずれもラスターの要約と照合し、照合を通過した要約はリビジョンと Rig の段階キャッシュへ直接入れ、繰り返し計算しません。素材一覧の検査は、素材メタデータだけを読み、ラスターファイルの存在を確認し、ピクセルはデコードしません（ピクセルは素材を読み込むときに照合する）。開くたびに 1 回だけ検査します。

現在の内容が HEAD と同じとき、通常の保存は履歴を追加しません。明示的な `checkpoint` は、変化がなくても点を残せます。保存の失敗を、すでに永続化したものとして扱ってはならず、画面のエラーを確認する必要があります。

すべての分岐は残ります。取り消しは親ノードに沿い、やり直しに後続が複数あるときは分岐を選びます。古いノードから編集すると新しい分岐ができます。タイトル、メモの変更、分岐を隠すことは、元のノードを書き換えず、素材も削除しません。

新しいパラメータ定義の作成、更新、削除は `rigEdits.authoringJournal` に書き、実際の編集順で再生します。そのためパラメータの削除は、それより前のキーフォームと、最後の既定値更新のあとに実行されます。旧版の静的パラメータ上書きフィールドは、元の読み取り順を保ち、既存のスナップショット、revision、ノード ID は書き換えられません。チャンネルのキーフォームとジオメトリ編集も、同様に永続化します。

内部のメッシュ置換記録 `canvas_mesh_rebuild` も、順序のある journal にあります。親のローカル頂点、三角形、ソースキャンバスのテクスチャ座標、旧頂点の補間の出所、Glue の頂点写像を保存します。任意の `neutral_bounds` は、置換メッシュの中立キャンバス境界を保存します。CMO3 をインポートしたキャンバス基形の最初の置換は、`previous_parent_points` を保存できます。再生は、まず通常およびブレンドのキーフォームを、これらの親の中立頂点へ基を置き直し、そのあと新しいトポロジへ移行します。既存のパスは元の三角形に沿って変換します。再生は、旧メッシュジオメトリの SHA-256、親、ソース画像の身元を照合します（記録した親が、もう基礎生成から生まれないとき、たとえばスケルトンを有効にしたあとの腕の垂下 Warp では、頂点数だけを照合し、頂点を記録点からキャンバスのテクスチャ座標へのアフィンフィットで現在の親空間へ移す。[DOCUMENT_LAYER](DOCUMENT_LAYER.md#親が生成されなくなる)を参照）。現在のテクスチャ位置から UV を再構築し、キーフォーム、ブレンドシェイプ、パス、頂点グループ、Glue を移行します。独立したメッシュ設定の変更は、それまでのログを残して順序のある置換を追加し、旧い作成記録や履歴を書き換えず、プロジェクト形式のバージョンも変えません。これは内部の再生形式です。

内部の作成記録 `canvas_mesh_create` は、元の生成入力に存在しないメッシュを保存します。固定 ID、ソース画像とレイヤーの身元、透明な被覆境界、親とパーツ、静的なマテリアル、ローカル頂点 / 三角形、キャンバスのテクスチャ座標、生成パラメータ / キーフォーム / チャンネル、パスです。再生は現在のアトラスを解析し直し、メッシュ ID がまだ存在しないことを要求します（`replace: true` 付きの記録は、同じ ID の既存メッシュを置き換え、その描画順とパーツ位置を残す。なければ作成する。画像をインポートして置くとき、メッシュがすでにチェックポイントの Rig にあるなら、書くのはこの種の記録）。親とソース画像が解決でき、ジオメトリ、キーフォーム、ラスターサイズを検証します。通常の透明レイヤー、および口が初めて可視ピクセルを描いたときは、メッシュを自動作成します。そのあと空にしても、作成したジオメトリとバインドは保ちます。メッシュ設定の変更は、現在の候補の中の作成ジオメトリを更新し、バインドし直したパスとウェイトを永続化します。それより前の履歴スナップショットはそのままです。これは内部形式で、プロジェクト形式のバージョンは変えません。

旧版の内部区画記録 `canvas_source_partition`（新しいバージョンは、CMO3 をインポートしたモデルの上でだけ書く）は、元のメッシュ ID、ローカルジオメトリの指紋、親、各元頂点が属する区画、ならびに新しいメッシュ / ソース画像の ID、名前、可視性、ローカル頂点、三角形、ソースキャンバスのテクスチャ座標、頂点補間の出所を保存します。再生は、元のログ位置でバインドを複製し、現在のアトラスを写し直します。元のレイヤーのソフト削除は、すべての編集を再生したあとでフィルタします。連結成分は元の順で Glue を移行します。シミュレーション対象、既存のベイクオフセット、Glue の役割は、同じドキュメント候補へ書きます。元の生成入力は透明なプレースホルダを追加してテクスチャの被覆を残し、既存の履歴は書き換えず、アーカイブ形式のバージョンも変えません。

内部のアートプリミティブ記録 `art_primitive` は、生成モデル上のポリゴン、連結成分、前後分割を記録します。記録位置で `supersedes` の中のメッシュを削除し、パーツがそれに代わります。元のレイヤーは `source` から外れ、凍結した `generationSource` にだけ残り、`deletedLayerIds` には入りません。パーツは通常のソースレイヤーです。分割は 1 回の再生成です。元のメッシュをジェネレーターが生成したときは、記録はバージョン 2（`v: 2`）で、ジェネレーターがパーツを生成する根拠になる内容だけを宣言します（静止キャンバスのメッシュ、レイヤー、分類。`authored` は空オブジェクト）。元のメッシュ上のユーザー変更は、三者マージでパーツへ運びます。元のメッシュが生成されたものでないとき（ログが作成したメッシュ）は、記録はバージョン 1 で、パーツはすべてのデータをユーザーオブジェクトとして伴います。どちらの場合も、記録の直後に `rig_checkpoint` が 1 つ続き、記録自体はもう再生しません。フィールドと生成入力の扱いは[ドキュメント層](DOCUMENT_LAYER.md#分割の実体化アートプリミティブ記録-art_primitive)を参照してください。

より早いバージョンが書いた記録も読めます。バージョン 1 の記録はパーツのすべてのデータを伴い、バージョン 2 の記録は `authored` に、生成値と異なるマテリアルとユーザーデータ、`geometry_residual` / `channels_residual` を保存し、直後に `generated_override` が続きます。それらのあとチェックポイントがないときは、今までどおり再生します。このようなプロジェクトを初めて編集するとき、元のログの末尾に現在のオーサード Rig のチェックポイントを書き、それ以後はこれらの記録を再生しません（[ドキュメント層](DOCUMENT_LAYER.md#旧版の再生)を参照）。旧プロジェクトの `canvas_source_partition`、`canvas_depth_split` も同様に扱い、アーカイブ形式のバージョンは変わりません。

内部の `mesh_generation_baseline` マークは、それまでのグローバルメッシュ、レイヤーごとの上書き、alpha しきい値を保存し、基礎生成にだけ影響します。ドキュメントの現在の設定は、今までどおり実際の要求を表します。その後のメッシュ更新、リセット、全体調整は、保存したメッシュ入力または現在のピクセルから置換を生成し、実際の親の中立座標で `canvas_mesh_rebuild` を追加します。通常、区画、新規、CMO3 をインポートしたメッシュは同じ置換手順を使い、通常 / ブレンドのキーフォーム、パス、頂点グループ、Glue、シミュレーションのベイクオフセットは新しいトポロジへ移行します。ベイクは旧い指紋と品質指標を残し、頂点数を更新し、入力が古いことを報告し続けます。削除済みのメッシュも、まず再生してからフィルタし、復元は新しいトポロジを使います。旧ドキュメントは、実際にメッシュを変更した新しい候補にだけマークを追加し、旧い revision、履歴ノード、アーカイブバージョンは変わりません。インポートしたモデルは、置き換えたメッシュのテクスチャアドレスだけを正規化し、完全に透明なソース画像は既存のトポロジを残します。置換のたびに、前のトポロジの編集オフセットを補間します。トポロジが粗くなったあと設定をリセットしても、すでに失った高周波の細部は回復できません。

レイヤーの削除はログレコード `layer_delete` を書きます（`{op, layer_id, meshes}`。オーサード Rig がこれらのメッシュと、それらを参照するマスク、Glue、パス、ウェイトを削除する）。レイヤーは同時に `source` と生成入力から離れ、構築はこの記録の前にチェックポイントを書きます。以下は旧バージョンのソフト削除にだけ当てはまります。それはドキュメントにすでにある `deletedLayerIds` を使い、ソースピクセルや順序のある編集を消さず、旧い履歴ノードも変更しません。作成記録、ソース画像の区画、奥行き分割、または内部の `layer_membership` マークを含むプロジェクトは、再構築 / 書き出しのとき、まず完全な生成入力と編集を回復し、そのあと削除済みレイヤーと派生した唇をフィルタし、活動中のモデルのマスク参照、Glue、パス、頂点グループを片付けます。復元は、保存した ID とバインドを再生し直します。通常のプロジェクトが初めて実際に削除または復元するとき、新しい候補に現在の生成範囲と、すべてのソース画像 / Drawable の身元を保存し、`op` フィールドだけの `layer_membership` マークを追加します。復元後もその身元の基線は残ります。CMO3 のインポートは元のモデルの ID と座標系を引き継ぎ、マークを追加するだけです。上記の記録がない旧ドキュメントは、今までどおり元の生成規則で読み、既存の revision とノードを自動ではアップグレードも書き換えもしません。削除中のメッシュ設定の変更も、隠したメッシュを再生し、バインドし直したパス / ウェイトを保存します。テクスチャの下限は完全な入力を使います。GUI と MCP の削除、指定 / すべての復元は候補の確定を共有し、繰り返し操作は履歴を追加しません。既存の journal と基線フィールドを引き継ぎ、アーカイブ形式のバージョンは変えません。

履歴ドキュメントの任意の `generationSource` は、現在のソース画像と同じキャンバス、レイヤー、ラスター blob の形式を使い、基礎 Rig の生成に必要な元のラスター形状を保存します。現在の `source` は、描画後の実際のピクセルを提供します。生成の座標系と基礎トポロジは保存した入力を使い、そのあとソースキャンバス座標に従って UV を現在のテクスチャへ写し直します。切り抜きを狭めるときは透明な被覆を補い、旧メッシュが隣の画像をサンプリングしないようにします。任意の `meshSource` は同じエンコードを使い、明示的な再構築または最初の作成の対象レイヤー入力を更新し、生成した唇の輪郭と色を保存します。メッシュの描画を残すことは、その入力を保ちます。生成入力を凍結したあと追加した、まだその中にないレイヤー（Agent が追加した画像など）は、現在のピクセルで生成します。初めて描くか、その画像を置き換えるとき、候補はまず変更前のピクセルを、そのメッシュの輪郭の描き方で `generationSource` へ書きます。`meshTrace = CANVAS` はキャンバス解像度（キャンバス単位あたり 1 ピクセル、整数境界）、`TEXTURE` はテクスチャの元の密度で整数境界へ敷きます（浮動小数の矩形はラスターへ折り込む）。残すメッシュの描画はトポロジを変えず、メッシュを再構築するときは元のメッシュから移行します。奥行き分割の前片、アートプリミティブのパーツ、区画の断片は、今までどおりそれぞれの記録に従います。アセットレイヤーを再び置くときはその項目を外し、メッシュは新しい配置に従って再生成します。既存の revision は補って書きません。頂点が変わっていなくても、派生したテクスチャ入力の更新は永続的な変化に属します。任意の `placementSource` もソース画像の形式を保存し、画像ファイルをインポートしたときに切り抜いたあとの元ピクセルを残して、ファイルインポートのレイヤーを識別します。インポートと配置はピクセルを再サンプリングせず、レイヤーのキャンバス矩形（`rect`）だけを変えます。旧バージョンが境界に合わせて縮小したレイヤーは、再び置くときにその元ピクセルへ戻ります。4 種のソース画像と履歴ノードは、重複を除いた PNG blob を共有します。新しいフィールドを省略しても、旧い revision や履歴ノードは変わりません。

GUI が捕捉したキャンバスピクセルと、MCP のラスタージェスチャーは、同じドキュメント候補に入ります。完全に消しても、再構築フラグを渡しても、レイヤー、基礎メッシュ、バインドは残り、暗黙のソフト削除はしません。CMO3 の描画は、編集していないメッシュの元のアトラスと UV を残し、描いたメッシュにだけテクスチャページを追加します。

プロジェクトを開き直すときは、リビジョンが保存したオーサード Rig、またはログの最後のチェックポイントからモデルを構築します。どちらもないときは、ソース画像、設定、編集ログから再構築します。ネイティブハンドル、ネットワーク接続、実行中のタスク、アニメーションの時計は保存しません。保存した Agent タスクは記録であり、実行を自動では回復しません。

確定済みのポーズとパラメータロックは、ランタイムの補助状態にワークスペースごとに保存します。アーカイブは、今までどおり `workspace.json` の元のワークスペース / キャンバスフィールドへ投影します。保存はワークスペースごとに、捕捉した永続値とロックを使い、GUI の一時的な表示値と評価キャッシュは除きます。旧いポーズは、照会、プレビューの変更、スナップショットの適用のとき、現在のパラメータ定義に正規化します。読み取りと論理に変化がなければ、旧い記録や履歴ノードは書き換えません。ワークスペースを複製すると、複製した永続ポーズを登録します。

`workspace.json` の任意の `assetCatalog` は `{version:1, assets:[ID...], workflow:[ID...]}` を保存し、確定済みの素材と、参照 / 位置合わせのメンバー集合を記録します。リソースは今までどおり既存の補助ディレクトリを使い、Rig journal には入りません。素材の書き込みはランタイムの永続 state を進め、Rig revision や履歴ノードは変えません。保存は捕捉した一覧に従ってリソースをコピーし、あとから確定した素材は除きます。旧ファイルに一覧がないときは、開く段階で既存の不変記録からメンバーを固定し、履歴は書き換えません。新しいプロジェクトは空の一覧から始まります。開くときは同時に、一覧のメンバーの存在、プロジェクトの身元、参照関係を検査します。素材の検査 / 試し合わせは、捕捉したメンバーだけを使い、失敗または確定前のキャンセルは候補ファイルを公開しません。

## 検証の境界

開くときは、バージョン（1 または 2）、マニフェスト、ハッシュ、ドキュメントノードのハッシュと schema、ペイロード参照、ラスター、履歴参照、HEAD を検証します。知らないドキュメントノードの型、またはより高い schema は、開くことを拒否し、内容を捨てません。重複エントリ、パスの範囲外、非対応のバージョンは拒否します。展開の制限は、最大 1,000,000 エントリ、実際の展開データ 64 GiB です。ZIP が宣言するサイズに頼って制限を回避しないでください。

展開して見ることはできますが、手作業の変更はすべての参照とマニフェストのハッシュを同期する必要があります。通常の操作は画面と履歴ツールを使います。旧い `.rgba.gz` の回復ストレージは互換読み取りに属し、新しいプロジェクトの主な書き込み形式ではありません。

## 入り口

- PSD のインポート：`Ctrl+Shift+O`。プロジェクトを開く：`Ctrl+O`。
- 保存 / 名前を付けて保存：`Ctrl+S` / `Ctrl+Shift+S`。名前を付けて保存は、既定で現在のプロジェクトと同じディレクトリに置き、提案するファイル名は現在のプロジェクトファイルでもなく、既存ファイルとも重なりません（`名称-2`、`名称-3`…）。対象がすでに存在するときはウィンドウ内で上書きを確認し、対象がまさに現在のプロジェクトファイルのときは別に説明します。編集がまだ適用中のときに要求した保存または名前を付けて保存は、キューに入りステータスバーで知らせ、編集が終わってから実行します。キューに入った名前を付けて保存は、その後の `Ctrl+S` で通常の保存へ格下げされません。システムのファイルダイアログは主ウィンドウを親にし、すでに 1 つ開いているときに再び要求すると、それを前面へ出します。
- MCP：`project_save`、`project_save_as`、`project_open`、ならびに `history_checkpoint`、`history_list`、`history_checkout`。名前を付けて保存と開くは絶対パスを使い、先に UI で目的地を選ぶ必要はありません。変更要求は現在の `project_id`、不透明な `state`、一意の `request_id` を使います。同じノードを開き直しても、旧い状態は失効します。公開された要約は、内部のプロジェクトフィールドをすべて照会できることではありません。[MCP 契約](../agent/MCP_AUTHORING.md)を参照してください。

独立した Warp の新規作成は、順序のある `authoringJournal` の `warp` コマンドに保存します。固定 ID、親、メッシュ一覧、フィットのオプションを記録します。新しいコマンドは、旧い静的な Warp/structure フィールドを追加しません。旧版の Warp 記録は、今までどおり元の再生順で読み、保存済みの履歴ノードは書き換えません。

モディファイアインスタンスは `inputFingerprint` を保存でき、高価な評価の完全な上流入力の身元になります。シミュレーションのベイクとその身元は、スタックとともに `rig` ノードとドキュメントリビジョンへ入ります。それは設定から独立し、旧いインスタンスは省略時に旧いベイク指紋で検証を続け、最初の候補準備のあと完全な身元を補記します。

モーションモディファイアが固定したクリップは `captured_ranges` を記録でき、各トラックを固定したときのパラメータの最小値、最大値、循環属性を保存します。このフィールドを含む `clips` ノードは schema 7 を使います。範囲が変わっていないとき、再構築は固定済みのカーブ制御点を書き換えず、実際に範囲を調整したあとでカーブを整え、記録を更新します。このフィールドを含まないノードは、元の schema を引き継ぎます。
