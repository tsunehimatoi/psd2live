# 프로젝트 형식 v2

[문서 목록](../README.md)

`.psd2live`는 암호화하지 않은 ZIP입니다. JSON은 UTF-8을 쓰고, 래스터 자원은 PNG입니다. 저장한 프로젝트에는 계속 편집하는 데 필요한 소스 소재와 히스토리가 들어 있으며, 원본 PSD 경로에 의존하지 않습니다. 내보내기 보고서 `.psd2live.json`은 이 형식이 아닙니다.

ZIP 항목의 압축 방식: PNG(`assets/`, `images/`, 관찰 그림)와 CMO3 소스 파일은 이미 압축되어 있어 `STORED`(압축하지 않음)로 씁니다. 1 MiB를 넘는 다른 비 JSON 파일(예: 소스 PSD)은 먼저 샘플링하고, 가장 빠른 단계로 샘플 압축한 결과가 원래 크기의 절반보다 작을 때만 DEFLATE(가장 빠른 단계)하며, 아니면 `STORED`입니다. JSON 등 나머지 항목은 평소처럼 DEFLATE합니다. `manifest.json`은 마지막 항목입니다. 항목은 이름순으로 정렬하고, 수정 시각은 모두 1980-01-01로 기록하며, 이름은 UTF-8입니다. 항목 수, 오프셋, 길이가 클래식 ZIP 범위를 넘으면 ZIP64 기록을 씁니다. 작은 항목은 여러 스레드에서 미리 읽고 압축한 뒤 순서대로 씁니다. 다시 읽어 맞추는 것과 열 때의 풀기도 항목 단위로 병렬입니다. 읽기는 어떤 압축 방식과 어떤 항목 순서든 받습니다. 이전 버전은 모든 항목을 DEFLATE하고 목록이 다른 항목 사이에 있었으며, 그런 아카이브도 평소처럼 엽니다. 압축 방식과 항목 순서는 형식 신원이 아니며, 목록 해시는 푼 뒤의 바이트를 대상으로 합니다.

## 저장 상태와 프로젝트 교체

제목 표시줄의 `*`와 저장 / 포기 확인은 프로젝트 내용을 기준으로 하며, 아카이브가 인터페이스 상태를 함께 기록하는지는 따로입니다.

| 변화 | 저장을 요구하는가 |
| --- | --- |
| 소스 그림, 모델 편집, 생성 / 내보내기 설정, 출력 디렉터리, 히스토리 전환 | 예 |
| 파라미터 자세와 잠금, 스냅샷, 히스토리 주석, 타임라인 보조(파라미터 북마크와 각 모션의 가림, 트랙 고정, 마커), 캔버스 레이어 / 디포머 가시성, 소재와 작업 기록 | 예 |
| 작업 공간 만들기, 삭제, 이름 변경, 재배열, 캔버스 만들기 또는 닫기 | 예 |
| 선택과 호버, 검색, 카메라, 작업 공간 / 캔버스 포커스, 편집 / 미리보기 모드, 레이아웃, 패널 펼침과 표시 옵션 | 아니요. 수동 저장할 때는 복구할 수 있는 인터페이스 상태를 여전히 기록 |
| 재생, 추적 스위치, 실시간 미리보기 프레임, 관찰 로그 | 아니요 |

저장은 완전한 버전 하나를 캡처합니다. 디스크에 쓰는 동안 생긴 새 내용 수정은 저장되지 않은 상태로 남고, 인터페이스 조작은 저장 완료에 영향을 주지 않습니다. 제출하지 않은 필드를 디스크의 값으로 되돌리면, 한 번의 수정 표시만으로 `*`가 남지 않습니다. 제출된 히스토리는 여전히 저장해야 합니다.

GUI에서 포기하고 열면, 이전에 실행 중이던 편집과 필드 제출이 끝난 뒤 교체 경계를 캡처합니다. 포기를 선택하면 이전의 저장하지 않은 내용을 교체할 수 있습니다. 불러오는 동안의 새 내용 편집이나 또 한 번의 프로젝트 교체는 이번 열기를 실패하게 합니다. 불러오는 동안의 인터페이스 조작은 교체를 막지 않습니다. 취소하거나 불러오기에 실패하면 원래 프로젝트와 복구 기록을 유지합니다. 깨끗한 프로젝트로 교체에 성공하면, 이전 복구 쓰기가 끝난 뒤 포기한 복구 표시를 정리합니다.

## 아카이브 배치(v2)

저장은 v2를 씁니다. 각 히스토리 개정은 내용으로 주소를 매기는 문서 노드로 나뉘고, 바뀌지 않은 부분은 개정 사이에 공유됩니다. 노드는 각자 schema 버전을 가집니다.

| 경로 | 내용 |
| --- | --- |
| `manifest.json` | 형식 이름, 버전 `2`, 프로젝트 UUID, 페이로드 SHA-256 목록 |
| `source/original.psd` 또는 `source/original.cmo3` | 원래 가져온 소스 파일. 그림으로 프로젝트를 만들면 PSD 소스 파일을 생성 |
| `history/HEAD.json` | 현재 노드와 노드 순서 |
| `history/nodes/` | 불변 부모 사슬 노드와 메타데이터(v1과 같음) |
| `history/revisions/<key>.json` | 각 개정의 인덱스: `{schema, nodes:{类型:哈希}, overrides?, clips?, payloads?}` |
| `document/nodes/<类型>/<sha256>.json` | 문서 노드 `{schema, kind, value}`. 유형은 `source`(소스 레이어와 그룹), `generation-source` / `mesh-source`(이전 버전이 쓴 `placement-source`는 읽을 때 무시), `layers`(가시성, 소프트 삭제, 분류, 부모, 메시와 텍스처 덮어쓰기), `settings`, `rig`(파라미터, 스켈레톤, 스윙, 시뮬레이션, 물리, 클릭 영역 등의 Rig 정의), `journal`(저작 편집 로그, 덮어쓰기 제외), `layout`(사용자 태그, 소재 연결, 생성 상태), `materials`(소재 라이브러리: 폴더와 항목, 픽셀은 `assets/`의 래스터를 참조, SVG 원문은 내장. PSD / CMO3에서 읽은 폴더는 `origin` 파일 이름을 달고, 그 항목의 `placementCanvas`는 기본 배치가 있는 캔버스 크기), `document`(나머지 필드). `layout`과 `materials`는 문서에 Layout 상태가 있을 때만 쓰며, 그것들을 모르는 이전 버전은 열기를 거부 |
| `document/nodes/payload/<sha256>.json` | 큰 로그 항목의 내용 주소 페이로드 노드. schema 2 개정이 `payloads`에 나열 |
| `document/overrides/<sha256>.json` | 생성 결과 덮어쓰기 `generated_override`. 편집 로그 안의 위치와 함께 |
| `document/clips/<sha256>.json` | 모션 클립(`motions`, 각 클립의 `events` 포함), 생성 모션 설정(`motionPresets`), 표정(`expressions`), 자세(`pose`). 뒤의 둘은 프로젝트가 표정을 편집했거나 자세 그룹을 설정했을 때만 씀 |
| `document/bakes/<sha256>.bin` | 시뮬레이션 베이크 결과(묶은 JSON, 아래 「베이크 파일」을 참조). schema 4 개정이 `bakes`에 나열 |
| `assets/` | 중복을 제거한 RGBA 래스터. PNG로 저장 |
| `auxiliary/assets/` | 임시 소재 메타데이터 |
| `auxiliary/views/`, `auxiliary/view-images/` | 관찰 그림의 공간 매핑. 더 이전에 저장한 프로젝트는 렌더 그림마다 가지고 있었으나, 지금은 저장할 때 더 이상 쓰지 않음 |
| `auxiliary/workflow/` | 소재 참조 패키지, 등록 / 배치 등의 보조 기록 |
| `auxiliary/tasks.json` | Agent 작업과 이벤트 기록 |
| `workspace.json` | 레이아웃, 카메라, 선택, 파라미터 미리보기, 히스토리 주석, 타임라인 보조(`timelineAids`), 로그 등의 영속 UI 상태 |
| `images/<hash>.png` | 로그 그림 |
| `rig/objects/` | Rig 오브젝트: 체크포인트 기록이 참조하는 오브젝트(체크포인트가 있는 개정에 필수), 그리고 각 개정 저작 상태 Rig의 오브젝트 |
| `rig/revisions/` | 선택. 각 개정의 저작 상태 Rig 인덱스(아래 「저작 상태 Rig」를 참조) |
| `cache/head/` | 선택. HEAD 개정 재구축에 쓰는, 지워도 되는 캐시(아래 「HEAD 캐시」를 참조) |
| `thumbnail.png` | 선택. 시작 페이지용 미리보기 그림. 저장할 때 모델의 정지 자세, 긴 변 256 px 이하. 열 때는 읽지 않으며, 저장할 때마다 다시 씀 |

문서 노드와 덮어쓰기, 클립 파일의 파일 이름은 그 바이트의 SHA-256이며, 열 때 하나씩 맞춥니다. 분리는 손실이 없습니다. 열 때 인덱스대로 각 개정의 완전한 문서를 다시 맞추며, revision ID, 노드 ID, 분기는 변하지 않습니다. 완전한 Rig 모델은 저장하지 않습니다. 개정에 저작 상태 Rig가 있으면 열 때 그것으로 바로 구축하고, 아니면 소스 그림, 설정, 편집으로 재구축합니다. 보조 디렉터리는 관련 기능을 쓰는지에 따라 나타납니다. `cache/`에는 지워도 되는 재구축 캐시만 두며, 어떤 신원에도 참여하지 않습니다.

### 체크포인트

로그 항목 `rig_checkpoint`(`{op, v:1, authored:{header, frame, deformers, meshes}, issues}`)는 저작 상태 Rig를 데이터로 로그 안의 그 위치에 저장합니다. `authored`는 아래 저작 상태 Rig의 인덱스(헤더와 오브젝트 해시)이고, `issues`는 그것을 쓴 다시 생성 병합이 깨끗하게 옮기지 못한 내용입니다(`{kind, target, detail}`, 고정 Rig를 참조). 재생은 마지막 체크포인트에서 시작합니다. 그 저작 상태 Rig(텍스처 아틀라스가 바뀌면 캔버스 텍스처 좌표로 다시 리그)에 그 이후의 항목을 더합니다. 이전 항목은 히스토리일 뿐이며 다시 재생하지 않습니다. 편집이 기초 생성 결과를 바꾸게 할 때, 생성한 모델을 처음 편집할 때, 마지막 체크포인트 이후가 32개가 찼을 때 프로그램이 체크포인트를 씁니다([문서 레이어](DOCUMENT_LAYER.md#체크포인트)를 참조). 사용자는 직접 편집하지 않습니다. 뒤의 둘은 편집 이전의 저작 상태 Rig를 저장하고, 생성 스냅샷 `generated`는 이전 체크포인트의 것을 그대로 씁니다. 따라서 이 버전에서 편집한 생성 프로젝트는 모두 개정 3입니다.

체크포인트의 오브젝트는 문서에 속합니다. 작업 디렉터리는 그것들을 참조하는 스냅샷을 쓰기 전에 오브젝트를 `<project>/rig-objects/`에 쓰고, 저장할 때 `rig/objects/`로 아카이브합니다.

### 저작 상태 Rig

`rig/revisions/`는 각 개정의 저작 상태 Rig를 저장합니다. 기초 생성(스켈레톤 베이크 포함)에 이전 형식의 정적 편집과 로그 전체를 더한 뒤, 스윙, 시뮬레이션 쓰기, 덮어쓰기 병합 이전의 Rig입니다(설계는 고정 Rig를 참조).

| 경로 | 내용 |
| --- | --- |
| `rig/objects/<sha256>.bin` | Rig 오브젝트 하나(`RigIrObjects`): 프레임(디포머와 메시 이외의 모든 내용), 디포머 하나, 또는 메시 하나. 바이트 SHA-256으로 이름 붙이며, 개정과 체크포인트 사이에 공유 |
| `rig/revisions/<revision>.json` | `{header, frame, deformers:[...], meshes:[...]}`: 헤더와 Rig 순서대로 나열한 오브젝트 해시 |

- 오브젝트는 중립 IR의 바이너리 형식(`RigIrBinary`, 부동소수점은 원래 비트로 저장)으로 인코딩하며, 매직 넘버, 인코딩 버전, 오브젝트 유형을 가집니다. 읽기는 `RigIrObjects.MIN_VERSION`부터의 각 버전을 받고, IR에 추가된 필드는 그것이 들어간 버전부터 읽습니다. 인코딩 버전 5부터 부동소수점 배열은 바이트 평면으로 씁니다(모든 값의 첫 바이트, 그다음 두 번째……). 수치는 변하지 않고 DEFLATE 압축률이 분명히 높아집니다. 버전 6은 IR의 클릭 영역을 더합니다(이전 버전 오브젝트는 평소처럼 읽음. 그 뒤 저장에서 새로 쓴 오브젝트는 모두 버전 6 인코딩이며, 내용이 바뀌지 않은 오브젝트도 새 해시를 얻으므로, 업그레이드 뒤 처음 체크포인트를 쓸 때 아카이브가 한 번에 커지고, 그 뒤는 평소처럼 공유). 기존 오브젝트는 그 해시가 체크포인트에 참조되며, 원래 인코딩을 유지합니다.
- 헤더 `{format:"psd2live-authored-rig", version:1, build, binding_key, pages, layers, bounds, face, warnings, skipped, visibility}`: 메시에서 텍스처 페이지, 소스 레이어, 중립 경계로의 매핑, 얼굴 중심, 반지름과 초기 기울기, 생성 경고, 재생에서 건너뛴 항목, 레이어 표시를 적용해야 하는 메시, 텍스처 아틀라스 리그 키입니다. 부동소수점은 원래 비트로 정수에 씁니다.
- 파일 이름의 개정 키는 문서의 개정 ID입니다(`WorkspaceRevisions.of`). 곧 구축이 그것으로 찾는 키입니다.
- 리그 키는 기초 Rig를 생성할 때 텍스처 아틀라스의 배치, 페이지 크기, 텍스처 레이어 사각형의 요약입니다. 열 때 현재 프로그램이 그 개정의 텍스처 아틀라스를 묶습니다. 키가 같으면 저장한 텍스처 좌표를 바로 쓰고, 다르면(이 프로그램이 다르게 묶음) 캔버스 텍스처 좌표로 새 타일에 옮깁니다. 항목을 읽을 수 없거나 검증에 실패하면 평소처럼 구축합니다.
- 저장은 현재 프로세스가 각 개정에 대해 구축한 저작 상태 Rig와, 아카이브를 열 때 읽은 항목을 쓰되, 헤더, 각 분기 끝, 로그에 체크포인트가 없는 개정으로 한정합니다. 나머지 개정은 마지막 체크포인트에서 구축하므로 기초 Rig를 생성할 필요가 없고, 그것들마다 한 부씩 저장하지 않습니다(고친 메시마다 아카이브의 또 다른 오브젝트입니다). 없는 개정은 쓰지 않습니다. `-Dpsd2live.materializedRigs=false`는 읽기와 쓰기를 끕니다.
- 개정 인덱스는 개정 ID나 문서 노드에 들어가지 않습니다. 그것이 없는 개정은 평소처럼 구축합니다. 로그에 체크포인트가 있으면 체크포인트에서 구축하고, 아니면 생성하고 재생합니다. CMO3를 가져온 모델은 저작 상태 Rig를 쓰지 않습니다.

### HEAD 캐시

저장할 때 `cache/head/`를 쓸 수 있습니다. HEAD 개정 재구축에서 비싸고 안전하게 재사용할 수 있는 중간 결과를 저장해, 열 때 재계산을 건너뛰게 합니다. 이것은 권위 데이터가 아닙니다. 열기는 여전히 소스 그림, 설정, 편집 로그로 완전히 재구축하며, 캐시는 생성기의 메모리 캐시를 미리 채울 뿐입니다. 쓸지는 그 캐시 자신의 내용 키가 정하므로, 캐시가 있을 때와 없을 때의 재구축은 비트 단위로 같은 모델을 얻습니다.

| 경로 | 내용 |
| --- | --- |
| `cache/head/manifest.json` | `{format:"psd2live-head-cache", version:1, build, generator, revision, language, entries:[{kind, file, sha256, bytes}]}` |
| `cache/head/skeleton-bake.bin` | HEAD의 스켈레톤 베이크: JSON 헤더(베이크 버전, 캐시 키, 스켈레톤 정의, 읽기 집합, 읽지 않은 오브젝트의 부모 다시 매달기 기록, 선택적 완전 해시) + 출력 모델의 바이너리 IR(`RigIrBinary`, 부동소수점은 원래 비트로 저장. 텍스처 아틀라스, 소스 그림 목록, 디폼 경로는 포함하지 않으며, 맞으면 새 기초 Rig에서 취함) |

- 키: HEAD revision ID, 프로그램 버전(`Compiler.version`), 생성기 상수 `ProjectHeadCache.GENERATOR`(생성 논리가 바뀌었는데 항목 자신의 키가 알아채지 못할 때 증가), 인터페이스 언어. 하나라도 다르면 전체를 무시합니다. 항목 안의 스켈레톤 캐시 키(`SkeletonRig.BAKE_VERSION`, 베이크가 읽은 모든 내용, 언어 포함)가 맞는지 다시 정합니다.
- 스켈레톤 베이크만 캐시합니다(콜드 스타트 약 5–7초, 맞으면 약 1–7 ms). 항목 하나가 64 MB를 넘으면 쓰지 않습니다. 저장할 때 프로세스 안에서 최근에 쓴, 스켈레톤 정의가 HEAD와 같은 베이크를 취합니다. 없으면 캐시를 쓰지 않습니다. `-Dpsd2live.headCache=false`는 쓰기와 읽기를 끕니다.
- 열 때 목록 형식, 키, 항목 체크섬이 맞지 않거나, 항목이 없거나, 잘리거나, 디코드할 수 없으면 로그만 남기고 버리며, 열기 실패로 이어지지 않습니다. 읽은 뒤 푼 디렉터리의 `cache/`를 삭제합니다.
- 캐시는 `history/`, `document/` 밖에 있으며, revision ID, 문서 노드, 히스토리에 들어가지 않습니다. 그 디렉터리가 없는 아카이브도 평소처럼 엽니다. 아카이브 목록은 이 파일들을 평소처럼 나열하고 검증합니다. 이전 v2 프로그램은 나머지 항목과 함께 푼 뒤 읽지 않으며, 캐시가 있는 아카이브도 열 수 있습니다. 그것들이 다시 저장할 때는 그 디렉터리를 유지하지 않습니다.

### 노드 schema

노드와 개정 인덱스의 schema는 새 필드를 쓸 때만 올리고, 나머지 노드는 여전히 schema 1을 씁니다. 내용은 바이트 단위로 변하지 않으며, 이전 프로젝트를 저장한 뒤 노드 해시와 개정 인덱스는 이전과 같습니다.

| schema | 적용 | 새 필드 |
| --- | --- | --- |
| 노드 1 | 아래 필드가 없는 노드 | — |
| 노드 2 | `source`와 세 가지 부가 소스 그림 노드에 `rect`가 있는 레이어가 있음. `layers`에 `textureOverrides`가 있음. `settings`에 `atlas` 또는 `atlasArrangement`가 있음 | 아래 텍스처 필드를 참조 |
| 노드 3 | `source` 또는 부가 소스 그림 노드에 `transform`이 있는 레이어가 있음 | 레이어 전체 변환 `[a, b, c, d, e, f]`(`x' = a·x + c·y + e`, `y' = b·x + d·y + f`, 캔버스 단위, y는 아래). 레이어의 프레임에 작용(정수 경계와 `rect`). 텍스처 좌표는 프레임에 고정되고, 생성은 프레임만 읽음. 단위 변환은 쓰지 않음 |
| 노드 4 | `layout` / `materials` 노드에 Layout 노드가 도입된 뒤 추가된 필드가 있음 | 레퍼런스 그림, 레퍼런스 레이어와 핀, 그림, 소재의 캔버스와 레퍼런스 표시 |
| 노드 5 | `clips` 노드에 `expressions`, `pose`가 있거나, `events`가 있는 모션 클립이 있음 | 표정 `{id, name, fade_in, fade_out, entries:[{parameter, blend, value}]}`(`blend`는 `ADD` / `MULTIPLY` / `OVERWRITE`). 자세 `{fade_in, groups:[[{part, links?}]]}`. 이벤트 `[{time, value}]` |
| 노드 5 | `rig` 노드에 `hitAreas`가 있음 | 클릭 영역 `{id, name, meshes}`. 판정 순서. [내보내기 대상](EXPORT_TARGETS.md#클릭-영역)을 참조 |
| 노드 6 | `rig` 노드에 `modifierStack`이 있음 | 명시적으로 순서가 있는 모디파이어 인스턴스, 알고리즘 버전, 고정 대상, 구성, 잠든 덮어쓰기, 은퇴한 인스턴스 ID, 적용한 능력. 없는 필드는 이전 프리셋 흐름을 뜻하고, 빈 스택은 추가 프리셋이 없음을 뜻함 |
| 노드 6 | `clips` 노드에 `file`이 있는 모션이 있음 | 적용한 모션이 유지하는 안정적인 파일 이름. 일반 클립 이름 변경을 따르지 않음 |
| 노드 7 | `clips` 노드에 `captured_ranges`가 있는 모션이 있음 | 고정한 곡선에 대응하는 파라미터 범위 `{min, max, repeat}`. 재구축할 때 원래 제어점이 바뀌지 않게 함 |
| 개정 1 | 로그가 페이로드 노드를 참조하지 않음 | — |
| 개정 2 | 로그가 페이로드 노드를 참조하고, 인덱스가 `payloads`를 나열 | `{"$payload": "<sha256>"}` 로그 항목 |
| 개정 3 | 로그에 체크포인트 기록 `rig_checkpoint`가 있음 | 인덱스의 `rig`가 기록이 참조하는 Rig 오브젝트를 나열하고, 아카이브가 `rig/objects/`에 그것들을 저장. `payloads`를 함께 나열할 수 있음 |
| 개정 4 | 베이크 결과가 있는 시뮬레이션이 있음 | `rig` 노드의 각 베이크를 `{"$bake": "<sha256>"}`로 쓰고, 인덱스의 `bakes`가 그것들을 나열하며, 내용은 `document/bakes/`에 있음. `payloads`와 `rig`를 함께 나열할 수 있음 |

schema 1만 읽는 프로그램은 schema 2 노드나 개정을 만나면 열기를 거부하며, 새 필드를 버리지 않습니다. 현재 프로그램은 노드 schema 1–4(`settings` 노드 1–5, `rig` 노드 1–6, `clips` 노드 1–7), 개정 schema 1–4를 읽고, 더 높은 schema는 여전히 거부합니다. schema 5를 모르는 프로그램은 표정, 자세, 모션 이벤트가 있는 `clips` 노드를 만나면 열기를 거부하며, 그것들을 버리지 않습니다. 개정 schema 4의 `rig` 노드는 인덱스가 나열한 베이크만 참조할 수 있으며, 열 때 해시로 각 베이크 파일을 맞춥니다. 이전 프로그램은 개정 schema 4를 만나면 열기를 거부하므로, 베이크가 있는 프로젝트를 저장한 뒤에는 그 프로그램으로 열 수 없습니다. 개정 schema 3의 인덱스는 `rig`를 나열해야 하며, 열 때 `rig/objects/`에 그 오브젝트가 있는지 하나씩 맞춥니다. 하나라도 없으면 열기를 거부합니다. schema 3를 지원하지 않는 프로그램은 이런 개정에서 모델을 구축할 수 없으므로 열기를 거부합니다. 개정 schema 2는 페이로드를 하나 이상 나열해야 하며, 로그는 자신이 나열한 페이로드만 참조할 수 있습니다. 저장할 때, schema 2 노드가 이미 있는 개정은 512자 이상의 저작 로그 항목을 페이로드 노드로 밖으로 뺍니다(로그 노드 안의 참조는 80자 미만). 각 페이로드는 한 번만 쓰고, 개정 인덱스는 schema 2입니다. schema 1만 읽는 프로그램은 원래 이런 개정을 열 수 없습니다. 새 필드가 없는 문서는 여전히 모두 schema 1을 쓰며, 노드와 인덱스는 바이트 단위로 변하지 않습니다. 이렇게 하면 긴 히스토리의 각 개정이 완전한 로그를 하나씩 저장하지 않으며, 아카이브 크기와 저장 시간이 개정 수의 제곱으로 늘지 않습니다.

### 베이크 파일

시뮬레이션 베이크(`rigEdits.simulations[*].bake`)는 정점 오프셋 배열이 주이며, 개정 문서의 대부분을 차지하는 일이 많고, 많은 개정 사이에서 변하지 않습니다. `rig` 노드에 두지 않습니다. 서로 다른 베이크마다 바이트 SHA-256으로 묶은 JSON 파일 하나를 저장하고, 개정 사이에 공유하므로, 스켈레톤 등 다른 Rig 정의를 고쳐도 베이크를 복사하지 않습니다.

묶은 JSON(`PackedJson`)은 JSON 값 하나를 손실 없이 저장합니다. 원소가 8개 이상이고 각 수의 텍스트가 그 float32 값의 규범 텍스트(프로그램이 float를 쓸 때의 표기)인 배열은, JSON 텍스트에서 `{"$f32": 序号}`로 바꾸고, 수치는 원래 비트로 텍스트 뒤에 씁니다. 나머지 수치는 원래 텍스트를 유지하며, 디코드하면 원소마다 같은 JSON을 얻습니다. 배치: 매직 넘버 `P2LJ`, 버전 1, 플래그(1은 텍스트에 참조가 없음을 뜻하며, 원래 값 자체에 `{"$f32": …}` 오브젝트가 있을 때 사용), 텍스트 길이와 UTF-8 텍스트, 배열 개수, 그다음 각 배열의 길이와 그 float를 바이트 평면으로 배열(모든 float의 첫 바이트, 그다음 두 번째……, DEFLATE 압축에 유리). 정수는 빅 엔디안입니다.

### 텍스처 필드

네 필드는 모두 선택이며, 없으면 이전 의미이고, 이전 문서의 revision에 참여하지 않습니다. 생성과 아틀라스 묶기가 그것들을 읽습니다(규칙은 [문서 레이어](DOCUMENT_LAYER.md#레이어별-크기)를 참조).

- 소스 레이어 `rect: [left, top, width, height]`: 부동소수점 캔버스 사각형(캔버스 단위). 곧 레이어가 캔버스에 있는 위치이며, 픽셀 조작은 그것을 바꾸지 않습니다. 없거나 정수 경계와 같으면 쓰지 않습니다. 정수 `left/top/width/height`는 여전히 외접 상자이며, 사각형은 그 안에 있어야 합니다. 레이어 래스터(`raster`의 너비와 높이)는 아무 해상도든 될 수 있고 사각형과 무관합니다. 래스터 픽셀 / 사각형 크기가 그 레이어의 고유 밀도이며, 두 축이 다를 수 있습니다.
- 문서 `textureOverrides: {图层 ID: {density?, lock?, pin?: {page, x, y}}}`: 레이어별 텍스처 밀도 배수(기본 1, 곧 래스터 원래 해상도), 잠금(아틀라스를 줄여야 할 때 밀도를 유지), 고정 아틀라스 위치(페이지, 왼쪽 위 페이지 픽셀). 모두 기본값인 항목은 쓰지 않습니다. `layers` 노드에 있습니다.
- 설정 `atlas: {pageSize, maxPages, padding}`: 아틀라스 예산. 없으면 예산은 이전 `atlasSize` / `texturePadding`에 기본 페이지 수 8을 더한 것입니다. 빠진 하위 필드도 이 둘로 되돌아갑니다.
- 설정 `atlasArrangement: {fitStep, tiles: {图层 ID: {page, x, y, rotation?, footprint?: {cell, columns, rows, bits}}}}`: 저장한 아틀라스 배치. `x`, `y`는 타일이 회전하지 않은 사각형의 왼쪽 위이고, `rotation`(도, 기본 0)은 타일 중심을 축으로 한 회전이며, 방향은 Umamo의 배치와 같습니다(y가 아래일 때 시계 방향). 없으면 재구축할 때마다 자동 배치합니다(이전 의미). 있으면 각 타일은 위치를 유지하고, 잠기지 않은 모든 타일은 `fitStep / 4096`의 공통 fit을 씁니다. `footprint`는 메시가 레이어 래스터에서 덮는 칸입니다(칸마다 `cell` 래스터 픽셀, `bits`는 행으로 배열한 비트맵, Base64로 인코딩한 `BitSet`). footprint가 있는 타일은 이 칸만 씁니다. 새로 가져온 프로젝트는 첫 배치를 저장합니다.

## v1 호환과 마이그레이션

v1 아카이브도 열 수 있습니다. v1은 각 개정을 완전한 스냅샷 하나로 저장합니다.

| 경로 | 내용 |
| --- | --- |
| `workspace/<projectId>/HEAD.json`, `history/nodes/` | 현재 노드, 노드 순서, 노드 메타데이터 |
| `workspace/<projectId>/history/snapshots/` | 각 개정의 완전한 문서: 소스 레이어, 구성, 구조, 편집 덮어쓰기 |
| `workspace/<projectId>/blobs/` | 중복을 제거한 RGBA 래스터(PNG) |
| `workspace/<projectId>/assets/`, `views/`, `view-images/`, `workflow/`, `tasks.json` | 보조 데이터 |

나머지 항목(`manifest.json`, `source/`, `workspace.json`, `images/`)은 v2와 같습니다. v1을 열면 이 스냅샷을 바로 읽어 들이며, 메모리의 문서는 v2와 같습니다. 다음 저장은 v2를 쓰고, 대상 파일을 바꾸기 전에 원래 v1 파일을 같은 디렉터리의 `<名称>.v1.psd2live`로 따로 저장합니다(같은 이름 백업이 있으면 덮어쓰지 않음). 마이그레이션은 저장 배치만 바꾸며, 모든 개정, 분기, 주석, 소재, 관찰 그림, 작업 기록은 원래대로 유지합니다. 작업 디렉터리 내부는 여전히 스냅샷 배치를 씁니다. 열 때 아카이브를 스냅샷으로 풀고, 저장은 스냅샷을 거치지 않으며, 메모리의 히스토리를 인코딩하고 v2 노드로 나누어 임시 디렉터리에 바로 씁니다.

작업 디렉터리의 스냅샷이 v1과 다른 점은 공유 내용뿐입니다. 새로 쓴 스냅샷은 비어 있지 않은 `rigEdits.authoringJournal`을 `{count, chunks:[键...]}`로 쓰고, 항목은 내용으로 나누어 `history/journal/<键>.json`에 저장합니다(블록은 요약이 고른 항목 뒤에서 끝나고, 평균 약 4개, 16개 또는 약 64K자를 넘지 않음. 키는 블록 안 각 항목 SHA-256의 SHA-256). 64K자를 넘는 `rigEdits.importedCmo3`는 `{payload: sha256}`로 쓰고, 내용은 `history/payloads/<sha256>.txt`에 있습니다. 시뮬레이션 베이크는 `{"$bake": sha256}`로 쓰고, 내용은 `history/bakes/<sha256>.bin`입니다(아카이브와 같은 묶은 JSON. 같은 베이크는 각 개정 사이에서 한 번만 읽고, 같은 오브젝트로 디코드). 항목을 추가하면 끝의 블록만 새로 생기고, 이전에 닫힌 블록은 개정 사이에 공유됩니다. 읽을 때 키를 맞춘 뒤 원래 스냅샷으로 되돌리며, 키 순서는 변하지 않습니다. v2로 묶기 전에도 같이 되돌리므로, 아카이브 노드는 영향을 받지 않습니다. 스냅샷은 조밀한 JSON으로 바뀌었습니다. 블록 나누기를 지원하지 않는 이전 프로그램은 오브젝트 형태를 읽으면 오류를 보고하며, 로그를 버리지 않습니다. v2를 풀 때도 이 공유 형태로 스냅샷을 쓰며, 읽을 때 같은 항목은 각 개정 사이에서 한 번만 해석하고 같은 오브젝트를 공유합니다(공유 블록에만 한정되지 않음. 로그 끝 블록은 로그 끝에서 잘리고, 이웃 개정의 끝 항목은 내용 중복 제거로 합쳐짐). 이전 버전이 쓴 완전한 스냅샷도 평소처럼 읽으며, 두 스냅샷은 섞어 저장할 수 있습니다.

내부 파일 이름은 논리 ID의 해시를 쓸 수 있으며, 표시 이름에서 추론할 수 없습니다. PNG는 투명 픽셀 아래의 RGB를 유지합니다. 서로 다른 개정은 래스터 자원을 공유합니다.

## 저장과 복구

PSD / CMO3를 가져올 때, 먼저 원본 바이트를 작업 디렉터리의 `sources/<sha256>.<格式>`에 복사한 뒤 그 사본에서 해석합니다. 외부 경로는 출처 설명에만 쓰이며, 원본 파일을 옮기거나 삭제하거나 고쳐도 저장에 영향을 주지 않습니다. `workspace.json`의 `originalSource: {format, sha256}`가 이 출처를 설명하고, 저장은 사본 요약을 다시 확인하며, 아카이브를 열 때 맞추고 출처를 인수합니다. 설명자가 없는 이전 프로젝트도 열 수 있습니다. 그림으로 만들거나 원래 출처가 없는 프로젝트는 루트 히스토리 소스 그림에서 PSD를 생성하고, CMO3를 가져온 모델은 문서의 원래 페이로드를 계속 유지합니다.

자동 복구는 작업 디렉터리의 `recovery.json`을 씁니다(schema `version: 1`, 아카이브 v2를 바꾸지 않음). 불러오기 신원, Runtime state, 히스토리 HEAD, 영속 보조 데이터, 작업 공간 presentation, 작업 기록이 들어갑니다. 먼저 히스토리와 참조 자원을 쓰고, 체크포인트를 원자적으로 갱신한 뒤, 마지막으로 세션 복구 포인터를 갱신합니다. 자세, 스냅샷, 주석, 가시성, 작업 공간 내용이 독립적으로 바뀌어도 복구 쓰기를 일으키며, 실시간 프레임과 순수 표시 변화는 일으키지 않습니다. 복구는 체크포인트 HEAD를 체크아웃하고 이 내용을 되돌리며, 저장되지 않은 상태를 유지합니다. 이전 작업 디렉터리에 체크포인트가 없으면 히스토리 호환으로 복구합니다. 작업 기록은 실행을 자동으로 다시 시작하지 않습니다.

백그라운드 쓰기는 목적지에 따라 실제로 디스크에 떨어진 버전을 확인합니다. 기다리는 완전한 스냅샷은 합칠 수 있으며, 더 이전 증명은 그것을 덮는 완전한 버전이 확인합니다. 실패는 해당 목적지에 남고, 같은 목적지의 성공한 재시도만 지웁니다. 저장은 프로젝트와 관련된 핵심 증명을 기다리며, 무관한 관찰 자원의 쓰기가 복구 실패를 가리지 않습니다. 정상적인 저장 / 포기 종료는 큐를 비운 뒤 일치하는 복구 포인터를 지우고, 소유한 푼 디렉터리를 해제합니다. 비정상 종료는 복구 자원을 유지합니다. 비우기 시간이 넘으면 등록을 유지하고, 다음 시작은 살아 있는 프로세스와 복구 참조가 없는 등록된 임시 디렉터리만 회수합니다.

스켈레톤 데이터는 구성의 `rigEdits.skeleton`에 있으며, 현재 스켈레톤 하위 구조 버전은 9입니다(프로젝트 형식 버전은 바꾸지 않음). 스켈레톤은 명시적 `connected`(없으면 이전 좌표 추론과 호환), 사본 `parameterOverride`, `mirror` 짝, `ik` 풀이 설정을 저장합니다. 스켈레톤은 `symmetryAxisX`, 이름이 있는 `savedPoses`, 뼈 ID를 키로 하는 `ikTargets`, 아트 프리미티브 ID를 키로 하는 `manualWeights`를 저장합니다. 수동 가중치에는 정지 캔버스 `positions`, `triangles`, 정점마다 뼈 ID → 가중치인 `weights`가 있어, 암호화된 정점이 삼각형 보간으로 읽게 합니다. 이전 프로젝트는 기본적으로 빈 수동 가중치, 고정 대상 없음, 기본 IK 설정으로 읽히며, 계속 편집할 수 있습니다.

저장은 불변 상태를 캡처하고, 같은 디렉터리의 임시 파일에 순서대로 쓴 뒤 목록을 검증하고, 대상을 원자적으로 바꿉니다. 원자적 바꾸기를 지원하지 않으면 실패를 보고하고 이전 프로젝트를 유지합니다. 캡처 뒤에 생긴 새 편집은 여전히 저장되지 않은 내용에 속합니다.

저장은 이미 있는 내용을 다시 인코딩하지 않습니다. 작업 디렉터리에 이미 있는 래스터 PNG는 하드 링크로(지원하지 않으면 수정 시각을 유지한 복사로) 임시 디렉터리에 넣고, 픽셀에서 다시 인코딩하지 않습니다. 개정의 분리 결과도 한 번만 계산합니다. 작업 디렉터리의 `archive/` 미러는 저장했거나 연 각 개정의 v2 인덱스(`archive/revisions/<快照键>.json`: `{version, index, rasters}`)와 그것이 참조하는 문서 노드(`archive/document/`)를 저장합니다. 저장할 때 이 파일을 바로 링크하고, 새 개정만 인코딩, 분리, 해시를 계산하므로, 다시 저장하는 시간은 히스토리 길이가 아니라 변경량에 따라 늘어납니다. v2 아카이브를 열 때, 현재 규칙으로 분리된 개정(인라인 베이크 없음. schema 2 노드가 있으면 긴 로그 항목이 이미 밖으로 나감)은 노드와 함께 미러로 바로 옮기며, 연 뒤의 첫 저장도 새 개정만 처리합니다. 나머지 개정은 저장할 때 다시 분리합니다. 미러 기록 버전이 다르거나 파일이 없으면 평소처럼 분리합니다. 아카이브를 쓸 때 `document/` 아래 각 항목의 SHA-256이 파일 이름과 일치하는지 맞추며, 미러 파일이 손상되면 저장이 실패하고 잘못된 아카이브를 쓰지 않습니다. 아카이브를 쓸 때 각 파일은 한 번만 읽고, SHA-256과 CRC-32는 쓸 때 계산해 그것으로 목록을 만듭니다. `STORED` 항목의 요약은 항목 이름, 길이, 수정 시각으로 프로세스 안에 캐시합니다(프로젝트를 열어 풀 때도 기록). 바뀌지 않은 래스터를 다시 저장할 때는 복사만 하고 다시 계산하지 않습니다. 임시 파일을 다 쓰고 `fsync`한 뒤, 스트림으로 다시 읽어 맞춥니다. 항목 집합은 쓴 항목에 목록을 더한 것과 같고, 각 항목의 길이와 CRC는 쓸 때와 같으며, 목록 바이트는 같습니다. 아카이브를 디스크에 풀어 해시를 다시 계산하지는 않습니다. 캐시가 무효여도 잘못된 아카이브를 쓰지 않습니다. `STORED` 항목은 쓸 때 CRC와 길이로 실제 바이트를 검사하고, 다시 읽어 한 번 더 맞추며, 하나라도 맞지 않으면 저장이 실패하고 원래 파일을 유지합니다. 열 때의 완전한 SHA-256 검증은 변하지 않습니다.

열 때는 HEAD 개정만 읽고 디코드합니다. 나머지 개정은 처음 쓸 때(히스토리 전환, 관찰, 저장이 그 내용을 필요로 할 때) 읽으며, 같은 작업 디렉터리가 읽은 개정은 로그 항목, 베이크, 래스터를 공유합니다. v2 아카이브를 열 때, 현재 규칙으로 분리된 개정은 작업 스냅샷을 쓰지 않고, 처음 쓸 때 미러의 노드로 바로 맞춥니다(각 노드, 항목, Rig 오브젝트 참조는 풀 때 이미 하나씩 맞춤). 저장은 읽지 않은 개정을 디코드하지 않습니다. 그 체크포인트 Rig 오브젝트는 미러 인덱스가 나열하고, 저작 상태 Rig는 노드의 개정 ID로 찾습니다. 히스토리에서 서로 다른 래스터는 한 번만 디코드하고, 개정 하나의 래스터는 여러 스레드가 병렬로 디코드합니다(스레드 수는 코어 수와 힙 메모리로 제한). 작업 디렉터리가 직접 쓴 8비트 RGBA/RGB, 비인터레이스 PNG는 RGBA 바이트로 바로 디코드하고, 다른 PNG는 ImageIO로 읽습니다. 결과는 모두 래스터 요약과 맞추며, 맞춘 요약은 개정과 Rig 단계 캐시에 바로 넣고 다시 계산하지 않습니다. 소재 목록 검사는 소재 메타데이터만 읽고 래스터 파일이 있는지만 확인하며, 픽셀을 디코드하지 않습니다(픽셀은 소재를 불러올 때 맞춤). 열 때마다 한 번만 검사합니다.

현재 내용이 HEAD와 같으면, 일반 저장은 히스토리를 추가하지 않습니다. 명시적 `checkpoint`는 변화가 없어도 점을 남길 수 있습니다. 저장 실패를 이미 영속된 것으로 쳐서는 안 되며, 인터페이스 오류를 확인해야 합니다.

모든 분기는 유지됩니다. 실행 취소는 부모 노드를 따르고, 다시 실행에 후속이 여러 개이면 분기를 고릅니다. 이전 노드에서 편집하면 새 분기가 생깁니다. 제목, 메모를 바꾸거나 분기를 숨겨도 원래 노드를 고치지 않으며, 소재를 삭제하지 않습니다.

새 파라미터 정의의 생성, 갱신, 삭제는 `rigEdits.authoringJournal`에 쓰이며, 실제 편집 순서대로 재생됩니다. 따라서 파라미터 삭제는 이전 키폼과 마지막 기본값 갱신 뒤에 실행됩니다. 이전 정적 파라미터 덮어쓰기 필드는 원래 읽기 순서를 유지하며, 이미 있는 스냅샷, revision, 노드 ID는 다시 쓰지 않습니다. 채널 키폼과 기하 편집도 같이 영속됩니다.

내부 메시 교체 기록 `canvas_mesh_rebuild`도 순서가 있는 journal에 있으며, 부모 로컬 정점, 삼각형, 소스 캔버스 텍스처 좌표, 이전 정점 보간 출처, Glue 정점 매핑을 저장합니다. 선택적 `neutral_bounds`는 교체 메시의 중립 캔버스 경계를 저장합니다. 가져온 CMO3의 캔버스 기초 형태를 처음 교체할 때는 `previous_parent_points`를 저장할 수 있습니다. 재생은 먼저 일반 키폼과 블렌드 키폼을 이 부모 중립 정점으로 다시 기반을 잡은 뒤 새 토폴로지로 옮기고, 이미 있는 경로는 원래 삼각형을 따라 변환합니다. 재생은 이전 메시 기하 SHA-256, 부모, 소스 그림 신원을 맞춥니다(기록된 부모가 더 이상 기초 생성이 만들지 않으면, 예를 들어 스켈레톤을 켠 뒤의 팔 늘어짐 Warp이면, 정점 수만 맞추고, 정점을 기록된 점에서 캔버스 텍스처 좌표로의 아핀 맞춤으로 현재 부모 공간에 옮깁니다. [DOCUMENT_LAYER](DOCUMENT_LAYER.md#부모가-더-이상-생성되지-않음)를 참조). 현재 텍스처 위치에서 UV를 재구축하고, 키폼, 블렌드 셰이프, 경로, 정점 그룹, Glue를 옮깁니다. 독립 메시 설정 변경은 이전 로그를 유지하고 순서 있는 교체를 추가하며, 이전 생성 기록이나 히스토리를 고치지 않고, 프로젝트 형식 버전도 바꾸지 않습니다. 이것은 내부 재생 형식입니다.

내부 생성 기록 `canvas_mesh_create`는 원래 생성 입력에 없던 메시를 저장합니다. 고정 ID, 소스 그림과 레이어 신원, 투명 덮개 경계, 부모와 파츠, 정적 머티리얼, 로컬 정점/삼각형, 캔버스 텍스처 좌표, 생성 파라미터/키폼/채널, 경로입니다. 재생은 현재 아틀라스를 다시 해석하고, 메시 ID가 아직 없을 것을 요구합니다(`replace: true`가 있는 기록은 같은 ID의 기존 메시를 바꾸고 그 그리기 순서와 파츠 위치를 유지하며, 없으면 생성. 가져온 그림을 놓을 때 메시가 이미 체크포인트의 Rig에 있으면, 쓰는 것이 바로 이런 기록). 부모와 소스 그림을 해석할 수 있어야 하고, 기하, 키폼, 래스터 크기를 검증합니다. 일반 투명 레이어와 입이 처음 보이는 픽셀을 그리면 메시를 자동으로 만듭니다. 그 뒤 비워도 생성 기하와 리그를 유지합니다. 메시 설정 변경은 현재 후보의 생성 기하를 갱신하고, 다시 리그한 경로와 가중치를 영속하며, 이전 히스토리 스냅샷은 원래대로입니다. 이것은 내부 형식이며, 프로젝트 형식 버전을 바꾸지 않습니다.

이전 내부 분할 기록 `canvas_source_partition`(새 버전은 가져온 CMO3 모델에서만 씀)은 원 메시 ID, 로컬 기하 지문, 부모, 각 원 정점이 속한 분할, 그리고 새 메시/소스 그림 ID, 이름, 가시성, 로컬 정점, 삼각형, 소스 캔버스 텍스처 좌표, 정점 보간 출처를 저장합니다. 재생은 원래 로그 위치에서 리그를 복사하고 현재 아틀라스를 다시 매핑합니다. 원 레이어의 소프트 삭제는 모든 편집을 재생한 뒤에 거릅니다. 연결 덩어리는 원래 순서로 Glue를 옮깁니다. 시뮬레이션 대상, 기존 베이크 오프셋, Glue 역할은 같은 문서 후보에 씁니다. 원래 생성 입력에 투명 자리 표시를 추가해 텍스처 덮개를 유지하고, 기존 히스토리는 고치지 않으며, 아카이브 형식 버전도 바꾸지 않습니다.

내부 아트 프리미티브 기록 `art_primitive`는 생성 모델 위의 다각형, 연결 덩어리, 앞뒤 분리 분할을 기록합니다. 기록 위치에서 `supersedes` 안의 메시를 지우고, 파츠가 그 자리를 차지합니다. 원 레이어는 `source`에서 제거되고, 얼린 `generationSource`에만 남으며, `deletedLayerIds`에 넣지 않습니다. 파츠는 일반 소스 레이어입니다. 분할은 한 번의 다시 생성입니다. 원 메시를 생성기가 만들었으면 기록은 버전 2(`v: 2`)이며, 생성기가 파츠를 만드는 데 쓰는 내용만 선언합니다(정지 캔버스 메시, 레이어, 분류, `authored`는 빈 오브젝트). 원 메시의 사용자 수정은 삼자 병합으로 파츠에 옮겨집니다. 원 메시가 생성된 것이 아니면(로그가 만든 메시) 기록은 버전 1이며, 파츠가 모든 데이터를 사용자 오브젝트로 가집니다. 두 경우 모두 기록 바로 뒤에 `rig_checkpoint`가 따르며, 기록 자체는 더 이상 재생하지 않습니다. 필드와 생성 입력의 처리는 [문서 레이어](DOCUMENT_LAYER.md#분할-실체화-아트-프리미티브-기록-art_primitive)를 참조합니다.

더 이전에 쓴 기록도 읽을 수 있습니다. 버전 1 기록은 파츠의 모든 데이터를 가지고, 버전 2 기록은 `authored`에 생성 값과 다른 머티리얼과 사용자 데이터, `geometry_residual` / `channels_residual`을 저장하며, 바로 `generated_override`가 따릅니다. 그 뒤에 체크포인트가 없으면 예전처럼 재생합니다. 이런 프로젝트를 처음 편집할 때, 원래 로그 끝에 현재 저작 상태 Rig의 체크포인트를 쓰고, 그 뒤로는 이 기록을 재생하지 않습니다([문서 레이어](DOCUMENT_LAYER.md#구버전-재생)를 참조). 이전 프로젝트의 `canvas_source_partition`, `canvas_depth_split`도 같이 처리하며, 아카이브 형식 버전은 변하지 않습니다.

내부 `mesh_generation_baseline` 표시는 이전의 전역 메시, 레이어별 덮어쓰기, alpha 임계값을 저장하며, 기초 생성에만 영향을 줍니다. 문서의 현재 설정은 여전히 실제 요청을 나타냅니다. 이후의 메시 갱신, 재설정, 전역 조정은 저장한 메시 입력 또는 현재 픽셀에서 교체를 생성하고, 실제 부모 중립 좌표에 `canvas_mesh_rebuild`를 추가합니다. 일반, 분할, 새로 만들기, 가져온 CMO3 메시는 같은 교체 흐름을 쓰며, 일반/블렌드 키폼, 경로, 정점 그룹, Glue, 시뮬레이션 베이크 오프셋이 새 토폴로지로 옮겨집니다. 베이크는 이전 지문과 품질 지표를 유지하고, 정점 수를 갱신하며, 입력이 오래되었음을 계속 보고합니다. 삭제한 메시도 먼저 다시 만든 뒤 거르며, 복구는 새 토폴로지를 씁니다. 이전 문서는 실제로 메시를 수정한 새 후보에만 표시를 추가하고, 이전 revision, 히스토리 노드, 아카이브 버전은 변하지 않습니다. 가져온 모델은 이미 교체한 메시의 텍스처 주소만 정규화합니다. 완전히 투명한 소스 그림은 기존 토폴로지를 유지합니다. 교체할 때마다 이전 토폴로지의 편집 오프셋을 보간하며, 토폴로지가 거칠어진 뒤 설정을 재설정해도 이미 잃은 고주파 세부를 복구할 수 없습니다.

레이어 삭제는 로그 기록 `layer_delete`를 씁니다(`{op, layer_id, meshes}`. 저작 상태 Rig가 이 메시와 그것들을 참조하는 마스크, Glue, 경로, 가중치를 삭제). 레이어는 동시에 `source`와 생성 입력을 떠나고, 구축은 그 기록 앞에 체크포인트를 씁니다. 아래는 이전 버전의 소프트 삭제에만 적용됩니다. 그것은 문서에 이미 있는 `deletedLayerIds`를 쓰며, 소스 픽셀이나 순서 있는 편집을 지우지 않고, 이전 히스토리 노드도 수정하지 않습니다. 생성 기록, 소스 그림 분할, 깊이 분할, 내부 `layer_membership` 표시가 있는 프로젝트는, 재구축/내보낼 때 먼저 완전한 생성 입력과 편집을 복구한 뒤 삭제한 레이어와 파생 입술을 거르고, 활동 모델의 마스크 참조, Glue, 경로, 정점 그룹을 정리합니다. 복구는 저장한 ID와 리그를 다시 재생합니다. 일반 프로젝트가 처음 실제로 삭제하거나 복구하면, 새 후보에 현재 생성 범위와 모든 소스 그림/Drawable 신원을 저장하고, `op` 필드만 있는 `layer_membership` 표시를 추가합니다. 복구 뒤에도 그 신원 기준선을 유지합니다. 가져온 CMO3는 원 모델의 ID와 좌표계를 그대로 쓰고, 표시만 추가합니다. 위 기록이 없는 이전 문서는 여전히 원래 생성 규칙으로 읽히며, 기존 revision과 노드를 자동으로 올리거나 고치지 않습니다. 삭제 중의 메시 설정 변경도 숨긴 메시를 다시 만들고 다시 리그한 경로/가중치를 저장하며, 텍스처 하한은 완전한 입력을 씁니다. GUI와 MCP의 삭제, 지정/전체 복구는 후보 제출을 공유하며, 반복 조작은 히스토리를 추가하지 않습니다. 기존 journal과 기준선 필드를 그대로 쓰며, 아카이브 형식 버전을 바꾸지 않습니다.

히스토리 문서의 선택적 `generationSource`와 현재 소스 그림은 같은 캔버스, 레이어, 래스터 blob 형식을 쓰며, 기초 Rig 생성에 필요한 원래 래스터 형태를 저장합니다. 현재 `source`는 그린 뒤의 실제 픽셀을 제공합니다. 생성 좌표계와 기초 토폴로지는 저장한 입력을 쓰고, 소스 캔버스 좌표로 UV를 현재 텍스처에 다시 매핑합니다. 자르기를 조일 때 투명 덮개를 채워, 이전 메시가 이웃 그림을 샘플하지 않게 합니다. 선택적 `meshSource`는 같은 인코딩을 쓰며, 명시적 재구축이나 처음 생성한 대상 레이어 입력을 갱신하고, 생성한 입술의 윤곽과 색을 저장합니다. 메시 페인팅을 유지하면 그 입력을 유지합니다. 생성 입력을 얼린 뒤에 추가되어 아직 그 안에 없는 레이어(예: Agent가 추가한 그림)는 현재 픽셀로 생성합니다. 처음 그리거나 그 그림을 교체할 때, 후보는 바꾸기 전의 픽셀을 그 메시가 윤곽을 따라 그리는 방식으로 `generationSource`에 씁니다. `meshTrace = CANVAS`는 캔버스 해상도(캔버스 단위당 픽셀 하나, 정수 경계)이고, `TEXTURE`는 텍스처 원래 밀도로 정수 경계에 깝니다(부동소수점 사각형을 래스터로 환산). 메시를 유지하는 페인팅은 토폴로지를 바꾸지 않고, 메시를 재구축하면 원 메시에서 옮깁니다. 깊이 분할의 앞조각, 아트 프리미티브 파츠, 분할 조각은 각자의 기록을 따릅니다. 자산 레이어를 다시 놓으면 그 항목을 제거하고, 메시는 새 배치를 따라 다시 생성됩니다. 기존 revision에는 보충해서 쓰지 않습니다. 정점이 바뀌지 않아도, 파생 텍스처 입력의 갱신은 영속 변화에 속합니다. 선택적 `placementSource`도 소스 그림 형식을 저장하며, 그림 파일을 가져올 때 자른 뒤의 원래 픽셀을 유지해 파일 가져오기 레이어를 식별합니다. 가져오기와 배치는 더 이상 픽셀을 다시 샘플하지 않고, 레이어 캔버스 사각형(`rect`)만 바꿉니다. 이전 버전이 경계에 맞춰 축소한 레이어는 다시 놓을 때 그 원래 픽셀로 복구됩니다. 네 가지 소스 그림과 히스토리 노드는 중복을 제거한 PNG blob을 공유합니다. 새 필드가 없으면 이전 revision이나 히스토리 노드를 바꾸지 않습니다.

GUI가 캡처한 캔버스 픽셀과 MCP 래스터 제스처는 같은 문서 후보로 들어갑니다. 완전히 지워도 재구축 플래그를 넘겨도 레이어, 기초 메시, 리그를 유지하며, 암묵적으로 소프트 삭제하지 않습니다. CMO3 페인팅은 편집하지 않은 메시의 원래 아틀라스와 UV를 유지하고, 그린 메시에만 텍스처 페이지를 추가합니다.

프로젝트를 다시 열면 개정이 저장한 저작 상태 Rig 또는 로그의 마지막 체크포인트로 모델을 구축합니다. 둘 다 없으면 소스 그림, 설정, 편집 로그로 재구축합니다. 네이티브 핸들, 네트워크 연결, 실행 중인 작업, 애니메이션 시계는 저장하지 않습니다. 저장한 Agent 작업은 기록이며, 실행을 자동으로 복구하지 않습니다.

제출된 자세와 파라미터 잠금은 런타임 보조 상태에 작업 공간별로 저장됩니다. 아카이브는 여전히 `workspace.json`의 원래 작업 공간/캔버스 필드로 투영합니다. 저장은 작업 공간마다 캡처한 영속 값과 잠금을 쓰고, GUI의 임시 표시 값과 평가 캐시는 제외합니다. 이전 자세는 조회, 미리보기 수정, 스냅샷 적용 때 현재 파라미터 정의로 정규화하며, 읽기와 논리가 변하지 않으면 이전 기록이나 히스토리 노드를 고치지 않습니다. 작업 공간을 복사하면 복사한 영속 자세를 등록합니다.

`workspace.json`의 선택적 `assetCatalog`는 `{version:1, assets:[ID...], workflow:[ID...]}`를 저장하며, 제출된 소재와 참조/정합의 구성원 집합을 기록합니다. 자원은 기존 보조 디렉터리를 쓰며, Rig journal에 들어가지 않습니다. 소재 쓰기는 런타임 영속 state를 진행하며, Rig revision이나 히스토리 노드를 바꾸지 않습니다. 저장은 캡처한 목록대로 자원을 복사하고, 나중에 제출한 소재는 제외합니다. 이전 파일에 목록이 없으면, 여는 단계에서 이미 있는 불변 기록으로 구성원을 고정하고 히스토리를 고치지 않습니다. 새 프로젝트는 빈 목록에서 시작합니다. 열 때 목록 구성원이 있는지, 프로젝트 신원, 참조 관계를 함께 확인합니다. 소재 검사/시험 맞춤은 캡처한 구성원만 쓰며, 실패하거나 제출 전에 취소하면 후보 파일을 게시하지 않습니다.

## 검증 경계

열 때 버전(1 또는 2), 목록, 해시, 문서 노드 해시와 schema, 페이로드 참조, 래스터, 히스토리 참조와 HEAD를 검증합니다. 모르는 문서 노드 유형이나 더 높은 schema는 열기를 거부하며, 내용을 버리지 않습니다. 중복 항목, 경로가 범위를 벗어남, 지원하지 않는 버전을 거부합니다. 풀기 제한은 항목 최대 1,000,000개, 실제로 푼 데이터 64 GiB입니다. ZIP이 선언한 크기로 제한을 우회하는 것에 의존하지 마세요.

풀어서 볼 수는 있지만, 수동 수정은 모든 참조와 목록 해시를 함께 맞춰야 합니다. 일반 조작은 인터페이스와 히스토리 도구를 씁니다. 이전 `.rgba.gz` 복구 저장은 호환 읽기이며, 새 프로젝트의 주 쓰기 형식이 아닙니다.

## 입구

- PSD 가져오기: `Ctrl+Shift+O`. 프로젝트 열기: `Ctrl+O`.
- 저장 / 다른 이름으로 저장: `Ctrl+S` / `Ctrl+Shift+S`. 다른 이름으로 저장은 기본적으로 현재 프로젝트와 같은 디렉터리에 두며, 제안하는 파일 이름은 현재 프로젝트 파일도 아니고 기존 파일과 겹치지 않습니다(`名称-2`, `名称-3`…). 대상이 이미 있으면 창 안에서 덮어쓰기를 확인하고, 대상이 바로 현재 프로젝트 파일이면 따로 설명합니다. 편집이 아직 적용 중일 때 요청한 저장이나 다른 이름으로 저장은 대기열에 넣고 상태 표시줄에 알리며, 편집이 끝나면 실행합니다. 대기 중인 다른 이름으로 저장은 이후의 `Ctrl+S`로 일반 저장으로 내려가지 않습니다. 시스템 파일 대화상자는 주 창을 부모 창으로 합니다. 이미 하나가 열려 있을 때 다시 요청하면 그것을 앞으로 가져옵니다.
- MCP: `project_save`, `project_save_as`, `project_open`, 그리고 `history_checkpoint`, `history_list`, `history_checkout`. 다른 이름으로 저장과 열기는 절대 경로를 쓰며, UI에서 먼저 목적지를 고를 필요가 없습니다. 수정 요청은 현재 `project_id`, 불투명한 `state`, 유일한 `request_id`를 씁니다. 같은 노드를 다시 열어도 이전 상태는 무효가 됩니다. 공개 요약이 모든 내부 프로젝트 필드를 조회할 수 있다는 뜻은 아닙니다. [MCP 계약](../agent/MCP_AUTHORING.md)을 참조합니다.

구현: [ProjectArchive](../../../src/main/kotlin/io/github/psd2live/project/ProjectArchive.kt) · [ProjectFormatV2](../../../src/main/kotlin/io/github/psd2live/project/ProjectFormatV2.kt) · [ProjectRepository](../../../src/main/kotlin/io/github/psd2live/project/ProjectRepository.kt) · [WorkspaceStore](../../../src/main/kotlin/io/github/psd2live/project/WorkspaceStore.kt).

독립 Warp 새로 만들기는 순서가 있는 `authoringJournal`의 `warp` 명령에 저장되며, 고정 ID, 부모, 메시 목록, 맞춤 옵션을 기록합니다. 새 명령은 이전 정적 Warp/structure 필드를 추가하지 않습니다. 이전 Warp 기록은 원래 재생 순서로 읽으며, 저장된 히스토리 노드는 고치지 않습니다.

모디파이어 인스턴스는 `inputFingerprint`를 저장할 수 있으며, 비용이 큰 평가의 완전한 상류 입력 신원으로 씁니다. 시뮬레이션 베이크와 그 신원은 스택을 따라 `rig` 노드와 문서 개정에 들어갑니다. 그것은 구성과 독립이며, 이전 인스턴스는 없을 때 이전 베이크 지문으로 계속 검증하고, 첫 후보를 준비한 뒤 완전한 신원을 보충합니다.

모션 모디파이어가 고정한 클립은 `captured_ranges`를 기록할 수 있으며, 각 트랙을 고정할 때의 파라미터 최솟값, 최댓값, 순환 속성을 저장합니다. 이 필드가 있는 `clips` 노드는 schema 7을 씁니다. 범위가 변하지 않으면 재구축이 이미 고정한 곡선 제어점을 다시 쓰지 않고, 실제로 범위를 조정한 뒤에야 곡선을 정리하고 기록을 갱신합니다. 이 필드가 없는 노드는 원래 schema를 그대로 씁니다.
