# 문서 레이어: 생성기, 덮어쓰기, 캐시

형식 설계는 프로젝트를 “의도 + 사용자 덮어쓰기”로 정의합니다. 생성기는 파라미터만 저장하고, 생성 결과는 순수 함수로 계산하며, 사용자가 생성 결과 위에서 한 수정은 안정 ID로 기록하고, 생성기를 다시 돌릴 때 삼자 병합을 합니다. 1단계는 스윙 생성기를 본보기로 메커니즘을 검증했습니다. 이 페이지는 나머지 생성기로의 확장, 측정에 따라 생성 캐시를 넣는 일, 프로젝트 형식 v2의 구현 상태를 기록합니다.

## 구현된 항목

| 부분 | 위치 | 내용 |
| --- | --- | --- |
| 내용 해시 | `format-compile` `document/ContentHash` | 각 부분 규범 텍스트의 SHA-256입니다. 길이로 구분하고, IR 값은 직접 해시할 수 있습니다 |
| 의존 그래프 | `document/GeneratorGraph` | 생성기가 읽고 소유하는 안정 ID를 선언합니다. 위상 정렬, 순환 금지, 객체 하나의 소유자는 하나입니다. 변화 뒤 다시 계산할 하류 생성기를 줍니다 |
| 생성 캐시 | `document/GenerationCache` | 입력 내용 해시로 생성 결과를 캐시합니다(LRU). 미스일 때는 잠금 밖에서 계산해, 느린 생성기가 다른 키를 막지 않습니다 |
| 삼자 병합 | `document/ThreeWayMerge` | 키별로 병합합니다. 사용자가 바꾸지 않은 값은 생성기를 따르고, 생성기가 바꾸지 않은 값은 사용자 값을 남기며, 양쪽이 모두 바꿔 서로 다르면 사용자 값을 남기고 충돌을 보고합니다 |
| 문서 생성기 그래프 | 루트 프로젝트 `core/DocumentGenerators` | 프로젝트의 생성기를 의존 그래프 노드로 등록합니다. 재생은 그래프 순서로 스윙과 시뮬레이션을 돌립니다. 덮어쓰기는 그래프로 키폼의 소유자를 찾습니다 |
| 생성 결과 덮어쓰기 | `core/GeneratedOverrides` | 스윙 Warp 키폼과 베이크한 시뮬레이션 메시 키폼 위의 캔버스 편집은 `generated_override`로 기록하고, 모든 생성기 뒤에 제어점 / 정점 삼자 병합으로 재생합니다 |
| 스켈레톤과 모션 캐시 | `core/SkeletonRig.generate`, `core/MotionPresets.tracks` | 스켈레톤 베이크와 생성 모션은 입력 내용 해시로 `GenerationCache`에 들어갑니다 |
| 재생 검사점 | `core/legacy/ReplayCheckpoints` | 체크포인트가 없는 로그에만 씁니다. 기초 Rig 인스턴스와 로그 접두 내용으로 재생 중간 모델을 캐시합니다. 추가는 새 항목만 재생하고, 실행 취소는 이미 있는 검사점에 맞습니다 |
| 생성기 재사용 | `core/DocumentGenerators`(`GeneratorReuse`) | 스윙과 시뮬레이션은 객체 단위 읽기를 선언합니다. 읽기가 그대로이면 지난 출력을 패치로 씌우고, 다시 생성하지 않습니다 |
| 분할 실체화 | `core/ArtPrimitiveJournal`, `core/RigRegenerationCheckpoint`(`split`), `application/WorkspaceArtPrimitives` | 분할은 한 번의 재생성입니다. 파츠가 원 레이어를 대신해 생성에 참여하고, 원 레이어에 한 사용자 수정은 삼자 병합으로 파츠에 실리며, `art_primitive` 기록 뒤에 체크포인트를 씁니다. [분할 실체화](#분할-실체화-아트-프리미티브-기록-art_primitive)를 참조합니다 |
| 저작 상태 Rig와 체크포인트 | `core/RigEditOverlay`(`replayAuthored`/`finish`), `core/RigCheckpoint`, `core/RigRegeneration`, `project/MaterializedRigStore` | 재생은 저작 상태 단계와 마무리 단계로 나뉩니다. 저작 상태 Rig는 리비전별로 저장하고 구축에 바로 씁니다. 생성 결과가 로그 아래에서 바뀌면 삼자 병합하고 체크포인트를 씁니다. [체크포인트](#체크포인트)와 고정 Rig를 참조합니다 |
| 프로젝트 형식 v2 | `project/ProjectFormatV2` | 각 리비전을 내용 주소와 schema 버전이 있는 문서 노드로 나눕니다. v1은 연 뒤 다음 저장 때 이전합니다. [프로젝트 형식](PROJECT_FORMAT.md)을 참조합니다 |

`format-compile`의 프레임워크 네 부분은 MIT이며, GPL 모듈에 의존하지 않습니다.

## 프리셋 설정 초안

프리셋 컨트롤은 설정 패치만 투영합니다. 현재 미리보기의 `RigEditOverlay`나 메시 기준선을 설정 편집으로 제출하지 않습니다. `WorkspaceSettingsIntent.patchSettings`는 바로 표시되는 연동 규칙을 제공합니다. `WorkspaceGenerationCommands.prepareSettingsDraft`는 캡처한 제출된 문서에 같은 의도를 적용하고, 저작 포즈를 해제하고, 재구축한 뒤 생성 결과를 병합합니다. 미리보기와 제출은 같은 순수 후보를 쓰고, 미리보기가 만든 검사점은 임시 모델에만 있습니다.

슬라이더, 숫자 입력, 색 팝업은 편집 세션으로 조작을 나눕니다. `WorkspaceSettingsDraft`는 연속 수치 샘플을 최종 패치로 합치고, 포즈를 해제하는 스위치 전환 순서는 남깁니다. 세션이 끝나면 `WorkspaceDraftQueue`와 런타임 CAS로 히스토리 노드 하나를 발행합니다. 변화가 없으면 추가하지 않습니다. 시뮬레이션과 물리 편집은 각자 애플리케이션 층 명령을 계속 씁니다. 저장은 먼저 컨트롤 세션을 끝내고 초안 제출을 기다립니다. 이전 편집 기록과 히스토리 스냅샷은 원래대로 둡니다.

## 생성기 의존 그래프

`DocumentGenerators.graph`는 프로젝트마다 다음 노드를 만듭니다(객체 ID: `document:<部分>`는 문서 상태, `rig:<阶段>`는 전체 Rig 단계, `parameter:<ID>`는 생성된 파라미터, `keyform:<warp|mesh>:<目标>@<参数>`는 생성기가 그 파라미터를 따라 대상에 추가하는 키폼).

| 노드 | 읽기 | 소유 |
| --- | --- | --- |
| `rig.footprints`(메시 윤곽) | 원본 그림, 설정, 레이어별 메시 설정 | `rig:footprints` |
| `rig.scaffold`(앵커, 얼굴, 프레임, 디포머) | `rig:footprints`, 레이어 분류, 설정, 스켈레톤 정의 | `rig:scaffold` |
| `mesh:<图层>`(레이어별 메시와 키폼. 레이어 목록을 주지 않으면 `rig.meshes`로 합침) | `rig:scaffold`, 그 레이어 픽셀, 분류와 메시 설정 | `rig:mesh:<图层>` |
| `rig`(조립과 텍스처 아틀라스 바인딩) | 각 레이어 메시, `rig:scaffold`, 원본 그림, 설정, 레이어 분류 | `rig:base` |
| `skeleton`(스켈레톤 베이크) | `rig:base`, 스켈레톤 정의 | `rig:skeleton` |
| `journal`(편집 재생) | `rig:skeleton`, 편집 로그 | `rig:authored` |
| `skeleton.skin`(로그가 배치한 메시의 본 스키닝. 로그가 본에 바인딩된 메시를 자기 디포머 아래에 걸 때만 있음) | `rig:authored`, 스켈레톤 정의 | 이 메시들이 사지 본, 위쪽 몸 반쪽, 스켈레톤 포즈 파라미터에서 가지는 키폼 |
| `swing:<ID>`(베이크하지 않은 스윙 각각) | `rig:authored`, 그 스윙의 설정 | 그 파라미터, 그리고 그 파라미터가 각 대상 Warp에 만드는 키폼 |
| `simulation:<ID>`(베이크했고 켜진 시뮬레이션 각각) | `rig:authored`, 그 시뮬레이션의 설정과 베이크 | 그 모드 파라미터, 그리고 모드 파라미터가 베이크 메시에 만드는 키폼 |
| `overrides`(덮어쓰기 병합) | 생성된 모든 키폼, 덮어쓰기, 생성기 집합 | `rig:final` |
| `seeThrough`(앞머리를 투과하는 복제본) | `rig:final`, 설정 | `rig:seeThrough` |
| `physics`(물리 그룹) | `rig:final`, `rig:seeThrough`, 생성된 파라미터, 물리와 스켈레톤 설정 | `physics` |
| `motions`(생성 모션) | `rig:final`, `rig:seeThrough`, `physics`, 모션 설정, 스켈레톤 정의 | `motions` |

- 재생(`RigEditOverlay.applyTo`)은 그래프의 위상 순서로 로그 이후 노드를 돌립니다. 먼저 `skeleton.skin`, 그다음 스윙과 시뮬레이션이며, 이전의 “스윙을 모두 돌린 뒤 시뮬레이션을 모두 돌리는” 순서와 같습니다. 선언 순서가 동점을 가릅니다.
- 앞머리를 투과하는 복제본(`SeeThroughLayers`, [디포머와 파라미터 참고](DEFORMER_AND_PARAMETER_SPEC.md#자동-변형)): `rig` 노드는 후보만 기록합니다(앞머리에 가려진 눈썹과 각 눈 레이어, 그리고 그 앞머리). `seeThrough` 노드는 덮어쓰기 병합, 레이어 표시와 그리기 순서 덮어쓰기 뒤(`AuthoredRig.finished` 끝, `withSeeThrough`)에 설정에 따라 원본에서 복제본을 만들고, 눈을 위해 앞머리에 창을 엽니다(앞머리 역 클리핑, `BuiltRig.seeThroughWindows`). 마스크, 그리기 순서, 불투명도는 그때의 원본과 앞머리에서 나옵니다. 창이 바꾼 앞머리 마스크는 완성 Rig에만 있고, 저작 상태와 로그의 앞머리에는 없습니다. 인스펙터는 `authoredMasksOf`로 문서 자신의 마스크를 표시하고 편집합니다. 구버전 소프트 삭제가 창이 열린 눈 레이어를 모두 지우면 창을 거둡니다(`withSeeThroughWindowsPruned`). 복제본은 저작 상태 Rig에 없고, `keyform:` 객체를 하나도 소유하지 않습니다. 참조 필드(분할의 참조 필드와 `id`, `masked_by` 등)에서 그것을 지목하는 문서 조작은(`WorkspaceDocumentEdits` 분기와 로그 기록) `WorkspaceGeneratedCopyEdit`(`generated_copy`)로 거부합니다. 설정 세 항목은 재생만 일으키며, 생성 설정으로 치지 않습니다. 복제본에는 자기 레이어 항목이 없고, 레이어 기준으로 메시를 다루는 곳은 `BuiltRig.layerOf`로 원본의 레이어를 가져옵니다(구버전 소프트 삭제는 원본과 함께 복제본을 지우고, 아틀라스를 압축하고 다시 바인딩합니다). 생성 이전이 Rig 데이터로 읽는 구축은 복제본을 만들지 않습니다(`SeeThroughLayers.withoutCopies`). 제출하지 않은 미리보기(캔버스 도구가 `CanvasEditor.preview`로 대입하는 값, 인스펙터 실시간 필드, Warp 제어 장)는 `SeeThroughLayers.refresh`로 미리보기의 원본과 앞머리에 맞춰 이어 받은 복제본을 다시 만듭니다. 마스크, 순서, 겉모습은 제출 때와 같습니다. 전체 재구축의 미리보기(스윙, 내부 조형 시험 재생)는 복제본이 이미 새 인스턴스이므로 같은 모델을 그대로 반환하고, 참조로 미리보기를 알아보는 곳은 영향을 받지 않습니다.
- 문서가 생성기 두 개에 같은 파라미터를 선언하게 하면, 먼저 선언한 쪽이 소유권을 유지하고 나중 선언은 버려집니다. 재구축은 계속되고, 충돌은 생성기 자신이 보고합니다.
- `DocumentGenerators.stale(before, after)`는 문서가 한 번 바뀐 뒤 다시 돌려야 하는 생성기를 줍니다. 바뀐 부분을 읽은 생성기와 그 하류 전부입니다. 수정되거나 삭제된 생성기가 원래 소유하던 객체도 변화로 봅니다. 예를 들어 스윙 하나를 조정하면 그 스윙, 덮어쓰기 병합, 물리, 모션만 다시 돌리고, Rig 생성, 스켈레톤, 다른 시뮬레이션은 다시 돌리지 않습니다.
- Rig 생성은 단계별로 노드에 등록합니다(아래 [Rig 생성 단계](#rig-생성-단계)). `graph(overlay, layers)`에 레이어 목록을 주면 레이어마다 `mesh:<图层>` 노드가 하나이고, 어떤 레이어의 픽셀이 바뀌면 그 레이어 메시, 조립, 그 하류만 만료됩니다.

## 증분 재생

`RigEditOverlay.applyTo`는 순서대로 저작 상태(체크포인트가 있으면 마지막 체크포인트에서 시작해 그 뒤 항목만 재생합니다. [체크포인트](#체크포인트) 참조. 체크포인트가 없으면 구형식 정적 편집—파라미터 삭제/생성, 정적 Warp, 구조, 키폼 set/copy/delete—과 `authoringJournal`의 모든 항목을 실행), 스윙과 시뮬레이션, 덮어쓰기 병합, 미룬 패널 편집을 실행합니다. 생성된 문서는 첫 편집 뒤에 체크포인트가 생기고, 그 뒤로는 최대 `CHECKPOINT_INTERVAL`개만 재생합니다. 아래 재생 검사점은 체크포인트가 없는 로그(이전 버전이 썼고 아직 편집하지 않은 리비전)만 담당합니다. 스윙과 시뮬레이션은 `GeneratorReuse`가 읽기 집합으로 재사용합니다.

**재생 검사점**(`core.legacy.ReplayCheckpoints`, 체크포인트가 없는 로그에만 사용)

- 검사점은 “구형식 정적 편집 + 앞 `i`개 로그” 이후의 모델입니다. 찾는 조건: 기초 모델이 같은 인스턴스입니다. 구형식 부분이 같습니다(스윙/시뮬레이션 파라미터 집합을 포함. 이것이 구조 편집 중 무엇을 미룰지와 인터페이스 언어를 결정). 앞 `i`개는 각각 검사점이 재생한 항목과 같습니다(먼저 참조를 비교하고, 다르면 내용을 비교).
- 무효는 접두 내용만 보고, 인덱스는 보지 않습니다. 이른 항목을 다시 쓰는 명령(드래그 병합, 생성 결과 덮어쓰기 캡처, 메시 정규화)은 그 항목과 그 뒤 검사점이 자연히 어긋나게 하고, 가장 가까운 유효 검사점에서 재생합니다.
- 각 체인은 인덱스 0, 16개마다, 마지막 3개의 상태를 남기며, 모두 소프트 참조입니다(메모리가 빠듯하면 해제). 체인은 최대 4개입니다(최근 사용 우선). 분기하면 이전 체인을 남겨, 다시 실행하거나 되돌아갈 때 씁니다.
- 항목을 하나 추가하면 그 항목만 재생합니다. 이전 상태로 실행 취소하면 바로 맞고, 재생하지 않습니다. 완전한 재구축(다시 열기, 타일 크기를 바꾸는 페인팅과 그림 교체)은 새 기초 Rig 인스턴스를 만들고 처음부터 재생합니다. 타일 크기와 위치를 하나도 바꾸지 않는 페인팅이나 그림 교체는 같은 기초 Rig 인스턴스를 이어 씁니다(아래 “텍스처 아틀라스와 페인팅”). 검사점은 그대로 맞습니다.
- 스켈레톤은 기초 Rig 안에서 베이크합니다(로그 이전). 로그 뒤에는 캔버스 스키닝 쓰기만 있습니다. 스켈레톤 편집은 기초 Rig의 내용을 바꾸므로, 그 이전의 모든 검사점은 더 이상 성립하지 않고 처음부터 재생합니다. “영향을 받은 첫 항목 앞에서 이어 재생”은 스켈레톤에 적용되지 않습니다. 내용으로 기초 Rig를 맞추지는 않습니다. 2배 tml(4096²)에서 기초 Rig 전체의 IR 내용 해시는 약 160 ms이고, 로그 26개의 전체 재생은 약 6 ms입니다. 내용이 같은 재구축은 단계 캐시가 같은 인스턴스를 돌려줍니다(“Rig 생성 단계” 참조). 인스턴스 일치로 이미 덮입니다.
- `PuppetModel`과 그 객체는 불변 값으로 공유합니다. `-Dpsd2live.replayCheckpoints=false`는 검사점과 생성기 재사용을 함께 끕니다. 코드에서는 둘을 따로 끕니다(`ReplayCheckpoints.enabled`, `GeneratorReuse.enabled`).

**생성기 재사용**

- 스윙이 읽는 것: 각 대상 Warp와 그 모든 조상(측정이 있는 부모 공간), 파라미터 목록과 파라미터 트리, 월드 원점(자동 받침점). 쓰는 것: 자기 파라미터, 파라미터 트리, 대상 Warp.
- 베이크한 시뮬레이션이 읽는 것: 대상 메시와 베이크 메시(지오메트리, 블렌드 셰이프, 채널), 파라미터 목록과 파라미터 트리, 런타임 대상(블렌드 셰이프를 쓸지 결정). 쓰는 것: 자기 파라미터, 파라미터 트리, 이 메시들.
- 생성기가 돈 뒤, 출력은 패치로 기록합니다. 새 파라미터 목록과 파라미터 트리, 그리고 교체된 객체입니다. 기록 전에 검사합니다. 읽기 집합 안의 객체만 바꿨고 나머지 필드 참조는 그대로여야 합니다. 그렇지 않으면 캐시하지 않습니다.
- 설정이 같고 읽기 집합이 항목마다 같으면(먼저 참조를 비교하고, 다르면 내용을 비교) 패치를 현재 입력에 바로 씌우고, 읽기 집합 밖의 객체는 현재 값을 유지합니다. 참조 비교는 비용이 거의 없습니다. 내용 해시로 읽기 집합을 비교하면 생성기 자체보다 비쌉니다(아래 표).
- 내용 비교는 놓칠 수 있고(배열 필드는 참조로 비교), 잘못 맞추지는 않습니다. 놓치면 다시 생성할 뿐입니다.
- `DocumentGenerators.stale`은 여전히 문서 단위의 다시 돌릴 범위를 줍니다. 재생할 때는 더 촘촘한 객체 단위 읽기 비교를 기준으로 합니다. 예를 들어 관계없는 메시를 편집하면 스윙과 시뮬레이션이 모두 재사용되고, 스윙 대상 Warp나 그 조상을 편집하면 그 스윙만 다시 돕니다.

**효과**(`CommitPerfTool.baseline`, 같은 기계에서 전후 비교. “끔”은 검사점과 생성기 재사용을 끈 것이고, “추가”는 마지막 항목을 뺀 로그를 먼저 재생한 뒤 전체 로그를 재생한 것입니다):

| 장면 | 이전 재생 | 끔 | 하나 추가 | 같은 문서를 다시 재생 |
| --- | ---: | ---: | ---: | ---: |
| 장면 a(스켈레톤 + 스윙 둘 + 베이크 시뮬레이션) | 약 3.7 ms | 약 4.3 ms | 약 1.0 ms | 약 0.6 ms |
| 로그 64개 | 약 16 ms | 약 20 ms | 약 0.7 ms | 약 0.1 ms |
| 로그 214개 | 약 43 ms | 약 45 ms | 약 0.4 ms | 약 0.1 ms |

기하 편집 200개를 추가한 뒤, 제출 한 번은 약 98 ms에서 약 46 ms로 줄고, 제출 안의 재구축은 약 79 ms에서 약 23 ms로 줄었습니다. 남은 것은 주로 moc3 묶기와 기하 안전 검사이며, 더 이상 로그 길이에 따라 늘지 않습니다.

## 체크포인트

로그 재생의 전제는, 항목을 쓸 때 마주한 생성 결과가 변하지 않는 것입니다. 생성 입력을 바꾸는 편집(머리카락 시뮬레이션 스위치, 스켈레톤, 생성 설정과 분류, 분할 등)으로 기초 Rig가 바뀌면, 이전 항목은 새 결과 위에서 재생하지 않고, 병합한 뒤 데이터로 저장합니다.

- **트리거**(`WorkspacePreviewBuilder.build`, `RigRegenerationCheckpoint.checkpointed`): 새 문서가 현재 문서를 잇습니다(`RigEditOverlay.continues`: 로그가 현재 로그로 시작. 공통 시작에 체크포인트가 없으면 구형식 정적 필드도 같아야 하고, 체크포인트가 있으면 더 이상 읽지 않음). 그리고 추가 경로로 갈 수 없습니다. 새 문서의 기초 Rig를 생성하고, 이전 항목이 본 부분(`BuiltRig.resolvedPuppet(records)`: 경계 이전 v2 분할 기록의 파츠는 제자리에 두고, 그 뒤 기록의 승객은 남김)과 현재 기초 Rig의 `resolvedPuppet()`을 중립 IR로 비교합니다. 다르면 현재 기초를 G, 새 기초를 G′, 현재 저작 상태 Rig를 M으로 병합합니다(`RigRegeneration.merge`. G와 M은 먼저 새 텍스처 아틀라스에 다시 바인딩). 현재 로그 끝, 이번 편집의 새 항목 앞에 `rig_checkpoint`를 넣습니다. 같으면 그대로 재생합니다.
- **부모 덮어쓰기와 그리기 순서 덮어쓰기**: 둘 다 기초 생성의 입력입니다. 생성된 모델에서 이것들을 바꾸면 마찬가지로 재생성 병합을 하고 체크포인트를 씁니다(체크포인트만으로 구축할 때는 기초 Rig를 생성하지 않으므로, 병합하지 않으면 이것들이 보이지 않습니다).
- **생성 설정과 분류**(`RigGenerationChange.changed`가 인정하는 변화: 얼굴 특징, 입 모양, 메시만, 머리·몸 강도, `rigTuning`, 레이어 분류): 생성된 모델은 편집을 준비할 때 바로 병합하고 체크포인트를 씁니다(`WorkspacePreviewBuilder.normalizeMeshEdits`). G′는 현재 원본 그림에서 생성합니다(저장한 메시 입력은 그대로 쓰고, `generationSource`가 얼린 뒤에 넣은 레이어도 그 안에 있습니다). `rig_generation_transition`, `rig_generation_frames`, 이전과 함께 만든 메시 기록은 더 이상 쓰지 않습니다. 병합은 현재 로그 끝의 저작 상태 Rig에서 출발하므로, 같은 편집은 그 뒤에만 항목을 추가할 수 있습니다. 이른 항목을 동시에 다시 쓰는 편집은 거부됩니다(“나눠 제출”). 이전 항목을 새 생성 결과 위에 조용히 재생하지 않습니다. CMO3를 가져온 모델에는 병합할 생성 결과가 없어, 여전히 이전 기록을 씁니다([구버전 재생](#구버전-재생) 참조).
- **분할**(`RigRegenerationCheckpoint.split`): [분할 실체화](#분할-실체화-아트-프리미티브-기록-art_primitive)를 참조합니다. 체크포인트는 분할 기록 뒤에 쓰며, 기록 자체는 재생하지 않습니다.
- **기록**(`RigCheckpoint`): 저작 상태 Rig의 인덱스(객체는 `RigObjects`에 있고 문서와 함께 유지), 그것이 기반한 생성 스냅샷, 병합 문제입니다. 모델 프리셋이 머리카락 시뮬레이션을 켤 때는 프리셋 안에서도 마찬가지로 병합하고 체크포인트를 쓴 뒤, 병합된 Rig로 가중치를 계산합니다.
- **직접 편집**: 생성된 모델에서, 로그를 잇고 항목을 추가하는 편집은 로그에 체크포인트가 없거나 마지막 체크포인트 뒤에 이미 `RigEditOverlay.CHECKPOINT_INTERVAL`(32)개가 있으면, 먼저 원래 로그 끝, 새 항목 앞에 현재 저작 상태 Rig의 체크포인트를 씁니다(`RigEditOverlay.checkpointsBeforeEntries`, `WorkspacePreviewBuilder`). 생성 스냅샷은 이전 체크포인트가 저장한 것을 이어 쓰고, 없으면 현재 기초 Rig를 씁니다. 그래서 첫 편집 뒤의 어떤 구축도 최대 32개에 이번 편집 항목을 더한 만큼만 재생합니다. 추가한 항목은 현재 저작 상태 Rig에 작용하고, 이른 항목을 다시 쓰는 편집(드래그 병합, 실행 취소, 다시 실행)은 체크포인트에서 그 뒤 항목을 재생하거나 저장한 리비전을 가져옵니다(`PSD2LivePipeline.updateRigEdits`, `RigPreviewModel.authoredWithoutBase`). 둘 다 기초 Rig를 생성하지 않습니다. tml 예제에서 첫 편집은 약 0.2 s, 이후 고정은 약 50 ms, 콜드 구축은 약 0.2 s입니다. CMO3를 가져온 모델도 이 두 가지 체크포인트를 씁니다(생성 스냅샷 없음, 바인딩 키는 `cmo3-import`). 가져오기 기준선에서 체크포인트부터 재생합니다.
- **재생**: `replayAuthored`는 마지막 체크포인트에서 시작합니다. 그 Rig는 `reboundTo`로 기초 Rig의 텍스처 아틀라스에 바인딩한 뒤, 이후 항목을 하나씩 재생합니다(재생 검사점을 거치지 않습니다. 재생 검사점 `core.legacy.ReplayCheckpoints`는 체크포인트가 없는 로그만 담당). `authoredRig`의 메시 매핑은 체크포인트 헤더에서 가져옵니다. 그 뒤에 `art_primitive` 기록이 없으면, 구축은 체크포인트에서 바로 합니다(`RigEditOverlay.authoredFromCheckpoint`, `materializedPreview(rebind = true)`). 기초 Rig를 생성하지 않습니다.
- **생성 기준선**: `rig_generation_baseline`이 얼린 생성 설정과 분류는, 그 뒤에 체크포인트가 없을 때만 기초 생성을 구속합니다(`RigGenerationBaseline.restore`). 이후 항목은 모두 체크포인트에서 재생을 시작하고, 기초 생성은 문서의 현재 설정으로 합니다.
- **제출**: 런타임은 재구축이 넣은 체크포인트를 제출 문서에 넣습니다(`WorkspaceRuntime.adopted`). 배치 멤버는 이전 후보로 구축하고(`rebuildFrom`), 병합의 M은 이전 후보의 저작 상태입니다.
- **마무리 단계**는 로그 전체를 그대로 훑습니다. 생성 결과 덮어쓰기와 미룬 패널 편집은 체크포인트의 영향을 받지 않습니다.
- **보고**: 마지막 체크포인트의 문제는 `RegenerationQuality`를 거쳐 `workspace_inspect`의 `quality.regeneration`에 들어갑니다. 제출 전에 `workspace_preview_regeneration`으로 시험 실행할 수 있습니다. 제출과 같이 후보를 준비하고 재구축하며, 쓸 체크포인트(`regeneration`은 병합 문제, `materialized`는 새 항목 앞의 저작 상태)와 추가·삭제된 객체를 보고하고, 아무것도 발행하지 않습니다(`WorkspaceDocumentCommands.previewRegeneration`).
- **시뮬레이션 베이크**는 저작 상태 Rig가 마무리 단계를 거친 결과를 읽습니다(`SimAuthoring.AuthoredRigs`, `RigPreviewModel.authoredPuppet`). 기초 Rig를 생성하지 않습니다.
- 생성된 모델은 스켈레톤을 켠 뒤 로그에서 정점 그룹을 다시 샘플링하지 않습니다(병합이 그것들을 이전합니다). CMO3를 가져온 모델에는 병합할 생성 결과가 없어, 원래 방식으로 처리합니다.

## 생성 결과 덮어쓰기

- 키폼의 소유자는 그래프가 결정합니다. 편집한 키에서 어떤 파라미터가 기본값을 떠나고, 그래프에 생성기가 `keyform:<类型>:<目标>@<该参数>`를 소유하면, 그 칸은 생성된 칸입니다.
- **스윙**: 그 파라미터 축이 대상 Warp에 추가한 키폼을 소유합니다. 덮어쓰기는 생성기, 대상 `warp:<ID>`, 전체 키, 그때 생성된 칸(`base`)과 사용자 칸(`points`)을 기록하고, 제어점마다 병합합니다.
- **베이크 시뮬레이션**: 모드 파라미터가 베이크 메시에 만드는 키폼을 소유합니다(키폼 축으로 쓰는 시뮬레이션. 블렌드 셰이프로 쓸 때는 메시 칸에 그 축이 없어, 편집이 덮어쓰기로 인식되지 않습니다). 덮어쓰기는 대상 `mesh:<ID>`, 그때 생성된 정점 오프셋(`base`), 사용자가 편집한 뒤의 오프셋(`points`, 현재 모델에 그 캔버스 편집을 씌워 얻음)을 기록하고, 정점마다 병합합니다. 다시 베이크하거나 게인을 바꾼 뒤, 사용자가 움직이지 않은 정점은 새 베이크를 따르고, 사용자는 움직였으나 베이크가 바꾸지 않은 정점은 남으며, 양쪽이 모두 바꾼 정점은 사용자 값을 남기고 충돌을 보고합니다.
- **채널**: 생성기가 자기 축에 키로 넣은 투명도, 그리기 순서, 곱색, 스크린색 키폼도 그것의 소유입니다. 어떤 채널의 트랙이 로그 뒤에야 생성기 축을 가지고(저작 상태 Rig의 같은 트랙에는 이 축이 없음), 편집한 키에서 그 파라미터가 기본값을 떠나면, 그 칸은 생성된 것입니다. 키폼 `set`이 그것을 쓸 때, 그런 채널마다 `channel`(`opacity` / `draw_order` / `multiply_color` / `screen_color`)이 있는 덮어쓰기 한 줄을 씁니다. `base`는 그때 생성된 값, `points`는 사용자 값입니다(스칼라는 숫자 하나, 색은 성분 셋). 재생할 때 성분마다 삼자 병합하고, 충돌과 고립은 그대로 보고합니다(`GeneratedOverrideIssue.channel`, 품질 보고서의 `evidence.channel`). 같은 `set`에서 생성기가 키를 넣지 않은 채널, 로그가 그 축에 스스로 만든 트랙은 여전히 일반 로그 편집입니다. 생성된 채널 칸으로 복사하거나 거기서 복사하기, 생성기가 채널에 둔 키를 지우기는 기록할 때 거부합니다. 저작 상태 Rig가 없는 호출(`ownedWrites`에 `authored`를 넘기지 않음)은 채널 덮어쓰기를 인식하지 않으며, 동작은 이전과 같습니다. 지금은 로그 뒤에 채널에 키를 넣는 생성기가 없습니다. 이 경로는 정적 주광, 투과 표시처럼 색 / 투명도 키폼을 쓸 생성기를 위해 준비합니다.
- 이전에 이 키폼 위의 캔버스 편집은 일반 `canvas_geometry`로 썼고, 재생할 때 파라미터가 아직 없어 재구축 전체가 실패해 편집을 제출할 수 없었습니다. 이제는 제출할 때 덮어쓰기로 다시 씁니다.
- 생성기가 삭제되거나, 베이크되거나(스윙), 베이크가 취소되거나(시뮬레이션), 축이 바뀌면, 키는 더 이상 생성된 칸에 대응하지 않습니다. 덮어쓰기는 적용되지 않고 고립으로 보고되며, 그 아래 정지 형태에 떨어지지 않습니다. 메시를 다시 생성해 정점 수가 바뀌어도 고립으로 보고합니다.
- 생성 파라미터가 기본값인 곳의 편집은 여전히 일반 편집이며, 정지 형태를 수정합니다. 이전 프로젝트의 명령은 변하지 않습니다. 새 제출만 덮어쓰기를 씁니다.
- Bezier 편집과 키폼 `set`(MCP `rig_deform` 포함)이 생성된 칸에 쓸 때도 덮어쓰기로 바꿉니다. 자식 위치를 남기는 편집, 생성된 칸으로 복사하거나 거기서 복사하기, 생성기 축에서 키를 더하거나 지우는 일은 덮어쓰기로 표현할 수 없어 기록할 때 거부합니다(`GeneratedOverrides.ownedWrites`).
- 다른 객체에서 생성 파라미터를 쓸 때(키를 찍기, 채널 키폼, 이름 변경, 범위 변경)는 먼저 로그에 생성기의 현재 정의로 그 파라미터를 만듭니다(`GeneratedParameterAdoption`). 그 뒤 파라미터는 문서에 속하고, 생성기는 그것을 이어 씁니다. 고정 Rig를 참조합니다.
- 덮어쓰기는 기초 Rig 생성에 영향을 주지 않습니다. 생성 기하 캐시의 키는 덮어쓰기 명령을 무시하므로, 덮어쓰기를 더하거나 빼도 기초 Rig가 다시 생성되지 않습니다.
- **문제 보고**: 재생할 때마다 기록대로 적용되지 않은 덮어쓰기를 구조화 기록으로 남깁니다(`GeneratedOverrideIssue`: 유형 `conflict` / `orphaned`, 생성기 ID, 대상, 전체 키, 충돌 점 수 또는 고립 덮어쓰기의 점 수, 형태 전체 점 수. 고립일 때는 이유 `missing_keyform` / `shape_mismatch` / `superseded`). `BuiltRig.overrideIssues`에 로그 순서로 넣고, 병합 의미는 바꾸지 않습니다. 분할로 대체된 메시 위의 덮어쓰기 이유는 `superseded`입니다.
- `core/quality/GeneratedOverrideQuality`는 이 기록을 관찰 보고서로 바꿉니다(버전 4, 영역 `overrides`, 검사 세 가지: `generated_overrides`. `superseded_entries`는 버전 2 분할 이전, 자기가 대체한 메시 때문에만 실패해 무조작으로 재생된 항목이며 등급은 info. `see_through`는 설정이 요구하는데 만들지 못한 앞머리 투과 복제본이며 `SEE_THROUGH_DROPPED`, 등급 info). 충돌은 `GENERATED_OVERRIDE_CONFLICT`, 고립은 `GENERATED_OVERRIDE_ORPHANED`입니다. 등급은 규칙 열거만 결정합니다(모두 warning, `can_proceed`는 항상 true). 텍스트에서 추론하지 않습니다. 문제가 없으면 보고서는 완전하고 findings는 비어 있습니다. MCP `workspace_inspect`(scope `project`, 프로젝트를 불러온 때)는 `quality.overrides`를 반환합니다. 엄격한 구조는 `WorkspaceQualitySchemas`를 참조합니다.
- 인스펙터 도구 막대는 문제가 있으면 개수 배지를 표시하고, 선택한 객체의 문제는 인스펙터 위에 나열합니다. 배지를 누르면 모든 문제를 나열하는 표시로 바뀝니다. 문구는 유형과 이유 코드로 현지화합니다(중/영/일).

스켈레톤 베이크의 보정 키폼은 덮어쓰기로 바꾸지 않았습니다(`skeleton.skin`이 로그가 배치한 메시 위에 쓰는 키폼은 예외. [로그가 배치한 메시](#로그가-배치한-메시) 참조). 스켈레톤은 편집 로그보다 먼저 돌고, 로그의 캔버스 편집은 원래 스켈레톤 뒤에 재생되며, 메시 재구축과 함께 새 토폴로지로 이전됩니다. 덮어쓰기로 바꾸면 메시를 다시 나눈 뒤 오히려 고립됩니다. 물리 그룹과 생성 모션은 이미 있는 전체 덮어쓰기를 이어 씁니다(같은 ID의 사용자 물리 그룹이 생성 그룹을 대체하고, `builtin` 모션 클립이 생성 모션을 대체).

## 측정과 생성 캐시

`GeneratorCostTool`(`PSD2LIVE_TOOLS=1`)은 tml에서 각 생성기와 그 입력의 내용 해시 시간을 재고, `build/tools/generator-cost/report.txt`를 출력합니다.

| 항목 | 생성 | 입력 해시 | 결론 |
| --- | --- | --- | --- |
| 스켈레톤 베이크(자동 스켈레톤) | 약 4.7 s | 약 5 ms(기초 Rig의 IR + 스켈레톤 정의) | 캐시에 넣으며, 맞으면 Rig 생성은 약 20 ms |
| 생성 모션(모든 프리셋, 스켈레톤 프리셋 포함) | 약 16 ms | < 1 ms | 캐시에 넣으며, 맞으면 약 1 ms. Rig IR 컴파일은 약 16 ms에서 약 2 ms로 감소 |
| 스윙(둘) | 2.8 ms | 8.4 ms | 내용 해시 캐시는 하지 않습니다. 객체 단위 읽기 집합의 참조를 비교한 뒤 출력 패치를 재사용합니다([증분 재생](#증분-재생) 참조) |
| 베이크 시뮬레이션 쓰기 | 약 0.8 ms | 약 8.6 ms(베이크 JSON) | 위와 같음 |
| 물리 그룹 목록 | 약 0.1 ms | 약 0.1 ms | 캐시하지 않음 |
| 시뮬레이션 베이크 자체 | 약 13 s | — | 명시적 조작입니다. 결과는 이미 문서에 저장되며, 다시 계산하지 않습니다 |

- 스켈레톤 캐시 키에는 베이크가 실제로 읽는 내용만 들어갑니다. 본에 바인딩된 메시(전체. UV는 바인딩하지 않은 레이어 오프셋). 본을 걸고, 굽힘 Warp와 바인딩 메시에 쓰는 디포머(몸, 호흡, 기울기, 다리 Warp, 머리 회전, 본 자신의 ID, 바인딩 메시의 부모)와 그 모든 조상. 파라미터, 파츠, Glue, 파라미터 트리. 나머지 디포머와 Drawable은 ID, 종류, 순서, 부모만 가져옵니다. 또 스켈레톤 정의, 몸 상자, 바인딩 메시 안의 손 토폴로지, 선 자세, 인터페이스 언어가 들어갑니다(생성된 디포머와 파라미터 이름은 이미 현지화됨). 텍스처 아틀라스, 원본 파일, 변형 경로는 읽지도 쓰지도 않으므로 키에 넣지 않습니다. 맞았지만 기초 Rig가 다르면, 읽지 않은 디포머와 Drawable(베이크 때의 부모 변경 기준), 텍스처 아틀라스, 원본 파일, 경로는 새 기초 Rig에서 가져오고, 그리기 순서를 다시 도출합니다. 베이크가 다른 방식으로 읽지 않은 객체를 바꿨다면, 그 결과는 IR 전체가 같은 기초 Rig에서만 맞습니다. 캐시는 최근 4개 결과를 남깁니다. 실행 취소, 히스토리 전환, 내보내기 전후의 같은 Rig 재생성, 본에 바인딩되지 않은 메시의 토폴로지 편집이나 메시 설정(몸 상자를 바꾸지 않을 때)은 맞습니다. 스켈레톤이 있는 전체 미리보기 재구축은 약 5.4 s에서 약 0.5 s로 줄었습니다.
- 내용 해시가 안정되도록, Rig가 생성하는 눈과 입술 변형 경로의 ID는 메시 ID와 경로 역할에서 파생하는 결정적 ID로 바꿨습니다. 이전에는 생성할 때마다 무작위 UUID였습니다.
- 요청이 ID를 주지 않은 새 객체(캔버스와 MCP가 만든 Warp, 회전 디포머, Glue, 변형 경로, 분할 조각, 깊이 분할의 레이어와 메시, 가져오거나 추가한 레이어)는 `StableIds`가 요청 내용(`state`, `request_id` 같은 전송 정보를 뺀 것)에서 ID를 파생합니다. 같은 문서의 같은 요청은 재시도, 시험 실행, 제출이 같은 ID를 얻고, 이미 쓰면 차례로 `_2`, `_3`를 붙입니다. 배치에서 참조해야 하는 객체는 여전히 요청에 ID를 줘야 합니다. 로그와 문서에 이미 있는 ID는 그대로 둡니다. 세션, 작업, 히스토리 노드, 파라미터 스냅샷, 소재 작업 흐름 기록처럼 Rig나 문서 객체가 아닌 ID는 이 제약을 받지 않습니다.
- 생성 모션의 캐시 키에는 프리셋 이름, 스켈레톤 정의, 조정 값, 제외한 파라미터가 들어갑니다.
- 기초 Rig 자체는 이미 있는 `GeneratedGeometryCache`(생성 입력을 저장한 프로젝트)와 빠른 재생 경로가 처리합니다. 전자는 최근 4개 결과를 남깁니다(최신 하나만 강한 참조이고 나머지는 소프트 참조이며, 메모리가 빠듯하면 해제). 실행 취소와 히스토리 전환이 최근 입력으로 돌아오면 재사용합니다.
- `canvas_geometry` 로그 항목은 버전 2부터 실행 위치 기하 대비 희소 양자화 증분을 저장합니다(`v`, `n`, `q`, 선택적 정점 인덱스 `i`, 정수 증분 `d`). 생산 쪽은 여전히 절대 점을 제출하고, `RigAuthoringJournal.compile`이 인코딩하며, 미리보기와 제출이 적용하는 것은 디코딩된 명령입니다. 버전 1의 절대 점은 그대로 재생합니다.
- 편집기 미리보기의 moc3 묶음은 다시 읽어 검증하지 않습니다(`validateBundle`). 사용자에게 쓰는 내보내기는 여전히 검증합니다. 테스트 JVM(어서션 사용)이나 `psd2live.validatePreviewBundles=true`이면 미리보기도 검증합니다.
- moc3 묶음에서 physics3/motion3의 생성과 정규화(지수 전개의 정규식 치환)는 이전 약 18–21 ms로 묶음 전체의 거의 절반이었습니다. `Moc3Target`은 입력(물리 그룹, 모션, 파라미터 집합, 파일 이름 접두)으로 최근 4개 텍스트를 캐시하며, 기하 편집은 이 입력을 바꾸지 않습니다. Rig IR 컴파일의 모션 목록도 입력으로 최근 4개를 캐시합니다. 이전에는 컴파일할 때마다 프리셋마다 스켈레톤 정의를 직렬화해 생성 모션 캐시를 조회했습니다(약 2.5 ms, IR 컴파일 2.9 → 0.3 ms). `POS_VALUES`는 전체 길이를 먼저 계산한 뒤 한 덩어리로 쓰고, 쓰는 쪽은 크기가 정확히 맞으면 버퍼를 그대로 넘기며 다시 복사하지 않습니다(tml 스켈레톤 Rig의 moc3는 약 7 MB, 쓰기 13.7 → 6.8 ms). 묶음 전체는 약 48 ms에서 약 20 ms로 줄고, 내보내기는 바이트 단위로 변하지 않습니다(`ExportGoldenTool`). Drawable별 IR 캐시는 만들지 않았습니다. `PuppetIr.toIr`은 배열을 감쌀 뿐이며 약 0.2 ms입니다.
- 기하 안전 검사는 객체를 비교할 때 각 메시와 디포머의 기하를 리스트로 상자에 넣지 않습니다. 같은 인스턴스는 바로 같은 것으로 보고, 나머지는 배열을 비트 단위로 비교합니다. 좌표별 샘플은 각 대상의 기준 면적과 유효성 검사를 재사용하고, 메시 샘플은 선택기가 쓰는 정규화 영역을 건너뛰며, 기준과 후보 점이 같으면 상태를 재사용합니다. 전체 보고서는 이전과 바이트 단위로 같습니다(`SafetyGoldenTool`이 무작위 편집 24조를 대조). 일반 메시 편집은 약 15–30 ms에서 2 ms 안으로 줄었습니다. 본에 바인딩되고 조합 영역이 16384개 좌표까지 샘플되는 메시는 여전히 약 1 s가 필요합니다(이전 약 2–3 s). 제출은 새로 추가된 로그 명령에 따라 비교 범위를 줄입니다. 규칙은 [MCP_AUTHORING.md](../agent/MCP_AUTHORING.md#기하-검사와-시험-실행)를 참조합니다.
- Rig 생성은 텍스처 아틀라스 배치를 읽지 않습니다. `RigBuilder`는 먼저 바인딩하지 않은 Rig를 생성합니다(`BuiltRig.unbound`). 메시의 텍스처 좌표는 정점이 레이어 사각형 왼쪽 위 대비 가지는 캔버스 단위 오프셋이고, 텍스처 아틀라스에는 배치 없는 타일만 있으며 페이지는 없습니다. 이어서 `UvBinding`이 현재 배치에 따라 페이지 UV로 환산해 페이지와 타일에 씁니다. 같은 레이어 묶음의 배치만 바꾸면, 바인딩하지 않은 Rig와 그 내용 해시는 변하지 않고 바인딩 결과만 바뀝니다. 0..1 레이어 단위 대신 오프셋을 쓰는 것은, 바인딩이 원래 페이지 UV를 비트 단위로 재현하게 하기 위해서입니다(내보내기는 바이트 단위로 변하지 않음). 스켈레톤은 바인딩하지 않은 Rig 위에서 베이크합니다(`BAKE_VERSION` skeleton-3부터). 관절 세분이 추가한 정점은 레이어 오프셋으로 보간하고, 이어서 다른 정점과 함께 `UvBinding`이 페이지 UV로 환산하므로, 베이크는 텍스처 아틀라스를 읽지 않습니다. 타일을 이동, 확대·축소, 재배치해도 스켈레톤 캐시에 맞습니다(tml에 자동 스켈레톤이 있을 때, 타일 고정, 밀도 변경, 예산 변경의 제출 한 번은 약 4.5–10.8 s에서 약 30–140 ms로 줄고, 레이어를 하나 소프트 삭제하면 약 90–150 ms. `TexturePerfTool`). 이전의 페이지 UV 보간과 비교하면, 추가된 정점의 UV만 마지막 자리 반올림이 다릅니다. canvas, 오프셋, 래스터, 페이지 UV 사이의 환산은 `LayerTexture`가 통일해 제공합니다(페인팅 재매핑, 생성 Rig를 현재 텍스처로 재배치, 메시 이전 로그, CMO3 가져오기가 공유).
- 텍스처 아틀라스와 페인팅(`AtlasLayout`): 자동 배치는 규범적인 사각형 배치입니다(`RectPack`, MaxRects: 각 블록 사방에 `padding`을 두고, 면적, 긴 변, 높이 세 순서에 “남은 가장 짧은 변”과 “가장 낮은 바닥” 두 점수를 각각 쓰며, 페이지 수가 가장 적고 마지막 페이지 사용 높이가 가장 작은 것을 고름). 문서만 결정합니다. 새로 만들기, 다시 열기, 실행 취소, 페인팅 제출, 내보내기가 같은 배치를 얻습니다. 풀이 결과는 타일 크기, 잠금, 고정, 예산으로 캐시합니다(최근 8개). 텍스처 크기를 바꾸지 않는 제출은 다시 풀지 않습니다. 증분인 것은 배치가 아니라 페이지입니다. 각 페이지는 “페이지 크기 + 각 타일 사각형과 픽셀 요약” 레시피로 합성하고 캐시합니다(소프트 참조, 최근 8페이지). 레시피가 변하지 않은 페이지는 이전 모델의 같은 `AtlasPage` 인스턴스를 그대로 씁니다. 바뀐 페이지는 다시 합성하고, 자기가 대체한 페이지와 다른 행을 기록합니다. “변하지 않은 타일은 고정하고, 바뀐 타일은 빈자리를 따로 찾는” 히스토리 의존 배치는 쓰지 않습니다. 크기가 그대로이면 둘은 같습니다(타일 원래 자리에 다시 그림). 크기가 바뀌면 어떤 배치든 그 타일의 UV가 바뀌고, 네이티브 미리보기는 메모리에서 모델을 다시 만들어야 합니다. 규범 재배치는 페이지 합성과 걸친 행의 띠 인코딩을 한 번 더 할 뿐이며(약 20 ms), 그 대가로 배치가 편집 히스토리와 무관합니다.
- 페이지 PNG 지연 인코딩: `AtlasPage.png`는 내보내기가 쓰는 ImageIO 규범 인코딩이며, 내보내거나 IR 컴파일이 읽을 때만 만듭니다. 편집기 실행 묶음은 `previewPng`를 씁니다. 16행을 한 띠로, Sub 필터, 각자 독립된 deflate(level 1, full flush로 끝)로 인코딩하고, 띠마다 IDAT 블록 하나이며, Adler-32는 각 띠를 합칩니다. 디코딩 픽셀은 규범 인코딩과 완전히 같습니다. 파생 페이지는 더러운 행이 있는 띠만 다시 인코딩하고, 나머지 띠는 대체된 페이지에서 가져옵니다. 페이지 전체를 처음부터 인코딩할 때는 띠를 병렬로 처리합니다. 변하지 않은 페이지의 바이트 배열은 같은 인스턴스를 유지하고, 미리보기 묶음 지문은 다시 해시하지 않으며, `CubismPreviewReload`는 바뀐 페이지만 올립니다.
- 페인팅 후보는 두 번째 패킹을 하지 않습니다. 메시를 유지하는 페인팅(및 그림 교체)은 `WorkspaceRasterEdits`에서 픽셀만 잘라 내고(`RasterPaintCommit.paintedSource`) 생성 입력을 얼립니다. Rig, 텍스처 아틀라스, 실행 묶음은 모두 이후의 재구축 한 번에서 옵니다. 메시를 다시 만들어야 하는 페인팅은 여전히 `RasterPaintCommit.prepare`를 호출해 이전 기록을 얻지만, 미리보기 실행 묶음은 더 이상 컴파일하지 않습니다. 재구축할 때 `WorkspacePreviewBuilder`는 현재 모델의 텍스처 아틀라스를 `buildPreview`에 넘기고, 그 페이지와 띠만 빌립니다. 결과는 처음부터 구축한 것과 완전히 같습니다.
- 재배치한 기초 Rig는 “생성 기하 캐시 항목 + 배치 + 텍스처 레이어 메타데이터(픽셀 제외) + 새 메시 ID”로 최근 4개를 캐시합니다. 타일 크기와 위치가 변하지 않는 페인팅은 같은 기초 Rig 인스턴스를 얻어, 재생 검사점이 계속 맞습니다. 레이어 불투명도 통계(`LayerClassifier`)는 래스터 배열 정체로 캐시하고, 합성 미리보기 그림(`PreviewRenderer.composite`)은 각 레이어 래스터 정체와 위치로 최근 3개를 캐시합니다. 재구축은 페인팅된 레이어만 다시 훑습니다.

## Rig 생성 단계

`RigBuilder.build`는 선언된 입력이 있는 단계로 나뉩니다. 각 단계의 출력은 `RigStageCache`(파이프라인마다 하나, `PreviewMeshCache`에 매달림)가 “그 단계가 읽는 내용만 담은” 키로 캐시합니다. 키는 이미 있는 값싼 요약과 설정 부분집합을 씁니다. 래스터는 배열 정체로 기억한 SHA-256(`RasterDigest`), 레이어 메타데이터(ID, 이름, 그룹, 순서, 경계, 의미, 풋프린트 경계와 무게중심, 불투명 픽셀 수), 그리고 `stageConfig`입니다. 메시, 입, 강도와 조정, 생성 모드, 런타임 대상만 남깁니다. 스켈레톤, 로그, 레이어별 표, 표시, 그리기 순서, 텍스처/물리/모션/내보내기 설정은 키에 넣지 않고, 스켈레톤을 읽는 단계가 읽는 부분으로 스스로 키에 넣습니다.

| 단계 | 키(읽는 내용) | 용량 |
| --- | --- | ---: |
| 풋프린트 `footprint` | 래스터 크기와 요약, 정수 위치, alpha 임계값, 그 레이어 메시 설정, 메시 스케일 | 512 |
| 프레임(매번 계산, 약 1 ms) | 풋프린트가 있는 분석: 앵커, 얼굴 Rig, 머리/얼굴/머리카락 상자, 선 자세와 몸 상자 | — |
| 디포머 `deformers` | 선 자세 내용 키, 각 상자, 얼굴 Rig의 모든 수치, 앵커, 좌우가 있는 레이어(메타데이터 + Rig 공간 경계), 상의 경계, 설정, 스켈레톤은 스위치와 쓸 수 있는 첫 상체 본의 양 끝만(`torsoFrame`) | 8 |
| 얼굴 기울임 `lean` | 디포머 목록 인스턴스 | 8 |
| 메시 `mesh:<图层>` | 레이어 메타데이터와 픽셀 요약, Rig 공간 경계와 무게중심, 부모와 그 상자, 머리 공간, 눈 레이어는 얼굴 Rig, 맞는 흰자 경계, 메시 스케일, 그 레이어 메시 덮어쓰기, 설정 | 1024 |
| 채널 `channels` | 유형, 파라미터, 개폐 키, 의미, 치아 페이드 | 256 |
| 입술 `lips` | 소속 Drawable, 메시 단계 출력 인스턴스, 부모 상자, 입술 레이어 메타데이터/픽셀/묶였는지/그리기 순서/표시, 설정 | 64 |
| 바인딩과 스켈레톤 `bound` | 조립 모델(구조가 같음, 메시는 인스턴스 기준), 머리카락 시뮬레이션 스위치, 텍스처 아틀라스 배치와 페이지 크기, 각 레이어 바인딩 메타데이터, 스켈레톤 정의와 입력, 나머지 결과 필드, 스켈레톤 캐시를 비운 횟수 | 4 |

- 조립(마스크, 파츠, 파라미터)은 매번 다시 하며, 약 1 ms입니다. 모든 단계가 맞으면 `bound`는 지난번과 같은 `BuiltRig` 인스턴스를 바로 반환합니다. `generatedBase`의 재배치 캐시는 기하 캐시 항목 대신 기하 Rig 인스턴스를 키로 쓰므로, 어느 단계도 읽지 않는 내용만 바뀌면(예를 들어 로그 항목 추가로 생성 기하 캐시가 어긋남) 기초 Rig는 여전히 같은 인스턴스이고, 재생 검사점이 계속 맞습니다.
- `bound`가 맞으면 그 스켈레톤 베이크를 최근 사용으로 표시합니다(`SkeletonRig.touch`). 프로젝트를 저장할 때 머리 캐시(`ProjectHeadCache`)가 가져가는 것은 여전히 현재 베이크입니다. `SkeletonRig.clearCache`가 증가시키는 횟수가 키에 들어가, 비운 뒤에는 다시 베이크합니다. `bound`는 여전히 텍스처 아틀라스 배치를 키로 쓰지만, 그 안의 스켈레톤 베이크는 배치를 읽지 않습니다. 텍스처 아틀라스가 바뀌면 `bound`는 어긋나고, 스켈레톤 캐시는 맞으며, 바인딩만 다시 합니다.
- 메시 설정이 바뀌면, 그 레이어 풋프린트가 앵커와 프레임을 움직일 수 있고, 부모 상자가 바뀐 메시는 그에 따라 재구축합니다(tml에서 하의 메시를 바꾸면 약 5개 메시를 재구축). 얼굴 각 레이어 메시는 원래 인스턴스를 유지합니다.
- `PreviewMeshCache`의 래스터 요약은 배열로 기억하는 `RasterDigest`를 씁니다. 이전에는 호출할 때마다 각 레이어를 다시 해시했습니다.
- `-Dpsd2live.rigStages=false`(`RigStageCache.enabled = false`)는 단계 캐시와 요약 기억을 끄며, 비교용입니다.

**정확성**: `ExportGoldenTool`은 변경 전(bcf919f2)과 바이트 단위로 같습니다.

**스켈레톤 제출**: 스켈레톤 편집(본 만들기, 바인딩, 관절 이동, 본 삭제)은 `bound`를 어긋나게 하고 스켈레톤을 다시 베이크합니다. 베이크는 `SkeletonRig` 안에서 다시 두 단계 캐시로 나뉘며, 건드리지 않은 사지는 다시 계산하지 않습니다.

- 단일 메시 스키닝(`skinDrawable`, 베이크의 주요 시간)은 읽는 내용 전부로 캐시합니다. 그 메시와 디포머 체인(사지 트리의 각 본, 부모, 호스트, 모든 조상)의 무손실 IR, IR에 나타나는 파라미터와 그 트리 각 본 파라미터의 범위와 기본값, 정지 캔버스 정점, 트리 안의 각 본과 그 부모 본, 프리셋 포즈, 소속 본, 트리 안의 블렌드 셰이프 본, 샘플, 손 가중치, 호스트입니다. 값은 소프트 참조이고 최대 128항이며, `SkeletonRig.clearCache`가 함께 비웁니다.
- 관절 세분(`SkeletonMeshRefine`)은 메시 배열, 정지 캔버스 정점, 관절 띠, 구간 수로 캐시합니다.
- 베이크 전체의 캐시 키는 같은 기초 Rig 인스턴스와 같은 입력에 대해 한 번만 계산합니다.
- 건드린 메시 자체의 스키닝: 각 샘플(어떤 본 파라미터 값 아래의 `computeDeltas`: 각 본 변환, 관절 템플릿, ARAP, 표면 평활)은 그 파라미터 값에만 의존합니다. 그래서 피팅, 키폼 칸, 포즈 블렌드 셰이프에 필요한 샘플은 공통 스레드 풀에서 한꺼번에 병렬로 풀고, 원래 순서로 읽어 들입니다. 결과는 스레드 수와 무관하고, 순서대로 푼 것과 비트 단위로 같습니다(`SkeletonRig.parallelSamples`는 테스트에서만 끌 수 있습니다). 피팅(`fittedSides`)은 각 본의 양쪽을 동시에 진행하고, 라운드마다 원래 순서로 각 구간을 검사하며, 이후 구간은 소수만 미리 가져옵니다. 더 계산하는 것은 실패 구간 뒤의 샘플뿐입니다. ARAP의 전역 방정식(자유 정점의 라플라스 행렬에 그 포즈의 유도 페널티를 더한 것)은 한 번 푸는 동안의 모든 국소/전역 반복과 두 좌표축에서 변하지 않습니다. 풀이마다 포락 Cholesky 분해를 한 번 하도록 바꿨습니다(역 Cuthill-McKee 정렬과 포락은 메시마다 한 번만 계산). 전역 단계마다 삼각 후대입을 두 번만 하며, 단계마다 최대 200회 반복하던 켤레기울기를 대체합니다. 켤레기울기 결과와의 차이는 4096² 캔버스에서 0.0005 px를 넘지 않습니다(`SkeletonBakeDiffTool`, 모든 키폼과 블렌드 셰이프 키, 렌더는 픽셀 단위로 같음). `BAKE_VERSION`은 skeleton-4, 스키닝 캐시 버전은 skin-2이며, 이전 버전이 쓴 머리 캐시는 더 이상 맞지 않습니다. 피팅 허용 오차는 여전히 캔버스 픽셀 1입니다. 샘플 수는 캔버스가 커질수록 늘지만, 현재 소요에서는 이미 있는 프로젝트의 키폼 수를 이 때문에 바꾸지 않습니다.
- 디포머 단계는 스위치와 상체 본만 키에 넣습니다(위 표). 다른 본, 바인딩, 포즈, 가중치의 변경은 디포머 인스턴스를 유지합니다.

정규화 메시 편집(`normalizeMeshEdits`)은 정점 그룹이 있으면 먼저 정점 그룹 항목이 없는 미리보기를 한 번 구축해 가중치를 이전하고, 이어지는 제출 구축은 프로세스 단위 베이크 캐시에 맞으며, 스켈레톤이 아닌 부분만 더 듭니다(약 60–120 ms). 정점 그룹 항목은 `SkeletonCanvasSkin.lockedTopology`를 거쳐 기초 Rig에 영향을 줄 수 있으므로, 이전 구축을 다음 구축에 바로 쓰지 않습니다.

로그만 바꾸는 제출은 빠른 경로를 탑니다(`PSD2LivePipeline.canFastUpdateRig`, 캐시한 기초 Rig 위에서 재생). 그러나 스켈레톤 베이크도 로그를 읽습니다. 손 토폴로지(`canvas_topology`) 메시, 본에 바인딩된 분할 파츠 기록, 로그가 배치한 캔버스 스키닝 메시와 그 정점 주소 기록의 정점 수(`RigBuilder.skeletonJournalInputs`). 이 내용이 바뀌면(예를 들어 본에 바인딩된 메시의 토폴로지 편집과 그 실행 취소) 빠른 경로를 타지 않고 재구축하며, 결과는 콜드 재구축과 같습니다(`SkeletonIncrementalBakeTest`).

## 레이어별 크기

레이어의 캔버스 위치와 픽셀 수는 서로 독립입니다(`core/LayerSpace.kt`).

- 캔버스 사각형: 부동소수점 캔버스 단위이며, 원본 레이어의 `rect`입니다. 없으면 정수 경계입니다. 레이어가 캔버스에서 어디에 있는지를 결정하고, 페인팅과 그림 교체 같은 픽셀 조작은 이것을 바꾸지 않습니다.
- 래스터: 레이어의 실제 원본 픽셀 W×H이며, 임의의 해상도일 수 있습니다.
- 네이티브 밀도: 래스터 픽셀 / 캔버스 단위이며, 두 축이 다를 수 있습니다. 래스터가 정수 경계를 정확히 덮고(픽셀 하나당 캔버스 단위 하나) 분수 사각형이 없는 레이어는 이전과 완전히 같습니다.

기하(`core/CanvasDensity.kt`):

- 분석, 분류, 앵커, 윤곽, 메시 생성, 입술, 연결 덩어리 분할은 모두 캔버스 단위로 래스터를 읽습니다. 밀도가 1이 아니거나 사각형이 분수인 레이어는 분석할 때 캔버스 해상도 뷰 `CanvasDensityLayer`로 바꿉니다. 같은 레이어이고, 래스터를 면적 평균(확대할 때는 쌍선형)으로 정수 경계, 픽셀 하나당 캔버스 단위 하나에 다시 샘플링하며, 사각형 밖은 투명입니다. 그래서 `meshTrace = CANVAS`에서는 32단위 사각형 위의 1024² 래스터와 32² 래스터가 같은 메시를 생성합니다. 완전히 투명한 자리 표시 래스터는 뷰를 바꾸지 않습니다. `meshTrace = TEXTURE`(새 프로젝트 기본)일 때는 메시 윤곽만 텍스처 자체를 읽습니다(원래 밀도로 정수 경계에 깔고, 최대 alpha로 최대 메시 단위의 4배 촘촘한 작업 해상도까지 줄임). 정점 간격과 오프셋은 여전히 캔버스 단위입니다. 메시 토폴로지를 참조합니다. 분류, 앵커 등 나머지 분석은 여전히 캔버스 뷰를 읽습니다.
- 생성기의 텍스처 좌표는 여전히 정수 경계 왼쪽 위 대비 캔버스 단위 오프셋입니다. `UvBinding` / `LayerTexture`는 텍스처 레이어(`textureLayer`, 뷰 뒤의 원 래스터) 공간에서 오프셋을 원 래스터로, 다시 타일로 환산합니다. `raster = (offset − (rect − bounds)) × 密度`. 사각형이 정수이면 빼는 항은 0이고, 결과는 이전과 비트 단위로 같습니다.
- 미리보기 합성(`PreviewRenderer.drawLayer`), 소재 작업 흐름, 관찰 렌더는 래스터를 캔버스 사각형에 늘려 그립니다.

텍스처 아틀라스(`AtlasLayout`):

- 각 타일의 텍스처 픽셀 = 래스터 픽셀 × `textureUpscale` × 밀도 배율(`textureOverrides.density`, 기본 1, 즉 래스터 원래 해상도) × fit입니다. `textureUpscale`은 여전히 요약으로 캐시하는 원본 그림 전처리이며, 효과는 이전과 같습니다.
- 페이지 크기는 예산의 `pageSize`를 쓰고, 이전과 같이 가장 큰 레이어의 캔버스 해상도 크기를 담을 때까지 늘어납니다(다음 2의 거듭제곱, 최대 16384). 밀도가 넘치는 부분은 fit이 처리합니다.
- fit ≤ 1은 잠그지 않은 모든 레이어가 공유하는 계수 하나입니다. 먼저 fit 1로 배치하고, `maxPages` 페이지를 넘지 않으면 1을 씁니다. 넘으면 1/4096 정수 간격에서 이분 탐색으로 들어갈 수 있는 최대 간격을 찾습니다. 결과는 문서만 결정하고, 같은 입력은 같은 배치를 얻습니다. 잠긴 레이어(`lock`)는 fit 1을 유지합니다. 고정 레이어(`pin`)는 지정한 페이지 위치에 먼저 두고, 사각형 배치는 그것들을 피합니다.
- 잠그거나 고정한 레이어가 단독으로 예산을 넘으면, 조용히 줄이지 않습니다. 잠금과 고정을 푼 뒤 함께 fit을 구하고, `PackedAtlas.notices`에 설명합니다(프로그램 로그에만 씀). 1/4096로도 들어가지 않으면 fit 1로 페이지 수를 넘기고 설명합니다. fit < 1도 설명을 줍니다. 설명은 내보내기 경고에 들어갑니다.
- 타일 크기가 래스터와 다르면 `RasterResample`(`format-compile`, 결정적, 프리멀티플라이 alpha)로 다시 샘플링합니다. 페이지 레시피는 “타일 사각형 + 픽셀 요약”을 키로 하므로 영향을 받지 않습니다. 배치의 `scaleX/scaleY` = 타일 픽셀 / 래스터 픽셀입니다.
- 기본값(모든 래스터가 경계와 같고, 기본 밀도, 이미 있는 설정, fit 1)에서는 배치, UV, 페이지, 내보내기가 이전과 바이트 단위로 같습니다(`ExportGoldenTool`).
- 저장한 배치(`atlasArrangement` 설정, `project/AtlasArrangement.kt`): 있으면 `AtlasLayout`은 자동 배치를 구하지 않고, `AtlasArrange.keep`가 저장한 위치와 fit으로 놓습니다. 예산 페이지 안에 있고, 페이지를 벗어나지 않으며, 이미 놓은 타일과 충돌하지 않는 타일은 원래 자리를 유지합니다. 나머지(새 레이어, 커진 뒤 이웃과 겹치거나 페이지를 벗어난 타일)는 페이지의 4×4 픽셀 셀 격자에 첫 빈자리에 넣습니다. 원래 저장 위치가 무효가 된 타일만 설명을 주고, 새 레이어(분할로 대체되어 아직 압축되지 않은 원 레이어 포함)는 조용히 넣습니다. 사각형 타일 사이는 `padding` 간격으로 판단하고, 메시 커버 영역이 관련되면 셀로 판단하며 `ceil(2×padding/4)` 칸만큼 확장합니다. 저장한 커버 영역은 구축할 때마다 타일의 현재 래스터로 교정합니다(`AtlasArrange.covering`). 셀 격자가 래스터 크기와 맞지 않으면(페인팅이나 그림 교체가 자르기를 바꿈) 무효로 하고 타일 사각형 전체로 처리합니다. 래스터에서 alpha ≥ 8인 픽셀이 커버 영역 밖에 떨어지면(페인팅이 메시를 넘음) 그 셀을 보탭니다. 그래서 이웃 타일이 충돌하면 빈자리로 밀리고, 서로 덮지 않습니다. 빈자리로 옮긴 타일도 커버 영역으로 검색하고 자기 셀만 씁니다. 규범 배치를 얼려 얻은 배치는 재구축하면 바이트 단위로 같은 페이지를 만듭니다.
- 한 번에 배치(`atlas_pack`, `AtlasLayout.arrange`): 메시 커버 영역은 현재 모델 최종 메시의 텍스처 좌표에서 가져오고, 래스터에서 메시 밖의 픽셀 셀을 보탭니다(`WorkspaceAtlasFootprints`, 셀은 래스터 픽셀 4, 변마다 최대 192칸, 삼각형과 셀이 만나려면 0.01픽셀 이상 들어가야 하며, 배치가 바뀐 뒤의 끝자리 반올림이 결과를 바꾸지 않게 함). 면적, 높이, 긴 변 세 순서로 셀 격자에서 위에서 아래, 왼쪽에서 오른쪽으로 최초 적합을 하고, 페이지 수가 가장 적고 마지막 페이지의 사용 행이 가장 적은 것을 고릅니다. 사각형은 서로 끼워 넣을 수 있습니다. 예산 페이지 수에 들어가지 않으면 fit은 먼저 64/4096 간격으로 이분하고, 다시 8/4096까지 세분화합니다. 사각형만으로 배치하면(`shape=rect`) 자동 배치 결과를 바로 얼립니다. 페이지를 합성할 때, 커버 영역이 있는 타일은 자기 셀만 씁니다(`TileKey.mask`가 레시피에 들어감). 업스케일 텍스처도 이웃 밖으로 가장자리를 넓히지 않습니다. 이후 메시 편집이 배치 때의 커버 영역을 넘으면, 텍스처 아틀라스가 읽는 `notices`가 다시 배치하라고 알립니다. 자동 배치(`auto=true`)는 저장한 배치를 지웁니다. 끄거나 타일을 옮기면 현재 배치를 저장합니다. 저장한 배치에서는, 자리를 유지할 수 없는 타일(새 레이어, 분할 파츠, 이웃이 커져 밀려난 타일)이 재구축할 때마다 첫 빈자리에 다시 들어갑니다. 그래서 타일을 옮기거나 밀도/잠금을 수정할 때는 먼저 현재 모델의 모든 타일 위치를 배치에 다시 씁니다(`WorkspaceTextureEdits.settled`). 이 타일들은 그 뒤 원래 자리를 유지하고, 옮기거나 줄여 빈 자리를 채우지 않습니다. 동시에 커버 영역이 없는 타일에는 그 메시의 커버 영역을 보탭니다(`meshed`, `WorkspaceAtlasFootprints`). 그 뒤 타일은 메시가 실제로 쓰는 셀로만 겹침을 판단하며, 텍스처 아틀라스 뷰에서 드래그할 때의 판단(`WorkspaceTextureView.meshFootprint`)과 완전히 같습니다. 뷰가 허용하는 위치가 실제로 놓이는 위치입니다. 타일은 중심을 축으로 회전할 수 있습니다(`ArrangedTile.rotation`, `AtlasPlacement.rotation`). 페이지 합성은 회전을 역으로 샘플링하고(`AtlasLayout.writeTurned`, 메시 셀만 씀), 커버 영역은 회전한 셀의 교집합을 구합니다(`AtlasArrange.shape`의 `rotation`). 메시 UV는 `LayerTexture.tilePlacement`로 Umamo의 회전 배치에 따라 환산하고, 내보내기도 회전을 함께 냅니다. 텍스처 아틀라스 뷰의 이동, 확대·축소, 회전은 편집 세션입니다(`TextureWorkspaceState.session`). 뷰 표시만 바꿉니다. 적용할 때 밀도와 위치를 `layer_set_pixel_density` / `atlas_set_tile` 배치로 제출하며, 재구축 한 번, 히스토리 노드 하나입니다. 이 두 편집(단일 또는 배치, GUI 또는 MCP)은 발행 전에 `WorkspaceTextureEdits.requireKept`가 후보 모델을 비교합니다. 이전에 자리를 유지하던 타일이 새 배치에서 배치 위치 밖으로 밀리면 `WorkspaceTileCollision`(`tile_collides`)을 던지고, 제출 전체가 되지 않습니다. 배치는 최종 배치만 검사하고, 배치에 다시 배치, 예산 변경, 픽셀 교체, 캔버스 사각형 이동이 없을 때만 검사합니다. 쌍 판단(`AtlasArrange.meet`)은 먼저 간격만큼 바깥으로 늘린 회전 외접 상자를 비교하고, 만날 때만 메시 셀을 비교해, 촘촘한 사각형 배치에 커버 영역을 보탠 뒤 셀 반올림 때문에 교차를 잘못 판단하지 않게 합니다.
- 메시 정체: 생성 입력을 바꾸는 편집(레이어 추가·삭제, 분류나 생성 설정 변경)은 정규화할 때 먼저 현재 각 메시의 ID를 `splitDrawableIds`에 씁니다(`WorkspacePreviewBuilder.pinnedIdentities`). 생성기는 이것으로 이름을 붙입니다. 그렇지 않으면 분류와 같은 종류 순번에서 파생한 ID가 이름이 바뀌거나 다시 번호가 매겨지고, 재생성 병합이 사용자의 이전 메시를 퇴역 객체로 새 메시 옆에 남깁니다.
- 레이어 삭제(`layer_delete`, `WorkspaceLayerEdits`)는 실제 삭제입니다. 레이어는 원본 그림과 생성 입력에서 떠나고, 그 메시는 로그 기록 `layer_delete`(`LayerDeletionJournal`)로 저작 상태 Rig에서 떠나며, 구축은 그 기록 앞에 체크포인트를 쓰고, 이전의 생성 기록은 더 이상 재생하지 않습니다. 실행 취소는 히스토리 전환입니다. 아래의 지연 필터는 이전 버전이 소프트 삭제한 레이어(`deletedLayerIds`, 읽기 전용, `layer_restore`로 복구 가능)와 입술 띠 같은 파생 행에만 씁니다.
- 소프트 삭제한 레이어(구식 분할이 남긴 원 레이어 포함)는 지연 필터 모드에서 여전히 완전한 생성과 재생에 참여하고, 완전한 텍스처 아틀라스가 그 타일을 패킹합니다. 필터한 모델은 남은 레이어만으로 다시 패킹하고(`RigLayerDeletion.compact`), 남은 메시는 `RigGenerationSource.repack`으로 새 텍스처 아틀라스로 옮기며, 캔버스 단위로 환산하고 같은 텍셀을 샘플링합니다. 그래서 미리보기, 텍스처 작업 공간, CLI, GUI 내보내기에는 삭제한 레이어의 픽셀이 없습니다. 기초 Rig가 바인딩한 완전한 텍스처 아틀라스는 `RigPreviewModel.generationAtlas`에 기록하고, 빠른 재생(`updateRigEdits`)도 필터 뒤에 마찬가지로 다시 바인딩합니다. CMO3 가져오기는 원래 배치를 유지합니다. 남은 메시가 어느 텍스처 아틀라스에서도 타일을 찾지 못하면 완전한 텍스처 아틀라스로 돌아갑니다. 레이어를 복구하면 완전한 텍스처 아틀라스를 다시 얻습니다. 분할로 대체된 원 레이어(`ArtPrimitiveJournal.visibleAnalysis`가 걸러 낸 것)도 같습니다. 생성할 때는 여전히 패킹하고, 미리보기와 내보내기는 재생 뒤에 보이는 레이어로 압축합니다. 생성 기하 텍스처 아틀라스(`generationSource`의 기하 Rig)는 텍스처 덮어쓰기와 저장한 배치를 읽지 않으므로, 텍스처 제출이 기하 캐시를 무효로 만들지 않습니다.

내보내기:

- moc3는 페이지와 페이지 UV만 읽으므로, 추가 처리가 필요 없습니다.
- cmo3(`Cmo3LayerArt`, `targets/cubism`): Cubism Editor 레이어는 픽셀 하나당 캔버스 단위 하나이고, 편집기가 레이어에서 텍스처 아틀라스를 다시 만듭니다. 기본 `canvas`: 밀도가 1이 아닌 레이어는 캔버스 사각형 크기(다운샘플)로 레이어 이미지에 쓰고, 저장한 텍스처 아틀라스 페이지는 고해상도를 유지하며, 타일 패킹 스케일이 그에 따라 커집니다. 어떤 타일이든 텍스처 아틀라스 밀도(텍스처 픽셀 / 캔버스 단위)가 1보다 크면, 내보내기는 `TEXTURE_SIZE` / `APPROXIMATED` 손실 항목을 줍니다(“Cubism Editor rebuilds the atlas from canvas-resolution layers”). 기존의 `textureUpscale` 프로젝트에도 마찬가지로 적용됩니다. 내부 설정 `layer_art=native`는 원래 해상도로 레이어를 쓰고 모델 이미지 변환으로 캔버스에 맞추지만, 편집기에서 아직 실측하지 않았으며 기본은 끕니다.

그림 교체(`core/LayerImageReplace.kt`):

- `LayerImageReplace.replace(document, layerId, raster, fit)`는 후보 문서를 반환합니다. 캔버스 사각형과 정수 경계는 그대로이고, 래스터만 바꿉니다(`STRETCH`는 그대로 늘리고, `CONTAIN`은 비율을 유지해 가운데 맞추고 투명을 채움). 처음 바꿀 때 그 이전의 원본 그림을 생성 입력으로 얼립니다(메시를 유지하는 페인팅과 같음). 메시, 키폼, 바인딩은 변하지 않고, 재구축 뒤에는 바인딩된 UV와 페이지만 다릅니다. 호출 쪽은 평소처럼 재구축하고 제출합니다.

가져오기(`core/LayerImport.kt`, 소재 작업 흐름, CMO3 가져오기):

- 이미지 파일 가져오기(`layer_import_images`)는 투명 가장자리를 자른 뒤 원래 래스터를 유지합니다. 캔버스를 넘으면 캔버스 사각형만 캔버스 안에 맞게 비율로 줄이고, 래스터는 그대로이므로 밀도가 1보다 큽니다. 들어가는 이미지는 여전히 픽셀 하나당 캔버스 단위 하나인 정수 경계이며, 이전과 같습니다.
- 가져온 이미지는 제출 한 번으로 저작 상태 Rig에 자기 메시를 가집니다(`canvas_mesh_create`). 생성 입력을 얼리지 않고, 자리 표시를 쓰지 않습니다. 생성기는 생성 기록이 소유한 레이어를 투명 자리 표시로 보고(`RigGenerationSource.createdCoverage`), 그것에 텍스처 블록만 찍습니다.
- 레이어 전체 변환(`layer_transform`, `application/WorkspaceLayerTransform`): 레이어의 프레임(정수 경계와 부동소수점 사각형)은 변하지 않고, 픽셀, 텍스처 타일, 텍스처 좌표는 프레임에 고정됩니다. 변환 `LayerTransform`(2×3 아핀)은 레이어에 기록하고, 레이어의 각 메시는 정지 포즈에서 오브젝트 모드 `canvas_geometry` 한 줄을 씁니다. 생성기는 프레임만 읽고 변환은 읽지 않으므로, 이동은 저작자의 편집이지 재생성이 아닙니다. 페인팅 세션은 프레임 안에서 하고, 캔버스는 완전한 변환으로 표시합니다(세션 래스터는 레이어를 따라 회전하는 사각형으로 그려지고, 획과 형태는 역변환으로 프레임에 떨어지며, 브러시 크기는 변환의 면적비로 환산). 오브젝트 모드 드래그가 어떤 레이어의 메시 전부를 덮으면, 캔버스는 그 조작으로 제출합니다(`AffineFit`이 드래그 전후 점을 맞추고, 순수 평행 이동, 축 스케일, 일반 아핀 중 0.01 캔버스 단위 안에 맞는 첫 번째를 차례로 고릅니다. 회전하지 않은 드래그는 부동소수점 잡음 때문에 회전으로 기록되지 않습니다. 변환을 합성할 때 백만 분의 일 규모 잔차는 버리고, `isAxisAligned`는 1e-5의 상대 회전각을 허용). `layer_set_canvas_rect`는 현재 표시 사각형에서 출발하는 변환 한 번입니다. 레이어 변환만 다른 원본 그림은 생성과 텍스처 아틀라스에 같은 한 벌입니다(`PSD2LivePipeline.sameArt`). 그래서 이동은 빠른 경로를 타고, 모델은 새 원본 그림을 씁니다. 생성 기록이 소유한 레이어만 더하거나 빼거나, 레이어만 이동하는 제출은 재생성 비교를 건너뜁니다(`WorkspacePreviewBuilder.onlyUsersLayersChanged`). 개발 도구 `LayerFlowPerfTool`은 가져오기, 이동, 부모 변경, 재구축, 삭제의 제출 시간을 잽니다.
- 소재 레이어(`layer_add_from_asset` / `layer_set_placement`)는 소재 픽셀을 래스터로, 배치한 캔버스 사각형을 레이어 사각형으로 씁니다. `WorkspaceCanvasPlacement.canvasUnitsPerPixelX/Y`가 실제 비율입니다. 평행 이동/확대·축소/명시적 미러의 정합은 보간하지 않고(미러는 행과 열만 뒤집음), 회전이 있는 정합만 소재 자신의 밀도로 외접 상자에 래스터화합니다.
- CMO3 가져오기는 각 타일의 모델 이미지 변환(`_materialLocalToCanvasTransform`, umamo `Cmo3AtlasIngest.canvasTransformByTile`)과 패킹 스케일로 페이지 텍셀/캔버스 단위를 구합니다. 1보다 크면 레이어는 같은 정수 경계 위에 그 밀도로 래스터를 다시 만듭니다(예를 들어 고밀도 레이어가 텍스처 아틀라스 페이지에만 있거나, 레이어 자체가 모델 이미지로 캔버스에 맞춰진 두 가지 쓰기). 그렇지 않으면 이전과 바이트 단위로 같습니다. umamo 원본 레이어 목록은 여전히 파일에 기록된 레이어 이미지 위의 사각형을 쓰며, 캔버스로 환산하지 않습니다.
- 크기 제한(`LayerSizeBudget`): 래스터와 캔버스 해상도 뷰(외접 상자)는 각각 16MP를 넘지 않고, 네이티브 밀도는 축마다 256픽셀/캔버스 단위를 넘지 않으며, 사각형은 축마다 최소 0.5단위입니다. 넘으면 분명히 거부하고, CMO3 가져오기가 넘으면 전체 밀도를 낮춥니다.

페인팅(`core/PaintSpace.kt`):

- 페인팅은 레이어 자신의 래스터 격자에서 합니다(`PaintSpace`). 초안 이미지의 픽셀이 레이어의 래스터 픽셀이며, 같은 밀도로 캔버스 가장자리까지 뻗고, 16MP를 넘으면 레이어 주변 여백을 비율로 줄입니다. 제스처, 반지름, 선 두께, 색 추출은 모두 캔버스 단위이며, 아핀으로 초안 픽셀에 매핑합니다. 두 축 밀도가 다르면 브러시 반지름은 기하 평균을 씁니다. 밀도가 1이고 사각형이 정수인 레이어(그리고 완전히 투명한 레이어)의 초안은 캔버스 그 자체이며, 이전과 비트 단위로 같습니다.
- 제출은 불투명 픽셀로 자른 래스터와 그 캔버스 사각형을 가져갑니다(`WorkspacePaintRaster.rect`). 캔버스 해상도로 줄이지 않습니다. 사각형은 레이어의 원래 사각형에서 잽니다. 움직이지 않은 변은 원래 좌표를 유지하고, 확장과 자르기는 밀도를 유지하며, 정수 경계는 외접 상자를 쓰고, 사각형과 정수 경계가 같으면 저장하지 않습니다. 제출할 때는 레이어의 원래 영역과 획이 쓴 영역만 읽고, 캔버스 전체를 복사하지 않습니다. 완전히 지운 레이어는 이전과 같이 캔버스 원점의 1×1 투명 픽셀이 됩니다.
- 앞뒤 분리의 앞 레이어는 래스터 크기를 유지합니다. 픽셀 중심에서 제출 픽셀을 샘플링하고, 격자가 맞으면 비트 단위로 복사합니다. 메시를 유지하는 페인팅, 메시를 다시 만드는 페인팅, CMO3를 가져온 페인팅은 모두 `LayerSpace`로 타일을 주소합니다(`RasterPaintCommit`의 슬라이스 재매핑, `Cmo3ModelImport`의 페인팅 텍스처 좌표). 연결 덩어리 분할은 원본 레이어 자신의 래스터에서 파츠를 자르고, 파츠는 원래 밀도를 유지합니다.

텍스처 명령(`application/WorkspaceTextureEdits`, `WorkspaceTextureOperations`): 텍스처 작업 공간(텍스처 아틀라스 페이지와 밀도 히트맵, 레이어별 크기 패널, 편집 캔버스의 원본 픽셀 미리보기, [조작 빠른 참조](../guide/USER_GUIDE.md#텍스처-작업-공간-요점))은 `WorkspaceTexturePort`로 제출합니다. MCP `layer_set_canvas_rect`, `layer_replace_image`, `layer_set_pixel_density`, `atlas_set_tile`, `atlas_set_budget`, `atlas_pack`과 같은 순수 후보를 쓰며, 모두 백그라운드 작업이자 원자 배치 멤버입니다. 조회는 `layer_get_texture`, `atlas_get`, `atlas_check_placement`, `atlas_render_page`입니다([MCP 인터페이스](../agent/MCP_AUTHORING.md#텍스처와-텍스처-아틀라스) 참조). 분수 사각형을 umamo의 원본 레이어 목록(정수)에 쓸 때는 정수 경계를 씁니다. 목록으로 텍스처를 해석하는 메시 이전(`LayerTexture.of`)은 분수 사각형에 대해 근사일 뿐입니다(정수 사각형은 정확합니다. 타일 너비·높이가 래스터 크기, 목록이 캔버스 크기이며, 비율이 밀도입니다). 생성 입력의 가장자리 보강(`RigGenerationSource.padded`, 메시를 유지하는 것, 새 메시, `art_primitive` 파츠의 텍스처 커버)은 고밀도 레이어에 원래 밀도로 투명을 보태고, 다운샘플하지 않습니다. `art_primitive`, `canvas_mesh_create` / `canvas_mesh_rebuild`의 `canvas_uvs`는 캔버스 단위이며, `LayerTexture.of`로 고해상도 타일에 매핑합니다.

## 성능 기준선

`CommitPerfTool.baseline`(`PSD2LIVE_TOOLS=1`)은 tml에 자동 스켈레톤, 스윙 둘(앞머리, 머리 장식), 베이크한 뒷머리 시뮬레이션 하나를 갖춘 프로젝트를 세우고, 단계별로 제출 경로를 재서 `build/tools/commit-perf/baseline.json`과 `baseline.md`를 출력합니다. 숫자는 Windows 개발 머신 한 대의 단일 실행에서 가져왔으며, 같은 기계의 전후 비교에만 씁니다. 기계, JIT 워밍업, 동시 부하가 다르면 절댓값은 두 배 이상 차이 날 수 있고, 단계 사이의 비율이 더 믿을 만합니다. 단계 값은 여러 번 웜 호출의 평균입니다. 제출 값은 애플리케이션 층 명령 경계를 거친 벽시계 시간입니다(제출할 때마다 히스토리 저장소에 쓰는 시간 포함). 네이티브 Cubism 미리보기 재로드는 네이티브 런타임과 GL 컨텍스트가 필요해 측정하지 않았습니다. 재로드 전에 런타임 파일을 쓰는 것(“쓰기”)만 측정했습니다.

- 재생, 리비전 번호 해시, 저장소 쓰기는 모두 로그 길이에 선형으로 늘어납니다(이것이 기준선입니다. 재생 검사점 이후, 추가 제출의 재생은 로그 길이와 무관합니다. [증분 재생](#증분-재생) 참조). 작업 저장소는 리비전마다 완전한 스냅샷을 한 벌 씁니다. 200개일 때 제출마다 약 7 MB가 늘고, 장면 시퀀스 전체 뒤 저장소는 약 1.2 GB입니다.

- 기하 제출에서 moc3 모델 전체 재컴파일과 기하 안전 검사가 원래 주요 부분이었습니다. 사이드카 텍스트와 모션 목록을 캐시하고, moc3 쓰기를 다시 하고, 기하 검사 범위를 줄인 뒤, 같은 장면의 웜 제출은 약 37 ms입니다(히스토리 저장소 쓰기 약 27 ms와 네이티브 재로드는 제외). 런타임 재구축 약 27 ms(그중 moc3 패킹 약 20 ms. 주로 메시별 키폼 다운그레이드, 정지 메시를 캔버스 공간으로 옮기기, 약 7 MB 쓰기. 재생 약 5–8 ms), 기하 검사 약 4 ms, 후보 준비와 메시 정규화 약 3 ms입니다.
- 페인팅과 그림 교체는 텍스처 아틀라스 패킹과 PNG 인코딩이 주도하며, 후보 준비와 재구축이 각각 한 번씩 합니다(이것이 기준선).
- 페인팅을 레이어 래스터 공간에서 제출하도록 바꾼 뒤(위 “레이어별 크기”의 페인팅), 후보는 더 이상 캔버스 전체를 복사하지 않습니다. 도구는 페인팅 세션과 같은 캡처 방식을 씁니다(레이어 원래 영역과 획 영역). 같은 기계에서 작은 레이어 페인팅 제출 중앙값은 약 0.25 s → 약 0.17 s이고, 그중 후보 준비는 약 56 ms → 약 1.5 ms이며, 나머지는 제출 안의 재구축입니다.
- 텍스처 아틀라스를 규범 배치 + 페이지 레시피 캐시 + 띠 미리보기 PNG로 바꾸고, 페인팅 후보가 더 이상 패킹하지 않은 뒤(위 “텍스처 아틀라스와 페인팅”), 같은 기계에서 동시 부하 아래 전후를 비교했습니다(두 실행의 절댓값은 모두 위 표의 유휴 머신 숫자보다 높음). 작은 레이어 페인팅 제출 중앙값은 약 2.5 s → 약 0.35 s(안정 후 약 0.3 s)이고, 그중 후보 준비는 약 1.5 s → 약 0.17 s, 제출 안 재구축은 약 1.2 s → 약 0.2 s입니다. 같은 형태 그림 교체는 약 2.1 s → 약 0.3 s입니다. 미러 교체 후 메시 재구축은 약 3.1 s → 약 0.45–0.8 s입니다. 스켈레톤이 있는 전체 재구축(스켈레톤 히트)은 약 1.0–1.6 s → 약 0.25–0.4 s입니다. 페이지 전체 미리보기 띠 인코딩은 약 20 ms입니다(규범 PNG는 약 0.5 s, 내보낼 때만 생성). 분석 두 번의 합은 약 0.2 s → 약 0.03–0.06 s입니다. 내보내기 파일은 변경 전과 바이트 단위로 같습니다(`ExportGoldenTool`). 미리보기 묶음은 텍스처 페이지 PNG 인코딩 외에는 변하지 않습니다.

**프로젝트 열기**: 스켈레톤 베이크 캐시는 프로세스 안에만 있으므로, 콜드 스타트 뒤 스켈레톤이 있는 프로젝트를 처음 열면 여전히 약 5–7 s를 베이크합니다. 저장할 때 머리의 베이크를 아카이브의 선택적 머리 캐시 `cache/head/`에 씁니다(형식은 [프로젝트 형식](PROJECT_FORMAT.md#head-캐시)). 열 때는 revision, 프로그램 버전, 생성기 상수, 언어를 대조한 뒤 `SkeletonRig` 캐시에 심습니다. 재구축은 여전히 완전한 경로를 타고, 스켈레톤 캐시 자신의 내용 키가 히트를 결정하며, 결과는 콜드 재구축과 비트 단위로 같습니다. 저장한 베이크는 읽기 집합 안의 메시와 디포머만 남기고, 읽기 집합 밖의 객체는 ID와 순서만 남기며, 맞으면 새 기초 Rig에서 가져옵니다. `OpenPerfTool.profile`은 위 장면(스켈레톤 + 스윙 둘 + 베이크 시뮬레이션)에서 아카이브 세 가지를 저장합니다. 지금의 쓰기(각 리비전의 저작 상태 Rig와 머리 캐시. 열 때 생성도 재생도 하지 않음. 고정 Rig 참조), 머리 캐시만(생성과 재생, 스켈레톤 베이크를 심음), 둘 다 없음(생성, 재생, 스켈레톤 베이크). 열기 전에 저작 상태 Rig 저장소(`MaterializedRigStore.clear()`)와 스켈레톤 캐시(`SkeletonRig.clearCache()`)를 비우고, 각각 3번 열며, 셋이 같은 모델을 구축하는지 대조합니다. 아래 표는 저작 상태 Rig를 도입하기 전에 뒤의 두 아카이브를 측정한 것입니다(각 3번 열기, 빈 스켈레톤 캐시).

| 아카이브 | 풀기와 심기 | 머리 재구축 | 합계(첫 표시) | 스켈레톤 베이크 |
| --- | ---: | ---: | ---: | ---: |

| 머리 캐시만(10.9 MB, 베이크 항목 6.9 MB, 압축 후 5.4 MB) | 약 0.37–0.47 s | 약 0.18–0.25 s | 약 0.7 s | 0 |

저장은 약 0.5 s가 더 듭니다(베이크 직렬화와 압축). 연 뒤의 첫 표시가 곧 전체 재구축 결과이며, 런타임 묶음을 따로 캐시하지 않습니다. 캐시가 있으면 재구축은 약 0.2 s만 남고, 이전 런타임 묶음을 먼저 보여 준 뒤 바꾸는 이익은 제한적입니다.

## 분할 실체화: 아트 프리미티브 기록 `art_primitive`

이전의 분할(`canvas_source_partition`, `canvas_depth_split`)은 원 레이어를 원본 그림에 남기고 소프트 삭제한 뒤, 재생할 때 원 메시를 비트 단위로 다시 생성하고(기하 지문과 부모를 대조) 기록 위치에서 그 바인딩을 파츠로 복사했습니다. 문제는 세 가지입니다. 생성 규칙이 바뀌면 이전 기록을 재생할 수 없습니다. 텍스처 아틀라스는 여전히 원 레이어를 패킹하고, CMO3 내보내기가 그 픽셀을 가져갑니다. “모두 복구”가 원 레이어를 되살립니다. 지금의 분할은 원 레이어를 파츠로 **실체화**합니다. 파츠가 유일한 그리기 객체이고, 원 레이어는 더 이상 없으며, 분할 전으로 실행 취소하는 것만 가능합니다.

**분할은 곧 재생성**(`WorkspaceArtPrimitives.materialize`, `RigRegenerationCheckpoint.split`): 분할은 원본 그림을 바꿉니다(원 레이어를 파츠가 대체). [체크포인트](#체크포인트) 방식으로 병합합니다. G는 현재 생성 결과, G′는 파츠가 원 레이어를 대신한 뒤의 생성 결과입니다. G와 현재 저작 상태 M 안의 원 메시는 모두 분할 자신(`SplitParts`: 연결 덩어리/다각형은 `SourcePartitionJournal.splitParts`, 앞뒤 분리는 `DepthSplit.splitParts`)이 같은 파츠로 자릅니다. 각자 자기 원 메시의 정지 위치, 키폼, 채널, 블렌드 셰이프, 경로, 정점 그룹, Glue를, 같은 정점 출처를 거쳐 가져갑니다. 그래서 사용자가 움직이지 않은 파츠는 생성한 파츠와 비트 단위로 같고, 원 메시에 한 사용자 수정은 파츠 위의 수정이 되며, 삼자 병합(`RigRegeneration.merge`)이 그것들을 G′의 파츠로 가져갑니다(부모가 바뀌면 부모 공간으로 환산하고, 스켈레톤이 관절 행을 넣을 때는 캔버스 텍스처 좌표로 이전). 분할이 새로 만든 Glue(다각형 절단점 추종, 앞뒤 분리의 방향 Glue)는 M 쪽에만 있으며 사용자의 것입니다. 분할은 `art_primitive` 기록을 쓰고, 바로 뒤에 `rig_checkpoint`를 씁니다(병합 결과와 G′ 스냅샷). 기록 자체는 결코 재생하지 않습니다. 이후 구축은 이 체크포인트에서 시작하며, 기초 Rig가 필요 없습니다.

- 원 메시를 생성기가 만들었으면, 기록은 버전 2 **선언**입니다. 각 파츠의 정지 캔버스 메시(G에서 원 메시를 자른 파츠를, 생성 디포머가 기본 포즈에서 캔버스로 환산), 레이어, 분류, `fixed_topology`(파츠에 사용자 Glue, 정점 그룹, 경로가 있으면 참), `authored`는 빈 객체, `glues`는 비어 있습니다. 기초 생성은 이것으로 파츠를 만듭니다([버전 2 기록](#버전-2-기록) 참조). 이후 얼굴 설정, 선 자세, 스켈레톤, 분류 변화는 다음 병합을 통해 마찬가지로 파츠에 도달합니다.
- 원 메시가 생성된 것이 아니면(로그가 만든 메시, 예를 들어 생성 입력을 얼린 뒤 가져온 그림), 기록은 버전 1입니다. 파츠는 모든 데이터를 가지고, 그 레이어는 기초 생성에 들어가지 않으며, 파츠는 병합에서 사용자 객체입니다.
- 버전 1 후퇴, 두 번 캡처, 가드는 없습니다. 병합은 실패하지 않고, 이전이 깨끗하지 않은 곳은 병합 문제로 보고합니다. 원 메시의 토폴로지를 손으로 바꿨으면, G 쪽에서는 같은 파츠를 자를 수 없고, 파츠는 사용자 토폴로지로 남습니다(병합에서 사용자가 토폴로지를 바꾼 규칙과 같음. 고정 Rig · 재생성 병합 참조).

**기록**(로그 항목, 버전 1. 지금은 생성되지 않은 원 메시에만 쓰며, 이전 버전의 분할은 모두 이것을 썼습니다. 버전 2는 [아래](#버전-2-기록)를 참조):

| 필드 | 내용 |
| --- | --- |
| `op`, `v`, `origin` | `art_primitive`, `1`, `split`(다각형/연결 덩어리) 또는 `depth`(앞뒤 분리) |
| `texture_source_id` | 파츠 텍스처가 있는 원본입니다(생성 모델은 `art-0`) |
| `supersedes`, `supersedes_layers` | 이 위치에서 삭제하는 메시 ID와 그 원본 레이어 ID |
| `replace` | 대체된 메시 → 파츠 메시. 파츠 트리에서의 위치에 씁니다. `masks`를 주지 않으면 다른 메시의 마스크에도 씁니다 |
| `masks` | 선택입니다. 대체된 메시가 마스크일 때 어떤 파츠가 맡는지입니다(앞뒤 분리는 뒤 레이어만 사용) |
| `primitives` | 파츠마다 한 항입니다. `id`, `layer_id`, `source_id`, `source_bounds`(텍스처가 덮어야 하는 캔버스 사각형), `neutral_bounds`, 이름, 부모, 파츠, 블렌드 모드, 정적 재질과 표시, 마스크, `user_data`. 부모 공간 정점 `positions`, `triangles`, 캔버스 단위 텍스처 좌표 `canvas_uvs`. 쓰는 파라미터 정의, 기하 키폼 `geometry`, 채널 키폼 `channels`, 블렌드 셰이프 `blends`(제한 곡선 포함), 경로 `paths`, 정점 그룹 `vertex_groups` |
| `glues` | `replaced`: 모델 순서대로, 대체된 메시에 닿는 Glue 각각에 대응하는 대체 Glue. `appended`: 마지막에 추가하는 Glue(연결 덩어리 분할의 절단점 추종, 앞뒤 분리의 방향 Glue) |
| `depth` | 앞뒤 분리에만 있습니다. `back`, `front` 레이어 ID와 `glue_id`. `DepthSplit.isFrontLayer`가 이것으로 앞 레이어 페인팅이 토폴로지를 유지하게 합니다 |

**재생**(`ArtPrimitiveReplay.replay`, 구버전 재생. 기록 뒤에 체크포인트가 없는 이전 로그에서만 합니다. [구버전 재생](#구버전-재생) 참조): 없는 파라미터는 기록대로 만듭니다. `supersedes`의 메시를 지우고, 파츠는 원 메시의 목록과 파츠 트리 위치에 들어갑니다(원 메시가 이미 없으면 기록의 파츠나 루트에 넣음). 다른 메시의 마스크는 `masks`/`replace`로 다시 씁니다. 대체된 메시에 닿는 Glue는 차례로 `replaced`의 대응 항목으로 바꿉니다(개수가 현재와 맞지 않으면, 닿는 Glue를 모두 지운 뒤 순서대로 대체 항목을 추가). 그다음 `appended`를 추가합니다. 대체된 메시의 경로와 정점 그룹은 지우고, 파츠의 경로와 정점 그룹은 기록대로 씁니다. 재생은 대체된 메시의 기하를 읽지 않고, 지문도 대조하지 않습니다. 텍스처 좌표는 캔버스 단위로 저장하고, 재생할 때 현재 텍스처 아틀라스로 환산합니다.

**분할할 때 캡처한 상태**: `RigEditOverlay.authored`는 구형식 편집과 로그 전체 이후, 스윙과 시뮬레이션 쓰기 이전의 모델을 줍니다. 파츠는 그 모델에서 가져오므로, 스윙과 시뮬레이션이 생성한 축은 기록에 들어가지 않습니다. 연결 덩어리/다각형 파츠의 정점, 키폼, 블렌드 셰이프, 경로, 정점 그룹, Glue는 원래 분할 알고리즘으로 이전합니다. 시뮬레이션 대상, 베이크 오프셋, Glue 역할은 파츠로 옮깁니다(앞뒤 분리는 뒤 레이어로). 그 뒤 시뮬레이션이 평소처럼 다시 씁니다.

**생성 입력**: 분할은 생성 입력을 얼립니다(`generationSource`). 원 레이어는 거기에만 남습니다. 생성할 때:

- 대체된 생성 레이어는 여전히 기초 Rig 생성에 참여하고, 대체 레이어가 현재 원본 그림에서 있는 위치에 놓입니다(대체 레이어의 가장 높은 `order`). 그래서 다른 레이어의 그리기 순서, 디포머 프레임, ID는 분할 전과 같고, 기록 이전의 로그는 그대로 재생됩니다.
- 파츠가 있는 레이어는 기록이 소유하며, 기초 생성에 들어가지 않습니다. 현재 픽셀은 `source_bounds`로 투명을 보태 덮은 뒤 패킹합니다.
- 대체된 레이어는 텍스처 아틀라스에서 1×1 투명 자리 표시만 차지해, 기록 이전의 로그 항목이 주소를 찾을 수 있게 합니다. 기록을 재생한 뒤, `BuiltRig.withRigEdits`가 Rig의 텍스처 아틀라스 타일과 아트 목록에서 그것을 지우고, 미리보기 분석도 더 이상 나열하지 않으므로, 내보낸 CMO3에는 그 레이어가 없습니다.
- 입이 층으로 나뉘면, 그것이 생성한 입술은 남습니다. 층으로 나뉜 것이 입술 자체이면, 그 입술은 대체됩니다.

**파츠 이후의 편집**: 파츠는 일반 원본 레이어입니다. 페인팅, 삭제/복구, 다시 분할할 수 있습니다(분할된 파츠도 마찬가지로 대체됨). 파츠의 메시 설정을 바꾸면 `MaterializedMeshRebuild`가 `canvas_mesh_rebuild`를 추가하고, 키폼과 바인딩을 이전합니다. 파츠는 더 이상 생성 규칙을 따라 자동으로 다시 생성되지 않습니다.

**스켈레톤 스키닝**(버전 1 파츠, 구버전 재생): 스켈레톤은 로그 전에 기초 Rig를 베이크하고, 파츠는 기록을 재생해야 나타납니다. 기초 Rig만 보면 본에 바인딩된 파츠는 존재하지 않습니다(좌우를 한 장으로 그린 뒤 분할한 다리, 신발은 그래서 스키닝되지 않고, 다리 본에는 키폼 없는 파라미터만 남음). 그래서 스켈레톤 단계(`RigBuilder`)는 먼저 기록에서 본에 바인딩된 파츠를 디코딩합니다(`ArtPrimitiveReplay.skinnable`: 캔버스 단위 텍스처 좌표, 타일과 마스크 없음). 기초 Rig와 함께 베이크한 뒤, 스키닝된 파츠와 베이크가 그것들에 더한 Glue를 기초 Rig에서 꺼내 `BuiltRig.primitiveSkins`에 넣습니다. 기초 Rig에는 여전히 대체된 원 메시만 있고, 기록 이전의 로그는 그대로 재생됩니다. 기록을 재생할 때는 스키닝 결과로 스스로 디코딩하는 것을 대신합니다(부모는 본 디포머, 텍스처 좌표는 현재 텍스처 아틀라스로 환산, 마스크는 기록에서). 양 끝이 이미 제자리인 Glue는 이어서 들어갑니다. 다음 파츠는 여전히 기록이 스스로 디코딩합니다. 부모나 키폼 파라미터를 더 이른 로그 항목이 만들어야 하거나, 경로나 정점 그룹이 있는 것(베이크는 그것들을 추가 정점으로 이전하지 않음). 기록의 부모가 더 이상 기초 생성에서 나오지 않으면, 디코딩은 [부모가 더 이상 생성되지 않음](#부모가-더-이상-생성되지-않음)에 따라 다시 겁니다. 재생 검사점은 `primitiveSkins` 인스턴스를 키의 일부로 씁니다. `RigEditOverlay.applyTo` / `authored`와 시뮬레이션 베이크는 모두 이것을 넘겨야 합니다(`authored(BuiltRig)`).

**소유**: 파츠는 편집 로그 노드에 속합니다(`journal`이 소유하는 `rig:authored`). 생성기 의존 그래프에 따로 나열하지 않습니다. 스윙과 시뮬레이션은 평소처럼 그것들을 읽습니다. 대체된 메시 위의 기존 `generated_override`는 대상을 잃은 뒤 고립으로 보고합니다.

**대체된 ID 참조**: 문서 조작의 참조 필드(`layer_id`, `target`, `source_id`, `middle_ids`, `meshes` 등)가 대체된 레이어나 메시를 가리키면, 오류를 반환하고 그것을 대체한 현재 ID를 나열합니다(여러 번 분할이면 단계별로 펼침). `source_get_components`도 같습니다. `layer_restore`는 원 레이어를 되돌릴 수 없습니다(`deletedLayerIds`에 없음).

**호환**: 이전의 `canvas_source_partition`, `canvas_depth_split`은 원래 규칙으로 재생하고, 첫 편집 때 고정됩니다([구버전 재생](#구버전-재생) 참조). `LegacySplitReplayTest`는 이전 버전이 저장한 프로젝트로 각 히스토리 노드를 재생한 뒤의 IR 해시가 이전 버전과 같은지 대조합니다. 이전 프로젝트의 소프트 삭제한 원 레이어는 여전히 복구할 수 있고, 이전 프로젝트의 새 분할은 실체화 규칙으로 합니다. CMO3를 가져온 모델의 분할은 여전히 이전 규칙을 씁니다(원 레이어 소프트 삭제).

### 부모가 더 이상 생성되지 않음

로그가 어떤 기록 전에 만든 디포머는, 그 기록까지 재생하면 다시 존재합니다. 그래서 기록의 부모가 재생 위치에서 없으면, 기초 생성이 더 이상 그것을 만들지 않는 경우뿐입니다. 분할 뒤에 생성 설정을 바꾼 것입니다(스켈레톤을 켜면 팔 늘어짐 Warp `DeformArmHang_L/R`을 더 이상 만들지 않고, 본이 팔을 인수). 이때 기록은 아래 규칙으로 재생하고, 저장한 기록은 다시 쓰지 않습니다. 규칙은 `VanishedParent`와 각 기록의 재생 구현이 담당하며, 결과는 결정적입니다.

- **버전 1 파츠**(`ArtPrimitiveReplay.rehome`, 구버전 재생): 파츠는 자기가 대체한 메시(`replace`의 키)가 현재 있는 부모로 다시 겁니다. 그 메시 자체가 더 이른 기록의 파츠이고, 스켈레톤 베이크가 디코딩할 때 기초 Rig에 아직 없으면(`skinnable`의 `earlier`), 그 기록을 따라 그것이 대체한 메시를 앞으로 찾습니다. 위치는 “기록 정점 → 캔버스 텍스처 좌표”의 최소제곱 아핀 피팅(규칙적인 정지 메시나 강체 프레임에서는 정확)으로 기본 포즈의 캔버스 위치를 복원한 뒤, 새 부모 공간으로 역을 구합니다. 키폼과 블렌드 셰이프의 변위는 피팅의 선형 부분을 거쳐 캔버스 변위로 바꾼 뒤 마찬가지로 넣습니다. 대체된 메시를 찾지 못하면 이전과 같이 `Art primitive parent is missing`을 보고합니다.
- **`canvas_mesh_rebuild`**(`RasterMeshJournal.replay`): 메시는 이미 다른 부모 공간에 있어 기하 지문을 다시 대조할 수 없고, 정점 수만 대조합니다(`glue_map` 길이). 기록의 `points`와 `previous_parent_points`는 같은 아핀 피팅으로 메시의 현재 부모 공간으로 옮깁니다.
- **구조 편집 `bind`(메시)와 `move`(디포머)**(`RigStructureEdits.replay`): 대상 부모가 없으면 그 항은 적용되지 않고, 객체는 원래 자리에 남습니다. 새로 제출하는 편집은 `RigStructureEdits.apply`를 타고, 부모가 없으면 여전히 오류를 냅니다.
- **`canvas_mesh_create`**에는 따라갈 대체 메시가 없어, 부모가 없으면 이전과 같이 오류를 냅니다.

본에 바인딩되었지만 로그가 본이 아닌 디포머 아래에 건 메시는 베이크에서 다시 걸지 않고, 로그 뒤에 스키닝합니다. [로그가 배치한 메시](#로그가-배치한-메시)를 참조합니다.

### 로그가 배치한 메시

스켈레톤 베이크는 로그 전에 본에 바인딩된 메시를 본의 회전 디포머 아래로 다시 걸고, 위치와 키폼을 모두 본 공간으로 바꿉니다. 로그가 그 뒤에 이 메시를 스스로 배치하면—구조 편집 `bind`가 본이 아닌 디포머로, `warp` 기록이 새 Warp로 감싸면—이 기록은 메시의 국소 좌표를 유지합니다(`space=local`, `fit_local`). 본 공간의 메시에서는 올바르게 재생할 수 없습니다. 이런 메시는 `SkeletonCanvasSkin.placedByRecords`가 스켈레톤 정의와 편집에서 정합니다(먼저 구버전 `structureEdits` / `warpEdits`, 그다음 순서대로 로그. 메시의 마지막 `bind`가 본 디포머이면 세지 않음). 아래 규칙으로 처리합니다. 로그에 체크포인트가 있으면, 스키닝 단계는 체크포인트 저작 상태 Rig에서 그 사지의 어떤 본에도 이끌리지 않는 바인딩 메시도 포함합니다(`SkeletonCanvasSkin.placed` / `unskinned`, 체크포인트 뒤에 본 디포머로 `bind`한 것은 제외). 기록, 재생성 병합, 이전 버전 중 무엇이 거기에 두었는지는 상관없습니다. 베이크는 기록으로만 결정합니다. 고정 Rig · 구조 인수와 병합 충실성을 참조합니다.

- **베이크**(`SkeletonRig.apply`의 `canvasSkinned`): 사지의 다른 메시와 같이 관절을 세분하고, 같은 사지의 파츠와 용접하며(`GlueSkel__` Glue), 블렌드 셰이프 계획에 넣습니다. 그러나 다시 걸지 않고, 스키닝 키폼을 쓰지 않으며, 생성된 부모 아래에 남습니다. 다시 걸었다면 걸려야 할 본의 디포머는 평소처럼 남습니다(메시가 없다고 잘라 내거나 접지 않음). 캔버스에서 본 체인 전체를 따라 움직이므로, 계획은 체인의 모든 본 파라미터를 서로 결합된 것으로 봅니다(블렌드 셰이프로 만들지 않음). 나머지 메시의 경로는 변하지 않습니다. 로그가 배치한 메시가 없는 프로젝트는 베이크와 내보내기가 바이트 단위로 변하지 않습니다(`ExportGoldenTool`).
- **스키닝**(생성 노드 `skeleton.skin`, 로그 뒤, 스윙과 시뮬레이션 앞): 본의 작용은 캔버스 공간에 정의됩니다. 어떤 포즈에서 각 정점은 가중치(`SkeletonWeights` / `SkeletonManualWeights`)에 따라 본의 캔버스 변환(`SkeletonPoseSolver.frames`: 디포머가 있는 본은 디포머를 읽고, 나머지는 부모 본의 회전을 따름)에 이끌리고, 베이크와 같이 관절 템플릿, ARAP, 표면 평활로 보정합니다(`SkeletonRig.corrected`). 얻은 캔버스 위치는 메시의 최종 부모 체인이 같은 포즈에서 가지는 역매핑으로 부모 국소 공간에 넣고, 정지와의 차이를 메시가 본 파라미터에서 가지는 키폼으로 씁니다. 블렌드 셰이프 계열 파라미터(계획이 독립으로 본 본, 스켈레톤 포즈)는 블렌드 셰이프로 씁니다. 축은 그 메시를 움직이는 사지 본, 그 위쪽 몸 반쪽, 스켈레톤 포즈 파라미터이며, 베이크와 같은 허용 오차로 가장 적은 키를 고릅니다. 메시는 다시 걸지 않고, 로그의 배치는 그대로입니다. 위에 사용자 Warp가 몇 층이든 같습니다.
- **이미 있는 키폼**: 스키닝 키폼은 메시의 원래 키폼과 더합니다(파라미터를 공유하면 양쪽 키를 병합). 이 칸에 대한 캔버스 편집은 `GeneratedOverrides.capture`가 `skeleton.skin`의 `generated_override`로 쓰고, 재생할 때 삼자 병합합니다. 로그가 이미 메시에 같은 파라미터의 블렌드 셰이프를 줬으면 사용자 데이터로 보고 그대로 둡니다.
- **Glue**: 다른 스키닝 메시와 짝인 정점은 각 키에서 같은 캔버스 목표를 가집니다. 다른 쪽이 베이크 스키닝(본 아래)이면 Rig가 평가한 위치를 씁니다. 양쪽이 모두 이 단계에서 스키닝되면 Glue 양쪽 가중치로 만남점을 잡고, 둘이 공유 파라미터에서 같은 키를 쓰게 합니다. 이 정점들은 ARAP에서 고정점이며, 메시는 이음매까지 매끄럽게 전환합니다.
- **토폴로지**: 관절 세분은 로그 전에 일어나고, 이후의 정점별 기록은 세분된 메시를 대상으로 합니다. 로그에서 그 메시를 대상으로 한 정점별 기록(`canvas_geometry`, `vertex_group_put`, 메시의 `generated_override`)의 정점 수가 세분 전 정점 수와 같으면(그 메시를 세분하지 않는 버전에서 씀), 그 메시는 세분하지 않습니다(`SkeletonCanvasSkin.lockedTopology`, 손 토폴로지와 같음). 이 기록이 어긋나지 않게 하기 위해서입니다. 관절 본에 바인딩된 다른 메시도, 이런 기록이 모두 세분 전 정점 수로 쓰였으면(스켈레톤 전에 쓴 정점 그룹 등) 마찬가지로 세분하지 않습니다. 세분 후 정점 수로 쓴 기록이 있으면 평소처럼 세분합니다.
- **비용과 캐시**: 사지 뿌리 본과 위쪽 몸 반쪽은 사지 전체를 강체로 이끌 뿐이므로, 풀 때는 먼저 그것들을 빼고 그 변환을 나중에 씌웁니다. 필요한 풀이 수는 사지 내부 관절의 키에만 의존합니다. 출력은 `GeneratorReuse`가 읽은 내용으로 재사용합니다. 스켈레톤 캐시 키는 이런 메시가 있으면 그 집합을 포함합니다.

### 버전 2 기록

버전 1은 원 레이어를 나누던 순간의 저작 상태 전체를 파츠에 스냅샷합니다. 기초 생성은 여전히 원 레이어(승객)만 보고 파츠는 보지 않으며, 생성기가 메시에 쓴 키폼(눈 개폐, 스켈레톤 스키닝 등)도 기록에 얼어, 이후 얼굴 설정, 선 자세, 스켈레톤 변화가 파츠에 닿지 않습니다. 버전 2는 파츠가 기초 생성에 참여하게 합니다. 생성된 원 메시의 분할은 모두 버전 2를 쓰며, 스위치는 없습니다. 지금의 버전 2 기록은 선언일 뿐입니다(`authored`가 비어 있고, 사용자 데이터는 그 뒤 체크포인트에 있습니다. [분할은 곧 재생성](#분할-실체화-아트-프리미티브-기록-art_primitive) 참조). 이전 버전이 쓴 버전 2 기록은 `authored`에 저작 데이터를 가지며, 아래의 잔차, 두 번 캡처, 승객 관용, 재생은 그것들을 설명하고, [구버전 재생](#구버전-재생)에서만 씁니다.

**해석된 레이어 집합**(`core/PrimitiveResolution`): 생성 레이어에서 v2 기록이 대체한 레이어를 빼고, v2 파츠 레이어를 더합니다. 앵커, 얼굴 Rig, 머리 공간, 프레임, 선 자세와 다리, 몸 프레임, 디포머(쌍 Warp, 팔 늘어짐 Warp 포함), 흰자, 마스크 출처인 메시, 입술의 얼굴 Rig, 스켈레톤 바인딩은 이 집합만 읽습니다. 미리보기 분석도 이것과 같습니다. 파츠 픽셀은 현재 픽셀을 `source_bounds`로 투명을 보탠 것이고, 메시는 여전히 기록 값을 씁니다. 분류는 `layerOverrides`를 씁니다(분할할 때 상속). 없으면 기록의 `classification`을 씁니다. 분할 기준선(`splitBaselineLayerIds`)이 있는 컨텍스트도 마찬가지로 파츠를 넣고 대체된 레이어를 뺍니다. 디포머를 유지하는 구축(`buildPreservingDeformers`, 페인팅 제출용)도 같습니다.

**승객**: 대체된 레이어는 여전히 원래 위치에서 생성됩니다(태그 개수가 결정하는 ID와 기본 그리기 순서는 변하지 않음). 자기 얼린 픽셀과 레이어별 키폼만 쓰고, 위 집계 단계를 읽지만 되먹이지 않으며, 본에 바인딩되지 않습니다. 기록 이전의 로그 항목이 주소를 찾도록 존재할 뿐이며, 기록을 재생할 때 삭제됩니다.

**적치**: 파츠는 기초 Rig에서 기록의 정지 캔버스 메시로 생성합니다(다시 메시를 만들지 않음. 텍스처 좌표는 캔버스 단위). 생성 키폼, 채널, 마스크, 파츠 트리 위치, 스켈레톤 스키닝을 얻습니다. UV 바인딩 뒤 전체를 `BuiltRig.primitiveSkins`로 옮깁니다(용접 Glue, 생성 경로, 파츠를 가리키는 생성 마스크, 파츠 슬롯, 소유, 지연 부모, 중립 경계와 함께). 기초 Rig에서 파츠를 가리키는 참조는 그 승객으로 다시 쓰므로, 기록 이전에 보이는 것은 “분할 전” Rig입니다. `BuiltRig.resolvedPuppet()`은 승객을 빼고 파츠를 넣습니다. 생성 이전(`RigGenerationMigration.generatedRig`)의 previous / desired가 이것으로 비교하므로, 얼굴 설정, 분류 등의 변화도 마찬가지로 파츠에 도달합니다.

**기록 필드**(`v: 2`, 나머지 최상위 필드는 버전 1과 같음): 각 파츠에는 `id`, `layer_id`, `source_id`, `source_bounds`, `neutral_bounds`, `name`, `classification`, `mesh{canvas_positions, triangles, canvas_uvs}`가 있습니다(정지 캔버스 메시. 파츠가 아직 원본의 생성 부모 아래에 있으면 기초 Rig의 생성 디포머로 환산하고, 로그가 부모 체인을 편집한 것은 재생할 때 한 번만 작용. 로그가 부모를 바꿨으면 저작 상태 부모를 거침). `parent`, `part`가 비어 있으면 생성 결과를 쓴다는 뜻이며, 로그 편집이 원 레이어를 바꿨을 때만 씁니다. 재질 필드는 생성 값과 다를 때만 씁니다. `masks`가 비어 있으면 생성 마스크를 씁니다. `parameters`는 사용자 축만 포함합니다. `geometry_residual`, `channels_residual`. `blends`, `paths`, `vertex_groups`는 사용자 데이터만 포함합니다(스켈레톤 포즈 블렌드 셰이프와 생성 경로는 제외). `fixed_topology`(파츠에 정점별 사용자 데이터가 있으면 참. 스켈레톤은 관절 행을 넣을 수 없음). `frozen_axes`. `glues`는 사용자 Glue만 포함합니다(`GlueSkel__` 용접은 제외).

**잔차**: 캡처할 때 A는 원 레이어의 저작 상태, G는 기초 생성 출력(스켈레톤 포함)입니다. 잔차 A − G는 분할의 정점 출처를 거쳐 파츠 정점으로 옮깁니다. 키에 생성기 축이 기본값이 아닌 칸은 기록 바로 뒤의 `generated_override`로 씁니다(`base`는 후보 기초 파츠의 칸, `points`는 `base`에 잔차를 더한 것, `generator`는 그 축을 소유한 노드). 나머지는 `geometry_residual` / `channels_residual`에 씁니다. 재생할 때 파츠 메시 = 적치한 생성 메시 ⊕ 잔차이며, 덮어쓰기는 평소처럼 모든 생성기 뒤에 삼자 병합합니다. 기초가 키폼을 만들지 않는 파츠(영 메시: 입술 띠의 슬라이스, 지연 부모의 파츠)에는 더할 생성 운동이 없어, 잔차는 저작 상태의 모든 키폼을 씁니다(A − 0). 같은 기록의 입 파츠는 모든 입 파츠를 합친 개구로 입 모양을 생성합니다. 각자 경계로 하면 반쪽 입이 각자 입 전체로 벌어져 절개에서 찢어집니다.

**재생**: 승객을 지우고, 적치한 파츠를 놓습니다(캔버스 텍스처 좌표는 현재 텍스처 아틀라스로 환산, 지연 부모는 그 부모 공간으로 환산). 생성 마스크와 파츠 슬롯을 복구하고, 양 끝이 있으면 용접을 넣으며, 생성 경로를 쓰고, 잔차와 저작 층을 더합니다. 적치 토폴로지와 기록이 다르면(스켈레톤이 관절 행을 추가, 이후 메시 재구축), 정점별 데이터는 캔버스 텍스처 좌표로 새 메시에 이전합니다.

**두 번 캡처와 가드**(이전 버전): 분할은 먼저 기초 필드를 쓰고, 후보 기초가 파츠를 만든 뒤 그것과 대조해 잔차와 덮어쓰기를 씁니다. 후보 기초가 이미 있는 로그가 참조하는 객체를 모두 생성하고 로그 전체가 그 위에서 재생될 때만 버전 2를 쓰며, 그렇지 않으면 버전 1로 되돌리고 `v2_fallback {reason, detail}`을 붙입니다. 지금의 분할은 병합으로 대신하며, 되돌림은 없습니다. 이전 기록의 `v2_fallback`은 역사로만 남습니다.

**승객 관용**: 기록 이전의 항목이, 자기가 참조하는 메시가 모두 이후 v2 기록의 승객이라서만 실패하면, 무조작으로 재생하고 설명 한 줄을 남깁니다(`SupersededEntryNote`: 로그 번호, `op`, 대상, 이유). 다른 실패는 평소처럼 오류를 냅니다. 설명은 재생 검사점과 함께 저장되고, 검사점에서 이어 재생해도 완전하며, `BuiltRig.supersededEntryNotes`를 거쳐 `workspace_inspect`의 `quality.overrides`에 들어갑니다(`SUPERSEDED_ENTRY_SKIPPED`, info, 막지 않음).

**다시 분할**: 파츠는 다시 분할할 수 있으며, 일반 레이어를 나누는 것과 같습니다. G와 M의 파츠를 각자 자른 뒤 다시 병합합니다. 더 이른 버전 1 기록이 v2 파츠를 대체하면, 그 파츠는 투명 자리 표시와 고정 메시로 해석된 집합에 남고, 기초 프레임은 변하지 않습니다.

**파츠 이후의 편집**: 페인팅은 픽셀만 바꾸고, 파츠 메시는 기록 값을 유지합니다. `rebuild_mesh` 페인팅이나 레이어별 메시 설정 수정은 기록 뒤에 `canvas_mesh_rebuild`를 추가하고, 키폼과 바인딩을 이전합니다.

**소유와 캐시**: `DocumentGenerators`의 문서 입력 `document:primitives`(v2 기록의 고정 입력)를 풋프린트, 프레임, 메시, 스켈레톤이 읽습니다. 파츠의 `keyform:mesh:<部件>@<参数>`는 적치의 소유에 따라 `mesh:<图层>` / `rig.meshes`(특징 축) 또는 `skeleton`(본 축)에 속합니다. `GeneratedOverrides.capture`는 이것으로 이후 이 칸에 대한 편집을 덮어쓰기로 씁니다. 단계 캐시와 바인딩 캐시의 키에는 v2 기록의 고정 입력 요약이 들어갑니다.

**호환**: 이전 버전이 쓴 버전 1과 저작 데이터가 있는 버전 2 기록은, 그 뒤에 체크포인트가 없으면 예전처럼 재생합니다(스켈레톤 스키닝과 스스로 디코딩 포함). 읽을 때 다시 쓰지 않고, 첫 편집 때 고정됩니다([구버전 재생](#구버전-재생) 참조). v2 기록이 없는 문서는 원래 코드 경로를 탑니다(`ExportGoldenTool` 바이트 단위 일치). v1과 v2 기록은 섞을 수 있고, v2 기록이 v1 파츠를 대체하면 그것을 지웁니다. 선언형 기록이 재생될 때(예를 들어 체크포인트가 없는 구축)는 생성된 파츠로 놓습니다. 이전 버전의 명시적 업그레이드 명령(`source_upgrade_split_records`)은 제거되었습니다.

**알려진 제한**:

- 분할된 입의 생성 입술은 여전히 대체된 입(승객의 얼린 픽셀)에서 가져오며, 파츠 현재 픽셀의 합성이 아닙니다. 분할할 때는 둘이 같습니다. 그 뒤 파츠에 페인팅하면 입술 텍스처는 따라가지 않습니다(일반 입의 입술 텍스처도 메시 입력에서 가져오며, 메시를 다시 만들기 전에는 따라가지 않음). 파츠 메시를 재구축해도 입술을 다시 생성하지 않습니다.
- `frozen_axes`: 쓰는 쪽은 항상 빈 값을 쓰므로, 지금은 나타나지 않습니다. 기초 생성이 비어 있지 않은 값을 읽으면, 생성 메시의 축에 얼린 축이 있을 때 그 파츠의 생성 메시 전체를 0으로 만들고 저작 데이터만 남깁니다. 구버전 재생은 비어 있지 않은 값을 만나면 바로 오류를 냅니다(지원하지 않음).
- 파츠 메시를 재구축한 뒤, 그 생성 칸을 대상으로 한 `generated_override`는 이전하지 않으며, 형태가 맞지 않으면 고립으로 보고합니다.
- 입 윤곽이 켜져 있으면, 입 파츠의 고정 메시는 원본의 윤곽 메시이며, 풋프린트는 원본의 래스터 메시와 약간 다릅니다. 입 상자가 정한 생성 입술의 정지 위치는 약 0.4 px 차이 납니다. 파츠 자체의 개구 형태에는 윤곽 기여가 없습니다(약 0.13 px).
- v2 파츠는 프레임 생성에 참여합니다. 고정 메시의 캔버스 위치를 부모로 왕복하면 부동소수점 반올림이 있고, 나누지 않은 메시의 국소 좌표와 프레임 제어점은 ulp 몇 개 차이 날 수 있습니다(월드 좌표 < 1e-4 px). 버전 1은 비트 단위로 변하지 않습니다.
- 원 메시의 토폴로지를 손으로 바꿨으면, 파츠는 사용자 토폴로지로 사용자 객체에 남고, 생성기 이후의 변화는 이 파츠의 기하에 더 이상 닿지 않습니다.

**테스트**: `PrimitiveResolutionTest`(손으로 쓴 v2 기록의 기초 생성), `ArtPrimitiveRecordV2Test`(구버전 기록의 인코딩, 잔차, 재생, 승객 관용, 검사점에서 이어 재생할 때의 설명. 인코더는 테스트의 `LegacyArtPrimitiveV2`), `SplitPartsCheckpointTest`(분할의 체크포인트, 쌍 Warp, 스켈레톤 스키닝). tml에서의 분할 효과는 `ArtPrimitiveV2VisualTool`로 눈으로 확인합니다(나누지 않은 것과 나눈 것의 각 포즈 차이. 이전의 버전 2 기록과 같음).

## 구버전 재생

이전 버전은 일부 편집을 기초 Rig 위에서 재생해야 하는 기록으로 썼습니다. 분할의 `art_primitive`(버전 1, 그리고 저작 데이터가 있는 버전 2), 생성 이전(`rig_generation_transition`, `rig_generation_frames`, `rig_generation_scaffold`, `rig_mesh_activation`), 이전의 `canvas_source_partition` / `canvas_depth_split`, 그리고 로그 이전의 구형식 정적 필드입니다. 생성된 모델은 더 이상 이것들을 쓰지 않습니다. CMO3를 가져온 모델에는 병합할 생성 결과가 없어, 여전히 이전 기록과 이전 분할을 쓰지만, 그것들을 쓴 제출은 바로 그 뒤에 가져온 모델의 체크포인트를 씁니다(`WorkspacePreviewBuilder.importedRecordsCheckpointed`). 기록은 이번 구축에서만 재생되고, 이후 구축, 열기, 실행 취소는 모두 체크포인트에서 시작합니다. 그래서 `core.legacy`는 두 곳에서만 돕니다. 한 번도 고정하지 않은 이전 로그를 처음 편집하기 전, 그리고 가져온 모델이 이런 기록을 쓰는 그 한 번의 제출입니다.

- **한 번만 고정**: 로그가 마지막 체크포인트 뒤에 여전히 이런 기록이 있으면(체크포인트가 없으면 구형식 정적 필드도 포함, `RigEditOverlay.replaysLegacy`), 그것을 잇는 첫 편집은 먼저 원래 로그 끝, 새 항목 앞에 현재 저작 상태 Rig의 체크포인트를 씁니다(`WorkspacePreviewBuilder`). 생성 스냅샷이 있으면 함께 저장합니다. 이 기록은 이로써 마지막으로 한 번 재생되고, 이후 구축은 모두 체크포인트에서 시작합니다. 열기, 히스토리 전환, 저장은 로그를 다시 쓰지 않으며, 이전 리비전은 기록대로 구축합니다.
- **코드**: 이 경로와 가져온 모델에서만 쓰는 부분은 `core.legacy`에 있습니다. `ArtPrimitiveReplay`(버전 1과 저작 데이터가 있는 버전 2 기록의 재생, 스켈레톤 베이크 전에 버전 1 파츠 디코딩, 재생성 병합 때 버전 1 파츠를 넣기), `StubTolerance`와 `SupersededEntryNote`(승객 관용), `VanishedParent`, 그리고 생성 이전의 쓰기와 재생(`RigGenerationMigration`, `RigGenerationJournal`, `RigGenerationFrames`, `RigGenerationScaffold`, `RigMeshActivation`, `RigGenerationResidual`, `RigGenerationTextures`). `ArtPrimitiveJournal`은 기록 형식과 문서 조회(대체 관계, 소유 레이어, 텍스처 커버)를 유지합니다. 편집이 생성 결과를 바꾸는지 판단하는 `RigGenerationChange`는 병합 경로의 트리거 조건이며 `core`에 있습니다. 병합(`RigRegenerationCheckpoint`)은 여전히 `core.legacy`에서 이전 이전 기록이 디포머에 붙인 이름과 버전 1 파츠를 읽어, 이전 로그의 G와 G′를 같은 방식으로 놓습니다. 이것은 호환 읽기이며, 새 기능과 함께 확장하지 않습니다(`LegacyReplayBoundaryTest`가 그것을 참조할 수 있는 파일을 고정).
- **잠금**: `LegacySplitReplayTest`는 이전 버전이 저장한 프로젝트로, 각 히스토리 노드를 기록대로 구축한 IR 해시를 대조합니다.

## 이후

- 분류 수정의 남은 시간은 분석에 있습니다. 생성된 모델은 병합으로 바꾼 뒤 생성 이전을 타지 않고, 남은 것은 CMO3를 가져온 모델의 이전과 분할 기준선이 새 래스터에 `CharacterAnalyzer.analyze`를 반복하는 것입니다(레이어별 분류 약 0.5 s/회). 레이어 메타데이터와 래스터 요약으로 분류 결과를 캐시할 수 있습니다.
- 블렌드 셰이프로 쓰는 시뮬레이션 키폼의 덮어쓰기. 덮어쓰기 보고를 통합 품질 검사 프레임워크에 넣은 뒤, 그 규칙 레지스트리와 펜스를 쓰도록 바꿉니다.
- 채널 덮어쓰기의 알려진 제한(지금은 로그 뒤에 채널에 키를 넣는 생성기가 없어 이 경로는 발동하지 않습니다. 첫 생성기를 넣기 전에 처리):
  - 키폼 `set`이 생성 채널 트랙의 정지 칸에 쓰일 때(키에서 생성기 파라미터가 기본값), `journalOnly`는 기하 편집에서만 생성기가 기본값에 둔 축을 벗겨 냅니다. 채널 편집의 키는 여전히 이 축을 가지므로, 로그를 재생할 때 사용자 자신의 트랙에 이 축이 생깁니다.
  - 채널 덮어쓰기를 넣기 전의 버전은 각 덮어쓰기를 정점이나 제어점 좌표로 읽어, 수치 개수가 짝수이기를 요구합니다. 스칼라(1개)와 색(3개) 덮어쓰기는 모두 “Invalid override form”을 보고하고, 채널 덮어쓰기가 있는 프로젝트는 이전 버전에서 재생에 실패합니다.
- 프로젝트를 열 때 고정 결과를 직접 읽기: 저작 상태 Rig의 저장과 읽기, 체크포인트, 재생성 병합, 시험 실행은 이미 구현되었습니다(고정 Rig · 구현 진행). CMO3를 가져온 모델은 가져오기 기준선에서 체크포인트부터 재생하며, 저작 상태 Rig만으로 따로 구축하지 않습니다.

## 내부 조형 생성기

선택적 `interiorEffect:<id>` 노드는 저작 로그 뒤, 생성 결과 덮어쓰기 앞에 돕니다. `NativeInteriorEffect`는 `rigEdits.interiorEffects`에 레시피, 압축 네이티브 blend 필드, 물리 그룹을 저장합니다. 이미 있는 입력 파라미터는 읽기 전용이고, 생성 파라미터와 대상 Mesh 축은 소유자가 하나입니다. 레시피 수정, 추가·삭제, 스위치는 모두 무효화 전파에 참여합니다. 메시, 소재, 바인딩이 맞지 않으면 레시피는 남기고 만료된 정점은 건너뜁니다. 네이티브 UI/MCP는 `interior_put`을 공유하고, 임시 시험 움직임은 문서에 들어가지 않습니다. 끄거나 무효가 된 효과의 쓰이지 않는 자체 파라미터는 내보내기 사본에서만 정리합니다. 발행하지 않은 밀집 실험은 호환을 남기지 않습니다. 삭제는 `interior_delete`로 같은 재생 경로에 들어갑니다. 내부 조형을 참조합니다.
