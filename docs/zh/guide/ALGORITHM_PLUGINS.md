# 算法插件

> **单版本与共享运行时架构**：所有 44 个绑定修改器已统一为规范版本 `version = 1`（`rig.scaffold` 保留 `v1` 与 `v2`）。`:algorithms:binding` 通过 `pluginPackages` 任务产出单一共享 `shared/runtime.jar`（入口 `ExpressionWorker`）与 46 份轻量 `<slug>/plugin.json` 清单；宿主按命令与文件摘要池化常驻工作进程并缓存输入/上下文资源哈希。外部插件可继续以任意语言实现 `protocol: 1` 工作进程协议。

预设中的每个修改器通过算法接口求值。内置算法在应用进程内执行；外部算法是常驻工作进程，可使用 Python、Kotlin、Rust、C、C++ 或 C#。安装包可以包含多个算法。

内置算法按类型和算法修订号分别列入插件目录，各项独立启停；摆动、模拟、物理、动作、表情开关、眉眼透发、皮肤裁切及绑定结构具有独立的 Kotlin 实现入口。新建实例记录 `builtin.*` 包身份、完整版本和内容摘要；已独立打包的算法覆盖完整包，其余入口仍使用字节码摘要。摘要不匹配时显示不可用，不自动替换。历史工程中没有插件引用的内置实例继续按原算法修订读取，不在打开时重写历史。`id=builtin,digest=builtin` 仅作为旧接口的整体启停兼容入口。

外部包可以在 `dependencies` 中引用 `plugin_list` 返回的内置包 ID 与版本；安装时锁定相同的内容摘要，内置项被停用或对应版本缺失时依赖包也不可用。`builtin` 整体身份保留；`builtin.*` 安装包必须声明与包 ID 和算法修订匹配的稳定类型别名，供历史内置算法恢复。启停状态保存在偏好中，求值从内存快照读取，不逐项访问系统偏好。

应用为 49 种修改器各随附至少一个可独立执行的包。历史实例继续按锁定修订重放。部分推荐预设仍使用 v1，从宿主生成模板提取结果；一些较新版本也仍接收宿主生成的前置运动或局部前后投影。可独立执行的包及没有整模模板调用，都不能单独证明原始源输入边界已经完成迁移。

Gradle 的 `processResources` 从 `bundledAlgorithm` 资源声明生成内置包索引。新增内置包时在构建中声明其任务和资源目录，应用从生成的索引读取包清单。已有包的清单和载荷仍按原始字节计算摘要。

对于拟合眉会改变其他网格坐标框的双眼素材，新建现代预设时会为头部、眼部和眉部一起选择兼容版本。拟合眉、眉形、眉睑联动、眨眼带眉和回弹随共享框架组合求值。笑眼、睁大、视线、情绪、高光、余震和虹膜挤压也有对应版本。眼睑淡出沿用 v3。已保存的实例按工程内锁定的算法修订与包摘要重放。

其中物理组实现已迁到 `:algorithms:physics`：`PendulumAlgorithm` 直接实现公共求值接口，配置解析、物理组转换和输出冲突检查均在该模块完成。算法仅使用 `algorithm-api`，应用注册入口只委托调用；普通物理导出和其他生成器复用同一转换实现。另由 `algorithm-worker` 提供工作进程入口，`./gradlew :algorithms:physics:pluginPackage` 在 `algorithms/physics/build/plugin` 生成独立安装目录（`plugin.json` 与携带依赖的 `algorithm.jar`），可交给 `plugin_install`。包 ID 为 `builtin.70687973696373.v1`，入口为该命名空间下的 `/pendulum`，`aliases: ["physics"]` 保留工程中的类型、算法修订和输出 ID。

应用携带并保留物理组、动作、摆动、烘焙模拟、表情开关、眉眼透发、皮肤裁切及绑定结构的完整安装包，新实例固定整个包的内容摘要。与当前包完全匹配时进程内执行；旧包引用只有在对应内容已安装时才通过工作进程执行，不回退到当前实现。旧版本安装包可以卸载与重装；当前应用自带版本只能启停。迁移之前仅记录入口字节码摘要的开发期引用不会被改写，也不能用新包替代；找不到原内容时仍报告不可用。

动作实现已迁到 `:algorithms:motion`，包 ID 为 `builtin.6d6f74696f6e.v1`，入口为 `/clip`，稳定别名为 `motion`。`MotionData` 提供原格式的数据模型、JSON 读写和曲线转换，应用编辑器与独立工作进程共用此实现；模块不依赖播放会话、UI 或 Umamo。构建命令为 `./gradlew :algorithms:motion:pluginPackage`，输出目录为 `algorithms/motion/build/plugin`。

摆动实现位于 `:algorithms:swing`，包 ID 为 `builtin.7377696e67.v1`，入口 `/sway`，稳定别名 `swing`。网格包裹、关键形求值和摆动物理组均在算法模块完成，不调用工程或历史接口。此模块使用 GPL Umamo 引擎与 Cubism 格式转换器，属于 GPL 算法，不能作为 MIT API／格式模块分发；不包含 Cubism 专有 SDK。构建命令为 `./gradlew :algorithms:swing:pluginPackage`。

烘焙模拟求值位于 `:algorithms:simulation`，包 ID 为 `builtin.73696d756c6174696f6e.v1`，入口 `/baked`，稳定别名 `simulation`。输入包含原烘焙结果和捕获的自动权重；插件检查烘焙与上游输入是否匹配，再写回权重、模式关键形和物理组。既有作者权重优先，不允许通过缺失或过期烘焙生成残缺结果。数值烘焙仍由原流程执行，此迁移不改变求解器。此模块同样依赖 GPL 引擎；构建命令为 `./gradlew :algorithms:simulation:pluginPackage`。

算法清单可声明 `derivedOutputs`，用于保留原有确定性对象名称。每条规则包含 `kind`、`localName`、`prefix`、`suffixes`（默认 `[""]`）和 `numbered`（默认 `false`）。宿主只接受 `prefix + instance.outputId(localName) + suffix`；开启 `numbered` 时另外允许 `_2` 到 `_10000` 的规范十进制后缀。规则不能跨对象种类或超出声明写入范围，不接受任意正则表达式。摆动使用 `Warp_Swing_` 和 `PhysicsSwing_` 规则，保持原工程对象 ID。

拟合脸 v2、拟合眼 v3 和拟合嘴 v2 可在添加面板中按版本选用。拟合脸 v2 要求共享中性脚手架 v2 的完整目标集，拟合眼 v3 和拟合嘴 v2 分别要求可迁移的眼部脚手架和中性嘴部脚手架。拟合眼 v4 还支持共享脚手架 v2 的完整目标集与拟合脸 v1 的组合，其中若有旧版身体，需使用 v1。v4 会调整眼部所需的头部坐标框架，无法保留作者几何或引用时会拒绝求值。从源素材新建带预设的工程时，若使用完整共享脚手架 v2 且插件可用，会采用旧版身体 v2。也可按版本手动选择旧版身体 v2。它从源测量计算身体运动和头部俯仰，要求带源数据的脚手架。共享脚手架须使用完整目标集。嘴部描边 v2 需要同一静态脚手架上的旧版嘴 v2，且前面没有其他活动绑定。虹膜挤压 v2 也可按版本选用，需要拟合眼和与源测量一致的虹膜拓扑。虹膜挤压 v3 支持拟合头转，也能接在包含眼部余震 v3 的独立眼睑序列之后。v4 还支持保留高光 v3 写入头转载体的形变。虹膜拓扑已修改时请使用 v1。工程保存稳定类型和所选安装包，后续修改器仍可按原类型查找前置项。

旧版眼部 v2 可显式选择，要求 v2 源脚手架的完整目标集。旧版风格预设在未经编辑、默认调校并使用普通头转的源素材上选用 v2。拟合头转或已经修改眼部拓扑时请选择 v1。

拟合眉 v2 可在添加面板中按版本选用。它要求共享 v2 脚手架，支持已验证的身体、头转和眼部前置版本。推荐预设使用拟合眉 v1。

拟合眉 v3 可在同一共享脚手架上的拟合脸 v3 之后选用。已对照搭配拟合眼 v2 和 v5 的完整推荐模型，其中 v2 组合还验证了安装后拟合眉 JVM 求值。拟合嘴的兼容路径仍可能请求拟合眉模板。

旧版眉 v2 可显式选择，支持带源数据的共享脚手架以及兼容的普通头转或拟合头转。已重挂接眉部父分支或拟合关键形超出网格预算时使用 v1。

旧版脸 v2 也可显式选择。它从源测量计算头转，要求带源数据的共享脚手架 v2 和完整目标集，支持使用同一脚手架的旧版身体 v1 或 v2 前置。新建源工程选择旧版预设时，满足源数据和目标要求且随附包可用便使用 v2。切换到内置预设会按同一规则创建新栈。已保存的实例按锁定版本重放。

景深头转 v2 可在添加面板中按版本选用。它需要带源数据的共享脚手架 v2 和旧版脸 v1 或 v2，可选身体 v1 或 v2。拟合脸与景深头转不能叠加。当前 v2 覆盖壳体转向。

拟合脸 v3 可在旧版身体 v1 或 v2 之后按版本选用。它沿用身体的俯仰调参，要求唯一的前置身体绑定与拟合脸使用同一套完整共享 v2 脚手架。现代预设仍使用拟合脸 v1，现有拟合眼路径会继续构建拟合脸模板。

拟合眼 v5 需要完整的共享 v2 脚手架、旧版身体 v1 或 v2，以及拟合脸 v1 或 v3。添加计划会列出需要补齐的前置绑定。现代预设仍使用拟合眼 v2，部分可选眼睑算法也依赖这一版本。

眼部睁大 v2 可按版本选用。它从源眼部测量和拟合眼绑定扩展开眼关键形与透明度。高光、眨眼带眉或睑耦合已在前面时，请继续使用 v1。

眼部睁大 v3 还可以在拟合头转后重新计算眼睑形变，包括闭眼线所需的头转变形器。需要移除已有变形器、重算其他网格共用的变形器，或源测量无法复现当前绑定时，仍可选择 v1。

眉形 v2 可按版本选用，需要共享脚手架 v2 和兼容的拟合眉。v3 支持拟合眉 v3、拟合眼 v5，并能接在虹膜挤压 v3 后。请先添加眉形，再添加其他眉部运动。已修改眉高关键形、拓扑或父框架时可继续使用 v1。

眉弹动 v2 添加回弹混合形和物理。它需要共享脚手架 v2、拟合眉 v1 或 v2，搭配拟合眼时需要拟合眼 v2。已编辑眉部几何、关键形或前面已有眼睑、眉部联动时，请使用 v1。

眉弹动 v3 可在兼容的眨眼带眉和眉睑联动之后按版本选用。它保留前置眉部框架和变形器，添加回弹形状与物理。v4 支持拟合眉 v3、拟合眼 v5、眨眼带眉 v3 和眉睑联动 v4。源框架已修改或无法复现前置变形器时，请使用 v1。

眨眼带眉 v2 将眉部动作与眨眼、睁大和笑眼联动，需要共享脚手架 v2 和保有原始高度、角度关键形的兼容拟合眉。v3 支持拟合眉 v3、拟合眼 v5，以及按推荐顺序排在前面的独立眼睑算法。已编辑眉部拓扑或这些关键形时，请使用 v1。

眉睑联动 v2 至 v4 可按版本选用。v2 和 v3 需要共享脚手架 v2、拟合眼 v2 和兼容的拟合眉。v3 支持拟合头转和前置视线联动，保留已有变形器 ID。v4 还支持拟合眼 v5、拟合眉 v3，并已验证 TML 预设中前置视线 v3 和眼部情绪的组合顺序。眼部拓扑或父框架已修改、前面已有颊睑联动或重复眉睑联动、使用独立深度转向时，请使用 v1。

笑眼 v2 需要共享脚手架 v2 和拟合眼 v2。它为原始眼睑添加笑眼关键形。已编辑眼睑几何或前面已有眼睑、眉部联动时，请使用 v1。

笑眼 v3 还支持拟合眼 v5，可以在拟合头转后重新计算眼睑形变，再接睁大眼 v3。需要移除已有变形器、重算其他网格共用的变形器，或源测量无法复现当前绑定时，仍可选择 v1。

眼部余震 v2 添加眼睑回弹和对应物理组，需要共享脚手架 v2 和兼容的拟合眼。v3 支持拟合眼 v5、前置视线 v3 和眼部情绪，并保留可重建的眼睑载体 ID。前面已有眉睑或嘴颊联动，或已编辑眼睑源框架、关键形时，请使用 v1。

视线带动眼睑 v2 从源眼睑生成共享和单眼视线联动，需要共享脚手架 v2 和兼容的拟合眼。v3 支持拟合头转后的拟合眼 v5，可接在笑眼和睁大 v3 之后，保留可以从源测量重建的头转载体。源眼睑几何已编辑，或前面已有余震、眉睑或嘴颊联动时，请使用 v1。

眼部情绪 v2 添加拟合的怒、哀和眯眼形变，需要共享脚手架 v2 和兼容的拟合眼。v3 可接在拟合眼 v5 和视线 v3 之后，保留可重建的载体 ID。已编辑眼睑几何、前置眉睑或嘴颊联动，或需要移除载体、修改共用载体时，请使用 v1。

眼部高光 v2 根据源测量、拟合眼和头转绑定计算视差与淡出。v3 支持拟合眼 v5、睁大 v3 和需要新建头转变形器的源素材。已重新挂接的高光仍用 v1。高光 v3 为同一载体添加形变时请选用虹膜挤压 v4。

嘴型元音 v2 添加五个标准元音参数及拟合形变，需要共享源脚手架和兼容的拟合嘴。有独立闭口图层、前置嘴部附加项，或嘴部拓扑、父框架已修改时，请使用 v1。

嘴部捕捉 v2 使用原始网格和兼容的拟合嘴生成捕捉关键形，支持前置嘴部描边或元音。捕捉 v3 还支持拟合嘴 v3、描边 v3 和元音 v4 的组合。使用独立闭嘴图、已编辑或降级的网格，或前置其他嘴部模块时，继续使用 v1。

拟合嘴 v3 可在共享源脚手架 v2 和拟合头转上显式选择。它从源嘴部测量求值，重算受嘴部地标影响的头部格点和局部形变。描边 v3、元音 v4、捕捉 v3 和下颌 v3 可与拟合嘴 v3 搭配。

嘴部描边 v3 可显式选择。它在共享源脚手架 v2 和拟合嘴上，从原始像素和嘴部测量生成描边，并重算受嘴部地标影响的头部格点、发束、头饰和颈部形变。改过的源网格或使用独立头转载体的组合仍可选择 v1。预设目前仍使用 v1，下游元音 v1 也仍会为前置描边构建兼容模板。

嘴型元音 v3 可接在同一共享脚手架的描边 v3 后，直接从源嘴部测量生成五个元音关键形。元音 v4 还支持拟合嘴 v3。独立闭嘴图、编辑过的源网格和其他先行嘴部模块仍可使用 v1。

下颌 v2 可显式选择。它使用共享 v2 源脚手架和兼容的拟合嘴，在脸、鼻子与嘴下方的面部细节上添加开口形变。普通和拟合头转、嘴部描边、元音和捕捉可以先于下颌。下颌 v3 使用拟合嘴 v3 的源测量。v4 还支持在拟合嘴 v3、捕捉 v3 和吐舌 v3 后运行。分层唇线或唇皮、修改过的目标网格和需要额外形变载体的组合继续使用 v1。

嘴颊联动 v4 支持拟合嘴 v3 和拟合眼 v2。它从源测量计算眼睑联动，并保留已验证的头转变形器。v5 在能重建原始几何和载体时也支持拟合眼 v5 和前置视线 v3。

双眼共享框架预设中，部分版本仍合并宿主生成的本项前后运动。在单眼开口链中，拟合眉 v4 使用前后投影，眉形 v6 与眨眼带眉 v6 接收前置眉头转形变，眉弹动 v7 接收生成的前置分支，嘴颊联动 v9 接收前置眼睑头转形变，嘴部弹性 v8 接收皮肤形变。眉睑 v8 的对应头转输入则是测量标量。这些边界说明不改变下述选版与等价结果，剩余源输入迁移见[迁移账本](../spec/MODIFIER_PLUGIN_MIGRATION.md)。

嘴颊联动 v9 用于适用的单眼开口源预设，要求共享脚手架 v2、拟合脸 v3、拟合眼 v5、拟合眉 v4 和拟合嘴 v3，并保留实际眼睑头转载体。独立闭嘴图、双眼素材、缺少或不兼容的脸部／眉部前置会被拒绝；其他预设组和已保存的版本锁继续沿用原有选择。

同一适用单眼开口预设还选择笑眼、睁大、视线联动、眼部情绪和高光 v3，以及余震和虹膜挤压 v4。眼睑淡出仍为 v3。预设中已有的眉形和眉睑联动分别选为 v6 与 v8。眉形 v6 要求共享脚手架 v2、拟合脸 v3、拟合眼 v5 和拟合眉 v4；眉睑 v8 还必须有兼容的前置眉形实例，只接受准确匹配的 v1 或 v6，眉形缺失或禁用时在捕获前暂停。两项包在此默认入口之外仍须显式选择版本。

同一适用预设也选择眨眼带眉 v6 与眉弹动 v7。眨眼带眉 v6 要求上述四项基础前置，以及眉形 v6 和眉睑 v8，从源测量与宿主捕获的前置眉头转形变计算眨眼、睁大和同侧笑眼带动的眉部动作。眉弹动 v7 还要求匹配的眨眼带眉 v1 或 v6，在保留前置变形器的基础上添加回弹混合形与物理，并可在所需源前缀已应用后重放。必需前置缺失时在捕获前暂停求值，不兼容的前置链仍会被拒绝。

## 安装与卸载

绑定结构提供算法修订 1／2 的独立包：运行 `./gradlew :algorithms:binding:pluginScaffold1 :algorithms:binding:pluginScaffold2`，输出为 `algorithms/binding/build/plugin-scaffold-1` 和 `plugin-scaffold-2`。包 ID 为 `builtin.7269672e73636166666f6c64.v1`／`.v2`，入口为包命名空间下的 `/structure`，稳定别名为 `rig.scaffold`。两种修订分别固定历史逐目标层级和共享层级语义。

阴郁表情 v5（`expression.gloom@5`）是嘴部弹性 v10、腮红 v5 之后的显式组合候选，其他必需版本及源素材限制与 v4 相同。它复用未修改的 `skinReplayV1` 重建真实腮红前态与阴郁后态，读取实际前置腮红强度，保留眼部拥有的高光透明度，并执行腮红 v5 同等的完整包、能力和源前缀校验。独立包任务为 `:algorithms:binding:pluginGloomV5`。联合链路 15 项定向测试全部通过，无跳过，覆盖真实默认及混合阶段的等价、左右与三类口腔组合、独立强度调参、真实密集腮红载体分配、安装 JVM 输出、真实前缀应用、关闭缓存重放、归档重开及源输入／提供者保护。核对的 444 个历史包文件保持不变。串行根项目全量回归共 1298 项：1133 通过、165 条件跳过，零失败或错误；既有实例保留版本及包锁，默认选版和旧工程转换不会升级此链，也未新增原位版本升级界面。

缺少素材的验证仅限于以下实际源样例及其初始化所得的前置链：

- 缺少表情细节层：左右均接受。
- 仅缺少眼部高光：左侧接受；右侧实际选择旧嘴颊联动 v1，被嘴部弹性 v10 拒绝。
- 缺少眼睑线与眼睑阴影细节：左右均接受。
- 同时缺少眼部高光、眼睑线与眼睑阴影细节：左右均接受。
- 同时没有表情细节、眼部高光、眼睑线／阴影及鼻子的最小样例：左右均实际选择旧嘴颊联动 v1，被嘴部弹性 v10 拒绝。

这些是实际源头部框架的适配边界，不能据此升级真实嘴颊联动提供者，也不代表任意缺层素材均受支持。下脸几何超过冻结下颌 v7 的分配预算时，仍在弹性 v10 之前拒绝；密集腮红结果不证明私有下脸载体动态接入。

当前 `scaffold/5` 契约捕获目标身份、源图层、中性坐标测量、未绑定网格拓扑和图集 UV。插件据此计算部件树、变形器、网格挂接和默认关键形。`scaffold/1` 至 `scaffold/4` 的历史包继续读取原有输入，包括当时所需的模板资源。

打开偏好设置的「算法插件」，选择 ZIP，或输入本地目录、HTTPS／SSH／git:// Git 地址。Git 地址可附分支、标签或完整提交号；安装器记录实际提交。仓库根目录必须是已构建的插件包，不拉取子模块，不运行安装脚本，不在用户机器编译源码。

包必须携带当前平台的程序和必要运行环境。Kotlin JAR 使用应用的 JVM；Python 和 .NET 插件不能假设用户另装了开发环境。插件执行本地代码，进程隔离不等于安全沙箱。

安装器校验协议、平台、配置 schema、文件清单和 SHA-256，再原子发布。相同内容重复安装不会产生副本；同一包版本不能用不同内容覆盖。不同版本可以并存，已有修改器固定引用创建时的版本和内容摘要。

卸载保留工程中的实例、参数和覆盖。缺失或停用的插件显示「插件缺失」；由于缺失算法的实际输出未知，其后缀保守暂停。受影响的工程不能导出，重新安装相同包后重新求值恢复。内置包可停用和恢复，不能删除应用自带文件。插件状态变化会后台刷新已打开工程，不追加历史节点。

偏好记录安装目录和启用状态，默认目录为用户目录下的 `.psd2live/plugins`。工程、历史和导出的预设 JSON 只保存包引用，不嵌入可执行代码。

## MCP

GUI 与 MCP 使用相同管理服务。`plugin_list` 返回包身份、启用状态、算法列表、配置 schema、默认值、依赖、目标类型和读写范围。随附包使用自身清单的依赖、冲突和读写声明。内置算法的配置 schema 来自宿主的校验契约。`problems` 列出不能加载的包。

```json
{"source":"D:/plugins/example-python.zip"}
```

以上为 `plugin_install` 的业务请求；`plugin_inspect` 接受相同输入，只检查、不安装。Git 请求可增加 `ref`。

`plugin_enable`、`plugin_disable`、`plugin_uninstall` 使用 `plugin_list` 返回的 `id` 与 `digest`。内置项也使用列表返回的独立身份；旧的两个值均为 `builtin` 的调用只兼容整体启停，不用于卸载。除列表外均返回后台任务，通过 `job_wait`／`job_get` 查询终态。无需已打开工程。

添加和编辑外部修改器继续使用 `modifier_plan`、`modifier_add`、`modifier_update` 等现有操作；配置按插件提供的 schema 校验。计划结果固定包引用，提交期间插件改变则拒绝旧候选。所有公开操作均声明严格结果 schema。

## 编写插件

JVM 契约已拆为独立的 `:algorithm-api` 模块，应用和插件共用同一份声明。它只依赖中立 `:format-model` 与 JSON 序列化库，不依赖应用、Umamo、Compose、工程或历史。`./gradlew :algorithm-api:build` 生成版本为 `1.7.0` 的 API JAR 与源码 JAR。

`ModifierAlgorithmPlugin.evaluate(input, instance, checkpoint)` 接收上游 `RigIR`、不可变 `RigModifierInstance` 和取消检查函数，返回候选 `RigIR`。实现不能原地修改输入数组；长循环需调用 `checkpoint`，异常原样交回宿主。对象身份使用 `instance.outputId(localName)`，兼容已有别名；宿主仍负责输出验证、依赖、覆盖、CAS 和历史提交。API 同时公开目标引用、固定包引用、清单、版本范围与依赖声明；原 JSON 字段、序列化类型名称和对象 ID 编码保持不变。

API JAR 本身不是可安装算法包。独立编译契约不等于内置实现已迁出应用；内置包加载与历史实现保留仍按上面的迁移状态处理。外部六语言工作进程继续使用下述版本化协议。

### JVM 模型结果适配

`algorithm-worker` 可把 `ModifierAlgorithmPlugin` 放入常驻 JVM 进程。入口调用 `AlgorithmWorker.run(mapOf((type to version) to implementation))`，不需要依赖应用、编辑器或工程。标准输出仅用于协议响应。请求的 `invocation` 提供完整实例信息（含持久化输出别名），原有 `instance`、`config`、`targets` 字段继续兼容其他语言。

宿主在 `capabilities` 中声明 `rig_objects` 后，工作进程可返回 `objects`，替代 `commands`；两者不能同时出现。`objects` 必须恰含 `changed`、`removed`、`mesh_order`、`deformer_order`：以请求输入为基线，仅列出改变的 `frame`、`mesh:<id>`、`deformer:<id>` 资源引用及被删除的键。资源采用 `RigIrObjects` 二进制格式，引用包含 `sha256` 和 `bytes`。单个资源上限 64 MiB，总计上限 512 MiB；宿主验证摘要、大小、对象类型和 ID，不接受路径作为资源引用。

宿主将对象差异合并回完整上游输入，因此按读写声明裁剪掉的无关内容不会丢失。随后检查结构、数值、声明的写入类型和输出 ID，再进入候选、覆盖与事务流程。进程内与工作进程调用同一算法实现；宿主不再通过物理配置命令重新执行该算法。二进制结果适配不改变其他语言已有的命令输出协议。

六语言源码与打包工具见 [examples/plugins](../../../examples/plugins/README.md)。包根目录的 `plugin.json` 声明：

- `protocol: 1` 或 `protocol: 2`，包 `id`、`version`、`name`。
- `commands`：以 `windows-x86_64` 等平台标识为键的参数数组；JVM 包使用 `jvm: ["$JAVA", "-jar", "worker.jar"]`。不经过 shell。
- `files`：每个有效载荷的相对路径及 SHA-256；禁止越界路径、符号链接和未列出的文件。
- `algorithms`：算法类型必须以 `包ID/` 开头；声明算法版本、名称、目标、依赖、互斥关系、读写范围、可组合写入类型、`configSchema` 和 `defaults`。
- 可选 `parameters` 声明共享标准参数的 `id/name/min/max/default`。定义必须兼容上游同名参数；其他新增对象使用实例所属 ID。

`protocol` 表示工作进程的通信协议版本。`plugin.json` 根级的 `version` 用于解析安装包依赖，算法列表中的整数 `version` 则与类型一起标识可执行入口。例如 `mouth.outline@4` 表示描边算法的第 4 版。工程同时锁定算法入口和安装包的版本、内容摘要及依赖锁。包升级后，已有实例继续使用保存时锁定的入口。

`protocol: 1` 每次请求和响应各占一行 UTF-8 JSON；二进制资源通过 `PSD2LIVE_PLUGIN_RESOURCES` 目录下的 SHA-256 文件引用（`{"sha256": "...", "bytes": N}`）。`protocol: 2`（适用于原生二进制与多语言高性能插件，如 Rust/C++/Zig/Go/Python）采用无临时文件、零 SHA-256 磁盘 I/O 的二进制分帧标准输入输出：`[u32le headerLen][UTF-8 JSON header][u32le blobCount]([u32le keyLen][UTF-8 key][u32le dataLen][bytes])*`，二进制引用改为内联键 `{"inline": "<key>", "bytes": N}`，宿主在启动进程时通过环境变量 `PSD2LIVE_PLUGIN_PROTOCOL=2` 通知工作进程。两种协议下标准输出均只用于协议传输，日志写标准错误。请求包含 `protocol/id/method/type/version/instance/config/targets`；响应回显 `protocol/id`，返回 `commands`、`objects`、`changes` 或 `error`。同一工作进程串行处理请求，故障或超时后重建进程；取消执行中的请求会终止进程，不提交其部分结果。排队中的请求可独立取消，不中断正在执行的其他请求；等待响应期间也检查取消。

模型输入按声明的读写组件裁剪；未知范围或 `*` 保守使用完整输入。`changed` 和 `removed` 同步对象索引，`reset` 表示全新会话。`frame`、`mesh:<id>`、`deformer:<id>` 的值为资源摘要，资源目录通过请求及 `PSD2LIVE_PLUGIN_RESOURCES` 提供；资源使用 `RigIrObjects` 的版本化精确二进制格式。`mesh_order` 和 `deformer_order` 保留顺序。

后续请求复用未改动的网格和变形器二进制资源。新对象会先编码，再按内容哈希判断是否发送。

便携视图 `meshes` 提供目标网格 ID、透明度及位置／UV 缓冲引用；`parameters` 提供已声明可读的参数。浮点缓冲格式为小端 `f32le`，文件名等于 SHA-256。返回命令中的浮点数组也可用该引用表示，宿主校验摘要和有限数值后展开。

返回命令支持：

- `mesh_opacity`：目标网格 `id` 与范围 0–1 的 `value`。
- `physics`、`motion`：`config` 使用相应内置修改器的配置格式，输出 ID 由宿主管理。
- 编辑原语：`structure`、`set`、`parameter_keys`、`delete`、`canvas_geometry`、`canvas_topology`、`canvas_create_warp`、`canvas_create_rotation`、`canvas_create_glue`、`canvas_glue_edit`、`path_put`、`path_delete`，沿用作者编辑记录的格式。它们只在隔离候选内执行，不直接写历史。

新增对象 ID 为 `modifier:<实例ID>:<局部名称的UTF-8十六进制>`。宿主校验实际写入范围、共享参数、依赖、覆盖和冲突；插件不得直接操作文档、历史或 GUI。

## 性能边界

内置算法直接调用，不承担跨进程序列化开销。外部插件复用进程、按内容寻址传输缓冲，并增量同步输入。作者基础输入、绑定中间模板和可声明依赖的算法结果分别缓存；文件夹调整不触发算法求值。

本轮验收检查独立算法生成、输出等价和历史重放。性能优化在迁移完成后进行。诊断工具继续记录首次和重复生成耗时，并单列同步烘焙耗时。

部分内置绑定仍从生成模板中提取结果。相邻内置算法的声明读写范围互不重叠，且依赖已满足时，宿主可以并行计算变更。宿主按栈顺序复核实际读取和写入前置条件，再合并结果。其他算法继续顺序求值。首次和重复生成分别计时。

## 版本和依赖关系

三个版本层次独立：`protocol` 是通信协议版本；包 `version` 是 `主.次.修订` 版本；算法 `version` 是已持久化的整数修订号。算法整数号保留兼容，不因更换运行语言而重新编号。包版本支持 `1.2.3-rc.1+build.7`；构建标记不参与先后比较，完整包内容仍由摘要区分。早期包的整数版本按 `N.0.0` 比较，新的包请使用完整版本号。

包的 `dependencies` 声明代码前置条件，`conflicts` 声明不能同时启用的包版本。它们与算法 `requires` 不同：后者要求栈中已经有同目标的算法结果，不会安装或启动另一个包。

```json
{
  "dependencies": [
    {"id": "geometry-core", "version": {"minimum": "1.2.0", "maximum": "2.0.0"}}
  ],
  "conflicts": [
    {"id": "other-cloth", "version": {"exact": "1.0.0"}}
  ]
}
```

- `minimum` 包含边界，`maximum` 不包含边界；`exact` 不能与范围组合。省略 `version` 表示任意版本。预发布版本按数字／文本段排序，不隐含排除预发布版本。
- 安装时选择满足范围的最高已启用版本，锁定完整传递依赖。缺少前置、循环或冲突会拒绝安装／启用，不自动下载依赖，也不关闭其他插件。
- 冲突检查是双向的，一方声明即可生效。不同版本可以共存，但显式冲突仍会阻止启用。
- 宿主保存安装依赖锁；工程的插件引用保存 `dependencyDigests`（`包ID@版本` → 内容摘要）。后来安装更新版本不会替换旧实例的依赖。
- 禁用／卸载前置项会停止工作进程，下游保留并不可用；恢复原内容后重新可用。相同包重新安装但解析到不同依赖时，旧工程引用保持不可用，不能静默升级。
- `plugin_list` 和 `plugin_inspect` 返回 `available/issues/dependencies/conflicts/resolved_dependencies`。`enabled` 只表示用户开关，不能代替 `available`；偏好面板同时显示具体不可用原因。

依赖关系不是跨插件函数调用。算法协作通过上游模型内容和算法 `requires` 完成；请求中的 `dependencies` 提供锁定的包身份，不暴露工程对象或其他工作进程句柄。

```

```

所有命令先在隔离候选中按顺序运行；验证输出后才返回求值结果。附属数据（权重、路径等作者内容）、纹理、画布、渲染层级也参与实际写入检查与冲突报告。一个包不能仅声明 `mesh` 却通过命令修改作者权重。进程隔离不提供安全沙箱；插件仍是用户安装的本地可执行代码。


### 作者输入上下文

API 1.2.0 增加可选的 `ContextualModifierAlgorithmPlugin`，接收独立的 `ModifierAlgorithmContext`。`values` 存结构化作者输入，`resources` 按逻辑名存不可变二进制数据；不写入用户配置，不暴露工程、历史或本机路径。原插件接口继续兼容。

宿主声明 `author_context_v1` 能力。请求的可选 `context` 包含 `version: 1`、元数据资源引用 `values` 和逻辑名称到资源引用的映射 `resources`。引用使用 SHA-256 与长度校验；元数据上限 1 MiB，单项资源上限 64 MiB，最多 10000 项、总计 512 MiB。同内容载荷只落盘一次；不支持的版本和损坏资源拒绝求值。缺省上下文为空。

宿主通过定义的 `authorContext` 捕获输入。前缀缓存和组件依赖缓存均比较上下文内容，资源变化会重新求值。这一接口及传输能力已实现；剩余绑定算法的图层语义、原始图像适配仍在迁移中，尚未全部通过此入口执行。

表情开关的应用计算已迁到 `:algorithms:binding` 的 `ExpressionAlgorithm`，实现 `ContextualModifierAlgorithmPlugin`。它直接构造开关透明度曲线、合并作者通道残差，并补充链物理的表情输入；不调用应用、历史或工程服务。上下文 `schema: "expression/1"` 的 `layers` 保存参数名称及可选开关编号，`meshes` 保存网格到图层的映射，`opacity` 保存源透明度，`chain_owners` 保存前置链修改器身份；二进制资源 `parameters` 使用 `RigIrBinary` 编码仅含已解析参数定义的空模型。`./gradlew :algorithms:binding:pluginPackage` 生成 `algorithms/binding/build/plugin`，包 ID 为 `builtin.65787072657373696f6e2e746f67676c6573.v1`，入口为 `/toggles`，保留别名 `expression.toggles`。当前包进程内执行，历史包通过工作进程接收同一上下文。宿主只为已知内置别名及算法修订绑定作者输入适配器，并核对前置依赖、互斥与可组合写入声明。动态共享参数由宿主从捕获的作者输入批准，新增参数必须与批准定义完全相同；工作进程不能自行扩大允许列表。别名和规范入口均使用同一适配。标准参数名称冲突时的参数解析仍保留兼容生成路径。

`MoodChannels` 已作为绑定模块的独立颜色计算内核，由完整生成和局部模板共享。腮红／阴影追加到已有绑定时，普通路径复用转换前的源几何，仅更新参数与颜色／透明度通道，再执行原有 Cubism 结构转换；不复用已经折叠关键形的结果，避免因颜色轴增加而漏掉转向变形器。标准参数命名冲突和缺少可复用前置输入时保留完整生成路径。关闭阶段缓存仍走完整生成，用于等价验证。腮红 v2 和阴郁表情 v2／v3 已打包，直接生成局部颜色变更。阴郁表情 v3 还可重建兼容的面部和鼻部变形器。

`BlendShapeLowering` 提供独立的 Cubism 混合形到关键形／承载变形器转换，位于 GPL 绑定模块。调用方传入名称策略和取消检查函数，不依赖应用本地化、工程或历史服务；应用适配保留原名称及确定性对象 ID。新增颜色轴可能改变关键形预算，因此局部颜色计算仍需从转换前的输入重新执行此步骤。此底层能力不等同于其余绑定修改器已经完成独立入口迁移。

`MoodBinding` 接收转换前绑定模型、已捕获的参数定义／排序和逐网格颜色权重，完成颜色参数、参数树、生成通道与 Cubism 转换，并同时返回转换前输入和最终模型。重复求值替换所属颜色轨道而不累积参数；未声明网格保留原内容。此接口不接收工程对象或编辑预览，作者覆盖仍由宿主合并。兼容路径通过此接口在模型降级前计算颜色。

`BindingComparison` 在候选生命周期内按对象身份缓存网格／变形器的规范表示。判断局部遮罩变化时只比较目标网格与指定祖先，不转换整份模型；几何数组内容、通道关键形、混合形和其他网格属性仍参与比较。缓存不能跨可变输入复用。

`SeeThroughBinding` 接收已捕获的覆盖候选、设置、命名函数和 ID 分配函数，独立计算眉眼副本、刘海反向遮罩、绘制顺序与透明度继承。预览刷新仅接收前后模型和副本／窗口映射，不读取工程或界面状态。应用层 `SeeThroughLayers` 保留源图像素覆盖识别及配置／本地化适配；类型与调用接口保持兼容。两类修改器均由 `SeeThroughAlgorithm` 的上下文入口求值；`schema: "see-through/1"` 包含覆盖候选 `candidates`、眼／眉类别 `eyes`、前置透发实例 `earlier_owners`、绘制间隔 `draw_order_step`、反向遮罩能力 `inverted_masks` 和含单个 `{meshName}` 的本地化名称模板 `name_pattern`。像素覆盖候选由宿主按捕获源图计算并共享；插件按当前模型顺序过滤候选与刘海，保留生成顺序。配置 `values.opacity` 保持原有 0–100 范围。`pluginEyeSeeThrough`／`pluginBrowSeeThrough` Gradle 任务生成 `algorithms/binding/build/plugin-eye`／`plugin-brow`，分别保留 `eye.see-through`／`brow.see-through` 别名，入口后缀为 `/visibility`；包可安装、恢复并由常驻工作进程执行，当前内置版本直接进程内调用。

`ModelIdRemap` 是 GPL 绑定模块公开的模型引用重写工具，覆盖关键形轴、混合形限制、父级／部件、遮罩、Glue、参数树与链接、路径、顶点组及绘制树。它只应用调用方提供的映射，不分配新身份或绕过宿主冲突检查；宿主仍负责实例派生 ID 与写入权限。与映射无关的模型分区及网格保留原引用，避免破坏只读输入缓存。应用层 `RigIdRemap` 是兼容别名。

绑定模块提供 `GeometryResidual`、`MeshBlendResidual` 和 `WarpBlendResidual`，分别处理关键形几何、网格混合形及变形器混合形在作者坐标系中的三方合并；`BindingVertices` 按已捕获的顶点索引／重心对应传递 x/y 值。输入是只读模型与顶点对应，循环接受取消检查，输出为几何网格／通道或混合形。它们不读取源工程、历史或界面，也不提交结果；实例覆盖归属、冲突判定和原子提交仍由宿主负责。应用中的旧名称保留为兼容别名。

`BindingFrames` 提供 `carriedToParent`、`pointsInParent` 和 `reparent`，将静态网格、关键形与混合形转换到目标父级空间，并支持只反演共享祖先以下的作者分支。普通编辑重新绑定与修改器合并共用此实现；不能还原中立姿态或出现父级循环时拒绝结果。独立接口接受取消检查，修改器路径传递宿主检查函数；它不修改模型身份或发布工程状态。

`BindingMerge.apply` 是独立的绑定结果合并入口：输入当前只读模型、实例及候选限定的 `BindingMerge.Source`，输出新模型。`Source` 提供前后生成投影、固定 ID 映射、静态坐标投影、参数兼容性决策及顶点对应，不得读取实时工程／UI 或提交编辑。主流程在模块内完成承载变形器增删、参数树／链接、关键形、混合形和遮罩的合并。`BindingAxes` 统一轴合并与有限的关键形坐标枚举。此接口是进程内计算契约，不是已完成的外部插件传输协议；当前产品适配仍提供生成模板与网格对应，物理结果、嘴部初始姿态和事务由宿主补充。剩余算法仍需把模板生成替换为各自计算，并接入资源化输入。

`SkinClipAlgorithm` 直接在 IR 上为皮肤叠层添加脸部遮罩，不转换网格或生成完整绑定。`schema: "skin-clip/1"` 捕获有序脸部对象与边界 `faces`、没有源图裁切的候选叠层边界 `overlays`、已由前置同类实例负责的目标 `already_active`；实例目标决定实际范围。算法沿用原 85% 覆盖判定，保留已有相同遮罩，拒绝冲突的作者遮罩／反转状态，其他字段与对象保持不变。源图裁切、已生效实例及目标副本的映射由宿主捕获。`./gradlew :algorithms:binding:pluginSkinClip` 生成 `algorithms/binding/build/plugin-skin`，保留 `face.skin-clip` 别名，入口后缀 `/clip`。此入口的参数声明与求值不再调用绑定模板；后续其他算法仍可能为自身输入生成带裁切的模板。

下游绑定请求以皮肤裁切结尾的源模板时，复用前一模板并调用同一裁切插件，只传递对象身份和遮罩状态，不重建几何。裁切差异同时惰性合入降级转换前的输入；其他遮罩与通道保持原状。已应用前缀使用捕获的源裁切数据，不再查询已移除的活动实例。关闭阶段缓存保留完整生成作为等价校验路径；这并未消除其他绑定模块的模板构建。

嘴部描边的源素材捕获按源分析、作者拆分／删除状态、描边颜色／宽度、网格设置和语言缓存；运动配方、绑定强度与调节值不参与该素材键。绑定模板复用唇线栅格和附加图集，避免每个后续模块重新提取轮廓及编码相同图像。阶段缓存关闭时仍重新计算。此缓存服务于兼容路径。独立打包的嘴部描边 v2 可为兼容的静态旧版嘴直接生成描边。

内置历史包的捕获输入契约按实际使用检查：依赖、互斥或可组合写入声明与宿主适配不一致时，只拒绝使用该精确包的参数查询、输入捕获和求值，并报告包 ID／版本。仅安装此包不再阻断其他工程构建算法目录；不兼容包不会回退到当前内置算法。

`MouthContour`、`MouthColumn` 与 `MouthStrokeMesh` 提供描边的独立几何内核：以 x/y 顶点数组和三角形索引提取边界，按等弧长采样上下唇，构造交叉端点路径及带圆角／端帽的固定拓扑带状网格。调用方提供捕获的几何，不传入产品 `MeshData`、工程或 UI。产品保留薄适配及类型别名；源图语义、像素栅格化、图集与实例输出合并仍需继续迁移到描边插件入口。这些几何 API 本身不发布结果，也不分配工程对象 ID。

`MouthOutlineRaster` 将捕获的唇线列、颜色、宽度和坐标转换函数直接转换成 RGBA、画布位置与不透明像素数；`perimeterColor` 从原始 RGBA 的外边界选取描边颜色，不读取内部细节或透明像素的 RGB。栅格化沿用原 AWT 三角形填充与接缝描线，接受取消检查并保证绘图资源释放。产品只负责源图层分类与输出图层包装；该内核仍不是独立可安装的完整描边修改器。

插件目录快照和包依赖解析按管理修订复用，最多缓存 256 个精确包引用的解析结果（包括缺失引用）。安装、卸载、启停内置或用户包后，下次查询重新构建快照并解析；已锁定的依赖内容不会自动升级。此缓存不缓存文件校验结果，不代替安装和执行前的完整性检查。阶段统计提供依赖解析次数与缓存命中数。

程序从随附清单读取完整的内置插件目录。当工程求值或打开的工程历史引用某一版本、安装的外部包锁定某个前置依赖，或需要启动工作进程时，程序才归档相应的可执行文件。归档用于应用升级后恢复这些精确版本。浏览目录无需写入归档。工程求值可与归档并行，候选须等归档校验完成后才返回。

安装、目录恢复与工作进程启动前的插件载荷 SHA-256 校验使用 64 KiB 流式缓冲。恢复目录时最多并发校验四个安装包，校验读取全部字节，保留大小限制，并在每块之间检查取消。`plugin payload verification` 记录各次校验的合计耗时，`plugin load: installed catalog` 与 `plugin load: retain bundled packages` 分别记录目录恢复和归档的实际耗时。

共享变形器阶段的缓存键只保留其真实读取的强度／调节、基础算法选择、头部转向、视线联动、手臂摆动、衣物／部件链与头发设置。局部眼部形变和描边颜色／宽度等网格输入不再使整套共享变形器失效；源几何、锚点、父级框架、骨骼及语言仍参与相应缓存键。此项减少绑定模板的重复计算，不代表这些模板已全部替换为独立插件求值。

明确的身体图层（上／下装、手脚、腿、颈饰和颈部）的网格阶段不再以眼眉嘴局部模块作为输入；仍保留胸部运动、颈部跟随、头部深度转向、基础选择及原有像素／网格／父级框架条件。衣物链等改变父级时仍通过网格键失效；其他图层保持保守输入范围。

`BrowFit`／`BrowRig`／`BrowOptions` 已位于独立绑定模块。拟合入口接收 RGBA、尺寸、画布位置、左右侧、头部水平及坐标映射，输出眉毛坐标系与 17 点中心线；运动入口生成眉高／角度关键形、眉形、眨眼／微笑联动和回弹混合形，接受取消检查。共享的 `Bounds`／`Side` 也在绑定模块，产品旧名称保留 Kotlin 类型别名，图层适配只负责捕获输入。算法公式不变；这还不是眉毛各修改器的完整可安装入口，实例合并与上下文传输仍需接入。

`HeadTurn`／`HeadShell`、`BustRig`、`ThinPlateSpline` 和 `BiharmonicField` 提供独立的头部深度转向、胸部运动、点集拟合与平滑位移场。接口仅接收数值、点集／固定节点和共享几何类型；网格运动保留原关键形与混合形定义，迭代求解和逐点输出支持取消。`ThinPlateSpline.solve` 公开原带主元消元实现供其他绑定内核复用，输入矩阵不原地改写。产品原类型名保持别名；图层识别、实例组合和可安装入口仍由后续适配完成。

`ThinPlateSpline.solveColumns` 接收同一方阵的多个右端列，只执行一次带主元消元；薄板样条的 X／Y 拟合共用此入口。每列保持原求解的运算顺序与奇异主元处理，矩阵和右端输入均不改写，取消检查覆盖每轮消元。

表情开关的捕获适配器在全部表情参数均为左右眼开合或嘴部开合时，直接查询拟合后的标准范围，不再为参数查询生成完整网格和图集。其他标准名称仍走兼容路径，因为生成后的 Cubism 降级可能改变参数类型；自定义名称继续使用独立表情目录。这是宿主输入捕获的优化，尚未消除其他绑定修改器的完整模板生成。

眉毛原始像素拟合通过共享阶段缓存复用，键包含源图层、眼线方向、脸部中心和坐标空间，不包含眉形、眨眼、回弹或手柄修正。修正在原始拟合之后应用，运动输出继续读取各实例选项；更换源图层或测量坐标仍使原始拟合失效。

绑定模板裁剪使用引擎的 `withParametersDeleted` 批量删除参数，按传入顺序保留原有通道折叠、静态值提升及混合形移除语义，最后只派生一次渲染树。批量入口支持参数之间的取消检查；它仅返回模型候选，不发布工程或历史。

独立绑定模块的 `BindingProjection.retain` 接收模型、保留参数集合及可选的源图姿态默认值，移除其余参数并保留插值后的静态网格／变形器几何。宿主通过源图默认值声明嘴部素材位于张嘴姿态，插件内核不依赖产品参数目录；保留的参数不受此覆盖影响。输入不原地修改，支持对象和轴处理之间的取消检查。模板裁剪及静态投影均使用该入口；源图识别和完整绑定模板生成仍在宿主，尚未完成所有修改器的可安装入口迁移。

`ScaffoldBinding.apply` 负责绑定结构的层级克隆、稳定 ID、共享对象冲突检查、父级框架迁移及组织树成员移动，直接使用引擎编辑原语，不再调用产品的 JSON 编辑分发器。`CapturedSource` 接收按目标索引的静态模板与普通素材网格；只对几何、UV、拓扑均未改变的原始素材使用直接挂接，其余网格通过默认姿态的逆坐标变换保留位置。版本 1 的逐目标层级、版本 2 的共享层级及固化后的别名保持兼容。该内核已被宿主和可安装工作进程使用；结构模板的源图计算仍由宿主捕获适配器提供。

眼部运动内核 `EyeRig`、素材观察数据 `EyeFit`／`EyeArtwork` 和内部眼带、眼睑及睁眼曲线模型归入独立绑定模块；`rig/eye-opening.bin` 随模块分发。宿主继续负责图层识别和修改器组合，这次抽离不等于眼部修改器已完整独立。

### 结构化变更接口（JVM API 1.3）

`ChangingModifierAlgorithmPlugin.changes` 返回 `ModifierModelChanges`。具有稳定 ID 的参数、部件、变形器、网格、物理组和动作使用 `ModifierObjectChanges` 明确新增、更新、删除和复用；更新和删除携带预期旧对象，不能改写对象身份。其他单值或有序关系使用 `ModifierFieldChange`，明确区分“不修改”和“改为 null”。未涉及的字段与缓冲区保留引用。

宿主在应用前用 `changeWrites` 校验实际写入部分，再校验对象前置状态；重复操作、已有 ID 的新增、旧值不一致均拒绝。应用只产生隔离候选，不提交工程。`contributions()` 当前报告对象集合操作，不包含单值字段的完整用户贡献；正式贡献、引用检查、覆盖和事务仍走现有宿主流程。物理组算法已使用此入口。

外部工作进程协商 `model_changes_v1` 能力后，直接返回 `changes`，不物化并编码完整输出。未声明该能力的宿主仍获得原来的 `objects` 响应。`commands`、`objects`、`changes` 必须且只能出现一种，外层协议仍为 1。

`changes` 严格包含 `schema`、`before`、`after`、`objects`、`fields`。`schema` 为 `model_changes_v1`；`before`／`after` 是带 SHA-256 和字节数的二进制资源引用，使用现有 RigIR 二进制版本 6，仅存放涉及的对象及字段，不包含未改动网格。`objects` 的键为 `parameters`、`parts`、`deformers`、`meshes`、`physicsGroups`、`clips`，每个值按 `[新增数, 更新数, 删除数, 复用数]` 排列。前置载荷顺序为删除、复用、更新旧对象；结果载荷顺序为新增、更新新对象。对象操作总数上限 10000，每个载荷上限 64 MiB。

`fields` 列出替换的单值或关系字段（与 `ModifierModelChanges` 的字段名一致）；列出的字段从前后载荷取值，允许明确替换为 null。JVM 编解码辅助库为 `AlgorithmChanges`。宿主校验版本、键集、计数、资源完整性、写入范围与旧对象前置条件，再执行现有完整引用和输出合法性检查。安装包清单中的写入名沿用 `textures`、`glue` 等既有目录词汇。

当前物理包已实测跨进程安装、连续求值、重开、卸载和重装等价。其他语言仍可使用既有命令协议；尚未完成六语言对新变更载荷的逐一实现与验收。宿主仍执行完整贡献比较。只读输入视图、工作进程读取跟踪和生成图像见下文对应小节。

### 捕获源素材（JVM API 1.4）

`ModifierSourceInputs` 通过 `source_layers/1` 表达生成前的源素材，不包含生成模板或宿主回调。`ModifierSourceLayer` 保存稳定源 ID、语义 tag／side／role、源画布左上角、宽高、观察边界、质心、不透明像素数量，以及 RGBA 资源名；`targets` 将稳定模型目标 ID 映射到源 ID。图像为从左上角开始、逐行、无填充的非预乘 RGBA8。素材源坐标是像素且 Y 向下，观察边界与质心也使用该空间。

`to_model` 是源画布到模型画布的可序列化仿射矩阵 `xx, xy, tx, yx, yy, ty`，支持镜像并拒绝奇异矩阵；它不是父变形器空间转换。`raster(layer)` 提供缓存的只读视图，`alpha(x,y)` 越界返回零，`rgba()` 返回独立副本。资源有内容摘要，可复用已有 `author_context_v1` 传输。构造时检查重复源 ID、目标引用、有限坐标、尺寸及 RGBA 长度；每张图上限 64 MiB，遵从上下文总量限制。

`context()`／`from()` 编解码此快照。宿主 `RigSourceCapture` 只捕获已有素材与分类结果。眼部轮廓拟合现已在独立绑定模块中直接读取此契约；宿主适配保留原有坐标变换调用，独立消费者可使用 `to_model`，不需要产品类型。这里只替换输入边界和拟合实现的位置，不改变运动设计，也不代表眼部修改器的几何生成、组合与打包已经完成。

目前该快照是栅格观察输入，不包含独立遮罩资源、父空间几何视图、上游能力快照或读取集合跟踪；这些仍属于框架后续工作。源掩码的处理保持调用前素材原有语义，不宣称此接口已能独立表达全部素材链路。

### 按读取对象求值（JVM API 1.5）

`ReadingModifierAlgorithmPlugin` 的入口接收 `ModifierEvaluationInput`，不能直接取得整个 `RigIR`。`parameter(id)`、`mesh(id)`、`deformer(id)`、`part(id)`、`physics(id)`、`motion(id)` 记录所读对象；找不到对象也记录一次观察，后续该对象出现会使缓存失效。读取集合或其他整体字段时记录该字段的完整值及顺序，`context` 当前按完整上下文跟踪。

`parentsOfMesh(id)` 返回从直接父级向外的变形器链，保留各自声明的局部坐标；它读取目标和所有祖先，拒绝循环、缺失父级和重复身份。这里不自动把不同空间的点混在一起，实际坐标运输继续使用绑定模块的坐标算法。

`reads()` 给出该次调用的独立读取快照。宿主对新入口缓存实例配置、插件实现身份、作者上下文、读取集合及结构化变更。上游修改后，只在所读值仍一致、输出写入前置条件仍满足时复用；若前置条件变化，重新计算。复用仍经过写入范围检查、覆盖、贡献冲突和事务流程。失败或取消的候选不替换成功快照。物理插件目前只读取实际引用的参数和物理配置，不读取所有几何。

进程内缓存核对实例、算法实现、捕获上下文和实际读取值。跨进程的读取集合和复用条件见下文对应小节。

### 显式上游能力（JVM API 1.6）

算法清单的 `provides` 声明其提供的能力别名，`requires` 可以引用算法类型或能力别名，循环检查覆盖两者。包的语义版本依赖仍由清单 `dependencies`／`conflicts` 处理，不与实例的执行前置关系混淆。

`ModifierAlgorithmContext.upstream` 保存宿主解析后的前置能力。每项 `ModifierUpstreamCapability` 包含请求能力名、实际算法类型和算法版本、前置实例 ID、目标引用、固化配置、输出别名，以及已知时的完整包引用（版本、内容摘要和依赖内容锁）。宿主只选择满足消费者目标和显式 provider 选择的前序／已固化提供者。旧记录缺少包引用时保持 null，不猜测当前安装版本。应用前缀会保留这些身份信息，固化内容继续满足下游依赖。

`ModifierEvaluationInput.upstream`／`providers(capability)` 将这些输入纳入读取集合和缓存失效判断。普通源素材 `values` 的 schema 不变，上游快照单独传递。外部算法须在清单声明 `contextVersion: 2` 才会收到上游输入，旧清单默认 1。上下文无上游数据时继续编码 v1；有上游数据时编码 v2，在原 `version`、`values`、`resources` 之外增加 `upstream` 资源引用，元数据上限 1 MiB。v2 接收器也读取 v1，旧包不被强制发送 v2。

GUI/MCP 共用的插件描述新增 `context_version` 和 `provides`，结果 schema 同步声明这两个字段。现已验证能力别名解析、上游配置变化使缓存失效、应用前缀保持能力、包身份保存恢复及 v1/v2 上下文编解码。外部读取集合回传与父空间坐标服务见下文；完整新算法迁移仍未完成。

### 父空间坐标服务

GPL 绑定模块的 `BindingCoordinates.forMesh(input, meshId, pose)` 从 `ModifierEvaluationInput` 捕获目标网格、完整祖先链以及祖先实际引用的参数，不转换其他网格或无关变形器。`pose` 为显式参数值，未给出的值采用参数默认值；不会读取当前播放帧。父级循环、缺失父级／参数和无效坐标会失败。

`toCanvas`／`fromCanvas` 的画布坐标为像素、Y 向下，服务内部处理运行时世界坐标的 Y 反向，插件不能再自行反转一次。逆变换使用现有运行时求解器，可传局部种子；结果必须重新投影到目标点的 0.05 像素以内，否则拒绝。点数组必须是有限 XY 对，输入不修改，转换边界检查取消。

`BindingCoordinates.reparent` 复用 `BindingFrames.carriedToParent`，返回结构化网格变更，运输默认位置、关键形及混合形，保留原有非几何属性。它不会自动提交层级或工程编辑，也不会代替依赖验证。已通过嵌套非线性网格／旋转坐标、Y 方向、实际读取范围和重新挂接后的默认姿态／关键形位置检查。该服务是共享框架能力，不计作某个剩余修改器的完整迁移。

### 外部读取跟踪与复用

宿主声明 `input_reads_v1` 后，实现 `ReadingModifierAlgorithmPlugin` 的 JVM 工作进程可随 `changes` 返回 `reads`。每项为 `{section, id?}`；省略 ID 表示读取整个字段，有 ID 表示读取指定对象，包括不存在对象的观察。读取集合上限 10000，重复／无效查询被拒绝。 API 的 `meshIds` 单独观察网格成员及顺序，不读取其几何和显示通道；跨进程使用 `input_mesh_ids_v1` 能力协商。不支持该能力的宿主仍接收变更结果，但不会收到含此读取键的缓存观察。旧宿主不收到额外字段，旧插件仍可返回 `objects` 或命令。

宿主使用实际发送的输入投影和上下文重建观察值，不接受插件提供的旧值。成功结果按包工作进程和实例保存，最多 128 项；匹配算法描述、完整实例配置、上下文和读取值后，尝试将结构化变更应用于当前完整模型。写入前置条件不满足时重新求值。复用仍执行输出身份、引用、范围和模型合法性检查；只跳过输入二进制序列化与工作进程调用。

缓存不会推进尚未发送的输入修订，下一次实际请求仍相对于上次发送状态生成增量。工作进程退出、停用或卸载时不能靠缓存绕过可用性检查；异常和取消会丢弃该工作进程。`plugin worker evaluations` 和 `plugin read cache hits` 计数用于专用验收。

真实物理插件包已验证：重复输入和增加未读取参数不增加工作进程求值次数，修改读取参数后重新求值，最终模型一致；重开、卸载与重装流程保持有效。此结果不是完整生成的性能达标证明，也不代表其他五种语言均已接入新读取协议。

### 生成图像的宿主边界

API 的 `ModifierRasterOutput` 描述生成图像、网格和可编辑路径：`owner` 是捕获的原网格及前置状态，`mesh` 是新增网格，`layer` 是源图元数据，`pixels` 是不可变 RGBA8 内容资源，`paths` 只能引用新增网格。画布位置由源图元数据记录；几何保持父局部坐标。默认 UV 为素材局部像素，宿主图集分配后才转换为图集 UV。`PAGE` 仅用于兼容已经绑定图集的旧输出，不能把素材像素误标成该模式。

宿主先检查整个批次：原网格未变化、输出身份无冲突、图像尺寸与字节数一致、几何与路径引用有效；每张资源不超过 64 MiB，整批不超过 256 MiB。随后在隔离候选中追加专用图集页、源图和 tile 记录，将新增网格放在原网格之前，并一起加入路径与可编辑原图。旧页面不重新布局。失败或取消不发布候选，仍由外层 CAS 和历史事务提交。

现有嘴部描边资源附加已使用此边界，并保留原像素与图集行为。API 1.9 的 `ModifierModelChanges.rasters` 将资源输出与普通对象变更放入同一候选：先应用普通变更，再核对资源输出的 `owner` 与该中间候选一致，最后调用宿主资源分配器。因此，若同次修改原网格，`owner` 应使用声明更新后的网格。没有宿主分配器时直接调用 `apply` 会明确失败；JVM 宿主使用 `applyWithResources`。资源写入保守要求 `mesh`、`part`、`hierarchy`、`textures` 和 `authoring` 范围。

宿主协商 `model_changes_v2` 后，含资源的变更在原稀疏变更信封中增加 `rasters` 数组；没有资源时继续发送 v1。每项严格包含 `model`、`pixels`、`uv_space`：前两项是 `{sha256, bytes}` 二进制资源引用，后者为 `RASTER_PIXELS` 或兼容用 `PAGE`。模型载荷使用 RigIR 二进制格式，仅包含按顺序排列的 owner／新 mesh，以及 `authoring.sources` 中唯一 `raster` 来源的图层元数据和 `authoring.paths`；其他模型字段必须为空默认值。像素为独立 RGBA8 资源。单资源上限 64 MiB，模型与像素合计的整批传输上限 256 MiB，最多 10000 项。哈希错误、额外字段、错误载荷或未协商的发送都失败。

JVM 工作进程自动编码此结果；其他语言可实现相同协议，但六语言图像结果验收尚未完成。读取缓存保留未分配图集的变更，每次命中仍由当前宿主候选和捕获的图集配置执行资源校验与分配。拟合嘴部描边的独立 JVM 包已使用此契约。


### 拟合嘴部源输入（迁移中）

GPL 算法库提供 `MouthSourceContext(fit, options, lineWidth)`。`encode()` 返回可传输的 `ModifierAlgorithmContext`，`decode(context).rig()` 在不加载产品模块的情况下构造 `MouthRig`。三层模型数据随算法包携带；产品只负责源素材分类和轮廓采样。这是算法输入接口，尚不代表 `mouth/fitted` 已完成安装入口和宿主接线。

控制对象严格包含 `schema: "mouth_source/1"` 和 `measurement: <SHA-256>`；资源表以该摘要为键。资源使用大端 Float32，顺序为嘴部原点／坐标轴／宽度、上下轮廓、可选分层框架、全部嘴部选项、可选线宽。轮廓各 49 个标量；分层框架保存四组 65 个二维轮廓点、开口列及其上下边界、可选局部部件边界和牙齿测量。可变列数使用有界 Int32；可选值和开关使用单字节 0／1。选项保留七点闭嘴曲线及捕捉、元音、下颌、深度、弹性和舌头等开关与数值。

该载荷只包含源测量和配置，不携带已求值姿势或完整绑定模板。解码拒绝未知 schema、缺失／摘要不匹配资源、非有限数值、非法长度和尾随字节。坐标仍使用源拟合的画布空间和局部框架，传输不归一化或重新采样浮点值。


候选协议 `mouth-fitted/1` 可引用 scaffold 已捕获的 `source_meshes` 资源，并显式指定目标网格到源网格的映射。算法只在父级、三角索引和每个归一化中性坐标的浮点位值均匹配时使用原始坐标；作者移动顶点、改变拓扑或重挂后，从当前几何重新计算，不能套用旧资源。UV 单独变化不会使原始位置失效。算法输出类型化变更，并可向宿主提供同一次求值的降级前候选，供后续绑定组合；宿主仍负责作者残差合并和事务提交。
