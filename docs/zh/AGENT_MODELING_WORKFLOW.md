# 从 Live2D 建模流程反推 Agent 能力

2026-09-13。本文是 [MCP 设计](AGENT_MCP_DESIGN.md) 的工作流依据。除文末标注的多姿态拼图外，接口和流程均为待实现方案，示例不是可调用 API。研究基于本地源码，不把参考项目的测试通过等同于实际建模质量。

## 1. 纠正此前的建模假设

此前方案主要解决“怎样改好一张形状”，但 Live2D 建模需要的是：**让一组图层在参数变化时，持续保持结构、体积、遮挡和角色特征，并能继续编辑。**

因此必须同时决定三件事：哪一级对象负责运动、形状写入参数空间的什么位置、这个变化会怎样与已有运动组合。只提供整网笔刷，仍无法回答这些问题。

| 此前不足 | 修正后的要求 |
|---|---|
| 局部修改优先创建小 Warp | 先选已有运动所有者；临时笔刷/路径不创建层级。需要独立运动才建永久 Warp/Rotation |
| 普通塑形以 Warp 为唯一目标 | ArtMesh 与 Warp 均是一等编辑目标；细眼睑/唇线可能应直接编辑网格关键形 |
| 把 pose 当作写入目标 | 区分观察姿态、精确关键形地址、基础形状和叠加修正；不从 GUI 当前值猜目的地 |
| 眼睛/嘴巴也归结为压缩 | 同一闭合轨迹下，不同素材承担孔径、线条、遮挡等不同作用，需要协同而非同倍率压扁 |
| 关键形创建/复制是配套功能 | 它们是主工作流：插入、复制、镜像、合成组合角、按参数切片修改与保留其他形状 |
| 合法网格即可继续 | 合法性、预期闭合、角色造型和中间插值分别评估；不能统一惩罚所有强压缩 |
| 拼图只是把图片放一起 | 布局必须表达参数关系和修改版本；每格可定位到对象、关键形与观察姿态 |

依据：Cubism 的 [变形笔刷](https://docs.live2d.com/en/cubism-editor-manual/deform-brush/)、[临时变形](https://docs.live2d.com/en/cubism-editor-manual/temporary-deform-tool/)、[变形路径](https://docs.live2d.com/en/cubism-editor-manual/deformpath/)。这些是编辑方式，不意味着每次操作都必须留下新的永久变形器。

## 2. 实际工作顺序与缺失能力

| 阶段 | Agent 应判断什么 | 程序应承担什么 | 不能冒充完成的情况 |
|---|---|---|---|
| 素材与网格 | 分件是否支持目标动作；露出的部分有没有像素；眼口边缘能否弯曲 | 图层定位、隐藏区域覆盖、拓扑/UV 保持；替换素材配准 | 缺像素时靠移动边界掩盖；已有绑定后静默重网格 |
| 层级与职责 | 共同运动与独立运动分别归谁；是否已被父级驱动 | 追踪直接/继承绑定，显示相关链；创建/迁移时验证原运动 | 给眼球重复添加眨眼，或让头发继承强面部压缩 |
| 单轴基础形 | 默认、两端及必要中间关键形是什么 | 从现有插值插入键，保持其他关键形/通道；明确目标轴值 | 滑块有值但对象未绑定；填满同一形状后宣称已建模 |
| 双轴组合 | 哪些运动可以相加，哪些组合必须修正 | 从已认可轴向形状生成角落候选；精确修改指定单元/切片 | 九个单元有数据就等于九方向转头自然 |
| 眼口与表情 | 孔径、轮廓、墨线、遮罩和前后关系如何协调 | 共享曲线、角色约束、多对象一次写入；通道级复制 | 睫毛与眼白等比缩到一条线；闭眼只把瞳孔隐藏 |
| 物理 | 静态输出端点是否好看；发根/连接处是否稳定 | 独立输出参数、时间驱动评测、回正/饱和定位 | 手工切换三个姿态代替物理测试 |
| 交付 | 已有动作是否保留；保存导出是否同样成立 | 相关端点、中间值、交叉组合及导出回读检查 | 只看正面截图；应用预览正确但导出改变运动 |

本项目不是空白编辑器。[现有层级规范](DEFORMER_AND_PARAMETER_SPEC.md) 已区分头壳跟随、面部九轴、眼部透视、瞳孔保持、视线和头发物理。Agent 应从已有绑定继续修正，而非再生成一套名字相近的结构。规范中的算法意图也不能作为造型质量已经通过的证据。

## 3. 最重要的新抽象：可核对的编辑目的地

`inspect` 的对象摘要应回答“能改什么、现在由谁控制”，按选区仅返回相关信息。示意：

```json
{"state":"h17","target":"mesh:lashL","direct":["EyeOpenL"],"inherited":["AngleX","AngleY"],"related":["mesh:whiteL","mesh:irisL"]}
```

这是实际绑定摘要，不是靠名称猜出来的标准模板。多个候选眼白/变体不明确时，返回候选名字让 Agent 选择，不能自动选第一个。语义识别结果须带来源并允许修正。

一次编辑目的地包含：工程版本、对象集合、通道、精确关键形地址、观察姿态和固定坐标框。服务端可生成短 edit handle，后续沿候选继承；不是“开始编辑”“激活对象”等额外工具。首次调用需足够显式，后续才省去重复字段。

三种写入不能混用：

- **基础形状**：改变不随指定参数变化的基准。必须说明对既有动画的迁移策略；不能把在转头姿态下看到的位置直接写成 rest mesh。
- **关键形**：写入指定 owner 的精确参数单元。显示姿态可以同时包含父级转头，但写入眨眼时不能顺便新增头部 XY 绑定。
- **组合修正**：写入已有组合单元或明确的增量层。仅在格式、运行时和导出均支持时使用独立增量层；否则烘焙到指定组合关键形，不能假称支持 Cubism Blend Shape。

画布笔刷的位移需要通过当前父链反算到目的地的局部坐标。不可逆/多解处返回定位错误，不把屏幕坐标直接当局部坐标。明确输出哪些对象、关键形和通道发生了变化；如果已有 edit handle 唯一限定且未扩展范围，才只返回 state。

关键形管理由程序做数组与插值运算：

1. 新增键采样当前插值，不清空其他格子；区分“有插值种子”“自动生成”“人工/Agent 修形”“外观已检查”。这是来源记录，不是质量分数。
2. 复制指定形状与通道，不复制整条参数定义；跨对象复制需要兼容拓扑或明确的映射，不能按顶点序号盲抄。
3. 镜像需要明确轴与对象配对，默认只补未编辑目标；覆盖须显式表达。镜像是生成候选，不是保证左右画风可互换。
4. 双轴先做轴向形，再合成指定角落；只覆盖选定角，保留其他格子。默认值不一定是参数范围中点。
5. 支持参数切片，例如 Smile=1 的所有 EyeOpen 键统一调绘制顺序，不触碰 Smile=0；几何与不透明度/绘制顺序可选择性编辑。

参考：[形状特殊粘贴](https://docs.live2d.com/en/cubism-editor-manual/paste-form-special/)、[动作镜像](https://docs.live2d.com/en/cubism-editor-manual/motion-mirroring/)、[四角形状合成](https://docs.live2d.com/en/cubism-editor-manual/synthesize-corners/)、[多关键形编辑](https://docs.live2d.com/en/cubism-editor-manual/multi-key/)。

本项目 `org/umamo/edit/KeyformGeometryEdits.kt` 已有保形插键；其注释也明确指出几何创作还需 posed deformer-chain inverse。不能把底层“可以移动键的位置”误报为已经具有完整的姿态下造型能力。

## 4. 三条完整建模路径

### 4.1 修好闭眼，并保持微笑与转头

1. 读左眼眼白、上下眼线/睫毛、虹膜、高光、已有闭眼素材及它们的直接/继承绑定。确认闭眼模式是几何、替换素材还是混合；沿用项目已有表达。
2. 确认闭眼写入 EyeOpenL 的哪个键；转头只作为观察条件。检查现有睫毛网格能否沿眼睑弧线弯曲，不能只看顶点数量。
3. 定义共同闭合弧与眼角锚点。眼白孔径沿弧闭合；睫毛沿弧弯曲并保留需要的墨线厚度；下眼睑协调移动；虹膜/高光保持合适形状并遵守眼白遮罩。各部件共享目标，不共享一套压缩倍率。
4. 在同一候选中写入相关对象，检查张眼、半闭、全闭；半闭若坏，再增加必要中间键，不能靠增加密度盲目修复。
5. 检查 EyeOpen × Smile 的局部参数矩阵。只在出问题的组合修改轮廓、厚度或绘制顺序。再看已有头部转向端点，确认没有重复眨眼/继承挤压。
6. 合理接近闭合的眼白可以高度压缩；自交、纹理翻面、残留白缝、睫毛消失分别诊断。不要通过统一“所有三角形面积须大于某比例”阻止闭合。

PuppetLoom 的眼白/睫毛联动很有价值，但 `eye-closure-authoring.ts` 明确注明受 PSD2Live 的 `eyeClosurePoint` 与 alpha 中线启发。因此应借鉴它的**绑定冲突检查、角色协调和关键形保留机制**，不能把自己的算法绕一圈当作外部已验证的新突破。

嘴部沿用这些编辑机制，但有自己的造型约束：上下唇闭合线、嘴角固定范围、口腔/牙齿/舌头遮挡、开口面积与笑形组合。不能复制闭眼阈值生成口型。

### 4.2 修头部 XY，而不是把整张脸压扁

先看已有轴向姿态与层级，区分整体轮廓错误、五官透视错误、头发跟随错误和遮挡错误。面部大 Warp 负责整体体积，眼/鼻/嘴局部负责剩余修形；头壳与头发继续使用自己的跟随链。

修改顺序：默认形确认 → 左右及上下轴向形 → 缺失角落合成候选 → 四角局部校正 → 中间轨迹检查。已有好的角落直接保留，不为统一流程全部重建。每次只修责任明确的一层，避免父级移动与子级补偿重复计入。

真正需要观察的是轮廓、眼鼻嘴相对间距、远近侧差异、下颌/颈部连接和耳发遮挡。简单 scale 可以是塑形步骤，不能代表“实现了转头”。同一对象不同区域前后顺序冲突时，可能要分件/调整拓扑；单个 draw-order 数值无法解决。

### 4.3 让一束头发独立摆动

确认它已有独立物理层还是仅与整片刘海共用运动。已有 owner 则直接编辑；需要独立输出时才插入局部 Warp，保留头部跟随层及已有动画。

用从发根到发梢的路径或大范围 bend 创作输出参数两端，发根为有限固定区域而非一个固定点，截面沿曲线转动。控制网的空白与边界同样参与，多个绘制段可共用一个编辑场；每个对象分别反算局部坐标。

检查中立/两端/中间形状、发根覆盖、邻束关系后再接物理。物理输入驱动的是已经建好的输出参数范围，调阻尼不能补救端点形状错误。用真实时间轨迹看回正、过冲与输出饱和，不以静态拼图冒充物理结果。

## 6. 工具与信息压缩要服务这个流程

核心职责应是 `inspect / view / rig / form / deform / revision`，配套 `asset / appearance / physics`。这是待测量的九个工具领域，不是为了满足数字隐藏任意命令；每个分支需要有限、互斥、可校验的类型。

- `rig` 管理永久运动结构；临时刷子/路径属于 `deform`，不留下节点。
- `form` 管理参数绑定与关键形集合操作；`deform` 在已明确的目的地塑形。绘制顺序/不透明度关键形也通过明确 channel 写入。
- `appearance` 管理静态显示、遮罩和连接关系；多个修改默认沿同一候选，`revision` 负责提交、恢复与查询。不要再为每个部位复制工具。
- `view` 接受有意义的参数矩阵/轨迹采样和局部范围。EyeOpen × Smile 可按行列组织；修改前后用并列矩阵或选定格子的两列对照，避免一次发 18 个无法辨识的缩略图。
- 稀疏回执应省掉重复上下文，不省掉写入范围、插值种子/生成来源、关键错误和未检查项。点数组、所有默认参数及全部父链不应每次重传。

不要求 Agent 读一份长建模手册才能操作。语义 owner、相关参数、路径与 edit handle 保存在工程；首次按选区读一次，出错时仅返回缺失信息。API 不应把“修头部”变成一个不透明的自动建模按钮。

## 7. 实施与验收

首先接通 **已有对象 + 精确关键形 + 多对象连续编辑 + 参数矩阵观察**。局部 Warp 是“需要新增独立运动层”分支的必要能力，不能占据整个路线而推迟现有模型的眼口修形。

三个端到端验收任务分别是上文闭眼组合、已有头部 XY 局部修正、独立发束物理。记录任务完成率、人工修复时间、实际运动范围、非目标关键形/通道是否保留、总 Schema/request/response/image 成本。正面好看、工具调用成功或九宫格填满都不算通过。数值检查之外仍需实际渲染和造型评审。

本轮已开始落地的范围：现有 `view_render_poses` 改为单张带标签拼图，公共参数只传一次，每格保留实际参数差异、原 viewId 和排除标签后的像素矩形；整张图受尺寸/字节预算约束。它仍是**同版本静态姿态对照**，尚不具备候选版本前后对照、关键形来源标注或真实物理时间采样。
