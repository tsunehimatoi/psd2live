# MCP usage and interface

[Documentation](../../README.md) · [中文](../../zh/agent/MCP_AUTHORING.md) · [Design and acceptance](../../zh/agent/AGENT_DESIGN.md) (Chinese) · [Measured capabilities](../../zh/STATUS.md) (Chinese)

The public definitions live in the application layer in [WorkspaceAuthoringOperations.kt](../../../src/main/kotlin/io/github/psd2live/application/WorkspaceAuthoringOperations.kt), [WorkspaceDocumentBatch.kt](../../../src/main/kotlin/io/github/psd2live/application/WorkspaceDocumentBatch.kt), [WorkspaceAuxiliaryOperations.kt](../../../src/main/kotlin/io/github/psd2live/application/WorkspaceAuxiliaryOperations.kt) and [WorkspaceOperations.kt](../../../src/main/kotlin/io/github/psd2live/application/WorkspaceOperations.kt); the MCP binding is in [AgentToolCatalog.kt](../../../src/main/kotlin/io/github/psd2live/agent/AgentToolCatalog.kt). Tools use `domain_operation` names; the old branch tools are removed and have no compatibility aliases. Use `workspace_list_operations` to discover capabilities page by page, then `workspace_get_operation` to read one operation's full schema.

## Connecting

1. Start the desktop app and load or create a workspace.
2. Open **Settings → MCP** (the gear on the right of the title bar) and copy the command or configuration for your host: a Claude Code command, Codex TOML, generic `mcpServers` JSON (the address field differs by host) or a Stdio proxy. **Copy setup prompt** produces a short prompt that lets the agent configure itself.
3. Prefer Streamable HTTP with a Bearer token. Do not switch to the deprecated `/sse` endpoint.
4. Hosts that only support Stdio run the root `mcp_proxy.py` with Python 3; the proxy reads `PSD2LIVE_MCP_ENDPOINT` and `PSD2LIVE_MCP_TOKEN`, and when they are unset on Windows it reads the port and token the app saved. Scripts and the command line use it too: `python mcp_proxy.py call <operation> [JSON | @file] [--edit] [--out dir]` (`--edit` fills in the current `state`, images are saved as PNG) and `python mcp_proxy.py operations`; in Python, `from mcp_proxy import Client`, then `call` / `edit`. Both tool profiles work, and background operations return their result once they finish.
5. After listing the tools, call `workspace_inspect` to read the actual object IDs, parameters, the current `project_id` and `state`.

The same dialog sets whether the server is enabled, the port (1024–65535, default 23871), the access token (32–256 letters, digits, `-`, `_`; regenerate it or enter your own) and the tool profile. These are stored in user preferences, and applying them restarts the endpoint. A restart keeps in-process jobs and request deduplication records; connected hosts must reconnect, and if the port or token changed, the host configuration must be updated as well.

The token allows editing the current workspace and should stay in the host configuration on this machine. The tools provide no image generation model; new images can come from existing pixels, painting or the host's image generator.

## Tool profiles

The profile only decides which tools `tools/list` publishes. Every operation can be called under both profiles, with the same execution and validation.

- **Compact (default)**: 27 tools that directly cover 123 operations (input schemas and descriptions are about 85,000 characters; the full profile is about 760,000 characters, plus about 4.26 million characters of output schemas).
  - Single tools: `workspace_overview`, `workspace_inspect`, `workspace_list_operations`, `workspace_get_operation`, `workspace_apply_edits`, `workspace_preview_edits`, `rig_deform`, `keyform_apply`, and the intent tools `author_axis`, `author_physics`, `author_compile` (see [Intent tools](#intent-tools)).
  - Family tools: `view`, `parameter`, `motion`, `expression`, `hit_area`, `pose`, `skeleton`, `path`, `physics`, `simulation`, `swing`, `source_paint`, `snapshot`, `history`, `project`, `job`. Calling `{"op":"set_key","request":{...},"wait_ms":20000}` runs `<family>_<op>` (here `motion_set_key`); the result's `operation` is that operation ID, and `request` is validated against that operation's full schema. The members are all registry operations with that prefix, except private drafts, audition and live preview sessions (`skeleton_draft_*`, `physics_audition*`, `*_preview*`), history annotations and the global physics preset library. A family tool publishes the flat union of its members' fields (no `oneOf`, `const` or `$ref`; fields whose shape differs between members only get a description), and each op's required fields are listed in the tool description.
  - Other operations are called through `workspace_call`: `{"operation":"layer_classify","request":{...}}`. An operation ID is also its member name in `workspace_apply_edits`.
  - No `outputSchema` is published (results still come back as `structuredContent`; the contract is in `workspace_get_operation`). For the `edits` members of an atomic batch, only the enum of operation names and the `request` object are published; member fields are strictly validated against the single-operation schema at execution.
  - `request_id` and `project_id` may be omitted. `project_id` defaults to the currently loaded project; `state` is still required, and a `state` belonging to another load reports `state_conflict` as usual. `request_id` is derived from the operation and its arguments (including `state`), so a retry with the same arguments gets the original result back; if the previous identical call failed (including a job ending `failed/cancelled`), calling again runs as a new attempt.
  - Background operations accept `wait_ms` (0–30000, default 20000): if the job ends within the limit, the terminal status and result are returned directly (the same structure as `job_wait`); otherwise the running job is returned and you continue with `job_wait`. `wait_ms: 0` returns the job handle immediately.
- **Full**: one tool per operation, publishing complete input and output schemas, with no derived context and no job waiting. Suited to hosts that load tools on demand or clients that need each contract.

## Intent tools

Intent tools are ordinary public operations in the registry (callable under both profiles), defined in [WorkspaceIntentOperations.kt](../../../src/main/kotlin/io/github/psd2live/application/WorkspaceIntentOperations.kt). The write tools compile the intent into existing batch members on the captured model for the request's `state`, then go through the same atomic batch as `workspace_apply_edits` (`startDocumentBatch`): rebuild, geometry check and CAS are identical, one success appends exactly one history node, and no new journal semantics are added. The job result is the same as for `workspace_apply_edits` (`edit_count` is the number of compiled members); problems found while compiling return `invalid_argument` immediately, and a failing member returns `invalid_edit` with the member index and operation. A captured version that differs from the request's `state` reports `state_conflict`.

| Tool | Compiles to | Notes |
| --- | --- | --- |
| `workspace_overview` | Read-only query | One capture returns the canvas, parameters, layers, deformer hierarchy (with parent and child count), mesh count, physics groups (input/output parameters) and motion clips; each list carries `total` and is cut to `limit` (1–500, default 200); parameters carry `kind` and `repeat` (a repeating parameter) |
| `author_axis` | `parameter_create` (when the parameter does not exist) → `keyform_apply` seed → `rig_deform` | Creates `parameter.id` when it does not exist (`name` defaults to the ID); when it exists, any given `min/max/default` must match the current values. Each shape target is first seeded at the parameter's default so the current shape becomes the neutral shape (skipped when the axis already has a key at the default and no `key` is given); then `rig_deform`'s `operations/selection` run at `value`. Other axes bound directly on the target take their own defaults; `key` can give values for combined angles. Rejected when `value` equals the default. With `mirror: true` each shape is also mirrored onto the opposite value (`2×default − value`, which must be in range), so authoring one side makes both. The engine creates the new axis's keys at min/default/max |
| `author_physics` | `physics_put` → `physics_fit` | Fields as in `physics_put`, plus `fit_target` (10–300, default 100; `null` skips fitting). With only `id` and `fit_target`, only an existing group is refitted; rejected when neither changes anything. Output parameters need authored shapes already |
| `author_compile` | Read-only query | Returns the members an intent would commit; see below |

Intent tools themselves have no dry run. `author_compile` compiles the same intent against the request's `state` and returns the members it would commit (`{"intent":"author_axis","request":{...}}`, where `request` carries `state` but not `request_id/project_id`), without changing the project; you can inspect or modify them and hand them to `workspace_preview_edits` to dry-run the geometry members, or to `workspace_apply_edits` to commit, with the same result as calling the intent directly.

overrides on simulated pendulums from the physics panel are three-way merged after a rebake; see [Simulation and baking](../guide/SIMULATION.md) |
| `model_apply_preset` | `preset`, `state`, `layers`, `sway` inside `request` | `front_hair/back_hair/clothing/auto_weights/classic_front_hair/classic_back_hair/remove_clothing`: generates weight groups and preset physics bodies in the background and bakes them; returns a job handle and adds exactly one history node on success; hair presets remove that hair type's old swing parameters, deformers and pendulums, `classic_*` restores them (`sway:false` turns classic swing off), and `remove_clothing` deletes all clothing preset physics bodies; `clothing` simulates only the loose parts of tops, bottoms, neckwear, sleeves and legwear, and returns each mesh's region (bottoms also carry the skirt / trousers decision and the waistline, crotch and hem), looseness ratio, drape start and whether it is simulated; see [Simulation and baking](../guide/SIMULATION.md), section "Model presets" |

The table lists business fields; every mutation also carries `request_id`, and workspace mutations carry `project_id` and `state` (the compact profile may omit the first two; see [Tool profiles](#tool-profiles)). The read-only background samplers `physics_simulate/simulation_simulate/simulation_compare/view_sample_motion` also require these three fields, for deduplication and to pin the sampled version. Fields differ per operation; read the JSON Schema the running service provides before calling. All public tools use the `{"request": {...}}` wrapper. Publishing and validation keep the same `oneOf`, `const`, field constraints and descriptions, and both the outer and business objects reject unknown fields. Results are uniformly `{"ok":true,"operation":"...","data":{...}}`; errors contain `ok:false` and `error.code/message`, and field validation errors also carry `field`. PNGs come back as MCP image content.

All 195 public operations (70 of them background, 91 batchable) must declare a complete `outputSchema`; the full profile publishes it, and the `output_schema` in the capability detail matches it; success data and failure errors are strictly mutually exclusive. The registry validates business results at the execution and deduplication boundaries, MCP validates the complete returned wrapper, and an operation missing its result contract cannot register. Background operations must also have a terminal `job_result_schema`; non-background operations may not have that field. The capability detail describes nested schemas with local `$defs/$ref`, so querying its own schema validates too; the actual HTTP keeps all root constraints. `output_contract` means the service implementation returned a result that does not match its declaration, and cannot be taken as evidence that a change was rolled back.

Append images with `layer_import_images`: it requires `state` and `paths` of 1–128 absolute paths, with an optional `parent_deformer_id` naming an existing parent deformer; when omitted, the layers bind to the model root. Optional `anchor_layer_id` draws the batch just in front of that layer (or mesh), `in_front=false` just behind it, the first image in front of the rest, written as explicit draw-order overrides; optional `at` `[x, y]` centres each image on that canvas point (kept inside the canvas); `as_reference=true` imports them as reference layers in the layer stack (no mesh, never exported), as dropping onto the layer list as a reference does, still one history node. Transparent edges are trimmed and the image is centered; the raster keeps its original resolution, and when it exceeds the canvas only the canvas rect is scaled down proportionally to fit (layer density above 1 pixel per canvas unit), while the mesh is generated at canvas resolution. Each file is at most 64 MiB and 16 megapixels, and a whole batch at most 32 megapixels. One success appends exactly one history node, and if any file fails, nothing from the batch is published; because it reads files, it cannot be an atomic document batch member. Get the new source layers and mesh handles from the job's terminal `affectedLayerIds/affectedObjectIds`. The original pixels are written into the project, so reopening later does not depend on the input files. Each image gets its own mesh in the authored rig (`canvas_mesh_create`, under the given parent), which the generator never regenerates; undo cancels the import.

Transform a whole layer with `layer_transform` (any layer: imported or from the PSD, at the root or under any deformer, bound or not): it requires `state/layer_id`, then either `matrix [a,b,c,d,e,f]` (`x' = a·x + c·y + e`, `y' = b·x + d·y + f`, canvas units, y down), or `translate [x,y]`, `scale` (a number or `[sx,sy]`), `rotate` (degrees, clockwise on screen) and `pivot [x,y]`; it composes with the layer's existing transform. Pixels, atlas tiles and texture coordinates do not change, and no regeneration is triggered: each of the layer's meshes moves by the transform at the rest pose (keyforms keep their offsets), the layer records where its pixels are shown, and painting follows (rotated layers too). It is one undoable history commit and can join atomic document batches.

Rebuild meshes with `layer_mesh_rebuild` (requires `state/layer_id`): it regenerates the layer's meshes from its current pixels and mesh settings, migrates keyforms, paths, weights and glue to the new topology, and keeps layers that were transformed as a whole in place. Meshes are only regenerated on import, by this command, by the `rebuild_mesh` option of painting and image replacement, on mesh setting changes and on regeneration; a layer without a mesh gets one the first time painting produces visible pixels. Pixels painted outside the mesh are not shown; the mesh panel in the UI shows the share and offers **Rebuild from pixels**.

Remesh along texture structure with `layer_mesh_structure` (requires `state/target`, a mesh id or `mesh:<id>`; optional `settings`: `sensitivity` 0–1, `min_length` in source pixels, `near_density` the spacing along lines relative to the kept edge rows (default 1), `fill` whether to add vertices between lines (default false: only the edge rows and the lines carry vertices), `far_density` the fill edge length relative to the former inner edge length, `bands` whether drawn creases get a row on each side with rungs across (default false), `kinds` a subset of `FOLD`/`SHADE`/`PATTERN`, `max_lines` ≤64, `max_vertices` ≤16000). The outline row and edge band stay; the inside is rebuilt along the creases, shading boundaries and pattern lines drawn into the texture. Keyforms, paths, weights and glue migrate as usual through one `canvas_mesh_rebuild` record. On a mesh with an interior effect its detected TOPOLOGY guides are replaced (drawn guides and guides marked FOLD stay) and the effect is baked again in the same history node (`interior_rebaked`). A region that cannot be meshed or a result over `max_vertices` fails without changing anything. `layer_mesh_structure_preview` (read-only, same arguments without `state`) returns the lines found (kind, `followed`, `banded`, in source pixels and canvas units) and the new mesh's canvas points and triangles.

### Mesh topology

`canvas_topology` (`request.mode` is `topology`) writes the same `canvas_topology` authoring journal entry as the editor's topology actions. It requires `state/id/action` (`id` is the mesh ID; `vertices` are vertex indices of the current mesh, none by default). Each of `anchors` is either an existing vertex `{vertex}` or a free point `{x, y}`, and `add_points` takes free points only. A refusal fails as `topology_refused`. Indices come from the current mesh, so use a fresh `state`: `mesh_get_topology` reads the vertex indices with their rest positions (the mesh's own space, the one `add_points` anchors use), the triangles and the outline edges. On a commit the result's `new_vertices` lists the vertices the action created or left selected, by their indices in the new mesh (the points `add_points` created, the points along a `knife` cut, the vertex a `merge` made); batch members do not return it. `action`:

| `action` | Input | Result |
| --- | --- | --- |
| `merge` / `duplicate` / `delete` | `vertices` | Merge into one point, duplicate the vertices and the faces they fully cover, or delete and fill the gap (at least three vertices must remain) |
| `connect` | exactly two `vertices` | Splits the edges the straight line between them crosses and joins them with new edges; fails when they are already joined or no new edge can be cut along the line |
| `subdivide` / `split` | `vertices` or `edges` | Subdivides the edges the selected vertices span, or the given edges |
| `knife` | `anchors` | Lays edges along a polyline (the editor's mesh points Line): each anchor lands on the mesh and every two neighbouring anchors are joined by an edge; an anchor is `{vertex}` or `{x, y}` in the mesh's own rest space |
| `add_points` | `anchors` (`{x, y}` in the mesh's own rest space, as for `knife`) | Adds one vertex per point: inside a triangle 1→3, on an edge it splits the edge, outside the mesh one triangle grows from the nearest visible outline edge; a point on an existing vertex is ignored; the new vertex's UV, keyforms, blend shapes and weights derive from the vertices around it by one set of weights, then edges are flipped where the texture mapping stays the same |
| `delete_edges` | `edges` (`[[a, b], …]`, required; `vertices` does not decide which edges go) | An inner edge is replaced by the other diagonal of its quad (fails when the quad is not convex at rest, in any keyform or in any blend form), an outline edge removes its triangle together with any vertex no longer used; the whole batch fails when a vertex would be pinched between two fans or no triangle would remain |
| `retriangulate` | `vertices` (empty for the whole mesh) | Flips edges around these vertices toward Delaunay (judged in canvas space at the default pose), only quads whose texture mapping stays the same and that are convex at rest and in every keyform and blend form; vertices and keyforms are unchanged; with nothing to flip it is no change (`applied:false`, no history) |

An action that does not apply returns an error and writes nothing. Keyforms, blend shapes, vertex groups and glue migrate with the topology (glue pairs of deleted vertices are removed) and paths are rebound; when the mesh carries an interior effect that matched it before the edit, the effect is baked again on the new mesh in the same node (a failed bake does not refuse the edit; the effect reports that the mesh changed). The result goes through the [geometry check](#geometry-checks-and-dry-runs). For the algorithms and a comparison with Cubism's mesh editing see [Mesh topology](../../zh/spec/MESH_TOPOLOGY_AND_SPLIT.md#手工拓扑编辑) (Chinese).

### Copying objects, find and replace, ID conversion

`object_paste` (`sources` as `mesh:/warp:/rotation:/part:/parameter:` handles; optional `parent`, `part`, `parameter_group`, `ids`) copies meshes, deformers (with their subtree and its meshes), Parts (with their children) and parameters. New IDs are fixed when the edit is recorded (`<id>_copy` by default, numbered on a clash, or given per source in `ids`), so replay yields the same IDs. Parents, masks, glue, paths and vertex groups among the copies point at the copies; references to objects not copied stay. With `parent`, meshes rebind in canvas space and deformers move in local space. A paste is planned on the authored rig: objects a swing, simulation or interior effect generates are not in it, naming one is refused, and a copied subtree leaves them out. A copy is not its layer's mesh: looking a layer's mesh up (picking, and the IDs splits and deletions keep) finds only the original, and deleting the layer deletes its copies too; a copy takes its draw order by its own mesh ID, and a layer transform does not move it. Called alone, the result's `ids` maps each source handle to its new ID exactly as recorded (the request is committed with every new ID fixed on the captured version), and `paths` maps the deform paths copied with the meshes (`path:<old id>` to the new ID); as a batch member, read the new handles from `changed`.

`mesh_duplicate` (`source`, `targets`) lays the source mesh's topology over each target mesh by canvas position, with UVs from the target's own texture; each target gets one `canvas_mesh_rebuild` record, so keyforms, paths, weights and glue migrate as usual.

`object_find` (read-only) searches names or IDs (`field`) among `kinds`, with `find`/`replace`, `regex`, `match_case`, `prefix`, `suffix`, `swap_sides` (L/R, Left/Right and 左/右 swapped where they stand as words of their own) and `standard_ids` (Cubism 2 style IDs to Cubism 3 standard IDs), returning each match before and after; `object_rename` commits the same arguments at once; both list only the authored rig's objects, so what a generator adds after the journal keeps the name and ID its generator gives. Renaming IDs and `object_convert_id` (`renames`: `target` and the new `id`) write one `convert_id` journal entry: keyforms, blend shapes, masks, glue, paths, vertex groups, motion curves, expressions, the pose, hit areas, user physics and swing targets follow (standard expressions not yet taken into the document find standard parameters under their new IDs; a copy over the bangs takes its ID from its original and is itself refused as `generated_copy` by conversion, paste and mesh duplication), generated overrides and deferred panel edits after it replay under the new IDs, and built-in physics, motion presets and expressions find the standard parameters again under their new IDs; parameter snapshots, each workspace's authored pose and the timeline bookmarks, shy and frozen tracks take the new IDs with the same commit and the old ones back on an undo or a checkout from before the conversion. IDs must be 1–64 ASCII letters, digits or underscores starting with a letter; duplicates within a kind, taken IDs and generator-owned objects (simulations, interior effects, swing parameters) are refused without changing anything, and so are meshes the skeleton binds or weights, bone parameters and bone deformers (the skeleton bakes before the journal under the original IDs), and the skeleton cannot newly bind a mesh whose ID was converted or that the journal made (a pasted copy, a mesh created on the canvas); the automatic skeleton leaves them out. A conversion onto an ID that a deleted parameter's leftover motion curve or expression entry still names is refused, naming that motion or expression. Splits, layer deletions and regenerations keep meshes under their pre-conversion IDs in the base stage and let the journal entry rename them; a regeneration's three-way merge maps the generated rig onto the converted IDs too. Exports check the IDs of the model they actually write: two objects of one kind under one ID (warps, rotations and the runtime's virtual bones share one; parameter folders, simulations and colliders included) refuse the export, IDs outside the alphabet only warn.


### Textures and atlases

A layer's canvas rect (canvas units, fractional allowed) and its raster pixels are independent: native density is raster pixels per canvas unit, and an atlas tile stores `raster pixels × density × fit`. Density defaults to 1; when the budget is exceeded, unlocked tiles share one fit (≤1) and shrink together, and locks and pins that cannot fit are dropped (the explanation is written only to the program log, not to the tool result). Geometry is unaware of the atlas: density, budget, pins and repacking only change tiles and bound UVs, not meshes.

- `layer_get_texture` (query): `layer_id`; returns `canvas_rect`, the integer bounding `bounds`, `raster`, `native_density`, `override{density,lock,pin}`, `deleted`, `tile` (page, texture pixel rect, texture pixels per raster pixel `scale_x/scale_y`, density, lock and pin; null for transparent or deleted layers) and `atlas_fit`, all from the same captured version.
- `atlas_get` (query): optional `page` filters tiles; returns the effective `budget{page_size,max_pages,padding}`, `fit`, `notices`, `auto` (whether it packs automatically every time), `pages[{index,width,height,tile_count,occupancy}]` and `tiles`. For mesh-packed tiles, `occupancy` counts only the cells the mesh actually uses. `notices` points out a page count over budget and tiles stored below their set density to fit the pages: a saved arrangement keeps its `fit`, so after switching to a higher-resolution image neither case shows up in `fit`. Results of texture edits and of `workspace_apply_edits` batches containing them also carry `atlas_fit` and `notices`; `atlas_set_budget` plus `atlas_pack` (which can go in the same batch as the replacement) brings it back within budget.
- `atlas_render_page` (read-only background job, requires `request_id/project_id/state`): `page`, optional `max_size` (64–16384, default 2048, scaling down by the long edge); the terminal status contains `revision`, the original and rendered sizes, `sha256` and the page's layers; the PNG comes back as image content, and `job_get/job_wait` can fetch it repeatedly.
- `layer_set_canvas_rect`: `layer_id`, `rect{left,top,width,height}`; moves and scales the layer so the canvas shows its pixels in that rect, i.e. one `layer_transform` starting from the current display position (rotated layers are rejected; use `layer_transform`). Pixels, texture and generation input are unchanged; meshes move along with their keyforms; works on any layer. `layer_get_texture`'s `canvas_rect` is where the layer is currently shown. The same rect is no change.
- `layer_replace_image`: `layer_id` plus one of `path` (absolute, PNG/WebP/TIFF/BMP, single only), `png_base64` or `material_id` (a material in the library; the layer becomes linked to it), with optional `fit` (`stretch`, the default, fills; `contain` keeps the aspect ratio, centers and pads with transparency) and `rebuild_mesh` (default false). The canvas rect is unchanged, the generation input freezes at the pixels before the first replacement, meshes, keyforms and bindings are kept, and only the tile and UVs change; `rebuild_mesh=true` regenerates the layer's meshes from the new pixels instead, and is rejected when the layer has authored edits or materialized geometry. A single call checks state before reading the file; batch members only accept `png_base64`, and giving `path` fails the whole batch with `invalid_edit`. At most 16MP; identical pixels are no change.
- `atlas_check_placement` (query): `placements` is 1–128 `{layer_id, page?, x?, y?, rotation?, density?}`, omitted fields keeping their committed values; returns `clear` and, per tile, the target `page/x/y/width/height/rotation`, `outside_page` (whether the rotated bounding box leaves the page or the page number exceeds the budget) and `overlaps` (tiles its mesh would intersect). It compares against the other committed tiles and the tiles checked together, with exactly the same rules as on commit: only when two tiles' bounding boxes, grown by the padding, intersect are the cells their meshes actually use (grown by the padding) compared; when neither has a mesh and neither is rotated, rectangles are compared. The atlas view uses the same rule when dragging, scaling and rotating; a `clear` placement always lands as given, and conflicting placements are rejected by the commands below.
- `layer_set_pixel_density`: 1–128 unique `layer_ids`, the required `density` (continuous in 1/64–16, `null` restores 1), and optional `lock` (omitted keeps the current value). With an existing arrangement each tile keeps its top-left corner; if growing would push it off the page or into another tile's mesh, the command is rejected with `tile_collides` and nothing changes.
- `atlas_set_tile`: `layer_id` and `pin{page,x,y,rotation?}` (texture pixels; `x`, `y` are the top-left of the unrotated rect, `rotation` is any number of degrees around the tile center, default 0) or `null` to drop it into free space; the page number must be within budget. The position is saved in the arrangement (the `atlasArrangement` setting); an auto-packed atlas first saves the current layout (`auto` becomes false), and with an existing arrangement each tile is first saved at its current position with its mesh coverage filled in, so other tiles do not move and do not squeeze into the space vacated. A position that after rotation would leave the page or intersect another tile's mesh is rejected with `tile_collides` and nothing changes; check first with `atlas_check_placement`. To move and scale at once (for example scaling with the opposite corner fixed, or swapping two tiles), put `layer_set_pixel_density` and `atlas_set_tile` in the same `workspace_apply_edits`: only the layout after the whole batch is checked, exactly like **Apply** for an adjustment session in the atlas view.
- `atlas_set_budget`: `page_size` (a power of two in 256–16384), `max_pages` (1–64), `padding` (0–32) and `auto`; give at least one, omitted ones keep their current values; the budget is written to the `atlas` setting. `auto=true` deletes the saved arrangement, after which every rebuild packs automatically by rectangles (MaxRects); `auto=false` saves the current layout.
- `atlas_pack`: packs once and saves the result (`auto` becomes false). Optional `shape`: `mesh` (default) packs by the texture coordinate coverage of each layer's final meshes (cells of 4 raster pixels, plus padding), so rectangles can nest and each tile writes only its own cells; `rect` packs by rectangles. Tiles are placed by occupied area from largest to smallest; when they do not fit the budgeted pages, all unlocked tiles shrink together in 1/64 steps. Optional `layer_ids` moves only those tiles, the rest keeping their position and fit. It also clears the pins of auto packing and the overrides of layers that no longer exist; packing the same input again is no change. If a later mesh edit goes beyond the coverage at packing time, `atlas_get`'s `notices` suggests repacking. A tile's `shaped` means it was packed by mesh coverage.

All six edits are process jobs and atomic batch members, committed through the `WorkspaceTextureEdits` pure candidates, a full rebuild and CAS; one success appends exactly one history node, and undo restores the previous tiles. The terminal status is `project_id/state/history_node_id/revision/applied/layers/atlas_fit` (possibly with `geometry_diagnostics`), where `layers` are the layers whose texture actually changed.

Control requests still follow the mutation deduplication and workspace token rules. Sessions may own their own tokens; the global physics library uses a separate library token. Reads, renders, playback frames and private drafts are not document commits; the `kind/job_backed/batchable` discovery metadata tells the execution modes apart.

Project save and open in the GUI and MCP call the same application-layer lifecycle interface, executed by the project controller held by the desktop adapter. A GUI entry can first confirm unsaved changes with the user and then explicitly pass the discard flag; MCP does not call confirmation dialogs and rejects switching with unsaved changes by default. A GUI call keeps the project and state from when it started and commits as the trusted user.

GUI field completions are rebuilt and committed asynchronously in an application-layer queue, and saving first waits for queued completions; a rejected draft cannot silently overwrite the project through a save. The queue only carries its own consecutive commits; outside changes or reopening the project still invalidate the old state. Queries keep reading the committed capture and do not publish unfinished UI drafts. `workspace_inspect` and the skeleton/motion compound queries use one separate session, so the returned state, model, settings and history belong to the same capture; commits or reopens during the query do not mix into that result. `scope=preview` reads the committed pose/locks; animation evaluation frames and uncommitted GUI values do not replace that pose. List discovery returns `items/total` and `next` where applicable. Jobs are owned by the app and can still be queried after a disconnect and reconnect; they are not restored after an app restart.

## Errors and recovery

When an immediate call fails, the tool returns `ok:false` and a structured `error`. When a background job fails, the `job_get/job_wait` query itself still returns `ok:true`, so check `data.status`; a `failed` job's `data.error` uses the same structure and has no successful `result`. Job queries, lists, disconnect and reconnect, and retries of the original request all keep the original error. After fixing the problem, a new attempt must use a new `request_id`; reusing the old ID gets the original result.

| `error.code` | What to do |
| --- | --- |
| `invalid_request` | Read the current schema; `field` locates the field |
| `output_contract` | The service implementation returned a result that does not match its declaration; `operation/field` locate the contract problem. Query the actual state of the project or job first; do not assume from this that the change was rolled back, and do not simply redo it |
| `invalid_argument` / `invalid_edit` | Fix the arguments or edit; batch errors also carry `edit_index` and `edit_operation` |
| `not_found` / `id_conflict` / `owned_by_generator` / `key_incomplete` / `topology_refused` | Refusals you can tell apart, with `target` (`kind:id`, such as `parameter:ParamAngleX` or `hit_area:HitAreaHead`) and, for a batch member, `edit_index` and `edit_operation`: the object, key or entry named does not exist; a new or converted ID is taken (a deleted parameter's leftover motion curve or expression entry included); the object belongs to a swing, simulation, interior effect or the skeleton and is handled in its panel; a keyform edit's key lacks an axis the target is directly bound to; the topology action does not apply to this mesh and selection. Nothing was committed |
| `tile_collides` | After the move, rotation or density change, the tiles in `layer_ids` would be pushed out of their arranged positions (off the page or intersecting another tile's mesh), and the whole change was not committed; find another position with `atlas_check_placement`, or put the related moves in the same batch |
| `state_conflict` | Reread the project; the error carries `expected_state` and `actual_state` |
| `project_conflict` | Confirm the target project; the error carries the nullable `expected_project` and `actual_project` |
| `request_id_reused` | The same ID was used for a different operation, arguments or author; use a new request ID |
| `unsaved_changes` | Save first, or explicitly pass a supported discard flag |
| `workspace_busy` | Wait for the ongoing work to finish, then read the current state |
| `io_error` / `permission_denied` | Check the file path, access permissions or disk according to `message` |
| `invalid_state` / `operation_failed` | Diagnose the business precondition or execution problem from `message` and the current project state |

`cancelled` is a separate job status, not an error code. A late cancellation or refresh exception after a successful commit keeps `completed` and the committed result; it is no basis for claiming the change was rolled back.

`rig_create_warp` resolves `mesh:<id>` in the captured candidate model and requires unique targets and a common parent warp. When `id` is omitted, it is assigned only once; an explicit `id` can be referenced by later items in the same batch, and the new warp also appears in the batch's `changed`. `rows/columns` default to 16, range 1–32; the actual lattice aligns with the parent lattice, ending at no more than 64 per axis; go by the actual divisions in the object detail. `fit_local` defaults to true, clipping to a conservative envelope of the ordinary keyforms and independent blend shapes stacked together, and remapping geometry and blend shapes accordingly, keeping UVs, scalar channels, paths and vertex weights. Fitting is rejected when the envelope goes beyond the parent domain; enlarge the parent domain first, or use `fit_local:false` to keep the full parent domain. Freely placed canvas warps still use `canvas_warp`. A single call's terminal `job_wait/job_get.result` contains `target/state/history_node_id`; failure or cancellation before commit publishes no new warp, and a refresh failure or late cancellation after commit keeps the success and the handle.

## Atomic document edits

`workspace_apply_edits` shares the outer `request_id`, `project_id` and `state`. Each item in `edits` is `{"operation":"...","request":{...}}`; the inner request only fills in that single tool's business fields and does not repeat the context fields. Members use the same business schema the single tool publishes; unknown fields and unsupported members are rejected before any candidate edit.

### Geometry checks and dry runs

The geometry authoring journal entries of `rig_deform`, `keyform_apply`, `rig_edit_structure`, `object_edit_appearance`, `canvas_warp/rotation/glue/topology`, `canvas_deform_stroke` and `path_deform` go through a geometry check after the full application-layer rebuild and before the formal CAS; the corresponding GUI journal and MCP use the same rules. A batch only checks the final candidate, allowing earlier items to degrade temporarily and later items to repair them. Other document operations do not get a wider check because of this rule.

`workspace_preview_edits` uses the same ordered candidate preparation, rebuild and check as a formal commit, but calls no projection or CAS and does not change state, history, the unsaved flag, the pose or resources. It is a read-only background job that still requires `request_id/project_id/state`; `job_wait/job_get.result` gives `dry_run:true`, the input `revision`, `candidate_revision`, `would_change`, `would_commit`, `changed` handles for new objects, and `diagnostics`. When creating a Warp, Rotation or Glue, provide an explicit `id`, then submit the same edits to `workspace_apply_edits` on the same state; only then can candidate revisions be compared repeatably. A dry run reserves no object IDs and does not authorize skipping later state conflict checks. Members other than geometry are not accepted for dry runs; the operation's schema defines what is supported.

`workspace_preview_regeneration` (called through `workspace_call` in the compact profile) dry-runs any document operation (except resource layer operations) the same way, to see the regeneration result before committing: `checkpoints` lists the checkpoints the commit would write to the journal (`index` is its position in the candidate journal; `kind: "regeneration"` is generated output merged onto the user's rig, with `issues` in the same format as `rig_update_generation`'s; `kind: "materialized"` is the current authored state materialized before a new entry), `added`/`removed` are the handles of objects the candidate adds and removes, plus `dry_run:true`, `revision`, `candidate_revision` and `would_change`.

The check covers the parent-local geometry of affected objects, including combinations of ordinary keys, blend shape keys and weight limit points. Non-finite coordinates, illegal topology and newly introduced zero-area degeneration block the commit, returning `geometry_unsafe` and structured `diagnostics.violations`. New local flips and local collapses below 1% of the reference triangle's area are kept in `diagnostics.warnings` and do not block by default: existing authoring workflows allow intentional folds, so a flip count cannot be taken as a rigging failure. Existing flips, degeneration and collapses are counted separately and do not block edits that add no new defects. Invertible affine mirroring and compression of a whole surface pass, while zero-area transforms are still rejected. When a topology change cannot keep the old triangle identities, the new mesh's reference geometry is used. When the Cartesian product of blend coordinates exceeds 16384, deterministic scattered sampling is used instead, keeping the combinations at both ends, and the candidate is no longer rejected with GEOMETRY_SAMPLING_LIMIT. The report's scope states explicitly that large combination domains are sampled; this is not a proof over all combinations.

Copies over the bangs (`<original id>_SeeThrough`) are made anew from the settings on every build and cannot be edited directly: any document operation naming one in a reference field (`target`, `id`, `layer_id`, `meshes` and the like) returns `generated_copy`, while names and other free text do not count (`details.target` is the copy, `details.original` the original to edit instead); edit the original or the settings `seeThroughBrows` / `seeThroughEyes` / `seeThroughOpacity`. Inspecting a copy through `objects` gives its original's layer as `topologyInfo.layerId` and the original as `topologyInfo.seeThroughOf`. The eyes show through a window in the bangs instead: the finished rig clips each bang over them inverted by the eye parts and draws a copy of the bang (`<bang id>_SeeThrough`, `seeThroughOf` the bang) clipped by them; those masks are the finished rig's alone, the bang's `topologyInfo.seeThroughWindow` lists them, and its own masks stay empty in the document - do not write them back as the bang's `masked_by`.

When the candidate only appends authoring journal entries relative to the starting document, the check scope is derived from the new commands: the meshes, Warps and Rotations the commands target directly, all their children, the glue partners of the meshes involved, and the targets of unbaked swings and baked simulations (these two generators recompute their targets on every replay). Commands that create or reattach objects, mesh rebuilds and other commands whose affected objects cannot be listed one by one, and candidates that also change document content outside the journal, fall back to comparing all objects. Classification within the scope is the same as in a full comparison. The report's `coverage` gives `mode` (`full` or `scoped`), the number of objects actually compared `checkedTargets` and the object totals of both models `totalTargets`; when the scope is narrowed, the `scope` text notes that the other objects were not compared.

Diagnostics cover only these sample points; they do not prove interpolation between keys, combined parent deformation, glue, masks, pixel coverage, physics or visual quality. A dry-run result belongs to its input version; once the project is edited or reopened, the result is no basis for the new version.

Formal geometry authoring commits may also return `geometry_diagnostics`, with the same blocking items and warnings; the field is omitted when the geometry check involved no objects. Flip warnings do not need to be expressed by rolling back the change.

Zero-area detection includes floating-point tolerance: a triangle whose absolute signed area is below `1e-12`, or whose area ratio is no more than `1e-6` of the reference shape, counts as numerically degenerate; coincident vertices leaving a tiny negative area are not reported as just a flip warning.

GUI parameter definitions, folder positions and parameter keys can combine into one shared commit; the canvas journal, internal typed edits and the field completion queue also enter the same candidate/rebuild/CAS boundary. GUI swing sessions, field edits, simulation changes and offline baking keep the state from when they started, so old results are not committed to a reopened or changed project; the GUI author is designated `user` by the trusted adapter.

Parameter definitions are now written to the journal in actual edit order, and deletion reads the preceding keyforms and the last default value; static parameter overrides in old projects stay readable for compatibility, and history is not rewritten. Pure channel changes such as opacity and color are persisted too; recapturing an identical existing key does not append history.

87 operations currently support batching (including material layer adding, registration positioning, finalizing, whole-layer transforms, mesh rebuilds and the six texture edits): settings, layer classification/mesh configuration, source polygon/component/depth splits and delete/restore, parameter definitions, independent warp creation, rig deform/keyform/structure/appearance/vertex groups, six source paint operations, seven skeleton changes, six motion changes, four canvas edits, path put/delete/deform, swing put/delete, physics put/delete/config/fit, and simulation put/delete/bake/clear_bake and model_apply_preset. Single calls of settings, classification, mesh configuration, source splits, image positioning/cancelling, layer soft delete/restore, independent warps, painting, physics, simulation and presets use background jobs; a batch runs the same application-layer candidate directly, progress for splitting, painting, baking and fitting includes the batch member it belongs to, the whole batch can be cancelled during preparation, and members' single-operation jobs are not nested; `classic_front_hair/classic_back_hair` support `sway:false`, turning off that type's classic swing after removing the simulation. Only `batchable:true` from the discovery tools means support; GUI field completion is wired into the asynchronous candidate queue, and generation settings/classification/mesh drafts are converted into shared pure candidates.

Material layer adding supports imported models and self-created parent deformers. The application candidate converts the source canvas geometry into the actual parent's neutral coordinates and saves the mesh creation record; re-registration uses the original processed pixels, replacing the created geometry in place while keeping the object ID and parent. Existing dedicated bindings or mask dependencies still reject single-layer positioning. Material layers keep the material's original resolution: after trimming transparent edges, the pixels become the layer raster directly, and the canvas rect given by material placement or registration becomes the layer rect (`canvasUnitsPerPixelX/Y` is the actual ratio); for example, a 1024-pixel material registered to a 32-unit region is a 32-unit, 1024-pixel layer. Registration by translation/scale (including explicit mirroring, which only flips rows and columns) involves no interpolation; only registration with rotation rasterizes to the bounding box at the material's own density. The material manifest and layers both keep the original pixels and no longer shrink back to canvas resolution. Before allocating, coordinates, the 16MP bounding box, the 16MP raster and the density limit are checked, and the preparation stage responds to cancellation; continuous GUI placement goes through a separate application session, and saving excludes the preview and waits for the formal confirmation.

Each item runs on the previous item's candidate document and rebuilt model, so a parameter can be created and then bound to keyforms or motion tracks in the same batch; a canvas object created earlier can be referenced in later edits. Objects that later items reference should get stable IDs. When an optional ID is omitted, the result's `changed` contains `kind:id` handles for generated objects; retrying the same request returns the original handles.

Only a successful final CAS publishes the document, model and one history node. A member edit or rebuild failure, cancellation before commit and state conflicts all keep the original workspace. Batches with no change, or that return to the original document, neither advance state nor append history. Member execution errors return `invalid_edit` with the 0-based `edit_index` and `edit_operation`; schema errors return `invalid_request` with the field path. Session changes, project switching, resource I/O, read-only time simulation (simulation_simulate) and nested batches cannot be members. A batch returns a process job handle; read the status and `data.result` through `job_wait/job_get`; a successful result contains `project_id/state/history_node_id/revision/applied/edit_count/changed`. Progress is reported while preparing each item and baking; cancellation before commit publishes no candidate; after a successful CAS the complete result is kept immediately, and a late cancellation or refresh failure still returns completed. Business failures keep the classification and index above in the job's `error`; schema errors return before the job is created. Disconnecting or cancelling the wait does not stop the job, and retrying the original request ID gets the same job back; direct internal GUI calls still use the same command boundary.

## Parameter snapshots and history annotations

When `snapshot_create` omits `values`, it saves the current authored pose; to save evaluated values during playback, pass the sampled values explicitly. `snapshot_update` can rename only, replace values only, or both; omitted fields keep their values. Deleting a snapshot does not change other snapshots' numbers. The GUI snapshot bar and MCP share neutral edit commands, the data is captured from the runtime, and save/reopen keeps snapshot IDs, numbers, parameter values and history annotations.

`snapshot_apply` keeps the values of locked parameters, ignores parameters in the snapshot that have been deleted, and clamps old values to the current parameter ranges. Applying a snapshot in the GUI is the same as in MCP and is not affected by the timeline auto-key toggle; to record the timeline, call the motion editing tools separately. No change keeps the original `state`; an actual change returns its own `state`, `project_id` and `history_node_id`. History annotations only change a node's display title, note and hidden flag; node content and branch relationships stay the same.

Parameters and locks omitted from `preview_set` keep the values in the runtime's committed pose; `snapshot_apply` likewise follows the committed locks, and parameters it does not hit keep their values. Animation evaluation frames and uncommitted GUI display values are not the merge baseline. `preview_reset` restores all defaults and releases locks. These three share a separate application command and auxiliary CAS, appending no rig history or auto keyframes; a logical no-change does not advance state, but can still restore the correct UI pose and stop playback. Saving also uses the captured persistent pose and locks per workspace, and a duplicated workspace's pose is registered immediately; in the archive these are projected into the workspace fields of `workspace.json`.

## State and history

- Write calls that advance model history need the latest `state`, and a success returns the state for subsequent calls. When it is stale, re-inspect and reconcile the edits instead of blindly overwriting.
- Edits within a batch are validated and rebuilt first and committed on success; one `rig_deform` / `keyform_apply` can contain 1–128 changes, and a single deformation can contain 1–16 operations.
- Keyforms generated by swing and simulation (the key has a generated parameter that is not at its default): `set` in `rig_deform` and `keyform_apply` is recorded as a generated result override and merged after the generators; `copy` to or from these lattice points, `delete`, and `parameter_keys` acting on a generator's axis are rejected, with the generator named in the error. Using a generated parameter on other objects (keying, renaming, changing the range) first writes the parameter into the project as the generator currently defines it, after which it behaves like an ordinary parameter; a generator's own parameters cannot be deleted with `parameter_delete`.
- Ordinary writes with no change should not create history nodes; `checkpoint` is the explicit exception. Restoring is a write and moves HEAD; continuing to edit from an old node forms a branch, and the original branch is kept.
- `project_save_as` gives an absolute path for the first save or a save to another location; `project_save` saves to the current location. `project_open` opens a project archive; with unsaved changes, first wait for a save job to succeed, or explicitly give `discard_unsaved=true`. These operations do not open GUI dialogs. `project_export_model` writes the deliverable files but does not replace saving the project. Staged assets are neither added to the model nor saved to disk.
- After a timeout or disconnect, check with `workspace_inspect` and `history_list` whether the change was committed before deciding the next step.
- Multi-tool cross-call transactions, a structured `history_diff` and `task_*` execution control are not part of the current public interface.

### General shapes and physics

`rig_deform` operations include `translate`, `scale`, `rotate`, `arc`, `curve` and `landmarks`. Coordinates use a normalized convention within fixed input bounds, X right, Y down, angles in degrees. Selections and falloff can limit the affected range; arbitrary per-point mesh arrays are not accepted.

`keyform_apply op=seed` samples the existing shape at the given key; `copy` copies an explicit source key; `set` writes channels or rotation shapes; `delete` removes the corresponding key data. A new parameter produces no motion by itself; shapes must be bound to it.

`keyform_apply op=mirror` reflects a keyform across a vertical canvas line. On commit it expands into ordinary `set` (and `copy`) entries, so replay never computes the reflection again:

| Field | Meaning |
| --- | --- |
| `target` | The source mesh, Warp or rotation deformer |
| `destination` | A target of the same kind; defaults to `target` (the same object); `auto` finds the object on the other side by L/R, Left/Right or 左/右 in its ID or name |
| `from` / `all_keys` | The source key; or `all_keys: true` for every keyform cell of the source, on one object only the keys on `side` (`positive`, the default, or `negative`) |
| `key` | The destination key; by default derived from `from`: left-right parameters flip about their default, a sided parameter (ParamEyeLOpen) switches to its other side when the destination binds that or neither, and destination axes left out take their defaults. Given explicitly, it must include every axis bound directly to the destination |
| `reflect` | The parameters that flip; by default the ordinary parameters whose range is symmetric about the default and that are a 2D link's horizontal axis or whose ID ends in X or Z |
| `axis_x` | Canvas x of the mirror line; defaults to the midpoint of the two objects' rest bounding-box centers (one object: its own center) |
| `channels` | What to carry over: `geometry` and `copy` channel names; geometry only by default |

A mirror covers the object's own deformation: both objects' points are mapped to the canvas through their parents at the default pose, each source point's move from its rest shape has its x reversed, is interpolated on the source triangles (a Warp's cells split corner to corner) at the target point's reflected position, and is mapped back into the target's parent space; a rotation deformer mirrors its origin's move and reverses its angle change. Symmetric objects and pairs correspond point to point. Blend shape keys are not supported.

`keyform_apply op=reset / interpolate / paste` writes a key's whole geometry (or only the points `vertices` names). On commit each expands into ordinary `set`s, so replay never reads another key; a geometry `set` on keyforms a generator owns is recorded as a generated override. `paste` writes moves: a mesh's from its rest, a Warp's or rotation deformer's from its default-key shape; the source is sampled when that command compiles, so in an MCP batch a later `paste` reads the candidate the earlier members wrote (so two `paste`s cannot swap A and B, in one batch or in two commits: the second reads what the first wrote; to swap them, `copy` A to an empty key C first, then paste B onto A and C onto B, which one batch may do in that order); the editor fixes the source when copying and computes all its `set`s from the model before the paste:

| Field | Meaning |
| --- | --- |
| `target` | Mesh, Warp or rotation deformer; the source for `paste` |
| `key` | The key written; it must include every directly bound axis of the target |
| `vertices` | Only these points change (mesh vertex or Warp control point indices); the rest keep the key's current shape. Not for rotation deformers |
| `to` (reset) | `default` (the default): the shape with the `along` parameters at their defaults; `rest`: meshes only, the undeformed mesh |
| `along` (reset) | With `to: default`: the parameters taken to their default; default all of the key's |
| `parameter` (interpolate) | The axis to interpolate along; defaults to the one axis the key sits between two keys of, and is required when there are several. Linear by position between the shapes at the neighbouring keys |
| `from` (paste) | The source key; the source's missing axes take their defaults, and the shape is read interpolated there |
| `destination` (paste) | Default `target`; for geometry another object must be of its kind with the same triangles (a Warp: rows and columns) under the same parent, or the paste is refused |
| `all_keys` (reset) | In place of `key`: every keyform of the object back to its default-key shape (restoring a deformer's shape) |
| `ratio` (paste) | 0–1, default 1: how far the key moves toward the pasted values; below 1 it blends |
| `flip` (paste) | `horizontal` or `vertical`: a Warp's columns or rows reversed; a mesh's vertices paired by their mirrored rest places (the rest must be symmetric that way, or it is refused); each point takes its partner's move turned around; a rotation's angle change reversed |
| `channels` (paste) | Any of `geometry`, `opacity`, `drawOrder`, `multiplyColor`, `screenColor`, default geometry only; channel values blend by `ratio` too |

`keyform_apply op=multi_key` changes the channels of many keyforms of several objects at once, expanding into one channel-only `set` per keyform: `targets` (meshes, deformers or parts); `keys` (partial keys a keyform must match one of) and `ranges` (per parameter, the key values allowed; keyforms not on that parameter pass), default every keyform; `opacity` (0–1), `drawOrder` (0–1000, not for deformers), `multiplyColor`, `screenColor` (`[r, g, b]`); `method` `overwrite` (default), `add`, `multiply` or `screen` (draw order takes the first two), results clamped to the valid range. Each channel is written at its own track's keys, or the object's geometry keys while it has none; `keys` / `ranges` filter those. The writes are ordinary channel keyforms, not generated overrides. It is refused when no keyform matches.

`path_get / path_list / path_preview / path_put / path_delete / path_deform` points use mesh local coordinates and support read-only queries, preview, binding and baking keyforms. Paths are an editing aid; for compatibility see [Deform paths](../guide/DEFORM_PATHS.md).

A physics group is a Cubism pendulum: `inputs` (`parameter`, `weight` 0–100, `type` either `x` for position X or `angle` for tilt gravity, `reflect`) push 1–16 `segments` (`length`, `mobility`, `delay`, `acceleration`), and `outputs` (`parameter`, `vertex`, `scale`, `weight`, `reflect`) read the angle of segment `vertex`'s end relative to the previous segment; `scale` is parameter value per radian (the native Cubism runtime does not read the scale of translation-type outputs, so they are always 0, and only angle outputs are offered). The exported physics3.json and CMO3 declare the project's physics FPS (default 60). The `min/default/max` of `normalization.position/angle` are the targets the input range maps to.

- `physics_put` only changes the given fields: an existing ID (including generated groups) starts from the current group, a new ID from "head and body inputs, one segment of length 10, no outputs". List fields are replaced as a whole; `length` is the total chain length and scales the segments proportionally, `mobility/delay/acceleration` and `output_scale` apply to all segments / outputs, and `segment_count` adjusts the number of segments. With only `enabled`, the group is just switched on or off; a modified generated group replaces the generated version until `physics_delete`. The old `input_parameter` / `output_parameter` are still read as a single input and single output.
- A parameter can be driven by only one active group; when a custom group drives a generated group's output, the generated group yields. `workspace_inspect scope=physics` returns `fps` and the groups in evaluation order, each with `origin`, `enabled`, `active`, `overridden`, `replaced_by` and `issue`.
- `physics_config`: `order` lists the group IDs to evaluate first, and the remaining groups follow in their original order; Cubism evaluates in order, so later groups read earlier groups' outputs in the same step. `fps` is the project's physics frame rate, an integer in 1–240, with 0 meaning unlimited (physics runs on every render frame, and the export declares no `Fps`). Preview frame output is not limited by it: the preview frame rate is a user setting that follows the display by default.
- `physics_import`: `path` is the absolute path of a physics3.json. The groups in the file become custom groups (the same ID replaces an existing group, and a generated group stays replaced until `physics_delete`), ordered after the existing groups in file order; other custom groups driving the same outputs are turned off; the file's `Fps` becomes the project's physics FPS. It returns the imported IDs, the groups turned off and missing parameters.
- `physics_fit`: runs the group with the panel response curve's standard shake (pull right for 1 second, then release) and adjusts each output's scale so the peak reaches exactly `target`% (default 100) of the parameter's end; outputs that do not move keep their scale. Given `observed_peaks` (keys are output indices `"0"`, `"1"`…, values are the reach ratios returned by `physics_audition`, where 1 is the parameter end), it fits to that measured response instead, sharing the candidate with **Fit scale to max** after dragging the pendulum in the panel; an invalid index, a value that is not a non-negative number, or no output moving at all is rejected before commit.

`physics_put/physics_delete/physics_config/physics_import/physics_fit` return process job handles and all require `request_id/project_id/state`. Read the committed state and result with `job_wait/job_get`; the import result also contains `imported`, plus `disabled/missing_parameters/fps` where applicable. Reading, fitting, rebuilding and committing report progress; fitting's settling and per-frame solving support cancellation; cancellation before commit or a state conflict keeps the original project, and a late cancellation or UI refresh exception after commit keeps the successful result. Disconnecting does not stop the job, and retrying the original request gets the same job back. Fitting supports atomic batches and reads the preceding candidate; file import does not support batching. Refitting a group already at its target scale creates no history node, and a group with no output response at all still reports an error.
- Make the motion ends for output parameters first, then attach physics. A static pose sheet does not advance time; use `physics_simulate` with a step input to check amplitude, overshoot and settle time, and `view_sample_motion` for whole motions (its native sampling environment must be available).

## View and spatial mapping

View renders PNGs from model data and does not depend on desktop screenshots. `canvas_rect` gives a canvas rectangle, `focus_layers` frames around objects; output pixel size and the model's canvas size are two different things.

`view_render_layer/view_render_context/view_render_model/view_render_poses/view_check_coverage` each read one captured project version. Every image of a multi-pose render shares that model and visible layers; later edits, reopening or switching projects do not mix into the result and do not invalidate an already captured query. The PNG, spatial mapping and revision stay consistent, and image and spatial references are kept in the project as captured.

- `poses` compares 1–9 poses in the same version and canvas rect, returning one labeled sheet. The total size budget applies to the whole sheet.
- Comparison poses are rendered in the background from the captured committed version, without reading or changing the authored pose or the GUI parameter sliders; do not switch poses with `preview_set` to make comparison images, since that changes the user's authored pose and advances `state`.
- Parameters not given in the request render at the **parameter default**, not the user's current authored pose. To start from the current pose, first read the committed pose with `workspace_inspect scope=preview`, put it into the shared `parameters`, then write only the differences in `poses`.
- When `include_layer_ids` is omitted, the active canvas's local visibility is used: layers the user hid, layers under hidden deformers and layers outside solo do not appear in the image. For a stable result independent of the user's canvas, pass layer IDs explicitly (available from `workspace_inspect scope=layers`).
- `view_compare_history` compares history versions; `view_sample_motion` samples over time; `view_check_coverage` only measures alpha coverage of the given rect and layers.
- Locate with the returned pixel↔canvas mapping; a whole multi-pose sheet cannot be used directly as the spatial reference for a single asset.
- Alpha coverage, mesh diagnostics and successfully written files are not art quality scores and do not prove that unsampled poses are fine.

`view_sample_motion` returns a read-only job handle and also requires `request_id/project_id/state`. `frames` are 2–32 strict frame objects (`time/parameters`), with time strictly increasing from 0 and at most 10 seconds; omitted parameters carry over the previous value. `samples` are 1–9 time points within the motion's duration, `fps` is 15–120 (default 60), and result times are quantized down to the sampling frame rate. The model, visible layers and resource targets are captured before the job starts; later changes, reopening or GUI animation do not mix into the sampling. Native Cubism evaluation, per-image rendering and the sheet report progress and support cancellation; the optional native runtime must be installed.

Read the terminal diagnostics and PNG with `job_get/job_wait`; repeated reads return the same image. The completed result contains `project_id/state/revision`, and an existing sheet's `revisionId` points to the same captured version. Native sampling uses a temporary model and does not change the GUI's live animation and physics state; a cancelled queued job does not run, and cancelling during the frame loop releases the model and temporary files. This read-only operation does not support document batches. History comparison is still an immediate query, but it too uses the history tree from one capture, so reopening the project does not replace its comparison basis.

Besides what Skia can render (paths, gradients, clipping, masks, filters such as `feGaussianBlur`, opacity), it supports element, `#id` and `.class` rules in `<style>`; `var(--name)` takes colors from the drawing kit, and `data-taper` on a path (width factors spread evenly from start to end, such as `"0.1 1 0.2"`) turns the stroke into a filled line tapering at both ends; blend modes and custom CSS variables are not rendered. Layers using it get their pixels replaced, and those placed at the old position move to the new `viewBox`; `edits` change the current drawing (or the `svg` given alongside) locally by element `id`: `set` sets attributes, null removes an attribute, `text` replaces the text of a `<style>`, for example changing only one path's `d` or one color; with neither `svg` nor `edits`, it rerenders at the new `density` |
| `layout_set_drawing_kit` | `state`, optional `colors` (name → `#rgb`/`#rrggbb`, merged, null deletes), `styles` (a class rule stylesheet), `defs` (SVG definitions: gradients, filters) | Colors, class rules and definitions shared by all drawings; `styles` and `defs` are replaced as a whole, and a drawing's own rules and ids of the same name win. All vector entries rerender at their original resolution, and changes sync to layers; rejected when it would leave a drawing missing a color |
| `reference_sample` | At least one of `points` (≤256 [x, y]), `radius` (canvas units, averaged), `rect`, `colors` (1–16, default 6) | Reads reference colors: each point's color and alpha; the dominant colors of opaque pixels within `rect` (dark to light by lightness, with shares), for choosing kit colors |
| `reference_trace` | `seed` ([x, y]), optional `tolerance` (Lab distance, default 12), `compare` (`seed`/`neighbor`), `simplify` (canvas units, default 0.6) | Magic wand: grows from the seed to opaque pixels close to the seed color (`neighbor`: close to the adjacent pixel, which can cross soft shading up to the lines), returning a simplified polygon `polygon` of the outer contour and a smooth closed path `path` through it (canvas coordinates, usable directly as a drawing's first sketch), plus area, bounding box, average color and the number of inner holes; `touches_edge` means it spread to the reference's edge; `holes` (0–16) also returns the outlines of the largest holes in `hole_outlines` — picked from the background, that is the character silhouette (when the character touches the image edge, the silhouette is in the outer contour) |
| `reference_snap` | `points` (1–256), optional `radius` (canvas units, default 4) | Snaps points to the center of the nearest line within `radius` (the nearest of the pixels clearly darker than their surroundings, then the darkest spot near it); points with no line nearby stay put with `snapped` false |
| `layer_place` | `state`, `material_id`, optional `rect` (single entry), `at` ([x, y] center), `layer_id` (new layer ID for a single entry), `reference` (`true` / `false` places every layer as a reference or model layer; omitted, each item follows its mark) | Places an entry or a whole folder as new source layers, drawn above the existing layers; by default at the PSD position (the PSD canvas centered onto the project canvas, scaled down proportionally when larger, in place when the size is the same), otherwise 1 material pixel = 1 canvas unit, scaled to fit the canvas; pixels are not resampled |
| `layer_tag` | `state`, `layer_ids` (1–128), `set` or `add`/`remove` | Semantic tags: part words and `left/right` decide the classification (such as `{hair, front}`, `{eye, iris, left}`), the rest are user tags; classification changes on generated layers wait for `rig_generate` |
| `layer_set_variant` | `state`, `layer_id`, `variant` (`none/toggle/switch`), optional `parameter`, `switch_id` | Variant properties; tags are kept |
| `layer_mark_reference` | `state`, `layer_ids` (1–128), `reference` | Make layers reference layers (`true`) or give them back to the model (`false`): a reference layer stays on the canvas and in the stacking order, but no generation reads it and the rig and exports leave it out. Only layers not generated yet, pending layers and reference layers change; a generated layer is refused. A layer given back in a generated project waits for `rig_generate`. `workspace_inspect scope=generation` lists them in `reference_layers` |
| `layer_pin_reference` | `state`, `layer_ids`, `points` (an array of keyform points) or a single `pin` | Pins reference layers to keyform points: each point maps parameter IDs to values (each within its range, at most 16 parameters), and the reference shows at any of its points (every parameter within 0.5% of its range), hiding at other poses; `[]`, `{}` or null unpins. Replaces the earlier points |
| `reference_place_grid` | `state`, `material_id`, `x_parameter`, optional `y_parameter`, `x_values`, `y_values`, `columns`, `rows`, `pixel_rect`, `rect`, `id_prefix` | Cut a reference sheet drawn as a grid of keyforms (say 3×3 head angles) into even cells, crop each into a material and place it as a reference layer pinned to its keyform: columns follow `x_values` left to right, rows `y_values` top to bottom, the order `view_render_pad` uses. Omitted values are the parameter's keyform values (y highest first, as on a 2D pad) and must then number `columns`/`rows`; without `y_parameter` the sheet is one row. `pixel_rect` is the grid's area in the image's pixels (default all of it), `rect` where every cell sits on the canvas (default each cell fitted into the canvas and centred). Layer and material IDs are `<id_prefix>_<row>_<column>`. One history node |
| `material_mark_reference` | `state`, `ids` (items or folders, 1–1024), `reference` | Whether items (every item in a folder) place as reference layers when `layer_place` does not say |
| `layer_reorder` | `state`, `layer_ids` (1–128), `to` (`front/back/forward/backward/above/below`); `above/below` need `target` | Changes the stacking order (that is, the base draw order): to the front or back, past one unmoved layer, or directly above or below `target`; moved layers keep their relative order. Only accepts layers the generator has not read (layers of an ungenerated project, pending layers); generated layers return an error, and their draw order is changed with `layer_draw_order` |
| `rig_generate` | `state`, optional `refresh_geometry` | Generates or regenerates: an ungenerated project is built from all current layers; a generated project takes in layers placed after the last generation and waiting classifications, keeping user edits by three-way merge, with what could not migrate cleanly in `quality.regeneration`. `refresh_geometry` lists generated layers whose meshes are rebuilt from current pixels; omitted means all layers whose image was replaced, `[]` keeps them all |

Ungenerated projects, empty canvases and pending layers use the ordinary editing workspace, including mesh, deformer, parameter, hierarchy, rotation and texture edits. Exports include the current model. `rig_generate` fits bindings and parameters from tags on existing mesh topology; explicit `refresh_geometry` retraces artwork. Imported PSD projects also register and link each layer as a material.

A typical flow: `project_create` → `material_import` → `material_list` → several `layer_place` (or placing a whole PSD folder) → `layer_tag` → `layer_reorder` → `rig_generate` → authoring edits → more `layer_place` → `rig_generate`. When an external tool has already split the parts, write a Layout manifest and use `project_import_layout` to get a placed, ungenerated project in one step; check it, then `rig_generate`.

`view_render_model` draws reference layers (`layer_mark_reference`) under the model (a `reference.mode` of `difference` compares the model alone). `view_render_model` also has `grid` (grid lines with coordinate labels every so many canvas units, widened by ×2, ×5, ×10… when too dense; the result's `gridStep` is the actual spacing) and `outline_material_ids` (traces the opaque edges of entries with a canvas position — drawings and cropped close-ups — on the view in their own colors, with ids), for reading coordinates and comparing drawings with the reference. To see only the reference, give `include_layer_ids: []` and `reference: {mode: under, opacity: 1}`.

`view_render_pad` lays the model out over a grid of keyforms in one labelled sheet, a whole 2D pad at once: columns are `x_parameter` at `x_values` left to right, rows `y_parameter` at `y_values` top to bottom; omitted values are the parameters' keyform values (y highest first), and a parameter of a 2D pad brings its partner when `y_parameter` is not given. `columns` / `rows` (`[from, to]`, inclusive indices into those values) cut out any sub-rectangle, e.g. `columns: [1, 3]`, `rows: [0, 1]` of a 5×3 pad. `show` picks what each cell holds: `model` (the model alone), `reference` (the reference layers shown at that keyform — pinned there or unpinned), `under` / `over` (references under the model, or over it at `reference_opacity`), `difference` (black where they match, each cell with a `difference` of 0–1), `side_by_side` (model | reference). Each cell's `imageRect` `[x,y,width,height]` maps to `canvasRect` and the cell lists the reference layers it shows; at most 64 cells, and `target_long_edge` / `max_bytes` bound the whole sheet. A grid of references drawn elsewhere in the same order reads back as pinned references with `reference_place_grid`.

Flow for drawing parts from a reference: `layout_set_reference` → `reference_sample` for colors, `layout_set_drawing_kit` to set colors and line classes → `view_render_model` with `grid` to zoom into the part, `reference_trace` for contours, `reference_snap` to correct points on lines → `material_draw` (draw hidden parts complete following the form; do not trace flaws in the artwork) → compare with `outline_material_ids`, or after placement with `reference` → revise repeatedly → `layer_place`, `layer_tag` → `rig_generate` → `view_render_poses` to check what turning reveals.

Flow for splitting parts from a reference: `material_import` the reference → `layout_set_reference` → `material_crop` (`canvas_rect`) close-ups → `material_export_png` → enlarge or repaint externally → `material_import` → `material_set_placement` (`from` the close-up) → layer by layer: generate an image with the frontmost part removed externally → `material_peel` → continue on the new base → `layer_place` → check with `view_render_model`'s `reference` (`difference` to see alignment; `referenceDifference` is the mean difference) and `density` (a texture density heat map; `texelDensity` lists each layer's texture pixels per canvas unit) → fine-tune with `layer_set_canvas_rect` / `layer_transform` → `layer_tag` → `rig_generate` → `view_render_poses` to check motion.

## Asset workflow (asset_*)

`asset_prepare_reference / asset_import_png / asset_register / asset_reprocess` return process job handles and all require `request_id/project_id/state`. Read the business result and the committed `state/project_id/history_node_id` from `data.result` of `job_wait/job_get`; reference images, registration previews and reprocessed images can be fetched repeatedly. Disconnecting or cancelling the wait does not stop the job, and retrying the original request gets the same job. A preparation failure, cancellation before commit or state conflict publishes no asset; a late cancellation after CAS keeps completed and the actual result.

The four writes share a separate application-layer asset session: a private candidate is prepared first, then immutable files and the asset manifest are published within an auxiliary CAS. Actually adding an asset invalidates the old state but does not change the rig revision or append history; reimporting the same content and mapping is no change. Inspection and trial compositing use the captured document and asset manifest, not GUI drafts or later registrations. Saving only copies the assets that belonged to the project at capture time (`assetCatalog` in `workspace.json`); PNG import checks the 16-megapixel limit before allocating pixel memory.

For new assets, usually use `reference → import → register → preview → add`, with `place → finalize` when needed. `project_create_artwork` can create a new project in the background from placed assets, rejecting unsaved changes by default when switching; `source_split_polygon` splits by a canvas polygon into inside and remainder, and `source_split_components` distributes existing pixels by the connected components of the current mesh; neither paints in occluded content.

`source_get_components` is a read-only query taking `layer_id`, returning the captured `project_id/state/revision`, `can_split/count` and component centers `canvas_x/canvas_y`. Components are sorted by source Y, then X; use that order to name them in `source_split_components`'s `names`, with optional `sides` of the same length and unique `piece_ids`. Names must be non-empty and unique after trimming, and their number must match the current components; omitting a side or using `none` inherits the original layer's. Component detection uses the current mesh captured by the query; later changes do not alter the old query result, and the commit must carry that captured state.

`source_split_polygon/source_split_components` require `request_id/project_id/state` and return background job handles; the `result` of `job_get/job_wait` keeps the new state, history node and new source layer IDs in `layers`. The polygon needs 3–32 canvas vertices and two `names` (inside, remainder), and both sides must have visible pixels; two unique `piece_ids` are optional. With new IDs given, later members of the same atomic batch can reference them, and the batch's `changed` includes both the new source layers' `layer:<id>` handles and the generated object handles. Preparation/rebuild can be cancelled, and a conflict or failure before commit keeps the original document; a late cancellation or refresh exception after commit keeps the complete successful terminal status, and the original request gets the same job back.

The pieces supersede the original source layer: the original layer leaves the source (it does not go into `deletedLayerIds`), and the pieces become ordinary source layers inheriting classification, parent, visibility, per-layer mesh and draw order overrides. A split is a regeneration: the pieces take part in generation at the original layer's position, and the user's keyforms, channels, blend shapes, paths, vertex weights and glue on the original layer are carried over to the pieces by three-way merge (except swing and simulation generated axes); later face settings, stance, skeleton and classification changes reach the pieces too; simulation targets, bake offsets and connection roles migrate to the pieces. The journal writes a checkpoint after the split's `art_primitive` record, and the record itself is no longer replayed. The atlas and export no longer include the original layer; `layer_restore` (including restore-all with `layer_ids` omitted) cannot bring it back; only undo/history switching back to before the split does. Later requests referencing the original layer or mesh IDs fail, and the error message lists the piece IDs that superseded it; `source_get_components` does the same. Pieces can be split again. Imported CMO3 models still soft-delete the original layer under the old rule. For the record format see [Document layer](../../zh/spec/DOCUMENT_LAYER.md#拆分物化画元记录-art_primitive) (Chinese). Ordinary, split, new and imported CMO3 meshes keep bindings and existing simulation offsets through ordered replacement on single-layer/global mesh updates and resets, including restoring deleted meshes; the new cut points and boundary vertex copies produced by a polygon split follow the piece owning the original vertex through directional glue, so both sides of the cut stay together. Deleted, masked (clipped), channel-masked or non-normal blend sources cannot be split. The component query uses the actual texture addresses and supports source padding, rotation and scaling, so an edited ordinary target can return `can_split:true`. The GUI mesh connected component split dialog calls the same application command, keeps the state from detection time, and commits multi-layer decisions as one user history commit; polygon splitting is currently an MCP entry point, so this is no basis for claiming the GUI has a lasso split menu.

`rig_update_generation` regenerates the rig with this build's generators (corresponding to **Model → Update Generated Rig** in the GUI). A project whose journal has checkpoints keeps the generator output from when the checkpoint was written, and does not change automatically after upgrading the program; this operation three-way merges the generation snapshot stored in the checkpoint, the result this build now generates for the same input, and the current authored rig: objects the user did not change follow the new output, the user's changes are kept, what could not migrate cleanly is listed in `issues` (and also goes into `workspace_inspect`'s `quality.regeneration`), and the result is appended to the end of the journal as a new checkpoint. If an earlier regeneration checkpoint in the journal would produce a different structure (different parent, vertex count, keyform axes or blend shapes) when merged by this build, it is first remerged by this build, and the fix is carried by three-way merge to later checkpoints and the current authored rig (issue `remerged`, `target` is `journal:<index>`, `detail` lists the objects whose structure differs); later edits are kept. The request needs only `request_id/project_id/state`, returns a background job handle, and is also an atomic batch member. The job `result` is `state/project_id/history_node_id/revision/applied`, `updated` and `issues` (each `{kind, target, detail?}`); when the generated output is the same and every merge agrees, `updated:false` and no history node is appended. Projects without checkpoints are generated by this build on every build anyway, and imported CMO3 models have no generated output, so neither needs updating (the latter is rejected).

`source_split_depth` corresponds to the GUI's depth split menu, multi-select and dialog. Pass the current mesh's original `source_id` and non-empty, unique `middle_ids` (without the `mesh:` prefix and not including the source); optional `names` are two non-empty unique names for the back and front layers, and optional `front_layer_id/front_mesh_id/back_layer_id/back_mesh_id/glue_id` give new IDs. It replaces the source mesh and its layer with two new layers and meshes, back and front, both carrying the original pixels and paintable independently, with the middle meshes between them; the result's `layers` are front then back. Both layers take the source mesh's current parent, geometry, channel keyforms, blend shapes, paths and vertex weights; the back layer takes over the source mesh's glue, masks and simulation targets, and directional glue makes the front layer follow the back one. The two layers use a fixed draw order, replacing the original draw order animation. The mouth and derived lips only copy the selected meshes and do not generate extra lips; an erased front layer still keeps its topology. Imported CMO3 models keep the old record: the source mesh and its layer stay, and a front layer and directional glue are duplicated on top (no new back layer).

A single call likewise requires `request_id/project_id/state`, and the job's terminal `layers` are the new layer IDs (an imported CMO3 model only has the new front layer). Unique `front_layer_id/front_mesh_id/back_layer_id/back_mesh_id/glue_id` can be given so later members of the same atomic batch can paint or edit the new objects; the batch's `changed` returns `layer:<id>/mesh:<id>/glue:<id>`. The GUI keeps the state from when the menu or dialog opened, and auxiliary data changes also invalidate an old confirmation. Preparation can be cancelled, and the exact terminal status is kept after commit; history replay, save and reopen, and CMO3 readback keep the motion and glue connection weights. It copies existing content; hidden parts still need painting in.

Open an existing PSD from a local absolute path with `project_import_psd`. The six paint operations `source_paint_brush / source_paint_pencil / source_paint_eraser / source_paint_bucket / source_paint_shape / source_paint_clear` return process job handles; get the committed state, history node and generated handles from `data.result` through `job_wait/job_get`. Their capability details are marked `job_backed:true`, `batchable:true` and provide `job_result_schema`. Brush, eraser, bucket and shape use the UI's raster algorithms; points, radius and line width are in canvas units and land on the layer's own raster: a layer with raster density (raster pixels / canvas unit, see [Per-layer size](../../zh/spec/DOCUMENT_LAYER.md#逐层尺寸) (Chinese)) 1 behaves as before, while for a layer storing a 1024² raster on a 32-unit rect, a brush of radius 2 paints a stroke of radius 64 pixels on the raster, and after commit the raster keeps its original resolution instead of shrinking back to canvas resolution. Painting outside the rect extends the rect at the same density, and cropping to opaque pixels keeps the density; a fully erased layer keeps one transparent pixel at canvas resolution. Private drafts are based on the layer raster too: `width/height` in the results of `paint_session_begin` and the like are draft raster pixels, `canvas_rect` is the canvas rect it covers `[left, top, width, height]`, and color picking reads the raster at canvas pixel centers; when a draft exceeds 16MP, the paintable margin around the rect shrinks. The default `rebuild_mesh:false` keeps existing meshes and all bindings and clips by the layer's meshes: pixels landing on the meshes stay in the layer (a layer linked to a material writes into the material, and all linked layers update together), while pixels outside the meshes are split into a new layer directly above it (named the original name plus `+`, with its own mesh, under the same parent and part, and placed as a new material in the folder of the original layer's material, linked to it); erasing outside the meshes has no effect; a layer with no mesh yet is not clipped. When the layer's own meshes should cover the new area, pass `rebuild_mesh:true`: the layer expands to all its pixels and migrates keyforms, blend shapes, paths, vertex groups and glue. Both ways are one commit and one history node. Existing keyforms, warps or glue no longer block painting. `clear` or erasing all pixels keeps the layer and bindings, and even the last layer can be cleared and repainted; delete layers with `layer_soft_delete`. A depth split front layer always keeps its topology. Deleting/restoring ordinary edited layers, depth front/back layers and imported CMO3 layers first replays edits, then filters active objects, keeping the IDs, keyforms and bindings needed for restoring; changing mesh settings during deletion still saves the rebinding results of hidden meshes. The first actual delete or restore in an old project pins identities and the generation baseline in the new candidate, so existing edits do not get redirected to other meshes when a layer is restored; old history nodes are not rewritten. `layer_mesh_update` changes a single layer's mesh parameters, and after a reset it inherits the global values.

An ordinary transparent layer creates a mesh automatically the first time visible pixels are drawn, without first passing `rebuild_mesh:true`. The first paint on the mouth also creates the derived lips and their generated keyforms. The `changed` of single and batch job results contains handles such as `mesh:<id>` for new objects, which can be edited further; retrying the same request gets the same job back, without creating again or appending history. Erasing completely keeps the mesh and bindings even when the rebuild flag is passed.

Generated lips follow the contour and color saved at an explicit rebuild or at first creation; later paints that keep the mesh do not regenerate the derived texture. GUI frozen pixels and MCP gestures share the document candidate, rebuild and state check through the separate `WorkspaceRasterCommands`; creation data goes into the ordered journal, and save/reopen and export re-resolve the current texture. Preparation reports progress and checks cancellation; cancellation before commit keeps the original pixels and history; a late cancellation or refresh failure after a successful commit still keeps the complete completed result. Disconnecting or cancelling the wait does not stop the job. Single-layer setting updates for new meshes are also written to the document, keeping IDs, rebinding paths and weights.

`layer_delete` and `layer_restore` both return process jobs and support atomic batches; read the actual state, history node and affected layers from the `result` of `job_wait/job_get`. `layer_delete` really deletes a layer: the pixels leave the project, and its meshes leave the authored rig through the journal record `layer_delete`, along with the masks, glue, paths and weights referencing them; a layer the generator reads also leaves the generation input, so later regeneration no longer generates meshes for it or lets it affect any framework. Earlier history nodes keep it, and `history_checkout` is the undo. The last layer cannot be deleted. Rows that are not independent source layers, such as lip strips and old left/right halves, are still hidden the old way. `layer_restore` only restores layers soft-deleted by older versions: pass 1–256 unique `layer_ids`, or omit them to restore all (original layers superseded by a split are not among them; naming one reports an error listing the pieces); with nothing deleted it is no change and appends no history.

The global mesh unit is `settings_update`'s `meshUnits`: `DOCUMENT` takes a 2048-pixel long document edge as reference, so the same image enlarged uses the same density; `PIXELS` uses source pixel lengths. In both modes, per-layer parameters still mean lengths in the chosen unit. Old v1 settings that have `meshSpacing` but no unit keep `PIXELS`, so reopening does not change old meshes; new settings, generation baselines and export store the actual unit. The GUI unit toggle and public changes use the same candidate regeneration and topology migration. `meshTrace` decides what the contour reads: `TEXTURE` (the default for new projects) reads the layer's own pixels, reduced by maximum alpha to a resolution at most 4 times finer than the mesh unit, so strokes thinner than a canvas pixel stay inside the mesh while vertex spacing is unchanged; `CANVAS` reads the view scaled to canvas resolution. Existing settings without the field are read as `CANVAS`, and `CANVAS` does not write the field, so old projects' settings text and meshes stay the same. `meshWrap` (0–64 mesh units, default 0) is wrap topology: before tracing the contour, gaps and notches narrower than the value are closed, small protrusions such as eyelashes and hair tips share one envelope, and all drawn pixels stay inside the mesh; `layer_mesh`'s `changes.wrap` overrides per layer, and the layer mesh settings in `inspect` return the actual `wrap`. At 0 the field is not written, and settings without it read as 0. See [Mesh topology](../../zh/spec/MESH_TOPOLOGY_AND_SPLIT.md#包裹拓扑) (Chinese).

`import` accepts an absolute path to an existing local PNG or image bytes; do not have the model generate Base64 character by character. Omitting `solid_background` keeps the native alpha; to remove a background, give the real solid color explicitly. A checkerboard screenshot is not a transparent asset.

`register` can use a frame, corresponding anchors or an absolute transform; anchor target positions are canvas coordinates, and generated image coordinates are original full PNG pixels. Mirroring and non-uniform stretching must be declared explicitly. A higher resolution should not automatically enlarge the footprint in the model.

Trial-composite first and check parent, draw order, masks and motion headroom before formally adding or deleting replacement layers. Assets that already have independent bindings, keyforms or finished positioning may refuse whole repositioning; go by the actual error and schema.

### Interior surface authoring

`interior_put` is a background, batchable operation shared with the native dock. Require `state` and `target` (mesh id or `mesh:<id>`); optional `enabled`, `settings`, `motion`, two `parameters` ids, and `guides` (at most 64). An enabled-only update retains the recipe without rebaking. Omitted bindings prefer body X/Y; an explicit empty id creates a private source. The stored native fields and physics use standard export paths. See the interior specification for ranges and safety/recovery behavior.

`interior_delete` removes the effect and owned physics while retaining externally referenced parameters. `workspace_inspect` with `scope=interiors` returns full settings/guides, input/output IDs and issue status without shape arrays. Nested settings/motion schemas allow partial updates and describe ranges/units.
