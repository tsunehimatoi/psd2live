# MCP use and interface

[Documentation](../README.md) · [Design and acceptance](AGENT_DESIGN.md) · [Capability record](../STATUS.md)

The public definitions live in the application layer, [WorkspaceAuthoringOperations.kt](../../../src/main/kotlin/io/github/psd2live/application/WorkspaceAuthoringOperations.kt), [WorkspaceDocumentBatch.kt](../../../src/main/kotlin/io/github/psd2live/application/WorkspaceDocumentBatch.kt), [WorkspaceAuxiliaryOperations.kt](../../../src/main/kotlin/io/github/psd2live/application/WorkspaceAuxiliaryOperations.kt), and [WorkspaceOperations.kt](../../../src/main/kotlin/io/github/psd2live/application/WorkspaceOperations.kt). The MCP binding is in [AgentToolCatalog.kt](../../../src/main/kotlin/io/github/psd2live/agent/AgentToolCatalog.kt). Tools use `domain_operation` names. The old branch tools have been removed, and there is no compatibility alias. Discover capabilities page by page with `workspace_list_operations`, then read one item's full schema with `workspace_get_operation`.

## Connecting

1. Start the desktop application and load or create a workspace.
2. Open **Settings → MCP** (the gear on the right of the title bar) and copy the command or the configuration for the host: a Claude Code command, Codex TOML, a generic `mcpServers` JSON (the address field differs by host), or the Stdio proxy. "Copy the install prompt" produces a short prompt that lets the Agent configure itself.
3. Prefer Streamable HTTP and a Bearer token. Do not switch to the deprecated `/sse` endpoint.
4. A host that supports only Stdio runs `tools/mcp_proxy.py` with Python 3. The proxy reads `PSD2LIVE_MCP_ENDPOINT` and `PSD2LIVE_MCP_TOKEN`. When they are not set, on Windows it reads the port and the token the application saved. Scripts and the command line call it the same way: `python tools/mcp_proxy.py call <操作> [JSON | @文件] [--edit] [--out 目录]` (`--edit` fills in the current `state` automatically, and images are stored as PNG), and `python tools/mcp_proxy.py operations`. In Python, `from mcp_proxy import Client` and then `call` / `edit`. Both tool profiles apply. A background operation waits until it finishes before it returns the result.
5. After listing the tools, call `workspace_inspect` and read the actual object IDs, the parameters, and the current `project_id` and `state`.

The same dialog sets whether the service is enabled, the port (1024–65535, default 23871), the access token (32–256 letters, digits, `-`, and `_`; it can be regenerated or filled in by hand), and the tool set. They are saved in the user preferences, and applying them restarts the endpoint. A restart keeps in-process tasks and the request-deduplication record. A host that is already connected has to reconnect. Changing the port or the token also requires updating the host configuration.

The token is allowed to edit the current workspace, and it should stay in the local host configuration. The tools do not provide an image-generation model. A new image can come from existing pixels, from painting, or from the host's image generator.

## Tool sets

A tool set only decides which tools `tools/list` publishes. Every operation can be called under both tool sets, and execution and validation are the same.

- **Reduced (the default)**: 27 tools, covering 123 operations directly (the input schemas and descriptions are about 85,000 characters; the full tool set is about 760,000 characters, plus about 4.26 million characters of output schema).
  - Single tools: `workspace_overview`, `workspace_inspect`, `workspace_list_operations`, `workspace_get_operation`, `workspace_apply_edits`, `workspace_preview_edits`, `rig_deform`, `keyform_apply`, and the intent tools `author_axis`, `author_physics`, and `author_compile` (see [Intent tools](#intent-tools)).
  - Family tools: `view`, `parameter`, `motion`, `expression`, `hit_area`, `pose`, `skeleton`, `path`, `physics`, `simulation`, `swing`, `modifier`, `source_paint`, `snapshot`, `history`, `project`, and `job`. Calling `{"op":"set_key","request":{...},"wait_ms":20000}` runs `<族>_<op>` (this example is `motion_set_key`). The result's `operation` is that operation ID, and `request` is validated against that operation's full schema. The members are every operation in the registry with that prefix, except private drafts, auditions, and live preview sessions (`skeleton_draft_*`, `physics_audition*`, `*_preview*`), history annotations, and the global physics-preset library. A family tool publishes the flat union of each member's fields (without `oneOf`, `const`, or `$ref`; a field whose shape differs by member is given only a description). The required fields of each op are listed in the tool description.
  - Other operations are called through `workspace_call`: `{"operation":"layer_classify","request":{...}}`. The operation ID is also the member name of `workspace_apply_edits`.
  - `outputSchema` is not published (the result is still returned as `structuredContent`; the contract is in `workspace_get_operation`). The `edits` members of an atomic batch publish only the operation-name enumeration and a `request` object. Member fields are validated strictly against the single-item schema at execution time.
  - `request_id` and `project_id` may be omitted. `project_id` takes the project that is currently loaded. `state` is still required. A `state` that belongs to another load still reports `state_conflict`. `request_id` is derived from the operation and the parameters (including `state`). A retry with the same parameters retrieves the original result. When the previous identical call already failed (including a task `failed/cancelled`), calling again runs as a new attempt.
  - A background operation accepts `wait_ms` (0–30000, default 20000). If the task finishes within the limit, the terminal state and the result are returned directly (the same structure as `job_wait`). Otherwise a task that is still running is returned, and `job_wait` continues it. `wait_ms: 0` returns the task handle immediately.
- **Full**: one tool per operation. It publishes the full input and output schemas, does not derive context, and does not wait for tasks. It suits a host that loads tools on demand, or a client that needs a contract per item.

## Intent tools

Intent tools are ordinary public operations in the registry (both tool sets can call them). They are defined in [WorkspaceIntentOperations.kt](../../../src/main/kotlin/io/github/psd2live/application/WorkspaceIntentOperations.kt). A write, on the captured model that the request's `state` corresponds to, compiles the intent into existing batch members, and then takes the same atomic batch as `workspace_apply_edits` (`startDocumentBatch`). The rebuild, the geometry check, and the CAS are all the same. One success appends only one history node, and it adds no journal semantics. The task result is the same as `workspace_apply_edits` (`edit_count` is the number of members that were compiled). A problem found at compile time returns immediately as `invalid_argument`. A member that fails to execute points out the member index and the operation with `invalid_edit`. When the captured version differs from the request `state`, it reports `state_conflict`.

| Tool | Compiles to | Description |
| --- | --- | --- |
| `workspace_overview` | A read-only query | One capture returns the canvas, the parameters, the layers, the deformer hierarchy (including parents and child counts), the mesh count, the physics groups (input and output parameters), and the motion clips. Each list carries `total` and is cut by `limit` (1–500, default 200). A parameter includes `kind` and `repeat` (a repeating parameter) |
| `author_axis` | `parameter_create` (when the parameter does not exist) → `keyform_apply` seed → `rig_deform` | When `parameter.id` does not exist, it is created (`name` defaults to the ID). When it already exists, the given `min/max/default` must match the current values. Each shape target is seeded first at the parameter's default, so the current shape becomes the neutral shape (skipped when that axis already has a key at the default and no `key` was given). Then `operations/selection` of `rig_deform` run at `value`. Other axes bound directly on the target take their own defaults. `key` can give the values of a combined corner. A `value` equal to the default is refused. With `mirror: true`, each shape is also mirrored to the opposite value (`2×默认值 − value`, which must be in range), and writing one side fills both sides. The keys of a new parameter axis are built by the engine at min, default, and max |
| `author_physics` | `physics_put` → `physics_fit` | The fields are the same as `physics_put`, plus `fit_target` (10–300, default 100; `null` skips the fit). Giving only `id` and `fit_target` only refits an existing group. When neither changes anything, it is refused. An output parameter needs an authored shape already |
| `author_compile` | A read-only query | Returns the members the intent would commit. See below |

An intent tool does not trial-run itself. `author_compile` compiles the same intent against the request's `state` and returns the members that would be committed (`{"intent":"author_axis","request":{...}}`; `request` carries `state` and does not carry `request_id/project_id`). It does not change the project. They can be checked or edited and then given to `workspace_preview_edits` to trial-run the geometry members among them, or to `workspace_apply_edits` to commit. The result is the same as calling the intent directly.

Part configuration (`eye`, `brow`, `mouth`, `face`, `body`, `hair`) stays strictly validated. A sub-feature configuration is stored in `subConfigs`. The key is the atomic feature type, such as `mouth.outline`. The value accepts the numeric, physics, dependency, and color fields that the matching algorithm declares, and the fixed `targets`. A folded record also saves the sub-instance `id`, `version`, and `outputAliases`. An update should keep the fields that were not edited. A sub-version supports only the public facade version `1`. Evaluation maps it to the matching implementation version. An unknown version refuses to run. The outline switch is `outline`. The canonical key of brow-and-eye coupling is `lidCoupling`. The historical `lid` is read only when the canonical key is absent. An explicit canonical key of `false` wins. After the interface changes that switch, only the canonical key is written. Reading and a history switch do not rewrite the old configuration.

A new preset folds only the current package candidates whose order, identity, targets, and dependencies can be kept. A repeated sub-feature, a disabled member, another step in between, a reference to an external sub-instance, an explicit version choice, or a package override keeps the related group expanded. A precise package lock that has already been saved is not converted automatically.

A motion modifier's `config` supports an optional `parameter_roles`, which maps a runtime role name to an array of parameter IDs. A blink add plan fills in `EyeBlink`. Evaluation checks the parameter references, and it refuses incompatible definitions of the same role. A query reports the change in the relation contribution. After the prefix is applied, the roles are saved as ordinary model metadata.

A query of a motion after it is checkpointed can return `captured_ranges: {参数ID: {min, max, repeat}}`, used to keep the curve control points from the time it was checkpointed. It updates with parameter rename, deletion, and range edits, and it enters save and restore.

A physics plan can capture the old rules with `preset: "PhysicsHairFront"`, `"PhysicsHairBack"`, or `"PhysicsEyeJelly"`. When a parameter is created by a modifier that is currently evaluated, the consumer can pin that provider. A query's `parameter_providers` returns the map from parameter ID to provider instance ID.

The table lists the business fields. Every edit must also carry `request_id`, and a workspace edit must carry `project_id` and `state` (the reduced tool set may omit the first two; see [Tool sets](#tool-sets)). The read-only background samples `physics_simulate/simulation_simulate/simulation_compare/view_sample_motion` require the same three fields, to deduplicate and to pin the sampled version. Each operation's fields differ. Read the JSON Schema the current service provides before calling. Every public tool uses the wrapper `{"request": {...}}` uniformly. Publishing and validation keep the same `oneOf`, `const`, field constraints, and descriptions. Both the outer object and the business object reject unknown fields. A result is uniformly `{"ok":true,"operation":"...","data":{...}}`. An error contains `ok:false` and `error.code/message`. A field-validation error also carries `field`. A PNG is returned as MCP image content.

All 195 public operations (70 of them background, 91 of them batchable) must declare a full `outputSchema`. The full tool set publishes it, and `output_schema` in the capability detail matches it. Success data and failure error are strictly exclusive. The registry validates the business result at the execution and deduplication boundary. MCP validates the full return wrapper. A missing result contract cannot be registered. A background operation must also have a terminal `job_result_schema`. A non-background operation is not allowed that field. The capability detail describes a nested schema through local `$defs/$ref`. A query of its own schema can be validated as well. The actual HTTP keeps every root constraint. `output_contract` means the service implementation's result does not match the declaration. Adding images uses `layer_import_images`: `state` is required, and `paths` is 1–128 absolute paths. An optional `parent_deformer_id` points at an existing parent deformer. When it is omitted, they bind to the model root. An optional `anchor_layer_id` draws the whole batch directly in front of that layer (or mesh). `in_front=false` is directly behind. The first image in the batch is the frontmost, and the draw order is written as an explicit override. An optional `at` `[x, y]` centers each image on that canvas coordinate (it stays against the canvas edge). `as_reference=true` imports them as reference layers in the layer stack (no mesh, not exported), the same as dragging onto the layer list and choosing "set as reference". It is still one history node. After the transparent edges are cropped, they are centered. The raster keeps the original resolution. When it exceeds the canvas, only the canvas rectangle is scaled down uniformly to fit inside the canvas (the layer density is greater than 1 pixel per canvas unit), and the mesh is generated at canvas resolution. A single file is at most 64 MiB and 16 million pixels. A whole batch is at most 32 million pixels. One success appends only one history node. If any file fails, the whole batch is not published. It reads files, and it cannot be a member of an atomic document batch. The handles of the new source images and meshes come from the task terminal state's `affectedLayerIds/affectedObjectIds`. The original image pixels are written into the project. A later reopen does not depend on the input file. Each image gets its own mesh in the authored rig (`canvas_mesh_create`, hung under the given parent). The generator never regenerates it. Undo cancels the import.

A transform of a whole layer uses `layer_transform` (any layer: imported or from a PSD, at the root or under any deformer, bound or not): `state/layer_id` are required, and then either `matrix [a,b,c,d,e,f]` (`x' = a·x + c·y + e`, `y' = b·x + d·y + f`, canvas units, y downward), or `translate [x,y]`, `scale` (a number or `[sx,sy]`), `rotate` (degrees, clockwise on the screen), and `pivot [x,y]`. It composes with the transform the layer already has. The pixels, the texture tiles, and the texture coordinates all stay unchanged, and it does not trigger a regeneration. Each mesh of the layer moves by that transform at the rest pose (the keyforms keep their offsets). The layer records where its own pixels are shown, and painting lines up with that (a layer that has been rotated does too). One undoable history commit, and it can join an atomic document batch.

Rebuilding a mesh uses `layer_mesh_rebuild` (`state/layer_id` required): the layer's mesh is generated again from the layer's current pixels and mesh settings. Keyforms, paths, weights, and Glue migrate to the new topology. A layer that was moved as a whole keeps its position. A mesh is regenerated only at these times: import, this command, the `rebuild_mesh` option of a paint and of an image replace, a mesh-setting change, and a regeneration. A layer that has no mesh gets a mesh the first time a paint draws a visible pixel. Pixels painted outside the mesh are not shown. The mesh panel in the interface gives the ratio and offers "rebuild from the current pixels".

Retopologizing by texture structure uses `layer_mesh_structure` (`state/target` required; target is a mesh ID or `mesh:<ID>`; optional `settings`: `sensitivity` 0–1, `min_length` in source pixels, `near_density` the multiple of the on-line point spacing relative to the kept edge-row point spacing (default 1), `fill` whether to add points between lines (default no: vertices exist only on the edge rows and on the lines), `far_density` the edge length when filling, relative to the original inner edge length, `bands` whether to add rows and crossbars on both sides of a drawn fold line (default no), `kinds` a subset of `FOLD`/`SHADE`/`PATTERN`, `max_lines` ≤64, `max_vertices` ≤16000): the outer contour rows and the edge band do not move, and the inside is rebuilt along the folds, the light-and-dark boundaries, and the pattern lines in the texture. Keyforms, paths, weights, and Glue migrate as usual, and one `canvas_mesh_rebuild` is written. When the target has an interior effect, the TOPOLOGY guide lines it detected are replaced (hand-drawn ones, and ones already marked FOLD, are kept), and it is rebaked in the same history node (`interior_rebaked`). When it cannot form a mesh, or it exceeds `max_vertices`, it errors and changes nothing. `layer_mesh_structure_preview` (read-only, the same parameters, no `state`) returns the recognized lines (the kind, whether it was followed `followed`, whether a band was added `banded`, source pixels and canvas coordinates) and the new mesh's canvas points and triangles. ### Mesh topology

`canvas_topology` (`request.mode` is `topology`) and the editor's topology operations are the same `canvas_topology` authoring journal. `state/id/action` are required (`id` is the mesh ID; `vertices` are vertex indices of the current mesh, and they default to empty). Each item of `anchors` is either an existing vertex `{vertex}` or a free point `{x, y}`. `add_points` accepts only free points. On a refusal the error code is `topology_refused`. Indices come from the current mesh, and the latest `state` must be used: read the vertex indices and the rest coordinates with `mesh_get_topology` (the mesh's own space that `add_points` anchors use), the triangles, and the outline edges. When a commit succeeds, the result's `new_vertices` lists the vertex indices that the operation created or left selected in the new mesh (`add_points` is the new points, `knife` is the points on the cut, and `merge` is the point after the merge). A batch member does not return this field. `action`:

| `action` | Input | Result |
| --- | --- | --- |
| `merge` / `duplicate` / `delete` | `vertices` | Merge into one point, duplicate the vertices and the faces they fully cover, or delete and fill the hole (at least three vertices remain) |
| `connect` | `vertices` is exactly two | Edges that the straight line between the two points cuts are split, and they are joined into a new edge. It fails when they are already connected, or when a new edge cannot be cut out along the straight line |
| `subdivide` / `split` | `vertices` or `edges` | Subdivide the edges that the selected vertices touch, or the given edges |
| `knife` | `anchors` | Add edges along a polyline (the Line of the editor's point tool): each anchor lands on the mesh, and neighboring anchors are joined into an edge. An anchor is `{vertex}` or `{x, y}` in the mesh's own rest space |
| `add_points` | `anchors` (`{x, y}`, the mesh's own rest space, the same as `knife`) | Each point adds one vertex: 1→3 inside a triangle, an edge is split when the point is on an edge, and outside the mesh a triangle is grown from the nearest visible outline edge. A point that lands on an existing vertex is ignored. The new vertex's UV, keyforms, blend shapes, and weights come from the surrounding vertices by the same weights, and edges are then flipped without changing the texture |
| `delete_edges` | `edges` (`[[a, b], …]`, which must be given; `vertices` does not decide which edges are deleted) | An interior edge is swapped to the other diagonal inside its quad (it fails when the quad is not convex in the rest shape, in any keyform, or in a blend shape). An outline edge deletes the triangle it belongs to, and a vertex that is no longer used is deleted with it. When it would leave a vertex touching only at a point, or delete every triangle, the whole batch fails |
| `retriangulate` | `vertices` (an empty array is the whole mesh) | Flip edges toward Delaunay around these vertices (judged in canvas space of the default pose). It flips only a quad whose texture mapping does not change and that is convex in the rest shape and in every keyform and blend shape. Vertices and keyforms stay unchanged. When nothing can be flipped, there is no change (`applied:false`, and no history is appended) |

When an operation does not apply, it returns an error and writes nothing. Keyforms, blend shapes, vertex groups, and Glue migrate with the topology (a Glue pair of a deleted vertex is deleted), and paths are rebound. When the target mesh has an interior effect and it was consistent before the change, it is rebaked on the new mesh inside the same node (a bake failure does not refuse the edit, and the effect reports that the mesh has changed). The result must pass the [geometry check](#geometry-checks-and-trial-runs). The comparison of the algorithm with Cubism mesh editing is in mesh topology.

### Copying objects, find and replace, and ID conversion

`object_paste` (`sources` are `mesh:/warp:/rotation:/part:/parameter:` handles; optional `parent`, `part`, `parameter_group`, `ids`) copies meshes, deformers (together with the subtree and the meshes in it), parts (together with their children), and parameters. The new IDs are fixed at record time (the default is `<ID>_copy`, a sequence number is added on a conflict, and `ids` can name them item by item). The replay result and the IDs stay fixed and consistent. Parent, mask, Glue, path, and vertex-group references among the copies are retargeted to the copies. A reference that points at an object that was not copied is kept. When `parent` is given, a mesh is reparented by canvas coordinates and a deformer is reparented by local coordinates. Paste is planned on the authored rig. Objects generated by swing, simulation, and interior effects are not in it. Naming them is refused, and copying a subtree does not bring them along. A copy does not count as a mesh of its layer. Looking up a mesh by layer (picking, a split, and keeping the mesh ID on delete) recognizes only the original mesh. When the layer is deleted, the copy is deleted with it. A copy sets its draw order by its own mesh ID. A whole-layer transform does not move a copy. On a single call, the result's `ids` gives the map from the original handle to the new ID, matching the record that was written (the request fixes every new ID from the captured version and then commits). `paths` gives the deform paths copied with the meshes (`path:<原 ID>` to the new ID). A batch member reads the new handles from `changed`.

`mesh_duplicate` (`source`, `targets`) fits the source mesh's topology onto each target mesh by canvas position. The UVs take the target's own texture. Each target writes one `canvas_mesh_rebuild`. Keyforms, paths, weights, and Glue migrate as usual.

`object_find` (read-only) searches in `kinds` by name or by ID (`field`). It supports `find`/`replace`, `regex`, `match_case`, `prefix`, `suffix`, `swap_sides` (an independent swap of L/R, Left/Right, and 左/右), and `standard_ids` (a Cubism 2 style ID changed to a Cubism 3 standard ID). It returns each item before and after. `object_rename` commits once with the same parameters. Both list only objects of the authored rig. An object a generator added after the journal keeps the name and the ID the generator gave it. Renaming by ID, and `object_convert_id` (`renames`: `target` and the new `id`), both write one `convert_id` journal item. Keyforms, blend shapes, masks, Glue, paths, vertex groups, motion curves, expressions, poses, hit areas, user physics, and swing targets that refer to it are renamed at the same time (a standard expression that has not yet been taken into the document also finds the standard parameter by the new ID; a copy that shows through the bangs changes ID with the original, and the copy itself cannot be converted, pasted, or mesh-copied, and is refused as `generated_copy`). Later generated overrides and deferred panel edits replay by the new ID. Built-in physics, motion presets, and expressions find the standard parameters again by the new ID. Parameter snapshots, the authored pose of each workspace, and timeline bookmarks, shy, and freeze switch to the new ID in the same commit, and they switch back to the original ID on undo or on a checkout to before the conversion. An ID must be 1–64 ASCII letters, digits, or underscores, starting with a letter. A duplicate within the same kind, an ID that is already taken, and an object a generator owns (simulation, an interior effect, a swing parameter) are refused, and nothing is changed. A mesh that is bone-bound or weighted, a bone parameter, and a bone deformer are refused the same way (the skeleton is baked by the original ID before the journal). The other way around, a bone also cannot newly bind a mesh whose ID was converted, or a mesh the journal created (a pasted copy, a mesh created on the canvas). Automatic bones skip them. When a motion curve or an expression entry of a deleted parameter remains on the target ID, the conversion is refused, and the motion or the expression it is in is named. On a split, a layer delete, and a regeneration, the base stage keeps the mesh by the ID from before the conversion, and the journal item then renames it. The regeneration three-way merge also converts the generated result to the ID from after the conversion. Before export, the IDs of the model that is actually exported are checked. A duplicate within the same kind (Warp, rotation, and a runtime virtual bone share a kind; this includes parameter folders, simulations, and colliders) refuses the export. A character that does not comply only warns.

### Textures and the atlas

A layer's canvas rectangle (canvas units, which may be fractional) and its raster pixels are independent of each other. The native density is the raster pixels per canvas unit. An atlas tile stores `栅格像素 × 密度 × fit`. The density defaults to 1. When the budget is exceeded, unlocked tiles share one fit (≤1) and shrink together. A lock or a pinned position that does not fit is cancelled (the notice is written only to the program log, and it does not enter the tool result). Geometry does not see the atlas. Density, the budget, a pinned position, and a reflow change only the tiles and the bound UVs. They do not change the meshes.

- `layer_get_texture` (a query): `layer_id`. It returns `canvas_rect`, the integer bounding box `bounds`, `raster`, `native_density`, `override{density,lock,pin}`, `deleted`, `tile` (the page, the texture-pixel rectangle, the texture pixels per raster pixel `scale_x/scale_y`, the density, the lock, and the pin; null for a transparent or deleted layer), and `atlas_fit`, all from the same captured version.
- `atlas_get` (a query): an optional `page` filters the tiles. It returns the effective `budget{page_size,max_pages,padding}`, `fit`, `notices`, `auto` (whether it arranges automatically every time), `pages[{index,width,height,tile_count,occupancy}]`, and `tiles`. `occupancy` counts only the cells a mesh-arranged tile actually uses. `notices` point out that the page count exceeds the budget, and tiles that are stored below the set density in order to fit on a page. A saved arrangement keeps `fit`, so after an image is replaced with a higher resolution, neither of these cases shows up in `fit`. A texture edit, and a `workspace_apply_edits` that contains a texture edit, also carry `atlas_fit` and `notices`. Adding `atlas_set_budget` and `atlas_pack` (they can sit in the same batch as a replace) brings it back inside the budget.
- `atlas_render_page` (a read-only background task, requiring `request_id/project_id/state`): `page`, and an optional `max_size` (64–16384, default 2048, scaled down by the long edge). The terminal state contains `revision`, the original size and the rendered size, `sha256`, and the layers of that page. The PNG is returned as image content. `job_get/job_wait` can fetch the image again.
- `layer_set_canvas_rect`: `layer_id` and `rect{left,top,width,height}`. It moves and scales the layer so the canvas shows its pixels at that rectangle, which is one `layer_transform` starting from the position currently shown (a layer that has been rotated is refused; use `layer_transform`). The pixels, the texture, and the generation input stay unchanged, and the mesh moves together with the keyforms. Any layer is allowed. The `canvas_rect` of `layer_get_texture` is the position the layer currently shows. The same rectangle is no change.
- `layer_replace_image`: `layer_id` and exactly one of `path` (an absolute path, PNG/WebP/TIFF/BMP, a single item only), `png_base64`, or `material_id` (artwork in the artwork library; the layer is then linked to that artwork). Optional `fit` (`stretch` fills it by default, `contain` keeps the aspect ratio, centers it, and pads with transparency) and `rebuild_mesh` (default false). The canvas rectangle stays unchanged. The generation input is frozen at the pixels from before the first replace. The mesh, the keyforms, and the binding are kept, and only the tile and the UVs change. `rebuild_mesh=true` regenerates that layer's mesh from the new pixels, and it is refused when there are author edits or materialized geometry. A single item checks the state first and then reads the file. A batch member accepts only `png_base64`. When `path` is given, the whole batch fails with `invalid_edit`. At most 16MP. Identical pixels are no change.
- `atlas_check_placement` (a query): `placements` is 1–128 items `{layer_id, page?, x?, y?, rotation?, density?}`. An omitted field keeps the committed value. It returns `clear` and, for each tile, the target `page/x/y/width/height/rotation`, `outside_page` (whether the bounding box after rotation leaves the page, or the page number exceeds the budget), and `overlaps` (the tiles whose meshes it would intersect). It compares with the other committed tiles and with the tiles checked together this time. The rule is exactly the same as at commit: when the bounding boxes of two tiles, expanded by the gap, intersect, it then judges by the cells the meshes actually use (expanded by the gap). When both have no mesh and neither is rotated, it judges by the rectangle. Dragging, scaling, and rotating in the atlas view use this same rule. A placement that is `clear` lands exactly as it is. A placement that conflicts is refused by the commands below.
- `layer_set_pixel_density`: 1–128 unique `layer_ids`, a required `density` (a continuous value from 1/64 to 16; `null` restores 1), and an optional `lock` (omitted keeps the original value). When an arrangement already exists, each tile keeps its top left. If growing would leave the page or intersect another tile's mesh, it is refused with `tile_collides` and nothing is changed.
- `atlas_set_tile`: `layer_id` and `pin{page,x,y,rotation?}` (texture pixels; `x` and `y` are the top left of the unrotated rectangle, and `rotation` is any number of degrees of rotation about the tile center, default 0) or `null` to put it in a free region. The page number must be inside the budget. The position is saved in the arrangement (the `atlasArrangement` setting). An atlas that arranges automatically first saves the current layout (`auto` becomes false). When an arrangement already exists, each tile is first saved at its current position and the mesh coverage is filled in, so the other tiles do not move, and they do not squeeze into a spot a move left empty. A position that would leave the page after rotation, or intersect another tile's mesh, is refused with `tile_collides`, and nothing is changed. Check first with `atlas_check_placement`. To move and scale at the same time (for example a scale that keeps a diagonal still, or swapping the positions of two tiles), put `layer_set_pixel_density` and `atlas_set_tile` into the same `workspace_apply_edits`. Only the layout after the whole batch is checked, exactly the same as Apply of an adjustment session in the atlas view.
- `atlas_set_budget`: `page_size` (a power of 2 from 256 to 16384), `max_pages` (1–64), `padding` (0–32), and `auto`, at least one of them. An omitted item keeps the current value. The budget is written to the `atlas` setting. `auto=true` deletes the saved arrangement, and after that every rebuild arranges automatically by rectangles (MaxRects). `auto=false` saves the current layout.
- `atlas_pack`: arrange once and save the result (`auto` becomes false). Optional `shape`: `mesh` (the default) arranges by the texture-coordinate coverage of each layer's final mesh (4 raster pixels per cell, plus the gap). Rectangles may nest inside each other, and each tile writes only its own cells. `rect` arranges by rectangles. Tiles are placed from largest occupied area to smallest. When they do not fit in the budget page count, every unlocked tile shrinks together at a step of 1/64. Optional `layer_ids` moves only those tiles, and the rest keep their place and their original fit. It also clears the pinned positions of automatic arrangement and the coverage of layers that no longer exist. Arranging the same input again is no change. If a later mesh edit goes outside the coverage from arrangement time, the `notices` of `atlas_get` prompt another arrangement. A tile's `shaped` means it was arranged by the mesh coverage.

The six edits are all process tasks and atomic batch members. They commit through a pure candidate of `WorkspaceTextureEdits`, a full rebuild, and CAS. One success appends only one history node, and undo restores the previous tiles. The terminal state is `project_id/state/history_node_id/revision/applied/layers/atlas_fit` (it may contain `geometry_diagnostics`). `layers` is the layers whose texture actually changed.

## Errors and recovery

When an immediate call fails, the tool returns `ok:false` and a structured `error`. When a background task fails, the query of `job_get/job_wait` itself still returns `ok:true`. `data.status` has to be checked. The `data.error` of a `failed` task uses the same structure, and it has no successful `result`. A task query, a list, a disconnect and reconnect, and a retry of the original request all keep the original error. After the problem is fixed, a new attempt uses a new `request_id`. Reusing the old ID retrieves the original result.

| `error.code` | What recovery is based on |
| --- | --- |
| `invalid_request` | Read the current schema. `field` locates the field |
| `output_contract` | The service implementation returned a result that does not match the declaration. `operation/field` locates the contract problem. Query the actual state of the project or the task first. It cannot be assumed from this that the edit has been rolled back, and it should not be redone directly |
| `invalid_argument` / `invalid_edit` | Fix the parameter or the edit. A batch error also carries `edit_index` and `edit_operation` |
| `not_found` / `id_conflict` / `owned_by_generator` / `key_incomplete` / `topology_refused` | A refusal that can be told apart, with `target` (`kind:id`, such as `parameter:ParamAngleX` or `hit_area:HitAreaHead`). A batch member also carries `edit_index` and `edit_operation`. The object, key, or entry it points at does not exist. The new ID, or the ID after a conversion, is already taken (including a motion curve or an expression entry left by a deleted parameter). The object belongs to swing, simulation, an interior effect, or the skeleton, and it has to be handled in its panel. The key of a keyform edit is missing an axis the target binds directly. A topology operation does not apply to that mesh and selection. None of them committed any edit |
| `tile_collides` | After a move, a rotation, or a density change, a tile in `layer_ids` would be pushed off its arranged position (it leaves the page, or it intersects another tile's mesh). The whole edit was not committed. Use `atlas_check_placement` to pick another position, or put the related moves into the same batch |
| `state_conflict` | Read the project again. The error carries `expected_state` and `actual_state` |
| `project_conflict` | Confirm the target project. The error carries the nullable `expected_project` and `actual_project` |
| `request_id_reused` | The same ID was used for a different operation, parameters, or author. Use a new request ID |
| `unsaved_changes` | Save first, or explicitly pass a supported discard flag |
| `workspace_busy` | Wait for the work that is in progress to finish, then read the current state |
| `io_error` / `permission_denied` | Check the file path, the access permission, or the disk problem from `message` |
| `invalid_state` / `operation_failed` | Diagnose the business precondition or the execution problem from `message` and the current project state |

`cancelled` is an independent task state. It is not an error code. A late cancel after a successful commit, or a refresh exception, keeps `completed` and the committed result. It cannot be claimed from this that the edit was rolled back.

`rig_create_warp` resolves `mesh:<id>` in the captured candidate model. It requires a unique target and a shared parent Warp. When `id` is omitted, it is assigned only once. An explicit `id` can be referred to by a later item of the same batch, and the new Warp also appears in the batch `changed`. `rows/columns` default to 16, range 1–32. The actual grid points align to the parent grid points, and each axis ends at no more than 64. The actual division in the object detail is what counts. `fit_local` defaults to true. It crops to a conservative envelope of the ordinary keyforms plus the independent blend shapes stacked on them, and it remaps the geometry and the blend shapes together, keeping the UVs, the scalar channels, the paths, and the vertex weights. When the envelope exceeds the parent domain, the fit is refused. The parent domain can be enlarged first, or `fit_local:false` keeps the full parent domain. A canvas Warp that is placed freely still uses `canvas_warp`. The single-item terminal state `job_wait/job_get.result` contains `target/state/history_node_id`. A failure or a cancel before the commit does not publish a new Warp. A refresh failure or a late cancel after the commit keeps the success and the handle.

## Atomic document edits

`workspace_apply_edits` shares the outer `request_id`, `project_id`, and `state`. Each item of `edits` is `{"operation":"...","request":{...}}`. The inner request fills in only that single tool's business fields. It does not repeat the context fields. A member uses the same business schema the single tool publishes. An unknown field, and a member that is not supported, are refused before the candidate edit.

### Geometry checks and trial runs

The geometry authoring journal of `rig_deform`, `keyform_apply`, `rig_edit_structure`, `object_edit_appearance`, `canvas_warp/rotation/glue/topology`, `canvas_deform_stroke`, and `path_deform` takes a geometry check after the application layer has fully rebuilt and before the formal CAS. The matching GUI journal and MCP use the same rules. A batch checks only the final candidate. An earlier item may degenerate temporarily, and a later item may repair it. Other document operations do not automatically widen the check because of this rule.

`workspace_preview_edits` uses the same ordered candidate preparation, rebuild, and check as a formal commit, but it does not call projection or CAS, and it does not change state, history, the unsaved flag, the pose, or resources. It is a read-only background task. It still requires `request_id/project_id/state`. Take `dry_run:true`, the input `revision`, `candidate_revision`, `would_change`, `would_commit`, the `changed` handles of new objects, and `diagnostics` from `job_wait/job_get.result`. When a Warp, a Rotation, or Glue is created, an explicit `id` must be given, and the same edits are then committed to `workspace_apply_edits` on the same state. Only then can the candidate revision be compared again. A trial run does not reserve object IDs, and it does not authorize bypassing the later state-conflict check. A member that is not geometry is not accepted for a trial run. The supported range follows that operation's schema.

`workspace_preview_regeneration` (called through `workspace_call` in the reduced tool set) trial-runs any document operation the same way (except resource-layer operations), so the result of a regeneration can be seen before the commit. `checkpoints` lists the checkpoints the commit would write into the journal (`index` is its position in the candidate journal; `kind: "regeneration"` is the generated result merged onto the user's rig, and `issues` uses the same problem format as `rig_update_generation`; `kind: "materialized"` is the current authored state checkpointed before the new entries). `added`/`removed` are the object handles the candidate adds and removes. There are also `dry_run:true`, `revision`, `candidate_revision`, and `would_change`.

The check covers the parent-local geometry of the affected objects, including the combinations of ordinary keys, blend-shape keys, and weight-limit points. A non-finite coordinate, illegal topology, and a newly added zero-area degeneration block the commit, and they return `geometry_unsafe` and structured `diagnostics.violations`. A newly added local flip, and a local collapse whose area is under 1% of the reference triangle, are saved in `diagnostics.warnings`. They do not block by default. The existing authoring flow allows an intentional fold, and a flip count cannot be taken directly as a failed make. An existing flip, degeneration, and collapse are counted separately. They do not block an edit that adds no new defect. A reversible affine mirror and compression of the whole surface are allowed through. A zero-area transform is still refused. When a topology change cannot keep the old triangle identity, the new mesh's reference geometry is used. When the Cartesian product of the blend coordinates exceeds 16384, it switches to deterministic scattered sampling, keeps the combinations at both ends, and no longer refuses the candidate with GEOMETRY_SAMPLING_LIMIT. The report scope states clearly that a large combined domain uses sampling. That is not a proof of every combination.

In an old project, a copy that shows through the bangs (`<原件 ID>_SeeThrough`) is regenerated from the settings on every build, and it cannot be edited directly. Any document operation that names the copy in a reference field (`target`, `id`, `layer_id`, `meshes`, and similar) returns `generated_copy`. Free text such as a name does not count (`details.target` is the copy, and `details.original` is the original that should be edited). Edit the original, or the settings `seeThroughBrows` / `seeThroughEyes` / `seeThroughOpacity`. When `objects` looks at a copy, `topologyInfo.layerId` is the original's layer, and `topologyInfo.seeThroughOf` is the original. An eye is changed to show through by opening a window in the bangs. The finished rig inverse-clips the bangs that cover the eye layers, and it draws one bangs copy clipped by them (`<刘海 ID>_SeeThrough`, `seeThroughOf` is the bangs). These masks exist only in the finished rig. The bangs' `topologyInfo.seeThroughWindow` lists them. The bangs' own mask in the document is still empty. Do not write them back into the bangs' `masked_by`.

When the candidate only appended authoring journal relative to the starting document, the check range is derived from the commands that were added: the meshes, Warps, and Rotations the commands point at directly, all of their children, the Glue partners of the meshes involved, and the targets of unbaked swing and of baked simulation (both of these generators recompute their targets on every replay). A command that cannot list the affected objects item by item, such as creating or reparenting an object or rebuilding a mesh, and a candidate that also changes document content other than the journal, fall back to comparing every object. Classification inside the range is the same as a full comparison. The report `coverage` gives `mode` (`full` or `scoped`), the number of objects actually compared `checkedTargets`, and the object total of both models `totalTargets`. When the range is narrowed, the `scope` text notes that the other objects were not compared.

The diagnostics cover only these sample points. They do not prove the interpolation between keys, a parent's combined deformation, Glue, masks, pixel coverage, physics, or visual quality. A trial-run result belongs to the input version. When the project is edited or reopened later, the result does not become the basis of the new version.

A formal geometry authoring commit may also return `geometry_diagnostics`, containing the same blocking items and warnings. When the geometry check involved no object, that field is omitted. A flip warning does not have to be expressed by rolling the edit back.

The zero-area decision includes floating-point error. A triangle whose absolute signed area is under `1e-12`, or whose area ratio is no more than `1e-6` of the reference shape, is treated as a numeric degeneration. A tiny negative area left by coincident vertices is not reported only as a flip warning.

A GUI parameter definition, a folder position, and a parameter key can be combined into one shared commit. A canvas journal, an internal typed edit, and the field-completion queue also enter the same candidate, rebuild, and CAS boundary. A GUI swing session, a field edit, a simulation edit, and an offline bake keep the state from the start, so an old result is not committed to a project that was reopened or that has changed. A GUI author is specified as `user` by the trusted adapter.

A parameter definition is now written to the journal in the actual edit order. A deletion reads the earlier keyforms and the last default. An old project's static parameter overrides stay compatible to read, and they do not rewrite history. A pure channel edit such as opacity and color is persisted as well. Capturing a key that already exists and is the same does not append history.

87 items currently support a batch (including adding an artwork layer, registration placement, confirm, a whole-layer transform, a mesh rebuild, and the six texture edits): settings, layer classification and mesh configuration, a source-image polygon, connected-component, and depth split and delete and restore, parameter definitions, creating an independent Warp, rig deform, keyforms, structure, appearance, and vertex groups, the six source-image paints, the seven skeleton edits, the six motion edits, the four canvas edits, path put/delete/deform, swing put/delete, physics put/delete/config/fit, and simulation put/delete/bake/clear_bake and model_apply_preset. The single calls of settings, classification, mesh configuration, a source-image split, image placement and cancel, layer soft delete and restore, an independent Warp, painting, physics, simulation, and presets use a background task. A batch runs the same application-layer candidate directly. The progress of a split, a paint, a bake, and a fit includes the batch member it is in. The whole batch can be cancelled during preparation. It does not nest a member's single task. `classic_front_hair/classic_back_hair` support `sway:false`. After the simulation is removed, that kind of classic swing is turned off. Discovery returns `batchable:true` only when it is supported. GUI field completion is already connected to the asynchronous candidate queue. A draft of generation settings, classification, or mesh is converted into the shared pure candidate.

Adding an artwork layer supports an imported model and a parent deformer that was built by the user. The application candidate converts the source canvas geometry into the actual parent's neutral coordinates, and it saves the mesh-create record. A new registration uses the original processed pixels. It replaces the created geometry in place and keeps the object ID and the parent. An existing dedicated binding or mask dependency still refuses a single-layer placement. An artwork layer keeps the artwork's original resolution. After the transparent edges are cropped, the pixels become the layer raster directly, and the canvas rectangle given by the artwork placement or the registration becomes the layer rectangle (`canvasUnitsPerPixelX/Y` is the actual ratio). For example, a 1024-pixel artwork registered into a 32-unit region is a layer of 32 units and 1024 pixels. A registration of translation or scale (including an explicit mirror, which only flips rows and columns) does not go through interpolation. Only a registration that includes a rotation is rasterized, at the artwork's own density, into the bounding box. Both the artwork manifest and the layer save the original pixels. They are no longer shrunk back to canvas resolution. Before assignment, the coordinates, the 16MP bounding box, the 16MP raster, and the density limit are checked. The preparation stage responds to cancel. Continuous GUI placement goes through an independent application session. A save excludes the preview and waits for a formal confirm.

Each item runs on the previous item's candidate document and rebuilt model, so a parameter can be created first and then a keyform or a motion track can be bound in the same batch. After a canvas object is created, a later edit can also refer to it. An object that a later item needs to refer to should provide a stable ID. When an optional ID is omitted, the result `changed` contains the generated object's `kind:id` handle. A retry of the same request returns the original handle.

The document, the model, and one history node are published only when the final CAS succeeds. A member edit or a rebuild failure, a cancel before the commit, and a state conflict all keep the original workspace. A batch that does not change anything, and a batch that returns to the original document, do not advance state or append history. A member execution error returns `invalid_edit`, with `edit_index` starting at 0 and `edit_operation`. A schema error returns `invalid_request` and the field path. A session edit, a project switch, resource I/O, a read-only time simulation (simulation_simulate), and a nested batch cannot be members. A batch returns a process task handle. The state and `data.result` are read through `job_wait/job_get`. A successful result contains `project_id/state/history_node_id/revision/applied/edit_count/changed`. Progress is reported during per-item preparation and during a bake. A cancel before the commit does not publish the candidate. The full result is kept immediately after a successful CAS. A late cancel or a refresh failure still returns completed. A business failure keeps the classification and the index above in the task's `error`. A schema error is returned before the task is created. A disconnect, or cancelling the wait, does not stop the task. A retry of the original request ID retrieves the same task. An internal GUI call still uses the same command boundary.

## Parameter snapshots and history annotations

When `snapshot_create` omits `values`, it saves the current authored pose. When the evaluated values during playback need to be saved, pass the sampled values explicitly. `snapshot_update` can rename only, replace values only, or change both. An omitted field keeps the original value. Deleting a snapshot does not change the numbers of the other snapshots. The GUI snapshot bar and MCP share a neutral edit command. The data is captured from the runtime. Save and reopen keep the snapshot ID, the number, the parameter values, and the history annotations.

`snapshot_apply` keeps the values of parameters that are locked, ignores parameters in the snapshot that have been deleted, and clamps an old value to the current parameter range. Applying a snapshot in the GUI is the same as MCP. It is not affected by the timeline's automatic-keyframe switch. To record the timeline, call a motion editing tool separately. No change keeps the original `state`. An actual edit returns its own `state`, `project_id`, and `history_node_id`. A history annotation changes only a node's display title, description, and hidden mark. The node content and the branch relation stay unchanged.

An omitted parameter and lock of `preview_set` keep the value in the pose the runtime has committed. `snapshot_apply` likewise follows the committed locks. A parameter that is not hit keeps its original value. An animation evaluation frame and an uncommitted GUI display value are not the merge baseline. `preview_reset` restores every default and clears the locks. These three share an independent application command and an auxiliary CAS. They do not append rig history or an automatic keyframe. No logical change does not advance the state, but it can still restore the correct interface pose and stop playback. A save also uses, per workspace, the captured persistent pose and locks. Copying a workspace's pose is registered immediately. In the archive it is projected as the workspace fields of `workspace.json`.

## State and history

- A write that advances the model history needs the latest `state`. On success it returns a state later calls can use. When it is stale, inspect again and coordinate the edits. Do not overwrite blindly.
- Edits inside a batch are validated and rebuilt first, and committed after success. One `rig_deform` / `keyform_apply` can contain 1–128 changes. A single deformation can contain 1–16 operations.
- A keyform generated by swing or simulation (the key contains a generated parameter and it is not at the default): the `set` of `rig_deform` and of `keyform_apply` is recorded as a generated-result override, and it is merged after the generators. `copy` to or from these grid points, and `delete` and `parameter_keys` acting on a generator's axis, are refused, and the error names the generator. Using a generated parameter on another object (keying, a rename, a range change) first writes that parameter into the project from the generator's current definition, and after that it is the same as an ordinary parameter. A generator's own parameter cannot be deleted with `parameter_delete`.
- An ordinary write that changes nothing should not create a history node. `checkpoint` is the exception that leaves a point explicitly. Restore is a write, and it moves HEAD. Continuing to edit from an old node forms a branch, and the original branch is kept.
- `project_save_as` uses an absolute path to name the first save or the save-as location. `project_save` saves to the current location. `project_open` opens a project archive. When there are unsaved edits, first wait for the save task to succeed, or give `discard_unsaved=true` explicitly. These operations do not open a GUI dialog. `project_export_model` writes the delivery files, but it does not replace saving the project. Staged artwork is not the same as already being in the model, and it is not the same as already being saved to disk.
- After a timeout or a disconnect, check with `workspace_inspect` and `history_list` whether it was already committed, and then decide the next step.
- A transaction across several tool calls, a structured `history_diff`, and `task_*` execution control are not provided as current public interfaces.

### General shapes and physics

`rig_deform` operations include `translate`, `scale`, `rotate`, `arc`, `curve`, and `landmarks`. Coordinates use the normalized convention inside the fixed input bounds, X to the right and Y downward, and angles are in degrees. A selection and a falloff can limit the range. It does not accept an arbitrary per-point mesh array.

`keyform_apply op=seed` samples an existing shape at a named key. `copy` copies an explicit source key. `set` writes a channel or a rotation shape. `delete` deletes the matching key data. Creating a parameter by itself does not produce motion. It needs a shape and a parameter binding.

`keyform_apply op=mirror` mirrors a keyform left and right along a vertical canvas line. At commit it expands into an ordinary `set` (and `copy`). Replay does not compute the mirror again:

| Field | Meaning |
| --- | --- |
| `target` | The source mesh, Warp, or rotation deformer |
| `destination` | A target of the same kind. The default is `target` (the same object). `auto` finds the object on the other side from L/R, Left/Right, or 左/右 in the ID or the name |
| `from` / `all_keys` | The source key. Or `all_keys: true` processes every keyform grid point of the source. On the same object, only the keys on the `side` (`positive` by default / `negative`) are taken |
| `key` | The target key. The default is derived from `from`: a left/right parameter is negated about the default, a parameter that carries a side (ParamEyeLOpen) is swapped to the other side when the target binds the other side or when neither is bound, and an axis the target lacks takes the default. When it is given explicitly, it must contain every axis the target binds directly |
| `reflect` | The parameters that are negated. The default is an ordinary parameter whose range is symmetric about the default, and that is the horizontal axis of a two-dimensional link or whose ID ends in X or Z |
| `axis_x` | The canvas x of the mirror line. The default is the midpoint of the centers of the two objects' default-pose bounding boxes (the same object is its own center) |
| `channels` | What is carried: `geometry` and the channel names of `copy`. The default mirrors only the geometry |

What is mirrored is the object's own deformation. The points of the two objects are mapped to the canvas by the parent of the default pose. The displacement of each source point relative to the default shape has its x reversed, it is interpolated at the mirrored position of the target point on the source triangles (a Warp is split on the cell diagonal), and it is mapped back into the target's parent space. A rotation deformer mirrors the origin displacement and negates the angle change. A symmetric object, or a pair of objects, corresponds point to point. A blend deform key is not supported.

`keyform_apply op=reset / interpolate / paste` writes the whole geometric shape of one key (or only the points given by `vertices`). At commit it likewise expands into an ordinary `set`. Replay no longer reads the other keys. When a geometry `set` acts on a keyform a generator owns, it is recorded as a generated-result override. What `paste` writes is a displacement: a mesh relative to the original shape, and a Warp and a rotation deformer relative to the default-key shape. The source is sampled when that command is compiled. A later `paste` in an MCP batch reads the candidate model after the earlier members have written (so two `paste`s cannot swap A and B: whether they are in the same batch or committed as two calls, the second read is the result after the first write. To swap, first `copy` A to an empty key C, then paste B onto A and C onto B, in that order in the same batch). The editor's paste freezes the source at copy time, and it computes every `set` at once from the model before the paste:

| Field | Meaning |
| --- | --- |
| `target` | A mesh, a Warp, or a rotation deformer. For `paste` it is the source |
| `key` | The key that is written. It must contain every axis the target binds directly |
| `vertices` | Change only these points (the index of a mesh vertex or a Warp control point). The other points keep that key's existing shape. It does not apply to a rotation deformer |
| `to` (reset) | `default` (the default): the shape when the parameters in `along` are at their defaults. `rest`: meshes only, the undeformed mesh |
| `along` (reset) | Used together with `to: default`: the parameters that take their default. The default is every parameter of the key |
| `parameter` (interpolate) | Which axis to interpolate along. The default is the axis whose key happens to sit between two keys. When there is more than one, it must be given. It interpolates linearly, by position, between the shapes of the neighboring keys on both sides |
| `from` (paste) | The source key. An axis the source lacks takes the default, and the shape is read interpolated at that place |
| `destination` (paste) | The default is `target`. When writing geometry, the other object must be the same kind, have the same triangles (a Warp has the same rows and columns), and have the same parent, or it is refused |
| `all_keys` (reset) | Instead of `key`: every keyform of the object returns to the default-key shape (restore a deformer's shape) |
| `ratio` (paste) | 0–1, default 1: the fraction the current key moves toward the pasted value. Less than 1 is a blend |
| `flip` (paste) | `horizontal` or `vertical`: a Warp reverses columns or rows. A mesh finds the mirrored matching vertex by the rest position (the rest shape must be symmetric in that direction, or it is refused). Each point takes the matching point's displacement and reverses it. A rotation deformer's angle change is negated |
| `channels` (paste) | A combination of `geometry`, `opacity`, `drawOrder`, `multiplyColor`, and `screenColor`. The default pastes only geometry. Channel values are blended by `ratio` as well |

`keyform_apply op=multi_key` changes the channels of several keyforms of several objects at once. It expands into one `set` per keyform that contains only channels. `targets` (meshes, deformers, or parts). `keys` (a partial key list; a keyform must match one of them) and `ranges` (the key values allowed for each parameter; a keyform that is not on that parameter is not limited). The default is every keyform. `opacity` (0–1), `drawOrder` (0–1000, not available for a deformer), `multiplyColor`, `screenColor` (`[r, g, b]`). `method` is `overwrite` (the default), `add`, `multiply`, or `screen` (draw order accepts only the first two). The result is limited to the legal range. Each channel is written only on a key that already has its own track. Only when there is no track yet is it written by the object's geometry keys. `keys` / `ranges` filter these keys. What is written is an ordinary channel keyform. It is not recorded as a generated-result override. When no keyform matches, it is refused.

`path_get / path_list / path_preview / path_put / path_delete / path_deform` use mesh-local coordinates for points. They support a read-only query, a preview, binding, and baking keyforms. A path is an editing aid. Compatibility is in [Deform paths](../guide/DEFORM_PATHS.md).

A physics group is a Cubism pendulum. `inputs` (`parameter`, `weight` 0–100, `type` of `x` for position X or `angle` for tilt gravity, `reflect`) push 1–16 `segments` (`length`, `mobility`, `delay`, `acceleration`). `outputs` (`parameter`, `vertex`, `scale`, `weight`, `reflect`) read the angle of the end of segment `vertex` relative to the previous segment. `scale` is the parameter value per radian (the native Cubism runtime does not read the scale of a displacement-type output, that kind of output is always 0, so only an angle output is provided). The exported physics3.json and CMO3 declare the project's computation FPS (default 60). The `min/default/max` of `normalization.position/angle` are the targets of the input-range mapping.

- `physics_put` changes only the fields that are given. An existing ID (including a generated group) starts from the current group. A new ID starts from "head and body inputs, one segment of length 10, no outputs". A list field is replaced as a whole. `length` is the total length of the whole chain and scales each segment in proportion. `mobility/delay/acceleration` and `output_scale` apply to every segment or output. `segment_count` changes the segment count. Giving only `enabled` only switches that group. After a generated group is edited, it replaces the generated version, until `physics_delete`. The old `input_parameter` / `output_parameter` are still read as a single input and a single output.
- The same parameter can be driven by only one group that is in effect. When a custom group drives the output of a generated group, the generated group yields. `workspace_inspect scope=physics` returns `fps` and the groups in computation order. Each group carries `origin`, `enabled`, `active`, `overridden`, `replaced_by`, and `issue`.
- `physics_config`: `order` lists the group IDs to compute first, and the other groups follow in their original order. Cubism computes in order. A later group reads an earlier group's output in the same step. `fps` is the project's physics frame rate, an integer from 1 to 240. 0 means unlimited (physics is computed with every render frame, and export does not declare `Fps`). Preview frame output is not limited by it. The preview frame rate is a user setting, and it follows the display by default.
- `physics_import`: `path` is the absolute path of a physics3.json. The groups in the file become custom groups (the same ID replaces an existing group; a generated group stays replaced until `physics_delete`), and they are placed after the existing groups in file order. Other custom groups that drive the same output are turned off. The file's `Fps` becomes the project's computation FPS. It returns the imported IDs, the groups that were turned off, and the missing parameters.
- `physics_fit`: it runs the group with the standard shake of the panel response curve (pull to the right for 1 second and then release), and it adjusts each output's scale so the peak reaches exactly `target`% of the parameter endpoint (default 100). An output that does not move keeps its original scale. When `observed_peaks` is given (the key is the output index `"0"`, `"1"`, …, and the value is the arrival ratio returned by `physics_audition`, 1 being the parameter endpoint), it fits from this measured response instead, sharing the candidate with "adjust the scale by the maximum" after the panel drags the pendulum. An illegal index, a value that is not non-negative, or no output moving at all is refused before the commit.

`physics_put/physics_delete/physics_config/physics_import/physics_fit` return a process task handle, and each requires `request_id/project_id/state`. Read the state and the result after the commit with `job_wait/job_get`. An import result also contains `imported`, and `disabled/missing_parameters/fps` where they apply. Reading, fitting, the rebuild, and the commit report progress. The fit's settling and the per-frame solve support cancel. A cancel before the commit, or a state conflict, keeps the original project. A late cancel after the commit, or an interface refresh exception, keeps the successful result. A disconnect does not stop the task. A retry of the original request retrieves the same task. A fit supports an atomic batch and reads the preceding candidate. A file import does not support a batch. Fitting again when the target scale has already been reached does not create a history node. A group with no output response at all still errors.
- Make the motion endpoints for the output parameters first, and then connect the physics. A static pose sheet does not include time advancing. Use `physics_simulate` with a step input to check the amplitude, the overshoot, and the settling time. For a whole motion, use `view_sample_motion` (its native sampling environment has to be available).

## View and space mapping

View renders a PNG from the model data. It does not depend on a desktop screenshot. `canvas_rect` gives the canvas rectangle. `focus_layers` frames the view around objects. The output pixel size and the model canvas size are two different things.

`view_render_layer/view_render_context/view_render_model/view_render_poses/view_check_coverage` each read one captured project version. Every image of a multi-pose set shares that model and the visible layers. A later edit, a reopen, or switching projects is not mixed into the result, and it does not invalidate a query that has already been captured. The PNG, the space mapping, and the revision stay consistent. The image and the space reference are kept in the project from capture time.

- `poses` compares 1–9 poses in the same version and the same canvas rectangle, and it returns one labeled sheet. The total size budget applies to the whole image.
- A comparison pose is rendered in the background from the captured committed version. It does not read, and it does not change, the authored pose or the GUI parameter sliders. Do not use `preview_set` to switch poses in order to produce a comparison image. It changes the user's authored pose and advances `state`.
- A parameter that is not given in the request is rendered at the **parameter default**, not at the user's current authored pose. To use the current pose as the base, first read the committed pose with `workspace_inspect scope=preview`, put it in the shared `parameters`, and then write only the differences in `poses`.
- When `include_layer_ids` is omitted, the local visibility of the current active canvas is used. A layer the user hid, a layer under a hidden deformer, and a layer outside solo do not appear in the image. When a stable result that does not depend on the user's canvas is needed, pass the layer IDs explicitly (they can be taken from `workspace_inspect scope=layers`).
- `view_compare_history` compares history versions. `view_sample_motion` samples by time. `view_check_coverage` measures only the alpha coverage of a named rectangle and named layers.
- Locate with the pixel-to-canvas mapping that is returned. A whole multi-pose sheet cannot be used directly as the space reference of a single piece of artwork.
- Alpha coverage, a mesh diagnostic, and a file that was written successfully are not an art-quality score, and they do not prove that an unsampled pose is fine.

`view_sample_motion` returns a read-only task handle, and it also requires `request_id/project_id/state`. `frames` is 2–32 strict frame objects (`time/parameters`). Time increases strictly from 0, up to 10 seconds. When a parameter is omitted, the previous value is kept. `samples` is 1–9 time points inside the motion duration. `fps` is 15–120 (default 60). The result times are quantized downward by the sample frame rate. Before the task starts, the model, the visible layers, and the resource target are captured. A later edit, a reopen, or a GUI animation is not mixed into the sample. Native Cubism evaluation, per-image rendering, and the sheet report progress and support cancel. The optional native runtime has to be installed.

Read the terminal diagnostics and the PNG with `job_get/job_wait`. Reading again returns the same image. A completed result contains `project_id/state/revision`. An existing sheet's `revisionId` also points at the same captured version. Native sampling uses a temporary model. It does not change the GUI's realtime animation and physics state. Cancelling a queued task does not run it. After the frame loop is cancelled, the model and the temporary files are released. This read-only operation does not support a document batch. A history comparison is still an immediate query, but it also uses the history tree of the same capture. Reopening the project does not replace what it compares against.

An ungenerated project, an empty canvas, and a layer waiting to be generated all use the ordinary editing workspace. They support mesh, deformer, parameter, hierarchy, rotation, and texture editing. Export contains the current model. `rig_generate` generates the rig and the parameters on the existing meshes by the tags, and it keeps the mesh topology, except when `refresh_geometry` refreshes it explicitly. A new project imported from a PSD likewise registers each layer as artwork and links it.

A typical flow: `project_create` → `material_import` → `material_list` → several `layer_place` (or place a whole PSD folder) → `layer_tag` → `layer_reorder` → `rig_generate` → authoring edits → `layer_place` again → `rig_generate`. When an external tool has already split the parts, write a Layout manifest, use `project_import_layout` to get a placed ungenerated project in one step, check it, and then `rig_generate`.

`view_render_model` draws the reference layers (`layer_mark_reference`) under the model (`reference.mode` of `difference` compares only the model). `view_render_model` also has `grid` (draw grid lines with coordinate labels every so many canvas units; when they are too dense, the step widens by ×2, ×5, ×10, …, and the result's `gridStep` is the actual spacing) and `outline_material_ids` (draw the opaque edges of entries that have a canvas position, drawings and cropped close-ups, on the view in their own colors, with the id), used to read coordinates and to compare a drawing with the reference image. To see only the reference image, give `include_layer_ids: []` and `reference: {mode: under, opacity: 1}`.

`view_render_pad` assembles the model's look at a set of keyforms into one labeled atlas, so a whole 2D pad can be seen at once. Columns are `x_parameter` on `x_values` from left to right. Rows are `y_parameter` on `y_values` from top to bottom. When the values are omitted, the parameter's keyform values are taken (y from large to small). A parameter that belongs to a 2D pad brings its partner along automatically when `y_parameter` is not given. `columns` / `rows` (`[起, 止]`, including both ends, indices into those values) take any sub-rectangle. For example, a 5×3 pad takes `columns: [1, 3]` and `rows: [0, 1]`. `show` decides the content of each cell: `model` (only the model), `reference` (the reference layers that keyform shows, pinned here or not pinned), `under` / `over` (the reference under the model, or stacked on top by `reference_opacity`), `difference` (where they agree is black, and each cell gives a `difference` of 0–1), `side_by_side` (model | reference). Each cell's `imageRect` `[x,y,width,height]` in the result maps to `canvasRect`, and the reference layers that were shown are listed. At most 64 cells. `target_long_edge` / `max_bytes` constrain the whole image. A grid reference image drawn externally in the same order can be read back as pinned references with `reference_place_grid`.

The flow for drawing a part from a reference image: `layout_set_reference` → `reference_sample` to take colors, `layout_set_drawing_kit` to set the colors and the line classes → `view_render_model` with `grid` to enlarge and look at the part, `reference_trace` to take the contour, `reference_snap` to correct the points on the lines → `material_draw` (draw the hidden part complete from the form, and do not copy a defect of the original art) → `outline_material_ids`, or compare with `reference` after placement → edit repeatedly → `layer_place`, `layer_tag` → `rig_generate` → `view_render_poses` to check the parts that show on a turn.

The flow for splitting parts from a reference image: `material_import` the reference image → `layout_set_reference` → `material_crop` (`canvas_rect`) to cut a close-up → `material_export_png` → enlarge or redraw externally → `material_import` → `material_set_placement` (`from` the close-up) → layer by layer: generate externally the image with the frontmost part removed → `material_peel` → continue on the new base image → `layer_place` → the `reference` of `view_render_model` (`difference` to see the alignment, `referenceDifference` is the average difference) and `density` (a texture-density heatmap, `texelDensity` lists each layer's texture pixels per canvas unit) to check → `layer_set_canvas_rect` / `layer_transform` to fine-tune → `layer_tag` → `rig_generate` → `view_render_poses` to check the motion.

## Artwork workflow (asset_*)

`asset_prepare_reference / asset_import_png / asset_register / asset_reprocess` return a process task handle, and each requires `request_id/project_id/state`. Read the business result and the `state/project_id/history_node_id` after the commit from `data.result` of `job_wait/job_get`. A reference image, a registration preview, and a reprocessed image can be fetched again. A disconnect, or cancelling the wait, does not stop the task. A retry of the original request gets the same task. A preparation failure, a cancel before the commit, or a state conflict does not publish the artwork. A late cancel after CAS keeps completed and the actual result.

The four writes share an independent application-layer artwork session. A private candidate is prepared first, and then the immutable files and the artwork manifest are published inside an auxiliary CAS. Artwork that was actually added invalidates the old state, but it does not change the rig revision or append history. Importing the same content and mapping again is no change. Inspect and a trial composite use the captured document and artwork manifest. They do not read a GUI draft or a later registration. A save copies only the artwork that belonged to the project at capture time (`assetCatalog` of `workspace.json`). A PNG import checks the 16-megapixel limit before it allocates pixel memory.

For new artwork, the usual order is `reference → import → register → preview → add`, and `place → finalize` when it is needed. `project_create_artwork` can create a new project in the background from placed artwork. A switch refuses unsaved edits by default. `source_split_polygon` splits by a canvas polygon into an inside and a remainder. `source_split_components` assigns the existing pixels by the connected components of the current mesh. Neither paints in content that was hidden.

`source_get_components` is a read-only query. Pass `layer_id`. It returns the `project_id/state/revision` at capture time, `can_split/count`, and the component centers `canvas_x/canvas_y`. Components are sorted by the source image's Y, then X. Use that order to name the `names` of `source_split_components`, with an optional `sides` of the same length and unique `piece_ids`. After the leading and trailing spaces are removed, a name must be non-empty and unique, and the count must match the current components. Omitting a side, or using `none`, inherits the original layer. Component detection uses the current mesh of the query's capture. A later edit does not change an old query's result. The commit must carry that captured state.

`source_split_polygon/source_split_components` require `request_id/project_id/state` and return a background task handle. The `result` of `job_get/job_wait` keeps the new state, the history node, and the new source-image `layers` IDs. A polygon requires 3–32 canvas vertices and two `names` (the inside and the remainder). Both sides must have visible pixels. Two unique `piece_ids` are optional. After the new IDs are given, a later member of the same atomic batch can refer to them. The batch `changed` contains both the new source image's `layer:<id>` handle and the generated object handles. Preparation and the rebuild can be cancelled. A conflict or a failure before the commit keeps the original document. A late cancel or a refresh exception after the commit keeps the full success terminal state. The original request retrieves the same task.

Parts replace the original source layer. The original layer leaves the source image (it does not enter `deletedLayerIds`). A part becomes an ordinary source layer and inherits the classification, the parent, the visibility, the per-layer mesh, and the draw-order override. A split is one regeneration. The parts take part in generation at the original layer's position. The user's keyforms, channels, blend shapes, paths, vertex weights, and Glue on the original layer are carried onto the parts by a three-way merge (except axes that swing and simulation generated). A later change of face settings, stance, skeleton, and classification reaches the parts the same way. A simulation's target, bake offset, and connection role migrate to the parts. The journal writes a checkpoint after the split's `art_primitive` record. The record itself is no longer replayed. The atlas and export no longer contain the original layer. `layer_restore` (including restore all, which omits `layer_ids`) cannot bring it back. Only undo or a history switch returns to before the split. A later request that refers to the original layer or the original mesh ID fails, and the error lists the part IDs that replaced it. `source_get_components` does the same. A part can be split again. A model imported from CMO3 still soft-deletes the original layer by the old rules. The record format is in [Document layer](../spec/DOCUMENT_LAYER.md#split-materialization-the-art-primitive-record-art_primitive). An ordinary mesh, a split mesh, a newly created mesh, and a mesh imported from CMO3, on a single-layer or global mesh update and on a reset, keep the binding and the existing simulation offsets through an ordered replacement, including the restore of a mesh that was deleted. A new cut point and a boundary-vertex copy produced by a polygon split follow, with directional Glue, the part that owns that original vertex, and the two sides of the cut stay flush. A source image that has been deleted, that is a mask (a clip), that has a channel mask, or that has a non-normal blend cannot be split. A component query uses the actual texture address. It supports source-image padding, rotation, and scale. An ordinary target that has been edited can return `can_split:true`. The GUI dialog for splitting a mesh into connected components calls the same application command. It keeps the state from detection time. A multi-layer decision is one user history commit. The polygon operation is currently an MCP entry. It cannot be claimed from this that the GUI has a lasso-split menu.

`rig_update_generation` regenerates the rig with this program's generators (the GUI's **Model → Update generated result**). A project whose journal has a checkpoint keeps the generator output from the time the checkpoint was written. Upgrading the program does not change it automatically. This operation takes the generated snapshot the checkpoint saved, the result this program now generates for the same input, and the current authored rig, and merges them three ways. An object the user did not change follows the new output. The user's edits are kept. What could not be migrated cleanly is listed in `issues` (it also enters `quality.regeneration` of `workspace_inspect`). The result is appended to the end of the journal as a new checkpoint. If an earlier regeneration checkpoint in the journal would come out with a different structure when this program merges it (a different parent, vertex count, keyform axes, or blend shapes), it is remerged by this program first, and the correction is carried onto the later checkpoints and the current authored rig by a three-way merge (issue `remerged`, `target` is `journal:<序号>`, and `detail` lists the objects whose structure differs). The edits after that are kept. The request needs only `request_id/project_id/state`. It returns a background task handle, and it is also an atomic batch member. The task `result` is `state/project_id/history_node_id/revision/applied`, `updated`, and `issues` (each `{kind, target, detail?}`). When the generated result is the same and every merge agrees, `updated:false`, and no history node is appended. A project with no checkpoint is generated by this program on every build anyway. A model imported from CMO3 has no generated result. Neither needs an update (the latter is refused).

`source_split_depth` corresponds to the GUI's depth-split menu, multi-select, and dialog. Pass the current mesh's original `source_id` and a non-empty, unique `middle_ids` (without the `mesh:` prefix, and not including source). Optional `names` are two non-empty unique names for the back layer and the front layer. Optional `front_layer_id/front_mesh_id/back_layer_id/back_mesh_id/glue_id` name the new IDs. It replaces the source mesh and its layer with two new layers and meshes, a back layer and a front layer. Both layers carry the original pixels and can be painted independently. The middle mesh sits between the two layers. The result's `layers` are the front layer, then the back layer. The two layers take the source mesh's current parent, geometry, channel keyforms, blend shapes, paths, and vertex weights. The back layer takes over the source mesh's Glue, masks, and simulation targets. Directional Glue makes the front layer follow the back layer. The two layers use a fixed draw order, replacing the original draw-order animation. A mouth and derived lips copy only the selected mesh. They do not generate extra lips. Erasing the front layer empty still keeps the topology. A model imported from CMO3 follows the old record: it keeps the source mesh and its layer, and it copies a front layer and directional Glue onto it (it does not create a back layer).

A single item likewise requires `request_id/project_id/state`. The `layers` of the task terminal state are the new layer IDs (a model imported from CMO3 has only the new front layer). Unique `front_layer_id/front_mesh_id/back_layer_id/back_mesh_id/glue_id` can be given, so a later member of the same atomic batch can paint or edit the new objects. The batch `changed` returns `layer:<id>/mesh:<id>/glue:<id>`. The GUI keeps the state from when the menu or the dialog was opened. An auxiliary-data edit also invalidates an old confirm. Preparation can be cancelled. After the commit, the exact terminal state is kept. History replay, save and reopen, and a CMO3 read-back keep the motion and the Glue connection weights. It copies existing content. A hidden part still has to be filled in by painting.

An existing PSD is opened from a local absolute path with `project_import_psd`. The six paints `source_paint_brush / source_paint_pencil / source_paint_eraser / source_paint_bucket / source_paint_shape / source_paint_clear` return a process task handle. Take the committed state, the history node, and the generated handles from `data.result` of `job_wait/job_get`. The capability detail marks `job_backed:true` and `batchable:true` and provides `job_result_schema`. The brush, the eraser, the paint bucket, and the shape use the UI's raster algorithm. Points, the radius, and the line width are all canvas units, and they land on the layer's own raster. A layer whose raster density (raster pixels / canvas units; see [Per-layer size](../spec/DOCUMENT_LAYER.md#per-layer-size)) is 1 is the same as before. On a layer that stores a 1024² raster on a 32-unit rectangle, a brush of radius 2 draws a stroke of radius 64 pixels on the raster. After the commit the raster keeps the original resolution. It is not shrunk back to canvas resolution. When the paint goes outside the rectangle, the rectangle grows at the same density. When it is cropped to the opaque pixels, the density stays unchanged. A layer that is erased completely keeps one transparent pixel at canvas resolution. A private draft uses the layer raster as its base the same way. The `width/height` of a result such as `paint_session_begin` are the draft raster pixels. `canvas_rect` is the canvas rectangle it covers, `[left, top, width, height]`. A color pick reads the raster at the center of a canvas pixel. When the draft exceeds 16MP, the paintable margin around the rectangle shrinks. The default `rebuild_mesh:false` keeps the existing mesh and every binding, and it clips by the layer mesh. A pixel that lands on the mesh stays on the layer (a layer linked to artwork writes the artwork, and every linked layer updates together). A pixel that lands outside the mesh is split into a new layer immediately above it (named the original name plus `+`, with its own mesh, hung under the same parent and part, and placed as new artwork in the folder of the original layer's artwork and linked to it). An erase outside the mesh does nothing. A layer that has no mesh yet is not clipped. When the layer's own mesh needs to cover the new region, pass `rebuild_mesh:true`. The layer grows by all of the pixels and migrates the keyforms, the blend shapes, the paths, the vertex groups, and the Glue. Both ways are one commit and one history node. Existing keyforms, a Warp, or Glue no longer block painting. `clear`, or erasing every pixel, keeps the layer and the binding. The last layer can also be cleared and painted again. Deleting a layer uses `layer_soft_delete`. The front layer of a depth split always keeps its topology. An ordinary layer that has been edited, the front and back layers of a depth split, and the delete and restore of an imported CMO3 first replay the edits and then filter the active objects, keeping the IDs, keyforms, and bindings that restore needs. Changing mesh settings while a layer is deleted still saves the rebind result of the hidden mesh. The first actual delete or restore of an old project fixes the identity and the generation baseline in the new candidate, so an existing edit does not retarget another mesh because a layer was restored. An old history node is not rewritten. `layer_mesh_update` changes the mesh parameters of a single layer. After a reset, it inherits the global values.

The first time an ordinary transparent layer draws a visible pixel, a mesh is created automatically. `rebuild_mesh:true` does not have to be passed first. The first paint on a mouth also creates the derived lips and their generated keyforms. The `changed` of a completed single or batch task contains handles such as `mesh:<id>` of the new objects, and they can be edited further. A retry of the same request retrieves the same task. It does not create again or append history again. Erasing completely, even when the rebuild flag is passed, still keeps the mesh and the binding.

Generated lips follow the contour and the color saved at an explicit rebuild or at the first create. A later paint that keeps the mesh does not regenerate the derived texture. GUI frozen pixels and MCP gestures share the document candidate, the rebuild, and the state check through an independent `WorkspaceRasterCommands`. The create data enters the ordered journal. Save and reopen, and export, resolve the current texture again. Progress is reported during preparation and cancel is checked. A cancel before the commit keeps the original pixels and the history. A late cancel or a refresh failure after a successful commit still keeps the full completed result. A disconnect, or cancelling the wait, does not stop the task. A single-layer settings update of a new mesh is written into the document the same way, keeping the ID, the rebound paths, and the weights.

`layer_delete` and `layer_restore` both return a process task, and they support an atomic batch. Read the actual state, the history node, and the affected layers from `result` of `job_wait/job_get`. `layer_delete` really deletes the layer. The pixels leave the project. Its meshes leave the authored rig through the journal record `layer_delete`, together with the masks, Glue, paths, and weights that refer to them. A layer a generator reads also leaves the generation input. A later regeneration no longer generates a mesh for it, and it no longer affects any frame. Earlier history nodes keep it. `history_checkout` is the undo. The last layer cannot be deleted. A row that is not an independent source layer, such as a lip band or an old-version left and right half, is still hidden the old way. `layer_restore` restores only a layer that an old version soft-deleted. It may pass 1–256 unique `layer_ids`. When they are omitted, it restores all of them (an original layer that a split replaced is not among them; naming it errors and lists the parts). When there is nothing deleted, it is no change, and no history is appended.

The global mesh unit uses `meshUnits` of `settings_update`. `DOCUMENT` takes a document long edge of 2048 pixels as the reference, and the same image uses the same density after it is enlarged. `PIXELS` uses the source-pixel length. The single-layer parameters of both modes still mean a length in the chosen unit. An old v1 setting that has `meshSpacing` and no unit keeps `PIXELS`, so reopening does not change an old mesh. A new setting, the generation baseline, and export save the actual unit. The GUI unit switch and the public edit use the same candidate regeneration and topology migration. `meshTrace` decides what the outline reads. `TEXTURE` (the default of a new project) reads the layer's own pixels, reduced by maximum alpha to a resolution at most 4 times finer than a mesh unit. A stroke finer than a canvas pixel also stays inside the mesh. The vertex spacing stays unchanged. `CANVAS` reads the view scaled to canvas resolution. An existing setting that does not have this field is read as `CANVAS`. `CANVAS` also does not write the field. An old project's settings text and meshes stay unchanged. `meshWrap` (0–64 mesh units, default 0) is wrap topology. Before the outline is traced, a gap or a notch narrower than that value is closed. A small protrusion such as lashes or hair tips shares one envelope. Every painted pixel is still inside the mesh. `changes.wrap` of `layer_mesh` overrides it per layer. The layer mesh settings of `inspect` return the actual `wrap`. When the value is 0, the field is not written. A setting with no field is read as 0. The details are in mesh topology.

`import` accepts an existing local PNG absolute path or image bytes. Do not have the model generate Base64 verbatim. Omitting `solid_background` keeps the native alpha. When the background has to be removed, give the real flat color explicitly. A checkerboard screenshot is not transparent artwork.

`register` can use a frame, matching anchors, or an absolute transform. The target position of an anchor is a canvas coordinate. A generated-image coordinate is an original full PNG pixel. A mirror and a non-uniform stretch must be declared explicitly. Raising the resolution should not automatically enlarge the footprint in the model.

Trial-composite first and check the parent, the draw order, the masks, and the motion margin, and then add it formally or delete the layer it replaces. Artwork that already has an independent binding, keyforms, or a finished placement may refuse a whole relocation. Follow the actual error and the schema.

### Eye structure correction

The `eye_structure` of `module_catalog` returns the eye components and `sourceStamp`. Through `changes.rig.eyeParts` of `settings`, set `side` (left/right), `region` (upper/lower), `primitive` (line/tuft/side/skin/auto), `contacts`, or `path` by layer ID and component ID. The first time a component is set, `sourceStamp` is required. Coordinates are the eye's local coordinates, normalized by the eye width, with down the face as positive. A component or a layer of null resets it. An override that does not match the original-art digest is kept but does not take effect. This edit enters the normal settings history and is saved with the project.

### Full preset switching and clothing simulation

`modifier_catalog.baselines` returns the switchable preset IDs in the preference library, including built-in and user presets. `modifier_switch` receives `state` and `group`. It replaces the current preset as a whole and keeps ordinary author content. It goes through an isolated candidate, CAS, and a single history node. The old version and the new version are modifier-group configurations. They create instances directly and are evaluated by the same stack. They do not run old-project generation and conversion. Switching is refused when generated content, an override, or a checkpointed capability cannot be migrated safely.

`modifier_plan` with `type: "simulation"` can be paired with `preset: "clothing" | "front_hair" | "back_hair"`. It calls the original recognition and the automatic-weight flow. The returned simulation configuration contains `automatic_weights`. The weights are evaluated with the instance. Author weights of the same name that already exist win. When the add is confirmed, it bakes in the background and produces the binding and the physics. The plan itself does not bake. The old `groups` and `modifier_add_group` keep the append semantics, for compatibility with existing clients.

A switchable entry of the preset library is returned by `modifier_catalog.presets` (`id`, `name`, and a nullable `name_key`). `modifier_switch.group` uses an ID from there, including user-saved and imported JSON presets. `modifier_organize` receives `state` and a complete `nodes` array. Each node has `id`, a nullable `parent`, and a nullable `name`. A name means a folder. No name means a reference to a modifier instance. The organization layout is saved with the document transaction. It does not change the execution order. An actual reorder still uses `modifier_move`. `modifier_stack.organization` returns the layout.

### Algorithm plugin management

`plugin_list`, `plugin_inspect`, `plugin_install`, `plugin_enable`, `plugin_disable`, and `plugin_uninstall` do not require a project to be open. Except for the list, they return a background task. The install source, the version pin, and the request format are in [Algorithm plugins](../guide/ALGORITHM_PLUGINS.md).

The `context_version` of each algorithm in a plugin description is the context version it supports. `provides` lists the capability aliases it provides. `requires` still means the execution prerequisites.
