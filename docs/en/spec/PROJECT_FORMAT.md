# Project format v2

[Documentation](../README.md)

`.psd2live` is an unencrypted ZIP. JSON is UTF-8. Raster resources are PNG. A saved project contains the source artwork and the history needed to keep editing. It does not depend on the original PSD path. The export report `.psd2live.json` is not this format.

ZIP entry compression: PNG (`assets/`, `images/`, observation images) and the CMO3 source file are already compressed, and they are written `STORED` (uncompressed). Other non-JSON files of 1 MiB or more (such as a source PSD) are sampled first. They are DEFLATEd (fastest level) only when a fastest-level sample compresses to less than half the original size. Otherwise they are `STORED`. JSON and the remaining entries are DEFLATEd as usual. `manifest.json` is the last entry. Entries are sorted by name. The modification time is always recorded as 1980-01-01. Names are UTF-8. When the entry count, offset, or length exceeds the classic ZIP range, a ZIP64 record is written. Smaller entries are read and compressed ahead on several threads, then written in order. The read-back check and the unpack on open also run per entry in parallel. Reading accepts any compression method and any entry order. Earlier versions DEFLATEd every entry and placed the manifest among the other entries. Such an archive still opens. The compression method and the entry order are not part of the format identity. The manifest hash is over the decompressed bytes.

## Save state and project replacement

The `*` in the title bar, and the save / discard confirmation, follow the project content. They are separate from whether the archive happens to record interface state:

| Change | Save required |
| --- | --- |
| Source image, model edits, generation / export settings, the output directory, a history switch | Yes |
| Parameter pose and locks, snapshots, history notes, timeline aids (parameter bookmarks and each motion's masks, frozen tracks, and markers), canvas layer / deformer visibility, artwork and task records | Yes |
| Creating, deleting, renaming, or reordering a workspace, creating or closing a canvas | Yes |
| Selection and hover, search, the camera, workspace / canvas focus, edit / preview mode, layout, panel expansion, and display options | No; a manual save still records recoverable interface state |
| Playback, tracking switches, and live preview frames, observation logs | No |

A save captures one complete version. A new content change that appears while the disk write is in progress stays unsaved. An interface operation does not affect the completion of the save. An uncommitted field that is changed back to the value on disk does not leave a `*` from one edit mark. Committed history still needs to be saved.

Discard-and-open in the GUI first waits for edits and field commits that are already running, then captures the replacement boundary. Choosing discard allows the previous unsaved content to be replaced. A new content edit during loading, or another project replacement, still makes this open fail. An interface operation during loading does not block the replacement. Cancel or a failed load keeps the original project and the recovery record. After a successful replacement with a clean project, the discarded recovery mark is cleaned up after the old recovery write.

## Archive layout (v2)

A save writes v2. Each history revision is split into content-addressed document nodes. Unchanged parts are shared across revisions. Each node carries its own schema version.

| Path | Contents |
| --- | --- |
| `manifest.json` | Format name, version `2`, the project UUID, and the payload SHA-256 manifest |
| `source/original.psd` or `source/original.cmo3` | The original imported source file. A project created from images generates a PSD source file |
| `history/HEAD.json` | The current node and the node order |
| `history/nodes/` | Immutable parent-chain nodes and metadata (the same as v1) |
| `history/revisions/<key>.json` | The index of each revision: `{schema, nodes:{类型:哈希}, overrides?, clips?, payloads?}` |
| `document/nodes/<类型>/<sha256>.json` | A document node `{schema, kind, value}`. The types are `source` (source layers and groups), `generation-source` / `mesh-source` (a `placement-source` written by an old version is ignored on read), `layers` (visibility, soft delete, classification, parent, mesh and texture overrides), `settings`, `rig` (parameters, skeleton, swing, simulation, physics, hit areas, and the other rig definitions), `journal` (the author edit log, without overrides), `layout` (user tags, artwork links, generation state), `materials` (the artwork library: folders and items, pixels referring to rasters in `assets/`, SVG source inlined; a folder read from a PSD / CMO3 carries an `origin` file name, and its item's `placementCanvas` is the canvas size of the default placement), `document` (the remaining fields). `layout` and `materials` are written only when the document has layout state. An old version that does not know them refuses to open |
| `document/nodes/payload/<sha256>.json` | A content-addressed payload node of a large journal entry, listed in `payloads` by a schema 2 revision |
| `document/overrides/<sha256>.json` | A generated-result override `generated_override`, together with its position in the edit log |
| `document/clips/<sha256>.json` | Motion clips (`motions`, including each clip's `events`), generated-motion settings (`motionPresets`), expressions (`expressions`), and poses (`pose`). The last two are written only when the project has edited expressions or has set pose groups |
| `document/bakes/<sha256>.bin` | Simulation bake results (packed JSON, see “Bake files” below), listed in `bakes` by a schema 4 revision |
| `assets/` | Deduplicated RGBA rasters, saved as PNG |
| `auxiliary/assets/` | Staged artwork metadata |
| `auxiliary/views/`, `auxiliary/view-images/` | Spatial mapping of observation images. A project saved earlier also carries each rendered image. A save now no longer writes them |
| `auxiliary/workflow/` | Artwork reference packs, registration / placement, and other auxiliary records |
| `auxiliary/tasks.json` | Agent task and event records |
| `workspace.json` | Persistent UI state: layout, camera, selection, parameter preview, history notes, timeline aids (`timelineAids`), and the log |
| `images/<hash>.png` | Journal images |
| `rig/objects/` | Rig objects: the objects a checkpoint record refers to (required for a revision that contains a checkpoint), and the objects of each revision's authored rig |
| `rig/revisions/` | Optional. The authored-rig index of each revision (see “Authored rig” below) |
| `cache/head/` | Optional. A deletable cache for rebuilding the head revision (see “Head cache” below) |
| `thumbnail.png` | Optional. The preview image for the Start page: the model's rest pose at save time, long side at most 256 px. Open never reads it. Every save writes it again |

The file name of a document node, an override, and a clip file is the SHA-256 of its bytes. Open checks each one. The split is lossless: on open, the index is assembled back into the full document of each revision. The revision ID, node IDs, and branches stay the same. The full rig model is not saved. When a revision has an authored rig, open builds directly from it. Otherwise it is rebuilt from the source image, the settings, and the edits. An auxiliary directory appears according to whether the related feature is used. `cache/` holds only a deletable rebuild cache. It takes part in no identity.

### Checkpoints

The journal entry `rig_checkpoint` (`{op, v:1, authored:{header, frame, deformers, meshes}, issues}`) stores the authored rig as data at its position in the journal. `authored` is the index of the authored rig described below (the header and the object hashes). `issues` is what the regeneration merge that wrote it could not migrate cleanly (`{kind, target, detail}`; see the checkpointed rig). Replay starts at the last checkpoint: its authored rig (rebound by canvas texture coordinates when the atlas changes) plus the entries after it. Earlier entries are history only and are not replayed. The program writes a checkpoint when an edit changes the result of base generation, when a generated model is edited for the first time, and when 32 entries have accumulated after the last checkpoint (see [Document layer](DOCUMENT_LAYER.md#checkpoints)). The user does not edit it directly. The latter two save the authored rig from before the edit, and the generated snapshot `generated` keeps the one from the previous checkpoint. So a generated project that this version has edited is revision 3.

A checkpoint's objects belong to the document. The working directory writes the objects to `<project>/rig-objects/` before it writes the snapshot that refers to them. On save they are archived to `rig/objects/`.

### Authored rig

`rig/revisions/` stores the authored rig of each revision: the rig after base generation (including the skeleton bake), the old-format static edits, and the whole journal, and before swing, simulation write-back, and override merge (the design is the checkpointed rig).

| Path | Contents |
| --- | --- |
| `rig/objects/<sha256>.bin` | One rig object (`RigIrObjects`): the frame (everything other than deformers and meshes), a single deformer, or a single mesh, named by the SHA-256 of its bytes, shared across revisions and checkpoints |
| `rig/revisions/<revision>.json` | `{header, frame, deformers:[...], meshes:[...]}`: the header and the object hashes listed in rig order |

- An object is encoded as the binary form of the neutral IR (`RigIrBinary`, floats stored by their raw bits), with its own magic, encoding version, and object type. Reading accepts every version from `RigIrObjects.MIN_VERSION` on. A field added to the IR is read only from the version that added it. From encoding version 5, float arrays are written by byte plane (the first byte of every value, then the second, and so on). The numbers are unchanged and the DEFLATE ratio is clearly higher. Version 6 adds the IR's hit areas (an old-version object still reads; objects newly written by a later save are all version 6 encodings, and an object whose contents did not change also gets a new hash, so the first time a checkpoint is written after the upgrade the archive grows once, and after that sharing continues as usual). An existing object is referred to by a checkpoint through its hash and keeps its original encoding.
- The header is `{format:"psd2live-authored-rig", version:1, build, binding_key, pages, layers, bounds, face, warnings, skipped, visibility}`: the mapping from meshes to texture pages, source layers, and neutral bounds; the face center, radius, and initial tilt; generation warnings; entries skipped by replay; meshes that need layer visibility applied; and the atlas binding key. Floats are written as integers by their raw bits.
- The revision key in the file name is the document's revision ID (`WorkspaceRevisions.of`), the key the build looks it up by.
- The binding key is a digest of the atlas placement, page size, and texture-layer rectangles at the time the base rig was generated. On open, the atlas is packed for that revision by the current program. When the key matches, the saved texture coordinates are used directly. When it differs (this program packs differently), they are moved onto the new tiles by canvas texture coordinates. When an entry cannot be read or the check fails, the build proceeds as usual.
- A save writes the authored rigs the current process has built for each revision, and the entries read when the archive was opened, but only for the head, the end of each branch, and revisions whose journal has no checkpoint. The other revisions build from the last checkpoint. They do not need a generated base rig, and a copy is no longer stored for each of them (each mesh that was changed is another object in the archive). A revision that is absent is not written. `-Dpsd2live.materializedRigs=false` turns reading and writing off.
- The revision index does not enter the revision ID or the document nodes. A revision without it still builds. When the journal has a checkpoint, it builds from the checkpoint. Otherwise it generates and replays. A model imported from CMO3 does not write an authored rig.

### Head cache

A save may write `cache/head/`. It stores intermediate results of the head-revision rebuild that are expensive and safe to reuse, so open can skip the recompute. It is not authoritative data: open still rebuilds in full from the source image, the settings, and the edit log. The cache only pre-fills the generator's memory cache. Whether it is used is decided by that cache's own content key, so a rebuild with the cache and a rebuild without it produce a model that matches bit for bit.

| Path | Contents |
| --- | --- |
| `cache/head/manifest.json` | `{format:"psd2live-head-cache", version:1, build, generator, revision, language, entries:[{kind, file, sha256, bytes}]}` |
| `cache/head/skeleton-bake.bin` | The head's skeleton bake: a JSON header (bake version, cache key, skeleton definition, the read set, reparent records for objects that were not read, an optional full hash) plus the binary IR of the output model (`RigIrBinary`, floats stored by their raw bits; it does not contain the atlas, the source-image manifest, or deform paths; on a hit those are taken from the new base rig) |

- Keys: the head revision ID, the program version (`Compiler.version`), the generator constant `ProjectHeadCache.GENERATOR` (incremented when the generation logic changes and the entry's own key would not notice), and the interface language. Any difference ignores the whole cache. The skeleton cache key inside the entry (including `SkeletonRig.BAKE_VERSION`, everything the bake read, and the language) then decides whether it hits.
- Only the skeleton bake is cached (about 5–7 s on a cold start, about 1–7 ms on a hit). A single entry over 64 MB is not written. On save, the most recently used bake in the process whose skeleton definition matches the head is taken. If there is none, no cache is written. `-Dpsd2live.headCache=false` turns writing and reading off.
- On open, a manifest format, key, or entry checksum that does not match, or an entry that is missing, truncated, or cannot be decoded, is only logged and discarded. It never makes open fail. After reading, `cache/` in the unpack directory is deleted.
- The cache sits outside `history/` and `document/`. It does not enter the revision ID, the document nodes, or history. An archive without that directory still opens. The archive manifest still lists and checks these files. An earlier v2 program unpacked it with the other entries and did not read it, and it can still open an archive that carries the cache. When they save again, they do not keep that directory.

### Node schema

The schema of a node and of a revision index is upgraded only when a new field is used. The other nodes are still written as schema 1. Their contents are unchanged byte for byte. After an old project is saved, the node hashes and the revision index match what they were:

| schema | Applies to | New fields |
| --- | --- | --- |
| Node 1 | A node that does not contain the fields below | — |
| Node 2 | `source` and the three extra source-image nodes that have a layer with `rect`; `layers` that contains `textureOverrides`; `settings` that contains `atlas` or `atlasArrangement` | See the texture fields below |
| Node 3 | `source` or an extra source-image node that has a layer with `transform` | The layer's overall transform `[a, b, c, d, e, f]` (`x' = a·x + c·y + e`, `y' = b·x + d·y + f`, canvas units, y downward), applied to the layer's frame (the integer bounds and `rect`). Texture coordinates are anchored on the frame. Generation reads only the frame. The identity transform is not written |
| Node 4 | A `layout` / `materials` node that contains a field added after the layout nodes were introduced | Reference images, reference layers and pins, drawings, an artwork item's canvas and reference mark |
| Node 5 | A `clips` node that contains `expressions` or `pose`, or that has a motion clip with `events` | An expression `{id, name, fade_in, fade_out, entries:[{parameter, blend, value}]}` (`blend` is `ADD` / `MULTIPLY` / `OVERWRITE`); a pose `{fade_in, groups:[[{part, links?}]]}`; an event `[{time, value}]` |
| Node 5 | A `rig` node that contains `hitAreas` | Hit areas `{id, name, meshes}`, in test order. See [Export targets](EXPORT_TARGETS.md#hit-areas) |
| Node 6 | A `rig` node that contains `modifierStack` | Explicit ordered modifier instances, the algorithm version, fixed targets, configuration, dormant overrides, retired instance IDs, and applied capabilities. Absent fields mean the old preset flow. An empty stack means no extra preset |
| Node 6 | A `clips` node that has a motion with `file` | The stable file name kept by an applied motion. It does not change when an ordinary clip is renamed |
| Node 7 | A `clips` node that has a motion with `captured_ranges` | The parameter range `{min, max, repeat}` that a baked curve corresponds to, so a rebuild does not change the original control points |
| Revision 1 | The journal does not refer to a payload node | — |
| Revision 2 | The journal refers to payload nodes, and the index lists `payloads` | A journal entry `{"$payload": "<sha256>"}` |
| Revision 3 | The journal contains the checkpoint record `rig_checkpoint` | The index's `rig` lists the rig objects the record refers to, and the archive stores them in `rig/objects/`. It can also list `payloads` |
| Revision 4 | A simulation has a bake result | Each bake in the `rig` node is written as `{"$bake": "<sha256>"}`. The index's `bakes` lists them. The contents are in `document/bakes/`. It can also list `payloads` and `rig` |

A program that reads only schema 1 refuses to open when it meets a schema 2 node or revision. It does not drop the new fields. The current program reads node schemas 1–4 (`settings` nodes 1–5, `rig` nodes 1–6, `clips` nodes 1–7) and revision schemas 1–4. A higher schema is still refused. A program that does not know schema 5 refuses to open when it meets a `clips` node that carries expressions, poses, or motion events, rather than dropping them. The `rig` node of revision schema 4 can refer only to bakes the index lists. On open, each bake file is checked by hash. An earlier program refuses to open on revision schema 4, so a project that carries a bake cannot be opened with them after it is saved. The index of revision schema 3 must list `rig`. On open, each object is checked to be present in `rig/objects/`. Missing any one of them refuses the open. A program that does not support schema 3 cannot build a model from such a revision, so it refuses to open. Revision schema 2 must list at least one payload. The journal can refer only to payloads it lists. On save, a revision that already contains a schema 2 node externalizes an author journal entry of more than 512 characters as a payload node (the reference inside the journal node is under 80 characters). Each payload is written only once. The revision index is schema 2. A program that reads only schema 1 already cannot open such a revision. A document with none of the new fields is still written entirely as schema 1. The nodes and the index are unchanged byte for byte. A long history therefore no longer stores a full journal in every revision. Archive size and save time no longer grow with the square of the revision count.

### Bake files

A simulation bake (`rigEdits.simulations[*].bake`) is mostly an array of vertex offsets. It often takes up most of a revision document, and it is unchanged across many revisions. It is not placed in the `rig` node: each distinct bake is stored as one packed JSON file by the SHA-256 of its bytes, shared across revisions. Changing other rig definitions, such as bones, no longer copies the bake.

Packed JSON (`PackedJson`) stores a JSON value without loss. An array of at least 8 elements, where each number's text is exactly the canonical text of its float32 value (the way the program writes a float), is replaced in the JSON text by `{"$f32": 序号}`, and the numbers are written after the text by their raw bits. The other numbers keep their original text. Decoding produces JSON that matches element by element. Layout: magic `P2LJ`, version 1, flags (1 means the text contains no reference, used when the original value itself contains a `{"$f32": …}` object), the text length and the UTF-8 text, the array count, then each array's length and its floats arranged by byte plane (the first byte of every float, then the second, and so on, which helps DEFLATE); integers are big-endian.

### Texture fields

All four fields are optional. Absent means the old meaning, and they do not take part in an old document's revision. Generation and atlas packing read them (the rules are in [Document layer](DOCUMENT_LAYER.md#per-layer-size)):

- A source layer's `rect: [left, top, width, height]`: a floating-point canvas rectangle (canvas units), the layer's position on the canvas. A pixel operation does not change it. It is not written when it is absent or equal to the integer bounds. The integer `left/top/width/height` is still the bounding box, and the rectangle must lie inside it. The layer raster (the width and height of `raster`) can be any resolution, unrelated to the rectangle. Raster pixels / rectangle size is that layer's native density. The two axes can differ.
- The document's `textureOverrides: {图层 ID: {density?, lock?, pin?: {page, x, y}}}`: the per-layer texture density multiplier (default 1, the raster's original resolution), the lock (density is kept when the atlas needs to shrink), and a fixed atlas position (page, top-left page pixels). An item that is all defaults is not written. It lives in the `layers` node.
- The setting `atlas: {pageSize, maxPages, padding}`: the atlas budget. When absent, the budget is the old `atlasSize` / `texturePadding` plus a default page count of 8. A missing sub-field falls back to those two the same way.
- The setting `atlasArrangement: {fitStep, tiles: {图层 ID: {page, x, y, rotation?, footprint?: {cell, columns, rows, bits}}}}`: the saved atlas layout. `x` and `y` are the top left of the tile's unrotated rectangle. `rotation` (degrees, default 0) is the rotation about the tile center, in the same direction as Umamo's placement (clockwise when y is downward). When absent, every rebuild arranges automatically (the old meaning). When present, each tile keeps its position, and every unlocked tile uses the shared fit of `fitStep / 4096`. `footprint` is the cells the mesh covers on the layer raster (each cell is `cell` raster pixels, `bits` is a row-major bitmap, a Base64-encoded `BitSet`). A tile with a footprint writes only those cells. A newly imported project saves its first layout.

## v1 compatibility and migration

A v1 archive can still be opened. v1 saves each revision as one complete snapshot:

| Path | Contents |
| --- | --- |
| `workspace/<projectId>/HEAD.json`, `history/nodes/` | The current node, the node order, and node metadata |
| `workspace/<projectId>/history/snapshots/` | The complete document of each revision: source layers, configuration, structure, and edit overrides |
| `workspace/<projectId>/blobs/` | Deduplicated RGBA rasters (PNG) |
| `workspace/<projectId>/assets/`, `views/`, `view-images/`, `workflow/`, `tasks.json` | Auxiliary data |

The other entries (`manifest.json`, `source/`, `workspace.json`, `images/`) are the same as v2. Opening v1 reads these snapshots directly. The document in memory matches v2. The next save writes v2, and before replacing the target file it saves the original v1 file as `<名称>.v1.psd2live` in the same directory (an existing backup of the same name is not overwritten). Migration changes only the storage layout. Every revision, branch, note, artwork item, observation image, and task record is kept as it was. The working directory still uses the snapshot layout internally: on open, the archive is unpacked into snapshots. A save does not go through snapshots. It encodes the history in memory, splits it into v2 nodes, and writes them to a staging directory.

The working directory's snapshots differ from v1 only in shared content. A newly written snapshot writes a non-empty `rigEdits.authoringJournal` as `{count, chunks:[键...]}`. Entries are stored in content chunks at `history/journal/<键>.json` (a chunk ends after the entry the digest selected, about 4 entries on average, and no more than 16 entries or about 64K characters; the key is the SHA-256 of the SHA-256 of each entry in the chunk). An `rigEdits.importedCmo3` of more than 64K characters is written as `{payload: sha256}`, with the contents at `history/payloads/<sha256>.txt`. A simulation bake is written as `{"$bake": sha256}`, with the contents at `history/bakes/<sha256>.bin` (the same packed JSON as the archive; the same bake is read once across revisions and decoded as the same object). Appending an entry adds only the chunk at the end. A chunk that was already closed is shared across revisions. On read, the original snapshot is restored after the keys are checked. The key order stays the same. The same restore happens before packing into v2, so the archive nodes are unaffected. Snapshots are now compact JSON. An old program that does not support chunks reports an error when it reads the object form. It does not drop the journal. Unpacking v2 also writes snapshots in this shared form. On read, the same entry is parsed once across revisions and shares one object (not only for a shared chunk: the last chunk of the journal is cut at the end of the journal, and the trailing entries of neighboring revisions are merged by content deduplication). A complete snapshot written by an old version still reads. The two kinds of snapshot can be stored together.

An internal file name may use a hash of the logical ID. It cannot be inferred from the display name. PNG keeps the RGB under transparent pixels. Different revisions share raster resources.

## Saving and recovery

On PSD / CMO3 import, the original bytes are copied first to `sources/<sha256>.<格式>` in the working directory, and that copy is what gets parsed. The external path is only a source description. Moving, deleting, or rewriting the original file does not affect the save. `originalSource: {format, sha256}` in `workspace.json` describes this source. A save rechecks the copy's digest. Opening an archive checks it and takes over the source. An old project with no descriptor can still be opened. A project created from images, or one that lacks an original source, generates a PSD from the root history source image. A model imported from CMO3 continues to keep the original payload in the document.

Automatic recovery uses `recovery.json` in the working directory (schema `version: 1`; it does not change archive v2): it contains the load identity, the runtime state, the history HEAD, persistent auxiliary data, the workspace presentation, and the task record. History and referenced resources are written first, then the checkpoint is updated atomically, and finally the session recovery pointer is updated. An independent change of pose, snapshot, notes, visibility, or workspace content also triggers a recovery write. A live frame and a pure display change do not. Recovery checks out the checkpoint HEAD and restores this content, and it stays unsaved. When an old working directory has no checkpoint, recovery follows history compatibility. A task record does not restart execution on its own.

A background write confirms the version that actually landed, by destination. A complete snapshot that is waiting can be merged. An earlier credential is confirmed by the complete version that overwrites it. A failure stays at its destination and is cleared only by a successful retry of the same destination. A save waits for the critical credentials related to the project. A write of an unrelated observation resource does not hide a recovery failure. A normal save / discard exit drains the queue, then deletes the matching recovery pointer and releases the unpack directory it owns. An abnormal exit keeps the recovery resources. A drain timeout keeps the registration. The next start collects only registered temporary directories that have no live process and no recovery reference.

Skeleton data lives in the configuration's `rigEdits.skeleton`. The current skeleton sub-structure version is 9 (it does not change the project format version). A bone stores an explicit `connected` (when absent, the old coordinate inference is compatible), a copy's `parameterOverride`, a `mirror` pair, and `ik` solve settings. The skeleton stores `symmetryAxisX`, named `savedPoses`, `ikTargets` keyed by bone ID, and `manualWeights` keyed by art-primitive ID. Manual weights contain the rest-canvas `positions`, `triangles`, and per-vertex `weights` of bone ID → weight, so an encrypted vertex is read by triangle interpolation. An old project reads, by default, as empty manual weights, no fixed target, and the default IK settings, and it can still be edited.

A save captures immutable state, writes a temporary file in the same directory in order, checks the manifest, and then replaces the target atomically. When atomic replacement is not supported, it reports failure and keeps the old project. A new edit that happens after the capture still belongs to unsaved content.

A save does not re-encode content that already exists: a raster PNG already in the working directory is placed in the staging directory by a hard link (or, when that is not supported, a copy that keeps the modification time). It is not encoded again from pixels. A revision's split result is also computed only once: the working directory's `archive/` mirror stores the v2 index of each revision that has been saved or opened (`archive/revisions/<快照键>.json`: `{version, index, rasters}`) and the document nodes it refers to (`archive/document/`). A save links those files directly. It encodes, splits, and hashes only new revisions, so the time of another save grows with the size of the change, not with the length of the history. When a v2 archive is opened, a revision split by the current rules (no inline bake; a long journal entry of a revision that contains a schema 2 node is already externalized) is moved into the mirror together with its nodes. The first save after open also handles only new revisions. The other revisions are split again on save. When the mirror's recorded version differs, or a file is missing, the split proceeds as usual. While the archive is written, the SHA-256 of each entry under `document/` is checked to match the file name. A damaged mirror file makes the save fail, and a wrong archive is not written. While the archive is written, each file is read only once. SHA-256 and CRC-32 are computed as it is written, and the manifest is generated from them. The digest of a `STORED` entry is cached in the process by entry name, length, and modification time (unpacking a project on open records it too). An unchanged raster is only copied on the next save, not recomputed. After the temporary file is written and `fsync`ed, it is checked by a streaming read-back: the entry set is exactly the entries that were written plus the manifest, each entry's length and CRC match what was written, and the manifest bytes are the same. The archive is not unpacked to disk to recompute hashes. A stale cache cannot write a wrong archive: a `STORED` entry checks the actual bytes by CRC and length as it is written, and the read-back checks them once more. Any mismatch makes the save fail and keeps the original file. The full SHA-256 check on open is unchanged.

On open, only the head revision is read and decoded. The other revisions are read the first time they are needed (a history switch, observation, or a save that needs their contents). Revisions read from the same working directory share journal entries, bakes, and rasters. When a v2 archive is opened, a revision split by the current rules does not write a working snapshot. The first time it is needed, it is assembled directly from the nodes in the mirror (each node, entry, and rig-object reference was already checked one by one during unpack). A save does not decode a revision that was not read: its checkpoint rig objects are listed by the mirror index, and the authored rig is looked up by the node's revision ID. Each distinct raster in the history is decoded only once. One revision's rasters are decoded in parallel on several threads (the thread count is limited by core count and heap memory). An 8-bit RGBA/RGB, non-interlaced PNG that the working directory wrote itself is decoded directly to RGBA bytes. Other PNGs are read through ImageIO. Both results are checked against the raster digest. A digest that passes is filled directly into the revision and rig stage caches, and it is not computed again. The artwork-manifest check reads only artwork metadata and confirms that the raster files exist. It does not decode pixels (pixels are checked when the artwork is loaded), and it checks only once per open.

When the current content matches HEAD, an ordinary save does not add history. An explicit `checkpoint` can leave a point when nothing has changed. A failed save should not be treated as persisted. Check the interface error.

Every branch is kept. Undo follows the parent node. When redo has several successors, a branch is chosen. Editing from an old node creates a new branch. Changing the title, the note, or hiding a branch does not rewrite the original node, and it does not delete artwork.

Creating, updating, and deleting a new parameter definition are written to `rigEdits.authoringJournal` and replayed in the actual edit order. A parameter deletion therefore runs after the earlier keyforms and after the last default-value update. The old static parameter-override fields keep their original read order. Existing snapshots, revisions, and node IDs are not rewritten. Channel keyforms and geometry edits are persisted the same way.

The internal mesh-replacement record `canvas_mesh_rebuild` also lives in the ordered journal. It stores parent-local vertices, triangles, source-canvas texture coordinates, the interpolation sources of the old vertices, and the Glue vertex map. The optional `neutral_bounds` stores the replacement mesh's neutral canvas bounds. The first replacement of a canvas base shape imported from CMO3 can store `previous_parent_points`: replay first rebases ordinary and blend keyforms onto those parent-neutral vertices, then migrates them to the new topology. Existing paths are converted along the original triangles. Replay checks the old mesh geometry's SHA-256, the parent, and the source-image identity (if the recorded parent is no longer produced by base generation, for example the arm-hang Warp after the skeleton is enabled, it checks only the vertex count, and moves the vertices into the current parent space by an affine fit from the recorded points to canvas texture coordinates; see [DOCUMENT_LAYER](DOCUMENT_LAYER.md#when-the-parent-is-no-longer-generated)). It rebuilds UVs from the current texture position, and migrates keyforms, blend shapes, paths, vertex groups, and Glue. An independent mesh-settings change keeps the earlier journal and appends an ordered replacement. It does not rewrite an old create record or history, and it does not change the project format version. This is an internal replay format.

The internal create record `canvas_mesh_create` stores a mesh that does not exist in the original generation input: a fixed ID, the source image and layer identity, the transparent coverage bounds, the parent and the part, the static material, local vertices/triangles, canvas texture coordinates, generation parameters/keyforms/channels, and paths. Replay resolves the current atlas again. It requires that the mesh ID does not already exist (a record with `replace: true` replaces an existing mesh of the same ID and keeps its draw order and part position, and creates it when there is none; when an imported image is placed, if the mesh is already in the checkpoint's rig, the record written is of this kind), and that the parent and the source image can be resolved. It validates the geometry, the keyforms, and the raster size. An ordinary transparent layer, and the first time the mouth draws a visible pixel, creates a mesh automatically. Clearing it afterward keeps the created geometry and the binding. A mesh-settings change updates the created geometry in the current candidate and persists the rebound path and weights. Earlier history snapshots stay as they were. This is an internal format. It does not change the project format version.

The old internal partition record `canvas_source_partition` (a new version writes it only on a model imported from CMO3) stores the original mesh ID, the local geometry fingerprint, the parent, the partition each original vertex belongs to, and the new mesh/source-image ID, name, visibility, local vertices, triangles, source-canvas texture coordinates, and vertex interpolation sources. Replay copies the binding at the original journal position and remaps the current atlas. The original layer's soft delete is filtered after every edit has been replayed. Connected components migrate Glue in the original order. Simulation targets, existing bake offsets, and Glue roles are written into the same document candidate. The original generation input adds a transparent placeholder to keep the texture coverage. Existing history is not rewritten, and the archive format version does not change.

The internal art-primitive record `art_primitive` records a polygon, connected-component, and depth-split split on a generated model: at the record's position it deletes the meshes in `supersedes`, and the parts take their place. The original layer is removed from `source` and kept only in the frozen `generationSource`. It is not added to `deletedLayerIds`. A part is an ordinary source layer. A split is one regeneration: when the original mesh was generated by a generator, the record is version 2 (`v: 2`). It only declares what the generator uses to generate the parts (the rest canvas mesh, the layer, the classification, and `authored` is an empty object). The user's changes on the original mesh are carried onto the parts by a three-way merge. When the original mesh was not generated (a mesh created by the journal), the record is version 1, and the parts carry all of the data as user objects. In both cases a `rig_checkpoint` follows the record immediately. The record itself is not replayed again. The fields and the handling of the generation input are in [Document layer](DOCUMENT_LAYER.md#split-materialization-the-art-primitive-record-art_primitive).

A record written by an earlier version can still be read: a version 1 record carries all of the parts' data; a version 2 record stores, in `authored`, the material and user data that differ from the generated values, `geometry_residual` / `channels_residual`, and it is followed by `generated_override`. When there is no checkpoint after them, they are replayed as before. The first time such a project is edited, a checkpoint of the current authored rig is written at the end of the original journal, and these records are not replayed after that (see [Document layer](DOCUMENT_LAYER.md#legacy-replay)). `canvas_source_partition` and `canvas_depth_split` in an old project are handled the same way. The archive format version does not change.

The internal `mesh_generation_baseline` mark stores the previous global mesh, the per-layer overrides, and the alpha threshold. It affects only base generation. The document's current settings still state the actual request. A later mesh update, reset, and global adjustment generates the replacement from the saved mesh input or the current pixels, and appends `canvas_mesh_rebuild` in the actual parent's neutral coordinates. An ordinary mesh, a partition, a newly created mesh, and a mesh imported from CMO3 use the same replacement flow. Ordinary/blend keyforms, paths, vertex groups, Glue, and simulation bake offsets migrate to the new topology. The bake keeps the old fingerprint and quality metrics, updates the vertex count, and continues to report that the input is stale. A deleted mesh is also regenerated first and then filtered. Restore uses the new topology. An old document adds the mark only in the new candidate of an actual mesh change. Old revisions, history nodes, and the archive version stay the same. An imported model only normalizes the texture address of a mesh that has been replaced. A fully transparent source image keeps the existing topology. Each replacement interpolates the edit offset of the previous topology. After the topology has been coarsened, resetting the settings cannot recover high-frequency detail that has already been lost.

Deleting a layer writes the journal record `layer_delete` (`{op, layer_id, meshes}`; the authored rig deletes these meshes and the masks, Glue, paths, and weights that refer to them). The layer leaves `source` and the generation input at the same time. The build writes a checkpoint before that record. The following applies only to the soft delete of an old version: it uses the document's existing `deletedLayerIds`. It does not erase source pixels or ordered edits, and it does not modify old history nodes. A project that contains a create record, a source-image partition, a depth split, or an internal `layer_membership` mark, on rebuild/export, first restores the full generation input and the edits, then filters deleted layers and derived lips, and cleans mask references, Glue, paths, and vertex groups in the active model. Restore replays the saved IDs and bindings again. The first actual delete or restore of an ordinary project saves, in the new candidate, the current generation range and every source-image/Drawable identity, and appends a `layer_membership` mark that has only the `op` field. After restore, that identity baseline is kept. An imported CMO3 keeps the original model's IDs and coordinate system, and only appends the mark. An old document without the records above is still read by the original generation rules. It is not upgraded automatically, and existing revisions and nodes are not rewritten. A mesh-settings change during deletion also regenerates hidden meshes and saves the rebound path/weights. The texture lower bound uses the full input. Delete, and restore of a specified layer or of all layers, in the GUI and in MCP share the candidate commit. A repeated operation does not append history. It reuses the existing journal and baseline fields. It does not change the archive format version.

The optional `generationSource` of a history document uses the same canvas, layer, and raster blob format as the current source image. It stores the original raster shape required to generate the base rig. The current `source` provides the actual pixels after painting. The generation coordinate system and the base topology use the saved input, then remap UVs to the current texture by source-canvas coordinates. When a crop is tightened, transparent coverage is filled in, so an old mesh does not sample a neighboring image. The optional `meshSource` uses the same encoding. It updates the target-layer input of an explicit rebuild or a first create, and stores the contour and color that generate the lips. Painting that keeps the mesh keeps that input. A layer added after the generation input was frozen, and not yet in it (for example an image an Agent added), is generated from the current pixels. The first time its image is painted or replaced, the candidate first writes the pixels from before that change into `generationSource` by the way its mesh traces a contour: `meshTrace = CANVAS` at canvas resolution (one pixel per canvas unit, integer bounds), `TEXTURE` laid onto the integer bounds at the texture's original density (a floating-point rectangle is folded into the raster), so painting that keeps the mesh does not change the topology, and a rebuilt mesh migrates from the original mesh. A depth-split front piece, an art-primitive part, and a partition fragment still follow their own records. Placing an asset layer again removes that entry, and the mesh regenerates with the new placement. An existing revision is not backfilled. An update of a derived texture input is a persistent change even when the vertices did not change. The optional `placementSource` also stores the source-image format. It keeps the original pixels after the crop at image-file import, and it is used to recognize a file-imported layer. Import and placement no longer resample pixels. They only change the layer's canvas rectangle (`rect`). A layer that an old version scaled by its bounds is restored to those original pixels when it is placed again. The four source images and the history nodes share deduplicated PNG blobs. When a new field is absent, it does not change an old revision or history node.

Canvas pixels captured by the GUI and an MCP raster gesture enter the same document candidate. Erasing a layer completely empty keeps the layer, the base mesh, and the binding even when a rebuild flag is passed. It does not soft-delete implicitly. CMO3 painting keeps the original atlas and UVs of an unedited mesh, and appends a texture page only for a mesh that has been painted.

Reopening a project builds the model from the authored rig saved by the revision, or from the last checkpoint of the journal. When it has neither, it rebuilds from the source image, the settings, and the edit log. Native handles, network connections, tasks that are running, and the animation clock are not saved. A saved Agent task is a record. It does not resume execution on its own.

A committed pose and parameter locks are saved per workspace in the runtime auxiliary state. The archive still projects them as the original workspace/canvas fields of `workspace.json`. A save uses, per workspace, the captured persistent values and locks, and excludes temporary GUI display values and the evaluation cache. An old pose is normalized by the current parameter definition when it is queried, when a preview is modified, and when a snapshot is applied. A read and a logic change that is not a change do not rewrite an old record or history node. Copying a workspace registers the copied persistent pose.

The optional `assetCatalog` of `workspace.json` stores `{version:1, assets:[ID...], workflow:[ID...]}`. It records the committed artwork and the member set of reference/registration. Resources still use the existing auxiliary directories. They do not enter the rig journal. Writing artwork advances the runtime persistent state. It does not change the rig revision or history nodes. A save copies resources by the captured manifest and excludes artwork committed later. When an old file lacks the manifest, the open stage fixes the members from the existing immutable records and does not rewrite history. A new project starts from an empty manifest. Open also checks that the manifest members exist, the project identity, and the reference relationships. An artwork check or a trial placement uses only the captured members. A failure, or a cancel before commit, does not publish a candidate file.

## Validation limits

On open, the version (1 or 2), the manifest, the hashes, the document-node hashes and schemas, the payload references, the rasters, the history references, and HEAD are checked. An unknown document-node type or a higher schema refuses the open. Content is not dropped. Duplicate entries, a path that escapes, and an unsupported version are refused. Unpacking is limited to at most 1,000,000 entries and 64 GiB of actually decompressed data. Do not rely on the size a ZIP declares to get around the limit.

The archive can be unpacked and inspected, but a manual edit has to update every reference and the manifest hash together. Ordinary operations use the interface and the history tools. The old `.rgba.gz` recovery store is a compatibility read. It is not the main write format of a new project.

## Entry points

- Import a PSD: `Ctrl+Shift+O`. Open a project: `Ctrl+O`.
- Save / save as: `Ctrl+S` / `Ctrl+Shift+S`. Save as defaults to the same directory as the current project. The suggested file name is neither the current project file nor a name that already exists (`名称-2`, `名称-3`, …). When the target already exists, overwrite is confirmed inside the window. When the target is the current project file, that is stated separately. A save or save-as requested while an edit is still applying is queued and shown in the status bar, and it runs after the edit finishes. A queued save-as is not downgraded to an ordinary save by a later `Ctrl+S`. The system file dialog uses the main window as its parent. A request while one is already open brings it to the front.
- MCP: `project_save`, `project_save_as`, `project_open`, and `history_checkpoint`, `history_list`, `history_checkout`. Save as and open use an absolute path. The destination does not have to be chosen in the UI first. A modification request uses the current `project_id`, the opaque `state`, and a unique `request_id`. Reopening the same node also invalidates the old state. A public summary does not mean every internal project field can be queried. See the [MCP contract](../agent/MCP_AUTHORING.md).

Creating a standalone Warp is stored in the `warp` command of the ordered `authoringJournal`. It records the fixed ID, the parent, the mesh list, and the fit options. A new command does not append the old static Warp/structure fields. An old Warp record is still read in its original replay order. A stored history node is not rewritten.

A modifier instance can store `inputFingerprint`, the full upstream-input identity of an expensive evaluation. The simulation bake and that identity enter the `rig` node and the document revision with the stack. It is independent of the configuration. When an old instance lacks it, verification continues by the old bake fingerprint, and the full identity is filled in after the first candidate is prepared.

A clip baked by a motion modifier can record `captured_ranges`, storing the parameter minimum, maximum, and repeat of each track at the time it was baked. A `clips` node that contains this field uses schema 7. When the range has not changed, a rebuild no longer rewrites the baked curve control points. The curve is tidied and the record is updated only after the range is actually adjusted. A node without this field keeps its original schema.
