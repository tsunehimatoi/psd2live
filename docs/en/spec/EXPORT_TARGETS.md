# Neutral rig IR and export targets

[Documentation](../../README.md) · [中文](../../zh/spec/EXPORT_TARGETS.md)

Every export starts from the same neutral rig IR: the editor compiles the currently committed rig into the IR, each export target lowers the IR to its own format, and writes a loss report listing what that format cannot keep.

## IR conventions

- Mesh rest positions and every deformer's keyforms are in the parent deformer's space: canvas pixels at the root (y down), the 0–1 grid space for children of a warp, local pixel coordinates for children of a rotation.
- All IDs are stable and survive regeneration.
- Motion clips are already compiled from presets into parameter curves; Bezier control-point times are restricted to their segment, and the curve parameter is evaluated advancing linearly with time (matching Cubism's `AreBeziersRestricted`).
- `restPose` gives the parameter values used when baking a base mesh for formats that need a canvas-space base mesh (for example, the mouth held open so texture coordinates cover the whole image).
- `PuppetIr` is lossless both ways: `toPuppet(toIr(model))` matches the original model field by field. A field added on either side requires updating the converters in the same change.

## Export targets

`spine`, `dragonbones` and `gltf` are experimental targets: they bake parameter by parameter and add the results, so combined poses differ visibly from the editor. They are hidden from the **File → Export as** menu and export only from the command line (`psd2live targets` marks them experimental). `unity` uses the same baking but appears under **File → Export as**: once the export folder is copied whole into a Unity project's `Assets`, the bundled installer script moves the importer to `Assets/PSD2Live/Editor` and deletes itself, so a second character can be copied whole too. The descriptions of experimental targets below record their current state.

| `cmo3` | Structured rig | Cubism Editor project; with motion clips, also a `.can3` of the same name (Cubism Animator project); parameter repeat is written as `isRepeat` (a Cubism 5.3 target; an earlier one strips it and lists it in the loss report) | Generator intent is not kept; blink and lip-sync effect curves in motion clips are not written (see [Cubism Animator](#cubism-animator)) |
| `dragonbones` | Structured rig | `_ske.json`, a `_tex_<i>.json` and texture per page | The same parameter-animation and clip baking as Spine; keys are rounded to frames; opacity is stored as whole percentages; the runtime addresses each animation's deform data with 16-bit offsets, so when that overflows, keys are reduced with a larger tolerance and reported (whole-body clips of skeleton models have larger errors); masks, screen color and physics are not written |
| `vtube-studio` | Structured rig | All `moc3` files + `.vtube.json` | Same as `moc3`; face tracking maps the standard parameters (head, body, eyes, gaze, brows, mouth, breath), one hotkey per motion clip and one `ToggleExpression` hotkey per expression; other settings take VTube Studio's defaults. | `web` | Structured rig | `index.html`, `p2l.js`, `p2l_runtime.wasm`, `.p2lrt` | Draws every color and alpha blend mode by the runtime header's compositing rules (modes that read the backdrop copy the pixels beneath the mesh and composite in a shader) and isolated groups (child meshes are drawn into a layer first, then composited with the group's opacity, multiply/screen color, mask and blend mode); masks (including group masks) are approximated with the stencil buffer, texel opacity ≥ 0.5 counting as covered; when a layer framebuffer cannot be created, isolated groups draw as pass-through; must be served over http |

| `sprite-sheet` | Raster | Grid sprite sheet PNG + TexturePacker (hash) JSON | Same as above |
| `gif` | Raster | Animated GIF | 256 colors (255 from a median cut over the whole motion's own pixels, shared by every frame), 1-bit transparency |
| `mp4` | Raster | H.264 video (ffmpeg) | No transparency; composited onto the background color (white by default) |
| `webm` | Raster | VP9 video with transparency (ffmpeg) | Transparency is stored in a VP9 side channel and needs libvpx to decode |
| `mov` | Raster | ProRes 4444 with transparency (ffmpeg) | — |
| `apng` | Raster | Animated PNG (ffmpeg) | — |
| `webp` | Raster | Animated WebP (ffmpeg) | Lossy compression |

Raster targets and `psd-pose` render through the host-supplied `FrameRenderer`. The editor's implementation (`IrFrameRenderer`) gets geometry from the engine's CPU evaluator, uses `IrColors` to resolve multiply/screen colors from channels and blend shapes along with parts' draw order and group compositing values, and draws pixel by pixel with `:format-compile`'s `SoftwareRasterizer` (MIT): a premultiplied float buffer, bilinear sampling, masks by texture alpha (including inverted), and color blending and alpha compositing by the compositing rules of `p2l_runtime.h` (the same as the editor): Cubism's additive/multiply ignore the alpha mode and keep the destination alpha, normal with over is premultiplied source-over, and every other combination takes the W3C blend function, weights the overlap by the alpha mode and uses its Porter-Duff coefficients (over, atop, out, conjoint/disjoint over). Draw order follows the render tree: each group is sorted by draw order, and a group takes part in sorting by its part's draw order at that pose; an isolated part's group is drawn into a cleared layer first, then takes the group's multiply/screen color, scales alpha by opacity and mask coverage, and composites with the group's blend mode. Pendulum physics advances between frames.

## Expressions, pose and events

Expressions, the pose and motion events are project data that, like motion clips, leave the rig unchanged. They are defined in `core/ModelSidecars.kt` and edited through the `expression_*`, `pose_*` and `motion_set_event` document operations (see the [MCP authoring reference](../agent/MCP_AUTHORING.md)). `RigIrCompiler` compiles them into the IR (`advanced.expressions`, `advanced.pose`, `Clip.events`), dropping parameters and parts the model no longer has, and every target writes them from there:

- **Expressions**: while `RigEditOverlay.expressions` is null a generated rig has the standard expressions (`ModelExpressions.standard`: Smile, Sad, Angry, Surprised, named in the interface language, each keeping only the standard face parameters the model has, and one with none of them left out), and an imported CMO3 model has none. The first edit takes the list of that moment into the document, after which only the document's list exports; an expression with no entries still exports, as the neutral expression a host resets to. `moc3` writes one `<base>.<id>.exp3.json` per expression (`Type`, `FadeInTime`, `FadeOutTime`, `Parameters` with `Id` / `Value` / `Blend`) and lists them, in order, under model3 `FileReferences.Expressions` (`Name` is the expression's name, `File` its file); `p2lrt` writes an `EXPR` chunk. Expression IDs are 1–64 file-name-safe characters, and names are unique in the project.
- **Pose**: `moc3` writes `<base>.pose3.json` (`Type`, `FadeInTime`, and per part of each of `Groups` its `Id` and `Link`) and references it from model3 `FileReferences.Pose`, keeping only parts the model has and writing nothing without a group; `p2lrt` writes a `POSE` chunk (groups of at least two parts).
- **Events**: clip events go into motion3 `UserData` (in time order, with `Meta.UserDataCount` / `TotalUserDataSize`), into the scene's user data frames in `.can3`, and into the clip extension record of `p2lrt`. A clip with events and no curve is left out like any empty clip.
- **When parameters and parts change**: deleting a parameter deletes its expression entries, and narrowing its range holds Overwrite values inside it. `ModelSidecars.withIdRenamed` is the general way to update motion curves, expression entries and pose parts when a parameter or part ID changes; ID conversion should call it (not wired up yet). References left dangling otherwise (deleting a swing, a simulation or a layer, regenerating) stay in the project: an edit checks only the entries and parts it writes (an expression or pose group keeps only its own dangling references), `missing` in `expression_get` / `expression_list` and `missing_parts` in `pose_get` list them, and export skips them.
- **Written IDs**: the exp3, pose3 and motion3 of `moc3` name objects by the IDs the moc was written with (`Moc3Sidecars.withWrittenIds`, as cdi3 does): an ID shortened to fit takes its shortened form, and parts not written (left out by `hidden_parts` / `guide_parts`) leave the pose, with the groups they empty, and their opacity curves leave the motions, with the curve, segment and point counts; when every ID is written as it is, these files are not parsed.
- **Preview**: the editor's preview bundle carries no pose3 (the Cubism SDK hides every part of a group but the first as it loads one); only written files do.
- **Export changes (after 3.6.0)**: a generated rig now also writes the standard expressions' exp3 files, model3 `Expressions` and the VTube Studio toggle hotkeys in `moc3` / `vtube-studio`; an imported CMO3 with unedited expressions no longer carries the standard expressions in `p2lrt`; replacing a generated rig with a CMO3 import takes the standard expressions of that moment into the document.
- **Read-back**: the bundle check in `PSD2LivePipeline` parses every exp3, pose3 and motion3 model3 references. Mesh-only export writes no expressions or pose; `cmo3` / `can3` do not store expressions or the pose and report them as `structure` / `dropped`.

## Cubism Animator

The `cmo3` target writes `<base>.cmo3` and also writes the IR's motion clips as `<base>.can3` (`Can3`, `:targets:cubism`); the legacy **Export Live2D model…** writes it too when CMO3 is ticked. With motion3/motion export off, or a mesh-only model, there are no clips and no can3 is written.

- **Container**: the same CAFF as cmo3, holding only one obfuscated, compressed `main.xml`.
- **Model link**: a can3 holds no model. Its single resource refers to `<base>.cmo3` in the same folder by file name; parameters are linked by ID (`live2dParam_<Id>`), and part opacity tracks carry that part's GUID from the cmo3 of the same export. cmo3 GUIDs differ on every export, so a can3 pairs only with the cmo3 exported with it.
- **Scenes**: one scene per clip, named `<base>.<file>`, matching the motion3 file names of a moc3 export. Scenes follow Animator's fixed track structure: a root group track and a model track, the model track carrying five effects: visual, parameter, part opacity, lip sync and blink. Each clip's duration, frame rate, looping, fades and user data (events) go into the scene and the model track.
- **Curves**: parameter curves go into the parameter effect (display name from the parameter name, range from the parameter range widened to cover every key), part opacity curves into the part effect, and overall opacity replaces the visual effect's opacity; a curve's own fades go into the track options. Keys are rounded to the nearest frame, Bezier control points keep their original times (fractional frames) as handles at both ends, and stepped and inverse-stepped segments keep their type.
- **Losses**: blink and lip-sync effect curves have no matching track in Animator; they are not written, together with curves that point to parameters or parts missing from the model, and are recorded as `timeline` / `dropped`.

## Spine

Spine has bones but no parameters. The exported skeleton space has its origin at the midpoint of the canvas bottom edge, y up, and:

- **Bones**: each rotation deformer becomes a bone whose parent is the nearest rotation deformer above it (the root bone if none), mirroring the deformer tree. The exporter computes the bones' setup pose and key values as world frames by the editor's rotation rules (see "Evaluation rules" in [Runtime](RUNTIME.md): the angle is the keyform angle plus the base angle; under a rotation parent the origin goes through the parent transform and angle and scale compose, with an extra half turn when the parent flips vertically or has negative scale; the deformer's own flip acts only on child coordinates; under a warp parent the frame stays rigid and turns with the grid direction), then converts them to values local to the parent bone. These frames are all rotation plus uniform scale with flips, and their products stay in the same class, so only rotation and scaleX/scaleY (flips as negative scale) are used, without shear. Each bone also carries a fixed turn so that it points at the center of the meshes it holds, with its length set to the meshes' farthest extent along that direction. A rotation whose scale tends to zero at any sampled pose does not become a bone; its children are baked onto the bone above and reported.
- **Meshes**: each visible mesh is an unweighted mesh attachment whose slot hangs on its nearest rotation bone, with vertices as coordinates in that bone's space; what the bone does not express (warps, mesh keyforms, blend shapes, Glue) is written as deform offsets in that bone's space. Meshes with no rotation ancestor hang on the root bone, as before.
- **Parameters**: one animation `param/<parameter ID>` per parameter, 1 second long, with time as the parameter's normalized value (minimum 0, maximum 1), keying at the parameter's sample points the bones' `rotate` (delta from the setup angle), `translate` (delta), `scale` (multiple of the setup scale) and mesh deforms; the runtime opens one track per parameter with additive blending (`MixBlend.add`) and sets the track time from the parameter value. Because bones multiply through the parent chain, several parameters rotating one rotation chain at once compose in series rather than adding their canvas offsets. Keyform opacity is written as slot `rgba`, and per-parameter draw order as `drawOrder`.
- **Cross terms**: at `sample_pairs` two-parameter combined poses, the pose is rebuilt by Spine's additive rules (bone values and deform offsets added track by track, scale as setup scale plus the multiple's difference, bones multiplied level by level) and compared with the evaluator; meshes off by more than 0.5 pixels go into the loss report. Rotations under a warp (for example, the head and upper-arm rotations an auto skeleton hangs under the body warp) are exact at a single parameter's sample points, but combined with a parameter that moves that warp, the pivot does not follow the warp's deformation, which is reported as approximate; joints implemented by warps (forearm, hand, upper-body bend) are still added per parameter in bone space.
- One animation `clip/<name>` per motion clip, sampled at `clip_fps`, then `KeyReduction` removes keyframes that linear interpolation can rebuild: the deform tolerance is `key_tolerance` pixels, the bones' rotation and scale tolerances are converted to the same pixel amount over the canvas diagonal, and translation is kept to a thousandth of a pixel.
- The atlas has one region per page covering the whole page, named after that page's image (`<name>_<i>`, image `<name>_<i>.png`); mesh attachments' `path` points to it, and UVs refer to that page directly. The runtime finds regions through the atlas; Spine Editor does not read the atlas when importing data and looks for images of the same name in the `images` folder (`./`), so meshes show right after import.
- Masks become clipping attachments: a clipping slot is inserted before the masked mesh (`end` points to that mesh), its polygon being the outer outline of a single mask mesh, or the convex hull with a report for several masks or several outlines; the clipping slot hangs on the bone that all mask meshes share, otherwise on the root bone; clipping attachments get deform keys with the mask meshes and move together with the masked mesh when draw order changes. Spine clips by polygon, not by texture alpha; inverted masks cannot be expressed and are dropped and reported.
- **Physics**: for outputs of pendulum groups whose source is an angle, if the output parameter's animation rotates bones, Spine 4.2 physics constraints (`rotate` 1) are set up on those bones; Spine drives the constraint from the bone's own motion and does not read the pendulum's input parameters, and settings are mapped empirically (inertia 1, strength = 100 × acceleration, damping = mobility, mix = output weight / 100, `fps` from the physics group's frame rate, default 60), which only approximates the original response and is reported as approximate; deforms the same output parameter also keys are not simulated, which the report notes. Pendulum groups with no output driving bone rotation (such as the auto-generated hair pendulums, which act on warps) are dropped and reported.
- **Binary**: with `binary=true`, a Spine 4.2 binary `.skel` is written (following the public spine-runtimes 4.2 `SkeletonBinary` layout: big-endian numbers, varint positive integers, a string table, no nonessential data), with the same content as the JSON. Binary meshes do not store a triangle count; the reader derives it as "2 × vertex count − hull − 2", so the hull length is set from the mesh's triangle count; meshes with more triangles than that formula allows (only with repeated triangles) get an unused copy of the first vertex appended.
- Verification (implemented and covered by the tests below; the official Spine runtime is not used, as its license requires holding a Spine license). The Spine 4.3 trial imports the JSON and shows every mesh (the version mismatch and missing nonessential data are only warnings); the 4.2 binary `.skel` cannot be imported because the editor requires a matching version; animations and masks have not been checked in the editor:
  - Unit tests rebuild poses by the Spine 4.2 runtime's rules (additive tracks, linear key interpolation, unweighted deforms as offsets from the setup pose, bones multiplied level by level under normal inheritance, draw order reordered by the offset algorithm): a three-level rotation chain (with mesh keyforms, flips and negative scale) at random poses with single parameters, parameters between keys and all parameters changing at once agrees within 0.002 pixels with a test evaluator implemented independently from the same rotation rules; motion clips agree at sampled frames.
  - A minimal `.skel` reader written in the tests from the public layout reads the binary back; bones, slots, physics constraints, attachments and poses rebuilt from each animation match the JSON, and two exports are byte-identical.

## DragonBones

The same baking as Spine: bones, each visible mesh an unweighted mesh display (origin at the midpoint of the canvas bottom edge, y down); one 1-second animation `param/<parameter ID>` per parameter, with deform (ffd) frames on the parameter keys rounded to frames, so a host can seek by parameter value and layer the animations additively; each clip sampled per frame and reduced. Interpolation between frames is written explicitly as `tweenEasing: 0` (the default is stepped). The DragonBones runtime addresses each animation's deform float data with 16-bit offsets (each frame stores all of the mesh's vertices); beyond roughly 32,000 floats, keyframes are reduced with a tolerance found by doubling and then bisecting, and the loss report gives the tolerance used. Verification: `DragonBonesFidelityTool` (`PSD2LIVE_TOOLS=1`, needs node) plays the export with `tools/dragonbones-check` (the official DragonBones 5.7 runtime core, without rendering): single-parameter poses of a sample without a skeleton agree with the editor within 0.25 pixels at keyframes; with a skeleton, animations affected by the limit above stay within the reported tolerance, and clip errors are in the report.

## glTF

Each visible mesh becomes an unlit (`KHR_materials_unlit`), double-sided, alpha-blended flat mesh at the rest pose, each layer moved 0.5 mm toward the viewer in draw order; units are meters (`pixels_per_meter`, default 1000), y up, with the origin at the midpoint of the canvas bottom edge. Each non-default key of each parameter becomes a morph target for the meshes it moves (`extras.targetNames` is `parameter=key`); parameter values map to weights by linear hat functions between keys, and the parameters and their keys are listed in `extras.psd2live.parameters`. Motion clips are sampled at `clip_fps` into weight animation and reduced with `KeyReduction`. Verification: unit tests rebuild sampled poses from the weights; the tml export passes the Khronos glTF Validator with zero errors and zero warnings, and renders correctly in Godot 4.4 at the rest pose and with a head-shake motion.

## Unity

Requires Unity 6.0 (6000.0) or later. The export folder can go whole into a Unity project's `Assets`. The bundled installer script installs `Psd2LiveUnityImporter.cs` to `Assets/PSD2Live/Editor` (not overwriting an existing copy that is not older) and then deletes itself, so a second character is also copied whole. The importer merges meshes that are adjacent in draw order and on the same texture into one skinned mesh on a shared root bone; a part from another texture in between breaks the run, and each run uses its own `sortingOrder`, so front hair is not drawn in front of the face just because it shares a page with back hair. Each non-default key of a parameter becomes a Blend Shape (a hat function over weights 0–100, as in glTF); several parameters changing at once are an additive approximation. Motion clips are sampled at `clip_fps` into Animator clips; a clip named Idle is the default state when present, otherwise the first clip plays; the other clips are written into the `.controller` of the same name and, with no transitions, do not play on their own. Once that file is generated, the prefab's Animator points to it, and instances in scenes still pointing to the embedded controller are switched over on import or when the hierarchy changes. Each parameter also gets a `param_<id>` clip outside the default state machine that the project can play on its own. The unit is one `pixels_per_unit`-th (default 100), y up, origin at the canvas center; texture V is flipped from PSD2Live's top-left origin to Unity's bottom-left origin. The character does not animate while off screen. Verification: the target module's unit tests check a sliding square's vertices, Blend Shape and weight at 0.5 seconds; the full tml character imports at the rest pose into a built-in render pipeline project in Unity 6000.4.7f1 and plays Idle in Play mode.

## Hit areas

The document's hit areas (`rigEdits.hitAreas`, edited in the inspector, the hierarchy's context menu and the MCP `hit_area_*` operations) compile, in test order, to `RigIR.hitAreas`: each area has its own ID (such as `HitAreaHead`), the name a host asks for (such as `Head`) and the meshes it covers. When a mesh is split (islands, polygon, depth slices) its pieces take its place in its areas, and a deleted layer's meshes leave them (an area left without meshes goes too). The IR keeps every mesh an area names; a target leaves out the meshes the rig no longer has, each a `structure` / `dropped` loss, and an area left with none is still the document's own, not replaced by the runtime's automatic ones. Targets that carry no hit areas (`cmo3`, `spine`, `dragonbones`, `gltf`, `unity`, `psd-pose` and the raster ones) report each area as a `structure` / `dropped` loss.

- **`moc3` / `vtube-studio`**: written to model3.json's `HitAreas`, each entry's `Name` the area's name and `Id` the ArtMesh ID as the moc wrote it (shortened where the moc shortened it; a mesh the moc does not contain, such as a hidden mesh the options omit, is not listed and is a `structure` / `dropped` loss, and with none left there are no `HitAreas`). A model3 entry names one ArtMesh, so an area of several meshes becomes several entries of the same name, with a `structure` / `approximated` loss (a host that only tests the first entry of a name tests only the first mesh); the area's own ID has no place in model3. A document without hit areas writes no `HitAreas`, and its export is byte for byte unchanged.
- **`p2lrt`**: version 2 writes the optional `HITA` chunk (area ID, name, mesh indices); a document without hit areas keeps the automatic `HitAreaHead` (the face) and `HitAreaBody` (the top, else the neck or the bottom). Version 1 has no hit areas: each of the document's areas is a `structure` / `dropped` loss.
- **Hit rule**: the first area in list order with a mesh that is visible, has an opacity above 0 and whose triangles (edges included) contain the point. A click on the editor's preview, MCP `hit_area_test` and the runtime's `p2l_hit_test` share this rule. The Cubism SDK samples test a mesh's bounding rectangle, which can differ.
- The binary IR (`RigIrBinary`) carries the field from encoding version 6; earlier versions read it as empty.

## Loss report

Every export writes `<name>.<target>.report.json` next to the files:

```json
{"target":"gif","compiler":"2.0.4","files":["model.gif"],
 "losses":[{"object":"*","feature":"structure","handling":"baked","note":"..."}]}
```

`handling` is `baked` (visuals kept, size grows), `approximated` (acceptable error) or `dropped`; `object` is a stable ID, with `*` meaning the whole rig; `error` is attached when an error is measured. The report records the compiler version, for tracing differences between two exports.

## Determinism

The same IR and the same compiler version produce byte-identical output; exports introduce no timestamps or random numbers. The exception is `cmo3`: Cubism Editor requires a unique GUID for every object, so the file bytes differ each time while the content is the same. Export-path refactors compare the file digests of the commits before and after with `ExportGoldenTool` (`PSD2LIVE_TOOLS=1`); cmo3 is compared by the digest of reading it back and lowering it again to moc3.

## Usage

- UI: **File → Export Live2D model…** exports moc3 / cmo3; **File → Export as** lists the other non-experimental targets grouped as **Runtimes and players**, **Images and video** and **Layered PSD**. Each target opens its own dialog, which exports the current committed state and lists the losses. Each target declares in `ExportTarget.settings` the setting keys it reads (motion choice, toggles, ranged numbers, text); the dialog builds matching rows from the declaration and sends only the values the user changed, the rest taking the target's defaults or the project's export settings; changes are kept per target for the current run. New targets must be registered in a menu group (`exportMenuGroups`, checked by `ExportTargetSettingsTest`).
- Command line: see the `export` command in [Development and CLI](../guide/DEVELOPMENT.md); `psd2live targets` lists each target with its setting keys, value ranges and defaults.
- The editor's own Cubism preview package and the `moc3` export are one compilation: **Export Live2D model…** (MCP `project_export_model`) and **Export as** both write the committed model itself (`PSD2LivePipeline.export`), without rebuilding from the source image or generating a base rig; they differ only in the report (the former reads back and validates and writes `.psd2live.json`, the latter writes a loss report). The command line first gets the model through the same build path (`buildPreview`), then writes it.
