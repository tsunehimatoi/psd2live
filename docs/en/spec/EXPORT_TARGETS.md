# Neutral rig IR and export targets

Every export starts from the same neutral rig IR. The editor compiles the currently committed rig into IR. Each export target then downgrades the IR into its own format and writes a loss report that lists what that format cannot keep.

## IR conventions

- A mesh's rest position and each deformer's keyforms are in the parent deformer's space: the root is canvas pixels (y downward), a Warp child is its 0–1 cell space, and a rotation child is its local pixel coordinates.
- Every ID is stable. It does not change after regeneration.
- Motion clips have already been compiled from presets into parameter curves. The control-point times of a Bezier segment are limited to the segment. The curve parameter is evaluated by advancing linearly in time (the same as Cubism's `AreBeziersRestricted`).
- Expressions, poses, and motion events come from the project (`RigEditOverlay.expressions` / `pose`, `MotionClip.events`; see [Expressions, poses, and events](#expressions-poses-and-events)). Parameters and parts that no longer exist in the model are removed at compile time. Expressions and poses are in `advanced`. Clip events are in `Clip.events`.
- `restPose` gives the parameter values used when a format that needs a canvas-space base mesh bakes that base mesh (for example the mouth stays open so the texture coordinates cover the whole image).
- `PuppetIr` maps `PuppetModel` fields in both directions. The round trip of `toPuppet(toIr(model))` is limited to those mapped fields. Packed images, texture-page bindings, physics, motion clips, and parameter roles are not stored in `PuppetModel` and must be passed to `toIr` explicitly. Rest pose, tile artwork, hit areas, and advanced runtime data that exist only in the IR are kept by the caller. The whole IR cannot be assumed to round-trip without loss automatically. When a field is added on either side of the mapping, the converter must be updated in the same change.

## Export targets

`spine`, `dragonbones`, and `gltf` are experimental targets: they bake parameter by parameter and then add the results, and a combined pose differs visibly from the editor. They are hidden from the File → Export as menu and can be exported only from the command line (`psd2live targets` marks them experimental). `unity` uses the same bake, but it does appear under File → Export as: after the whole export directory is copied into a Unity project's `Assets`, the bundled install script places the importer at `Assets/PSD2Live/Editor` and deletes itself, so a second character can also be copied in whole. The description of experimental targets below keeps the current state.

| `sprite-sheet` | Raster | A sprite-sheet PNG in a grid, plus TexturePacker (hash) JSON | The same |

| `mp4` | Raster | H.264 video (ffmpeg) | No transparency. Composited onto a background color (white by default) |
| `webm` | Raster | VP9 video, with transparency (ffmpeg) | Transparency is stored in the VP9 alpha side channel. Decoding needs libvpx |
| `mov` | Raster | ProRes 4444, with transparency (ffmpeg) | — |
| `apng` | Raster | An animated PNG (ffmpeg) | — |
| `webp` | Raster | An animated WebP (ffmpeg) | Lossy compression |

Raster targets and `psd-pose` render through the `FrameRenderer` the host provides. The editor's implementation (`IrFrameRenderer`) gets geometry from the engine's CPU evaluator, uses `IrColors` to compute multiply/screen color from channels and blend shapes and the parts' draw order and group composite values, then draws pixel by pixel with `:format-compile`'s `SoftwareRasterizer` (MIT): a premultiplied float buffer, bilinear sampling, masks by texture alpha (including inverted). Color blend and alpha composite follow the composite rules in `p2l_runtime.h` (the same as the editor): Cubism's add/multiply ignore the alpha mode and keep the destination alpha, normal with over is premultiplied source-over, and the other combinations take the W3C blend function, overlap weighting by the alpha mode, and its Porter-Duff coefficients (over, atop, out, conjoint/disjoint over). Draw order follows the render tree: each group is sorted by draw order inside the group, and a group takes part in the sort by its part's draw order at that pose. An isolated part's group is drawn into a cleared layer first, then takes the group's multiply/screen color, scales alpha by opacity and mask coverage, and composites by the group's blend mode. Pendulum physics advances between frames.

### VTube Studio model package

Put the whole export directory into VTube Studio's `Live2DModels`, then open or restart VTube Studio. `<名称>.vtube.json` stores the face-capture mapping and the hotkeys. `FileReferences.Model` points at `<名称>.model3.json` in the same directory. That file references the `.moc3`, the textures, and the exported physics, motions, expressions, and other resources. VTube Studio recommends a 512 × 512 PNG or JPG as the model-picker icon. [Official import guide](https://github.com/DenchiSoft/VTubeStudio/wiki/Loading-your-own-Models)

The exporter generates `<名称>.icon.png` with a transparent background from the model's default pose, scales the visible content uniformly, and centers it. It writes the relative file name in `FileReferences.Icon`. When the picture is fully transparent, the icon is skipped.

Motion and expression hotkeys refer to the files that were actually written, and they use the names from the project. A generated hotkey waits for the user to assign a trigger. The three keyboard fields are left empty, and `Triggers.ScreenButton` is written as `-1`. That value matches the unassigned value of the models shipped with VTube Studio, and it fixes the problem where an old export that wrote `0` could fail to open the expression editor. VTube Studio's official notes record what the configuration file is for. Field values follow a configuration that was actually saved. [Official configuration guide](https://github.com/DenchiSoft/VTubeStudio/wiki/VTube-Studio-Model-File) · [Issue #90](https://github.com/tsunehimatoi/psd2live/issues/90)

## Expressions, poses, and events

Expressions, poses, and motion events are project data. Like motion clips, they do not change the rig. They are defined by `core/ModelSidecars.kt`. Editing goes through document operations such as `expression_*` / `pose_*` / `motion_set_event` (see the [MCP editing reference](../agent/MCP_AUTHORING.md)). `RigIrCompiler` compiles them into the IR, and each target writes them from the IR:

- **Expressions**: When `RigEditOverlay.expressions` is null, a generated rig uses the standard expressions (`ModelExpressions.standard`: smile, sad, angry, surprised; the names follow the interface language; each keeps only the parameters the model already has, and one with no parameters at all is omitted. When the model has rig-module parameters — eye shape, brow angle, smiling eyes, squint, blush, and so on — each expression is pushed further. Shy, sleepy, and gloomy are generated only when the model has a blush parameter, a squint parameter of the fitted eyes, and a gloomy parameter). An imported CMO3 model has no expressions. The first edit takes the list of that moment into the project. After that, only the list in the project is exported (an expression with no entries is still exported, as an empty expression the host can use to reset). `moc3` writes one `<base>.<id>.exp3.json` per expression (`Type`, `FadeInTime`, `FadeOutTime`, and `Parameters`' `Id` / `Value` / `Blend`), and writes them in list order into model3's `FileReferences.Expressions` (`Name` is the expression name, `File` is the file name). `p2lrt` writes an `EXPR` block. An expression ID is limited to 1–64 characters that are safe in a file name. The name is unique in the project.
- **Poses**: `moc3` writes `<base>.pose3.json` (`Type`, `FadeInTime`, and each part's `Id` and `Link` inside `Groups`) and writes it into model3's `FileReferences.Pose`. Only parts that exist in the model are kept. When there is no group, it is not written. `p2lrt` writes a `POSE` block (only groups with at least two parts are kept).
- **Events**: Clip events are written into motion3's `UserData` (sorted by time, with `Meta.UserDataCount` / `TotalUserDataSize` kept in sync). `.can3` writes them into the scene's user-data frames. `p2lrt` writes them into the clip extension record. A clip that has only events and no curves is not exported, the same as any other empty clip.
- **Changes to parameters and parts**: Deleting a parameter deletes its expression entries with it. Shrinking a parameter's range pulls an overwrite-blend value into the new range (`WorkspaceDocumentEdits.parameter`). `ModelSidecars.withIdRenamed` is the general interface that, when a parameter or part ID is rewritten, updates motion curves, expression entries, and pose parts in sync. An ID change should call it (it is not wired yet). In other cases (deleting a swing, a simulation, or a layer, or regenerating), dangling references that remain are kept in the project: an edit validates only the entries and parts written this time (one expression or pose group keeps only the dangling references it already had). `missing` of `expression_get` / `expression_list` and `missing_parts` of `pose_get` list them. Export skips them.
- **IDs that are written**: exp3, pose3, and motion3 of `moc3` name objects by the IDs the moc actually wrote (`Moc3Sidecars.withWrittenIds`, the same as cdi3): an ID that was shortened because it was too long is replaced by the shortened form. A part that was not written (omitted by `hidden_parts` / `guide_parts`) is removed from the pose. A group that becomes empty is removed with it. Their opacity curves in motions are removed too (the counts of curves, segments, and points stay in sync). When every ID is written unchanged, those files are not parsed.
- **Preview**: The editor's preview bundle does not carry pose3 (when the Cubism SDK loads pose3 it hides every part in a group except the first). Only the written files carry it.
- **Export changes (after 3.6.0)**: A generated rig writes, in `moc3` / `vtube-studio`, the exp3 files of the standard expressions, model3's `Expressions`, and VTube Studio's toggle hotkeys. An imported CMO3 whose expressions were not edited no longer carries the standard expressions in `p2lrt`. When a generated rig is replaced by a CMO3 import, the standard expressions of that moment are taken into the project.
- **Read-back**: The bundle check of `PSD2LivePipeline` parses every exp3, pose3, and motion3 that model3 references. A mesh-only export does not write expressions or poses.

## CMO3 references and author data

Before writing CMO3, a mesh's texture-source reference is materialized as the texture page and tile of the corresponding source, keeping the consuming mesh's own UVs and keyforms. Both the `canvas` and `native` layer-write modes use this binding. An existing Glue ID is written with the file and restored on import. A Glue with no ID uses a deterministic fallback name. A runtime vertex-weight group cannot be stored in CMO3. Each group is reported as `structure` / `dropped` by mesh ID. It is not treated as lossless in silence.

## Cubism Animator

The `cmo3` target writes the IR's motion clips as `<base>.can3` (`Can3`, `:targets:cubism`) at the same time as `<base>.cmo3`. The old “Export Live2D model”, when CMO3 is checked, writes it the same way. When “export motion3/motions” is off, or the model has only meshes, there are no clips, and can3 is not written.

- **Container**: The same CAFF as cmo3, with a single obfuscated, compressed `main.xml`.
- **Linked model**: can3 does not contain the model. Its only resource refers, by file name, to `<base>.cmo3` in the same directory. Parameters are linked by ID (`live2dParam_<Id>`). A part-opacity track carries that part's GUID from the cmo3 of the same export. A cmo3 GUID is different on every export, so a can3 matches only the cmo3 of the same export.
- **Scenes**: One scene per clip, named `<base>.<file>`, the same as the motion3 file name of a moc3 export. A scene uses Animator's fixed track structure: a root group track and a model track. The model track has five effects: visual, parameters, part opacity, lip sync, and blink. The clip's duration, frame rate, loop, fades, and user data (events) are written to the scene and the model track.
- **Curves**: Parameter curves go into the parameter effect (the display name is the parameter name; the range is the parameter range, expanded to cover every key point). Part-opacity curves go into the part effect. Overall opacity replaces the opacity of the visual effect. A curve's own fade-in and fade-out are written to the track options. Key points are rounded to the nearest frame. Bezier control points keep their original time (a fractional frame) as the handles at the two ends. Step and inverse-step segments keep their type.
- **Losses**: Blink and lip-sync effect curves have no matching track in Animator. They are not written, together with curves that point at a parameter or part that does not exist in the model, and they are recorded as `timeline` / `dropped`.

## Spine

Spine has bones and no parameters. The exported bone-space origin is the midpoint of the canvas's bottom edge, y upward, and:

- **Bones**: Each rotation deformer becomes one bone. Its parent bone is the nearest rotation deformer above it (the root bone when there is none), mirroring the deformer tree. The bone's setup pose and key values are computed by the export side from the editor's rotation rules (see [Runtime](RUNTIME.md) “Evaluation rules”: the angle is the keyform angle plus the base angle; when the parent is a rotation, the origin is transformed by the parent and the angle and scale are composed; a vertical parent flip or a negative parent scale adds a half turn; the object's own flip affects only child coordinates; when the parent is a Warp, the frame stays rigid and rotates with the cell's direction) as a world frame, then converted to a local value relative to the parent bone. These frames are all a rotation plus a uniform scale that may be flipped. Their product is still of the same kind, so only rotation and scaleX/scaleY are used (a flip is a negative scale). Shear is not needed. Each bone also carries a fixed turn so the bone direction points at the center of the mesh it carries, with a length of the mesh's farthest distance along that direction. A rotation whose scale tends to zero under any sampled pose does not become a bone. Its children are baked onto the bone above and reported.
- **Meshes**: Each visible mesh is a mesh attachment with no weights. The slot hangs on its nearest rotation bone, and the vertices are coordinates in that bone's space. The part the bones do not express (Warp, mesh keyforms, blend shapes, Glue) is written as a deform offset in that bone's space. A mesh with no rotation ancestor hangs on the root bone, the same as before.
- **Parameters**: Each parameter is one animation `param/<参数 ID>`, 1 second long. Time is the parameter's normalized value (minimum 0, maximum 1). At the parameter's sample points it keys the bone's `rotate` (the increment relative to the setup angle), `translate` (the increment), `scale` (the multiple relative to the setup scale), and the mesh deform. At runtime each parameter gets one track, with additive blend (`MixBlend.add`), and the track time is set from the parameter value. Because bones multiply along the parent chain, several parameters rotating one rotation chain at the same time combine in series, rather than adding their canvas offsets. Keyform opacity is written as the slot `rgba`. Draw order that changes with a parameter is written as `drawOrder`.
- **Cross terms**: On `sample_pairs` two-parameter combined poses, the pose is rebuilt by Spine's additive rules (bone values and deform offsets add per track, scale adds the multiple difference onto the setup scale, and bones multiply level by level) and compared with the evaluator. A mesh beyond 0.5 pixels is written to the loss report. A rotation under a Warp (for example the head and upper-arm rotations of an automatic skeleton hanging under the body Warp) is exact at a single parameter's sample points, but when it is combined with a parameter that moves that Warp, the pivot does not follow the Warp's deformation, and it is reported as an approximation. A joint implemented by a Warp (forearm, hand, upper-body bend) is still added per parameter in bone space.
- Each motion clip is one animation `clip/<名称>`, sampled at `clip_fps`, then `KeyReduction` removes keyframes that linear interpolation can rebuild: the deform tolerance is `key_tolerance` pixels, the bone's rotation and scale tolerances are converted to the same pixel amount by the canvas diagonal, and offsets are kept to one thousandth of a pixel.
- The atlas is one region per page covering the whole page. The region name matches that page's image (`<名称>_<i>`, image `<名称>_<i>.png`). A mesh attachment's `path` points at it, and UVs refer to that page directly. The runtime finds the region through the atlas. When Spine Editor imports the data it does not read the atlas. It looks for the image of the same name in the `images` directory (`./`), so the meshes display directly after import.
- A mask becomes a clipping attachment: a clipping slot is inserted before the masked mesh (`end` points at that mesh). The polygon is the outer contour of a single mask mesh. Several masks or several contours take the convex hull and are reported. The clipping slot hangs on that bone when every mask mesh shares one bone, and otherwise hangs on the root bone. The clipping attachment writes deform keys with the mask mesh, and moves together with the masked mesh when the draw order changes. Spine clips by the polygon, not by texture alpha. An inverted mask cannot be expressed. It is dropped and reported.
- **Physics**: An output in a pendulum group whose source is an angle, if that parameter's animation rotates bones, builds a Spine 4.2 physics constraint (`rotate` 1) on those bones. Spine drives the constraint from the bone's own motion. It does not read the pendulum's input parameter. The settings are mapped empirically (inertia 1, strength = 100 × acceleration, damping = mobility, mix = output weight / 100, `fps` is the physics group's frame rate, default 60). It can only approximate the original response, and it is reported as an approximation. Deformation keyed on that output parameter at the same time is not simulated, and the report says so. A pendulum group whose output does not drive a bone rotation (for example an automatically generated hair pendulum, which acts on a Warp) is dropped and reported.
- **Binary**: When `binary=true`, a Spine 4.2 binary `.skel` is written (by the public spine-runtimes 4.2 `SkeletonBinary` layout: big-endian numbers, variable-length positive integers, a string table, no nonessential data). The contents match the JSON. A binary mesh does not store the triangle count. The reader derives it as “2 × vertex count − hull − 2”, so the hull length is set from the mesh's triangle count. A mesh with more triangles than that formula allows (this happens only when triangles repeat) appends an unused copy of the first vertex at the end.
- Verification (implemented and covered by the tests below; the official Spine runtime is not used, and its license requires a Spine license). The Spine 4.3 trial can import the JSON and display every mesh (a version mismatch and missing nonessential data are only warnings). A 4.2 binary `.skel` cannot be imported because the editor requires the versions to match. Animation and masks have not been checked in the editor:
  - Unit tests rebuild poses by the Spine 4.2 runtime's rules (additive tracks, linear keyframe interpolation, an unweighted deform is an offset from the setup pose, bones multiply level by level with normal inheritance, and draw order is rearranged by the offset algorithm): a three-level rotation chain (including mesh keyforms, flips, and negative scale), on random poses of a single parameter, between parameters, and with every parameter changing at once, differs by less than 0.002 pixels from a test evaluator implemented independently by the same rotation rules. Motion clips match on the sampled frames.
  - A minimal `.skel` reader written inside the test by the public layout reads the binary back. Bones, slots, physics constraints, attachments, and the poses rebuilt from each animation match the JSON, and two exports are identical byte for byte.

## DragonBones

The same bake as Spine: bone by bone, each visible mesh as a mesh display with no weights (the origin is the midpoint of the canvas's bottom edge, y downward). Each parameter is a 1-second animation `param/<参数 ID>`. Deformation (ffd) frames sit on the frame the parameter key point rounds to. The host can locate by the parameter value and layer them. Each clip is sampled by frame and then reduced. Interpolation between frames writes `tweenEasing: 0` explicitly (the default is step). The DragonBones runtime addresses each animation's deformation float data with a 16-bit offset (each frame stores every vertex of that mesh). Beyond about 32,000 floats, keyframes are reduced by a tolerance that doubles and then bisects, and the tolerance used is written in the loss report. Verification: `DragonBonesFidelityTool` (`PSD2LIVE_TOOLS=1`, requires node) plays the export with `tools/dragonbones-check` (the official DragonBones 5.7 runtime core, no rendering). A single-parameter pose of a sample with no skeleton differs from the editor by less than 0.25 pixels on keyframes. With a skeleton, an animation affected by the limit above stays within the reported tolerance. Clip error is in the report.

## glTF

Each visible mesh becomes a flat mesh that is unlit (`KHR_materials_unlit`), double-sided, and blended as translucent, in the rest pose, stepped 0.5 millimeters toward the viewer per draw-order layer. The unit is meters (`pixels_per_meter`, default 1000), y upward, and the origin is the midpoint of the canvas's bottom edge. Each non-default key point of each parameter becomes a morph target on the meshes it moves (`extras.targetNames` is `参数=关键点`). The mapping from parameter value to weight is a linear hat function between key points. The parameters and their key points are listed in `extras.psd2live.parameters`. Motion clips are sampled at `clip_fps` into a weight animation and reduced with `KeyReduction`. Verification: unit tests rebuild sampled poses from the weights. The tml export passes the Khronos glTF Validator with zero errors and zero warnings, and renders correctly in Godot 4.4 at the rest pose and for a head-shake motion.

## Unity

Requires Unity 6.0 (6000.0) or newer. The export directory can be placed whole into a Unity project's `Assets`. The bundled install script installs `Psd2LiveUnityImporter.cs` at `Assets/PSD2Live/Editor` (it does not overwrite one that is already there and is not older) and then deletes itself, so a second character is also copied in whole. The importer merges meshes that are adjacent in draw order and land on the same texture into one skinned mesh, attached to a shared root bone. When a part on another texture is inserted in between, that run breaks, and each run uses its own `sortingOrder`, so front hair is not drawn in front of the face for the whole page just because it shares a page with the back hair. Each non-default key point of each parameter becomes a Blend Shape (a hat function of weight 0–100, the same as glTF). When several parameters change at once, the result is an additive approximation. Motion clips are sampled at `clip_fps` into Animator clips. When there is a clip named Idle, it is the default state; otherwise the first clip plays. The other clips are written in a `.controller` of the same name. Without a transition they do not play automatically. The prefab's Animator points at that file after it is generated. An instance in the scene that still points at the embedded controller is retargeted on import or when the hierarchy changes. Each parameter also has a `param_<id>` clip that does not enter the default state machine, and it can be played on its own in the project. The unit is one over `pixels_per_unit` (default 100), y upward, and the origin is the canvas center. Texture V is flipped from PSD2Live's top-left origin to Unity's bottom-left origin. The character does not play while it is outside the picture. Verification: the target module's unit tests check the vertices, Blend Shapes, and 0.5-second weights of a sliding square. The full-character tml imports at the rest pose in a Unity 6000.4.7f1 project on the built-in render pipeline, and Play plays Idle.

## Hit areas

The document's hit areas (`rigEdits.hitAreas`, edited in the editor inspector, the hierarchy context menu, and MCP `hit_area_*`) are compiled into `RigIR.hitAreas` in test order. Each area has its own ID (such as `HitAreaHead`), a name the host queries (such as `Head`), and the meshes it covers. When a mesh is split (connected components, polygon, depth split), the pieces take the original mesh's place in the area. When a layer is deleted, its meshes leave the area (and the area is deleted with them when it therefore has no meshes). The IR keeps every mesh the area refers to. When a target writes, it skips meshes that no longer exist in the rig and records a `structure` / `dropped` loss for each. An area whose meshes are all absent is still the document's own area. It does not fall back to the runtime's automatic areas. A target that does not carry hit areas (`cmo3`, `spine`, `dragonbones`, `gltf`, `unity`, `psd-pose`, and the raster targets) records a `structure` / `dropped` loss for each area.

- **`moc3` / `vtube-studio`**: Written to `HitAreas` in model3.json. Each item's `Name` is the area name, and `Id` is the ArtMesh ID written in the moc (when an ID was shortened, the shortened value is used; a mesh that was not written into the moc, for example a hidden mesh omitted by an export option, is not listed and records a `structure` / `dropped` loss; when none remain, `HitAreas` is not written). Each model3 item refers to only one ArtMesh, so a multi-mesh area is written as several items of the same name, and a `structure` / `approximated` loss is recorded (a host that looks up only the first item by name tests only the first mesh). The area's own ID is not in model3. A document with no hit areas does not write `HitAreas`, and the export is unchanged byte for byte.
- **`p2lrt`**: Version 2 writes the optional block `HITA` (area ID, name, mesh index). When the document has no hit areas, it keeps `HitAreaHead` (the face) and `HitAreaBody` (the top; otherwise the neck or the bottom) obtained from semantics. Version 1 has no hit areas. Each area of the document records a `structure` / `dropped` loss.
- **Hit rule**: The first area that hits, in list order, is taken. A mesh hits when it is visible, its opacity is greater than 0, and one of its triangles (including edges) contains the point. The editor preview click, MCP `hit_area_test`, and the runtime `p2l_hit_test` use the same rule. The Cubism SDK sample judges by the mesh's bounding rectangle, which can differ from this.
- The binary IR (`RigIrBinary`) writes this field from encoding version 6. An earlier version reads it as empty.

## Loss report

Each export writes `<名称>.<目标>.report.json` beside the files:

```json
{"target":"gif","compiler":"2.0.4","files":["model.gif"],
 "losses":[{"object":"*","feature":"structure","handling":"baked","note":"..."}]}
```

`handling` is `baked` (the look is kept, the size grows), `approximated` (an acceptable error), or `dropped` (discarded). `object` is a stable ID. `*` means the whole rig. When an error was measured, `error` is attached. The report records the compiler version, so the difference between two exports can be traced.

## Determinism

The same IR and the same compiler version produce output that is identical byte for byte. Export introduces no timestamp and no random number. The exception is `cmo3`: Cubism Editor requires each object to have a unique GUID, so the file bytes differ every time while the contents stay the same. The export-path refactor compares file digests before and after a commit with `ExportGoldenTool` (`PSD2LIVE_TOOLS=1`). cmo3 is compared by the digest of reading it back and then downgrading it to moc3.

## Usage

- Interface: File → Export Live2D model… exports moc3 / cmo3. File → Export as lists the other non-experimental targets, grouped as runtime and player, image and video, and layered PSD. Each target opens its own dialog, exports the currently committed state, and lists the losses. Each target declares the setting keys it reads in `ExportTarget.settings` (motion choice, switches, numbers with a range, text). The dialog builds the matching rows from that declaration. It sends only the values the user changed. The rest take the target default or the project's export settings. Changes are kept per target for this run. A new target must be registered in a menu group (`exportMenuGroups`, checked by `ExportTargetSettingsTest`).
- Command line: see the `export` command in [Development and the command line](../guide/DEVELOPMENT.md). `psd2live targets` lists each target and its setting keys, value ranges, and defaults.
- The editor's own Cubism preview bundle and the `moc3` export are the same compilation. Export Live2D model (MCP `project_export_model`) and Export as both write the committed model itself (`PSD2LivePipeline.export`). They do not rebuild from the source image, and they do not generate a base rig. They differ only in the report (the former read-back checks and writes `.psd2live.json`; the latter writes the loss report). The command line first obtains the model by the same build path (`buildPreview`) and then writes it.
