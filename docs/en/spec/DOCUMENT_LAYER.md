# Document layer: generators, overrides, and cache

The format design defines a project as "intent + user overrides": a generator saves only parameters, the generated result is computed by a pure function, a user's edits on the generated result are recorded by stable ID, and a three-way merge runs when the generator runs again. The first stage verified the mechanism with the swing generator as the sample. This page records the implementation status of extending it to the other generators, of attaching the generation cache from measurements, and of project format v2.

## Implemented

| Part | Location | Content |
| --- | --- | --- |
| Content hash | `format-compile` `document/ContentHash` | SHA-256 of the canonical text of each part, separated by length. An IR value can be hashed directly |
| Dependency graph | `document/GeneratorGraph` | A generator declares the stable IDs it reads and the stable IDs it owns. Topological sort, cycles forbidden, and an object can have only one owner. Given a change, it gives the downstream generators that need to recompute |
| Generation cache | `document/GenerationCache` | Caches a generated result by the content hash of its input (LRU). On a miss, the computation runs outside the lock, so a slow generator does not block other keys |
| Three-way merge | `document/ThreeWayMerge` | Merge key by key: what the user did not change follows the generator, what the generator did not change keeps the user's value, and when both sides changed and they differ the user's value is kept and a conflict is reported |
| Document generator graph | Root project `core/DocumentGenerators` | Registers the project's generators as nodes of the dependency graph. Replay runs swing and simulation in the graph's order. An override looks up the owner of a keyform from the graph |
| Generated-result overrides | `core/GeneratedOverrides` | A canvas edit on a swing Warp keyform, and on a baked simulation mesh keyform, is recorded as `generated_override`, and is replayed after every generator by a three-way merge per control point or vertex |
| Skeleton and motion cache | `core/SkeletonRig.generate`, `core/MotionPresets.tracks` | The skeleton bake and the generated motions are attached to `GenerationCache` by the content hash of their input |
| Replay checkpoints | `core/legacy/ReplayCheckpoints` | Used only for a journal that has no checkpoint: caches the intermediate model of a replay by the base rig instance and the content of the journal prefix. An append replays only the new entries, and an undo hits an existing checkpoint |
| Generator reuse | `core/DocumentGenerators` (`GeneratorReuse`) | Swing and simulation declare object-level reads. When the reads are unchanged, the previous output is applied as a patch and is not generated again |
| Split materialization | `core/ArtPrimitiveJournal`, `core/RigRegenerationCheckpoint` (`split`), `application/WorkspaceArtPrimitives` | A split is one regeneration: parts replace the original layer and take part in generation, the user's edits on the original layer are carried onto the parts by a three-way merge, and a checkpoint is written after the `art_primitive` record. See [Split materialization](#split-materialization-the-art-primitive-record-art_primitive) |
| Authored rig and checkpoints | `core/RigEditOverlay` (`replayAuthored`/`finish`), `core/RigCheckpoint`, `core/RigRegeneration`, `project/MaterializedRigStore` | Replay is split into an authored stage and a finish stage. The authored rig is saved per revision and used directly for the build. When the generated result changes under the journal, a three-way merge runs and a checkpoint is written. See [Checkpoints](#checkpoints) and the checkpointed rig |
| Project format v2 | `project/ProjectFormatV2` | Each revision is split into content-addressed document nodes that carry a schema version. A v1 file migrates on the next save after it is opened. See [Project format](PROJECT_FORMAT.md) |

The four framework parts in `format-compile` are MIT. They do not depend on any GPL module.

## Preset settings drafts

A preset control only projects a settings patch. It does not commit the currently previewed `RigEditOverlay`, or the mesh baseline, as a settings edit. `WorkspaceSettingsIntent.patchSettings` provides coupling rules that display immediately. `WorkspaceGenerationCommands.prepareSettingsDraft` applies the same intent on the captured committed document, releases the authored pose, rebuilds, and merges the generated result. Preview and commit use the same pure candidate. A checkpoint produced by a preview exists only in the temporary model.

A slider, a numeric input, and the color popup divide operations by edit session. `WorkspaceSettingsDraft` merges consecutive numeric samples into the final patch, and keeps the order of switch toggles that release a pose. After the session completes, one history node is published through `WorkspaceDraftQueue` and the runtime CAS. When nothing changed, nothing is appended. Simulation and physics edits continue to use their own application-layer commands. A save first ends the control session and waits for the draft to commit. Old edit records and history snapshots stay as they are.

## Generator dependency graph

`DocumentGenerators.graph` builds the following nodes for each project (object IDs: `document:<部分>` is document state, `rig:<阶段>` is a whole-rig stage, `parameter:<ID>` is a generated parameter, and `keyform:<warp|mesh>:<目标>@<参数>` is a keyform the generator adds on the target along that parameter):

| Node | Reads | Owns |
| --- | --- | --- |
| `rig.footprints` (mesh outlines) | The source image, the settings, and the per-layer mesh settings | `rig:footprints` |
| `rig.scaffold` (anchors, the face, the frame, and deformers) | `rig:footprints`, layer classification, the settings, and the skeleton definition | `rig:scaffold` |
| `mesh:<图层>` (the per-layer mesh and keyforms; when no layer list is given, they combine into `rig.meshes`) | `rig:scaffold`, that layer's pixels, and the classification and mesh settings | `rig:mesh:<图层>` |
| `rig` (assembly and atlas binding) | Each layer's mesh, `rig:scaffold`, the source image, the settings, and the layer classification | `rig:base` |
| `skeleton` (skeleton bake) | `rig:base`, the skeleton definition | `rig:skeleton` |
| `journal` (edit replay) | `rig:skeleton`, the edit journal | `rig:authored` |
| `skeleton.skin` (bone skinning of meshes the journal placed; present only when the journal hangs a bone-bound mesh under its own deformer) | `rig:authored`, the skeleton definition | The keyforms of these meshes on their limb bones, on the upper body half above them, and on the skeleton pose parameters |
| `swing:<ID>` (each swing that is not baked) | `rig:authored`, that swing's settings | Its parameters, and the keyforms of its parameters on each target Warp |
| `simulation:<ID>` (each simulation that is baked and enabled) | `rig:authored`, that simulation's settings and bake | Its pattern parameters, and the keyforms of the pattern parameters on the baked meshes |
| `overrides` (override merge) | Every generated keyform, the overrides, and the set of generators | `rig:final` |
| `seeThrough` (copies that show through the bangs) | `rig:final`, the settings | `rig:seeThrough` |
| `physics` (physics groups) | `rig:final`, `rig:seeThrough`, the generated parameters, and the physics and skeleton settings | `physics` |
| `motions` (generated motions) | `rig:final`, `rig:seeThrough`, `physics`, the motion settings, and the skeleton definition | `motions` |

- Replay (`RigEditOverlay.applyTo`) runs the nodes after the journal in the graph's topological order: `skeleton.skin` first, then swing and simulation, the same order as the previous "all swing first, then all simulation". Declaration order breaks a tie.
- Copies that show through the bangs (`SeeThroughLayers`, see [Deformer and parameter reference](DEFORMER_AND_PARAMETER_SPEC.md#automatic-deformation)): the `rig` node only records candidates (brows covered by the bangs, and each eye layer together with its bangs). The `seeThrough` node, after the override merge, layer visibility, and draw-order overrides (at the end of `AuthoredRig.finished`, `withSeeThrough`), makes copies from the originals according to the settings and opens a window for the eyes in the bangs (an inverse clip of the bangs, `BuiltRig.seeThroughWindows`). The mask, the draw order, and the opacity all come from the original and the bangs at that moment. The bangs mask changed by the window exists only in the finished rig. The bangs in the authored state and in the journal do not carry it. The inspector shows and edits the document's own masks through `authoredMasksOf`. When an old-version soft delete removes every windowed eye layer, the window is taken back (`withSeeThroughWindowsPruned`). A copy is not in the authored rig, and it does not own any `keyform:` object. Any document operation that names it in a reference field (a split reference field, and `id`, `masked_by`, and similar), at the `WorkspaceDocumentEdits` dispatch site and at the journal-record site, is refused as `WorkspaceGeneratedCopyEdit` (`generated_copy`). The three settings only trigger a replay. They do not count as generation settings. A copy has no layer entry of its own. Where a mesh is handled by layer, `BuiltRig.layerOf` takes the original's layer (an old-version soft delete removes the copy along with the original, then compacts the atlas and rebinds). A build that generation migration reads as rig data does not make copies (`SeeThroughLayers.withoutCopies`). An uncommitted preview (assignment by each canvas tool through `CanvasEditor.preview`, a live inspector field, the Warp control field) rebuilds the copies that were carried over, through `SeeThroughLayers.refresh`, from the original and the bangs in the preview. The mask, the order, and the appearance match a commit. A preview of a whole rebuild (swing, an interior-effect trial) already has new copy instances. It returns the same model as it is, and a place that identifies a preview by reference is unaffected.
- If the document lets two generators declare the same parameter, the one that declares it first keeps ownership and the later declaration is dropped. The rebuild can still proceed, and the generator itself reports the conflict.
- `DocumentGenerators.stale(before, after)` gives the generators that need to run again after one document change: a generator that read a changed part, and all of its downstream, and the objects previously owned by a generator that was modified or deleted also count as changed. For example, adjusting one swing reruns only that swing, the override merge, physics, and motions. It does not rerun rig generation, the skeleton, or another simulation.
- Rig generation is registered as nodes by stage (see [Rig generation stages](#rig-generation-stages) below). When `graph(overlay, layers)` is given a layer list, each layer is one `mesh:<图层>` node. A change to one layer's pixels expires only that layer's mesh, the assembly, and their downstream.

## Incremental replay

`RigEditOverlay.applyTo` runs, in order, the authored stage (when there is a checkpoint it starts at the last checkpoint and replays only the entries after it, see [Checkpoints](#checkpoints); when there is no checkpoint it runs the old-format static edits, parameter delete and create, static Warp, structure, and keyform set/copy/delete, and every entry of `authoringJournal`), then swing and simulation, the override merge, and deferred panel edits. A generated document has a checkpoint after its first edit, and after that at most `CHECKPOINT_INTERVAL` entries are replayed. The replay checkpoints below serve only a journal that has no checkpoint (a revision written by an earlier version and not yet edited). Swing and simulation are reused by `GeneratorReuse` according to the read set.

**Replay checkpoints** (`core.legacy.ReplayCheckpoints`, used only for a journal that has no checkpoint)

- A checkpoint is the model after "the old-format static edits + the first `i` journal entries". The lookup requires: the base model is the same instance; the old-format part is equal (including the set of swing and simulation parameters, which decides which structure edits are deferred, and the interface language); each of the first `i` entries is the same as the entry the checkpoint replayed (reference first, and content when the reference differs).
- Invalidation looks only at the prefix content, not at the index. A command that rewrites an earlier entry (a drag merge, capture of a generated-result override, mesh normalization) makes that entry and the checkpoints after it miss naturally, and replay resumes from the nearest checkpoint that is still valid.
- Each chain keeps the state at index 0, every 16 entries, and the last 3 entries, all as soft references (released when memory is tight). At most 4 chains are kept (most recently used first). On a branch, the old chain is kept, for a redo or a switch back.
- Appending one entry replays only that entry. Undoing to the previous state hits directly and does not replay. A full rebuild (reopen, or a paint or an image replace that changes a tile's size) produces a new base rig instance and replays from the start. A paint or an image replace that changes no tile size and no tile position keeps the same base rig instance (see "Atlas and painting" below), and checkpoints hit as usual.
- The skeleton is baked inside the base rig (before the journal). After the journal, only canvas skinning is written back. A skeleton edit changes the content of the base rig, so every checkpoint from before that no longer holds, and replay starts over. "Continue from before the first affected entry" does not apply to the skeleton. The base rig is not matched by content: on 2× tml (4096²) the IR content hash of the whole base rig is about 160 ms, while a full replay of 26 journal entries is about 6 ms. A rebuild with the same content is handed back the same instance by the stage cache (see "Rig generation stages"), so instance matching already covers it.
- `PuppetModel` and its objects are shared as immutable values. `-Dpsd2live.replayCheckpoints=false` turns off both checkpoints and generator reuse. In the code they are two switches (`ReplayCheckpoints.enabled`, `GeneratorReuse.enabled`), and each can be turned off on its own.

**Generator reuse**

- What swing reads: each target Warp and all of its ancestors (the parent space the measurement is in), the parameter list and the parameter tree, and the world origin (the automatic pivot). What it writes: its own parameters, the parameter tree, and the target Warp.
- What a baked simulation reads: the target meshes and the baked meshes (geometry, blend shapes, channels), the parameter list and the parameter tree, and the runtime target (which decides whether blend shapes are used). What it writes: its own parameters, the parameter tree, and these meshes.
- After a generator runs, its output is recorded as a patch: the new parameter list and parameter tree, plus the objects that were replaced. Before the record is kept, it is checked: only objects in the read set were changed, and the other field references are unchanged. Otherwise it is not cached.
- When the settings are the same and the read set matches item by item (reference first, content when the reference differs), the patch is applied directly onto the current input, and objects outside the read set keep their current values. Comparing references costs almost nothing. Hashing the read set by content is more expensive than the generator itself (see the table below).
- A content comparison can only miss, never mismatch: array fields are compared by reference. A miss only means generating again.
- `DocumentGenerators.stale` still gives the document-level range to rerun. During replay, the finer object-level read comparison wins. For example, when an unrelated mesh is edited, both swing and simulation are reused, and when a swing's target Warp or one of its ancestors is edited, only that swing runs again.

**Effect** (`CommitPerfTool.baseline`, before and after on the same machine. "Off" means checkpoints and generator reuse are off. "Append" means replay the journal with the last entry removed, then replay the full journal):

| Scenario | Replay before | Off | Append one | Replay the same document again |
| --- | ---: | ---: | ---: | ---: |
| Scenario a (skeleton + two swings + a baked simulation) | about 3.7 ms | about 4.3 ms | about 1.0 ms | about 0.6 ms |
| Journal of 64 entries | about 16 ms | about 20 ms | about 0.7 ms | about 0.1 ms |
| Journal of 214 entries | about 43 ms | about 45 ms | about 0.4 ms | about 0.1 ms |

After 200 geometry edits are appended, one commit drops from about 98 ms to about 46 ms, and the rebuild inside the commit drops from about 79 ms to about 23 ms. What remains is mainly moc3 packing and the geometry safety check, and it no longer grows with the journal length.


## Checkpoints

Replay of the journal assumes that the generated result an entry faced when it was written does not change. An edit that changes the generation input (the hair-simulation switch, the skeleton, generation settings and classification, a split, and similar) changes the base rig, and an old entry is then no longer replayed on the new result. It is merged and saved as data:

- **Trigger** (`WorkspacePreviewBuilder.build`, `RigRegenerationCheckpoint.checkpointed`): the new document continues the current document (`RigEditOverlay.continues`: the journal starts with the current journal; when the shared prefix has no checkpoint the old-format static fields must also match, and when there is a checkpoint they are no longer read), and it cannot take the append path. The base rig of the new document is generated. The part the old entries saw (`BuiltRig.resolvedPuppet(records)`: parts of a v2 split record before the boundary are in place, and passengers of a record after it are kept) is compared with `resolvedPuppet()` of the current base rig, as neutral IR. When they differ, the current base is G, the new base is G′, and the current authored rig is M, and they are merged (`RigRegeneration.merge`; G and M are rebound to the new atlas first). `rig_checkpoint` is inserted at the end of the current journal, before the new entries of this edit. When they are the same, replay proceeds as usual.
- **Parent overrides and draw-order overrides**: both are inputs of base generation. Changing them on a generated model is likewise merged as a regeneration and writes a checkpoint (a build that goes only through a checkpoint does not generate a base rig, and without the merge they would not be visible).
- **Generation settings and classification** (the changes `RigGenerationChange.changed` recognizes: face features, mouth shape, mesh only, head and body strength, `rigTuning`, layer classification): a generated model is merged and a checkpoint is written while the edit is being prepared (`WorkspacePreviewBuilder.normalizeMeshEdits`). G′ is generated from the current source image (a saved mesh input is still used, and a layer added after `generationSource` was frozen is in it too). `rig_generation_transition`, `rig_generation_frames`, and the mesh records created along with a migration are no longer written. The merge starts from the authored rig at the end of the current journal, so the same edit can only append entries after it. An edit that also rewrites an earlier entry is refused ("commit them separately"), and an old entry is no longer silently replayed onto the new generated result. A model imported from CMO3 has no generated result to merge, and it still writes a migration record (see [Legacy replay](#legacy-replay)).
- **Split** (`RigRegenerationCheckpoint.split`): see [Split materialization](#split-materialization-the-art-primitive-record-art_primitive). The checkpoint is written after the split record. The record itself is not replayed.
- **Record** (`RigCheckpoint`): the index of the authored rig (the objects are in `RigObjects` and are persisted with the document), the generated snapshot it is based on, and the merge issues. When a model preset turns hair simulation on, the same merge and checkpoint are written inside the preset, and the weights are then computed from the merged rig.
- **Direct edit**: on a generated model, an edit that continues the journal and appends entries, when the journal has no checkpoint, or when `RigEditOverlay.CHECKPOINT_INTERVAL` (32) entries already sit after the last checkpoint, first writes a checkpoint of the current authored rig at the end of the original journal, before the new entries (`RigEditOverlay.checkpointsBeforeEntries`, `WorkspacePreviewBuilder`). The generated snapshot keeps the one the previous checkpoint saved, or the current base rig when there is none. After the first edit, any build therefore replays at most 32 entries plus the entries of this edit. An appended entry acts on the current authored rig. An edit that rewrites an earlier entry (a drag merge, undo, redo) replays the entries after the checkpoint, or takes the saved revision (`PSD2LivePipeline.updateRigEdits`, `RigPreviewModel.authoredWithoutBase`). Neither generates a base rig. On the tml sample, the first edit is about 0.2 s, a later checkpoint is about 50 ms, and a cold build is about 0.2 s. A model imported from CMO3 writes these two kinds of checkpoint as well (with no generated snapshot, and with the binding key `cmo3-import`), and replays from the checkpoint on the import baseline.
- **Replay**: `replayAuthored` starts at the last checkpoint. Its rig is bound to the base rig's atlas through `reboundTo`, and the entries after it are replayed one by one (not through replay checkpoints; the replay checkpoints `core.legacy.ReplayCheckpoints` are used only for a journal that has no checkpoint). The mesh map of `authoredRig` is taken from the checkpoint header. When there is no `art_primitive` record after that, the build proceeds directly from the checkpoint (`RigEditOverlay.authoredFromCheckpoint`, `materializedPreview(rebind = true)`) and does not generate a base rig.
- **Generation baseline**: the generation settings and classification frozen by `rig_generation_baseline` constrain base generation only when there is no checkpoint after them (`RigGenerationBaseline.restore`). Entries after that all start replay from the checkpoint, and base generation uses the document's current settings.
- **Commit**: the runtime folds a checkpoint inserted by the rebuild into the committed document (`WorkspaceRuntime.adopted`). A batch member is built from the previous candidate (`rebuildFrom`), and the M of the merge is the authored state of the previous candidate.
- **Finish stage**: the whole journal is scanned as usual. Generated-result overrides and deferred panel edits are not affected by a checkpoint.
- **Report**: the issues of the last checkpoint enter `quality.regeneration` of `workspace_inspect` through `RegenerationQuality`. Before a commit, `workspace_preview_regeneration` can run a trial: it prepares and rebuilds the candidate the same way a commit does, reports the checkpoint that would be written (`regeneration` carries the merge issues, and `materialized` is the authored state before the new entries) and the objects added and removed, and publishes nothing (`WorkspaceDocumentCommands.previewRegeneration`).
- **Simulation bake** reads the result of the authored rig after the finish stage (`SimAuthoring.AuthoredRigs`, `RigPreviewModel.authoredPuppet`). It does not generate a base rig.
- After a generated model enables the skeleton, vertex groups are no longer resampled in the journal (the merge migrates them). A model imported from CMO3 has no generated result to merge, and it is still handled the original way.

## Generated-result overrides

- The owner of a keyform is decided by the graph: some parameter in the edited key leaves its default, and some generator in the graph owns `keyform:<类型>:<目标>@<该参数>`. That grid point is a generated grid point.
- **Swing**: it owns the keyforms its parameter axes add on the target Warp. An override records the generator, the target `warp:<ID>`, the full key, the cell generated at that time (`base`), and the user's cell (`points`), and merges control point by control point.
- **Baked simulation**: it owns the keyforms of the pattern parameters on the baked meshes (a simulation written back as keyform axes; when it is written back as blend shapes, the mesh cells do not contain that axis, and the edit is not recognized as an override). An override records the target `mesh:<ID>`, the vertex offsets generated at that time (`base`), and the offsets after the user's edit (`points`, obtained by applying that canvas edit on the current model), and merges vertex by vertex. After a rebake or a gain change, a vertex the user did not touch follows the new bake, a vertex the user touched while the bake did not change is kept, and a vertex both sides changed keeps the user's value and reports a conflict.
- **Channels**: opacity, draw order, multiply color, and screen color keyforms that a generator keys on its own axis belong to it as well. When a channel's track gains the generator's axis only after the journal (the same track of the authored rig does not have this axis), and the parameter leaves its default in the edited key, that grid point is generated. When a keyform `set` writes it, each such channel is written as one override with `channel` (`opacity` / `draw_order` / `multiply_color` / `screen_color`): `base` is the value generated at that time, and `points` is the user's value (one number for a scalar, three components for a color). On replay they are merged component by component, and a conflict or an orphan is reported as usual (`GeneratedOverrideIssue.channel`, `evidence.channel` of the quality report). A channel the generator did not key in the same `set`, and a track the journal itself built on that axis, stay ordinary journal edits. Copying to or from a generated channel grid point, and deleting a key the generator placed on a channel, are refused at record time as well. A caller with no authored rig (`ownedWrites` is not passed `authored`) does not recognize a channel override, and the behavior is the same as before. No generator currently keys a channel after the journal. This path is prepared for generators that will write color or opacity keyforms, such as a static key light or a see-through display.
- A canvas edit on these keyforms used to be written as an ordinary `canvas_geometry`. On replay the parameter did not exist yet, the whole rebuild failed, and the edit could not be committed. It is now rewritten as an override at commit time.
- After a generator is deleted, baked (swing), unbaked (simulation), or has its axes changed, the key no longer corresponds to a generated grid point. The override does not take effect and is reported as orphaned. It does not fall onto the rest shape under it. A change in vertex count after a mesh is regenerated is likewise reported as orphaned.
- An edit of a generated parameter at its default is still an ordinary edit. It changes the rest shape. Commands in an old project stay unchanged. Only a new commit writes an override.
- A Bezier edit and a keyform `set` (including MCP `rig_deform`) are likewise rewritten as an override when they write a generated grid point. An edit that keeps a child's position, a copy to or from a generated grid point, and adding or deleting a key on a generator's axis cannot be expressed as an override, and they are refused at record time (`GeneratedOverrides.ownedWrites`).
- When a generated parameter is used on another object (keying, a channel keyform, a rename, a range change), that parameter is first created in the journal from the generator's current definition (`GeneratedParameterAdoption`). After that the parameter belongs to the document, and the generator keeps using it. See the checkpointed rig.
- Overrides do not affect base rig generation: the key of the generated-geometry cache ignores override commands, and adding or deleting an override does not make the base rig generate again.
- **Issue report**: each replay stores an override that did not take effect as recorded, as a structured record (`GeneratedOverrideIssue`: kind `conflict` / `orphaned`, generator ID, target, the full key, the number of conflicting points or the number of points of an orphaned override, and the total number of points of the shape; when orphaned, a reason `missing_keyform` / `shape_mismatch` / `superseded`) in `BuiltRig.overrideIssues`, in journal order. The merge semantics do not change. An override on a mesh that a split superseded has the reason `superseded`.
- `core/quality/GeneratedOverrideQuality` turns these records into an observation report (version 4, domain `overrides`, three checks: `generated_overrides`; `superseded_entries`, entries from before a version 2 split that are replayed as a no-op only because the mesh they superseded failed, level info; `see_through`, a copy that shows through the bangs which the settings asked for but which could not be made, `SEE_THROUGH_DROPPED`, level info). A conflict is `GENERATED_OVERRIDE_CONFLICT`, an orphan is `GENERATED_OVERRIDE_ORPHANED`, and the level is decided only by the rule enumeration (both are warning, and `can_proceed` is always true). It is not inferred from text. When there is no issue, the report is complete and findings is empty. MCP `workspace_inspect` (scope `project`, when a project is loaded) returns `quality.overrides`. The strict structure is in `WorkspaceQualitySchemas`.
- The inspector toolbar shows a count badge when there is an issue, and the issues of the selected object are listed at the top of the inspector. Clicking the badge switches to listing every issue. The copy is localized by kind and reason code (Chinese, English, and Japanese).

The corrective keyforms of a skeleton bake were not changed into overrides (except the keyforms `skeleton.skin` writes on a mesh the journal placed; see [Meshes placed by the journal](#meshes-placed-by-the-journal)): the skeleton runs before the edit journal, a canvas edit in the journal is already replayed after the skeleton, and it migrates to the new topology together with a mesh rebuild. Changing them into overrides would instead make them orphaned after the mesh is divided again. Physics groups and generated motions keep the existing whole-object override (a user physics group of the same ID replaces the generated group, and a `builtin` motion clip replaces the generated motion).

## Measurement and the generation cache

`GeneratorCostTool` (`PSD2LIVE_TOOLS=1`) measures, on tml, the time of each generator and of hashing its input, and writes `build/tools/generator-cost/report.txt`:

| Item | Generation | Input hash | Conclusion |
| --- | --- | --- | --- |
| Skeleton bake (automatic skeleton) | about 4.7 s | about 5 ms (the base rig's IR + the skeleton definition) | Attached to the cache. After a hit, rig generation is about 20 ms |
| Generated motions (every preset, including skeleton presets) | about 16 ms | < 1 ms | Attached to the cache. After a hit, about 1 ms. Rig IR compilation drops from about 16 ms to about 2 ms |
| Swing (two) | 2.8 ms | 8.4 ms | No content-hash cache. After the object-level read set is compared by reference, the output patch is reused (see [Incremental replay](#incremental-replay)) |
| Baked simulation write-back | about 0.8 ms | about 8.6 ms (the bake JSON) | The same |
| Physics-group catalog | about 0.1 ms | about 0.1 ms | Not cached |
| The simulation bake itself | about 13 s | — | An explicit operation. The result is already saved in the document and is not recomputed |

- A skeleton cache key contains only what the bake actually reads: bone-bound meshes (complete, with UVs as the unbound layer offset); the deformers used to hang bones, to bend Warps, and to bind meshes (body, breath, lean, and leg Warps, head rotation, the bones' own IDs, and the parents of bound meshes) and all of their ancestors; parameters, parts, Glue, and the parameter tree. Other deformers and Drawables contribute only ID, kind, order, and parent. It also contains the skeleton definition, the body box, hand-made topology among the bound meshes, the stance, and the interface language (generated deformer and parameter names are already localized). The atlas, the source file, and deform paths are neither read nor written, and they are not in the key. On a hit with a different base rig, unread deformers and Drawables (by the reparenting at bake time), the atlas, the source file, and the paths are taken from the new base rig, and the draw order is derived again. If a bake changed an unread object in some other way, that result hits only for a base rig whose whole IR is the same. The cache keeps the most recent 4 results. Undo, a history switch, generating the same rig again before and after export, and a topology edit or a mesh setting of a mesh no bone is bound to (when it does not change the body box) all hit. A full preview rebuild with a skeleton drops from about 5.4 s to about 0.5 s.
- To keep the content hash stable, the eye and lip deform paths of rig generation now use a deterministic ID derived from the mesh ID and the path role. Previously every generation was a random UUID.
- A new object whose request gives no ID (a Warp, rotation deformer, Glue, or deform path created from the canvas or from MCP; a split fragment; a layer or mesh of a depth split; a layer that was imported or added) gets its ID from `StableIds`, derived from the request content (sending information such as `state` and `request_id` is removed). The same request on the same document gets the same ID for a retry, a trial run, and a commit. When the ID is already taken, `_2`, `_3`, and so on are added in order. An object that must be referenced inside a batch should still give its ID in the request. An ID that already exists in the journal or the document is kept as it is. An ID that is not a rig or document object, such as a session, a task, a history node, a parameter snapshot, or an artwork-workflow record, is not under this constraint.
- The cache key of a generated motion contains the preset name, the skeleton definition, the adjustment values, and the excluded parameters.
- The base rig itself is still handled by the existing `GeneratedGeometryCache` (a project that saved its generation input) and by the fast replay path. The former keeps the most recent 4 results (only the newest is a strong reference, and the rest are soft references, released when memory is tight). Undo and a history switch reuse it when they return to a recent input.
- From version 2, a `canvas_geometry` journal entry saves a sparse quantized delta relative to the geometry at the point of execution (`v`, `n`, `q`, an optional vertex index `i`, and integer deltas `d`). The producer still submits absolute points. `RigAuthoringJournal.compile` encodes them, and both preview and commit apply the decoded command. The absolute points of version 1 replay as usual.
- The moc3 bundle of the editor preview is no longer read back and checked (`validateBundle`). An export written for the user is still checked. A preview is checked the same way on a test JVM (assertions enabled) or when `psd2live.validatePreviewBundles=true`.
- Generating and canonicalizing physics3/motion3 inside an moc3 bundle (the regular-expression replacement that expands exponents) used to take about 18–21 ms, nearly half of the whole bundle. `Moc3Target` caches the most recent 4 texts by input (physics groups, motions, the parameter set, and the file-name prefix). A geometry edit does not change these inputs. The motion list of rig IR compilation is likewise cached, the most recent 4, by input. Previously every compilation serialized the skeleton definition for each preset to look up the generated-motion cache (about 2.5 ms; IR compilation 2.9 → 0.3 ms). `POS_VALUES` computes the total length first and then writes the whole block. When the size matches exactly, the writer hands over the buffer directly and no longer copies it (the moc3 of a tml skeleton rig is about 7 MB; the write goes from 13.7 → 6.8 ms). The whole bundle drops from about 48 ms to about 20 ms, and the export is unchanged byte for byte (`ExportGoldenTool`). A per-Drawable IR cache was not built: `PuppetIr.toIr` only wraps arrays, about 0.2 ms.
- The geometry safety check no longer boxes the geometry of every mesh and deformer into a list when it compares objects: the same instance is treated as equal directly, and the rest are compared element by element as arrays. Per-coordinate sampling reuses each target's reference area and validity check. Mesh sampling skips the normalized domain the selector uses. When the baseline and the candidate points are the same, the state is reused. A full report is byte-for-byte the same as before (`SafetyGoldenTool` checks 24 groups of random edits). An ordinary mesh edit drops from about 15–30 ms to within 2 ms. A mesh that binds bones, or whose combined domain is sampled at 16,384 coordinates, still needs about 1 s (previously about 2–3 s). A commit also narrows the comparison by the journal commands that were added. The rules are in [MCP_AUTHORING.md](../agent/MCP_AUTHORING.md#geometry-checks-and-trial-runs).
- Rig generation does not read the atlas layout: `RigBuilder` first generates an unbound rig (`BuiltRig.unbound`). A mesh's texture coordinates are the canvas-unit offset of a vertex from the top left of the layer rectangle. The atlas has only tiles with no placement, and no pages. `UvBinding` then converts them to page UVs by the current placement and writes the pages and the tiles. When the same set of layers is arranged another way, the unbound rig and its content hash stay unchanged, and only the bound result changes. Offsets are used instead of 0..1 layer units so that binding reproduces the original page UVs bit for bit (the export is unchanged byte for byte). The skeleton is baked on the unbound rig (from `BAKE_VERSION` skeleton-3 on): vertices added by joint subdivision are interpolated by the layer offset, and then `UvBinding` converts them to page UVs together with the other vertices, so the bake does not read the atlas. Moving, scaling, or rearranging tiles all hit the skeleton cache (with an automatic skeleton on tml, one commit that keeps tiles fixed, changes density, or changes the budget drops from about 4.5–10.8 s to about 30–140 ms, and to about 90–150 ms when one layer is also soft-deleted; `TexturePerfTool`). Compared with interpolating on page UVs before, only the UVs of added vertices differ in the last-bit rounding. Conversion among canvas, offset, raster, and page UV is provided entirely by `LayerTexture` (paint remapping, reflowing a generated rig onto the current texture, the mesh-migration journal, and CMO3 import share it).
- Atlas and painting (`AtlasLayout`): automatic layout is a canonical rectangle arrangement (`RectPack`, MaxRects: `padding` is left around every block; three orders, by area, by long side, and by height, each use the two scores "shortest remaining side" and "lowest bottom edge"; the one with the fewest pages is taken, and on a tie the one whose last page uses the least height). It is decided only by the document. A new file, a reopen, undo, a paint commit, and export get the same layout. The solved result is cached by tile size, lock, pin, and budget (the most recent 8). A commit that does not change texture size does not solve again. What is incremental is the page, not the layout: each page is composited and cached by the recipe "page size + each tile's rectangle and pixel digest" (soft references, the most recent 8 pages). A page whose recipe did not change keeps the same `AtlasPage` instance from the previous model. A page that changed is composited again, and the rows that differ from the page it replaces are recorded. A history-dependent layout that "keeps unchanged tiles fixed and finds another empty spot for a changed tile" is not used: when the size is unchanged the two are the same (the tile is redrawn in place); when the size changes, any layout changes that tile's UVs, and the native preview has to rebuild the model from memory either way, while a canonical reflow costs only one extra page composite and the strip encoding of the rows it spans (about 20 ms), and the layout is then independent of edit history.
- Lazy page PNG encoding: `AtlasPage.png` is the canonical ImageIO encoding that export writes, and it is generated only when export or IR compilation reads it. The editor's runtime bundle uses `previewPng`, encoded as strips of 16 rows, Sub filter, each with its own deflate (level 1, ended with a full flush), one IDAT chunk per strip, and the Adler-32 combined from the strips. The decoded pixels are exactly the same as the canonical encoding. A derived page re-encodes only the strips that contain dirty rows, and the other strips are taken from the page it replaces. When a whole page is encoded from scratch, the strips run in parallel. The byte array of an unchanged page stays the same instance, the preview-bundle fingerprint is not hashed again, and `CubismPreviewReload` uploads only changed pages.
- A paint candidate no longer does a second pack: a paint that keeps the mesh (and an image replace) in `WorkspaceRasterEdits` only crops the pixels (`RasterPaintCommit.paintedSource`) and freezes the generation input. The rig, the atlas, and the runtime bundle all come from the one rebuild that follows. A paint that needs the mesh rebuilt still calls `RasterPaintCommit.prepare` to obtain the migration record, but it no longer compiles a preview runtime bundle. On rebuild, `WorkspacePreviewBuilder` hands the current model's atlas to `buildPreview` and only borrows its pages and strips. The result is exactly the same as a build from scratch.
- The base rig after a reflow is cached, the most recent 4, by "the generated-geometry cache entry + the layout + the texture-layer metadata (without pixels) + the IDs of new meshes". A paint that does not change tile size or position gets the same base rig instance, and replay checkpoints keep hitting. Layer opacity statistics (`LayerClassifier`) are cached by raster-array identity. The composite preview image (`PreviewRenderer.composite`) is cached by each layer's raster identity and position, the most recent 3. A rebuild rescans only the layers that were painted.

## Rig generation stages

`RigBuilder.build` is split into stages with declared inputs. The output of each stage is cached by `RigStageCache` (one per pipeline, hung on `PreviewMeshCache`) under a key that "contains only what that stage reads". A key takes the cheap digests and the settings subset that already exist: SHA-256 of a raster remembered by array identity (`RasterDigest`), layer metadata (ID, name, group, order, bounds, semantics, footprint bounds and centroid, and the opaque-pixel count), and `stageConfig`, which keeps only mesh, mouth, strength and tuning, generation mode, and the runtime target. The skeleton, the journal, the per-layer tables, visibility, draw order, and texture, physics, motion, and export settings are never in the key. A stage that reads the skeleton puts the part it reads into the key itself.

| Stage | Key (what it reads) | Capacity |
| --- | ---: | ---: |
| Footprint `footprint` | Raster size and digest, integer position, the alpha threshold, that layer's mesh settings, and the mesh scale | 512 |
| Frame (computed every time, about 1 ms) | Analysis with footprints: anchors, the face rig, the head, face, and hair boxes, and the stance and the body box | — |
| Deformers `deformers` | The stance content key, each box, every value of the face rig, the anchors, layers that have a left and a right side (metadata + bounds in rig space), the top's bounds, the settings, and from the skeleton only the switch and the two ends of the first usable upper-body bone (`torsoFrame`) | 8 |
| Face lean `lean` | The deformer-list instance | 8 |
| Mesh `mesh:<图层>` | Layer metadata and the pixel digest, bounds and centroid in rig space, the parent and its box, head space, the face rig for an eye layer, the matching eye-white bounds, the mesh scale, that layer's mesh override, and the settings | 1024 |
| Channels `channels` | Kind, parameters, the on/off key, semantics, and tooth fade | 256 |
| Lips `lips` | The owning Drawable, the mesh-stage output instance, the parent box, lip-layer metadata, pixels, whether it is packed, draw order, and visibility, and the settings | 64 |
| Bind and skeleton `bound` | The assembled model (structurally equal, meshes by instance), the hair-simulation switch, atlas placement and page size, each layer's binding metadata, the skeleton definition and input, the other result fields, and the skeleton-cache clear count | 4 |

- Assembly (masks, parts, parameters) is redone every time, about 1 ms. When every stage hits, `bound` returns the same `BuiltRig` instance as last time. The reflow cache of `generatedBase` now keys on the geometry-rig instance (rather than the geometry-cache entry), so when only content that no stage reads has changed (for example an appended journal entry makes the generated-geometry cache miss), the base rig is still the same instance, and replay checkpoints keep hitting.
- On a `bound` hit, its skeleton bake is marked most recently used (`SkeletonRig.touch`), so the head cache taken when the project is saved (`ProjectHeadCache`) is still the current bake. The count incremented by `SkeletonRig.clearCache` is in the key, and a clear bakes again. `bound` still keys on atlas placement, but the skeleton bake inside it does not read placement: when the atlas changes, `bound` misses, the skeleton cache hits, and only the binding is redone.
- When mesh settings change, that layer's footprint may move the anchors and the frame, and a mesh whose parent box changed is rebuilt with it (changing a lower-garment mesh on tml rebuilds about 5 meshes). The face layers' meshes keep their original instances.
- The raster digest of `PreviewMeshCache` now uses `RasterDigest` remembered by array. Previously every call hashed every layer again.
- `-Dpsd2live.rigStages=false` (`RigStageCache.enabled = false`) turns off the stage cache and digest memory, for comparison.

**Correctness**: `ExportGoldenTool` is byte-for-byte the same as before the change (bcf919f2).

**Skeleton commits**: a skeleton edit (creating a bone, binding, moving a joint, deleting a bone) makes `bound` miss and bakes the skeleton again. The bake is split into two more cache levels inside `SkeletonRig`, and a limb that was not touched is not recomputed:

- Single-mesh skinning (`skinDrawable`, the main cost of the bake) is cached by everything it reads: the lossless IR of that mesh and its deformer chain (each bone of the limb tree, the parent, the host, and all ancestors), the ranges and defaults of parameters that appear in the IR and of each bone parameter of that tree, the rest canvas vertices, each bone in the tree and its parent bone, the preset pose, the owning bone, blend-shape bones in the tree, the sampling, the hand-painted weights, and the host. Values are soft references, at most 128 entries, and `SkeletonRig.clearCache` clears them together.
- Joint subdivision (`SkeletonMeshRefine`) is cached by the mesh arrays, the rest canvas vertices, the joint band, and the segment count.
- The cache key of a whole bake is computed only once for the same base rig instance and the same input.
- Skinning of a mesh that was itself touched: each sample (`computeDeltas` under one set of bone-parameter values: each bone's transform, the joint template, ARAP, and surface smoothing) depends only on its parameter values, so the samples needed by the fit, the keyform grid points, and the pose blend shapes are solved in a batch, in parallel, on the common thread pool, and read back in the original order. The result does not depend on the thread count and is bit-for-bit the same as solving in order (`SkeletonRig.parallelSamples` exists only so tests can turn it off). The fit (`fittedSides`) advances both sides of each bone together. Each round checks the segments in the original order and prefetches only a few later segments. What is computed extra is only the samples after a segment that failed. The global ARAP equation (the Laplacian matrix of the free vertices plus that pose's guide penalty) is unchanged across every local and global iteration of one solve and across the two coordinate axes. It is now one envelope Cholesky factorization per solve (the reverse Cuthill-McKee order and the envelope are computed once per mesh), and each global step is only two triangular backsolves, replacing conjugate gradient of at most 200 iterations per step. The difference from the conjugate-gradient result is no more than 0.0005 px on a 4096² canvas (`SkeletonBakeDiffTool`, every keyform and blend-shape key, and the render is the same pixel for pixel). `BAKE_VERSION` is skeleton-4, and the skin-cache version is skin-2. A head cache written by an old version no longer hits. The fit tolerance is still 1 canvas pixel: the sample count grows as the canvas grows, but at the current cost there is no need to change the keyform count of an existing project for that.
- The deformer stage keys only on the switch and the upper-body bone (see the table above). A change to other bones, bindings, poses, or weights keeps the deformer instance.

Normalizing a mesh edit (`normalizeMeshEdits`), when there are vertex groups, first builds one preview without the vertex-group entries in order to migrate the weights. The commit build that follows hits the process-level bake cache, and only the non-skeleton part is extra (about 60–120 ms). A vertex-group entry can affect the base rig through `SkeletonCanvasSkin.lockedTopology`, so the previous build is not used directly for the next one.

A commit that changes only the journal takes the fast path (`PSD2LivePipeline.canFastUpdateRig`, replay on the cached base rig), but the skeleton bake also reads the journal: meshes of hand-made topology (`canvas_topology`), records of bone-bound split parts, canvas-skinned meshes the journal placed, and the vertex count of their vertex-addressing records (`RigBuilder.skeletonJournalInputs`). When this content changes (for example a topology edit of a bone-bound mesh, and its undo), the fast path is not taken. The build is a rebuild, and the result matches a cold rebuild (`SkeletonIncrementalBakeTest`).

## Per-layer size

A layer's canvas position and its pixel count are independent of each other (`core/LayerSpace.kt`):

- Canvas rectangle: floating-point canvas units, the source layer's `rect`, defaulting to the integer bounds. It decides where the layer sits on the canvas. A pixel operation such as painting or an image replace does not change it.
- Raster: the layer's actual source pixels, W×H, at any resolution.
- Native density: raster pixels / canvas units. The two axes can differ. A layer whose raster covers the integer bounds exactly (one pixel per canvas unit) and that has no fractional rectangle is exactly the same as before.

Geometry (`core/CanvasDensity.kt`):

- Analysis, classification, anchors, outlines, mesh generation, lips, and a connected-component split all read the raster in canvas units. A layer whose density is not 1, or whose rectangle is fractional, is swapped at analysis time for a canvas-resolution view, `CanvasDensityLayer`: the same layer, the raster resampled onto the integer bounds at one pixel per canvas unit by an area average (bilinear when enlarging), and transparent outside the rectangle. Therefore, under `meshTrace = CANVAS`, a 1024² raster on a 32-unit rectangle and a 32² raster generate the same mesh. A fully transparent placeholder raster is not swapped for a view. Under `meshTrace = TEXTURE` (the default of a new project), only the mesh outline reads the texture itself (laid onto the integer bounds at the original density, and reduced by maximum alpha to a working resolution at most 4 times finer than a mesh unit). Vertex spacing and offsets stay in canvas units. See mesh topology. Classification, anchors, and the rest of the analysis still read the canvas view.
- A generator's texture coordinates are still the canvas-unit offset from the top left of the integer bounds. `UvBinding` / `LayerTexture` convert the offset to the original raster and then to the tile, by the space of the texture layer (`textureLayer`, the original raster behind the view): `raster = (offset − (rect − bounds)) × 密度`. When the rectangle is an integer, the subtracted term is 0, and the result is bit-for-bit the same as before.
- Preview compositing (`PreviewRenderer.drawLayer`), the artwork workflow, and observation rendering stretch the raster into the canvas rectangle to draw it.

Atlas (`AtlasLayout`):

- The texture pixels of each tile = raster pixels × `textureUpscale` × the density factor (`textureOverrides.density`, default 1, the raster's original resolution) × fit. `textureUpscale` is still the source-image preprocessing cached by digest, and the effect is the same as before.
- The page size takes the budget's `pageSize`, and, as before, grows until it can hold the largest layer at canvas resolution (the next power of 2, at most 16384). The part that density pushes past that is handled by fit.
- fit ≤ 1 is one coefficient shared by every unlocked layer. Arrange first at fit 1, and use 1 when it does not exceed `maxPages` pages. Otherwise binary-search, on integer steps of 1/4096, for the largest step that still fits. The result is decided only by the document. The same input produces the same layout. A locked layer (`lock`) keeps fit 1. A pinned layer (`pin`) is placed first at the given page position, and the rectangle arrangement goes around it.
- When a locked or pinned layer exceeds the budget by itself, it is not quietly shrunk. Lock and pin are released, fit is solved for all of them together, and this is stated in `PackedAtlas.notices` (written only to the program log). When even 1/4096 does not fit, the page count is exceeded at fit 1, and that is stated. fit < 1 is stated as well. The statements enter the export warnings.
- When the tile size is not the raster size, it is resampled by `RasterResample` (`format-compile`, deterministic, premultiplied alpha). A page recipe keys on "tile rectangle + pixel digest" and is unaffected. A placement's `scaleX/scaleY` = tile pixels / raster pixels.
- At the defaults (every raster equals its bounds, the default density, the existing settings, fit 1), the layout, the UVs, the pages, and the export are byte-for-byte the same as before (`ExportGoldenTool`).
- A saved arrangement (the `atlasArrangement` setting, `project/AtlasArrangement.kt`): when it is present, `AtlasLayout` no longer solves an automatic layout. `AtlasArrange.keep` places by the saved position and fit. A tile that is still inside a budget page, has not left the page, and does not collide with a tile already placed keeps its place. The rest (a new layer, or a tile that overlaps a neighbor or leaves the page after it grows) is put at the first free position on the page's 4×4 pixel cell grid. A notice is given only for a tile whose original stored position is no longer valid. A new layer (including an original layer that a split replaced and that has not yet been compacted away) is placed in silence. Rectangle tiles are judged by the `padding` gap. When a mesh coverage region is involved, they are judged by cells and expanded by `ceil(2×padding/4)` cells. The saved coverage is corrected on every build from the tile's current raster (`AtlasArrange.covering`). When the cell grid does not match the raster size (a paint or an image replace changed the crop), it is discarded and the whole rectangle is used. When a raster pixel with alpha ≥ 8 falls outside the coverage (paint went past the mesh), those cells are added, so a neighboring tile that collides with it is pushed into an empty spot instead of covering it. A tile moved into an empty spot likewise searches by its coverage and writes only its own cells. Freezing the arrangement that the canonical layout produced rebuilds pages that are byte-for-byte the same.
- A one-shot arrangement (`atlas_pack`, `AtlasLayout.arrange`): the mesh coverage is taken from the texture coordinates of the final meshes of the current model, and the raster's pixel cells that lie outside the mesh are added (`WorkspaceAtlasFootprints`; a cell is 4 raster pixels, at most 192 cells on each side; a triangle counts as meeting a cell only when it enters by 0.01 pixels, so last-bit rounding after a layout change does not change the result). First fit runs on the cell grid from the top down and from the left to the right, in three orders, by area, by height, and by the long side. The one with the fewest pages is taken, and on a tie the one whose last page uses the fewest rows. Rectangles may nest inside one another. When it does not fit in the budget page count, fit is binary-searched first at a step of 64/4096, then refined to 8/4096. Arranging by rectangles only (`shape=rect`) freezes the result of the automatic layout directly. When a page is composited, a tile that has a coverage region writes only its own cells (`TileKey.mask` enters the recipe), and an upscaled texture does not bleed its edge outward onto a neighbor. If a later mesh edit goes outside the coverage from arrangement time, the `notices` the atlas reads ask for another arrangement. Automatic arrangement (`auto=true`) deletes the saved arrangement. Closing, or moving a tile, saves the current layout. Under a saved arrangement, a tile that has no position it can keep (a new layer, a split part, a tile pushed out because a neighbor grew) is placed again at the first free position on every rebuild. Therefore, when a tile is moved, or when density or lock is changed, every tile position of the current model is written back into the arrangement first (`WorkspaceTextureEdits.settled`). Those tiles then stay where they were, and they do not fill a spot that a move or a shrink left empty. At the same time, a tile that has no coverage is given the coverage of its mesh (`meshed`, `WorkspaceAtlasFootprints`). After that, a tile judges overlap only by the cells the mesh actually uses, exactly the same judgment as a drag in the atlas view (`WorkspaceTextureView.meshFootprint`), and a position the view allows is the position that lands. A tile can rotate about its center (`ArrangedTile.rotation`, `AtlasPlacement.rotation`). Page compositing samples backward by the rotation (`AtlasLayout.writeTurned`, writing only mesh cells). Coverage intersects the cells after rotation (`rotation` of `AtlasArrange.shape`). Mesh UVs are converted through Umamo's rotated placement by `LayerTexture.tilePlacement`, and export carries the rotation out as well. Move, scale, and rotation in the atlas view are an edit session (`TextureWorkspaceState.session`), and they change only what the view shows. On apply, density and position are committed as one batch of `layer_set_pixel_density` / `atlas_set_tile`: one rebuild, one history node. Both of these edits (one item or a batch, from the GUI or from MCP) are checked before publish by `WorkspaceTextureEdits.requireKept`, which compares the candidate model. If any tile that previously kept its position is pushed off its arranged position in the new layout, `WorkspaceTileCollision` (`tile_collides`) is thrown and the whole edit is not committed. A batch checks only the final layout, and only when the batch does not contain a rearrangement, a budget change, a pixel replacement, or a move of the canvas rectangle. The pair test (`AtlasArrange.meet`) first compares the rotated bounding boxes expanded by the gap, and compares mesh cells only when those boxes meet, so a tight rectangle arrangement is not judged to intersect by mistake after coverage is filled in, just because cells were rounded.
- Mesh identity: an edit that changes the generation input (adding or deleting a layer, or changing classification or generation settings), during normalization, first writes the ID of each current mesh into `splitDrawableIds` (`WorkspacePreviewBuilder.pinnedIdentities`), and the generator names from that. Otherwise an ID derived from the classification and from the index among the same kind is renamed or renumbered, and the regeneration merge keeps the user's old mesh beside the new mesh as a retired object.
- Deleting a layer (`layer_delete`, `WorkspaceLayerEdits`) is a real delete. The layer leaves the source image and the generation input. Its meshes leave the authored rig through the journal record `layer_delete` (`LayerDeletionJournal`). The build writes a checkpoint before that record, and a create record from before it is no longer replayed. Undo is a history switch. The deferred filtering below applies only to a layer that an old version soft-deleted (`deletedLayerIds`, read-only, and `layer_restore` can restore it) and to a derived row such as a lip band.
- A soft-deleted layer (including an original layer left behind by an old-style split), in deferred-filter mode, still takes part in the full generation and replay, and the full atlas packs a tile for it. The model after filtering is repacked from the layers that remain (`RigLayerDeletion.compact`). The remaining meshes are moved onto the new atlas by `RigGenerationSource.repack`, converted in canvas units, sampling the same texel. Preview, the texture workspace, and CLI and GUI export therefore contain no pixels of a deleted layer. The full atlas the base rig is bound to is recorded in `RigPreviewModel.generationAtlas`. A fast replay (`updateRigEdits`) rebinds the same way after filtering. A CMO3 import keeps its original layout. When a remaining mesh cannot find a tile in any atlas, it falls back to the full atlas. Restoring the layer produces the full atlas again. An original layer that a split replaced (filtered out by `ArtPrimitiveJournal.visibleAnalysis`) is the same: it is still packed at generation time, and both preview and export compact by the visible layers after replay. The generated-geometry atlas (the geometry rig of `generationSource`) does not read texture overrides or a saved arrangement, and a texture commit does not invalidate the geometry cache.

Export:

- moc3 reads only pages and page UVs. It needs no extra handling.
- cmo3 (`Cmo3LayerArt`, `targets/cubism`): a Cubism Editor layer is one pixel per canvas unit, and the editor rebuilds the atlas from the layers. The default is `canvas`: a layer whose density is not 1 is written into the layered image at the canvas-rectangle size (downsampled). The stored atlas pages still keep the high resolution, and the tile's pack scale grows with that. As soon as some tile's atlas density (texture pixels / canvas units) is greater than 1, export reports a `TEXTURE_SIZE` / `APPROXIMATED` loss entry ("Cubism Editor rebuilds the atlas from canvas-resolution layers"). An existing `textureUpscale` project is covered the same way. The internal setting `layer_art=native` writes the layer at the original resolution and scales it to the canvas with the model-image transform. It has not been measured in the editor yet, and it is off by default.

Image replace (`core/LayerImageReplace.kt`):

- `LayerImageReplace.replace(document, layerId, raster, fit)` returns a candidate document. The canvas rectangle and the integer bounds stay unchanged, and only the raster is replaced (`STRETCH` stretches it directly; `CONTAIN` keeps the aspect ratio, centers it, and pads with transparency). On the first replace, the source image from before is frozen as the generation input (the same as a paint that keeps the mesh). The mesh, the keyforms, and the binding stay unchanged. After the rebuild, only the bound UVs and the pages differ. The caller rebuilds and commits as usual.

Import (`core/LayerImport.kt`, the artwork workflow, and CMO3 import):

- An image-file import (`layer_import_images`) crops the transparent edges and then keeps the original raster. When it is larger than the canvas, only the canvas rectangle is scaled down uniformly so that it fits inside the canvas. The raster is unchanged, so the density is greater than 1. An image that fits is still integer bounds of one pixel per canvas unit, the same as before.
- An imported image has its own mesh in the authored rig in that one commit (`canvas_mesh_create`). It does not freeze the generation input and it does not write a placeholder. The generator treats a layer that a create record owns as a transparent placeholder (`RigGenerationSource.createdCoverage`), and it only packs a texture tile for it.
- A transform of the whole layer (`layer_transform`, `application/WorkspaceLayerTransform`): the layer's frame (the integer bounds and the floating-point rectangle) stays unchanged. The pixels, the texture tiles, and the texture coordinates are all anchored on the frame. The transform `LayerTransform` (a 2×3 affine) is stored on the layer, and every mesh of the layer writes one object-mode `canvas_geometry` at the rest pose. The generator reads only the frame. It does not read the transform, so a move is the author's edit and not a regeneration. A paint session runs inside the frame. The canvas shows the full transform (the session raster is drawn as a quadrilateral that rotates with the layer, a stroke and a shape land on the frame by the inverse transform, and the brush size is converted by the area ratio of the transform). When an object-mode drag covers every mesh of a layer, the canvas commits that operation (`AffineFit` fits the points before and after the drag, and takes the first of a pure translation, an axis-aligned scale, and a general affine that agrees within 0.01 canvas units. A drag that did not rotate is not recorded as a rotation because of floating-point noise. When transforms compose, a residual on the order of one millionth is dropped, and `isAxisAligned` allows a relative turn of 1e-5). `layer_set_canvas_rect` is one transform that starts from the rectangle currently shown. Source images that differ only in the layer transform are the same image for generation and for the atlas (`PSD2LivePipeline.sameArt`), so a move takes the fast path and the model switches to the new source image. A commit that only adds or removes a layer owned by a create record, or that only moves a layer, skips the regeneration comparison (`WorkspacePreviewBuilder.onlyUsersLayersChanged`). The development tool `LayerFlowPerfTool` measures the commit time of import, move, reparent, rebuild, and delete.
- An artwork layer (`layer_add_from_asset` / `layer_set_placement`) takes the artwork's pixels as the raster and the placed canvas rectangle as the layer rectangle. `WorkspaceCanvasPlacement.canvasUnitsPerPixelX/Y` is the actual ratio. Registration by translation, scale, or an explicit mirror does not interpolate (a mirror only flips rows and columns). Only a registration that includes a rotation is rasterized, at the artwork's own density, into the bounding box.
- A CMO3 import computes page texels per canvas unit from each tile's model-image transform (`_materialLocalToCanvasTransform`, umamo `Cmo3AtlasIngest.canvasTransformByTile`) and from the pack scale. When that is greater than 1, the layer rebuilds the raster at that density on the same integer bounds (for example a high-density layer that exists only on an atlas page, or either of the two writings in which the layer itself is scaled onto the canvas by the model image). Otherwise it is byte-for-byte the same as before. The umamo source-layer manifest still records the rectangle on the file's layered image. It is not converted to the canvas.
- Size limits (`LayerSizeBudget`): the raster, and the canvas-resolution view (the bounding box), are each at most 16MP. Native density is at most 256 pixels per canvas unit on each axis. The rectangle is at least 0.5 units on each axis. Going past a limit is refused outright. A CMO3 import that goes past a limit lowers the density of the whole import.

Painting (`core/PaintSpace.kt`):

- Painting runs on the layer's own raster grid (`PaintSpace`). A pixel of the draft image is a raster pixel of the layer. It extends toward the canvas edge at the same density, and when that would pass 16MP the margin around the layer shrinks in proportion. A gesture, a radius, a line width, and a color pick are all in canvas units, and an affine maps them onto draft pixels. When the two axes differ in density, the brush radius takes the geometric mean. The draft of a layer whose density is 1 and whose rectangle is an integer (and of a layer that is fully transparent) is the canvas itself, bit-for-bit the same as before.
- A commit carries the raster cropped to the opaque pixels, and its canvas rectangle (`WorkspacePaintRaster.rect`). It is not shrunk back to canvas resolution. The rectangle is measured from the layer's original rectangle: an edge that did not move keeps its original coordinate, and both an expansion and a crop keep the density. The integer bounds take the bounding box. When the rectangle and the integer bounds are the same, the rectangle is not stored. At commit time only the layer's original region and the region the stroke wrote are read. The whole canvas is not copied. A layer that was erased completely becomes, as before, one transparent pixel of 1×1 at the canvas origin.
- The front layer of a depth split keeps the raster size. It samples the committed pixels at pixel centers, and when the grids line up the copy is bit for bit. A paint that keeps the mesh, a paint that rebuilds the mesh, and a paint on an imported CMO3 all address tiles through `LayerSpace` (the slice remap of `RasterPaintCommit`, and the paint texture coordinates of `Cmo3ModelImport`). A connected-component split crops the parts inside the source layer's own raster, and a part keeps the original density.

Texture commands (`application/WorkspaceTextureEdits`, `WorkspaceTextureOperations`): the texture workspace (the atlas pages and the density heatmap, the per-layer size panel, and the original-pixel preview on the editing canvas; see [Quick reference](../guide/USER_GUIDE.md#texture-workspace-notes)) commits through `WorkspaceTexturePort`. It shares one pure candidate with the MCP commands `layer_set_canvas_rect`, `layer_replace_image`, `layer_set_pixel_density`, `atlas_set_tile`, `atlas_set_budget`, and `atlas_pack`. Each of them is a background job and a member of an atomic batch. The queries are `layer_get_texture`, `atlas_get`, `atlas_check_placement`, and `atlas_render_page` (see [MCP interface](../agent/MCP_AUTHORING.md#textures-and-the-atlas)). A fractional rectangle written into umamo's source-layer manifest (which stores integers) takes the integer bounds. Mesh migration that resolves a texture from the manifest (`LayerTexture.of`) is only an approximation for a fractional rectangle (an integer rectangle is exact: the tile width and height are the raster size, the manifest is the canvas size, and the ratio is the density). Padding of the generation input (`RigGenerationSource.padded`: the texture coverage of a kept mesh, of a newly created mesh, and of an `art_primitive` part) pads a high-density layer with transparency at the original density, and does not downsample. The `canvas_uvs` of `art_primitive`, of `canvas_mesh_create`, and of `canvas_mesh_rebuild` are canvas units, and `LayerTexture.of` maps them onto the high-resolution tile.

## Split materialization: the art-primitive record `art_primitive`

The earlier splits (`canvas_source_partition`, `canvas_depth_split`) left the original layer in the source image and soft-deleted it. On replay they first regenerated the original mesh bit for bit (checking the geometry fingerprint and the parent), and then, at the record's position, copied its binding onto the parts. That has three problems. Once the generation rules change, an old record can no longer be replayed. The atlas still packs the original layer, and a CMO3 export carries its pixels. "Restore all" brings the original layer back. A split now **materializes** the original layer into parts. The parts are the only things drawn. The original layer no longer exists, and the only way back is to undo to before the split.

**A split is a regeneration** (`WorkspaceArtPrimitives.materialize`, `RigRegenerationCheckpoint.split`): a split changes the source image (the original layer is replaced by the parts) and is merged the way a [checkpoint](#checkpoints) merges. G is the current generated result, and G′ is the generated result after the parts take the original layer's place. The original mesh in G, and the original mesh in the current authored state M, are each cut into the same parts by the split itself (`SplitParts`: a connected component or a polygon is `SourcePartitionJournal.splitParts`, and a depth split is `DepthSplit.splitParts`). Each takes its own copy of the original mesh's rest position, keyforms, channels, blend shapes, paths, vertex groups, and Glue, through the same set of vertex sources. A part the user did not touch is therefore bit-for-bit the same as the generated part, and the user's edits on the original mesh become edits on the parts. The three-way merge (`RigRegeneration.merge`) carries them onto the parts of G′ (when the parent changes, through the parent space; when the skeleton inserts a joint row, by migrating canvas texture coordinates). Glue that the split itself creates (cut-point follow of a polygon cut, and the directional Glue of a depth split) exists only on the M side, and it belongs to the user. The split writes an `art_primitive` record, and a `rig_checkpoint` is written immediately after it (the merge result and the G′ snapshot). The record itself is never replayed. A later build starts from this checkpoint and does not need a base rig.

- When the original mesh was generated by a generator, the record is a version 2 **declaration**: each part's rest canvas mesh (the part cut from the original mesh in G, moved to the canvas by the generation deformer at the default pose), the layer, the classification, and `fixed_topology` (true when the part carries user Glue, a vertex group, or a path). `authored` is an empty object, and `glues` is empty. Base generation generates the parts from this (see [Version 2 records](#version-2-records)). A later change of face settings, stance, skeleton, or classification reaches the parts the same way, through the next merge.
- When the original mesh was not generated (a mesh the journal created, for example an image imported after the generation input was frozen), the record is version 1. The parts carry all of the data. Their layers do not enter base generation, and in the merge the parts are user objects.
- There is no version 1 fallback, no two-pass capture, and no guard. The merge does not fail. A place that did not migrate cleanly is reported as a merge issue. When the original mesh's topology was edited by hand, the G side cannot cut out the same parts, and the parts are kept with the user's topology (the same rule as a topology the user changed inside a merge; see the checkpointed rig, Regeneration merge).


**Record** (a journal entry, version 1. It is now written only for an original mesh that was not generated; a split from an earlier version always wrote it. Version 2 is [below](#version-2-records)):

| Field | Content |
| --- | --- |
| `op`, `v`, `origin` | `art_primitive`, `1`, `split` (a polygon or a connected component) or `depth` (a depth split) |
| `texture_source_id` | The source the part textures live in (a generated model uses `art-0`) |
| `supersedes`, `supersedes_layers` | The mesh IDs deleted at this position, and their source-layer IDs |
| `replace` | Superseded mesh → part mesh, used for the position in the part tree. When `masks` is not given, it is also used for the masks of other meshes |
| `masks` | Optional. When the superseded mesh was a mask, which parts take that over (a depth split uses only the back layer) |
| `primitives` | One entry per part: `id`, `layer_id`, `source_id`, `source_bounds` (the canvas rectangle the texture must cover), `neutral_bounds`, the name, the parent, the part, the blend mode, the static material and visibility, the masks, and `user_data`; parent-space vertices `positions`, `triangles`, and canvas-unit texture coordinates `canvas_uvs`; the parameter definitions used, geometry keyforms `geometry`, channel keyforms `channels`, blend shapes `blends` (including limit curves), paths `paths`, and vertex groups `vertex_groups` |
| `glues` | `replaced`: in model order, the replacement Glue for each Glue that touched the superseded mesh. `appended`: Glue appended at the end (cut-point follow of a connected-component split, and the directional Glue of a depth split) |
| `depth` | A depth split only: the `back` and `front` layer IDs and `glue_id`. `DepthSplit.isFrontLayer` uses this so that painting the front layer keeps its topology |

**Replay** (`ArtPrimitiveReplay.replay`, legacy replay, and only in an old journal that has no checkpoint after the record; see [Legacy replay](#legacy-replay)): a missing parameter is created from the record. The meshes in `supersedes` are deleted, and the parts take their place in the original mesh's list and in the part tree (when the original mesh is already gone, they join the recorded part or the root). Masks of other meshes are rewritten by `masks` / `replace`. Glue that touched the superseded mesh is replaced, in order, by the matching item in `replaced` (when the count does not match the current model, every touching Glue is deleted and the replacements are then appended in order), and then `appended` is appended. The superseded mesh's paths and vertex groups are deleted, and the parts' paths and vertex groups are written from the record. Replay does not read the superseded mesh's geometry, and it does not check its fingerprint. Texture coordinates are stored in canvas units, and on replay they are converted through the current atlas.

**The state captured at the split**: `RigEditOverlay.authored` gives the model after the old-format edits and the whole journal, and before swing and simulation write-back. The parts are taken from that model, so an axis that swing or simulation generated is not written into the record. Vertices, keyforms, blend shapes, paths, vertex groups, and Glue of a connected-component or polygon part migrate by the original partition algorithm. A simulation target, a bake offset, and a Glue role move onto the parts (a depth split moves them onto the back layer), and the simulation writes them back as usual afterward.

**Generation input**: a split freezes the generation input (`generationSource`). The original layer remains only there. During generation:

- A superseded generated layer still takes part in base-rig generation, placed at the position of its replacement layer in the current source image (the highest `order` of the replacement layers). The draw order of the other layers, the deformer frame, and the IDs therefore match the time before the split, and the journal from before the record replays as usual.
- The layer a part lives on is owned by the record and does not enter base generation. Its current pixels are packed after transparent coverage is padded to `source_bounds`.
- A superseded layer occupies only a 1×1 transparent placeholder in the atlas, so a journal entry from before the record can still address it. After the record is replayed, `BuiltRig.withRigEdits` deletes it from the rig's atlas tiles and from the art manifest. Preview analysis no longer lists it, and the exported CMO3 therefore does not have that layer.
- When a mouth is split into layers, the lips it generated are kept. When what is split is the lips themselves, those lips are superseded.

**Edits after a part**: a part is an ordinary source layer. It can be painted, deleted and restored, and split again (a part that is split is superseded the same way). Changing a part's mesh settings appends `canvas_mesh_rebuild` through `MaterializedMeshRebuild`, and migrates the keyforms and the binding. A part is no longer regenerated automatically when the generation rules change.

**Skeleton skinning** (a version 1 part, legacy replay): the skeleton bakes the base rig before the journal, while a part does not appear until the record is replayed. Looking at the base rig alone, a bone-bound part does not exist (a leg or a shoe split out of a combined left-and-right drawing is therefore not skinned, and a leg bone is left with parameters that have no keyforms). So the skeleton stage (`RigBuilder`) first decodes the bone-bound parts from the record (`ArtPrimitiveReplay.skinnable`: canvas-unit texture coordinates, with no tiles and no masks), bakes them together with the base rig, and then takes the skinned parts, and the Glue the bake added for them, back out of the base rig and stores them in `BuiltRig.primitiveSkins`. The base rig still contains only the superseded original mesh, and the journal from before the record replays as usual. When the record is replayed, the skinned result is used instead of decoding it again (the parent is a bone deformer, the texture coordinates are converted through the current atlas, and the masks are taken from the record). Glue whose both ends are already in place is added afterward. The following parts are still decoded by the record itself: a parent or a keyform parameter that has to be created by an earlier journal entry, and a part that has a path or a vertex group (the bake does not migrate those onto a vertex it added). When the recorded parent is no longer produced by base generation, decoding reparents it by [When the parent is no longer generated](#when-the-parent-is-no-longer-generated). A replay checkpoint includes the `primitiveSkins` instance in its key. `RigEditOverlay.applyTo` / `authored` and a simulation bake both have to be given it (`authored(BuiltRig)`).

**Ownership**: a part belongs to the edit-journal node (the `rig:authored` that `journal` owns). It is not listed on its own in the generator dependency graph. Swing and simulation read it as usual. A `generated_override` that used to sit on the superseded mesh loses its target and is reported as orphaned.

**Referring to a superseded ID**: when a reference field of a document operation (`layer_id`, `target`, `source_id`, `middle_ids`, `meshes`, and similar) points at a superseded layer or mesh, it returns an error and lists the current IDs that replaced it (unfolded level by level across several splits). `source_get_components` does the same. `layer_restore` cannot bring the original layer back (it is not in `deletedLayerIds`).

**Compatibility**: an old `canvas_source_partition` or `canvas_depth_split` is replayed by the original rules, and it is checkpointed on the first edit (see [Legacy replay](#legacy-replay)). `LegacySplitReplayTest` uses a project saved by an old version and checks that the IR hash of each history node after replay matches the old version. An original layer that an old project soft-deleted can still be restored. A new split on an old project follows the materialization rules. A split of a model imported from CMO3 still uses the old rules (the original layer is soft-deleted).

### When the parent is no longer generated

A deformer that the journal created before some record exists again when replay reaches that record. So if the recorded parent is missing at the replay position, the only possibility is that base generation no longer produces it: the generation settings were changed after the split (after the skeleton is enabled, the arm-hang Warp `DeformArmHang_L/R` is no longer generated, and bones take over the arms). The record is then replayed by the rules below. The stored record is not rewritten. The rules are implemented by `VanishedParent` and by each record's replay, and the result is deterministic:

- **A version 1 part** (`ArtPrimitiveReplay.rehome`, legacy replay): the part is reparented to the parent that the mesh it replaces (the key in `replace`) currently has. When that mesh is itself a part from an earlier record, and the base rig does not yet contain it at the time the skeleton bake decodes (`earlier` of `skinnable`), the search continues forward along that record to the mesh it replaces. The position is restored to the canvas position at the default pose by a least-squares affine fit of "recorded vertices → canvas texture coordinates" (exact for a regular rest mesh or a rigid frame), and then inverted into the new parent space. The displacement of a keyform and of a blend shape is converted to a canvas displacement through the linear part of the fit, and moved in the same way. When the replaced mesh cannot be found, it still errors with `Art primitive parent is missing`.
- **`canvas_mesh_rebuild`** (`RasterMeshJournal.replay`): the mesh is already in another parent space, and the geometry fingerprint can no longer be checked. Only the vertex count is checked (the length of `glue_map`). The recorded `points` and `previous_parent_points` are moved into the mesh's current parent space by the same affine fit.
- **A structure edit `bind` (a mesh) and `move` (a deformer)** (`RigStructureEdits.replay`): when the target parent is missing, that item does not take effect, and the object stays where it was. A newly committed edit goes through `RigStructureEdits.apply`, and a missing parent is still an error.
- **`canvas_mesh_create`** has no replaced mesh to follow. When the parent is missing, it still errors.

A mesh that is bone-bound, but that the journal hung under a deformer that is not a bone, is not reparented during the bake. It is skinned after the journal. See [Meshes placed by the journal](#meshes-placed-by-the-journal).

### Meshes placed by the journal

Before the journal, the skeleton bake reparents a bone-bound mesh under the bone's rotation deformer, and both the position and the keyforms are moved into bone space. If the journal later places that mesh itself, a structure edit `bind` onto a deformer that is not a bone, or a `warp` record that wraps it in a new Warp, those records keep the mesh's local coordinates (`space=local`, `fit_local`), and they cannot be replayed correctly on a mesh that is in bone space. Such a mesh is identified by `SkeletonCanvasSkin.placedByRecords` from the skeleton definition and the edits (the old `structureEdits` / `warpEdits` first, then the journal in order; a mesh whose last `bind` is onto a bone deformer does not count), and it is handled by the rules below. When the journal has a checkpoint, the skinning stage also includes a bound mesh in the checkpoint's authored rig that is not driven by any bone of its limb (`SkeletonCanvasSkin.placed` / `unskinned`, except one that is `bind` onto a bone deformer after the checkpoint), whether a record, a regeneration merge, or an old version put it there. The bake decides from the records only. See the checkpointed rig, Structure handoff and merge fidelity.

- **Bake** (`canvasSkinned` of `SkeletonRig.apply`): like the other meshes of the limb, it subdivides joints and welds with the parts of the same limb (`GlueSkel__` Glue), and it is counted in the blend-shape plan. It is not reparented, and it does not write skinning keyforms. It stays under the generated parent. The bone it would have been reparented under keeps its deformer as usual (it is not pruned or collapsed for having no mesh). Because it moves on the canvas with the whole bone chain, the plan treats every bone parameter on the chain as coupled with the others (they are not made into blend shapes). The path of the other meshes is unchanged. A project that has no mesh placed by the journal bakes and exports byte-for-byte the same (`ExportGoldenTool`).
- **Skinning** (the generation node `skeleton.skin`, after the journal and before swing and simulation): the effect of a bone is defined in canvas space. At a pose, each vertex is driven by its weights (`SkeletonWeights` / `SkeletonManualWeights`) and by the bone's canvas transform (`SkeletonPoseSolver.frames`: a bone that has a deformer reads the deformer, and the others rotate by the parent bone), and it is then corrected the same way as the bake, through the joint template, ARAP, and surface smoothing (`SkeletonRig.corrected`). The resulting canvas position is moved into the parent's local space by the inverse of the mesh's final parent chain at the same pose, and the difference from rest is written as the mesh's keyform on the bone parameters. A blend-shape parameter (a bone the plan treats as independent, and a skeleton pose) is written as a blend shape. The axes are the limb bones that move this mesh, the body half above them, and the skeleton pose parameters, and the fewest keys are taken at the same tolerance as the bake. The mesh is not reparented. The journal's placement stays as it is, however many user Warps sit above it.
- **Existing keyforms**: a skinning keyform is added to the mesh's original keyforms (when they share a parameter, the keys of both sides are merged). A canvas edit of these cells is written by `GeneratedOverrides.capture` as a `generated_override` of `skeleton.skin`, and it is three-way merged on replay. A blend shape of the same parameter that the journal already gave the mesh counts as user data and stays unchanged.
- **Glue**: a vertex paired with another skinned mesh takes the same canvas target on every key. When the other end is bake-skinned (hung under a bone), the position the rig evaluates is used. When both ends are skinned by this stage, the meeting point is taken from the weights on the two sides of the Glue, and the two use the same keys on the shared parameters. These vertices are fixed points in ARAP, and the mesh transitions smoothly to the seam.
- **Topology**: joint subdivision happens before the journal, and a later per-vertex record addresses the mesh after subdivision. If the vertex count of a per-vertex record aimed at this mesh in the journal (`canvas_geometry`, `vertex_group_put`, and the mesh's `generated_override`) equals the vertex count from before subdivision (written in a version that did not subdivide this mesh), that mesh is not subdivided (`SkeletonCanvasSkin.lockedTopology`, the same as hand-made topology), so those records do not miss. Another mesh bound by a joint bone is likewise not subdivided when every such record was written at the pre-subdivision vertex count (a vertex group written before the skeleton, and similar). When a record was written at the post-subdivision vertex count, it is subdivided as usual.
- **Cost and cache**: the limb's root bone and the body half above it only carry the whole limb rigidly. The solve leaves them out first and then applies their transform, so the number of solves depends only on the keys of the joints inside the limb. The output is reused by `GeneratorReuse` according to what was read. When such a mesh exists, the skeleton cache key contains its set.

### Version 2 records

Version 1 snapshots the whole authored state, at the moment the original layer was split, into the parts. Base generation still sees only the original layer (the passenger) and does not see the parts. Keyforms a generator wrote into the mesh (eye open and close, skeleton skinning, and similar) are frozen in the record as well, and a later change of face settings, stance, or the skeleton never reaches the parts. Version 2 lets the parts take part in base generation. A split of a generated original mesh always writes version 2. There is no switch. A version 2 record as written now is only a declaration (`authored` is empty, and the user data is in the checkpoint after it; see [A split is a regeneration](#split-materialization-the-art-primitive-record-art_primitive)). A version 2 record written by an earlier version carries author data in `authored`. The residual, the two-pass capture, the passenger tolerance, and the replay described below are about those records, and they are used only in [Legacy replay](#legacy-replay).

**The resolved layer set** (`core/PrimitiveResolution`): generated layers, with the layers a v2 record superseded removed, plus the v2 part layers. Anchors, the face rig, head space, the frame, the stance and the legs, the body frame, deformers (including paired Warps and the arm-hang Warp), the eye whites, meshes used as a mask source, the face rig of the lips, and skeleton binding all read only this set. Preview analysis agrees with it. A part's pixels are the current pixels with transparency padded to `source_bounds`. The mesh still takes the recorded value. Classification takes `layerOverrides` (inherited at the split), or the recorded `classification` when there is none. A context that has a split baseline (`splitBaselineLayerIds`) likewise counts the parts and excludes the superseded layers. A build that preserves deformers (`buildPreservingDeformers`, used by a paint commit) does the same.

**Passengers**: a superseded layer is still generated at its original position (the ID decided by the tag count, and the default draw order, stay unchanged). It uses only its own frozen pixels and its per-layer keyforms. It is read, but it does not feed back into the aggregate stages above, and it is not bound to a bone. It exists only so that a journal entry from before the record can address it, and it is deleted when the record is replayed.

**Parking**: a part is generated in the base rig from the recorded rest canvas mesh (it is not remeshed, and the texture coordinates are canvas units), which produces the generated keyforms, the channels, the masks, the position in the part tree, and the skeleton skinning. After UV binding, the whole of it is moved into `BuiltRig.primitiveSkins` (together with the weld Glue, the generated paths, the generated masks that point at the part, the part slot, the ownership, the deferred parent, and the neutral bounds). A reference in the base rig that points at a part is rewritten to its passenger, so what is seen before the record is the rig from "before the split". `BuiltRig.resolvedPuppet()` removes the passengers and puts the parts in. Generation migration (`RigGenerationMigration.generatedRig`) compares previous / desired with that, so a change of face settings, classification, and similar reaches the parts as well.

**Record fields** (`v: 2`; the other top-level fields are the same as version 1): each part has `id`, `layer_id`, `source_id`, `source_bounds`, `neutral_bounds`, `name`, `classification`, and `mesh{canvas_positions, triangles, canvas_uvs}` (the rest canvas mesh: while the part is still under the original's generation parent, it is converted through the base rig's generation deformer, and an edit the journal made to the parent chain takes effect only once, at replay; when the journal has changed the parent, it goes through the authored parent). An empty `parent` or `part` means to take the generated result, and they are written only when a journal edit changed the original layer. A material field is written only when it differs from the generated value. An empty `masks` means to take the generated masks. `parameters` contains only user axes. `geometry_residual` and `channels_residual`. `blends`, `paths`, and `vertex_groups` contain only user data (not skeleton-pose blend shapes, and not generated paths). `fixed_topology` (true when the part carries per-vertex user data, and the skeleton must not insert a joint row). `frozen_axes`. `glues` contains only user Glue (not the `GlueSkel__` weld).

**Residual**: at capture, A is the authored state of the original layer and G is the base-generation output (including the skeleton). The residual A − G is moved onto the part's vertices through the partition's vertex sources. A cell whose key has a generator axis away from its default is written as a `generated_override` immediately after the record (`base` is the cell of the candidate base part, `points` is `base` plus the residual, and `generator` is the node that owns that axis). The rest is written to `geometry_residual` / `channels_residual`. On replay, the part mesh = the parked generated mesh ⊕ the residual, and overrides are three-way merged as usual after every generator. A part that the base does not generate keyforms for (a zero mesh: a slice of a lip band, a part with a deferred parent) has no generated motion to add back, and the residual takes every keyform of the authored state (A − 0). The mouth parts of one record generate the mouth shape from the opening of all the mouth parts merged together, not from each part's own bounds. Otherwise each half of a mouth would open as if it were the whole mouth, and tear at the cut.

**Replay**: delete the passengers, place the parked parts (canvas texture coordinates are converted through the current atlas, and a deferred parent is moved into its parent space), restore the generated masks and the part slots, add the welds when both ends are present, write the generated paths, and then add the residual and the author layer. When the parked topology differs from the record (the skeleton added a joint row, or a later mesh rebuild), per-vertex data is migrated onto the new mesh by canvas texture coordinates.

**Two-pass capture and the guard** (an earlier version): a split first writes the base fields, then has the candidate base generate the parts, and writes the residual and the overrides against that. It writes version 2 only when the candidate base still generates every object an existing journal entry refers to and the whole journal can be replayed on it. Otherwise it falls back to version 1 and carries `v2_fallback {reason, detail}`. A split now uses the merge instead, and there is no fallback. A `v2_fallback` on an old record is history only.

**Passenger tolerance**: an entry from before the record that fails only because every mesh it refers to is a passenger of a later v2 record is replayed as a no-op, and a note is recorded (`SupersededEntryNote`: the journal index, `op`, the target, and the reason). Any other failure is still an error. The note is saved with the replay checkpoint, a continuation from a checkpoint is complete as well, and it enters `quality.overrides` of `workspace_inspect` through `BuiltRig.supersededEntryNotes` (`SUPERSEDED_ENTRY_SKIPPED`, info, and it does not block).

**Splitting again**: a part can be split again, the same as splitting an ordinary layer. The part in G and the part in M are each cut and then merged. When an earlier version 1 record supersedes a v2 part, that part stays in the resolved set as a transparent placeholder with a fixed mesh, and the base frame does not change.

**Edits after a part**: a paint only replaces pixels, and the part mesh keeps the recorded value. A `rebuild_mesh` paint, or a change of the per-layer mesh settings, appends `canvas_mesh_rebuild` after the record and migrates the keyforms and the binding.

**Ownership and cache**: the document input `document:primitives` of `DocumentGenerators` (the fixed input of a v2 record) is read by footprints, the frame, meshes, and the skeleton. A part's `keyform:mesh:<部件>@<参数>` belongs, by the parked ownership, to `mesh:<图层>` / `rig.meshes` (a feature axis) or to `skeleton` (a bone axis). `GeneratedOverrides.capture` uses that to write a later edit of these cells as an override. The keys of the stage cache and of the binding cache contain the digest of a v2 record's fixed input.

**Compatibility**: a version 1 record written by an earlier version, and a version 2 record that carries author data, are replayed as before when there is no checkpoint after them (including skeleton skinning and decoding them itself). Reading does not rewrite them, and they are checkpointed on the first edit (see [Legacy replay](#legacy-replay)). A document with no v2 record takes the original code path (`ExportGoldenTool` is byte-for-byte the same). A v1 record and a v2 record can be mixed. When a v2 record supersedes a v1 part, it deletes it. When a declarative record is replayed (for example in a build that has no checkpoint), it is placed as the generated parts. The explicit upgrade command of the old version (`source_upgrade_split_records`) has been removed.

**Known limits**:

- The generated lips of a mouth that was split are still taken from the superseded mouth (the passenger's frozen pixels), not from a composite of the parts' current pixels. At the split the two agree. Painting on a part afterward does not make the lip texture follow (the lip texture of an ordinary mouth is likewise taken from the mesh input, and it does not follow until the mesh is rebuilt), and rebuilding a part's mesh does not regenerate the lips either.
- `frozen_axes`: the writer always writes it empty, so it does not occur now. When base generation reads a non-empty value, if the generated mesh's axes include an axis that was frozen, that part's whole generated mesh is zeroed and only the author data is kept. Legacy replay errors immediately on a non-empty value (it is not supported).
- After a part mesh is rebuilt, a `generated_override` aimed at one of its generated cells is not migrated. When the shape does not match, it is reported as orphaned.
- When the mouth outline is on, the fixed mesh of a mouth part is the original's outline mesh, and the footprint differs slightly from the original's raster mesh. The rest position of the generated lips, which the mouth box determines, differs by about 0.4 px. The opening shape of the part itself does not include the outline's contribution (about 0.13 px).
- A v2 part takes part in frame generation. The canvas position of a fixed mesh has floating-point rounding on the trip through the parent. The local coordinates of a mesh that was not split, and the frame's control points, can differ by a few ulp (world coordinates < 1e-4 px). Version 1 is unchanged bit for bit.
- When the original mesh's topology was edited by hand, the parts are kept as user objects with the user's topology, and a later change from a generator no longer reaches the geometry of these parts.

**Tests**: `PrimitiveResolutionTest` (base generation of a hand-written v2 record), `ArtPrimitiveRecordV2Test` (encoding of an old record, the residual, replay, passenger tolerance, and the note when continuing from a checkpoint; the encoder in the test is `LegacyArtPrimitiveV2`), and `SplitPartsCheckpointTest` (a split's checkpoint, paired Warps, and skeleton skinning). The look of a split on tml is checked by eye with `ArtPrimitiveV2VisualTool` (the difference between unsplit and split at each pose, the same as the version 2 records from before).

## Legacy replay

An earlier version wrote some edits as records that have to be replayed on the base rig: a split's `art_primitive` (version 1, and version 2 that carries author data), generation migration (`rig_generation_transition`, `rig_generation_frames`, `rig_generation_scaffold`, `rig_mesh_activation`), the old `canvas_source_partition` / `canvas_depth_split`, and the old-format static fields from before the journal. A generated model no longer writes them. A model imported from CMO3 has no generated result to merge, and it still writes the migration records and the old partition, but the commit that writes them immediately writes a checkpoint of the imported model after them (`WorkspacePreviewBuilder.importedRecordsCheckpointed`). The records are replayed only in that build. A later build, an open, and an undo all start from the checkpoint. `core.legacy` therefore runs in only two places: before an old journal that has never been checkpointed is edited for the first time, and in the one commit where an imported model writes this kind of record.

- **Checkpointed only once**: when the journal still has this kind of record after the last checkpoint (and, when there is no checkpoint, this includes the old-format static fields, `RigEditOverlay.replaysLegacy`), the first edit that continues it first writes a checkpoint of the current authored rig at the end of the original journal, before the new entries (`WorkspacePreviewBuilder`). The generated snapshot is saved along with it when it is on hand. These records are replayed for the last time, and every later build starts from the checkpoint. Opening, switching history, and saving do not rewrite the journal. An old revision still builds from the records.
- **Code**: the parts used only on this path and on an imported model are in `core.legacy`: `ArtPrimitiveReplay` (replay of a version 1 record and of a version 2 record that carries author data, decoding a version 1 part before the skeleton bake, and placing a version 1 part during a regeneration merge), `StubTolerance` and `SupersededEntryNote` (passenger tolerance), `VanishedParent`, and the writing and replay of generation migration (`RigGenerationMigration`, `RigGenerationJournal`, `RigGenerationFrames`, `RigGenerationScaffold`, `RigMeshActivation`, `RigGenerationResidual`, `RigGenerationTextures`). `ArtPrimitiveJournal` keeps the record format and the document queries (the supersede relation, the layers it owns, and the texture coverage). `RigGenerationChange`, which decides whether an edit changes the generated result, is the trigger of the merge path, and it is in `core`. The merge (`RigRegenerationCheckpoint`) still reads, from `core.legacy`, the names an old migration record gave deformers, and the version 1 parts, so that G and G′ of an old journal are placed the same way. These are compatibility reads. They are not extended with new features (`LegacyReplayBoundaryTest` fixes the files that may refer to it).
- **Lock**: `LegacySplitReplayTest` uses a project saved by an old version and checks the IR hash of each history node built from the records.

## Follow-ups

- The remaining time of a classification change is in analysis. A generated model no longer goes through generation migration once it was changed to merge, and what is left is the migration of a model imported from CMO3, and the split baseline running `CharacterAnalyzer.analyze` again on a new raster (per-layer classification is about 0.5 s each). The classification result can be cached by layer metadata and the raster digest.
- Overrides of simulation keyforms that are written back as blend shapes. After the override report is brought into the unified quality-check framework, it switches to that framework's rule registry and fences.
- Known limits of channel overrides (no generator currently keys a channel after the journal, so this path does not fire; handle these before the first such generator is added):
  - When a keyform `set` is written on the rest cell of a generated channel track (the generator's parameter in the key is at its default), `journalOnly` strips a generator's axis at the default only for a geometry edit. The key of a channel edit still carries that axis, and journal replay builds that axis on the user's own track.
  - A version from before channel overrides were added reads every override as vertex or control-point coordinates, and it requires an even number of values. Both a scalar override (1 value) and a color override (3 values) report "Invalid override form", and a project that contains a channel override fails to replay in an old version.
- Reading the checkpointed result directly when a project is opened: saving and reading the authored rig, checkpoints, the regeneration merge, and the trial run are all implemented (the checkpointed rig, Implementation progress). A model imported from CMO3 replays from the checkpoint on the import baseline. It is not built from the authored rig on its own.


## Interior-effect generators

An optional `interiorEffect:<id>` node runs after the author journal and before generated-result overrides. `NativeInteriorEffect` stores the recipe, the compact native blend fields, and the physics group in `rigEdits.interiorEffects`. An existing input parameter is read-only. A generated parameter and a target mesh axis have a single owner. Changing the recipe, adding or deleting one, and the switch all take part in invalidation. When the mesh, the artwork, or the binding does not match, the recipe is kept and stale vertices are skipped. The native UI and MCP share `interior_put`. A temporary trial does not enter the document. Idle owned parameters of a disabled or invalidated effect are cleaned up only in the export copy. An unpublished dense experiment does not keep compatibility. Deletion goes through `interior_delete` into the same replay chain. See interior effects.
