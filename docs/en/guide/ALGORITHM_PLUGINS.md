# Algorithm plugins

> **Single version and a shared runtime architecture**: The binding modifiers currently bound use the canonical facade `version = 1` (`rig.scaffold` keeps `v1` and `v2`). `:algorithms:binding` produces, through the `pluginPackages` task, one shared `shared/runtime.jar` (entry `ExpressionWorker`) and a light `<slug>/plugin.json` manifest for each type. The types and the manifest count follow the declarations in `algorithms/binding/build.gradle.kts` and the generated `index.txt`. The host pools resident worker processes by command and file digest, and caches input and context resource hashes. An external plugin can still implement the `protocol: 1` worker protocol in any language.

Each modifier in a preset is evaluated through the algorithm interface. A built-in algorithm runs inside the application process. An external algorithm is a resident worker process, and it can use Python, Kotlin, Rust, C, C++, or C#. An install package can contain several algorithms.

Built-in algorithms are listed in the plugin catalog separately by type and algorithm revision. Each can be enabled and disabled on its own. Swing, simulation, physics, motion, expression toggles, see-through brows and eyes, skin clip, and the binding structure each have their own Kotlin implementation entry. A new instance records the `builtin.*` package identity, the full version, and the content digest. An algorithm that has already been packaged on its own covers the full package. The other entries still use a bytecode digest. When the digest does not match, it is shown as unavailable. It is not replaced automatically. A built-in instance in a historical project that has no plugin reference continues to be read by the original algorithm revision. History is not rewritten on open. `id=builtin,digest=builtin` is only the whole-catalog enable and disable compatibility entry of the old interface.

An external package can refer, in `dependencies`, to a built-in package ID and version returned by `plugin_list`. Install locks the same content digest. When a built-in item is disabled, or the matching version is missing, the dependent package is unavailable too. The `builtin` identity as a whole is kept. A `builtin.*` install package must declare a stable type alias that matches the package ID and the algorithm revision, so a historical built-in algorithm can be restored. Enable and disable state is stored in preferences. Evaluation reads a memory snapshot. It does not touch system preferences item by item.

The application ships modifier packages that can run on their own. The full type range is the built-in package index the build generates. A historical instance continues to replay by the locked revision. Some recommended presets still use v1 and extract the result from a host-generated template. Some newer versions also still receive prior motion or a local front/back projection generated by the host. A package that can run on its own, and a call that has no whole-model template, cannot by themselves prove that the original source-input boundary has finished migrating.

Gradle's `processResources` generates the built-in package index from the `bundledAlgorithm` resource declarations. When a built-in package is added, declare its task and resource directory in the build. The application reads the package manifests from the generated index. An existing package's manifest and payload still compute the digest from the original bytes.

For two-eye artwork where a fitted brow changes the coordinate frame of other meshes, creating a modern preset selects a compatible version together for the head, the eyes, and the brows. Fitted brows, brow shape, brow-lid coupling, blink-with-brow, and bounce are evaluated together on the shared frame. Smiling eyes, wide open, gaze, emotion, highlights, aftershock, and iris squeeze also have matching versions. Eyelid fade stays on v3. A saved instance replays by the algorithm revision and package digest locked in the project.

The physics-group implementation has moved to `:algorithms:physics`: `PendulumAlgorithm` implements the public evaluation interface directly. Configuration parsing, physics-group conversion, and the output-conflict check are all done in that module. The algorithm uses only `algorithm-api`. The application registration entry only delegates the call. Ordinary physics export and the other generators reuse the same conversion implementation. `algorithm-worker` also provides the worker entry. `./gradlew :algorithms:physics:pluginPackage` generates a standalone install directory at `algorithms/physics/build/plugin` (`plugin.json` and `algorithm.jar` carrying its dependencies), which can be given to `plugin_install`. The package ID is `builtin.70687973696373.v1`, the entry is `/pendulum` under that namespace, and `aliases: ["physics"]` keeps the type, the algorithm revision, and the output ID in the project.

The application carries and keeps the full install packages for physics groups, motion, swing, baked simulation, expression toggles, see-through brows and eyes, skin clip, and the binding structure. A new instance fixes the content digest of the whole package. When it matches the current package exactly, it runs in process. An old package reference runs through a worker only when the matching content is installed. It does not fall back to the current implementation. An old-version install package can be uninstalled and reinstalled. The version the current application ships can only be enabled and disabled. A development-period reference that recorded only the entry bytecode digest before the migration is not rewritten, and it cannot be replaced by the new package. When the original content cannot be found, it is still reported as unavailable.

The motion implementation has moved to `:algorithms:motion`. The package ID is `builtin.6d6f74696f6e.v1`, the entry is `/clip`, and the stable alias is `motion`. `MotionData` provides the data model of the original format, JSON read and write, and curve conversion. The application editor and the standalone worker share this implementation. The module does not depend on the playback session, the UI, or Umamo. The build command is `./gradlew :algorithms:motion:pluginPackage`, and the output directory is `algorithms/motion/build/plugin`.

The swing implementation is in `:algorithms:swing`. The package ID is `builtin.7377696e67.v1`, the entry is `/sway`, and the stable alias is `swing`. Mesh wrapping, keyform evaluation, and the swing physics group are all done in the algorithm module. It does not call project or history interfaces. This module uses the GPL Umamo engine and the general IR conversion bridge `:umamo-ir-bridge`. It is a GPL algorithm. It cannot be distributed as an MIT API / format module. It does not contain the Cubism proprietary SDK. The build command is `./gradlew :algorithms:swing:pluginPackage`.

Baked-simulation evaluation is in `:algorithms:simulation`. The package ID is `builtin.73696d756c6174696f6e.v1`, the entry is `/baked`, and the stable alias is `simulation`. The input contains the original bake result and the captured automatic weights. The plugin checks that the bake matches the upstream input, then writes back the weights, the pattern keyforms, and the physics group. Existing author weights win. A missing or stale bake is not allowed to generate an incomplete result. Numeric baking is still done by the original flow. This migration does not change the solver. This module also depends on the GPL engine. The build command is `./gradlew :algorithms:simulation:pluginPackage`.

An algorithm manifest can declare `derivedOutputs`, used to keep the original deterministic object names. Each rule contains `kind`, `localName`, `prefix`, `suffixes` (default `[""]`), and `numbered` (default `false`). The host accepts only `prefix + instance.outputId(localName) + suffix`. When `numbered` is on, it also allows the canonical decimal suffixes `_2` through `_10000`. A rule cannot cross object kinds or write outside the declared range. An arbitrary regular expression is not accepted. Swing uses the `Warp_Swing_` and `PhysicsSwing_` rules, and keeps the original project object IDs.

## Writing a plugin

The JVM contract has been split into the standalone `:algorithm-api` module. The application and the plugins share the same declarations. It depends only on the neutral `:format-model` and the JSON serialization library. It does not depend on the application, Umamo, Compose, the project, or history. `./gradlew :algorithm-api:build` generates the API JAR and the sources JAR at version `1.7.0`.

`ModifierAlgorithmPlugin.evaluate(input, instance, checkpoint)` receives the upstream `RigIR`, the immutable `RigModifierInstance`, and a cancellation-check function, and it returns a candidate `RigIR`. An implementation must not modify the input arrays in place. A long loop must call `checkpoint`. An exception is handed back to the host as it is. Object identity uses `instance.outputId(localName)`, compatible with existing aliases. The host is still responsible for output validation, dependencies, overrides, CAS, and the history commit. The API also exposes target references, the fixed package reference, the manifest, the version range, and the dependency declarations. The original JSON fields, the serialized type names, and the object-ID encoding stay unchanged.

The API JAR itself is not an installable algorithm package. Compiling the contract on its own does not mean the built-in implementation has moved out of the application. Loading of built-in packages and retention of historical implementations are still handled by the migration status above. The external six-language workers continue to use the versioned protocol below.

### JVM model-result adaptation

`algorithm-worker` can place a `ModifierAlgorithmPlugin` in a resident JVM process. The entry calls `AlgorithmWorker.run(mapOf((type to version) to implementation))`. It does not need to depend on the application, the editor, or the project. Standard output is used only for protocol responses. The request's `invocation` provides the full instance information (including the persisted output alias). The original `instance`, `config`, and `targets` fields stay compatible with other languages.

After the host declares `rig_objects` in `capabilities`, the worker can return `objects` instead of `commands`. The two cannot appear together. `objects` must contain exactly `changed`, `removed`, `mesh_order`, and `deformer_order`: taking the request input as the baseline, it lists only the changed resource references `frame`, `mesh:<id>`, and `deformer:<id>`, and the keys that were deleted. Resources use the `RigIrObjects` binary format. A reference contains `sha256` and `bytes`. A single resource is limited to 64 MiB, and the total is limited to 512 MiB. The host checks the digest, the size, the object type, and the ID. It does not accept a path as a resource reference.

The host merges the object difference back into the full upstream input, so unrelated content that was trimmed by the read and write declarations is not lost. It then checks the structure, the numbers, the declared write types, and the output IDs, and then enters the candidate, override, and transaction flow. The in-process call and the worker call the same algorithm implementation. The host no longer re-runs that algorithm through a physics configuration command. Binary result adaptation does not change the command-output protocol other languages already have.

The six-language sources and the packaging tools are in [examples/plugins](../../../examples/plugins/README.md). `plugin.json` at the package root declares:

- `protocol: 1` or `protocol: 2`, and the package `id`, `version`, and `name`.
- `commands`: an argument array keyed by a platform identifier such as `windows-x86_64`. A JVM package uses `jvm: ["$JAVA", "-jar", "worker.jar"]`. It does not go through a shell.
- `files`: the relative path and SHA-256 of each payload. A path that escapes, a symbolic link, and a file that is not listed are forbidden.
- `algorithms`: an algorithm type must start with `包ID/`. It declares the algorithm version, the name, the targets, the dependencies, the exclusions, the read and write ranges, the writable types that can be combined, `configSchema`, and `defaults`.
- The optional `parameters` declares `id/name/min/max/default` of a shared standard parameter. The definition must be compatible with an upstream parameter of the same name. Other new objects use the ID the instance owns.

`protocol` is the communication-protocol version of the worker. `version` at the root of `plugin.json` is used to resolve install-package dependencies. The integer `version` in the algorithm list, together with the type, identifies the executable entry. For example `mouth.outline@4` means version 4 of the stroke algorithm. The project locks both the algorithm entry and the install package's version, content digest, and dependency lock. After a package upgrade, an existing instance continues to use the entry locked at save time.

`protocol: 1` uses one line of UTF-8 JSON for each request and each response. A binary resource is a SHA-256 file reference under the `PSD2LIVE_PLUGIN_RESOURCES` directory (`{"sha256": "...", "bytes": N}`). `protocol: 2` (for native binaries and high-performance plugins in several languages, such as Rust/C++/Zig/Go/Python) uses binary-framed standard input and output with no temporary files and zero SHA-256 disk I/O: `[u32le headerLen][UTF-8 JSON header][u32le blobCount]([u32le keyLen][UTF-8 key][u32le dataLen][bytes])*`. A binary reference becomes the inline key `{"inline": "<key>", "bytes": N}`. The host tells the worker through the environment variable `PSD2LIVE_PLUGIN_PROTOCOL=2` when it starts the process. Under both protocols, standard output is used only for protocol transfer. Logs are written to standard error. A request contains `protocol/id/method/type/version/instance/config/targets`. A response echoes `protocol/id` and returns `commands`, `objects`, `changes`, or `error`. The same worker handles requests serially. After a fault or a timeout the process is rebuilt. Cancelling a request that is running terminates the process. Its partial result is not committed. A request that is queued can be cancelled on its own, without interrupting another request that is running. Cancellation is also checked while waiting for a response.

The model input is trimmed by the declared read and write components. An unknown range or `*` uses the full input, conservatively. `changed` and `removed` keep the object index in sync. `reset` means a fresh session. The values of `frame`, `mesh:<id>`, and `deformer:<id>` are resource digests. The resource directory is provided by the request and by `PSD2LIVE_PLUGIN_RESOURCES`. Resources use the versioned exact binary format of `RigIrObjects`. `mesh_order` and `deformer_order` keep the order.

A later request reuses mesh and deformer binary resources that did not change. A new object is encoded first, then the content hash decides whether it is sent.

The portable view `meshes` provides the target mesh ID, the opacity, and references to the position / UV buffers. `parameters` provides the parameters declared readable. The float-buffer format is little-endian `f32le`. The file name equals the SHA-256. A float array in a returned command can also be represented by that reference. The host checks the digest and that the numbers are finite, then expands it.

Returned commands support:

- `mesh_opacity`: the target mesh `id` and a `value` in the range 0–1.
- `physics` and `motion`: `config` uses the configuration format of the matching built-in modifier. The output ID is managed by the host.
- Edit primitives: `structure`, `set`, `parameter_keys`, `delete`, `canvas_geometry`, `canvas_topology`, `canvas_create_warp`, `canvas_create_rotation`, `canvas_create_glue`, `canvas_glue_edit`, `path_put`, `path_delete`. They follow the format of the author edit records. They run only inside an isolated candidate. They do not write history directly.

A new object ID is `modifier:<实例ID>:<局部名称的UTF-8十六进制>`. The host checks the actual write range, shared parameters, dependencies, overrides, and conflicts. A plugin must not operate on the document, the history, or the GUI directly.

## Performance limits

Algorithm generation, worker communication, and synchronous bake timing are different measurements from the time from capturing a revision to the offscreen GPU readback, and from model-activation capture to the window GPU finishing. The development tools, the modes, and the exclusion range of the latter two are in [Development tools](DEVELOPMENT.md#development-tools). They cannot be added together and treated as the full edit latency.

A built-in algorithm is called directly. It does not pay cross-process serialization. An external plugin reuses the process, transfers buffers by content address, and syncs the input incrementally. The author's base input, the binding's intermediate templates, and the results of algorithms whose dependencies can be declared are cached separately. A folder adjustment does not trigger algorithm evaluation.

This round of acceptance checks standalone algorithm generation, output equivalence, and history replay. Performance work happens after the migration is finished. The diagnostic tools continue to record the time of the first generation and of a repeat generation, and they list the synchronous bake time on its own.

Some built-in bindings still extract the result from a generation template. When the declared read and write ranges of neighboring built-in algorithms do not overlap, and the dependencies are already satisfied, the host can compute the changes in parallel. The host rechecks the actual read and write preconditions in stack order, then merges the results. Other algorithms continue to evaluate in order. The first generation and a repeat generation are timed separately.

## Versions and dependencies

The three version layers are independent. `protocol` is the communication-protocol version. The package `version` is a `主.次.修订` version. The algorithm `version` is the persisted integer revision. The algorithm integer stays compatible. It is not renumbered because the language it runs in changes. A package version supports `1.2.3-rc.1+build.7`. The build metadata does not take part in ordering. The full package content is still distinguished by the digest. An integer version of an early package is compared as `N.0.0`. A new package should use a full version number.

A package's `dependencies` declare code prerequisites. `conflicts` declare package versions that cannot be enabled at the same time. They differ from an algorithm's `requires`: the latter requires that the stack already has an algorithm result for the same target. It does not install or start another package.

```json
{
  "dependencies": [
    {"id": "geometry-core", "version": {"minimum": "1.2.0", "maximum": "2.0.0"}}
  ],
  "conflicts": [
    {"id": "other-cloth", "version": {"exact": "1.0.0"}}
  ]
}
```

- `minimum` includes the boundary. `maximum` does not include the boundary. `exact` cannot be combined with a range. Omitting `version` means any version. A prerelease version is ordered by numeric / text segments. Prerelease versions are not excluded implicitly.
- On install, the highest enabled version that satisfies the range is chosen, and the full transitive dependencies are locked. A missing prerequisite, a cycle, or a conflict refuses install / enable. Dependencies are not downloaded automatically, and other plugins are not turned off.
- The conflict check is two-way. A declaration on one side is enough to take effect. Different versions can coexist, but an explicit conflict still blocks enable.
- The host saves the install dependency lock. A project's plugin reference saves `dependencyDigests` (`包ID@版本` → content digest). Installing a newer version later does not replace an old instance's dependencies.
- Disabling / uninstalling a prerequisite stops the worker. The downstream is kept and becomes unavailable. After the original content is restored, it is available again. When the same package is reinstalled but resolves to different dependencies, the old project reference stays unavailable. It cannot be upgraded silently.
- `plugin_list` and `plugin_inspect` return `available/issues/dependencies/conflicts/resolved_dependencies`. `enabled` only means the user's switch. It cannot stand in for `available`. The preferences panel also shows the concrete reason it is unavailable.

A dependency is not a function call across plugins. Algorithms cooperate through the upstream model content and the algorithm `requires`. `dependencies` in the request provides the locked package identity. It does not expose project objects or another worker's handle.

## Lower-level capabilities and module boundaries

`:algorithms:binding`, `:algorithms:swing`, and `:algorithms:simulation` share `io.github.psd2live.bridge.PuppetIr` of the GPL module `:umamo-ir-bridge`. They do not obtain the general conversion capability through `:targets:cubism`. The bridge depends only on `:umamo` and `:format-model`. Target downgrade, compilation, and writing still belong to the export targets. The MIT `:algorithm-api`, `:format-model`, and `:format-compile` do not depend on this GPL implementation.

| Layer | Responsibility |
| --- | --- |
| `ModifierAlgorithmPlugin.kt` | The serializable contract of packages, algorithms, targets, parameters, and version relations |
| `ModifierPluginDependencies.kt` | Version comparison, range matching, the dependency graph, and conflict diagnosis |
| `ModifierPluginStore.kt` | Validation, atomic install, the dependency lock, disable, and uninstall |
| `ModifierPluginWorkers.kt` | Resident processes, cancel / timeout, incremental input, and binary resources |
| `ModifierPluginOutput.kt` | Runs the lower-level commands on the candidate model, and validates the actual write range |
| `RigModifierEvaluator.kt` | Stack meaning, shared parameters, overrides, contributions, write conflicts, and the result cache |
| Application layer | GUI / MCP operations, background jobs, CAS, and the history commit |

`capabilities` in the request lists the commands the host supports. The lower-level operations include:

| Purpose | Command | Main write range |
| --- | --- | --- |
| Parameter creation, ranges, folders, relations, object parent and child | `structure` | `parameter/hierarchy/relations/mesh/deformer/part`, declared by the actual change |

For example, there is currently no command for an external plugin to create a texture resource directly. Input whose subdivided fields were not declared uses a conservative cache. Its independence is not inferred.

A weight-command example (the array length must equal the mesh vertex count; a buffer reference with `bytes/count/format/sha256` can also be used):


The detailed fields of a command follow the matching author edit primitive. The host runs the same validation. Bypassing a model-edit invariant is not allowed.

Every command runs in order inside an isolated candidate first. The evaluation result is returned only after the output is validated. Attached data (author content such as weights and paths), textures, the canvas, and the render hierarchy also take part in the actual write check and the conflict report. A package cannot declare only `mesh` and then modify author weights through a command. Process isolation does not provide a security sandbox. A plugin is still local executable code the user installed.

### Structured change interface (JVM API 1.3)

`ChangingModifierAlgorithmPlugin.changes` returns `ModifierModelChanges`. Parameters, parts, deformers, meshes, physics groups, and motions that have a stable ID use `ModifierObjectChanges` to state add, update, delete, and reuse explicitly. An update and a delete carry the expected old object. They cannot rewrite object identity. Other single values or ordered relations use `ModifierFieldChange`, which distinguishes “do not modify” from “change to null” explicitly. A field or buffer that is not involved keeps its reference.

Before applying, the host checks the part that was actually written with `changeWrites`, then checks the object's prior state. A repeated operation, an add of an ID that already exists, and an old value that does not match are all refused. Apply produces only an isolated candidate. It does not commit the project. `contributions()` currently reports object-set operations. It does not include the full user contribution of single-value fields. The formal contribution, the reference check, the override, and the transaction still go through the existing host flow. The physics-group algorithm already uses this entry.

After an external worker negotiates the `model_changes_v1` capability, it returns `changes` directly. It does not materialize and encode the full output. A host that did not declare that capability still receives the original `objects` response. Exactly one of `commands`, `objects`, and `changes` must appear. The outer protocol is still 1.

`changes` strictly contains `schema`, `before`, `after`, `objects`, and `fields`. `schema` is `model_changes_v1`. `before` / `after` are binary resource references with a SHA-256 and a byte count. They use the existing RigIR binary version 6. They store only the objects and fields involved. They do not contain an unchanged mesh. The keys of `objects` are `parameters`, `parts`, `deformers`, `meshes`, `physicsGroups`, and `clips`. Each value is arranged as `[新增数, 更新数, 删除数, 复用数]`. The prior payload order is delete, reuse, and the old objects of updates. The result payload order is add, and the new objects of updates. The total number of object operations is limited to 10000. Each payload is limited to 64 MiB.

`fields` lists the single-value or relation fields that were replaced (the field names match `ModifierModelChanges`). A listed field takes its value from the before and after payloads. An explicit replacement with null is allowed. The JVM encode and decode helper is `AlgorithmChanges`. The host checks the version, the key set, the counts, resource integrity, the write range, and the old object's preconditions, then runs the existing full reference and output-validity checks. Write names in an install-package manifest follow the existing catalog vocabulary, such as `textures` and `glue`.

The current physics package has been measured for cross-process install, repeated evaluation, reopen, uninstall, and reinstall equivalence. Other languages can still use the existing command protocol. A one-by-one implementation and acceptance of the new change payload in the six languages is not finished. The host still runs the full contribution comparison. The read-only input view, worker read tracking, and generated images are in the matching sections below.

### Capturing source artwork (JVM API 1.4)

`ModifierSourceInputs` expresses the source artwork from before generation through `source_layers/1`. It does not contain a generation template or a host callback. `ModifierSourceLayer` stores the stable source ID, the semantic tag / side / role, the top left of the source canvas, the width and height, the observation bounds, the centroid, the opaque pixel count, and the RGBA resource name. `targets` maps a stable model target ID to a source ID. An image is non-premultiplied RGBA8, starting at the top left, row by row, with no padding. Source-artwork coordinates are pixels and Y is downward. The observation bounds and the centroid use that space too.

`to_model` is the serializable affine matrix from the source canvas to the model canvas, `xx, xy, tx, yx, yy, ty`. It supports mirroring and refuses a singular matrix. It is not a parent-deformer space transform. `raster(layer)` provides a cached read-only view. `alpha(x,y)` returns zero outside the bounds. `rgba()` returns an independent copy. A resource has a content digest, and it can reuse the existing `author_context_v1` transport. Construction checks duplicate source IDs, target references, finite coordinates, sizes, and the RGBA length. Each image is limited to 64 MiB, and the context total limit is observed.

`context()` / `from()` encode and decode this snapshot. The host `RigSourceCapture` captures only artwork that already exists and the classification result. Eye-contour fitting now reads this contract directly in the standalone binding module. The host adapter keeps the original coordinate-transform call. An independent consumer can use `to_model`. It does not need the product types. This only replaces the input boundary and where the fit is implemented. It does not change the motion design, and it does not mean the geometry generation, combination, and packaging of the eye modifiers are finished.

This snapshot is currently a raster observation input. It does not contain an independent mask resource, a parent-space geometry view, an upstream capability snapshot, or read-set tracking. Those still belong to later framework work. Handling of a source mask keeps the artwork's original meaning from before the call. This interface is not claimed to express the whole artwork chain on its own.

### Evaluation by read objects (JVM API 1.5)

The entry of `ReadingModifierAlgorithmPlugin` receives `ModifierEvaluationInput`. It cannot obtain the whole `RigIR` directly. `parameter(id)`, `mesh(id)`, `deformer(id)`, `part(id)`, `physics(id)`, and `motion(id)` record the object that was read. An object that is not found is also recorded as one observation. If that object appears later, the cache is invalidated. When a read set or another whole field is read, the full value of that field and its order are recorded. `context` is currently tracked as the full context.

`parentsOfMesh(id)` returns the deformer chain from the direct parent outward, keeping the local coordinates each of them declares. It reads the target and every ancestor. It refuses a cycle, a missing parent, and a duplicate identity. It does not automatically mix points from different spaces. Actual coordinate transport continues to use the binding module's coordinate algorithms.

`reads()` gives the independent read snapshot of that call. The host caches, for the new entry, the instance configuration, the plugin implementation identity, the author context, the read set, and the structured changes. After an upstream change, it is reused only when the values that were read still match and the output-write preconditions are still satisfied. If a precondition changes, it is computed again. Reuse still goes through the write-range check, the override, the contribution conflict, and the transaction flow. A failed or cancelled candidate does not replace a successful snapshot. The physics plugin currently reads only the parameters and the physics configuration it actually refers to. It does not read all of the geometry.

A run failure of a plugin that has not been baked is isolated per instance: a failed instance does not publish geometry, physics, or object ownership. Its dependents pause. An independent instance continues to evaluate. Initialization, editing, and simulation baking use the same principle. A valid document command can commit a modifier stack that carries a failed state. The error is shown in the modifier panel. Correcting the configuration or enabling it again can retry. A batch command still commits only one complete history node. An invalid request, a cancel, a state conflict, and a change that cannot preserve content that has already been baked still reject the whole commit.

The in-process cache checks the instance, the algorithm implementation, the captured context, and the values that were actually read. The cross-process read set and the reuse conditions are in the matching section below.

### Explicit upstream capabilities (JVM API 1.6)

`provides` in the algorithm manifest declares the capability aliases it provides. `requires` can refer to an algorithm type or a capability alias. The cycle check covers both. A package's semantic-version dependencies are still handled by the manifest `dependencies` / `conflicts`. They are not mixed up with an instance's execution prerequisites.

`ModifierAlgorithmContext.upstream` stores the prerequisite capabilities the host resolved. Each `ModifierUpstreamCapability` contains the requested capability name, the actual algorithm type and algorithm version, the prerequisite instance ID, the target reference, the baked configuration, the output alias, and, when it is known, the full package reference (version, content digest, and the dependency content lock). The host chooses only an earlier / already baked provider that satisfies the consumer's target and the explicit provider choice. When an old record lacks the package reference, it stays null. The currently installed version is not guessed. Applying a prefix keeps this identity information. Baked content continues to satisfy downstream dependencies.

`ModifierEvaluationInput.upstream` / `providers(capability)` include these inputs in the read set and in the cache-invalidation decision. The schema of ordinary source-artwork `values` stays unchanged. The upstream snapshot is passed separately. An external algorithm receives the upstream input only when the manifest declares `contextVersion: 2`. An old manifest defaults to 1. When the context has no upstream data, it continues to encode v1. When it has upstream data, it encodes v2, and besides the original `version`, `values`, and `resources` it adds an `upstream` resource reference. Metadata is limited to 1 MiB. A v2 receiver also reads v1. An old package is not forced to be sent v2.

The plugin description shared by the GUI and MCP adds `context_version` and `provides`. The result schema declares these two fields in sync. Capability-alias resolution, cache invalidation when the upstream configuration changes, a prefix apply keeping the capability, save and restore of the package identity, and v1/v2 context encode and decode have been verified. External read-set return and the parent-space coordinate service are below. The full migration of the new algorithms is still not finished.

### Parent-space coordinate service

`BindingCoordinates.forMesh(input, meshId, pose)` of the GPL binding module captures, from `ModifierEvaluationInput`, the target mesh, the full ancestor chain, and the parameters the ancestors actually refer to. It does not convert other meshes or unrelated deformers. `pose` is explicit parameter values. A value that is not given uses the parameter default. The current playback frame is not read. A parent cycle, a missing parent / parameter, and invalid coordinates fail.

The canvas coordinates of `toCanvas` / `fromCanvas` are pixels, Y downward. The service handles the Y reversal of the runtime world coordinates internally. A plugin must not reverse them once more on its own. The inverse transform uses the existing runtime solver. A local seed can be passed. The result must reproject to within 0.05 pixels of the target point, or it is refused. A point array must be finite XY pairs. The input is not modified. The conversion boundary checks cancellation.

`BindingCoordinates.reparent` reuses `BindingFrames.carriedToParent`. It returns a structured mesh change, transports the default position, the keyforms, and the blend shapes, and keeps the original non-geometry properties. It does not commit a hierarchy or a project edit automatically, and it does not replace dependency validation. Nested nonlinear mesh / rotation coordinates, the Y direction, the actual read range, and the default pose / keyform position after reparenting have been checked. This service is a shared framework capability. It is not counted as the full migration of some remaining modifier.

### External read tracking and reuse

After the host declares `input_reads_v1`, a JVM worker that implements `ReadingModifierAlgorithmPlugin` can return `reads` along with `changes`. Each item is `{section, id?}`. Omitting the ID means the whole field was read. An ID means the specified object was read, including an observation of an object that does not exist. The read set is limited to 10000. A duplicate / invalid query is refused. The API's `meshIds` observes mesh membership and order on its own. It does not read their geometry and display channels. Cross-process use negotiates the `input_mesh_ids_v1` capability. A host that does not support that capability still receives the change result, but it does not receive a cache observation that contains this read key. An old host does not receive the extra field. An old plugin can still return `objects` or commands.

The host rebuilds the observed values from the input projection and the context it actually sent. It does not accept an old value provided by the plugin. A successful result is saved by package worker and instance, at most 128 items. After the algorithm description, the full instance configuration, the context, and the read values match, it tries to apply the structured changes to the current full model. When a write precondition is not satisfied, it evaluates again. Reuse still runs the output-identity, reference, range, and model-validity checks. It skips only the input binary serialization and the worker call.

The cache does not advance an input revision that has not been sent yet. The next actual request still generates the delta relative to the last sent state. When a worker exits, is disabled, or is uninstalled, the cache cannot be used to bypass the availability check. An exception and a cancel discard that worker. The `plugin worker evaluations` and `plugin read cache hits` counts are for dedicated acceptance.

The real physics plugin package has been verified: a repeated input, and adding a parameter that was not read, do not increase the worker evaluation count. After a parameter that was read is modified, it evaluates again, and the final model matches. The reopen, uninstall, and reinstall flow stays valid. This result is not proof that a full generation meets a performance target, and it does not mean the other five languages have all connected to the new read protocol.

### Host boundary for generated images

The API's `ModifierRasterOutput` describes a generated image, a mesh, and an editable path. `owner` is the captured original mesh and its prior state. `mesh` is the new mesh. `layer` is the source-image metadata. `pixels` is the immutable RGBA8 content resource. `paths` can refer only to the new mesh. The canvas position is recorded by the source-image metadata. Geometry stays in parent-local coordinates. The default UV is local pixels of the artwork. It is converted to atlas UVs only after the host assigns the atlas. `PAGE` is only for compatibility with an old output that is already bound to an atlas. Artwork pixels must not be mislabeled as that mode.

The host checks the whole batch first: the original mesh is unchanged, the output identities do not conflict, the image size matches the byte count, and the geometry and path references are valid. Each resource is at most 64 MiB. The whole batch is at most 256 MiB. It then appends, in the isolated candidate, a dedicated atlas page, the source image, and the tile record, places the new mesh before the original mesh, and adds the paths and the editable original image together. Old pages are not laid out again. A failure or a cancel does not publish the candidate. The outer CAS and the history transaction still commit it.

The existing mouth-stroke resource attachment already uses this boundary, and it keeps the original pixel and atlas behavior. API 1.9's `ModifierModelChanges.rasters` places the resource output and the ordinary object changes in the same candidate: the ordinary changes are applied first, then the resource output's `owner` is checked to match that intermediate candidate, and finally the host resource allocator is called. So if the same change modifies the original mesh, `owner` should use the mesh declared after the update. Calling `apply` directly when there is no host allocator fails explicitly. The JVM host uses `applyWithResources`. A resource write conservatively requires the `mesh`, `part`, `hierarchy`, `textures`, and `authoring` ranges.

After the host negotiates `model_changes_v2`, a change that contains resources adds a `rasters` array to the original sparse change envelope. When there are no resources, it continues to send v1. Each item strictly contains `model`, `pixels`, and `uv_space`. The first two are binary resource references `{sha256, bytes}`. The last is `RASTER_PIXELS`, or `PAGE` for compatibility. The model payload uses the RigIR binary format. It contains only the owner / new mesh in order, plus the layer metadata of the single `raster` source in `authoring.sources` and `authoring.paths`. The other model fields must be empty defaults. Pixels are an independent RGBA8 resource. A single resource is limited to 64 MiB. The whole-batch transport of the model and the pixels together is limited to 256 MiB, and at most 10000 items. A wrong hash, an extra field, a wrong payload, or a send that was not negotiated all fail.

A JVM worker encodes this result automatically. Other languages can implement the same protocol, but acceptance of image results in the six languages is not finished. The read cache keeps the change before the atlas is assigned. Each hit still runs the resource check and the assignment from the current host candidate and the captured atlas configuration. The standalone JVM package of the fitted mouth stroke already uses this contract.


### Fitted-mouth source input (in migration)

The GPL algorithm library provides `MouthSourceContext(fit, options, lineWidth)`. `encode()` returns a transportable `ModifierAlgorithmContext`. `decode(context).rig()` constructs `MouthRig` without loading a product module. The three-layer model data travels with the algorithm package. The product is responsible only for source-artwork classification and contour sampling. This is an algorithm input interface. It does not yet mean `mouth/fitted` has finished its install entry and its host wiring.

The control object strictly contains `schema: "mouth_source/1"` and `measurement: <SHA-256>`. The resource table is keyed by that digest. The resource uses big-endian Float32, in the order mouth origin / coordinate axes / width, the upper and lower contours, the optional layered frame, every mouth option, and the optional line width. Each contour is 49 scalars. The layered frame stores four groups of 65 two-dimensional contour points, the opening column and its upper and lower bounds, the optional local part bounds, and the tooth measurement. A variable column count uses a bounded Int32. An optional value and a switch use a single byte 0 / 1. The options keep the seven-point closed-mouth curve and the switches and numbers for capture, vowels, jaw, depth, spring, and tongue.

This payload contains only the source measurement and the configuration. It does not carry an evaluated pose or a full binding template. Decoding refuses an unknown schema, a missing resource or a digest that does not match, a non-finite number, an illegal length, and trailing bytes. Coordinates still use the canvas space and the local frame of the source fit. Transport does not normalize or resample the float values.


The candidate protocol `mouth-fitted/1` can refer to the `source_meshes` resource the scaffold has already captured, and it states the mapping from target meshes to source meshes explicitly. The algorithm uses the original coordinates only when the parent, the triangle indices, and the float bits of every normalized neutral coordinate all match. After the author moves vertices, changes the topology, or reparents, it recomputes from the current geometry. The old resource cannot be applied. A UV change on its own does not invalidate the original position. The algorithm outputs a typed change, and it can give the host the pre-downgrade candidate of the same evaluation, for a later binding combination. The host is still responsible for merging the author residual and for committing the transaction.
