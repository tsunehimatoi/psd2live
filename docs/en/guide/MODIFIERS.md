# Presets

A project that already has an explicit stack shows the Presets panel. An older project keeps using the previous presets panel when it is opened. Convert to Presets converts it explicitly. Ordinary materials, a basic legacy binding, and modern preset cases with several parts and add-on modules are verified today. Other projects can still be refused when the result would differ. A disabled legacy simulation is kept as a disabled instance. An enabled legacy simulation needs its existing bake to match the candidate inputs. Source-art bindings can already be added, adjusted, ordered, and applied in the new panel. Swings, physics groups, simulations, and generated motions can be added from the same entry and adjusted inside the stack. Shortcut combinations on the Start page also add explicit modifiers through an isolated conversion.

## New PSD projects

Legacy and Modern are two modifier-group presets of the same project model. They are not two project versions. Recommended presets on the Start page adds the fitted binding, add-on modules, physics, motions, and clothing simulation from the Modern group directly. The stack evaluates them together. It does not generate an old model first and then convert it. Features are no longer dropped by a “standard” module level. A failure or a cancel does not install a partial project.

## Adding and switching

1. Select meshes, or select nothing to handle every mesh. After adding, the targets are fixed and do not follow the selection.
2. Add Preset is grouped by part. The legacy and modern algorithms for the same part sit together. Clothing, front-hair, and back-hair simulations are in the matching groups. They recognize the parts and build materials, weights, and bake bindings. General generators are in the advanced group.
3. Clicking an entry only plans the dependencies and the list of additions. Confirm runs the expensive evaluation. An item that cannot stack, and that every selected target already has, is no longer shown. A disabled item still counts as present. When only some targets already have it, the existing count is shown, and only the uncovered targets are filled in. Swings, motions, and other items that may stack can still be added.
4. Switch preset chooses a modern, legacy, or custom template in the template menu, and chooses the simulation method and the module count (empty, base, minimal, standard, full). Apply replaces the whole stack. Ordinary authored content is kept. One switch records one history node, and undo restores the original stack.

Legacy uses the original base algorithms and the default dynamics. Modern uses the full modern recipe from before the refactor. Close-fitting clothing skips simulation when it does not need it, and that does not block generation of the whole group. Automatic weights are saved with a simulation instance that was added on its own. An existing authored weight of the same name wins. A whole-group switch currently refuses, clearly, when it meets a generated-content override or an applied preset capability, and it does not discard edits. Those contents have to be handled first. The count steps in the template menu filter modules only when a template is chosen explicitly. An ordinary import and the command line still initialize from the configured recipe.

The panel has two modes. Settings groups by folder, and groups by purpose by default. Folders can be added, renamed, and deleted, and modifiers and folders can be dragged to arrange them. Arranging does not change evaluation order and does not recompute the model. Order shows a flat list and uses the parameter list’s drag interaction to change the real evaluation order. An illegal dependency order is still refused. A new item brings its prerequisites with it automatically and does not reorder existing instances. The folder layout is saved with the project and supports undo and redo.

Switch preset also offers Stylized Rig · No Simulation, Stylized Rig · Full Simulation, and Classic Amplitude Rig · No Simulation. The bottom of the template menu can save the current configuration, import or export JSON, and delete the selected library preset. A save includes the modifier configuration and the folders. It does not include authored overrides on generated content or bake caches. A simulation bakes again when it is applied. User presets and built-in presets are both stored as JSON in the application preferences. When a built-in item is missing, it is restored first from the JSON shipped with the application, then read from the same path. Applying across projects locates a target by a stable object reference, or by the only object of the same name and type. When it cannot be matched uniquely, it reports an error and does not widen the scope.

Facial feature displacement on the shared structure modifier uses the existing deformation hierarchy. If the head-and-face binding comes after it, that hierarchy is still kept after the shared structure is applied.

A newly added shared structure uses version 2 and shares the parent of one target group, so each mesh does not copy a full parent chain. A later binding of a shared structure must cover the whole target set of that group. Targets under different authored parents cannot be merged into the same structure. A saved version 1 stack keeps replaying by the original object IDs. This pass does not upgrade or merge old branches automatically.

## Adjusting and locating

Click a preset in the list and adjust the full values directly on the right, including turn style, strength, and each detail. The list keeps a compact row height. The two sides scroll independently, and the divider in the middle can be dragged to change the width. Values use the inspector layout. Physics edits the current input, output, or segment. A motion edits the current track and keyframe.

Targets and Generated content provide locating the affected objects and the actual contribution. Apply through here stays in the current item’s actions.

The face has two base algorithms that exclude each other: `face/legacy` (the legacy algorithm) and `face/fitted` (the fitted turn). The same target cannot have both enabled. A fitted item reuses the existing fit algorithm inside, and provides the head-and-face parameters downstream needs. It does not add a legacy face item as well. A `face.depth-turn` record in an old project keeps replaying. The new add entry uses `face/fitted`. When adding a single item needs a head-and-face dependency, it reuses a legacy face provider already on the target. When there is no provider, it adds the fitted face by default. Choosing the legacy face, or a legacy algorithm group, explicitly still uses the legacy algorithm. An existing stack is not rewritten automatically.

In Order mode, dragging a modifier’s name changes the real evaluation order. The drag ghost and the way neighbouring rows make room are shared with the parameter panel. A move that breaks a dependency is refused, and the original stack stays. A continuous slider drag or typed value commits only one history node when it ends.

A disabled item is no longer evaluated. Downstream items that depend on it stay in the stack and show Missing dependency. Enabling the original instance again restores its overrides. Removing likewise keeps the overrides dormant, and undo can restore them. A new instance added afterward does not inherit the edits of the removed instance.

Generated meshes, parts, and deformers can be renamed in the ordinary editor, have the static appearance that applies adjusted, be reparented to another deformer, or be moved in the hierarchy. A referenced object must already exist when that item is evaluated. Renames, range changes, and default-value changes of a generated parameter are saved with the instance that provides that parameter. An adjustment that conflicts with a downstream parameter definition is refused. An edit follows the modifier that created the object. It sleeps while that modifier is disabled, and returns when it is enabled again.

Keyforms can be inserted, moved, and deleted on the object tracks a modifier generates. If a command would change tracks that belong to different instances at once, choose a specific track. Panel keys of a generated parameter are also saved with the instance that provides that parameter.

Deform tools share a correction mode. Relative, the default, stores the local change, and later adjustments of the modifier keep adding the correction on top. Fixed keeps the value of this edit, and reports a conflict when the generated result changes that value too. The choice applies the same way to brushes, vertex and transform edits, and Bezier and keyform geometry commands. History is not rewritten automatically. An explicit keyform assignment through the API still defaults to a fixed override, and can choose explicitly with `correction_mode`. After topology, UVs, or a parent binding change, a correction that cannot be matched reliably is kept and reported as a mismatch. It is not applied to other vertices. Deform mode keeps the current parameter values by default and adds keyforms as needed. With Snap to the nearest shared keyform, a multi-selection snaps by parameter together. When there is no shared key value, it asks you to choose a single track or to fill in the keyforms. That policy applies to every deform tool.

When the export format supports a runtime live simulation, an enabled simulation whose bake is valid is exported with the model, and it references the parameters and physics groups generated by that same evaluation.

### Part subsettings and physics

In the Settings list, select eyes, brows, mouth and lower face, head and face, body, or hair, then open the Adjust page on the right. Base settings holds the parameters of that part’s current base algorithm. When there is a Mode choice, the current base algorithm can be seen there. The sub-features each part offers differ. The entries the panel lists are the ones that apply.

1. Click the arrow beside a sub-feature name to expand its settings. Check the box in front of the name to enable the feature, and clear it to disable the feature. Collapsing only hides the controls. Local settings are kept after it is disabled, and can be used again when it is enabled.
2. Expand Independent targets to see that sub-feature’s own object list. When it shows Part targets, it uses the objects of the part it belongs to. The count is shown on the right of the title. Click an object name to locate it on the canvas or in the matching panel. Selecting other objects on the canvas does not change this list.
3. Adjust that feature’s values in the expanded area. For example, Mouth and lower face → Lip line can set Line width, take a six-digit RGB hex color, or click Sample edge color to return to automatic color. A color input commits on Enter or when focus leaves. A continuous slider drag or typed value records one history step when it ends, and can be undone and redone.

A sub-feature that has physics also shows a Physics checkbox, which enables or disables physics generation for that feature. The Physics row with an arrow below it expands the actual physics groups. After it is expanded, select an input, an output, or a pendulum segment, and adjust weight, scale, and each segment’s parameters. Turning the physics switch off keeps the existing local settings. If it asks you to enable the sub-feature and fill in dependencies first, handle those conditions before editing the generated physics group.

These local settings are saved to the project with the part they belong to. After adjusting, press `Ctrl+S`, and see [Save status](USER_GUIDE.md#2-save-state-and-recovery). Recovery copy saved still needs the `.psd2live` project file to be saved.

Stage in Deform mode can be automatic ownership, the base before modifiers, after some enabled modifier, or the end of the current stack. The canvas shows the shape at that stage, and picking and keyform snapping use it too. A base edit may use only the parameters that existed then. A correction for a chosen stage is saved after the matching node, and downstream continues from there. Choosing the end of the stack records the end node at the time of this edit. A modifier added later does not move the old record automatically. When a stage is unavailable, that choice is left and a notice is shown. It does not keep writing to a node that is no longer valid.

## Applying modifiers

Above the apply button, the panel first lists the items that will be materialized, the disabled items removed with the prefix, the downstream that is kept and evaluated again, and the explicit dependencies that cross the apply boundary. Hand edits list a merge count and a dormant count separately. Choose Apply selected modifier or Apply through here. After the selected item is materialized, it keeps its original evaluation position, and upstream and downstream keep running in the original order. It is not placed into the base early and then run through upstream again. An incompatible change to an upstream input is refused. The apply has to be undone, or the dependency applied with it. Any enabled item that has a failure, a missing dependency, or an orphaned correction blocks apply, including retained downstream. A background commit still rechecks the full result. The plan in the interface does not stand in for the commit check. A conflict from an old-style fixed override still keeps the hand value. After the interface says so, applying the current result is allowed.

Apply through here materializes the current item and the valid results before it as ordinary editable content, and removes the whole prefix. Disabled items are removed with the prefix and do not take part in the current evaluation. Saved disabled motions and physics groups are still kept as ordinary content that can be enabled again. Later items keep their instances and object references. The full result before and after apply must agree.

A physics group becomes an ordinary physics configuration. A generated motion becomes an ordinary clip (the file name, the export group, and the runtime’s default fade in and fade out are kept). A simulation materializes the bindings it has already generated. It does not record the frame currently playing. A missing dependency, an override that cannot be matched, or an invalid bake blocks apply. A failure does not leave a partial result. Undo restores the original stack.

An eye modifier can also add widen, eyelid-line fade, and highlight parallax. Widen explicitly extends the open-eye range to 2, and the contribution list shows the parameter change. The plan for adding highlights includes the head-and-face binding dependency. A keyform at a newly added stop shows its coordinates, so its source can be told apart.

Bangs see-through for the eyes and for the brows can be added and have its opacity adjusted separately. The contribution list shows the generated copy meshes, the hierarchy, and the mask relationships.

Switch arrangement adds parameters and opacity keyforms for toggles and variant layers in the targets. When a variant switches, the new layer fades in first, and the old layer fades out afterward. Toggles and variants can also drive a swing chain that has already been added. The contribution list names the physics groups that are affected.

Lip outline generates upper and lower lip meshes, and a texture for each, for mouth materials it applies to. Line width can be adjusted in the modifier, an RGB color can be entered, or automatic color restored. After apply, the meshes and textures are saved with the project.

## Native generators

A swing can adjust the pivot, the offset, the axes, the segments, the shape, and the physics that comes with it. A physics group can adjust parameter inputs and outputs, each segment, and normalization. A generated motion uses the existing algorithms and adds only the tracks the current parameters can support. Choose a preset in the popup menu. Once it is in the stack, duration, loop, fade in and fade out, tracks, and keyframes can be adjusted. Values are edited in the preset adjustment area after adding.

A physics group needs output parameters that already exist and are usable, and input parameters that differ from them. When no suitable parameter exists, add a binding or an ordinary parameter first. An output write conflict blocks the add. It does not replace an existing physics group. A simulation bakes the real stack prefix in the background, and does not use the frame currently playing. Material, inputs, mode count, key count, and exaggeration can be adjusted, a blend-shape output mode can be chosen, and static input axes can be added or removed. Pin, stiffness, shape, mass, damping, and wind can choose a named vertex group on the targets. By default each target’s first group of that kind is read. A collider can choose a mesh that is not a simulation target, set vertices A and B, the radius at each end, and friction, or be removed. Two equal endpoints mean a circle. Different endpoints mean a capsule. Vertex indices start at 0. A training clip can be an existing ordinary motion or a preceding motion in the stack, and its weight can be adjusted or it can be removed. When a referenced clip is missing, the simulation is kept and evaluation is suspended. Moving the simulation before the motion that provides the clip is refused. With automatic baking on, an upstream edit refreshes the result inside the same transaction. With it off, a stale result blocks the commit. An input without enough motion is refused. Check Keep when a small input needs to be kept on purpose.

Blink aftershock and brow spring add physics groups together with the binding. Expand Physics inside the modifier to adjust inputs and outputs, segments, and normalization. The values are stored in that instance. Different targets can share a compatible standard physics group. The reuse list shows where it comes from, and the name keeps the earlier item. Changing a physics value so it is no longer compatible with the parties that share it refuses the commit. The other sharing parties have to be disabled first, then each item adjusted until they agree. After it is applied, the result is an ordinary physics configuration that keeps those values.

The mouth can also add mouth capture, tongue out, jaw follow, mouth depth, and mouth spring. The add plan lists the prerequisites it needs. Blush and gloom add color channels, and can be combined with mouth shapes. Edits of color keyforms belong to the instance too. They sleep after it is disabled, and take effect again after the original instance is restored.

Cheek v4 (`expression.cheek@4`) is a source-input candidate for explicit choice only. It supports a full open mouth whose eye, brow, and lashes on the same side are all present, and preset skin that is unedited and unsplit. Prerequisite versions must match the source chain listed in [Algorithm plugins](ALGORITHM_PLUGINS.md), and both emotion parameters must be unused. The separately compiled and frozen `skinReplayV1` helper rebuilds the motion from source measurements, checks the existing skin and carrier exactly, and only then adds the warm color. When a dense detail mesh cannot reproduce the previous state exactly, it is refused. Agreement is not obtained by lowering a prerequisite version. The existing defaults and the project’s version locks stay as they are. Gloom v4 still requires cheek v1. This candidate does not mean the whole preset chain has been migrated on its own.

The Physics panel shows the groups the stack actually evaluates, with the source marked Preset. Adjust a generated group inside the modifier it belongs to. Open Presets returns to that panel. The order of generated groups is decided by the modifier stack. After they are applied, they become custom configurations that can be edited, disabled, and reordered in the ordinary way.

Skin clipping adds face masks for blush, skin light and dark, and bangs shadows. Neck follow tilts the neck with the head and clips the neck shadow. The add plan includes a fixed head-and-face binding prerequisite. Both reuse existing materials. The contribution area shows the mask’s source and invert state before and after the add. Click an object or a source to locate it.

Neck follow v4 is a source-input candidate version for explicit choice only. The worker rebuilds ordinary neck tilt and shadow turn motion from the current prerequisite configuration. It currently requires the prerequisite package bundled now, and supports only a neck mesh parented directly under the shared body / breath branch, not split left and right, whose source UVs and topology are unchanged. An old prerequisite-package digest, a paired neck, a custom parent wrapper, and a case that needs a new independent turn carrier are refused. The existing neck versions, the preset choice, and saved v1–v3 package locks stay as they are.

Hair can choose the chain-segment base algorithm, which excludes the legacy hair sway on the same target. A skirt hem, ribbons and pendants, animal ear / tail / wing chains, and bust and arm follow can be added on their own. The add plan lists the body and head-and-face bindings it needs. A chain’s swing amount, hair stiffness, and the actual physics group are adjusted inside the item they belong to. Changing the order of other items does not change these chains’ object references.

The fitted face is itself the head-and-face base binding. Adjust the turn amount, the depth, and the styling inside that item. Choosing a new styling restores that item’s other values to their defaults. Side hair that qualifies turns behind the face on a large head turn.

When adding physics, the front-hair, back-hair, and eye-jelly presets can be chosen. When a required parameter is missing, the add plan lists the base bindings that need to be added at the same time. When adding a motion, the original or natural version of idle, blink, nod, and shake can be chosen, or natural speech. When a natural motion is chosen, the add plan fills in missing base bindings. Editing values before confirm keeps the prerequisites in the plan. After the add is confirmed, physics rules and motion tracks can both be edited inside the matching instance.

## Shared with MCP

`modifier_apply_plan` accepts `id` and `scope` (`selected` is the selected items, `prefix` is the prefix through here, and the default is `prefix`). It returns the captured `state`, the apply range, the disabled items, the retained items, the dependencies that cross the boundary, and the reasons that block it. It does not change the project. After the range is confirmed, call `modifier_apply` with the same `scope` and that `state`. `can_apply` in the plan only says the captured report has no known blocker. The final materialize still needs a full evaluation and a consistency check.

`modifier_catalog` provides the algorithm catalog. `modifier_stack` provides the captured version’s state and actual contributions. `modifier_plan` plans source-art bindings and their prerequisites, and also supports native configuration of swings, physics groups, simulations, and generated motions. Hand its `group` and `entries` to `workspace_preview_regeneration` first, then submit `modifier_add_group` with the same `state`, and the GUI’s add flow is reproduced. See [MCP API](../agent/MCP_AUTHORING.md).

The blink-motion modifier also contributes the EyeBlink runtime parameter role, which is shown in the relation list. After the modifier is applied, that role is materialized as ordinary model metadata and saved with the project.

Applying a motion modifier keeps the original clip’s file name and curve control points. Adjusting a parameter range afterward retimes an ordinary motion to the new range. Saving, reopening, or rebuilding alone does not change the curves.

A motion track can be expanded inside the stack to edit key time, value, interpolation, and the Bezier in / out handles. Event groups support add, edit time and contents, and delete. After apply they remain ordinary motion clips.

## New projects that are not PSDs

A blank Layout and a Layout manifest import use an empty preset stack. Materials can still be edited in the ordinary way. The first generation of an empty stack uses the full modern baseline. Generating new materials after presets already exist still fills in bindings by the selected compatible group, and the existing presets stay. `rig_generate.preset_group` in MCP can be one of six groups or `none` (ordinary meshes are kept). A new project from source-art data uses the recommended group. An old project still keeps the old generation path.

A new project from a CMO3 uses an empty preset stack. The imported model and physics configuration are kept as ordinary authored content.

Installing, uninstalling, and adding languages for algorithms are in [Algorithm plugins](ALGORITHM_PLUGINS.md).
